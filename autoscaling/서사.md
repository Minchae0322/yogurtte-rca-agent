# 포트폴리오 서사 설계 - 정적 배치의 한계를 측정하고, 서비스 특성에 맞는 스케일링 전략을 설계하다

> 제목부터 "오토스케일링 개선기"가 아니다. 실제로 해결하는 것이 서로 다른 병목에
> 서로 다른 전략을 붙이는 일이기 때문이다:
> **CPU 문제 → HPA · Node capacity 문제 → Node scaling · Kafka backlog 문제 → KEDA ·
> WebSocket state 문제 → Redis Pub/Sub**
>
> 마지막 메시지: **"하나의 오토스케일링 전략으로 전체 시스템을 해결하지 않았다."**

---

## 서사의 뼈대 - 의사결정 트리를 먼저 만들고, 실험 결과가 가지를 고른다

기존 서사의 약점: "A 발생 → A 해결 → B 발생 → B 해결" 구조는 B가 실제로 안 나오면
뒤의 기술이 등장할 이유가 사라진다. 그래서 **각 단계에 Plan A/B를 사전에 세우고,
측정 결과가 어느 경로로 갈지를 결정하게 한다.** 실험 결과가 예상과 달라도 서사가
무너지지 않는다 - 포트폴리오를 완성하고 데이터를 끼워 넣는 게 아니라, 트리를 먼저
만들고 결과에 따라 가지를 선택한다.

```
                 현재 구조 (정적 비대칭 배치)
                        │
                 [부하 특성 측정]
                        │
          ┌─────────────┴─────────────┐
     자원 병목인가?                이벤트 적체인가?
          │ YES                       │ YES
         HPA                         KEDA
          │                           │
      Node 부족?                   lag 해소?
       /      \                    /      \
     YES       NO                YES       NO
      │         │                 │         │
   Node 증설    끝                끝     다른 지표
      │
   재검증
      │
  WebSocket은? ── 상태 공유 문제? ── YES → Redis Pub/Sub
                        │
                        NO → 끝
```

### 사전 선언 - Plan A / Plan B 표 (이 표가 핵심 장치다)

시작 시점에 이렇게 선언한다:

> 현재 클러스터는 제한된 자원에서 트래픽 특성을 기준으로 content 2 · auth 1 · chat 1
> replica로 비대칭 배치되어 있다. 하지만 이 배치가 실제 부하에서도 적절한지는 검증되지
> 않았다. 따라서 오토스케일링을 바로 적용하지 않고, 먼저 부하테스트로 **병목의 종류와
> 위치**를 식별한 뒤 그 결과에 따라 전략을 선택하기로 했다.

| 발견할 수 있는 문제 | Plan A | Plan B |
|---|---|---|
| Pod CPU 포화 | HPA | VPA / 구조 개선 |
| Pod 증가 후 Pending | Node 증설 | requests 재조정 |
| CPU 정상 + Kafka lag 증가 | KEDA | consumer 처리량 개선 |
| WebSocket scale-out 문제 | Redis Pub/Sub | sticky session / 별도 브로커 |
| DB connection 포화 | connection pool 조정 | DB/쿼리 최적화 |
| scale-out 후 cold start | minReplica 증가 | JVM/startup 최적화 |

### 서술 규율

1. **실측만 확정 서술.** 안 돌린 실험은 가설 + Decision Gate + `[실측 예정]`.
2. **Decision Gate(성공/실패 조건)를 실험 전에 정의한다.** 어느 쪽이 나와도 문장이 준비돼
   있다 - "Pending이 나왔다 → capacity가 두 번째 병목" / "안 나왔다 → Node 증설 불필요 확인".
3. 모든 챕터는 같은 구조: Question → Hypothesis → Experiment → **Finding(가장 크게)** →
   Decision → Re-test.
4. 기술 목록을 강조하지 않는다. *"Pod를 늘리면 해결되는 문제와, Pod를 늘리기 때문에
   생기는 문제를 부하테스트로 구분했다"* 가 강한 문장이다.
5. 이 방식은 RCA-Agent 트랙의 "관측 → 가설 → 검증 → 다음 문제 정의" 방법론과 같은
   틀이다 - 두 포트폴리오가 하나의 사고방식으로 묶인다.

## Chapter 0. 왜 지금 구조를 이렇게 설계했는가 [완료]

개선 없이 Baseline만 정의한다.

```
                CloudFront (yogurtte.com — HTTP + WSS 단일 진입)
                    │
                Ingress (edge 노드 DaemonSet)
                    │
    ┌───────────────┼───────────────┐
    ↓               ↓               ↓
  auth           content           chat
  1 pod           2 pods           1 pod
                                    │
                               WebSocket (STOMP)
```

| 서비스 | 예상 트래픽 | Replica | 상태 |
|---|---|---:|---|
| content | 80% | 2 (podAntiAffinity 분산) | Stateless |
| auth | 15% | 1 | Stateless |
| chat | 5% | 1 | **Stateful connection** |
| Kafka consumer (chat) | 이벤트 처리 | 1 | Consumer |

**첫 번째 설계 가설:** 전체 요청의 약 80%가 content로 발생할 것으로 예상해 content에만
replica를 추가했다. 제한된 노드 자원(t3.micro~medium 4노드)에서 모든 서비스를 동일하게
이중화하기보다 예상 트래픽에 따라 자원을 비대칭적으로 배치했다.

## Chapter 1. 먼저 병목을 찾았다 [서비스별 실측 완료 · 혼합 breaking point 실측 예정]

- **Question**: ~~"몇 명까지 버티나?"~~ → **"요청량이 증가했을 때 가장 먼저 제한되는
  자원은 무엇인가?"** 숫자는 입력이 아니라 발견이다.
- **Hypothesis**: 트래픽 80%를 받는 content가 가장 먼저 병목이 될 것이다.
- **Experiment**: 100 → 300 → 600 → 1,000 VU 계단, 실제 비율 혼합(content 80/auth 15/chat 5).
  측정 축: p50·p95·p99 · error rate · Pod CPU/mem · Node CPU/mem · DB connections ·
  Kafka lag · WS connections - 클라이언트(k6)와 서버(Mimir)를 같은 시각에 쌍으로.
- **사전 정의한 경우의 수** (결과를 미리 정하지 않는 장치):

  | Case | 신호 | Decision |
  |---|---|---|
  | A | content CPU 포화 + p99 급증, DB·Node 정상 | HPA |
  | B | content CPU 여유 + DB connection 100% | HPA 아님 - pool/쿼리 문제 |
  | C | Pod CPU 여유 + Node CPU 포화 | Pod보다 노드가 먼저 문제 |
  | D | 모든 자원 정상 + p99 급증 | 네트워크/락/외부 의존 추가 조사 |

- **Finding (서비스별 개별 시험 실측, [실행 1회차](loadtest/results/2026-08-16-실행-1회차.md)):**

  **초기 가설은 절반만 맞았다. 첫 병목은 content가 아니라 auth였고, 서비스마다
  무너지는 방식이 전부 달랐다.**

  | 서비스 | 실측 | Case 판정 |
  |---|---|---|
  | auth (300 VU) | p99 49.4s · 실패 29.75% · **CPU 100%(BCrypt) + 풀 pending 190** | A+B 복합 - 요청량이 아니라 **요청당 CPU 비용**이 문제, replica만으론 부족 |
  | content (500 VU) | p99 4.5~4.9s · 실패 0% · CPU 99% · 풀 정상 | 정확히 Case A - HPA 후보 |
  | chat (200 WS) | 연결 100% · 브로드캐스트 이론치의 7% · CPU 천장 | 제3의 유형 - 자원 추가 전에 구조 문제 의심 |
  | 리액션 (200 VU) | 한 피드 집중 시 p99 8.8s, 분산 시 2.9s (대조군) | 정확히 Case D - **락**이었다. 스케일링으로 안 풀리는 병목의 실증 |

  Case 표를 미리 만들어놨기에 네 결과가 전부 자리를 찾는다 - 이것이 이 장치의 힘이다.
- **남은 실험**: 혼합 비율 breaking point (스크립트 신규 · ingress 직결 경로 필요 -
  CloudFront 경유는 CF 타임아웃이 한계를 오염). `[실측 예정]`
- **주의**: t3 CPU 크레딧 - 시험 전 CPUCreditBalance 확인, 10~15분 단위. 크레딧 고갈을
  한계로 착각하면 결론이 오염된다.

## Chapter 2. Pod를 늘리면 해결되는가? - HPA와 Decision Gate [실측 예정]

> **개선 문서: [개선/cpu개선.md](개선/cpu개선.md)** - 이 Chapter의 변경 SoT(CPU-1~CPU-5 · 검증 순서 · 반증 조건).
>
> **Decision Gate에 가지 하나가 빠져 있다 (T2-B 소급 관측, 2026-08-19).** 아래 게이트는 Pending을
> 물리적 실패의 신호로 잡는데, **CPU 경로에서는 Pending이 안 난다.** content requests는 0.3인데
> 실사용이 1.49다(5배 오버커밋). 스케줄러는 requests만 보고 3번째 replica를 태연히 앉히고,
> 그 다음 셋이 노드 CPU를 나눠 쓰며 전부 스로틀된다 - **Pending 없이 처리량만 안 오르는 조용한 실패**다.
> (실측: content limit 1.5 × 2 = 3.0 vs 워커 총 capacity 4.0 − 시스템 0.4~0.7 → 3번째가 쓸 CPU가 없다.)
>
> 따라서 게이트는 세 갈래가 된다: **① Pod 정상 + 처리량 증가** = 성공 · **② Pod Pending** = 아래 그림
> (메모리 경로. requests 1Gi라 여전히 유효) · **③ Pod 정상인데 처리량 미증가** = CPU 스로틀.
> ③의 증거물은 `kubectl describe`의 Insufficient가 아니라 **CFS 스로틀 비율과 파드별 CPU**다
> (`rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])`).
> **그래서 requests/limits 재설정(CPU-2)이 HPA(CPU-5)보다 먼저다.**

정적 배치의 한계를 먼저 논증한다 (실측 인용):

| 구성 | 평시 (실측: 8.9rps 전부 100ms대) | 스파이크 (실측: 위 표) |
|---|---|---|
| 고정 2 replica | 충분 | 부족 |
| 고정 4 replica | 자원 낭비 (평시 CPU 한 자릿수 %) | 감당 가능(추정) |

어떤 고정값도 양쪽을 만족하지 못한다 → 동적 배치가 논리적으로 도출된다.

- **Action**: JVM 다이어트 → 실측 기반 requests/limits → HPA (변경군 분리, 각각 전후 측정).
- **Decision Gate (실험 전 정의):**

  ```
  HPA scale-out
        │
        ├─ Pod 정상 생성 → 성공. "추가 replica가 정상 스케줄링되어 Node 증설은 불필요했다"
        │
        └─ Pod Pending → "논리적 스케일링은 성공, 물리적 스케일링은 실패"
                │
           ┌────┴────┐
        Node 증설   requests 재조정
  ```

  Pending 가설의 근거: 노드 3대가 이미 메모리 70%대(실측), content requests 1Gi.
  증거물은 `kubectl describe pod`의 "Insufficient memory" - 이벤트가 빨리 사라지니
  시험 전 `kubectl get events -w`를 걸어둔다.
- **Node 증설 시**: headroom 용도 t3.small 1대 - "평시 파드는 기존 노드, 스파이크 시
  새 파드가 추가 노드로". Re-test에서 replica 2→N→2 증감 시계열이 증거물.

## Chapter 3. CPU가 workload를 제대로 설명하는가? - KEDA는 대안 가설 [실측 예정]

- **Question**: HTTP 요청량과 이벤트 처리량은 **동일한 지표**로 스케일링할 수 있는가?
- **Hypothesis**: consumer가 I/O 대기 구간이면 CPU는 infrastructure utilization일 뿐,
  Kafka lag(아직 처리되지 않은 workload 자체)과 괴리될 가능성이 있다.
- **Experiment**: 동일한 이벤트 부하에서 consumer CPU와 `kafka_consumergroup_lag` 동시 측정
  (lag 지표는 Mimir에 이미 존재 - RCA 트랙 사용 중).
- **Decision Gate:**
  - CPU 낮음 + lag 증가 실측 → "CPU 기반 HPA의 사각지대" → KEDA, lag 회복시간 비교로 검증
  - CPU와 lag이 같이 움직임 → KEDA를 사각지대 서사로 쓰지 않고 **"CPU와 lag 중 어느
    지표가 더 적합한지 비교한 실험"**으로 기록 (HPA 유지도 유효한 결론)
- 근거 프레임: HPA는 resource utilization 기반, KEDA는 event 기반 scaling - 지표별
  역할 분리가 결론의 형태다.

## Chapter 4. 모든 서비스를 동일하게 확장할 수 있는가? - Chat [가설 · 재현 예정]

이 질문 하나로 앞의 챕터들과 급이 갈린다. 앞은 전부 "Pod를 늘리면 된다"였지만,
여기서는 **Pod를 늘리는 것 자체가 문제를 만든다.**

- **Hypothesis**: auth·content는 stateless라 scale-out이 그대로 통하지만, chat은
  WebSocket 연결 상태가 파드에 귀속되어 있어 replica 2가 되는 순간 서로 다른 파드의
  사용자 간 메시지가 전달되지 않을 것이다.

  ```
  User A ──→ Pod A ── 로컬 브로드캐스트만
                 X
  User B ──→ Pod B      (User B 못 받음)
  ```

- **Experiment**: chat replica 2로 늘리고 두 사용자를 의도적으로 다른 파드에 붙인 뒤
  (파드 로그로 확인) 교차 전달 여부 확인. **재현 로그가 나오기 전에는 "유실된다"고
  쓰지 않는다.** `[재현 예정]`
- **Plan A/B/C (재현되면):**

  | Plan | 방식 | 판단 기준 |
  |---|---|---|
  | A | sticky session | 같은 사용자를 같은 파드로 - 그러나 **다른 파드 사용자 간 대화**는 못 푼다 |
  | B | Redis Pub/Sub | 파드 간 메시지 중계 - 저지연, 이미 Redis 보유 |
  | C | 별도 메시지 브로커 | 과설계 여부 검토 |

  검증해서 선택한다. 결론의 형태: *"stateless 서비스와 stateful connection 서비스의
  스케일링 전략을 분리했다."*
- **역할 분리 표** (선택 후):

  | 목적 | 기술 | 이유 |
  |---|---|---|
  | 채팅 실시간 fan-out | Redis Pub/Sub | 저지연 전달 |
  | 이벤트 스트리밍 | Kafka | 영속성 · 소비자 분리 |
  | WebSocket 연결 | Chat Pod | 연결 상태 유지 |

  주의: "Pub/Sub은 유실 허용" 같은 표현은 실제 영속화 경로(현 구조: 메시지는 Kafka →
  Mongo 저장, 전달만 브로커)를 확인한 뒤에 쓴다.
- **선행 정리**: 공유 Redis의 chat 세션 KEYS O(N) 결함([sample-review-report](../docs/sample-review-report.md)) -
  pub/sub을 얹기 전에 정리하지 않으면 스케일아웃할수록 Redis가 병목이 된다.
- **이미 있는 단서 [실측]**: 1 replica에서도 브로드캐스트가 이론치의 7%(chat CPU 천장).
  scale-out은 전달 구조를 풀기 전에 CPU 문제로도 이미 필요하다.

## Chapter 5. 최종 설계 - 여기서 비로소 전체 그림을 보여준다

```
                     Traffic
                        │
                    CloudFront
                        │
                     Ingress
                        │
        ┌───────────────┼────────────────┐
        │               │                │
       Auth           Content           Chat
        │               │                │
       HPA             HPA         HPA + Redis Pub/Sub
        │               │                │
        └───────────────┼────────────────┘
                        │
                      Kafka
                        │
                     KEDA Scaler
                        │
                     Consumer
```

핵심 메시지: **하나의 오토스케일링 전략으로 전체 시스템을 해결하지 않았다.**
병목을 찾아간 순서(HTTP 요청량 → CPU → Node capacity → Kafka lag → WebSocket state)가
곧 전략이 분화된 순서다.
