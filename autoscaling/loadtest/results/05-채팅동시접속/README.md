## 사전 검증에서 확인한 제약

T1에서 메시지가 조용히 버려진 원인(방 부재)을 해소하려 실제 방을 만들며 확인된 것:

1. **NORMAL 방은 참여자 1명(1:1)만 허용** (`ChatRoomCreateValidator`). 50명 방은 CHANNEL
   타입이어야 하는데 STOMP 핸들러가 `ChatRoomType.NORMAL` 하드코딩 - 시험은 1:1 방
   (load1-load2, roomId `6a8183c7d2c54bf44544e516`)으로 진행.
2. **방 생성 API가 hidden 필드 `creatorId`를 body에 요구** - `@Valid`가 principal 주입보다
   먼저 돌아서.
3. **WS 구독·전송에 멤버십 검증이 없다** - 비참여자(load3)가 남의 1:1 방을 SUBSCRIBE·SEND
   해도 저장·브로드캐스트 성립 (단건 실측). REST 조회는 `validateUserAccess`로 막혀 있어
   **WS 경로만 뚫린 접근제어 결함.**

단건 검증: 실제 방으로 SEND → MESSAGE 수신 성립 (참여자·비참여자 모두). T1의 "수신 0건"은
방 부재로 **확정** (가설→실측 승격).

- **Experiment**: 6분(램프 2m + 유지 3m + 종료 1m) · WS 세션 999개 · 토큰 풀 50 ·
  실제 방 대상. STOMP CONNECT → SUBSCRIBE → 5초마다 SEND (Kafka → Mongo 저장 →

## 재실행 (2026-08-23 밤 · 2차 diet 구성 · nginx 직결) - 같은 CPU 포화에서 수신이 11.5배 - CF가 팬아웃 출력을 조르고 있었다

> **결론:** 연결 100%(899/899·1차 99.7%) · 송신 13,617건(동등)에 **수신 1,716,858건 -
> 1차 149,650의 11.5배**다. chat CPU는 이번에도 988m(limit 1.0) 포화로 1차와 같은데
> 출력만 11.5배 - **1차의 "팬아웃 이론치 7%" 판정에는 CloudFront 경유라는 관측 병목이
> 섞여 있었다**는 뜻이다. 직결 실측으로 수신/송신 배율은 8.7 → **126배**(이론 200배의
> 63%)로 정정된다.

### 조건

200 WS 세션·6분·5초 간격 SEND·실제 방 - 1차와 동일. 구성 diet · nginx 직결(ws://).

### 핵심 결과 (1차 → 2차)

| 항목 | 1차 (CF) | **2차 (직결)** |
|---|---|---|
| ws 101 / STOMP CONNECTED | 100% / 99.7% | **100% / 100%** (899/899) |
| ws_connecting med | - (p99 632ms) | **28.9ms** |
| 송신 | 17,110 (35.3/s) | 13,617 |

| chat CPU | 0.999 포화 (소급) | **988m = limit 1.0 포화** (ktop) |

### 판정 - 1차 결론의 절반이 정정된다

1. 1차 가설 ①(브로커 아웃바운드 포화)은 **부분 정정**: 내보낼 CPU가 없어서가 아니라,
   상당 부분이 **CF 경유 WS 스트림의 전송 병목**이었다. 같은 CPU 포화에서 경로만 바꿔
   출력이 11.5배 나온 것이 증거.
2. 그래도 이론(200배)의 63%에서 멈춘 것은 여전히 chat CPU 포화의 몫 - "메시지 팬아웃이
   chat의 병목"이라는 큰 결론은 유지된다.
3. **부수 관측(사건 씨앗 1)**: 시험 구간에 chat 워킹셋이 611 → 695Mi로 **+84Mi 계단 상승
   후 반납되지 않음** (ktop 실측). WS 세션 버퍼류 off-heap으로 추정 - [12-메시지처리량
   재실행](../12-메시지처리량/README.md)의 노드 사망 사건으로 이어지는 첫 번째 계단이다.
