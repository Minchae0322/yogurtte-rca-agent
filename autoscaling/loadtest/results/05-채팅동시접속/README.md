# T2-C 채팅 동시접속 테스트

> **결론:** chat 1 replica는 연결 200개를 여유롭게 받지만 **팬아웃 출력에서 CPU가 포화한다.**
> 실측 천장은 약 4,500 msg/s(전 구간 평균)이고, 200명 방 하나가 요구하는 약 7,000 msg/s에 미달한다.
> 1차에 기록한 "이론의 7%"는 서버 성적이 아니라 **CloudFront가 만든 관측 병목**이었다 -
> 경로만 직결로 바꾸자 같은 CPU 포화에서 출력이 11.5배 나왔다.
>
> **다만 이 시험은 설계가 무효에 가깝다 (2026-08-24 코드 감사, [§4](#4-설계-결함---이-시험은-프로덕션에-없는-상태를-쟀다-2026-08-24-코드-감사)).**
> 1:1 방 하나를 200 세션이 구독하는 상태는 **WS 멤버십 검증 결함을 뚫어야만 성립**하고,
> 그 탓에 Kafka 파티션도 하나로 몰려 **팬아웃 컨슈머 병렬성이 1**이었다. 둘 다 프로덕션에 없는 조건이다.
> "CPU 포화" 판정도 상류를 못 짚었다 - 그 CPU를 팬아웃이 먹었는지 세 컨슈머가 먹었는지 안 갈렸다.

| 구분 | 내용 |
|---|---|
| 상태 | 1차 2026-08-16 · 2차(재실행) 2026-08-23 · **설계 결함 확인 2026-08-24** |
| 자원 기준 | chat 1 replica · CPU limit 1.0 · 단일 방 |
| 부하 | 200 WS 세션 · 6분 · 유입 약 40 msg/s → **출력 요구 약 8,000 msg/s** |
| 판정 | 연결 통과 · 팬아웃 미달 · **원인 미확정 (설계 재실행 필요)** |

서사상 위치는 [Chapter 1](../../../서사.md)의 제3 유형이자 [Chapter 4](../../../서사.md)의
chat scale-out 검증을 시작하게 만든 근거다.

## 0. 기준 - 왜 이 숫자로 쟀나

부하시험에서 제일 먼저 무너지는 건 숫자가 아니라 **그 숫자를 고른 이유**다.
아래 값들은 각각 어디서 나왔는지를 함께 적는다. 근거가 없는 값은 **"근거 없음"** 이라고 쓴다.

| 값 | 왜 이 값인가 | 근거 등급 |
|---|---|---|
| **VU 200** | 목표 규모가 아니라 **탐색 시작점**. chat 1 replica(CPU limit 1.0)의 WS 천장이 미지수여서 200에서 시작해 T3-J에서 1,000까지 계단으로 올려 한계를 찾는 설계 | 배포 스펙 + 후속 실측 |
| **5초 간격** | 발화율 가정이 아니라 **유입률 손잡이**(`MSG_INTERVAL_MS`). T2-C(5초) · [WS-B](../12-메시지처리량/README.md)(단축) · [T3-J](../09-WS연결폭주/README.md)(전송 없음)를 "출력 msg/s" 한 축에 올리려고 고정 | 시험 간 대조 설계 |
| **단일 방 · 팬아웃 200** | 부하의 실체가 유입이 아니라 **출력**이기 때문. 방을 쪼개면 같은 VU에서도 출력이 1/N로 떨어져 다른 시험이 된다 (`ROOM_COUNT`가 그 대조군) | 측정 대상 정의 |
| **6분 (램프 2 / 유지 3 / 종료 1)** | 유지 3분 = Prometheus scrape 15초 × **표본 12개**. p99를 말하려면 이 정도는 필요하다. 램프 2분은 JVM·커넥션풀 예열. 누수는 T3-I soak가 따로 본다 | 관측 주기 |
| **세션 60초 후 재접속** | 연결 유지 부하는 T3-J의 소관. 여기선 **접속·구독·전송이 반복되는 상태**를 유지하려는 것 | 시험 분리 |
| **토큰 풀 50** | 로그인(BCrypt) 비용을 chat 측정에서 빼려고 `setup()`에서 미리 받는다. 그 비용은 T2-A가 따로 잰다 | 시험 분리 |

### 부하의 단위는 VU가 아니라 출력 msg/s다

WS 팬아웃에서 VU 수는 부하 크기를 설명하지 못한다. 같은 200 VU라도 방을 10개로 쪼개면 서버 일은 1/10이다.

```
유입  200 세션 / 5초        =    40 msg/s   (하찮다)
출력  40 × 구독자 200       = 8,000 msg/s   (이것이 부하다)
```

**그래서 이 시험의 캐파 단위는 "초당 outbound 메시지 수"로 잡는다.**

### 합격선 (SLO)

| 항목 | 기준 | 왜 이 기준인가 |
|---|---|---|
| WS 핸드셰이크 · STOMP CONNECTED | `checks rate > 0.99` | 연결은 되거나 안 되거나다. 관행 기준 |
| 접속 지연 | `ws_connecting p(99) < 1000ms` | 채팅 진입 체감 한계. 관행 기준 |
| **배달 지연** | **`ws_delivery_latency p(99) < 1000ms`** | **사용자가 체감하는 유일한 값.** SEND 시각을 본문에 실어 다른 세션이 받은 시각과의 차로 잰다 |

**배달률(수신/이론)은 합격선으로 삼지 않는다.** 이유가 둘이다.

1. 채팅에서 메시지 유실은 성능 미달이 아니라 **결함**이다. 목표는 100%이지 "80% 이상 통과"가 아니다.
2. 애초에 **유실인지 k6 수신 한계인지 아직 분리되지 않았다** (1차 가설 ③). 2차에서 경로만 바꿔
   출력이 11.5배 나온 것 자체가 "못 받던 쪽"이 병목이었다는 증거다.
   **원인이 갈리지 않은 지표에 합격선을 걸 수 없다.**

배달률은 합격선이 아니라 **캐파 관측치**로만 인용한다.

> **주의 - 이 기준은 사후 정의다.** 1차·2차는 배달 지연을 재지 않은 채 돌았고, 위 SLO는 그 결과를 보고 정리한 것이다.
> [`c-chat-ws.js`](../../c-chat-ws.js)에 `ws_delivery_latency`를 박아 두었으므로 **다음 회차부터 사전 박제 기준으로 적용**한다.
> 결과를 보고 정한 기준은 근거가 아니라 결과 맞춤이므로, 1차·2차 판정에 소급하지 않는다.

## 1. 사전 검증에서 확인한 제약

T1에서 메시지가 조용히 버려진 원인(방 부재)을 해소하려 실제 방을 만들며 확인된 것:

1. **NORMAL 방은 참여자 1명(1:1)만 허용** (`ChatRoomCreateValidator`). 50명 방은 CHANNEL
   타입이어야 하는데 STOMP 핸들러가 `ChatRoomType.NORMAL` 하드코딩 - 시험은 1:1 방
   (load1-load2, roomId `6a8183c7d2c54bf44544e516`)으로 진행.
2. **방 생성 API가 hidden 필드 `creatorId`를 body에 요구** - `@Valid`가 principal 주입보다
   먼저 돌아서.
3. **WS 구독·전송에 멤버십 검증이 없다** - 비참여자(load3)가 남의 1:1 방을 SUBSCRIBE·SEND
   해도 저장·브로드캐스트 성립 (단건 실측). REST 조회는 `validateUserAccess`로 막혀 있어
   **WS 경로만 뚫린 접근제어 결함.**

단건 검증: 실제 방으로 SEND → MESSAGE 수신 성립 (참여자·비참여자 모두). T1의 "수신 0건"은
방 부재로 **확정** (가설→실측 승격).

## 3. 2차 재실행 (2026-08-23 · diet 구성 · nginx 직결) - 같은 CPU 포화에서 출력 11.5배

> **결론:** 같은 200 세션·같은 CPU 포화(988m / limit 1.0)인데 **수신이 11.5배**다.
> 1차의 "이론의 7%"에는 **CloudFront 경유라는 관측 병목**이 섞여 있었다.

### 조건

200 WS 세션 · 6분 · 5초 간격 SEND · 실제 방 - 1차와 동일. 구성 diet · nginx 직결(ws://).

### 핵심 결과 (1차 → 2차)

| 항목 | 1차 (CF) | **2차 (직결)** |
|---|---|---|
| ws 101 / STOMP CONNECTED | 100% / 99.7% | **100% / 100%** (899/899) |
| ws_connecting med | - (p99 632ms) | **28.9ms** |
| 배달 지연 p99 | 미측정 | **미측정** |
| 송신 (전체 WS 프레임) | 17,110 (35.3/s) | 13,617 (35.3/s) |
| **수신** | **149,650 (308/s)** | **1,716,858 (4,456/s)** |
| 수신/송신 배율 | 8.7배 | **126배** |
| chat CPU | 0.999 포화 (소급) | **988m = limit 1.0 포화** (ktop) |

> **송신 총량 차이는 부하 차이가 아니다.** 초당 송신률은 35.3/s로 동일하고, 1차가 8분 05초·2차가
> 6분 25초를 돌아 누적만 갈렸다(1차는 종료 구간에서 세션이 늦게 닫혔다). 부하는 같았다.

> **`ws_msgs_sent`는 채팅 메시지가 아니라 전체 WS 프레임 수다.** 세션마다
> CONNECT·SUBSCRIBE·DISCONNECT 3개가 붙어 999 × 3 ≈ 3,000이 섞여 있다.
> 채팅 SEND만 세면 1차 약 14,100 / 2차 약 10,600이다.
> 따라서 "이론의 63%"는 분모에 제어 프레임이 섞인 값이고, 채팅 송신만으로 다시 나누면 약 81%다.
> 램프 구간엔 구독자가 200명이 안 되므로 분자 쪽도 정확하지 않다 -
> **인용할 때는 단일 수치가 아니라 "이론의 6~8할"로 쓴다.**

### 캐파 - 이 시험에서 건질 수 있는 하나의 숫자

| | 값 |
|---|---:|
| 200명 방 하나가 요구하는 출력 | 약 7,000 msg/s |
| chat 1 코어의 실측 출력 | **약 4,500 msg/s** (CPU 988m 포화) |

→ **"chat 1 코어의 WS 팬아웃 천장은 약 4,500 msg/s."**
200명 방 하나에 코어 약 2개, 500명 방이면 약 50,000 msg/s가 필요하다.

> **단서:** 4,456/s는 램프를 포함한 **전 구간 평균**이라 실제 천장은 이보다 높다.
> 정확한 캐파는 유지 3분 구간만 잘라 재측정해야 한다 - **미측정.**

### 판정 - 1차 결론의 절반이 정정된다

1. 1차 가설 ①(브로커 아웃바운드 포화)은 **부분 정정**: 내보낼 CPU가 없어서가 아니라, 상당 부분이
   **CF 경유 WS 스트림의 전송 병목**이었다. 같은 CPU 포화에서 경로만 바꿔 출력이 11.5배 나온 것이 증거.
2. 그래도 이론의 6~8할에서 멈춘 것은 chat CPU 포화의 몫 - **"메시지 팬아웃이 chat의 병목"이라는
   큰 결론은 유지된다.** 연결 수가 아니라는 것은 [T3-J](../09-WS연결폭주/README.md)가
   1,000 연결에 CPU 31%로 확인했다.
3. **부수 관측(사건 씨앗 1)**: 시험 구간에 chat 워킹셋이 611 → 695Mi로 **+84Mi 계단 상승 후
   반납되지 않음** (ktop 실측). WS 세션 버퍼류 off-heap으로 추정 -
   [12-메시지처리량 재실행](../12-메시지처리량/README.md)의 노드 사망 사건으로 이어지는 첫 번째 계단이다.

## 4. 설계 결함 - 이 시험은 프로덕션에 없는 상태를 쟀다 (2026-08-24 코드 감사)

### 발견

`§1 사전 검증`에 이미 적혀 있던 두 제약이 사실은 결론을 뒤집는 것이었다.

1. **NORMAL 방은 1:1만 허용** (`ChatRoomCreateValidator`)
2. **WS SUBSCRIBE에 멤버십 검증이 없다**

즉 **1:1 방 하나를 200 세션이 구독하는 상태는 코드상 불가능한데, 2번 결함을 뚫고 만든 것**이다.
T2-C가 잰 팬아웃 200은 **접근제어 결함이 있어야만 성립하는 부하**이고, 프로덕션에는 존재하지 않는다.

### 그리고 팬아웃은 Kafka를 경유한다

`APP_KAFKA_ENABLED` 기본 `true`(`application.yml`), `ChatMessageProducer`가
`@ConditionalOnProperty(havingValue="true", matchIfMissing=true)`이므로 시험은 이 경로로 돌았다.
`DirectChatMessageSender`는 `havingValue="false"` - 로컬 개발용이라 뜨지 않았다.

```
SEND → ChatMessageProducer (kafka.send 후 즉시 "접수됨" 응답)
     → chat.messages (파티션 키 dm:{roomId})
     → ChatRelayConsumer (groupId = relay-{app.server.id})
     → StompMessageSender.sendToChatRoom → 구독자 배달
```

**배달 속도 = relay 컨슈머 소비 속도**다. 그리고 T2-C는 방이 하나였으므로 파티션 키가 전부 같아
**전량이 단일 파티션 → relay 병렬성 1**이었다(`setConcurrency(3)`도 무력).
이 직렬 지점 역시 서비스 특성이 아니라 **시험 설계가 만든 인공물**이다.
[WS-B](../12-메시지처리량/README.md)의 "단일 파티션 hot-spot" 판정도 같은 인공물을 본 것이다.

### 그래서 판정을 이렇게 좁힌다

**"CPU 포화라서 다 못 보냈다"는 상류를 못 짚은 판정이다.** CPU 포화는 실측이 맞지만,
그 CPU를 무엇이 먹었는지가 안 갈렸다 - SimpleBroker 팬아웃인지, 아니면 같은 파드 한 코어를 나눠 쓰는
세 컨슈머(`relay-*` · `db-writer` · `notification`)인지. 그 앞의 단일 파티션은 아예 관측 밖이었다.

### 시험을 둘로 가른다

| | 방 구성 | 팬아웃 | 파티션 | 실행 | 가능? |
|---|---|---:|---|---|---|
| **C-1 DM 현실 모델** | 1:1 방 100개 × 2세션 | 2 | 자연 분산 | `-e ROOM_COUNT=100 -e SUB_ALL=0` | 가능 (방 시딩 필요) |
| **C-2 라이브 이벤트** | CHANNEL 방 1개 × 200명 | 200 | 1개 (설계상 정상) | - | **불가** |
| C-3 파티션 대조군 | 방 N개 · 전 방 구독 | 200 고정 | 분산 | `-e ROOM_COUNT=20` | 가능 |

C-2가 원래 재려던 것인데 **STOMP 핸들러가 `ChatRoomType.NORMAL`을 하드코딩**해서 지금은 못 만든다.
코드 수정이 선행이다. 현재 T2-C는 C-1도 C-2도 아닌 **결함으로 만든 제3의 상태**다.

`SUB_ALL` 파라미터를 [`c-chat-ws.js`](../../c-chat-ws.js)에 신설해 C-1을 실행 가능하게 해뒀다.

### 부수 - 가설 ②는 코드로 기각된다

"참여자 선별 전송이라 8명한테만 갔다"는 1차 가설 ②. `sendToChatRoom`은
`/topic/chatroom/{roomId}` **구독자 전원**에게 나가고, 참여자 목록(`roomMemberIds`)은
헤드업 알림 대상 선별에만 쓰인다. **재시험 없이 기각.**

## 5. 관측 목록 - 다음 회차에 반드시 켤 것

Kafka 익스포터는 이미 붙어 있는데(`kafka_consumergroup_lag{consumergroup, partition, topic}`)
**팬아웃 컨슈머가 관측에서 통째로 빠져 있었다.**

실제 수집된 그룹: `chat-service-fcm-tokens` · `chat-service-notification-settings` · `db-writer`.
**`relay-*` 없음.** 이유는 그룹 이름이 `relay-${app.server.id}`라 **파드 재시작마다 바뀌기 때문**이다 -
고정 이름으로 대시보드에 못 박고, 죽은 그룹이 계속 쌓인다. 정규식 집계로 푼다.

| 패널 | 쿼리 | 왜 |
|---|---|---|
| **relay lag** | `sum by (partition) (kafka_consumergroup_lag{topic="chat.messages", consumergroup=~"relay-.*"})` | **이게 밀리면 그게 곧 배달 미달·배달 지연** |
| 그룹별 lag 대조 | `sum by (consumergroup) (kafka_consumergroup_lag{topic="chat.messages"})` | relay vs db-writer vs notification - 한 코어를 누가 먹는지 |
| 파티션 분산 | 위 relay lag을 partition별로 | 단일 파티션이 직렬 지점인지 확인 |
| 소비 속도 | `sum(rate(kafka_consumergroup_current_offset{...}[1m]))` | lag은 적체량, 이건 처리율 |
| chat CPU | `container_cpu_usage_seconds_total{container="chat-service"}` | 기존 |
| 배달 지연 | k6 `ws_delivery_latency` p99 | 신설 · 합격선 |
