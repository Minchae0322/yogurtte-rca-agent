## 사전 검증에서 확인한 제약

T1에서 메시지가 조용히 버려진 원인(방 부재)을 해소하려 실제 방을 만들며 확인된 것:

1. **NORMAL 방은 참여자 1명(1:1)만 허용** (`ChatRoomCreateValidator`). 50명 방은 CHANNEL
   타입이어야 하는데 STOMP 핸들러가 `ChatRoomType.NORMAL` 하드코딩 - 시험은 1:1 방
   (load1-load2, roomId `6a8183c7d2c54bf44544e516`)으로 진행.
2. **방 생성 API가 hidden 필드 `creatorId`를 body에 요구** - `@Valid`가 principal 주입보다
   먼저 돌아서.
3. **WS 구독·전송에 멤버십 검증이 없다** - 비참여자(load3)가 남의 1:1 방을 SUBSCRIBE·SEND
   해도 저장·브로드캐스트 성립 (단건 실측). REST 조회는 `validateUserAccess`로 막혀 있어
   **WS 경로만 뚫린 접근제어 결함.**

단건 검증: 실제 방으로 SEND → MESSAGE 수신 성립 (참여자·비참여자 모두). T1의 "수신 0건"은
방 부재로 **확정** (가설→실측 승격).

## 시험 설계

- **Question**: 라이브 이벤트급 동시 유입(200 세션)에서 연결·메시지 경로는 버티는가?
- **Experiment**: 6분(램프 2m + 유지 3m + 종료 1m) · WS 세션 999개 · 토큰 풀 50 ·
  실제 방 대상. STOMP CONNECT → SUBSCRIBE → 5초마다 SEND (Kafka → Mongo 저장 →
  브로드캐스트 경로 실측정).

## 해석과 다음 조치

수신이 송신의 8.7배에 그쳤다(이론 200배). 후보 가설은 다음과 같다.
① 브로커(인메모리 심플 브로커) 아웃바운드 포화 ② 참여자 선별 전송(참여자 세션 약 8개
≈ 배수 8.7과 일치) ③ k6 수신 한계. → [소급 관측](../99-소급관측/README.md): 시험 창 내내 **chat CPU
0.999 천장** - ①이 유력. ②를 기각하려면 참여자 세션만으로 재시험 필요.

scale-out이 필요하지만, scale-out 시 Chapter 4의 상태 공유 문제도 함께 검증해야 한다.
