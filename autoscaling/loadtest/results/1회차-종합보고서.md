# 부하테스트 1회차 종합 보고서 - 한계는 시스템이 아니라 CPU가, CPU는 노드가 아니라 파드가 정했다

> 2026-08-16 ~ 08-19 · 시험 15건 완주(부분 2건 포함 전 항목 종결, soak 제외).
> **결론: "동시 사용자 N명"이라는 단일 한계는 존재하지 않았다.** 읽기는 1,200 VU에서도 건강했고,
> 로그인은 300 VU에서 붕괴했으며, 채팅은 연결 1,000개를 버티고 메시지 초당 77건에서 무너졌다.
> 그리고 서로 달라 보이던 세 병목(커넥션 풀 고갈 · Kafka lag · 팬아웃 붕괴)의 상류를 추적하자
> **전부 같은 곳 - 파드 CPU limit - 에 도달했다.** 노드 스펙(t3 크레딧 포함)은 한 번도 먼저 깨지지 않았다.

각 시험의 상세는 [실행 인덱스](2026-08-16-실행-1회차.md), 설계 원칙과 판정 분기는
[부하테스트-설계-1.md](../../부하테스트-설계-1.md), 의사결정 서사는 [서사.md](../../서사.md).

## 1. 무엇을 재려 했나

목적은 "터지는지 보기"가 아니라 **무엇이 먼저 깨지는지를 계층별로 분리해서 재는 것**이었다.

```
트래픽 증가 → 어디가 먼저 한계인가? (노드 CPU / 파드 CPU / DB / 풀 / Kafka / WS / 구조)
           → 원인에 맞는 개선 선택 → 동일 조건 재검증 (2차)
```

그래서 스모크 → 기준선 → 축별 분리 진단(CPU·DB·풀·전파·Kafka·WS) → 한계 탐색(혼합·급증)
순서로 올라가고, 극한 시나리오에는 대조군을 붙였다. **17개를 다 도는 것이 목표가 아니라,
측정 결과가 다음 실험을 고르게 했다** - 실제로 2건(T2-B 소급, WS-B 대조군)은 1차 실행이
남긴 질문이 만든 시험이다.

## 4. 핵심 발견 넷

### 4-1. "동시 N명 한계"는 시스템 값이 아니라 가장 약한 서비스의 값이다

혼합 1,200 VU에서 읽기는 p99 252ms로 멀쩡했고 로그인만 무너졌다. 그 시점(551 VU) 노드는
62% 여유였는데 **auth 파드가 자기 CPU limit(500m)에 정확히 붙어 있었다.** 즉 이 시스템의
용량 질문은 "클러스터가 몇 명을 버티나"가 아니라 "auth의 limit과 replica를 어떻게 하나"로
바뀐다. 노드를 보고 "여유 있다"고 답하면 틀리는 구조다.

### 4-2. 세 갈래 병목의 상류가 전부 파드 CPU로 수렴했다

1차 실행에서 서로 다른 세 병목으로 보이던 것들을 추적 시험이 하나로 모았다.

| 증상 (1차 관측) | 추적 (2차 시험/소급) | 상류 |
|---|---|---|
| Hikari pending (T2-A 190건) | 풀 계단: pending 이탈 200 VU **이전에** CPU 0.83 도달, 커넥션 점유 0.3→2.0s | 처리 CPU 부족이 점유 시간을 늘려 풀을 고갈시킴 |
| Kafka lag 2.6만 · 단일 파티션 | 다중 방 대조군: 파티션 9개로 분산돼도 소비 1~5 msg/s 그대로 | **db-writer가 chat 파드 안** - 팬아웃과 CPU를 나눠 씀 |
| "CPU 99%" (T2-B) | 노드/파드 분리 소급: worker2는 노드에 0.5코어 남았는데 파드 limit 스로틀 95.5% | 스펙이 아니라 **limit 설정** |

**풀 상향·파티셔닝·노드 증설은 전부 증상 처방이다.** 개선 순서는 CPU 계층이 먼저고
([개선/cpu개선.md](../../개선/cpu개선.md) CPU-1~5), 그 뒤에 같은 시험으로 재검증한다.
예외는 하나 - 순간 급증(spike)만은 노드 CPU 99%가 실측된 노드 계층 한계다.

### 4-3. 대조군이 두 번 처방을 바꿨다

- **T3-D**: 같은 VU·같은 시간에 핫키 집중과 분산의 처리량이 3.1배 갈렸다 - "부하량"이라는
  답을 기각하고 락을 특정. 대조군 없이는 스케일아웃으로 갔을 것.
- **WS-B 다중 방**: 팬아웃(수신자 수)을 통제 변수로 고정하고 파티션 키만 분산 -
  hot-spot 가설의 현상은 확증하되 **처방("파티셔닝 선행")은 반증**했다. 파티션 병렬성이
  9배 열려도 소비할 CPU가 없었다. KEDA 서사(Chapter 3)의 전제가 이 시험으로 두 번 수정됐다.

### 4-4. 격리는 작동한다 - 이 구조의 성공 사례

auth를 97% 붕괴시킨 상태에서 content 읽기는 실패 0%였다. 3초 타임아웃 + 익명 폴백
(`user.fallback` 카운터 동반 상승으로 인과 확인)이 설계대로 동작했다. 장애 전파 축은
1차에서 개선 대상이 아니라 **보존 대상**으로 판정.

## 5. 깨짐의 세 가지 모양

같은 "한계 도달"도 사용자가 겪는 방식이 셋으로 갈렸고, 개선의 긴급도가 다르다.

| 모양 | 어디서 | 특징 | 긴급도 |
|---|---|---|---|
| 우아한 포화 | content 읽기 · 풀 계단 | 실패 0% 유지, 지연만 상승, VU를 늘려도 처리량 정체 | 낮음 - 용량 문제 |
| 붕괴 | auth 로그인 · spike | 실패 30~65%, 타임아웃 상한 도달 | **높음** - limit·replica |
| 조용한 적체 | Kafka lag | 클라이언트는 정상으로 보이는데 저장이 뒤처짐, 종료 후에도 증가 | **높음 - 지표 없이는 안 보임** |

## 6. 시험이 부수적으로 찾은 결함

| 결함 | 발견 경위 | 상태 |
|---|---|---|
| `websocket_active_users` 항상 0 | 실연결 200개 창에서도 0 ([소급](99-소급관측/README.md)) | **Ch4 선행 과제** - Gauge 재구현 전 replica 2 재현 불가 |
| NF-13: 스로틀 파드에서만 커넥션 847회 재생성 | T2-B 소급 (쌍둥이 파드는 18개) | pending 지표로 안 보임 - 원인 미확정 |
| `ChatRoomController` principal 바인딩 결함 | 시험 준비 중 (방 생성 불가) | 미수정 - 시험은 우회 |
| WS 멤버십 검증 부재 (임의 문자열 방 통과) | 시험이 이 결함 덕에 성립 | 수정 여부 미결 |
| 1,200 VU 실패 분해 불가 | CloudFront 타임아웃(~30s)이 한계 오염 | 절차 개정: Phase 3는 ingress 직결 |

## 7. 2차로 넘기는 것

**2차 = 개선 적용 후 동일 조건 재검증.** Before 수치는 [설계 문서의 Before/After 표](../../부하테스트-설계-1.md)에
전부 채워져 있고, 변경군을 섞지 않는 순서로 간다.

1. **CPU 계층** ([cpu개선.md](../../개선/cpu개선.md)): auth limit 500m·replica 1 재설정(4-1) ·
   content 요청당 16.9ms 절감 · requests 5배 오버커밋 해소 → mixed·T2-B·풀 계단 재실행
2. **chat 구조**: 저장 컨슈머 CPU 분리(4-2) → WS-B 재실행. WS 세션 Gauge 재구현 → Ch4 replica 2 재현
3. **HPA/KEDA는 1·2 다음** - T2-B 소급이 "HPA 1순위" 결론을 이미 한 번 뒤집었고(limit 3.0 vs
   워커 여유 부족), WS-B 대조군이 KEDA 전제를 수정했다. 스케일링은 CPU 예산이 확보된 뒤의 이야기다.

## 8. 한계와 미측정

- **soak(1시간) 미실행** - 누수·40분 후 열화는 이 회차가 답하지 못한다. 크레딧 제약은
  해소됐으므로(unlimited·미소진) 시간 확보만 남음.
- **DB 계층 판정 보류** - MySQL 익스포터 부재로 풀 계단의 DB 원인 가설을 완전히 못 닫았다
  (정황상 약함). T3-D 판정의 3중 근거화와 함께 정리 항목.
- **N=1** - 전 시험이 1회 실행이다. 수치는 "이 조건에서 이렇게 나왔다"이지 분포가 아니며,
  2차 재검증이 사실상의 재현 시험을 겸한다.
- WS-B 대조군의 수신 붕괴(277건, 단일 방 42,479 대비)는 **미해명** - 판정에는 영향 없으나 기록.
