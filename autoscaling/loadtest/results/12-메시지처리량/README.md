# WS-B 메시지 처리량 + Kafka Consumer 테스트 (단일 방 + 다중 방 대조군)

> **결론:** 200 연결에 초당 ~500건을 흘리자 chat CPU가 0.99로 포화하고 신규 연결이 62% 실패했다. 저장 컨슈머(db-writer)의 lag이 2만 건 넘게 쌓였고, 부하 종료 후에도 줄지 않았다. 1차 판정은 단일 파티션 hot-spotting이었으나, **다중 방 대조군(08-19)이 이를 절반만 확증했다** — lag 분산은 실제로 일어났지만(9/12 파티션, 최대 점유 23%) 총 소비 속도는 1~5 msg/s 그대로였다. **병렬성의 상한은 파티션이 아니라 chat 파드 CPU였다** (db-writer가 chat 파드 안에서 돌아 팬아웃과 CPU를 나눠 쓴다).

|---|---|
| 상태 | 실측 완료 · 단일 방 2026-08-18 · **다중 방 대조군 2026-08-19** |
| 목적 | 연결 아닌 **메시지 처리량**의 한계 + CPU vs Kafka lag 관계 → 대조군: 파티션 가설 검증 |

| 판정 | **메시지 팬아웃 = chat의 진짜 병목** · hot-spot은 실재하나 **소비 제약의 상류는 CPU** |

## 시험 설계

T3-J(연결 1,000개에 CPU 31%)와 T2-C(200연결·5초 간격)의 중간을 메운다. 연결 수는 200으로
고정하고 **메시지 전송 간격만 400ms로 낮춰**(c-chat-ws.js의 `MSG_INTERVAL_MS` 신규 파라미터)
메시지 처리량을 끌어올렸다. chat이 메시지를 Kafka `chat.messages`로 보내면 `db-writer`
컨슈머 그룹이 소비해 저장하므로, 같은 부하로 Kafka Consumer 시험도 겸한다.

## 원인 분석 — 단일 파티션 hot-spotting

부하 종료 후 5분이 지나도 lag이 줄기는커녕 26,001까지 늘었다. 파티션별로 보니
**전량이 `chat.messages` 파티션 6번 하나에 몰려 있었다** (다른 파티션 정상).

원인: 시험이 **한 채팅방(roomId 1개)** 에만 메시지를 보냈고, Kafka 파티션 키가 roomId라
전부 같은 파티션으로 라우팅됐다. 파티션 하나 = 컨슈머 스레드 하나이므로, chat이 CPU를
더 써도 그 파티션의 소비 속도를 못 올린다. **파티션 단위 병렬성이 무력화된 것.**

## 해석과 다음 조치

- **메시지 처리량이 chat의 진짜 병목**임이 확정됐다 (연결 아님 - T3-J와의 대비).
- **Kafka Case 판정**: CPU 0.99 + lag 증가 = 설계의 **Case A** (CPU도 lag도 높음).
  단순 CPU 기반 확장으로 consumer를 늘리는 게 방향이지만 - **파티션 수가 병렬성 상한**이라
  파티션 6에 몰린 이상 consumer replica를 늘려도 그 파티션은 한 컨슈머가 잡는다.
  즉 KEDA/HPA 이전에 **파티셔닝 키·파티션 수 설계가 선행**돼야 한다는 것이 이 시험의 교훈.
- 이 발견은 서사 Chapter 3(KEDA)의 전제를 바꾼다: "CPU vs lag"만이 아니라
  "파티션 병렬성"이 이벤트 스케일링의 진짜 축이다.

미측정: lag 완전 소진 시간(회복 곡선)은 부하 종료 후에도 CPU가 포화라 관측 창 안에
안 끝났다 - 백그라운드 소진 중. 여러 방으로 분산한 재시험이 파티션 가설을 확증한다.

## 다중 방 대조군 (2026-08-19 23:19~23:26 KST) - 파티션 가설의 절반만 살아남았다

### 설계 - 팬아웃을 통제 변수로 고정한다

방을 나누면 방당 구독자도 줄어 **팬아웃 부하(CPU)와 파티션 분산이 동시에 변한다.**
그래서 스크립트를 "각 VU가 전 방(20개)을 구독하되 전송은 자기 방으로만"으로 짰다
(c-chat-ws.js `ROOM_COUNT` 신설) - 메시지당 수신자 수는 단일 방과 동일하게 유지되고
바뀌는 것은 Kafka 파티션 키(roomId)의 분산뿐이다. 나머지 조건은 08-18과 동일
(200연결·400ms·6분). 사전 확인: 이전 lag 2.6만 전량 소진 · `chat.messages` 파티션 12개.

### 결과 - 두 실행 대조

| 지표 | 단일 방 (08-18) | 다중 방 20개 (08-19) |
|---|---|---|
| 송신 (통제 확인) | 30,419 (77/s) | 29,539 (74/s) - 동등 |
| chat CPU (통제 확인) | 0.99 포화 | **1.00 포화 - 동등, 통제 성립** |
| **lag 분포** | **파티션 6 하나에 전량 (100%)** | **9/12개 분산 · 최대 파티션 점유 23%** |
| lag 정점 | 26,001 (종료 후에도 증가) | 13,077+ (종료 8분 후에도 증가) |
| **db-writer 소비 속도** | (미계측) | **1~5 msg/s** (유입 74/s의 3~7%) |
| STOMP CONNECTED | 38% | 32% (재현) |
| 메시지 수신 | 42,479 (이론치의 7%) | **277 (사실상 0)** - 아래 미해명 |

### 판정 - hot-spot은 실재, 그러나 소비 제약의 상류는 CPU

1. **파티션 hot-spot 가설 자체는 확증됐다.** roomId 분산만으로 lag이 파티션 하나(100%)에서
   9개(최대 23%)로 퍼졌다 - 파티션 키 설계가 lag 분포를 지배한다는 것은 사실.
2. **그러나 "파티셔닝이 선행"이라는 1차 결론의 처방은 반증됐다.** 파티션 병렬성이 9배로
   열렸는데 총 소비 속도는 1~5 msg/s 그대로다. 이유는 배치 구조다 - **db-writer는 별도
   배포가 아니라 chat 파드 안의 컨슈머 스레드**이고(클러스터 배포 3개: auth·content·chat 실측),
   그 파드 CPU를 팬아웃이 다 먹는다(1.00). 파티션을 아무리 나눠도 소비할 CPU가 없다.
3. **결론 개정: 순서는 파티셔닝 → 스케일링이 아니라 CPU 분리 → 파티셔닝 → 스케일링.**
   저장 컨슈머를 chat 파드에서 분리(또는 chat CPU 확보)하지 않으면 KEDA로 무엇을 늘려도
   같은 CPU를 나눠 먹는다. [11-커넥션풀](../11-커넥션풀/README.md)과 동형의 발견 -
   풀/파티션 지표는 하류 증상이고 상류는 CPU다. 서사 Chapter 3 전제 2차 수정.
4. lag이 종료 8분 후에도 증가(9,133 → 13,077)한 것은 chat 프로듀서 측 백로그가 계속
   flush되고 있다는 뜻 - 종료 후에도 CPU 1.00이 유지된 것과 부합한다.

미해명 1건: 메시지 수신이 277건(단일 방 42,479 대비 사실상 0)으로 오히려 악화됐다.
가설은 ① 세션당 구독 20개 등록이 브로커 팬아웃 경로를 추가로 태움 ② CPU 포화 심화로
배달 스레드 기아. 판정에는 영향 없음(팬아웃 붕괴 방향은 동일)이나 별도 재현 필요.

## 재해석 (2026-08-21 · MEM-3 폭주 검증 창에서 발견) - 이 문서의 결론에 큰 별표가 붙는다

> **발견:** WS-B 전 실행의 저장 소비 바닥(1~5 msg/s)·lag 적체는 CPU도 파티션도 아니라
> **시험 설계 결함**이 만든 것이었다. 시험이 쓰는 방 `loadtest-room`은 실존하지 않고,
> db-writer는 저장(insert) 성공 후 `updateLastMessage`에서 `CHAT_ROOM_NOT_FOUND`로
> **전량 예외 → retry 토픽 루프**를 돌았다 (`ChatRoomService.java:80` orElseThrow 실측,
> retry-1000 소비가 본토픽과 1:1 동률·Mongo insert 카운터와 로그로 확인).

기전: 본토픽에서 saveMessage 성공 → updateLastMessage 예외 → retry-1000 발행 →
1초 백오프 뒤 retry에서 existsByMessageId 중복 감지 → 조기 return = "성공".
메시지당 예외 1회 + 토픽 홉 1회 + 파티션 직렬 = 소비 ~2 msg/s 고정.
**chat CPU 0.28/1.0(여유) 상태에서도 소비 1.9/s** - "소비 상한 = chat CPU" 결론이 반증됐다.

| 기존 결론 | 재해석 |
|---|---|
| 단일 파티션 hot-spot이 소비 병목 | 분산 확증은 유효하나, 소비 바닥의 원인 아님 |
| CPU 분리가 소비의 선행 조건 | **반증** - CPU 여유에서도 동일. 원인은 실패 루프 |
| lag 2.6만·"백그라운드 소진 중" | poison 시나리오 측정값. **데이터 유실은 없음**(insert는 본토픽에서 성공) |
