## 시험 설계

auth를 300 VU로 포화시키는 동안 content 읽기(`GET /feeds/scroll`)를 50 VU로 병행했다.
content는 피드 작성자 정보를 auth에서 가져오는데, 실패 시 예외 대신 익명으로 폴백하고
별도 카운터를 올린다. 이 폴백이 정상 상태에서는 캐시 히트로 발동하지 않으므로,
auth가 느릴 때만 경로가 드러난다.

## 서버 관측 — 전파 징후

정점(auth 300 VU) 동시 스냅샷: auth CPU 0.57 · **auth 풀 pending 141** 로 포화되는 동안,
content에도 **풀 pending이 0 → 3으로 번졌다** (content CPU는 0.28~0.40으로 여유).
즉 auth 지연이 content→auth 호출 경로를 통해 content 커넥션을 잠깐 붙잡는 전파가
실측됐으나, **3초 타임아웃 + 익명 폴백이 그 이상 번지는 것을 차단**했다.

## 해석과 다음 조치

**장애 격리 설계가 실제로 작동함을 실증했다** - "auth가 죽어도 content가 버티도록"이라는
의도가 auth 97% 붕괴라는 극한에서도 content 실패 0%로 성립했다. 서사상 이 결과는
"모든 병목을 스케일링으로 푸는 게 아니라, 이미 구조로 막아둔 것도 있다"는 대조 사례다.

전파의 강도(몇 %가 폴백을 탔는지)를 수치화하려면 그 카운터가 필요하다. content pending
