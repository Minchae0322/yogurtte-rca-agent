## 해석 - 설계 3-3 판정 분기 적용

세 갈래(Pool 부족 / DB 포화 / 쿼리 느림) 중 어디에도 깨끗이 떨어지지 않고, **Phase 1 해석
규칙("CPU가 낮은데 pending이 오르면 풀 계층")의 대우**가 적용된다: CPU가 먼저 포화했다.

1. **인과 순서가 명확하다.** 100 VU에서 CPU 0.83(pending 0) → 커넥션 점유 시간이
   0.31s → 1.41s로 4.5배 → 200 VU에서 풀 상한 도달·pending 이탈. 처리 CPU가 모자라
   커넥션을 오래 물고 있는 것이 고갈의 기전이다.
2. **따라서 "풀 상향(20→?)"은 근본 대응이 아니다.** CPU가 그대로면 풀을 키워도 점유 시간이
   길어 pending이 다시 쌓인다. 대응은 CPU 계층([개선/cpu개선.md](../../../개선/cpu개선.md)
   CPU-1~5: 요청당 16.9ms CPU 절감·limit 재설정)이 먼저고, 풀은 그 뒤 재측정.
3. **처리량 정체가 이를 뒷받침한다.** 100→400 VU에서 VU 4배에 처리량 +7.7%(158→170 rps) -
   늘어난 VU는 전부 대기(acquire 최대 1.19s + 응답 p95 2.42s)로 갔다.
4. **DB 계층은 판정 보류.** MySQL 익스포터 부재(정리 항목 기존 등재)로 DB CPU·커넥션을
   못 봤다. 단 점유 시간 증가가 파드 CPU 포화와 동기화돼 있어 DB 원인 가설은 약하다.

T2-A(auth 풀 10에 pending 190)·T3-D(락이 풀 고갈)와 함께 놓으면: **같은 "풀 고갈"이라도
원인 계층이 셋 다 다르다** - auth는 BCrypt CPU, T3-D는 락 직렬화, 여기는 처리 CPU 부족.
풀 지표만 보고 풀을 키우는 대응이 왜 틀리는지의 3중 실증.
