# T2-A 로그인 폭주 테스트

> **결론:** auth는 CPU 포화와 DB 커넥션 풀 고갈이 함께 발생해 실패율 29.75%, p99 49.4초를 기록했다. replica만 늘리는 방식으로는 해결되지 않는다.

## 시험 설계

1분에 50 VU까지 올린 뒤 2분 동안 300 VU로 스파이크, 2분 유지, 1분 종료했다. 요청은
`POST /api/auth/login` 단일 경로이며 BCrypt 검증, JWT 서명, refresh token upsert를 포함한다.
클라이언트(k6)와 서버(Mimir)를 정점에서 동시에 관측했다.

## 회복 특성

부하 종료 직후에도 CPU 1.0 · pending 166 (잔류 큐 소화 중) → 약 3.5분 뒤
완전 회복 (CPU 0.014 · pending 0 · 스레드 238→47 · 실 로그인 207ms). 재시작 없이 스스로
돌아오지만 종료 후 수 분간 신규 요청이 줄을 서는 구간이 존재 (2점 측정이라 정확한 곡선은
미상 - range 쿼리로 소급 가능).

## 결론과 다음 조치

**A+B 복합 병목**이다. CPU만 늘려서는 해결되지 않으며 DB 커넥션 총량도 함께 설계해야 한다.
Chapter 2(HPA)에서는 auth replica와 풀·커넥션 설정을 함께 검증한다.

실패 666건의 유형(타임아웃 vs 5xx/CF 504)은 아직 분해하지 못했다. 중앙값 35.5초가
CloudFront 오리진 타임아웃(기본 30초) 부근이므로 일부는 CF 504일 수 있다. 다음 실행에서
상태코드 태그로 분해한다.

## 재실행 (2026-08-21 · MEM-3 폭주 검증 창) - 실패 29.75% → 0.39%

CPU-2(limit 500m→1500m)·MEM-3(힙 512→384) 적용 후 동일 조건(300 VU) 재실행.
**힙 384 통과** (정점 힙 226/384Mi·워킹셋 636/768Mi·GC 무부담·재시작 0).
성능은 참고 수치(변경군 섞임): **실패 29.75% → 0.39%** · max 37s - pending은 똑같이 190까지
가는데 CPU 3배로 커넥션 회전이 빨라져 "타임아웃 500"이 "느리지만 완료"로 바뀌었다.
