# T2-A 로그인 폭주 테스트

> **결론:** auth는 CPU 포화와 DB 커넥션 풀 고갈이 함께 발생해 실패율 29.75%, p99 49.4초를 기록했다. replica만 늘리는 방식으로는 해결되지 않는다.

## 시험 설계

1분에 50 VU까지 올린 뒤 2분 동안 300 VU로 스파이크, 2분 유지, 1분 종료했다. 요청은
`POST /api/auth/login` 단일 경로이며 BCrypt 검증, JWT 서명, refresh token upsert를 포함한다.
클라이언트(k6)와 서버(Mimir)를 정점에서 동시에 관측했다.

## 회복 특성

부하 종료 직후에도 CPU 1.0 · pending 166 (잔류 큐 소화 중) → 약 3.5분 뒤
완전 회복 (CPU 0.014 · pending 0 · 스레드 238→47 · 실 로그인 207ms). 재시작 없이 스스로
돌아오지만 종료 후 수 분간 신규 요청이 줄을 서는 구간이 존재 (2점 측정이라 정확한 곡선은
미상 - range 쿼리로 소급 가능).

## 결론과 다음 조치

**A+B 복합 병목**이다. CPU만 늘려서는 해결되지 않으며 DB 커넥션 총량도 함께 설계해야 한다.
Chapter 2(HPA)에서는 auth replica와 풀·커넥션 설정을 함께 검증한다.

실패 666건의 유형(타임아웃 vs 5xx/CF 504)은 아직 분해하지 못했다. 중앙값 35.5초가
CloudFront 오리진 타임아웃(기본 30초) 부근이므로 일부는 CF 504일 수 있다. 다음 실행에서
상태코드 태그로 분해한다.

## 재실행 (2026-08-21 · MEM-3 폭주 검증 창) - 실패 29.75% → 0.39%

CPU-2(limit 500m→1500m)·MEM-3(힙 512→384) 적용 후 동일 조건(300 VU) 재실행.
**힙 384 통과** (정점 힙 226/384Mi·워킹셋 636/768Mi·GC 무부담·재시작 0).
성능은 참고 수치(변경군 섞임): **실패 29.75% → 0.39%** · max 37s - pending은 똑같이 190까지
가는데 CPU 3배로 커넥션 회전이 빨라져 "타임아웃 500"이 "느리지만 완료"로 바뀌었다.
로그인 단가 실측 **1건당 ~106ms CPU**(1.5코어/14.1rps) - BCrypt 의도 비용. 남은 벽 = 풀 10(CPU-4).

## 재실행 (2026-08-23 밤 · 2차 diet 구성 · nginx 직결) - 직결이 CF의 30초 상한을 걷어내자 실패의 모양이 또 바뀌었다

> **결론:** 시도 6,228건(1차 2,238 · MEM-3 재실행 4,789 - 직결로 유입 자체가 커짐) 중
> 실패 **10.7%(665건)** · med 6.1s · p99 35.6s. auth 파드는 이번에도 **CPU 1,501m = limit
> 1.5 벽**에 상주(노드 82%)했고, 성공 5,563건/360s = **15.4건/초 = 처리 상한(~15/s,
> 단가 106ms × 1.5코어)과 정확히 부합**. 결론 불변 - auth의 벽은 CPU limit이고, 경로·구성이
> 바뀌어도 상한 처리율이 그대로 관측된다.

### 조건

300 VU·6분 동일 · diet 구성 · nginx 직결. 비교 대상 둘: 1차(08-17, limit 500m, CF) ·
MEM-3 재실행(08-21, limit 1500m, CF).

### 결과 비교 - 세 실행의 실패 모양이 전부 다르다

| | 1차 (limit 0.5 · CF) | MEM-3 (limit 1.5 · CF) | **2차 (limit 1.5 · 직결)** |
|---|---|---|---|
| 시도 / 처리량 | 2,238 (5.9/s) | 4,789 (13.3/s) | **6,228 (17.3/s)** |
| 성공 | 1,572 | 4,770 | **5,563 (15.4/s)** |
| 실패율 | 29.75% | 0.39% | **10.68%** |
| med / p99 | 35.5s / 49.4s | 15.4s / 33.1s | **6.1s / 35.6s** |
| auth CPU | 1.0 (limit 벽) | 1.5 (limit 벽) | **1.501 (limit 벽)** |

**실패율 10.7%가 MEM-3(0.39%)보다 나쁜 이유는 회귀가 아니라 유입 차이다.** CF 경유에서는
엣지가 병목·타임아웃(30s) 역할을 해 유입이 13.3/s에 머물렀지만, 직결에서는 클라가 17.3/s로
밀어넣는다. 처리 상한 15.4/s를 넘는 초과분(~2/s × 360s ≈ 700)이 실패로 떨어진 것 -
실제 실패 665건과 부합. **closed-loop에서 경로 병목을 제거하면 실효 부하가 커진다**는
mixed-v2 때 정리한 원리의 재확인.

### 실패 유형 - 미확정 (정직 기록)

네트워크 에러 0건(k6 경고 없음) = 전부 서버 응답 상태코드. 그런데 같은 창의 auth 파드
로그가 0줄이라 서버측 분해 불가. max 36.1s(클라 60s 타임아웃 아님)로 보아
**auth Hikari 획득 30s 타임아웃 → 500 추정**(T2-A 1차의 pending 190 기전과 동일) -
Mimir는 해당 창 대부분 공백(관측 노드 플래핑)이라 pending 곡선 소급 불가.
