# T3-J WebSocket 연결 폭주 테스트 (WS-A)

> **결론:** 1,000 동시 WS 연결이 전부 성립했고 chat CPU는 31%에 그쳤다. 연결 수 자체는 병목이 아니다 - chat의 한계는 연결이 아니라 메시지 처리(T2-C)에 있다.

## 시험 설계

메시지를 보내지 않고 STOMP CONNECT 후 연결만 유지했다. 연결 유지 부하(세션 레지스트리 ·
FD · 메모리)와 메시지 처리 부하(T2-C)를 분리하기 위한 시험이다.

## 해석과 다음 조치

**연결 수는 chat의 병목이 아니다.** 1,000 연결을 CPU 31%로 버텼다 - T2-C에서 200 연결에
메시지를 5초마다 흘렸을 때 CPU 0.999로 천장을 친 것과 정반대다. 즉 chat의 실제 한계는
**연결이 아니라 메시지 브로드캐스트(팬아웃) 처리**에 있다.

서사적 의미(설계 1 · CPU 소비 성격 분해): chat은 connection-intensive가 아니라
message-intensive였다. Chapter 4(scale-out + Redis)의 동기는 "연결이 많아서"가 아니라
"메시지 팬아웃이 단일 파드 CPU를 포화시켜서"로 정확히 좁혀진다.

미측정: 이 시험은 인그레스 리밋 상향 상태에서 CloudFront 경유로 돌았다. 더 높은 연결
수(2,000)나 FD 한계는 재보지 않았다 - 현재로선 1,000이 여유이므로 우선순위 낮음.

## 재실행 (2026-08-23 밤 · 2차 diet 구성 · nginx 직결) - 1,000연결 여전히 무부하 - 단 워킹셋 계단(+58Mi)이 사건의 두 번째 씨앗이었다

> **결론:** 1,000 동시 WS 연결 100% 성립(1,167/1,167) · ws_connecting med 15.7ms ·
> chat CPU max **84m**(1차 310m) - "연결 수는 병목 아님" 재확인. 그러나 시험 구간에
> chat 워킹셋이 **692 → 750Mi(+58Mi)로 오르고 종료 후에도 반납되지 않았다** (ktop 실측).
> T2-C의 +84Mi에 이은 두 번째 계단으로, 직후 WS-B에서의 노드 사망을 만든 누적이다.
