## 시험 설계

## 해석과 후속 조치

1. **최대 병목은 `GET /chat/rooms`** - 다른 읽기가 100ms대일 때 혼자 1.8s.
   → [소급 관측](../99-소급관측/README.md)에서 원인 확정: chat 단일 레플리카 CPU 0.99 포화.
2. **로그인 p95 673ms - 동시 5 VU만으로 임계값 초과.** BCrypt 비용이면 T2-A(300 VU)에서
   크게 무너질 예고편 → [T2-A](../03-로그인폭주/README.md)에서 실증됨.
3. **채팅 메시지가 되돌아오지 않았다 - "실패한 줄 모른 채 통과" 실증.** 송신 2,800 대
   수신 400(CONNECTED 프레임뿐). 존재하지 않는 `loadtest-room`으로 보내 서버가 조용히
   버림 → [T2-C](../05-채팅동시접속/README.md) 전에 실제 방 생성으로 해소.
   T1의 채팅 수치는 "연결 유지 부하"만 잰 것이다.

서비스별 극한 시험(T2)을 진행한다. 우선순위는 auth와 chat이다. 서사상 위치는
[Chapter 1](../../../서사.md)의 "어디가 먼저 제한되는가"를 확인하는 첫 데이터다.
