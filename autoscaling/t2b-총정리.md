# T2-B 콘텐츠 폭주 - 시작부터 끝까지 총정리 (포트폴리오)

> 같은 부하 시나리오(콘텐츠 읽기 폭주)를 두 달에 걸쳐 구성만 바꿔가며 15회 이상
> 반복 측정해, 병목을 6번 옮겨 다니며 잡아낸 전 과정의 단일 정리 문서.
> 각 절의 상세·원자료는 링크된 SoT 문서에 있고, 이 문서는 서사와 수치 요약이다.
> [실측]/[가정] 구분, 반증된 실험 포함 - 성공만 골라 쓰지 않았다.

---

## 0. 한 장 요약

| 지표 | 시작 (2026-08 중순) | 끝 (2026-08-30) | 델타 |
|---|---|---:|---|
| 서버 처리량 (500 VU 폐루프) | 176.7 rps | ~400 rps | **+126%** |
| 요청당 CPU | 20.9 ms | 12.6 ms | **−40%** |
| 스파이크급 부하(400rps)에서의 실패 | 601건 (0.46%) | **0건** | 소멸 |
| 평시 피크(동접 1,250) SLO | 미정의 | **p99<800ms 통과** (med 42ms) | 첫 SLO 통과 |
| 월 인프라 비용 | 기준 | **절감** (spot 전환·Xmx 축소) | 성능↑ 비용↓ |

**한 문장:** *"CPU 스로틀링에서 시작해 앱 단가 → 노드 경합 → 톰캣 상한 → 커넥션 풀 →
로드밸런싱까지 병목을 6번 실측으로 옮겨 잡았고, 마지막에 부하 모델을 세워
'동접 몇 명을 어떤 품질로 받는가'를 숫자로 답할 수 있게 만들었다."*

## 1. 테스트 정의 - 무엇을, 왜 이 부하로

**T2-B**: 콘텐츠 읽기 폭주 시나리오. 실서비스 호출의 약 70%를 차지하는 핫패스 3종
(`/feeds/scroll` 커서 페이징 · `/feeds/hot` 인기 정렬 · `/feeds/{id}` 상세)을 1:1:1로 섞는다.

부하 기준은 임의 숫자가 아니라 **트래픽 모델에서 역산**했다 ([부하모델.md](부하모델.md)):

```
DAU 50,000 [가정] → 저녁 피크 2시간에 25% 집중 [가정, 시간대 편중 자체는 Reddit
1.4억 timestamp 연구로 실증] → 피크 동접 1,250명 (Little's law)
→ think time 평균 15초 [가정: 헤비 20%·일반 70%·방치 꼬리 10% 가중 분포]
→ 평시 피크 83 rps → 푸시 스파이크 ×5 → 400 rps = 동접 6,000명 상당
```

| 티어 | 부하 | SLO |
|---|---|---|
| baseline | 동접 1,250 (~83 rps) | p99 < 800ms · 실패 0 |
| target | 400 rps ≈ 300 VU | p99 < 3s · 실패율 < 0.1% |
| stress | 500 VU | 없음 - 한계 탐색용 |

환산 검증 [실측]: 300 VU = 394 rps (모델 예측 400과 일치) ·
현실 모드 동접 1,250 = 75~83 rps (예측 78~83과 일치) - 모델이 두 번 적중했다.

## 2. 병목의 연대기 - 여섯 번 옮겨 다닌 벽

각 단계는 "가설 → 단일 변수 변경 → 실측 → (자주) 반증"으로 진행했다.
상세: [cpu총개선.md](개선/cpu총개선.md) · [ec2개선.md](개선/ec2개선.md)

### 벽 1. CPU limit과 CFS throttling (176.7 rps)

500 VU에서 content 파드가 CPU limit 1.5에 걸려 CFS throttling **76~95.5%**.
limit을 1.7로 올리자 처리량이 오히려 **−16%** (스로틀링 지속) - 반증.
limit을 제거하자 스로틀링 0, 180.8 rps 회복. **"limit 상향"이 아니라 "limit 구조"가
문제였다.** 동시에 Xmx 768→512Mi 축소 실험으로 메모리는 무죄임을 확정.

### 벽 2. 애플리케이션 CPU 단가 (180.8 → 195.6 rps)

자원을 더 넣기 전에 요청 하나의 비용부터 줄였다 - readOnly 전환 + 조회수 UPDATE 분리로
dirty checking 제거: 요청당 CPU 20.9→18.6ms, **+7.7%**.

### 벽 3. 노드 CPU 경합 (195.6 → 241.2 rps)

content가 auth·chat·관측과 같은 노드에서 CPU를 경쟁하고 있었다. content를 **t3.small
spot 전용 노드 2대로 분리** (spot이 온디맨드 micro의 절반 가격에 메모리 2배):
**+23%, 실패율 0.25→0.03%, 비용은 절감.** micro 축소 실험은 −20%로 기각 [실측] -
메모리 용량만 보고 인스턴스를 줄이면 CPU 여유가 사라진다.

### 벽 4. 숨은 수용 상한 - 톰캣 스레드 40 (241.2 → 337 rps)

replica 3 확장(+30%) 후, 핫리스트 캐시를 넣었는데 적중률 100%인데도 처리량 등가라는
반증이 나왔다. 해부 결과 **prod 톰캣 스레드가 40**(3파드 합산 동시 120)으로 앞선 모든
회차의 숨은 상한이었다. 200으로 상향: **+26%.** 대가도 실측했다 - 대기가 톰캣 큐에서
앱 내부(풀 대기 최대 9.1s)로 이동, med 3.3배.

### 벽 5. "CPU 미포화인데 풀 대기" - 눌린 노드의 발견 (337 → ~400 rps)

scroll·detail 경로를 코드 레벨로 전수 해부(버려지는 쿼리 2·중복 1·순차 Redis GET)해
쿼리 다이어트: 요청당 CPU **16.0→12.6ms (−21%)**, 사상 처음 CPU 미포화(71~96%).
그런데 풀 대기(acquire max 10.1s)는 남았다. 이 모순은 **세 파드 자연 대조**로 풀었다 -
같은 146쿼리/s를 받고도 건강한 노드는 점유 41ms·대기 0, 눌린 노드는 67ms·대기 84건.
**풀 12는 원인이 아니라 CPU 압력이 실패로 변환되는 지점**이었다. 노드 감사로 눌림의
실체(관측 스택 동거 0.29코어·steal 2.6%·스왑 3.5G)를 특정, 관측 중앙부를 t3.micro
spot(~$3/월)으로 분리하자 최악 노드가 최우수로 바뀌었다.

### 벽 6. 분배 - 느린 파드에도 같은 몫을 밀어넣는 round_robin (실패 601 → 0)

여기까지의 처방이 매번 자원(노드·replica·분리)이었다는 자기반박에서
[개선점.md](개선/개선점.md) 9개(6개 비용 0)가 나왔고, 1순위가 로드밸런싱이었다.
남은 실패 601건을 초 단위로 분해하니 **전량이 한 파드의 5초 버스트 2회**(GC pause
0.4s 정황)였다 - round_robin은 파드가 멈춰도 같은 몫을 계속 보낸다.
ingress `load-balance: ewma` **설정 1줄(비용 0)** 적용 후 재실행:
**실패 601 → 0, 문제 파드가 최소 유입(30.5%) 수신** [실측, N=1 · 경로 혼입 단서 포함].
상세: [라우팅개선.md](개선/라우팅개선.md)

## 3. 계층별 개선 총람

| 계층 | 변경 | 근거 실측 | 효과 [실측] |
|---|---|---|---|
| 앱 (C-1) | readOnly + 조회수 UPDATE 분리 | dirty checking 비용 | 단가 20.9→18.6ms, +7.7% |
| 앱 (C-2) | 핫리스트 Redis 캐시 | 1시간마다 바뀌는 목록을 매 요청 재계산 | 16ms 제거, 처리량 등가 → 벽 4 발견의 열쇠 |
| 앱 (C-3) | 쿼리 다이어트 (낭비 2·중복 1 제거, MGET 배치, levelTable 캐시) | 경로 전수 해부 | 단가 −21%, CPU 첫 미포화 |
| 앱 (C-4) | 조회수 AFTER_COMMIT 비동기 이벤트 | 요청당 커넥션 2회 획득 | 커넥션 획득 2→1회 |
| 앱 (C-5) | 커넥션 점유 경계 축소 (Redis/HTTP를 트랜잭션 밖으로) | 점유 시간 = 수용량 (RDS 60 제약) | **델타 없음 - 판정 불가로 정직 기록** (§5) |
| 자원 | spot 전용 노드 분리 · Xmx 512Mi · replica 3 · 풀 20→12 (RDS 60 검산) | 노드 경합·커넥션 예산 | +23% · +30% · 비용 절감 |
| 자원 | 관측 중앙부 micro spot 분리 | 동거 0.29코어 실측 | 최악 노드 → 최우수 |
| 제어 (D-1) | ingress ewma (설정 1줄) | 파드 유입 146/146/99 편차 · 버스트 집중 | **실패 601→0** |
| 제어 | 톰캣 스레드 40→200 | 숨은 상한 해부 | +26% |
| 측정 | rate limit 시험용 상향 절차 | 직결 단일 IP가 limit-rps 30에 걸림 (503 97%) | 직결 측정 성립 조건 확립 |

## 4. 측정 방법론의 진화 - VU에서 동접 기준으로

### 폐루프의 한계를 실측으로 확인

VU 고정 폐루프는 서버가 느려지면 부하도 같이 줄어든다(coordinated omission).
실측 증거: VU 300→500으로 67% 올려도 rps는 394→398로 정체 - **추가 VU는 처리량이
아니라 대기줄이 된다.** 또한 폐루프 포화에서 지연 ≈ VU÷처리량으로 잠기므로,
개선이 지연 지표에 나타나지 않는다 (§5의 C-5가 그 사례).

### 두 모드로 분리

| 모드 | 구성 | 답하는 질문 |
|---|---|---|
| 압력 모드 | 300~500 VU, think time 없음 | 한계가 어디이고 어떤 모양으로 무너지나 |
| **현실 모드** | **VU = 동접**, think time 가중 분포 (헤비 20% 1~3s · 일반 70% 5~25s · 방치 10% 30~50s, 평균 15s) | **동접 N명을 SLO 안에서 받는가** |

현실 모드는 커넥션 축도 실제와 같다 - 동접 1,250이면 keepalive 커넥션 1,250개가
실제로 열린다 (압력 모드는 VU 수인 300~500개만 열려 이 축을 보지 못했다).

### 현실 모드 실측 (2026-08-30) - 첫 SLO 통과

| 지표 | 동접 1,250 (평시 피크) v1 | SLO | 판정 |
|---|---|---|---|
| 실패 | 0 / 30,351 | < 0.1% | 통과 |
| p99 | < 800ms (p95 68.7ms · max 275ms) | < 800ms | **통과 (k6 exit 0 - 13회 만의 첫 통과)** |
| med | 41.6ms | - | 쾌적 |
| 유지 rps | 75.4 | 모델 예측 ~78 | 일치 |
| 노드 CPU | 7~25% | - | 여유 4배 |

**평시와 스파이크의 격차가 정량화됐다**: 같은 서버가 평시 동접 1,250에선 med 42ms,
스파이크(400rps 압력)에선 med 600ms대. 이 서비스의 문제는 평시가 아니라
**스파이크 순간**이고, 위 개선들이 전부 그 순간을 겨냥한 것이다.

## 5. 반증된 실험들 - 성공만 쓰지 않았다

| 실험 | 가설 | 실측 결과 | 얻은 것 |
|---|---|---|---|
| CPU limit 1.5→1.7 | 더 주면 빨라진다 | **−16%** | limit 구조 자체가 문제 (제거로 해소) |
| t3.micro 축소 | 메모리 되니까 충분 | **−20%** | 시스템 영역 CPU를 놓친 산정 - 기각 |
| 핫리스트 캐시 | DB 벽 우회 | 적중 100%인데 처리량 등가 | 숨은 상한(톰캣 40) 발견의 열쇠 |
| 인그레스 편중 가설 (재실행 11) | 분배 쏠림이 실패 원인 | 그 창의 분배는 균등 - 기각 | GC 스톨 정황으로 재지목 → ewma의 논리 정련 |
| C-5 트랜잭션 경계 축소 | 점유 단축 → med 개선 | **델타 없음** (−2.6% rps · med +12%, 노이즈 대역) | 평시 지연의 지배 항은 풀 대기가 아니라 CPU임을 역으로 확정. 판정 조건(풀 포화 유도·Hikari 실측) 명시하고 보류 |

C-5가 특히 중요하다 - "커넥션이 병목"이라는 서사를 스스로 반증해 **"실패의 병목(버스트
시 풀)"과 "평시 지연의 병목(CPU)"을 분리**하게 됐고, 이후 개선의 과녁이 정확해졌다.

## 7. 예상 꼬리질문 방어

- **"그래서 몇 명까지 받아요?"** - 평시 피크 동접 1,250명은 SLO(p99<800ms) 안에서
  실측 통과. 스파이크급(400rps)은 실패 0으로 생존하나 p99 3초대라 SLO 조건부 수용점은
  개방 루프로 확정 예정. "생존"과 "SLO 수용"을 구분해 답한다.
- **"VU 300이 동접 300명이에요?"** - 아니다. think time 없는 VU 1개 = 실사용자 ~20명
  몫. 300 VU는 동접 6,000명 상당의 요청 압력이다 (커넥션 축은 별개 - §4 현실 모드).
- **"그 개선으로 점수(성능)가 올랐어요?"** - 항목별로 다르며 전부 실측 표가 있다.
  올라간 것(+126%, 실패 소멸), 등가였던 것(캐시), 판정 불가인 것(C-5)을 구분해 답한다.
- **"자기 채점 아니에요?"** - 판정 기준(SLO)을 먼저 박고 k6 임계값이 기계 판정한다.
  첫 통과가 13회 만이라는 것 자체가 기준이 후하지 않았다는 증거다.
- **"부하 숫자는 어떻게 정했어요?"** - [부하모델.md](부하모델.md) 사슬로 즉답.
  가정 5개(DAU·집중률·세션·think time·스파이크 배수)를 명시했고, 가정을 바꾸면
  결론이 어떻게 변하는지 즉답 가능하다.
