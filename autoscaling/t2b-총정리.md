# T2-B 콘텐츠 폭주 성능 개선
## 병목을 하나씩 제거하며 176 → 400 RPS까지 확장한 과정

### 1. 문제 정의 — 먼저 "얼마나 받아야 하는가"를 정의했다

운영 트래픽이 없는 상태에서 임의로 VU를 정해 부하 테스트를 시작하지 않았다.  
먼저 **실서비스에서 발생할 수 있는 부하를 추정하고, 그 부하를 서비스가 어느 수준의 품질로 처리해야 하는지 정의**했다.

커뮤니티 서비스의 트래픽이 특정 시간대에 집중된다는 전제에서 다음과 같이 부하 모델을 만들었다.

```text
DAU 50,000명
   ↓
피크 시간대에 25%가 집중한다고 가정
   ↓
2시간의 피크 구간
   ↓
평균 세션 12분
   ↓
평균 동접 ≈ 1,250명
   ↓
사용자 평균 요청 간격 15초 가정
   ↓
평시 피크 ≈ 83 RPS
```

여기에 푸시 발송처럼 사용자의 행동이 동시에 발생하는 상황을 별도의 **스파이크 시나리오**로 정의했다.

요청 간격이 약 3초까지 짧아진다고 가정하여,

```text
1,250명 × 1 / 3초 ≈ 417 RPS
```

수준을 목표로 잡고, 테스트 목표를 약 **400 RPS**로 설정했다.

| 구간 | 부하 모델 | SLO |
|---|---:|---|
| 평시 피크 | 동접 약 1,250명 / 약 83 RPS | p99 < 800ms |
| 스파이크 | 약 400 RPS | 실패율 < 0.1% |
| Stress | 500 VU | 한계 탐색 |

따라서 이 테스트에서 확인하고 싶었던 것은 단순히

> "서버가 몇 RPS까지 나오느냐"

가 아니었다.

**"예상되는 평시 동접을 SLO 안에서 처리할 수 있는가?"와  
"갑작스러운 400 RPS 수준의 폭주를 실패 없이 흡수할 수 있는가?"**

두 가지를 검증하는 것이 목적이었다.

# 2. 첫 결과 — 400 RPS를 받지 못했다

콘텐츠 조회의 핵심 경로인

- `/feeds/scroll`
- `/feeds/hot`
- `/feeds/{id}`

를 실제 사용 비율에 맞춰 구성하고 부하를 걸었다.

초기 서버 처리량은 **176.7 RPS** 수준이었다.

400 RPS를 목표로 했기 때문에 단순 계산으로도 상당한 차이가 있었다.

그리고 스파이크 테스트에서는 **601건의 요청 실패**가 발생했다.

이 시점에서 서버를 바로 증설하지 않았다.

먼저 질문을 바꿨다.

> **"왜 400 RPS를 못 받는가?"**

성능 개선의 목표를 "무조건 빠르게 만들기"가 아니라  
**병목의 원인을 하나씩 찾아 제거하는 것**으로 정의했다.

---

# 3. 첫 번째 가설 — CPU Limit이 병목인가?

처음 확인한 것은 Kubernetes의 CPU 설정이었다.

콘텐츠 서비스는 다른 서비스와 동일한 노드에서 실행되고 있었기 때문에, 처음에는 **한 서비스가 CPU를 과도하게 사용하는 것을 막고 다른 서비스와 자원을 나눠 쓰기 위해 CPU limit을 설정하는 것이 합리적이라고 판단했다.**

즉,

```text
Node
 ├─ Content
 ├─ Auth
 ├─ Chat
 └─ Monitoring
```

구조에서 특정 서비스가 CPU를 독점하지 못하도록 제한하려는 의도였다.

하지만 부하 테스트 결과 이 판단과 실제 시스템의 동작 사이에 차이가 나타났다.

CPU limit을 1.5 → 1.7로 높여보는 실험을 먼저 했다.

### 결과

예상과 달리 처리량이 **약 16% 감소**했다.

즉,

> "CPU를 조금 더 주면 빨라질 것이다."

라는 가설이 틀렸다.

여기서 CPU 사용률만 보고 판단하지 않고 **CFS throttling 여부를 확인했다.**

CPU limit에 도달하면 컨테이너가 사용할 수 있는 CPU 시간이 제한되고, 해당 주기 동안 실행이 중단되는 **CPU throttling**이 발생할 수 있다.

따라서 limit을 더 높이는 것보다,

> **이 워크로드에서는 CPU limit 자체가 병목으로 작용하고 있는가?**

를 확인하기 위해 limit을 제거하고 동일한 부하를 다시 측정했다.

그 결과 throttling이 사라지고 처리량이 다시 **180.8 RPS** 수준으로 회복됐다.

### 판단

CPU limit을 제거한 이유는 단순히

> "CPU는 많을수록 좋으니까"

가 아니었다.

**공유 노드에서 자원 독점을 막기 위해 설정했던 제한이, 실제로는 CPU가 부족한 상황에서 애플리케이션의 실행 시간을 강제로 제한하고 있었다는 것을 부하 테스트로 확인했기 때문**이다.

다만 여기서 문제를 해결했다고 판단하지 않았다.

CPU limit을 제거한 이후에도 부하 상황에서 CPU 사용률은 계속 높았고, 서버 처리량은 여전히 400 RPS와 큰 차이가 있었다.

따라서 다음 질문으로 넘어갔다.

> **"CPU를 제한해서 느린 것이 아니라면, 애초에 요청 하나를 처리하는 데 CPU를 너무 많이 사용하는 것은 아닌가?"**

---

# 4. 두 번째 가설 — 서버를 늘리기 전에 요청 하나의 비용부터 줄일 수 있는가?

코드를 확인한 결과 조회 API에 불필요한 비용이 있었다.

조회 요청인데도 트랜잭션이 일반 `@Transactional`로 열려 있어 JPA의 dirty checking 대상이 되었고, 조회 과정에서 조회수 증가까지 함께 수행되면서 읽기 요청에 쓰기 작업이 섞여 있었다.

이를 분리했다.

### 변경

```text
기존
조회 요청
 ├─ 조회
 ├─ JPA dirty checking
 └─ 조회수 UPDATE

변경
조회 요청
 └─ readOnly 조회

조회수
 └─ 별도 UPDATE
```

### 결과

| 지표 | Before | After |
|---|---:|---:|
| 요청당 CPU | 20.9ms | 18.6ms |
| 처리량 | 180.8 RPS | 195.6 RPS |
| 처리량 변화 | - | **+7.7%** |

큰 폭의 개선은 아니었지만 중요한 사실을 확인했다.

**서버를 증설하기 전에 요청당 CPU 비용을 줄이면 같은 하드웨어에서도 처리량을 높일 수 있었다.**

하지만 195.6 RPS 역시 목표인 400 RPS와는 거리가 있었다.

따라서 다시 시스템 전체를 바라봤다.

---

# 5. 세 번째 가설 — 애플리케이션이 아니라 CPU 자원 자체가 부족한가?

여기서 메모리와 CPU를 분리해서 확인했다.

메모리 사용량을 확인한 결과:

- OOM 없음
- eviction 없음
- 재시작 없음
- GC 이상 없음
- Xmx 768Mi → 512Mi로 줄여도 처리량 유지

즉,

> **메모리가 부족해서 느린 상황은 아니다.**

반면 CPU는 부하 상황에서 지속적으로 높은 사용률을 보였다.

결국 문제를 다음과 같이 좁혔다.

```text
Memory
 └─ 여유 있음

CPU
 └─ 지속적인 고사용률
 └─ CPU가 병목일 가능성 높음
```

이때부터는 "메모리가 얼마나 필요한가"가 아니라

> **"콘텐츠 서비스가 실제로 사용할 수 있는 CPU를 어떻게 확보할 것인가?"**

가 자원 설계의 핵심 질문이 됐다.

---

# 6. 네 번째 가설 — 더 작은 인스턴스로 비용을 줄이면서 CPU를 확보할 수 있는가?

당시 노드 구성을 확인한 뒤 단순히 큰 서버를 선택하지 않고 여러 인스턴스 타입을 비교했다.

처음에는 메모리 사용량이 충분히 작아 보였기 때문에 **t3.micro로 축소할 수 있을 것이라는 가설**도 세웠다.

실제로 t3.micro에 콘텐츠 서비스를 배치하고 동일한 부하를 걸었다.

### 예상

> 메모리 사용량이 1GB 안에 들어오므로 성능을 유지하면서 비용을 줄일 수 있을 것이다.

### 실측

메모리는 실제로 문제가 없었다.

- 워킹셋 약 529Mi
- OOM 없음
- eviction 없음
- 재시작 없음

그런데 처리량은 **192.6 RPS**로 떨어졌다.

기존 small 기반 구성과 비교하면 약 **20% 감소**했다.

CPU를 다시 확인하자 차이가 나타났다.

노드 전체 CPU 사용량은 높았지만, micro에서는 시스템 영역과 기타 프로세스가 CPU를 상당 부분 사용하면서 **애플리케이션이 실질적으로 사용할 수 있는 CPU가 줄어들었다.**

따라서 여기서 중요한 결론을 얻었다.

> **"메모리에 들어간다 = 충분한 서버가 아니다."**

이번 테스트에서 실제 병목은 메모리가 아니라 CPU였기 때문에, 메모리가 작은 micro로 줄이는 것은 비용 측면에서는 매력적이지만 서비스 처리량을 희생시키는 선택이었다.

따라서 micro는 기각했다.

---

# 7. 자원 선택 — "큰 서버"가 아니라 "필요한 자원에 맞는 서버"를 선택했다

CPU가 핵심 자원이라는 것이 확인됐기 때문에 CPU 기준으로 인스턴스를 다시 비교했다.

이 과정에서 스팟 인스턴스를 함께 비교했다.

당시 측정한 가격은 다음과 같았다.

| 인스턴스 | 비용 |
|---|---:|
| t3.micro On-Demand | $0.013/hr |
| t3.small On-Demand | $0.026/hr |
| t3.small Spot | **$0.007/hr** |

콘텐츠 서비스는 stateless하고 replica를 여러 개 운영할 수 있기 때문에 Spot 중단에 대응할 수 있는 구조였다.

따라서:

```text
비싼 큰 인스턴스 1대
        ↓
작은 인스턴스 여러 대
        ↓
Spot + Replica
```

구조로 변경했다.

결과적으로 워커 계층은

```text
기존
medium On-Demand + small On-Demand

변경
small On-Demand × 2
small Spot × 2
```

로 구성했다.

### 결과

- vCPU: **4 → 8**
- 비용: 약 **$0.078/hr → $0.066/hr**
- 비용 약 **15% 절감**
- 처리량: **195.6 → 241.2 RPS**

즉,

> **서버를 무작정 크게 만든 것이 아니라, 실제 병목이 CPU라는 것을 확인한 뒤 CPU를 더 확보하면서 비용까지 줄이는 방향으로 토폴로지를 변경했다.**

# 8. 다섯 번째 가설 — CPU를 확보했는데도 왜 400 RPS가 안 나오는가?

241.2 RPS까지 올라왔지만 여전히 목표에는 부족했다.

여기서 다시 애플리케이션과 인프라의 경계를 살펴봤다.

캐시를 적용했는데도 기대한 만큼 처리량이 증가하지 않는 현상이 발견됐다.

핫리스트를 Redis에 캐시해 DB 조회 비용을 제거했는데,

> **캐시 적중률은 100%인데 처리량이 거의 증가하지 않았다.**

이 결과는 중요한 단서였다.

DB가 병목이라면 캐시 적용 후 처리량이 증가해야 한다.

그런데 증가하지 않았다.

따라서 DB가 아니라 **다른 곳에 상한이 존재할 가능성**을 다시 조사했다.

확인 결과 production Tomcat의 `maxThreads`가 **40**으로 설정되어 있었다.

즉, 애플리케이션이 더 많은 CPU를 사용할 수 있게 되었지만 HTTP 요청을 동시에 처리할 수 있는 애플리케이션 스레드 자체가 제한되어 있었다.

### 변경

```text
Tomcat maxThreads
40 → 200
```

### 결과

**241.2 → 337 RPS (+26%)**

그리고 여기서 또 하나의 중요한 현상이 발생했다.

Tomcat 입구를 넓히자 처리량이 증가했지만, 기존에 보이지 않던 **DB connection 대기**가 나타났다.

즉,

```text
Tomcat 40
   ↓
[Tomcat에서 대기]

Tomcat 200
   ↓
[DB Connection Pool에서 대기]
```

가 됐다.

이 프로젝트에서 반복해서 나타난 패턴이었다.

> **하나의 병목을 제거하면 시스템은 끝나는 것이 아니라 다음 병목을 드러낸다.**

---

# 9. 여섯 번째 가설 — DB Connection Pool이 진짜 병목인가?

Tomcat을 확장한 뒤 DB connection 대기가 발생했기 때문에 처음에는 Connection Pool이 다음 병목이라고 판단할 수 있었다.

하지만 바로 Pool 크기를 늘리지 않았다.

먼저 CPU와 메모리, 파드별 상태를 비교했다.

세 개의 콘텐츠 파드가 동일한 요청을 받고 있었는데 특정 노드에서만 CPU 및 응답 지연이 크게 나타났다.

즉,

```text
같은 요청량
    ↓
Node A → 정상
Node B → 정상
Node C → 지연
```

이라는 차이가 있었다.

그리고 지연이 큰 노드에서는 CPU 압력이 높았고, CPU 압력이 높아지면서 요청 하나가 connection을 더 오래 점유했다.

결과적으로:

```text
CPU 압력
   ↓
요청 처리시간 증가
   ↓
DB Connection 점유시간 증가
   ↓
Connection Pool 대기
   ↓
요청 지연
```

이라는 구조가 만들어지고 있었다.

따라서 단순히

> "Connection Pool이 작으니까 늘리자."

라고 결론 내리는 것은 원인과 결과를 뒤집는 것이었다.

# 10. CPU 단가를 다시 줄였다

다시 콘텐츠 조회 경로를 전수 조사했다.

그 결과:

- 불필요한 쿼리 2개
- 중복 조회 1개
- Redis 순차 조회
- 요청 처리 과정에서 불필요하게 긴 작업

등을 발견했다.

이를 제거하고 Redis 조회도 batch 방식으로 변경했다.

### 결과

요청당 CPU 비용이

**16.0ms → 12.6ms**

로 약 **21% 감소**했다.

이 시점에서 CPU가 처음으로 충분히 여유를 보이기 시작했다.

그런데 여기서 끝이 아니었다.

DB Connection 대기가 여전히 남아 있었다.

따라서 파드별 상태를 다시 비교했다.

# 11. 문제의 원인은 Pool이 아니라 "느린 노드"였다

동일한 약 146 query/s를 처리하는 상황에서 파드별 차이를 비교했다.

| 상태 | Connection 점유 | 대기 |
|---|---:|---:|
| 정상 노드 | 약 41ms | 0 |
| 문제 노드 | 약 67ms | 84건 |

Connection Pool 자체가 동일한데 특정 노드에서만 점유 시간이 길었다.

따라서 Pool 크기를 무작정 늘리는 대신 **왜 특정 노드에서 요청 처리가 느린지**를 다시 추적했다.

해당 노드는 콘텐츠 서비스 외에 모니터링 프로세스가 함께 실행되고 있었고, 노드에서 애플리케이션 외 CPU 사용이 발생하고 있었다.

즉 최종적인 구조는:

```text
Content
   +
Monitoring
   ↓
CPU 경쟁
   ↓
Content 처리 지연
   ↓
DB Connection 장시간 점유
   ↓
Connection Pool 대기
```

였다.

이 결과를 바탕으로 관측 스택을 별도 노드로 이동시켜 콘텐츠와 CPU 자원을 분리했다.

---

# 12. 여기까지의 개선으로 약 400 RPS에 도달했다

이 과정을 거치면서 처리량은

```text
176.7
  ↓
180.8
  ↓
195.6
  ↓
241.2
  ↓
337
  ↓
~400 RPS
```

까지 증가했다.

하지만 마지막에 예상하지 못한 문제가 하나 남았다.

**400 RPS 수준에서 간헐적으로 요청 실패가 발생했다.**

그리고 초기 테스트에서 발생했던 **601건의 실패가 완전히 해결된 것은 아니었다.**

이제 문제는 처리량 자체가 아니라

> **"느려지는 특정 파드가 발생했을 때 요청을 어떻게 분산할 것인가?"**

로 바뀌었다.

---

# 13. 마지막 문제 — 모든 파드가 항상 같은 속도라는 가정이 틀렸다

기본 Round Robin 방식에서는 파드의 현재 응답 상태와 관계없이 요청을 순서대로 분배한다.

예를 들어:

```text
Pod A  정상
Pod B  정상
Pod C  순간적으로 느려짐

Round Robin

A → B → C → A → B → C ...
```

Pod C가 잠시 느려져도 계속 요청이 들어간다.

따라서 마지막 실패 601건의 원인을 추적하면서 **파드별 응답 속도에 따라 트래픽을 다르게 분배하는 것이 효과적인지**를 검증했다.

Ingress의 load balancing 방식을 Round Robin에서 **EWMA** 방식으로 변경했다.

EWMA는 최근 응답 시간을 기준으로 상대적으로 느린 파드에 보내는 요청 비율을 낮추는 방식이다.

### 결과

동일한 부하를 다시 실행했을 때:

```text
실패
601 → 0
```

으로 감소했다.

문제가 발생했던 파드도 전체 요청 중 약 30.5% 수준으로 상대적으로 적은 요청을 받는 것을 확인했다.

즉 마지막 개선은 서버를 추가하거나 CPU를 더 제공한 것이 아니었다.

**이미 확보한 자원을 어떻게 사용할 것인지에 대한 트래픽 제어 문제였다.**

---

# 14. 최종 결과

| 지표 | 초기 | 최종 |
|---|---:|---:|
| 처리량 | 176.7 RPS | **약 400 RPS** |
| 처리량 개선 | - | **약 2.3배** |
| 요청당 CPU | 20.9ms | **12.6ms** |
| 스파이크 실패 | 601건 | **0건** |
| 평시 피크 동접 | - | **약 1,250명 모델** |
| 평시 p99 | 미정 | **실측 800ms 이하** |
| 평시 median | - | **약 42ms** |
| 워커 계층 비용 | 기준 | **약 15% 절감** |
| 워커 vCPU | 4 | **8** |

현실적인 사용자 행동을 반영한 평시 부하에서는 **약 1,250명 동접 모델에서 p99 800ms SLO를 통과**했고, 스파이크 테스트에서는 **약 400 RPS에서 요청 실패 0건**을 확인했다.

# 15. 이 과정에서 가장 중요했던 것은 "무엇을 바꿨는가"가 아니었다

이 프로젝트에서 의미 있었던 것은 CPU limit을 제거하거나, EC2를 바꾸거나, Tomcat을 200으로 올린 것 자체가 아니다.

핵심은 **하나의 원인으로 모든 현상을 설명하려 하지 않았다는 것**이다.

처음에는 CPU limit이 문제라고 생각했지만 limit을 높이는 것이 오히려 성능을 떨어뜨리는 것을 확인했다.

그 다음에는 애플리케이션 CPU 비용을 줄였지만 목표에는 도달하지 못했다.

그래서 메모리와 CPU를 분리해 관찰했고, 메모리는 충분하지만 CPU가 부족하다는 것을 확인했다.

CPU를 확보하자 이번에는 Tomcat Thread Pool이 상한이 되었고, 이를 늘리자 DB Connection 대기가 나타났다.

Connection Pool을 바로 늘리지 않고 파드별 CPU와 처리시간을 비교한 결과 특정 노드의 CPU 경합이 원인임을 확인했다.

그리고 마지막에는 서버 자원이 충분해진 이후에도 순간적으로 느려지는 파드에 동일한 트래픽을 보내는 **로드밸런싱 문제가 실패를 만들어내고 있다는 것**을 확인했다.

결국 병목은 다음과 같이 이동했다.

```text
CPU limit / throttling
        ↓
요청당 CPU 비용
        ↓
CPU 자원 부족
        ↓
Tomcat Thread Pool
        ↓
느린 노드의 CPU 경합
        ↓
DB Connection 대기
        ↓
파드별 부하 분배
```

각 단계에서 **가설을 세우고 → 하나의 변수만 변경하고 → 동일 부하를 다시 넣고 → 결과가 맞지 않으면 가설을 버리는 방식**으로 접근했다.

따라서 이 프로젝트의 핵심 성과는 단순히

> **176 → 400 RPS**

가 아니라,

> **시스템 전체를 하나의 병목으로 보지 않고, 관측 결과에 따라 병목의 위치를 계속 재정의하면서 애플리케이션·CPU 자원·스레드 풀·DB·로드밸런싱까지 문제의 범위를 단계적으로 좁혀간 것**

이다.

## 최종적으로 보여주고 싶은 역량

**1. 숫자로 문제를 정의했다.**  
→ 임의 VU가 아니라 DAU → 동접 → RPS → SLO로 부하를 정의

**2. 증설보다 먼저 원인을 찾았다.**  
→ CPU limit → 애플리케이션 CPU 비용 → 자원 → Thread Pool 순으로 확인

**3. 가설이 틀리면 버렸다.**  
→ CPU limit 상향 실패, micro 성능 저하, 캐시 효과 제한, Connection Pool 가설 등을 그대로 기록

**4. 한 병목을 해결한 뒤 나타난 다음 병목까지 추적했다.**  
→ CPU → Thread Pool → Connection → 노드 경합 → Load Balancing

**5. 성능과 비용을 동시에 봤다.**  
→ vCPU 2배 확보하면서 워커 계층 비용 약 15% 절감

**6. 최종적으로 "얼마나 받을 수 있는가"를 SLO와 실측으로 답했다.**  
→ 평시 동접 약 1,250명 모델에서 p99 800ms 이하  
→ 스파이크 약 400 RPS에서 실패 0건

### 한 줄 요약

> **"성능을 높이기 위해 서버를 키운 것이 아니라, 관측과 실험을 통해 병목의 위치를 하나씩 좁혀가며 필요한 자원과 제어 지점을 찾아냈고, 그 결과 같은 예산에서 처리량을 2.3배 높였다."**
