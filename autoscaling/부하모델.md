# 부하 모델 및 성능 테스트

## 1. 테스트 기준 수립

실제 운영 트래픽이 충분히 축적되지 않은 상황에서 임의의 동시 사용자 수를 기준으로 부하를 설정하지 않고, **커뮤니티 서비스의 시간대별 트래픽 특성과 사용자 행동을 기반으로 부하 모델을 수립**했습니다.

Reddit 사용자 51,372명의 약 1억 4천만 건 게시물 timestamp를 분석한 연구에서 시간대에 따라 활동량이 크게 변화하는 패턴을 확인했습니다. 이를 참고하여 커뮤니티 서비스에 특정 시간대의 트래픽 집중이 발생한다고 가정하고, 서비스 규모와 사용자 행동을 바탕으로 목표 부하를 산정했습니다.

> **주의:** Reddit 연구는 커뮤니티 트래픽에 시간대별 편차가 존재한다는 근거이며, 아래의 `25% / 2시간`이나 `5배 스파이크` 자체를 뒷받침하는 수치는 아닙니다. 해당 값은 실제 운영 데이터가 부족한 상황에서 테스트 시나리오를 구성하기 위해 설정한 **가정**입니다.

---

## 2. 트래픽 모델

### 2.1 DAU → 피크 구간 평균 동접

| 단계 | 구분 | 값 |
|---|---|---:|
| 목표 DAU | [가정] | 50,000명 |
| 피크 집중률 | [가정] | 25% |
| 피크 시간 | [가정] | 2시간 |
| 피크 구간 활성 사용자 | 계산 | 12,500명 |
| 평균 세션 길이 | [가정] | 12분 |
| **피크 구간 평균 동접** | 계산 | **약 1,250명** |

계산:

```text
50,000 × 25%
= 12,500명
```

피크 2시간 동안 12,500명의 사용자가 방문하고, 각 사용자의 평균 세션 길이가 12분이라고 가정하면:

```text
12,500명 × 12분
----------------
120분

= 1,250명
```

따라서 **피크 구간의 평균 동접을 약 1,250명으로 추정**했습니다.

> 1,250명은 실제 운영 환경에서 측정한 동접이나 최대 동접이 아닙니다.  
> `DAU 50,000명`, `피크 집중률 25%`, `세션 12분`이라는 가정을 적용하여 계산한 **피크 구간 평균 동접 추정치**입니다.

---

### 2.2 평균 동접 → RPS

사용자가 피드를 탐색하면서 평균적으로 약 15초마다 요청을 발생시킨다고 가정했습니다.

```text
1,250명 ÷ 15초
≈ 83 RPS
```

따라서 예상되는 **평시 피크 요청률을 약 83 RPS**로 산정했습니다.

여기서 15초는 모든 사용자가 동일한 간격으로 요청한다는 의미가 아니라, 사용자 행동을 단순화한 **평균 요청 간격에 대한 모델 가정**입니다.

---

### 2.3 스파이크 부하

이벤트 오픈이나 푸시 발송과 같이 짧은 시간 동안 유입과 요청 빈도가 증가하는 상황을 별도로 고려했습니다.

평시 피크 대비 5배의 부하가 발생한다고 가정했습니다.

```text
83 RPS × 5
≈ 415 RPS
```

테스트 목표는 이를 단순화하여:

> **약 400 RPS**

로 설정했습니다.

따라서 전체 부하 모델은 다음과 같습니다.

```text
DAU 50,000명
      │
      ▼
25%가 2시간에 집중 [가정]
      │
      ▼
12,500명
      │
      ▼
평균 세션 12분 [가정]
      │
      ▼
피크 구간 평균 동접 약 1,250명
      │
      ▼
평균 요청 간격 15초 [가정]
      │
      ▼
평시 피크 약 83 RPS
      │
      ▼
스파이크 ×5 [가정]
      │
      ▼
약 415 RPS
      │
      ▼
테스트 목표 약 400 RPS
```

## 3. 왜 VU가 300개인가?

k6에서는 VU(Virtual User)를 이용하여 부하를 발생시켰습니다.

단, **VU 수와 실제 서비스의 동시 사용자 수는 동일한 개념이 아닙니다.**

이번 테스트에서는 요청이 완료된 후 일정 시간 대기하는 closed-loop 방식으로 부하를 생성하기 때문에, VU 수는 실제 사용자의 수가 아니라 **동시에 요청을 발생시키는 가상 실행 주체의 수**로 해석해야 합니다.

목표 RPS와 평균 응답시간을 기준으로 필요한 VU를 대략 추정했습니다.

```text
필요 VU
≈ 목표 RPS × 평균 응답시간

≈ 400 × 0.75초
≈ 300 VU
```

이 값을 초기 Target 부하로 설정한 후 실제 k6 결과를 확인했습니다.

### 실제 측정

```text
300 VU
   ↓
약 394 RPS
```

따라서 300 VU에서 모델링한 목표인 약 400 RPS를 실제 테스트 환경에서 재현할 수 있음을 확인했습니다.

> 이 계산은 `300 VU = 실제 사용자 300명`이라는 의미가 아닙니다.  
> VU는 테스트 시나리오의 실행 단위이며, 실제 사용자 수와의 관계는 think time, 응답시간, 세션 패턴 등에 따라 달라집니다.

# 4. 테스트 환경

Application Server는 AWS EC2 `t3.small` 3대로 구성했습니다.

| 항목 | 구성 |
|---|---:|
| Instance | `t3.small` |
| Instance 수 | 3대 |
| vCPU | 2 vCPU / 인스턴스 |
| Memory | 2 GiB / 인스턴스 |
| 총 vCPU | 6 vCPU |
| 총 Memory | 6 GiB |
| Application | Spring Boot |
| Load Test | k6 |

T3 계열은 Burstable Instance이므로 지속적인 CPU 부하 상황에서는 CPU Credit의 영향도 고려해야 합니다.

따라서 단순히 RPS만 측정하지 않고 애플리케이션과 인프라의 주요 지표를 함께 관찰했습니다.

# 5. 테스트 티어

| 티어 | 부하 | 목적 |
|---|---:|---|
| Smoke | 소량 | 기능 및 테스트 경로 검증 |
| Baseline | 약 83 RPS | 예상 평시 피크 성능 확인 |
| **Target** | **약 400 RPS / 300 VU** | **목표 스파이크 부하 검증** |
| Stress | 500 VU | 처리량 포화 및 시스템 한계 탐색 |
| Open-loop | 250 → 400+ RPS | RPS 기준 수용점 확인 |

### Target

목표 부하인 약 400 RPS가 안정적으로 처리되는지 확인했습니다.

### Stress

Target보다 높은 500 VU까지 부하를 증가시켜 **추가적인 VU 증가가 실제 처리량 증가로 이어지는지** 확인했습니다.

### Open-loop

현재 테스트는 VU 기반 closed-loop 방식이므로, 최종적인 최대 Capacity를 확정하기 위해서는 향후 목표 RPS를 직접 주입하는 open-loop 테스트가 필요합니다.

# 6. 부하 테스트 결과

## 6.1 Target — 300 VU

### [실측]

```text
300 VU
  ↓
약 394 RPS
```

300 VU에서 약 394 RPS가 발생했습니다.

모델에서 산정한 목표 부하인 약 400 RPS와 유사한 수준으로 실제 부하를 재현할 수 있음을 확인했습니다.

---

## 6.2 Stress — 500 VU

### [실측]

```text
300 VU → 약 394 RPS
500 VU → 약 398 RPS
```

300 VU에서 500 VU로 부하를 증가시켰음에도 처리량은 약 394~398 RPS 수준에서 정체되었습니다.

즉,

```text
VU 증가
   │
   ▼
요청 발생량 증가
   │
   ▼
시스템 처리량 증가
   │
   ▼
약 394~398 RPS
   │
   ▼
처리량 증가 정체
```

가 발생했습니다.

이를 통해 **추가적인 VU 증가가 처리량 증가로 이어지지 않는 포화 구간**을 확인했습니다.

다만 이것만으로 특정 자원이 병목이라고 단정하지 않고, CPU·JVM·Thread Pool·DB Connection 등의 지표를 함께 분석했습니다.

# 7. 성능 판단 지표

단순히 "몇 VU까지 처리했는가"를 기준으로 성능을 판단하지 않고 다음 지표를 함께 확인했습니다.

| 지표 | 확인 목적 |
|---|---|
| RPS | 실제 처리량 확인 |
| p95 | 일반적인 Tail Latency 확인 |
| p99 | 극단적인 응답 지연 확인 |
| Error Rate | 부하 상황에서의 안정성 확인 |
| CPU | 애플리케이션 서버 CPU 병목 확인 |
| CPU Credit | T3 Burst 성능 지속 여부 확인 |
| Memory | 메모리 부족 및 GC 영향 확인 |
| JVM / GC | JVM 내부 병목 확인 |
| Tomcat Thread Pool | 요청 처리 동시성 및 Thread 고갈 확인 |
| Hikari Connection Pool | 애플리케이션 DB Connection 병목 확인 |
| RDS Connection | DB Connection 한계 확인 |

# 8. 병목 분석 및 개선

## 8.1 Read-only 조회 전환

조회 API에서 일반적인 `@Transactional`을 사용하면서 영속성 컨텍스트의 Dirty Checking이 발생할 수 있는 구조를 확인했습니다.

또한 Feed 조회 과정에서 조회수 증가를 함께 처리하면서 조회 요청에도 DB UPDATE가 발생했습니다.

### 기존

```text
Feed 조회
   │
   ├── Entity 조회
   │
   ├── 조회수 증가
   │
   └── UPDATE 발생
```

### 개선

```text
Feed 조회
   │
   └── Read-only 조회

조회수 처리
   │
   └── 조회 경로와 분리
```

### 결과

```text
181.6 RPS
     ↓
195.6 RPS

약 +7.7%
```

조회 경로에서 불필요한 DB 작업을 제거하여 처리량을 개선했습니다.

# 9. Hot Data 캐싱

반복적으로 조회되는 Hot Feed 및 Hot Battle 데이터를 Redis에 캐싱했습니다.

### 기존

```text
Request
   ↓
Application
   ↓
DB
```

### 개선

```text
Request
   ↓
Application
   ↓
Redis
   │
   ├── HIT → 응답
   │
   └── MISS → DB
```

이를 통해 반복 조회되는 데이터의 DB 접근을 줄이고, DB 병목을 완화했습니다.

---

# 10. 인프라 및 DB Connection 최적화

애플리케이션의 CPU 사용량뿐만 아니라 DB Connection을 함께 확인하여 병목 지점을 구분했습니다.

단순히 서버 사양을 높이는 방식이 아니라:

```text
부하 테스트
    ↓
자원 지표 확인
    ↓
CPU / JVM / Thread / DB Connection 분석
    ↓
병목 구분
    ↓
Application 개선
    ↓
Cache 적용
    ↓
Infrastructure 최적화
```

순서로 개선했습니다.

특히 DB Connection Pool과 RDS Connection 제한을 확인하여 애플리케이션 서버의 Scale-out이 항상 처리량 증가로 이어지는 것은 아니라는 점을 확인했습니다.

|---|---:|
| 개선 전 | **181.6 RPS** |
| Read-only / 조회수 분리 | **195.6 RPS** |

| 초기 대비 | **약 +73%** |

최종적으로 처리량을:

```text
181.6 RPS
     ↓

```

까지 향상시켰습니다.

단순히 서버를 증설하는 것이 아니라 **애플리케이션의 불필요한 DB 작업 제거 → Hot Data 캐싱 → DB Connection 및 인프라 자원 최적화** 순서로 병목을 제거했습니다.

# 12. 테스트 결과 해석

이번 테스트에서 중요한 것은 단순한 "300 VU 처리"가 아니라 **VU를 증가시켜도 처리량이 증가하지 않는 포화 구간을 실제로 확인했다는 점**입니다.

```text
                    처리량
                      ▲
                      │
                      │             ─────── 약 398 RPS
                      │          ───
                      │       ──
                      │    ──
                      │ ──
                      └────────────────────────▶ VU
                         300              500
                         ↑                 ↑
                      394 RPS          398 RPS
```

300 VU 이후 추가적인 VU 증가에도 처리량 증가 폭이 매우 작았기 때문에, 약 400 RPS 부근에서 시스템의 Capacity 한계에 접근하고 있음을 확인했습니다.

다만 **정확한 수용 Capacity는 VU 기반 테스트만으로 확정하지 않았습니다.**

최종 Capacity를 확정하려면 RPS를 직접 제어하는 open-loop 테스트에서:

```text
250 RPS
  ↓
300 RPS
  ↓
350 RPS
  ↓
400 RPS
  ↓
450 RPS
  ↓
500 RPS
```

와 같이 단계적으로 부하를 증가시키면서 `p99 latency`, `error rate`, `CPU`, `DB Connection` 등의 SLO 충족 여부를 함께 확인하는 것이 필요합니다.

# 14. 한계

현재 부하 모델은 실제 운영 데이터가 충분하지 않은 상황에서 **테스트 기준을 체계적으로 설정하기 위한 모델**입니다.

따라서 다음 값들은 실제 운영 데이터가 축적되면 교체할 수 있습니다.

```text
현재 가정
│
├── DAU 50,000
├── 피크 집중률 25%
├── 평균 세션 12분
├── 요청 간격 15초
└── 스파이크 ×5
        │
        ▼
실제 운영 데이터
│
├── 시간대별 사용자 분포
├── 사용자별 세션 길이
├── API별 요청 간격
├── Peak RPS
├── Peak Concurrent Users
└── Spike RPS
        │
        ▼
부하 모델 보정
```

또한 현재 테스트는 VU 기반 closed-loop 방식이므로, `300 VU = 300명의 실제 동시 사용자`로 해석하거나 `500 VU = 실제 동접 500명`으로 해석해서는 안 됩니다.

향후 open-loop 테스트를 통해 **SLO를 만족하는 최대 RPS**를 측정하면 실제 서비스 Capacity에 대한 보다 직접적인 근거를 확보할 수 있습니다.

# 16. 포트폴리오 요약

> **실제 운영 트래픽이 충분하지 않은 상황에서 Reddit의 시간대별 활동량 분석 자료와 사용자 행동을 참고해 커뮤니티 서비스의 부하 모델을 수립했습니다. DAU 5만 명, 피크 집중률 25%, 평균 세션 12분 등의 가정을 통해 피크 구간 평균 동접을 약 1,250명으로 추정하고, 약 400 RPS를 스파이크 목표 부하로 설정했습니다. AWS EC2 t3.small × 3 환경에서 k6를 이용해 300 VU에서 약 394 RPS를 재현했으며, 500 VU까지 증가시켜도 약 398 RPS에서 처리량이 정체되는 포화 구간을 확인했습니다. 이후 CPU, JVM, Thread Pool, DB Connection 등의 지표를 기반으로 병목을 분석하고 Read-only 조회 전환, 조회수 처리 분리, Hot Data 캐싱 및 인프라·DB Connection 최적화를 수행하여 처리량을 181.6 RPS에서 314.3 RPS로 약 73% 향상시켰습니다.**
