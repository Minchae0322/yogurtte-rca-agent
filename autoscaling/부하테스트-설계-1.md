# 부하테스트 설계 1 - 제한된 인프라에서 무엇이 먼저 깨지는지 분리한다

> 2026-08-14 초판 설계의 개정판 (초판은 폐기, 원칙은 여기 승계). 초판의 원칙(한 시험 한 자원 ·
> 코드 확인 · 대조군 · 기준선 우선)은 그대로 두고, **목표를 "오토스케일링 검증"에서
> "한계 식별 → 원인 계층 분리 → 원인별 개선 → 재검증"으로 넓힌다.** HPA/KEDA/Redis는
> 목적이 아니라 결과에 따라 선택되는 후보다.
>
> 상태 표기: `[실측 완료]` 결과 문서 있음 · `[스크립트 있음]` 미실행 · `[신규]` 작성 필요

## 전제 - 이 시스템의 가장 큰 제약은 코드가 아니라 노드 CPU다

Yogurtte는 비용을 제한하기 위해 소형 EC2 기반 K3s 클러스터로 구성했다.
**전 노드가 2 vCPU (t3 버스터블)** 이다 (실측):

| 노드 | 타입 | vCPU | 메모리 | 역할 |
|---|---|---:|---|---|
| master | t3.micro | 2 | 936Mi | control-plane (앱 없음) |
| worker 1 | t3.medium | 2 | 3.9Gi | auth·content·chat |
| worker 2 | t3.small | 2 | 1.9Gi | content |
| edge (proxy) | t3.nano | 2 | 424Mi | Ingress |

노드당 CPU가 낮아서 애플리케이션 부하가 증가하면 **애플리케이션 자체의 병목과 노드 CPU
포화가 쉽게 섞인다.** 그래서 무작정 1,000→2,000 VU까지 올리는 시험은 "Yogurtte가 어디까지
버티는가"가 아니라 "t3 CPU가 언제 먼저 죽는가"를 재는 실험이 되기 쉽다. 두 가지 결론:

1. **노드 → Pod → DB → 외부 의존성의 병목을 분리해서 관측한다.** CPU가 높다고 앱 문제가
   아니고(노드 공유 포화일 수 있다), CPU가 낮다고 여유가 아니다(풀·락일 수 있다).
2. **t3 CPU 크레딧을 반드시 함께 본다.** `부하↑ → CPU 80% → Credit 감소 → burst 유지 →
   Credit 고갈 → CPU 성능 제한 → 응답 급증` 현상이 있으므로, "300 VU에서 p99 2초"가 아니라
   "노드 CPU 포화 + CPUCreditBalance 감소 후 p99 급증"으로 써야 인프라 제약까지 설명된다.

## 최종 목표

**제한된 EC2 자원에서 어느 계층이 먼저 한계에 도달하는지 측정하고, 병목의 원인에 맞는
개선을 적용한 뒤 동일한 조건에서 재검증한다.** "동시 사용자 N명을 견뎠다"가 아니라
**RPS · p99 · error rate · Node/Pod CPU · DB · Kafka lag · recovery time**의 전후 비교로 보인다.

```
트래픽 증가 → 어디가 먼저 한계에 도달하는가?
              (CPU? DB? Connection Pool? Kafka? WebSocket? 네트워크? 애플리케이션 구조?)
           → 원인에 맞는 해결책 선택 → 재측정 → 새로운 병목 발견 → 반복
```

결과별 대응 후보 (사전 선언 - [서사.md](서사.md)의 Plan A/B 표와 연동):

| 병목 | 대응 후보 |
|---|---|
| CPU | HPA / JVM / 코드 최적화 |
| DB | Query / Index / Cache |
| Connection Pool | Hikari 튜닝 / DB connection 관리 |
| Kafka | Consumer 튜닝 / KEDA |
| WebSocket | Connection 구조 (Redis Pub/Sub 등) |
| MSA 전파 | Cache / Timeout / Bulkhead |
| Spike | Scaling latency / warm capacity |
| Memory | JVM / leak 추적 |

**17개를 다 실행하는 것이 목표가 아니다.** 측정 결과가 다음 실험과 개선을 고른다.

## Phase 0 - Correctness + Infrastructure (부하 전 · 인프라 한계 먼저)

**0-1. Correctness (Smoke).** 1 VU로 주요 경로 1회: 로그인 · Content 조회 · Reaction ·
Battle · WS CONNECT/STOMP · Kafka 소비. 확인: HTTP 2xx · **STOMP CONNECTED까지**
(101만 보면 안 된다 - 초판 §1의 교훈, T1에서 "존재하지 않는 방으로 조용히 버려짐"을 실증) ·
DB 반영 · Kafka 소비. 여기서 깨지면 부하테스트를 시작하지 않는다.

**0-2. Node Capacity - 애플리케이션을 보기 전에 노드 자체의 한계를 잰다 [신규].**
"어떤 서비스가 병목인가"보다 먼저 **"노드 CPU가 병목인가, 특정 서비스 CPU가 병목인가"**를
가른다. 혼합 부하를 100→200→300→400 계단으로 올리며 계층별로 동시에 본다:

| 계층 | 지표 | 왜 |
|---|---|---|
| Node | node CPU · load · **CPU throttling · CPU steal · CPUCreditBalance** · memory · network | t3 크레딧 고갈을 한계로 착각하지 않기 위해 |
| Pod | 서비스별 CPU(millicore) · memory | 노드 포화가 특정 서비스 때문인지, 전체 공유 포화인지 구분 |
| DB | connection count · CPU | CPU가 낮은데 느리면 여기 |

판정 예시 (같은 "느림"도 원인이 다르다):

| 관측 | 해석 |
|---|---|
| Node CPU 100% · content 900m · auth 50m | content가 CPU 병목 → content 스케일/최적화 |
| Node CPU 100% · 세 서비스 400m씩 | 노드 CPU capacity 공유 포화 → 배치/노드 문제 |
| Node CPU 50% · Hikari pending↑ · p99↑ | CPU를 늘려도 무의미 → 풀/DB 계층 |

**CPUCreditBalance는 CloudWatch에서 본다** (`aws cloudwatch get-metric-statistics
--namespace AWS/EC2 --metric-name CPUCreditBalance`). AWS CLI 미설치 상태 - 인프라
시험 전에 `brew install awscli` + 자격증명 필요. 시험은 크레딧 고갈을 피해 10~15분 단위로.

### CPU capacity 대조군 - "CPU가 진짜 병목인가"를 증명 [신규·선택]

CPU 부족이 의심되면 대조군으로 증명한다: 동일 시험을 현재(2 vCPU)와 잠깐 키운 환경
(4 vCPU, 인스턴스 타입 일시 변경)에서 각각 돌린다.

| 결과 | 결론 |
|---|---|
| 2vCPU p99 1,200ms → 4vCPU p99 400ms | **CPU capacity가 실제 병목이었다** (강한 증거) |
| 2vCPU 1,200ms → 4vCPU 1,100ms | CPU가 근본 원인이 아니다 → DB/풀을 찾는다 |

**단, EC2를 키우는 것을 최종 해결책으로 쓰지 않는다** (돈으로 때운 것이 되므로). CPU
소비 패턴을 서비스별로 분해해 원인에 맞는 개선으로 간다:

| 서비스 | CPU 소비 성격 | 개선 방향 |
|---|---|---|
| auth | CPU-intensive (BCrypt) - T2-A 실측 | replica scale-out (단 풀 동반) |
| content | DB-intensive (CPU는 응답 대기) - T2-B는 CPU 포화지만 데이터 증가 시 DB로 이동 | query / cache |
| chat | connection-intensive (idle 연결) - T3-J 1000연결에 CPU 31% 실측 | connection 구조 (Redis) |

이 표 자체가 "CPU 부족 → EC2 4배"가 아니라 "CPU를 무엇이 쓰는가를 분해했다"의 증거다.

## Phase 1 - Baseline

**Endpoint Baseline**: 기능별 분리 측정 (Login 5~10 · Content 30~50 · Reaction 10~20 ·
Battle 10~20 VU · Chat 20 connections · Upload 1~5 VU).
**User Journey**: 세션 단위 + think time (읽기 70 / 반응 20 / 채팅 10 비율 근사).

측정 축 (전 시험 공통): **3계층을 동시에 본다.**
- **Node**: CPU · load · throttling · steal · CPUCreditBalance · memory · network
- **Pod**: 서비스별 CPU(millicore) · memory · GC · thread pool
- **DB / 의존성**: Hikari active/pending/acquire-time · DB connection · Kafka lag · WS connections
- **Client(k6)**: RPS · p50/p95/p99 · error rate

클라이언트(k6)와 서버(Mimir)를 같은 시각에 쌍으로 - 정점을 놓치면 `max_over_time` 소급.
**해석 규칙: 앱 지표가 정상인데 느리면 노드 계층을, 노드가 정상인데 느리면 DB/풀 계층을 본다.**

## Phase 2 - 원인 분리 진단 (축별)

### 3-1. CPU / Compute - Login Burst [실측 완료 · 확장 여지]

300 VU 실측 완료 (CPU 100% + 풀 pending 190 이중 병목). 확장: 500·800 VU 단계와
함께 **Tomcat busy threads · request queue · GC · CPU throttling · heap을 같이 본다.**

| 결과 | 대응 |
|---|---|
| CPU 포화 | replica 증가 / HPA |
| Thread 포화 | thread pool / blocking I/O 조사 |
| GC 증가 | heap/JVM 조사 |
| CPU 낮은데 느림 | DB/외부 호출 조사 |

### 3-2. Database - 읽기와 쓰기를 분리

**Read**: Content 50→100→300→500 VU. 관측: query latency · DB CPU · connections ·
rows examined · slow query · buffer hit. (500 VU 실측에서는 앱 CPU가 먼저 포화 -
DB 병목은 현 데이터 규모에서 미발현. 데이터 증가 시 재검.)
**Write**: 분산 key(e-guest-swipe · d SPREAD) vs hot key(d 본군) 대조군 - 락 실측 완료.

### 3-3. Connection Pool [신규 - 반드시 추가]

`Request ↑ → query ↑ → Hikari active ↑ → pending ↑ → acquire timeout` 체인을 잡는 시험.
DB-heavy 경로(리액션 쓰기 또는 로그인)를 VU 계단으로 올리며 **pending이 0을 벗어나는
지점과 acquire time 분포**를 찾는다. 관측: Hikari active/idle/pending/max ·
connection acquire time · DB 쪽 connection count.

| 결과 | 대응 |
|---|---|
| Pool 부족 (DB는 여유) | Pool 상향 (auth 10 → ?) - 단 DB max_connections 총량 안에서 |
| DB 자체 포화 | Query/Index/Cache |
| Query가 오래 걸림 | SQL 개선 |

이미 근거가 있다: T2-A에서 auth 풀 10에 pending 190, T3-D에서 락이 풀을 고갈.
이 시험은 그것을 **한계 곡선**(어느 VU부터)으로 만든다.

### 3-4. Cache 효과 [신규 · 조건부 - 코드 확인 결과 반영]

**전제 확인 완료: 피드 조회 본경로에는 Redis 캐시가 없다** (content의 Redis는
작성자 정보 캐시 · 핫스코어 스케줄러용). 따라서 "Cache ON/OFF 비교"는 두 형태만 가능:

1. **지금 가능**: content→auth 사용자 정보 캐시(FollowingCacheStore·UserCacheStore)의
   히트/미스 차이 - 3-5(전파) 시험과 겹치므로 거기서 함께 관측.
2. **개선 실험으로**: 피드 경로에 캐시를 넣는 것 자체가 개선 아이템 - Phase 2 진단에서
   DB가 병목으로 나오면 "무작정 DB 증설 대신 캐시 적중률" 서사로 Before/After를 잰다.
   (진단 전에 미리 넣지 않는다 - 변경군 섞임 방지.)

### 3-5. 서비스 간 전파 - f-cascade [스크립트 있음]

auth 포화(300 VU) 중 content 읽기(50 VU)의 p99 · timeout · fallback 카운터를 본다.
"서비스 하나의 장애가 전체로 전파되는가"가 질문. 대응 후보: timeout 튜닝 · 캐시 ·
fallback · async/bulkhead.

### 3-6. Kafka Consumer [신규]

KEDA를 목표로 하지 않는다. 질문: **이벤트 처리량이 증가할 때 consumer가 어느 지점에서
처리하지 못하는가.** WS 메시지 전송률을 올려 Kafka 유입을 늘리고(chat 경로가 Kafka 경유),
producer rate · consumer throughput · lag · consumer CPU/memory · 처리 latency를 본다.

| Case | 신호 | 대응 |
|---|---|---|
| A | CPU 90% + lag 증가 | Consumer replica 증가 |
| B | CPU 40% + lag 급증 | CPU가 scaling 신호로 부적절 → KEDA 검토 |
| C | CPU 90% + lag 없음 | 충분히 처리 중 - 조치 불필요 |

### 3-7. WebSocket - 연결과 메시지를 분리

**WS-A 연결 용량** (j-ws-storm): 메시지 없이 200→500→1,000→2,000 connections.
관측: 성공률 · handshake latency · active sessions · **FD** · memory · CPU.
주의: `websocket_active_users` 메트릭은 결함 확정(실연결 200에서도 0) - **Gauge 재구현이
이 시험의 선행 조건**이다. 안 고치면 서버측 연결 수를 못 잰다.
**WS-B 메시지 처리량** (c-chat-ws 확장): 200 connections 고정, 10→30→50→100 msg/s.
관측: 전달 latency · drop률 · Mongo latency · CPU. 1회 실측에서 이미 35 msg/s ×
200구독에서 팬아웃이 이론치의 7%로 무너짐 - 레이트를 내려가며 **무너지기 시작하는
지점**을 찾는 것이 목적. (스크립트에 메시지 간격 파라미터 추가 필요.)

## Phase 3 - 한계 · 회복 · 지속

- **Breakpoint (혼합)** [신규]: content 80/auth 15/chat 5 가중치 혼합, 100→300→600→1,000→1,500
  VU 계단. 각 단계에서 p95/p99/error/RPS + 서버 지표. SLO(예: p99 500ms)가 깨지는 지점이
  **"동시 사용자 N명"이라는 실측 한계**가 된다 - 숫자는 입력이 아니라 발견.
- **Spike**: 100 VU → (10초) → 1,500 VU → 100 VU. 보는 것: 처리량이 아니라 **반응** -
  최대 p99 · error · recovery time · (HPA 도입 후엔) scaling time · DB/Kafka lag 회복.
- **Soak**: 동일 부하 1시간. Memory/Connection/Thread/Redis key/WS session leak ·
  lag 누적. "처음 10분은 정상, 40분 후 느려짐"을 잡는 시험.
- **Upload**: 1GB 단건이 아니라 **10MB×100 · 50MB×50 동시 업로드**로 재설계.
  핵심 서사에서는 비중 낮게.

## 실행 원칙 (초판 계승 + 이번 판 추가)

1. **초판 계승**: 한 시험 한 자원 · 부하 지점은 코드에서 확인한 것만 · 대조군 · 기준선 우선 ·
   코드가 규약을 정한다(경로·인증 키·STOMP 프레임 - 초판 §1).
2. **경로**: 한계 탐색(Phase 3)은 **ingress 직결** - CloudFront 타임아웃(~30s)이 한계를
   오염시킨다 (T2-A 실패 분해 불가의 교훈). 직결에는 부하 소스 IP를 SG 80/443에 한시 허용.
   기능 진단(Phase 2)은 CloudFront 경유도 무방 - 단 어느 경로였는지 반드시 기록.
3. **t3 크레딧**: 시험 전 CPUCreditBalance 확인, 10~15분 단위로 끊기. 크레딧 고갈을
   한계로 착각하면 결론이 오염된다 (master t3.micro · edge t3.nano라 특히 민감).
4. **인그레스 리밋**: 상향(2000/2000/120000) → 시험 → 원복(20/30/600) 절차 매회.
5. **기록**: 시험당 결과 md 1개([results/](loadtest/results/) 형식 - Question→Hypothesis→
   Experiment→Finding→Decision + Case 판정), 원본 output/summary 보존, 서버 정점은
   Mimir 동시 또는 소급.
6. **개선은 진단이 끝난 뒤에** - 지금 HPA/KEDA/Redis Pub/Sub을 구현하지 않는다.
   측정이 무엇이 필요한지 고른다. 변경군을 섞지 않는다.
