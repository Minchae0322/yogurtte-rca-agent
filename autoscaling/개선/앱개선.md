# 앱개선 - 코드 레벨 개선의 의사결정 기록 (변경군 C)

> 설정([cpu개선.md](cpu개선.md))·인프라([ec2개선.md](ec2개선.md))와 구분되는 **애플리케이션
> 코드의 개선 기록**이다. 이 트랙의 전제: 처리량 상한 = CPU 총량 ÷ 요청당 CPU 단가 -
> 설정·인프라가 분자를 다 짜낸 뒤(314 rps·RDS 59/60), 남은 전진은 분모(단가)뿐이다.

## C-1. readOnly 전환 + 조회수 분리 (2026-08-21 배포·검증 완료)

### 무엇을 발견했나

T2-B 코드 분석(CPU-1)에서 "슬로우 SQL"보다 큰 것 둘:

1. **`FeedService` 클래스 전체가 `@Transactional`(readOnly 아님)** - 모든 읽기가 쓰기
   트랜잭션으로 돌아 Hibernate가 로드한 전 엔티티의 스냅샷을 뜨고 커밋 시 dirty checking
   (순수 CPU). 외부 auth 호출까지 트랜잭션 안이라 커넥션 점유도 동반.
2. **`getFeed`가 조회마다 `incrementViewCount()`** - 읽기 시험에 초당 ~50건의 UPDATE가
   숨어 있었고, 리액션 토글이 잠그는 같은 행이라 락 경합까지.

### 결과 (toy-content `7906ef1` · T2-B 동일 조건)

| | 전 | 후 |
|---|---|---|
| 요청당 CPU | 20.5ms | **18.6ms (웜업 후 ~16ms)** |
| 처리량 | 181.6 rps | 195.6 rps (+7.7%) |
| p95 | 4.89s | 4.53s |

**판정: 유의미하나 크지 않음** - dirty checking+조회수 몫이 요청당 ~4ms였다는 실측.
남은 ~16ms가 쿼리+직렬화 본체이고, 그 답이 C-2다.

## C-2. 핫리스트 캐시 (2026-08-23 구현 완료 · 배포 대기)

### 대상 선정 - 무엇을 캐시하고 무엇을 안 하나

| 경로 | 캐시 | 근거 |
|---|---|---|
| feeds/hot · battles/hot · 인기 products | **O** | 실트래픽 최다(대시보드 3종 동시 호출) + **사용자 무관 동일 응답** + 핫스코어는 스케줄러가 1시간마다 갱신 - 갱신 주기당 최대 100만 번 같은 결과를 재계산하던 경로 |
| feeds/scroll · 상세 · 검색 | X | 사용자별·실시간 경로 (제품 판단) |
| products 목록 중 키워드 검색·관리자 조회 | X (조건부 제외) | 키 폭발·판매자 화면 낡음 방지 - `condition = keyword == null && !isAdmin` |

### 저장소 결정 - Caffeine으로 시작해서 Redis로 끝난 이유 (이 문서의 핵심)

**1차 결정: Caffeine(파드 로컬).** 근거 - replica 3이라 파드별 재계산이 TTL당 3회뿐이라
공유의 이득이 없고, 네트워크·직렬화 비용 0, 장애 지점 추가 0. 메모리는 캐시당 200엔트리
상한으로 수 MB 미만(힙 512Mi의 1%). **전환 조건 3개를 함께 박제**: ① replica 수십 개로
파드별 재계산이 유의미해질 때 ② 파드 간 즉시 정합 요구 ③ 타 서비스가 같은 캐시를 읽을 때.

**반전: 무효화 설계 중 ShedLock 발견.** 핫스코어 스케줄러들이 Redis 분산 락으로 **리더
파드 1곳에서만** 돈다. 그러면 로컬 캐시에서 갱신 직후의 그림은:

```
리더 파드:   @CacheEvict로 즉시 새 순위
나머지 2파드: 옛 순위를 TTL(5분) 만료까지 서빙
→ 갱신 후 ~5분간 새로고침마다 순위가 왔다갔다 (로드밸런서가 파드를 바꾸므로)
```

**제품 판정: "이렇게 되면 안 된다"** - 파드 간 순위 불일치 불허. **전환 조건 ②가 발동**됐고,
결정대로 Redis로 전환했다. 도구가 바뀐 게 아니라 요구사항이 확정되며 미리 정해둔 분기를
탄 것이다.

**Redis 전환의 손익** (마침 content가 ShedLock·작성자 캐시로 이미 Redis 의존 - 인프라 추가 0):

| | Caffeine | Redis (채택) |
|---|---|---|
| 히트 비용 | ~0 (메모리 참조) | 네트워크 ~1ms + 직렬화 - **DB 재계산 16ms의 1/10 이하라 수용** |
| 갱신 반영 | 리더만 즉시, 나머지 TTL | **evict 1번 = 전 파드 즉시 일관** |
| 장애 지점 | 없음 | Redis 의존 - CacheErrorHandler로 강등(아래) |

### 무효화·안전 설계 (3겹)

1. **스케줄러 연동 evict** - 핫스코어·트렌딩·인기도 재계산 메서드 7곳(4개 스케줄러)에
   `@CacheEvict(allEntries)`. 기본 동작이 메서드 완료 후 실행이라 "재계산 커밋 → 비움" 순서 보장
2. **TTL 5분** - evict 누락(스케줄러 실패 등) 대비 안전망으로 강등
3. **CacheErrorHandler** - Redis 다운·배포 간 역직렬화 실패를 전부 **캐시 미스로 강등**해
   DB 폴백. 캐시는 최적화지 의존성이 아니다 - 캐시 장애가 서비스 장애로 승격되지 않는다

직렬화 함정 처리: `Page` 계열은 JSON 직렬화가 잘 깨지는 유명한 문제라 JDK 직렬화(RedisCache
기본)를 쓰고, 캐시에 실리는 DTO 5종(HotFeedResponse·BattleHotList·BattleHotItem·ProductList·
AttachmentFileResponse)에 `Serializable` + **serialVersionUID 고정**. 그래도 깨지는 배포가
오면 3번 안전밸브가 받는다.

|---|---|---|---|---|

| T2-B 서버 rps | 314.3 | ~500 | **305.1 (등가)** | **반증** |

**반증의 해부 - 둘 다 예측의 가정이 틀렸다:**

1. **처리량·단가 반증**: "요청당 16ms"를 세 경로 평균으로 뭉뚱그린 것이 오류. 비싼 경로는
   scroll·detail(LAZY 연관)이고 **hot은 원래 싼 경로**였는데, 캐시 대상은 hot뿐이며 비싼
   경로는 실시간이라 의도적으로 제외했다(대상 선정은 옳았음). 즉 **T2-B(스크롤 중심 극한
   시험)는 이 캐시의 무대가 아니다** - 가치는 실트래픽 구성(대시보드 3종 최다)에서 발현되며,
   그 검증 시험(journey-v2 After)은 보류 상태. 교훈: 단가는 경로별로 재야 예측이 선다 (CPU-1).
2. **RDS 반증**: 59는 사용 중이 아니라 **풀 상주분**(minimumIdle=max 기본, content 36 상시
   점유) - 캐시는 사용을 줄이지 상주를 못 줄인다. **커넥션 예산 회수의 레버는
   `minimum-idle` 축소**(별도 설정 후보)다.

## C-3. scroll·detail 요청 해부 - 단가의 내역이 나왔다 (2026-08-23 코드 분석 · 미적용)

### 적용 내역 (2026-08-23 · 빌드+테스트 통과 · 커밋/배포 전)

한 변경군(C, 쿼리 수 절감)으로 묶어 2·3·4를 함께 적용했다. 1(조회수)은 동작 변화가 있는
별도 변경이라 다음 회차로 분리 - 이번 묶음의 델타가 "쿼리 수" 하나로 설명되게 하기 위함.

| 파일 | 무엇을 |
|---|---|
| `FeedRepositoryCustomImpl` | `fetchAssociations`·`fetchHashtags`·`fetchUserReactions` 삭제 (결과를 버리던 쿼리 2개 + service와의 중복 1개). 컬렉션 초기화는 `default_batch_fetch_size=100`이 담당함을 주석으로 박제 |
| `UserCacheStore` | `getCachedUserInfoBatch(List)` 신설 - `opsForValue().multiGet` 왕복 1회. 역직렬화 실패·미존재는 미스 처리, Redis 장애 시 빈 맵(기존 단건 폴백 규약과 동일) |
| `ExternalUserInfoService.getUserInfos` | ID당 순차 GET 루프를 위 배치 호출로 교체 |
| `LevelExpService` | `getLevelTable()`에 인메모리 TTL 10분 캐시 (`volatile` + `List.copyOf`). 테이블 쓰기는 부팅 초기화(`LevelExpDataInitializer`)뿐이라 TTL은 안전망 |
| `FeedViewedEvent` + `FeedViewCountEventListener` (신규) | 조회수 증가를 `@Async("viewCountExecutor")` + `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution)` + `REQUIRES_NEW`로 이관. 원자 UPDATE(`incrementViewCount`) 유지. 실패는 로그+span error (notification 리스너와 같은 관례) |
| `AsyncConfig` | `viewCountExecutor` 신설 - 스레드 2~4·큐 5,000·**CallerRuns**(큐 포화 시 유실 대신 요청 스레드 역압)·종료 시 큐 소진 대기 10s·trace 전파. 큐 깊이는 Boot의 executor.* 자동 계측으로 관측 |
| `FeedController` / `FeedService` | 컨트롤러의 선행 `increaseViewCount` 호출 제거, `getFeed`가 이벤트 발행. `increaseViewCount` 메서드 삭제 |
| `FeedResponse.Detail.from` | `viewCount + 1` 보정 - 본인 조회 몫이 이 응답의 SELECT에는 안 실리므로. 화면 동작은 종전과 동일 |

예측 (반증 가능하게 박제): scroll 요청당 DB 쿼리 9→6 · Redis 왕복 ~20→1, detail 쿼리 −1
+ **요청 경로 커넥션 획득 2→1회**. 평시(journey-v2) scroll med 57.7ms에서 Redis 왕복 몫,
detail med 54.5ms에서 UPDATE tx 몫만큼 하락. 극한(T2-B)에서는 **acquire max·pending이
1번(이벤트화) 몫으로 유의미하게 내려가는 것이 예측**이고, 단가 16ms는 소폭(−1~2ms)만 움직인다.

수용한 트레이드오프 (1번 이벤트화): 극한에서 조회수 반영이 큐 적체만큼 지연될 수 있고
(CallerRuns라 유실은 없음 - 대신 그 순간 요청 지연으로 되밀림), 파드 강제 종료 시 큐 잔량
(최대 5,000)이 유실될 수 있다. graceful shutdown 10s가 롤링 배포의 유실 창을 막는다.

반증 조건: 위를 적용해도 T2-B 극한 단가(16ms)·p95가 안 움직이면 남은 병목은 직렬화/네트워크이고,
그때는 프로파일러(async-profiler)로 내려간다. 평시 지연(55ms)의 배분(쿼리 n회 왕복 vs Redis 20 RTT)은
Tempo 트레이스 1건으로 확정 가능 - 적용 전 측정 항목.

## C-4. 피드 조회수 처리 비동기 이벤트 분리 (2026-08-23 구현 · 포트폴리오 서술)

> C-3 1번 항목의 전체 서술. 흐름: 문제 → 개선 → 적용 시 고려사항 → 기대 효과 → 핵심 판단.

### 문제

피드 단건 조회 시 콘텐츠 조회와 조회수 증가를 동일한 요청 흐름에서 처리하고 있었다.

```
GET /feeds/{feedId}
        │
        ├── 조회수 UPDATE
        │
        └── 피드 SELECT
                ↓
              응답
```

조회수 증가를 위해 쓰기 트랜잭션이 필요했기 때문에, 읽기 중심인 피드 조회 요청이
DB UPDATE까지 완료한 이후 응답하는 구조였다.

트래픽이 증가하면 조회수 UPDATE가 DB Connection과 애플리케이션 Thread를 추가로 점유하여,
피드 조회 자체의 처리 지연으로 이어질 가능성이 있었다.

### 개선

조회수 증가를 `FeedViewedEvent`로 분리하고, 피드 조회 요청의 Critical Path에서 제거했다.

```
GET /feeds/{feedId}
        │
        ├── SELECT (readOnly)
        │
        ├── Commit
        │
        └── 응답
             │
             └── FeedViewedEvent
                    ↓
                  @Async
                    ↓
              REQUIRES_NEW
                    ↓
          UPDATE view_count + 1
```

피드 조회는 readOnly 트랜잭션으로 유지하고, 조회수 증가는 AFTER_COMMIT 이후
별도 트랜잭션에서 비동기로 처리한다.

### 적용 시 고려사항

**1. Spring 비동기 처리 함정**

이벤트 기반으로 변경하더라도 설정을 잘못하면 의도한 동작이 보장되지 않는다.

- `@Async` 누락 시 이벤트가 동기 처리되어 기존 구조와 동일하게 동작
- AFTER_COMMIT 이후 DB UPDATE를 수행하기 위해 별도 `REQUIRES_NEW` 트랜잭션 사용
- 비동기 처리 중 발생한 예외는 원래 HTTP 요청으로 전파되지 않으므로
  실패 로그와 처리량 모니터링 추가

**2. 조회수의 Eventual Consistency 허용**

조회수는 피드 본문과 달리 수 ms 단위의 즉시 반영이 필수적인 데이터가 아니므로
비동기 처리를 적용했다.

```
평상시
조회 요청 → 이벤트 처리 → 조회수 반영
             거의 즉시

고부하 상황
조회 요청 → 이벤트 대기 → 조회수 반영
                     ↑
                  수 초 지연 가능
```

따라서 조회 API의 응답 성능을 개선하는 대신, 조회수 반영 시점이 지연될 수 있다는
트레이드오프를 수용했다.

**3. 정합성 및 장애 대응**

조회수는 단순히 엔티티를 조회한 뒤 +1하여 저장하지 않고 기존의 원자적 UPDATE를 유지한다.

```sql
UPDATE feed
SET view_count = view_count + 1
WHERE id = ?
```

이를 통해 동시에 여러 조회 이벤트가 발생해도 조회수 증가가 서로 덮어써지는 문제를 방지한다.

또한 애플리케이션 재시작이나 배포 과정에서 대기 중인 이벤트가 유실될 가능성을 고려하여
graceful shutdown을 적용해 유실 가능성을 최소화한다.

응답에 표시되는 조회수는 현재 요청에 의해 발생한 증가분을 반영하여, 비동기 처리 시점과
관계없이 사용자에게 자연스러운 값을 제공한다.

### 기대 효과

| 항목 | 기존 | 개선 |
|---|---|---|
| 피드 조회 | SELECT + UPDATE | SELECT |
| 조회수 처리 | 동기 | 비동기 이벤트 |
| 조회 요청의 UPDATE 대기 | 발생 | 제거 |
| 조회 요청의 DB Connection 점유 | 상대적으로 증가 | 감소 |
| Tomcat Thread 점유 시간 | 증가 가능 | 감소 가능 |
| 조회수 반영 | 즉시 | 비동기 |
| 데이터 일관성 | 강한 일관성 | Eventual Consistency |
| 고부하 대응 | 조회수 UPDATE 영향 받음 | 조회 경로와 분리 |

### 핵심 판단

조회수 증가 자체의 DB 작업량을 없앤 것이 아니라, 사용자에게 피드 데이터를 반환하는
Critical Path에서 부가적인 쓰기 작업을 제거했다.

이를 통해 높은 동시성 환경에서 피드 조회 요청이 조회수 UPDATE와 DB Connection 및
Thread를 두고 경쟁하는 시간을 줄이고, 읽기 요청의 처리 지연과 요청 대기열 증가를
완화하는 방향으로 구조를 개선했다.

성능 개선 효과는 적용 전후 부하테스트에서 p95 응답시간, CPU 사용률, Hikari Connection
Pool 대기, Tomcat Busy Thread를 비교하여 검증한다. Before는 T2-B 재실행 10
(337 rps · med 302ms · Hikari pending 174 · acquire max 9.1s)과 journey-v2 기준선
(detail med 54.5ms)이고, 배포 후 동일 조건 재실행이 After가 된다.

### 구현 (toy-content `ca93bca`)

| 요소 | 내용 |
|---|---|
| `FeedViewedEvent` | feedId를 담은 record - 조회 트랜잭션은 publish만 한다 |
| `FeedViewCountEventListener` | `@Async("viewCountExecutor")` + `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)` + `@Transactional(REQUIRES_NEW)` + 원자 UPDATE. 실패는 로그 + span error |
| `viewCountExecutor` | 스레드 2~4 · 큐 5,000 · CallerRuns(포화 시 유실 대신 역압) · 종료 시 큐 소진 10s 대기 · trace 전파 · Boot executor.* 자동 계측 |
| 응답 보정 | `Detail.from`에서 `viewCount + 1` - 본인 조회 몫이 SELECT에 안 실리므로 |

## 결론 - "그럼 CPU를 늘려야 하나"에 대한 답: 지금은 문제가 아니다

캐시 After까지 끝난 시점의 현실 점검:

```
실서비스 평시 트래픽:  ~15 rps  (journey-v2 기준선 실측 · 실패 0%)
현재 시스템 용량:      ~305 rps (T2-B 극한 실측)
여유:                 약 20배
```

**CPU 증설은 해법이 아니라 시기의 문제이고, 그 시기가 아니다.** 수요 없이 늘리는 것은
비용이지 개선이 아니다. 대신 이번 주 작업이 "늘려야 할 때"의 조건을 바꿔놨다:

| | 이번 주 전 | 지금 |
|---|---|---|
| 같은 하드웨어의 용량 | 176.7 rps | **305~314 rps (+73%)** - 설정·토폴로지·코드로 |
| 증설 비용 | medium 추가 ~$38/월 | **스팟 small ~$5/월** + 라벨 한 줄 (디플로이먼트 무수정) |
| 증설의 선행 조건 | 불명 | 특정됨 - RDS 커넥션 재설계 (`minimum-idle` 축소 + 필요시 max_connections) |
| 남은 공짜 레버 | 불명 | 특정됨 - **CPU-1 경로별 단가 분해** (scroll·detail ~20ms의 내역: 직렬화·LAZY·페이로드 중 무엇인지 미측정) |

증설이 필요해지는 신호와 그때의 순서까지 박제해 둔다:
**평시 트래픽이 용량의 ~30%(90 rps)에 접근하면 → ① CPU-1 분해로 코드 절감 여지 확인
→ ② min-idle 축소로 RDS 예산 확보 → ③ 스팟 노드 추가.** 이 순서를 건너뛰고 ③부터 하면
비싼 코드를 코어로 선형 구매하게 된다 - 이번 주 내내 반복 확인된 원칙(코드 > 설정 > 스펙)이다.
