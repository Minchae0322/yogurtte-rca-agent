# 라우팅개선 - 자원을 늘리기 전에 분배를 고쳤어야 했다 (ewma)

> EC2 분리(자원 계층)로 얻은 +23%와 별개로, 실측 데이터는 처음부터 **분배(라우팅) 결함**을
> 가리키고 있었다. 이 문서는 그 판단의 이유와 근거, 그리고 ewma 전환의 검증 기록이다.
> 실행 상세(적용 명령·백업·리로드 확인)는 [인프라개선.md D-1](인프라개선.md)이 SoT이고,
> 이 문서는 "왜 이것이 EC2 분리보다 먼저였어야 했나"의 서사와 검증 결과를 담는다.

## 상황

| 항목 | 내용 |
|---|---|
| 배경 | T2-B 시리즈 11회 동안 처방은 매번 자원(노드 정리·replica·EC2 분리)이었다 |
| 자원 처방의 성과 | content 전용 spot 노드 분리로 처리량 195.6 → 241.2 rps(+23%), 실패율 0.25% → 0.03% ([cpu총개선.md](cpu총개선.md)) - 성과 자체는 실측으로 확인됨 |
| 남아 있던 결함 | ingress-nginx `load-balance` 미설정 = 기본 **round_robin**. 파드가 느려지든 멈추든 같은 몫을 계속 받는다 |
| 관측된 증상 | 파드별 유입·부하 쏠림이 회차마다 재현 (아래 근거) |
| 변경 | ConfigMap `load-balance: ewma` 1줄 - 비용 0, 무중단 적용 완료 (2026-08-25) |
| 결과 | 검증 1회 완료 (2026-08-30) - **실패 601건 → 0건, 단일 파드 버스트 미재현** (아래 §검증 결과) |

## 무엇이 일어났나

### 근거 1 - 파드 하나는 놀고 있었다 (분배는 균등, 능력은 불균등)

300 VU 수용성 측정에서 파드별 유입이 **146 / 146 / 99 rps**. 재실행 10에서는
busy threads가 **193 / 81 / 200**. 한 파드는 한가한데 round_robin은 파드 상태를
보지 않으므로 느린 파드에도 같은 몫이 계속 꽂혔다. 최악 노드가 바뀌어도
(42-158 → 40-241) "느린 쪽이 같은 몫을 받아 무너지는" 패턴 자체는 매번 재현됐다.
즉 **CPU 총량 부족이 아니라 분배 결함**이 실패 지점을 만들고 있었다.

### 근거 2 - 실패 601건은 전량 한 파드의 버스트였다

재실행 11의 실패 601건(k6 기준)을 초 단위로 분해하면, 유지 구간 4분은 실패 0이고
**전량이 종료 구간 한 파드(wd4jd)의 5초짜리 버스트 2회**(17:17:18~22, 17:17:28~31)에서
나왔다. 파드 로그는 `SQLTransientConnectionException ... timed out after 10000ms
(total=12, active=12, waiting=16)` - Hikari 10초 상한에 걸린 대기자들의 동반 500이다.

그 창의 요청 분배는 파드당 1/3(141.4 rps), CPU도 ±6%로 균등해서 "인그레스 편중"
가설은 그 회차에선 기각됐다. 남은 유력 정황은 그 파드만 기록한 **major GC pause
0.401s**(타 파드 0/0.3s, GC 로그 미활성이라 미확정). 여기서 문제의 성격이 드러난다:

**원인이 편중이든 GC 스톨이든, round_robin은 파드가 일시적으로 멈춰도 계속 같은
몫을 밀어넣는다.** 0.4초 정지가 한계 부근의 풀 FIFO 대기에 얹히면 10초 상한을
넘기는 요청이 무더기로 생긴다. 스톨 자체를 없애는 것과 별개로, **스톨 난 파드로
덜 보내는 장치**가 없었다 - 그것이 라우팅 계층의 자리다.

### 왜 EC2 분리보다 먼저였어야 했나

| | EC2 분리 (자원) | ewma (제어) |
|---|---|---|
| 비용 | 노드 추가 (spot이라 절감했지만 구조 변경) | **0 - 설정 1줄** |
| 푸는 문제 | CPU 총량 부족 | 총량이 충분해도 생기는 **쏠림에 의한 실패** |
| 근거 1·2에 대해 | 무력 - 노드를 늘려도 느린 파드에 같은 몫이 간다 | 정면 해법 - 느린 파드에 덜 보낸다 |

자원 처방이 틀린 것이 아니라(실측 +23%는 진짜다) **순서가 뒤였다.** 비용 0의 제어
수단으로 "같은 하드웨어에서 꼬리와 실패가 어디까지 내려가는가"를 먼저 확인한 뒤에
자원을 늘렸어야, 자원 추가분이 무엇을 산 것인지 분리 증명이 된다.
([개선점.md](개선점.md) 총평 - 9개 제어 수단 중 6개가 비용 0이었고 이것이 1순위)

## 무엇을 바꿨나

① 변경: ConfigMap `ingress-nginx/ingress-nginx-controller`에 `load-balance: ewma`
(전역 기본값. 적용 명령·백업·롤백은 [인프라개선.md D-1](인프라개선.md) §적용 내역)

② 신호 도달 확인 (2026-08-25 실측): 컨트롤러 `Backend successfully reloaded`,
실사용 트래픽 200 유지(3개 파드 분산 확인), 내부 스모크 200/195ms. **무중단 적용 완료.**

③ 검증 설계 - 한 번에 하나만: 직결(nginx) 경로 **T2-B 500 VU 재실행 1회**.
앱 코드 `ca93bca`·노드·replica·풀 설정 전부 동결, 이 설정 하나만 바뀐 상태로
재실행 11과 대조한다.

④ 반증 조건

- 파드별 유입·busy threads 편차가 그대로 → 쏠림 원인은 분배가 아니라 상류
  (커넥션 재사용·keepalive)로 재지목, 이 변경은 효과 없음으로 기록
- 실패 버스트가 그대로 재현 → 원인은 GC 스톨 자체. 다음 수는 GC 로그 활성화 + 힙 튜닝
- 주의: ewma는 스톨을 없애지 않는다. 기대 효과는 처리량 상승이 아니라
  **꼬리(p99)와 실패 버스트의 감소**다. 처리량이 크게 오르면 오히려 다른 변수를 의심한다

**판정 (N=1 · 확정 아님):** 이번 검증의 표적이던 **실패 버스트가 재현되지 않았다**(601→0).
반증 조건 "실패 버스트가 그대로 재현되면 GC 스톨이 원인"에는 해당하지 않았고, 전 회차
버스트 파드가 최소 몫을 받은 것은 ewma의 기대 동작과 부합한다. 다만 두 가지 이유로
"ewma가 막았다"고 확정하지 않는다: ① GC 스톨은 확률 사건이라 이번 회차에 스톨 자체가
없었을 가능성을 배제 못 함 (GC 로그 미활성 지속) ② 경로가 CF 경유 → 직결로 함께 바뀌어
순수 단독 대조가 아님. 확정하려면 직결 조건 반복 재실행(N≥2)과 GC 로그 활성화가 필요하다.

부수 발견 (이번 실행에서):

- **직결 부하는 ingress rate limit에 먼저 걸린다** - `api-ingress`의 IP당
  `limit-rps: 30`이 단일 IP 부하를 503으로 잘랐다(웜업 실패율 97%로 발견). CF 경유
  회차들은 소스 IP 분산으로 안 걸리던 제한이다. 레포에 문서화된 시험용 상향
  (README §리밋 시험용 상향, rps 2000)을 적용 후 진행했고, 시험 종료 후 평시값 원복.
  **직결 시험 체크리스트에 "리밋 상향" 추가 필요.**
- 관측 spot 노드(ip-172-31-33-159)가 `kubectl top`에서 `<unknown>` - metrics-server
  미보고. 별건으로 확인 필요.
