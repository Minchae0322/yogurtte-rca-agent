### 감점 24점이 어디에 있었는가 — 채점자가 실측으로 찾았다

**결함 ④가 막은 것이 정확히 무엇인지 이번엔 숫자로 말할 수 있다.**

| 감점 | 항목 | 앵커가 요구한 신호 | **실제로 있었나** |
|---|---|---|---|
| −10 | 1) content 캐시 히트 미지목 | content가 왜 멀쩡한가 | ✅ 있었다 |
| −7 | 2) ⓑ user-service 호출 span 없음 | 스팬 부재 | ✅ 있었다 |
| −5 | 4) content TTL 동안만 무영향 | 피드 200 유지 | ✅ 있었다 |
| −2 | 6) TTL 만료 시 저하 예고 | (위에서 파생) | ✅ 있었다 |

**채점자 실측** — 장애 #1 한복판(01:29:57.127Z)의 피드 읽기 `6a69579560583a7e528a3d7eeb7026b1`:

```
http get /feeds/scroll                    55.59ms   200
 └ secured request (53.62ms)
    └ connection (51.57ms)
       ├ query ×7 + result-set ×7                 ← 피드 본문·첨부 조회
       └ GET ×4  (0.34 / 0.40 / 0.57 / 0.34ms)    ← Redis = user 캐시 히트
27 spans · 전부 content-service · auth/user 호출 span 0건
```

**앵커 ⓑ가 요구한 "user-service 호출 span 없음"이 문언 그대로 있었다.**
`{ name =~ "http get /user.*" }` 검색도 창 전체에서 **0건**이다.
즉 이 회차는 **캐시 히트 갈래(갈래 A)가 교과서적으로 성립**했고, 앵커는 부적합이 아니었다.

**에이전트가 못 본 이유는 유실이 아니라 도구 경로다** (AP-2 회차 2와 동일).

1. 탐색 스윕은 Tempo를 `{ status = error }`로만 검색한다 → auth 다운 구간에 에러 트레이스가
   없으니(요청이 auth에 **도달조차 못 함**) traceId가 안 잡힌다. **이 판단 자체는 정답이다.**
2. `Scope`에 traceId가 없으면 심층 수집이 **Tempo를 통째로 건너뛴다** → `trace: 0B / 0 spans`, `tempo 0ms`.
3. 그래서 **정상 트레이스까지 함께 버려졌다.**

> **수정하면 오를 자리가 24점 있다.** 단 *"user span이 없다 → 캐시 히트다"* 를 에이전트가
> 실제로 연결하는지는 별개 문제이고, 그것이 다음 회차가 시험할 내용이다.
> **신호의 존재는 확인됐고, 해석 능력은 아직 미측정이다** — 이 구분이 AP-1·AP-2 예측이
> 반증된 지점이었다.

### ⚠️ 종료 원인 오귀인은 앵커가 잡지 않는다 — 그리고 실측으로 반증됐다

에이전트의 1순위는 **"재시작 루프"**, 2순위는 **"OOMKilled / liveness probe 실패 / eviction"** 이다.
**둘 다 틀렸다.**

**채점자 실측** (kube-state-metrics — 데이터소스에 있으나 수집기 쿼리 목록엔 없다):

```
kube_deployment_spec_replicas{deployment="auth-service"}
  01:20:00 = 1  →  01:29:30 = 0  →  01:30:30 = 1  →  01:33:30 = 0  →  01:34:30 = 1
kube_pod_container_status_restarts_total{pod=~"auth-service.*"}
  45fxb = 0      x7rtr = 0      wf6c7 = 0        ← 컨테이너 재시작 0건
```

**재시작이 아니라 의도적 scale 0 → 1이 두 번**이다. 재시작 카운터는 내내 0이다.

**그런데 이 오귀인은 채점에 반영하지 않았다.** AU-2 앵커의 5) 오귀인 요건은
*"content 미지목 + ingress 오인 안 함"* 뿐이고, **"왜 죽었는가"의 오귀인은 요건에 없다.**
앵커에 없는 잣대를 끌어오면 §8상 그 회차가 무효가 되므로 감점하지 않는다.

**그리고 에이전트는 이 답을 얻는 방법을 정확히 알고 있었다:**

> 조치 3 — *"`kube_pod_container_status_restarts_total{pod=~"auth-service.*"}` (재시작 횟수·주기) …
> `kube_deployment_spec_replicas{deployment="auth-service"}` — **레플리카 1개 가정 검증**"*

**채점자가 그대로 실행해 답을 얻었다.** AP-2 회차 2의 조치 1(레벨 무관 전체 로그 조회)과
**같은 패턴이 세 번째로 반복된다** — *에이전트는 막힌 채널을 뚫는 정확한 다음 수를 알고 있고,
도구가 그 수를 실행해 주지 않는다.*

> **🔴 앵커 결함으로 등재한다.** AU-2 앵커의 오귀인 항목이 **이 문항에서 실제로 발생한

> 현실적 실패 모드인데, 요건이 content·ingress만 본다. 다음 회차부터 적용할 개정 후보:

| 대조군 (B) | "chat·content의 up은 전 구간 연속 · 단일 pod 유지" | ✅ **앵커 문언 그대로** |
| 오탐 | 창 안의 **AP-3 주입 에러 트레이스**(content `http post /feeds`, 00:56:32Z)를 **자력 기각** | ✅ |

**루브릭 v3가 신설 근거로 든 시험을 통과했다.** rubric-v3 §3은
*"탐색 앞단이 에러 트레이스 검색만 하면 12문항 중 6문항을 원리적으로 못 찾는다"* 며
AU-2를 **메트릭 채널 문항**으로 분류했다. 이번 회차가 그 분류의 첫 실증이다 —
선정 이유 6줄 중 **4줄이 `up` 시계열**, 1줄이 Loki 버킷, 1줄이 트레이스 부재였다.

**AP-2 회차 2에 이어 두 번째로 "traceId를 지어내지 않았다."** 그리고 이번엔 창 안에
**다른 문항의 주입(AP-3)이 오답으로 남아 있었는데** 그것을 고르지 않았다 —
근거는 *"auth-service 트레이스는 0건 — 로그인 실패 구간에 auth 트레이스가 아예 생성되지 않음"*.

> **단 탐색이 잘한 만큼 수집이 못 받았다.** S 판정은 *무엇을 보러 갔는가*이고
> (v3 §3 F5/F6 분리), 못 받은 것은 2)에서 이미 −7로 벌했다. 같은 실패를 두 번 깎지 않는다.
> **AP-2 회차 2에서 채점자 판정으로 처리했던 이 논점이, 이번엔 앵커 문언만으로 결정됐다** —
> AU-2 앵커의 8점 문언("content 트레이스만 보고 정상으로 종결")이 실제 행동과 명확히 다르기 때문이다.

## 다음 회차로 넘기는 것

1. **🔴 결함 ④ 수정 — 이 문항이 가장 큰 델타를 가진다.** traceId가 없을 때 수집기가
   **(창 + 서비스) 기준으로 status 무관 Tempo 검색**을 하도록. **오를 자리 24점이 실측으로 확인됐다.**
   수정 후 AU-2를 재조사하면 **결함 ④의 기여를 단독으로 분리**할 수 있다(입력 모델·앵커 고정)
2. **🔴 앵커: AU-2에 종료 사유 오귀인 축 추가** — 실제 발생한 오귀인(재시작 루프/OOMKill)을
   현행 요건이 못 잡는다. AP-2(조치 갈래 ㄴ)·AP-3(중간 구간)와 함께 처리
3. **🔴 주입 1회로 고정** — 2회 주입이 "재시작 루프" 오해를 만들었다. 회차 간 비교를 위해 사양 준수
4. **B-4(수집 창이 복구를 담도록)** — 이번엔 운으로 피했다. 1회 주입으로 돌아가면 다시 걸린다
5. **수집 메트릭에 kube-state-metrics 추가 검토** — `kube_deployment_spec_replicas` ·
   `kube_pod_container_status_restarts_total`. 둘 다 데이터소스엔 있고 쿼리 목록엔 없다.
   **단 이건 변경군 A/B와 별개 축이므로 델타 측정 순서를 정한 뒤에 넣는다**
