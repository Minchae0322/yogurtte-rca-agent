## 1. 주입 구간에 트래픽을 붙였다 — `trigger_IN_1`

**회차 2에는 없던 절차다.** toy-content `chaos.sh`의 `run` 흐름은
`inject → trigger_<ID>(있으면) → hold_pre → measure` 인데 **IN-1만 `trigger_`가 없어**
`IN1_HOLD_PRE` 전체가 무트래픽 대기였다. 회차 2가 점수를 낸 것은 **그 창에 외부 트래픽이
우연히 겹쳤기 때문**이고, 겹치지 않으면 증상이 관측에 남지 않는다.

> **장애를 주입해도 그 구간에 요청이 없으면 증상은 존재하지 않는다.**
> CH-3에서 이미 실측된 실패 모드다 — [ch-3/round-3.md §5](../ch-3/round-3.md)의 *"채점 불가"* 시행이
> 같은 원인이었다(세 채널 무신호).

**적용 결과 (채점자 실측)** — 주입 구간 `01:43:44~01:46:18Z`:

```
Tempo { name =~ "http.*" }  →  89건 · 3초 초과 10건 · 최대 20,273ms
Loki  |~ "user-cache"       →  42줄, 전부 실패 (조회 실패 / 저장 실패)
Loki  {service_name="auth-service"}  →  10줄
Mimir up{job=redis}         →  전 구간 1 (익스포터가 또 못 잡았다)
Mimir websocket_active_users →  전 구간 0 (주입 전부터 — 대조 불가)
```

**앵커 2)③(미스→auth 직행)이 이번에 관측됐다** — 한 트레이스 안에서
`user:info:1` 조회 실패 → `http get /external/users?userIds=1,3,7,9,56` **119.3ms status 200**.

**채점 기준**: 5 = *"Redis 복구 + **캐시 재적재 확인**"* / 3 = *"복구만"*

| 요건 | 판정 | 리포트가 쓴 것 |
|---|:-:|---|
| Redis 복구 | 충족 | 조치 1 — `systemctl status redis` · `redis-cli ping` · **OOM kill 확인**(`dmesg \| grep -i oom`, `maxmemory`). 조치 2 — 재기동 후 `ConnectionWatchdog` 재연결·`[HTTP-SLOW]` 소멸 확인 |
| **캐시 재적재 확인** | **미충족** | 없다. 조치 10이 *"Redis 복구 후에도 재현되는지 먼저 확인"* 이지만 이는 **③ 원인 규명**이지 캐시 콜드 스타트 확인이 아니다 |
| 재발 방지 | 요건 밖 | 조치 6 `MGET`/파이프라인 · 조치 7 **서킷 브레이커** · 조치 8 **트랜잭션에서 Redis·HTTP 분리**(20.3초 커넥션 점유 근거) · 조치 9 **요청 단위 deadline** |
| 계측 보강 | 요건 밖 | 조치 3 `redis_up`·`redis_connected_clients` 추가 · 조치 4 *"60초마다 실패 중인데 알림이 없었다"* |

**→ 3점.** **회차 2와 정확히 같은 자리에서 같은 사유로 두 번째다.**

> **두 회차 다 재발 방지·계측 보강은 앵커가 요구하지 않은 수준까지** 냈는데
> (회차 2는 `MGET`·서킷 브레이커, 이번엔 거기에 deadline·트랜잭션 분리까지)
> *"캐시 재적재 확인"* 만 두 번 다 빠졌다.
> **N=2로 재현됐으므로 요건 쪽을 의심할 근거가 생겼다** — 관측으로 도달할 수 없는 요건인지,
> 프롬프트가 *"복구 후 확인 항목"* 을 안 묻는 것인지. → §5-3.
>
> 3구간 앵커(5/3/0)가 판정을 강요하는 문제도 회차 2가 이미 지적했다
> ([round-3 보류 목록 ㄷ·ㄹ](../round-3/README.md)).
