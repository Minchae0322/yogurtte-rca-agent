# 3. 왜 못 봤나 — 스윕 3채널 실측 대조

## 3.0 🔴 탐색 LLM이 실제로 받은 입력 전부 — `reports/raw/scan-1785300609-*` (회차 2)

**추정이 아니라 스윕 원본 아티팩트다.** 이것이 이 회차의 가장 강한 증거다.

| 채널 | 05:20:09 | ← **주입 05:22:01~38** → | 05:25:09 |
|---|---|---|---|
| `mongodb_up` | **1** | 두 샘플 사이로 빠짐 | **1** |
| `kafka_consumergroup_lag` p3 | **0** | 23초 지연이 5분 격자에 안 걸림 | **0** |
| Loki ERROR/WARN (chat) | — | | **1** ← **유일한 흔적** |
| Tempo `{status=error}` | **4건 전부** 05:01 · 05:02 · 05:30(무관 15ms) · 깨진 행 — **05:22 없음** | | |

`mongodb_up`은 창 전체에서 **0이 딱 하나**이고 그것이 05:00:09(=CH-1)다.
Loki 같은 계열 버킷은 **05:05 = 54 · 05:25 = 1**.

**에이전트가 시간을 잘못 고른 것이 아니라, 05:22를 가리키는 신호가 "1"이라는 값 한 칸뿐이었고
바로 옆에 54가 있었다.** 그리고 그 "1"은 버려진 것이 아니라 **좁힌 창 밖으로 밀렸다** —
탐색이 **단일 패스**라 가장 센 이상 하나를 고르면 끝이고, 약신호 구간은 재확인 없이 사라진다
(결함 ⑭ → [B-19](../round-3/README.md)).

> **CH-2 회차 2가 창 안 두 원인을 계층 분리해 100점을 받은 것과 대비된다.** 거기서는 두 원인이
> **둘 다 좁힌 창 안에 들어왔다.** **분석 단계는 받은 것 안에서는 잘한다 — 못 받은 것은 못 한다.**

## 3.1 Mimir — 23초 딥이 샘플 사이로 빠진다

회차 1의 스윕 창을 그대로 재현한 결과다.

```
mongodb_up  step=5m  창 04:45:40 ~ 05:45:40      ← 회차 1 스윕 창 그대로
  04:45:40 = 1     05:05:40 = 1     05:25:40 = 1
  04:50:40 = 1     05:10:40 = 1     05:30:40 = 1
  04:55:40 = 1     05:15:40 = 1     05:35:40 = 1
  05:00:40 = 0 ←CH-1     05:20:40 = 1  ┐         05:40:40 = 1
                                       ├ 05:22:15~38 이 사이로 빠진다
                         05:25:40 = 1  ┘         05:45:40 = 1
```

**주입은 스윕 창 안에 있었는데 샘플 격자에 안 걸렸다.** 15초 해상도로 다시 조회하면
05:22:37 스크레이프가 0으로 또렷이 나온다. **창의 문제가 아니라 해상도의 문제다.**

## 3.2 Tempo — 지연 채널이 아예 없다

`application.yml`의 스윕 설정은 `trace-query: '{ status = error }'` **단독**이다.
CH-3의 정답 트레이스는 **전 span 정상 종료**라 이 쿼리로는 원리적으로 0건이다.

**앵커가 이것을 이미 알고 있었다.** [anchors-v2 §탐색 채널 감사](../../../toy-content/docs/chaos/anchors-v2.md):

| 문항 | 정답 대상 (S) | 도달 채널 | 트레이스로 잡히나 |
|---|---|---|---|
| CH-3 | 200 성공인데 공백이 큰 트레이스 | **Tempo 지연 기준** | ⚠️ **error로는 안 걸림** |

그리고 CH-3 앵커의 3) 탐색 만점 요건도 문언 그대로
*"**S = 200 성공이면서 duration 이상한 트레이스**(지연 채널)"* 다.
**요구된 채널이 도구에 구현돼 있지 않다.**

## 3.3 에이전트는 창 안에서 할 수 있는 것을 했다

두 회차 모두 결론을 과장하지 않았다. 회차 2는 스스로 이렇게 적었다:

> *"'앱이 버벅였다'는 증상과 이 트레이스의 인과는 **관측 데이터로 확정할 수 없음**"*
> *"사용자 제보 시각을 재확인 — 13:59~14:04(알림 실패)인지 14:06~14:15(알림 지연)인지"*

**제보 시각을 되물었다.** 증상 문안이 가리키는 사건을 특정하지 못했음을 인지하고 있었다는 뜻이다.
[round-3 능력 결함 '가'](../round-3/README.md)(*"장애 서비스 밖을 스스로 보지 않는다"*)와는 다른
성격이다 — 여기서는 **볼 대상 자체가 컨텍스트에 없었다.**

## 4.3 🔴 최초 판정을 뒤집었다 — "채점 불가"는 틀렸다

최초 판정은 *"**채점 불가** — 신규 범주(도구 요건 미충족)"* 였다. 근거는 *"부분점 문언이 전부
CH-3 진술을 전제하는데 진술이 없으니 어느 칸에도 못 넣는다"* 였다. **틀렸다.**

| | 최초 판정 | **정정** |
|---|---|---|
| 진술이 없으면 | 칸에 못 넣는다 → 채점 불가 | **요건 미충족 = 0점.** 점수는 *충족한 만큼* 준다 |
| 0점 칸의 성격 | 해당해야만 0이 되는 **게이트** | 전형적 0점 행동의 **예시**. 게이트가 아니다 |
| "도구 요건 미충족" | 새 채점 범주 | **앵커 밖 잣대.** §8상 무효 |

**세 가지가 이 정정을 강제한다.**

1. **"채점 불가"의 정의가 다르다** — 이 대장에서 채점 불가는 **앵커가 그 회차 전개를 표현하지
   못하는 경우**(유형 A·B·C)다. CH-3 앵커는 멀쩡하다(§1.2에서 만점 요건 4요소 실재 확인).
2. **[CH-2 회차 2 정정](../scoring/README.md)이 금지한 행위다** — *"앵커에 없는 잣대를 끌어오면
   그 회차가 무효다."* "도구 요건 미충족"은 앵커에도 루브릭에도 없고 채점자가 만든 범주다.
3. **루브릭 v3가 탐색 15를 신설한 이유가 정면으로 이것이다** — 탐색 실패로 분석이 성립하지
   않는 것은 **측정 실패가 아니라 측정 결과**다. 채점 불가로 빼면 v3가 재려던 것을 못 잰다.

**도구 결함(⑫·⑬·⑭)은 점수의 원인이지 면제 사유가 아니다.**
**v0.1은 20~25초 장애를 못 찾는다 — 그것이 이 4점의 내용이다.**

## 4.4 🏆 §8.1을 완전히 충족하는 최초의 회차 쌍 — **평균 4 ± 0**

| §8.1 요건 | 충족 |
|---|---|
| 같은 **문항** | ✅ CH-3 · 같은 주입 1건 |
| 같은 **자** | ✅ anchors-v2 `add5aff` · 루브릭 v3 · 도구 상태 동일 |
| 같은 **입력 모델** | ✅ 자연어 · **문안 문자 그대로 동일** |
| N ≥ 2 · 편차 ±10 이내 | ✅ 2회 · **편차 0** |

**이 프로젝트 최초의 인용 가능한 점수이고, 그 값이 4다.** 지금까지 "인용 가능한 점수 0개"였던
것은 회차마다 자나 입력 모델이 함께 바뀌었기 때문인데 이번에는 전부 고정됐다.

**AU-4의 N=2와 성격이 다르다.**

| | AU-4 회차 1·2 | **CH-3 회차 1·2** |
|---|---|---|
| 재현된 것 | 원인 30 — **추론의 실패** | 총점 4 — **감지의 실패** |
| 통제 변수 | 입력 모델·출력 분량이 **바뀌었다** | **전부 동일** |
| §8.1 지위 | 항목 단위 재현 | **완전 충족** |

> **⚠️ 두 회차는 완전히 독립적이지 않다.** 4분 간격이고 같은 주입 데이터를 본다. 스윕 입력이
> 사실상 동일했으므로(탐색 in 49,826 / 49,820) 편차 0은 당연한 결과에 가깝다.
> 재현된 것은 *"다른 날 다시 해도 4"* 가 아니라 **"같은 조건에서 결정적으로 4"** 이고,
> **§8.1이 원래 재려던 실행 간 분산은 이 쌍으로 측정되지 않는다.** 인용 시 함께 밝힌다.
