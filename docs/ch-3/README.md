| | |
|---|---|

### 왜 다운을 30초 미만으로 잡나

경계를 가르는 것은 엄밀히는 *트리거 발사 시점에 남은 다운 시간*이 드라이버 서버 셀렉션 대기
상한(30초)보다 짧은가다. 그런데 **다운 자체가 30초 미만이면 트리거가 다운 중 어느 시점에
발사되든 남은 시간이 자동으로 30초 미만**이라, 조건이 무조건 성립한다.

CH-1 회차 1은 **73초** 다운에서 트리거가 복구 23.4초 전에 *우연히* 떨어져 경계 안이 됐다.
재현되지 않는 설계다. 다운을 짧게 가져가면 **트리거 타이밍 파라미터화가 불필요**해지고,
두 문항이 **다운 시간 하나로만** 갈린다.

| | 주입 | 트리거 |
|---|---|---|
| **CH-1** (경계 밖) | 다운 **≥ 5분** | 주입 직후 |
| **CH-3** (경계 안) | 다운 **20~25초** | 주입 직후 |

20~25초를 택한 근거: ① 30초 경계에서 5~10초 마진 — 드라이버가 정확히 30.0초에 던지는 것은
CH-1 회차 2에서 실측됨(30.0초×4회) ② 공백 ~20초는 자식 span 합(~1초)의 20배라 관측이 뚜렷
③ 트리거 도달 지연은 실측 약 0.1초(POST 72.75ms + publish 18ms + 핸드오프 1.45ms)라 여유 충분.

**질문 문구가 이 문항의 절반이다.** 같은 트레이스라도 "알림이 **안** 왔어요"(CH-1·IN-2)와
"알림이 **늦게** 왔어요"(CH-3)는 정답이 다르다. 지연을 유실로 답하면 영향 판정 오류이고,
그 반대도 마찬가지다. 질문에 원인 힌트를 넣지 않는다 — "Mongo가 느렸나?"는 평가 오염이다.

## 2. 이 문항이 어려운 이유

**에러 span이 하나도 없다.** 전 구간 성공이고, 사용자는 200을 받았고, 알림도 도착했다.
유일한 신호는 **"자식으로 설명되지 않는 공백"**이다.

이는 실전 조사 1호(dispatch 996ms 중 994ms 미계측 갭)와 **같은 유형**이고,
[strategy.md](../strategy.md)의 **(c)유형 실패**(위치는 특정하나 원인 확정 불가)에 직결된다.

**CH-1과 서로 대조군이다** — 같은 주입·같은 경로인데 트리거 타이밍 하나로 정답이 갈린다.
"에이전트가 지연과 유실을 구별하는가"를 직접 시험한다.

## 4. 채점 앵커 (DRAFT · v0)

### 근본 원인 (40)

**만점 원인 1줄:**

> Mongo 미가용 구간이 컨슈머의 첫 Mongo 작업과 겹쳤고, **드라이버 서버 셀렉션 대기(상한 30초)
> 안에 Mongo가 복구되어 그 첫 시도가 예외 없이 성공**했다 → 알림은 **지연 도착, 유실 0**.

네 요소: ① 원인이 **Mongo 미가용** ② 대기 지점이 **첫 Mongo 작업 직전**
③ **드라이버 서버 셀렉션 대기 중 복구** ④ **예외 없이 통과 = 지연이지 유실 아님**

| 점수 | 요건 |
|---|---|
| **40** | 네 요소 전부 |
| **30** | ①②③ 충족, ④(유실 아님) 미명시 — 또는 성공 경로를 **"리스너 재시도로 성공"으로 오독**(실제는 첫 시도가 대기 후 성공). 결론은 맞고 메커니즘만 틀린 경우 |
| **20** | 공백 **위치는 특정**했으나 원인을 Mongo로 **확정 못 함**(가설·확신도 낮음) |
| **10** | 영향을 **유실/미도착으로 오판** (실제는 지연 도착) — 오판은 미판단보다 무겁다 |
| **0** | "이상 없음 / 장애 근거 없음"으로 결론 · content 또는 Kafka를 원인으로 지목 |

> **⚠️ 두 가지를 요건에 박지 않는다 — 실측과 다르기 때문이다.**
>
> **(1) "30초 안으로 다운"** — 30초는 **다운 시간이 아니라 드라이버 대기 상한**이다.
> 회차 1의 실제 다운은 **73초**였고, 갈래를 가른 것은 *트리거 발사 시점에 남은 다운 시간*
> (23.4초)이 그 상한보다 짧았다는 점이다. 다운 길이를 요건에 쓰면 같은 갈래인데도
> 초 수가 안 맞아 채점이 깨진다.
>
> **(2) "재시도에서 성공"** — 리스너 재시도(`FixedBackOff` 3회)와 DLQ는 **예외가 나야**
> 발동하는데 예외 자체가 없었다. 실측은 **첫 시도가 대기 후 그대로 성공**이다.
> 이 구별은 트레이스로 관측 가능하다 — 경계 안은 `process-notification` span이 **1개**,
> 경계 밖(CH-1)은 `receive` span이 **4개**다. 따라서 "재시도로 성공"은 오독이며 30점 구간에 둔다.
>
> 두 문언 모두 AU-4를 채점 불가로 만든 **유형 C**(코드·추측을 실측으로 착각)의 재발 지점이다.
