## 🔴 A-1(로그 접두사 규약)의 첫 실전 확인

오늘 배포된 `[user-fallback]` 접두사가 **2) 근거 만점을 만들었다.**

> *"content-service ERROR 로그 원문 (14:09:25.8Z):
> `c.e.t.e.u.s.ExternalUserApiClient - **[user-fallback] auth 목록 조회 실패 → 4명 익명
> 대체: userIds=[1, 3, 7, 9]**`
> → '작성자 이름이 이상하게 보인다'는 제보와 직접 대응하는 **유일한 관측값**."*

**증상과 로그가 한 줄로 이어졌다.** 회차 2에서는 fallback 로그가 문구 3종으로 흩어져
있었고(하네스 프로브가 0건으로 오보고한 원인), A-1이 그것을 접두사 하나로 묶었다.
게다가 **몇 명이 익명으로 바뀌었는지(`4명`)와 누구인지(`userIds=[1,3,7,9]`)** 까지 실려
영향 판정의 재료가 됐다.

### 2) 근거 — 25점 만점

| 점수 | 요건 |
|---:|---|
| 25 | ⓐ **실패 방식 구별**(즉시 거절 23.5ms vs 3s timeout) + ⓑ **fallback 로그** |
| 18 | 둘 중 하나 |
| 10 | 500·익명만 인용 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| ⓐ 실패 방식 구별 | 충족 | *"소요 **22.6ms** — **타임아웃이 아니라 즉시 거절**(Connection refused). 즉 Service VIP는 살아있으나 **뒤에 Ready 상태의 파드가 없었다**는 신호"* |
| ⓑ fallback 로그 | 충족 | `[user-fallback] auth 목록 조회 실패 → 4명 익명 대체: userIds=[1, 3, 7, 9]` **축자 인용** |
| (부가) client span 전문 | 충족 | `http.url=http://auth-service:8081/api/external/users?userIds=1,3,7,9` · `error=finishConnect(..) failed: Connection refused: …10.43.13.21:8081` · `status=CLIENT_ERROR` |

**→ 25점.** 18점 문언("둘 중 하나")과 갈리는 지점이 **둘을 다 했는가**인데 둘 다 했다.
**문언 이상**: 즉시 거절의 의미를 *"Service VIP는 살아있으나 Ready 파드가 없다"* 로 해석해
쿠버네티스 계층까지 짚었다.

### 3) 탐색 — 15점 만점

앵커: **S = `http get` client span `STATUS_CODE_ERROR`** + B(정상 구간 auth 호출 span 대조).

| 축 | 판정 | 근거 |
|---|---|---|
| **T** 시간창 | 충족 | 좁힌 창 13:40:00~14:17:11Z — 다운 구간(14:00~14:11:30Z) **포함** |
| **S** 대상 선정 | 충족 | INC-11 evidence — *"content-service `http get /feeds/scroll` 71ms **error** (14:09:25Z), 28스팬 중 **errorCount 1**, 실패 스팬은 22ms — **전체 조회는 성공했는데 내부 부가 호출 1건만 깨졌다(이름이 비거나 폴백될…)**"* |
| **B** 대조군 | 충족 | 정상 성공 호출(INC-9 · auth span 8개 · 2,785ms · `200/SUCCESS`)과 실패 호출(22.6ms refused)을 **분석에서 명시 대조** — *"이 느린 호출들은 모두 성공했고 해당 트레이스에는 `[user-fallback]` 로그가 없음"* |

**→ 15점.** S에서 **client span의 error 하나를 골라내고 그 의미까지 추론**한 것이 결정적이다
— *"이름이 비거나 폴백될"* 이라고 탐색 단계에서 이미 적었다.

### 4) 영향 판정 — 10점 만점

| 점수 | 요건 |
|---:|---|
| 10 | **저하(degraded)이지 붕괴(broken)가 아님** — 200 유지 + 익명 전환. fallback이 의도대로 버팀 |
| 5 | 유보 |
| 0 | 붕괴로 오판 · 또는 "정상"으로 판정 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| 저하 ≠ 붕괴 | 충족 | *"그런데도 상위 서버 span `http get /feeds/scroll`은 `status=200, outcome=SUCCESS`로 종료 → **에러가 사용자에게 노출되지 않고 잘못된(익명) 이름으로 200 응답이 나감**. 제보 양상(장애가 아니라 '이름이 이상함')과 일치"* |
| 범위 | **부분** | *"폴백 로그는 **1건**(userIds=[1,3,7,9])만 확보 … 영향 범위를 수치화할 수 없음"* |

**→ 10점. 판정이다.** 만점 문언이 요구하는 것은 **degraded/broken 판정**이고 그것을 확정했다.
남은 유보는 **건수 규모**에 대한 것이라 5점 문언(*"유보"*)이 가리키는 판정 자체의 유보와는
다르다고 읽었다. **반대 판정(5)이면 총점 83.**

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|

## 🔴 주입 사양 결함 — 폴백 창이 구조적으로 좁았다

**폴백은 트래픽이 있어야 발생한다.** RUNBOOK §6 AU-4의 판정 절차 자체가
`curl "$BASE/content/feeds/scroll?size=10" | jq '…nickname'` 으로 *"만료 전 실명 / 만료 후
사용자N"* 을 보는 것이다 — **요청을 날리는 것이 주입의 일부**다.

그리고 폴백이 **관측될 수 있는 창**은 다운 시간 전체가 아니다:

```
폴백 관측 창 = 다운 시간 − 캐시 TTL(10분)

이번 회차   11분 30초 − 10분 = 약 1분 30초    → 폴백 로그 1건
회차 2      22분      − 10분 = 약 12분        → 조건 양호
```

실제로 폴백은 **14:09:25Z**에 났고 다운은 **14:11:30Z**에 끝났다 — **2분 남았을 때** 겨우
한 건이 들어온 것이다. 리포트가 *"12분 다운타임 동안 다수 발생했을 것으로 보이나 … 영향
범위를 수치화할 수 없음"* 으로 유보한 이유가 이것이고, **4) 영향의 범위 축이 여기서 막혔다.**

**RUNBOOK 사양(`10분+ 유지`)이 TTL과 같아서 폴백 창이 거의 0이 된다.** 두 가지를 함께 고쳐야
문항이 재현된다.

| 고칠 것 | 어떻게 |
|---|---|
| **유지 시간** | `10분+` → **`TTL + 10분` 이상**(현재 TTL 10분이면 **20분+**). 폴백 창이 최소 10분은 열려야 한다 |
| **트래픽** | 다운 구간 **후반부**(TTL 경과 후)에 `scripts/api-sweep.sh`를 반복 실행. 주입 스크립트에 넣어 우연에 맡기지 않는다 |

**이것은 개정 대기열 ㅂ**(*"관측이 우연히 존재해야만 달성 가능한 요건 · 트래픽 운이 점수를
가른다"*)**의 다른 얼굴이다.** A-1(`[user-fallback]` 접두사)이 익명 전환을 **관측 가능**하게
만들었지만, **몇 건 찍히느냐는 여전히 트래픽에 달려 있다.**
