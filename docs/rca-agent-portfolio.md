# RCA-Agent

### Observability 기반 장애 원인 분석 Agent의 설계 · 검증 · 개선

작성 2026-08-07 · 근거는 전부 이 저장소의 회차 기록과 실측치다.
숫자마다 원문 링크를 달았고, **측정하지 않은 것은 "미측정"으로 적었다.**

---

## 1. 문제 정의와 시스템 설계

### 1.1 왜 만들었는가

장애 조사는 매번 같은 일을 반복한다 — 시간대를 좁히고, Trace에서 느린 구간을 찾고,
같은 traceId의 Log를 붙이고, Metric으로 범위를 확인한다. 세 채널을 오가며 상관을 세우는
작업 자체가 정형적이라 자동화 대상이 된다.

목표는 **Root Cause와 Evidence를 함께 내는 것**이다. "Redis가 문제입니다"가 아니라
"어느 신호로 그렇게 판단했는지"까지 리포트에 남아야 검증이 가능하다.

### 1.2 Architecture

```
POST /investigate  (자연어 질문)      POST /diagnose  (traceId)
        |                                    |
   [Triage]  Trace(error·slow) / Log 광역 / Metric 이상  3채널 스윕
        |
     Signal  ->  Incident  ->  창 · 대상 서비스 · 후보 traceId
        |
   [Collector]  Tempo / Loki / Mimir 수집
        |
     Evidence  ->  단일 패스 LLM  ->  Report(원인 랭킹 + 근거 + 조치)
```

`api -> service -> collector(client) + analyzer -> llm -> notify -> report`.
탐색 도메인은 `triage/{survey, incident, window, plan}`으로 분리돼 있다.

### 1.3 핵심 설계 원칙

> **탐색은 결정론적으로, 판단은 LLM으로.**

LLM에 조회 도구를 주고 스스로 탐색하게 하는 tool-calling 루프를 일부러 쓰지 않았다.
근거는 **대조군**이다 — "루프가 더 낫다"는 주장은 루프 없는 기준선이 있어야 증명된다.
부수 효과로 실패를 세 유형으로 나눌 수 있다: (a) 신호는 왔는데 모델이 놓침 /
(b) 신호가 수집되지 않음 / (c) 신호를 보고도 확정 불가. 이 분류가 다음 투자를
프롬프트에 할지, 수집 쿼리에 할지, 코드 연동에 할지를 정한다.

→ [ADR-002](decisions/adr-002-single-pass-baseline.md)

## 2. Observability를 먼저 검증했다

### 2.1 Brave vs OTel Agent

Brave 라이브러리 계측은 개발자가 넣은 구간만 잡힌다. 실제로 Kafka observation 누락을
겪었고, zero-code로 커버리지를 보장하는 OTel Agent 전환을 검토했다.

48시간 A/B를 설계했다가 **더 싼 검증을 먼저** 했다 — 대표 흐름(댓글 작성)의 E2E 트레이스
실측이다.

**결과** (트레이스 `6a5dc9c1…` · 2 services / 30 spans / 1.26s)

- security filterchain 1.21ms · JDBC 2~5ms(query/result-set/generated-keys 분리) · Redis GET 689μs
- Kafka 경계를 넘어 chat-service `receive`(1.11s)까지 **하나의 traceId로 연결**

### 2.2 결정 — Brave 유지

현재 RCA 요구를 이미 충족하므로 전환의 추가 이점이 제한적이고, Pod당 메모리·CPU 경합·
전환 리스크는 실재한다. **48시간 A/B는 수행하지 않았다** — 의사결정에 필요한 정보가
더 싼 검증으로 이미 확보됐기 때문이다.

### 2.3 남은 리스크는 실제로 현실화됐다

실전 조사에서 `push-dispatcher#dispatch` 996ms 중 **994ms가 자식 span 없이 비어 있었다.**
원인은 계측되지 않은 FCM 동기 호출이었다. 이는 결정이 틀렸다는 뜻이 아니다 —
zero-code 전환으로도 서드파티 SDK 내부는 잡히지 않는다. **라이브러리 계측의 잔여
리스크를 코드 인지 RCA로 보완해야 한다는 근거**로 남겼다.

→ [ADR-001](decisions/adr-001-brave-over-otel.md) · [NF-02](findings/nf-02-fcm-call-no-timeout-no-span.md)

## 3. 데이터는 있는데 Evidence가 사라지고 있었다

### 3.1 Loki — 조회가 6회 연속 0건

조사 6회 동안 로그가 한 줄도 안 들어왔다. 원인은 **독립된 두 결함**이었다.

| | 무엇 | 왜 |
|---|---|---|
| B-1 | 셀렉터 `{app=~"content\|auth\|chat"}` | `app` 라벨은 Loki에 없고 값에 `-service` 접미가 빠져 매칭 스트림 0개 |
| B-2 | `\| logfmt \| level=~"ERROR\|WARN"` | 평문 Logback에서 `level` 필드가 안 만들어져 셀렉터를 고쳐도 이 쿼리만 빈 결과 |

셀렉터만 고쳤으면 절반만 열렸다. **하나의 증상 뒤에 결함이 둘이었다.**

### 3.2 Loki — Stack Trace 손실

셀렉터를 고친 뒤에도 라인 필터 `|~ "ERROR|WARN"`가 **스택 프레임 줄을 배제**했다.
정답이 로그의 스택트레이스에만 있는 문항(AP-2)에서 근거가 전량 사라졌다 → B-11로 스택
패턴을 필터에 추가.

### 3.3 Tempo — Span 관계 손실

span은 다 수집되는데 `TraceSpans`가 `parentSpanId`를 읽지 않았다. **트레이스를 갖고도
누가 누구를 불렀는지 모르는 상태**였다. 데이터에는 이미 있었다(`spanId`·`parentSpanId` base64)
→ B-28 호출 그래프 추출로 적용.

### 3.4 핵심 발견

> **Observability Backend에 데이터가 존재하는 것과, Agent가 Evidence로 쓸 수 있는 것은 다르다.**

이후 규칙을 하나 박았다 — **감점마다 "그 신호가 백엔드에 실제로 존재했는가"를 채점자가
직접 쿼리해 확인한다.** 추측으로 도구 탓을 하지 않기 위해서다.

## 4. 장애가 있었는데 Agent가 찾지 못했다 — CH-3

### 4.1 1초 차이로 잘렸다

| | |
|---|---|
| 실제 장애 | MongoDB 정지 **05:22:01Z ~ 05:22:38Z** (약 23초) |
| 스윕 창 | 04:50:09 ~ 05:50:09Z — **주입을 포함한다** |
| 좁힌 창 | 04:57:00 ~ **05:22:00Z** |
| 결과 | 주입 **1초 전**에 창이 끝났다 · 점수 **4 / 100** (N=2 · 4 ± 0) |

이 4점이 **이 프로젝트 최초의 인용 가능한(N=2, 편차 0) 점수**다. 그 값이 4였다.

### 4.2 채널별 역추적

| Channel | 무엇이 있었나 |
|---|---|
| Trace | `{status=error}`에 05:22 **없음** — 에러가 아니라 **23초 지연**이었다 |
| Log | `ERROR\|WARN` 05:25 버킷 **1건** (05:05은 54건) — 판별력 없음 |
| Metric | `mongodb_up` **step 5m에 한 샘플도 안 걸림** |

### 4.3 가설 수정

처음엔 *"창이 좁아서 실패했다"* 로 읽었다. 채널 원본을 재보니 **창을 넓혀도 후보를 만들
Signal 자체가 없었다.** 창이 아니라 **해상도와 채널 종류**가 막은 것이다.

### 4.4 구조 개선과 결과

- **B-17 지연 트레이스 채널(`slow`) 신설** — 에러가 안 나는 장애를 찾는 경로.
  후보 10건이 전부 `slow` 채널에서 나왔고 그중 2건이 정답 → **4 → 85**
- **B-20 Incident를 1급 개념으로** — 창 안에 장애가 둘이면 둘 다 유지
- **C-4 프롬프트** *"대기 시간을 타임아웃 상한과 대조하고 최종 상태를 명시하라"* —
  코드·수집·창 무변경으로 **85 → 100**. 없던 절이 생겼다:
  *"상한 30,000ms ↔ 실측 22.5s → 만료되지 않음 · 최종 상태 성공"*
- 회차 5에서 **창을 지정하지 않고** 자력 파싱으로 다시 100

### 4.5 처방은 맞았고 숫자가 틀렸다 (정정 기록)

메트릭 해상도 대책으로 넣은 `min_over_time`(B-18)이 회차 5에서도 주입을 놓쳤다.
*"B-18 처방이 틀렸다"* 고 적었다가 **철회했다** — `min_over_time`은 이미 적용돼 있었고,
하한은 쿼리 해상도가 아니라 **스크레이프 간격**이었다(15초로 알았는데 실측 30초).
23.6초 다운이 두 샘플 사이에 빠진다. **포착 79% · 실종 21%** — 이번이 그 21%였다.
근본책은 인프라 exporter 30s -> 10s뿐이고, 그날 만점은 **전부 앱 채널**에서 나왔다.

## 5. 더 많은 Context가 더 좋은 RCA를 만드는가

### 5.1 자연 실험 — 창 길이만 달랐다

같은 문항(AP-3)을 두 번 돌렸는데 탐색이 고른 창 길이만 갈렸다.

| | 짧은 창 | 넓은 창 | |
|---|---:|---:|---|
| 창 | 10분 43초 | 24분 16초 | ×2.26 |
| 분석 컨텍스트 | 115,328자 | 198,644자 | **+72.2%** |
| 비용 | $1.3628 | $1.8900 | **+38.7%** |
| 점수 | 100 | 95 | **안 올랐다** |

### 5.2 무엇이 늘었는가

증가분이 거의 전부 **메트릭**이었다 — 8종 × 98포인트 × 다중 시리즈로 **164,988B**.
같은 창의 로그는 **16줄**, 트레이스는 **18,908B**였다.

> 결론은 *"Context를 많이 줘도 정확도가 안 오른다"* 가 아니라
> **"늘어난 Context 대부분이 정답 판단과 관계없는 채널이었다"** 다.

창을 좁히도록 강제하는 대신 **메트릭 적재 방식**을 고쳤다(B-25, 요약 적재).
단 순서를 강제했다 — 5분 샘플링이 23초 장애를 삼킨 전례가 있어, 요약이 짧은 이상 구간을
지우면 같은 실패가 재발한다. 그래서 **집계 함수 교정(응답 크기 불변)을 먼저** 넣었다.

### 5.3 비용은 어디서 발생하는가

| 단계 | 토큰 | 비중 |
|---|---:|---:|
| 탐색 | 5,576 | 2% |
| 분석 | 217,423 | **98%** |

분석 입력을 다시 쪼개면 트레이스 203KB(47%) · 로그 179KB(42%)다.

**첫 가설은 틀렸다.** Loki step을 5m -> 1m으로 줄여 창을 17.6% 좁혔는데 **로그 크기는
변화 없고 비용만 약 3% 늘었다.** 원인은 `log-limit 1000줄`이었다 — 창과 무관하게 항상
1000줄이 오고, 그 1000줄이 실제로 **약 106초**만 덮고 있었다.

### 5.4 공급과 수요를 각각 셌다

버릴 것을 고르는 대신 **쓰인 것**을 셌다.

| 로그 데이터 | 공급 비중 | 리포트 44건이 실제 인용 |
|---|---:|---:|
| 라이브러리 프레임 | **71%** (903줄) | **0회** |
| 애플리케이션 프레임 | **3.7%** (50줄) | **32회** / 12개 클래스 |

고유 로그는 191줄, **중복률 81%**. 가장 많은 자리를 차지하는 것이 분석에서 한 번도
쓰이지 않았다. **문제는 데이터 양이 아니라 정보 밀도였다.**

### 5.5 압축 — 지우지 않고 접었다

**접는 것**: 라이브러리 프레임(요약 줄로), ANSI, 중복 식별자, 반복 블록
**보존하는 것**: 애플리케이션 프레임, 예외 메시지, 그 안의 수치 값, 앱 프레임 경계 ±1

```
at com.example.Service.method(...)
… 14 frames (org.springframework, io.lettuce)

[x47회 · 01:43:53 ~ 01:46:18 · 평균 2초 간격]
QueryTimeoutException ...
```

반복 블록도 **삭제가 아니라 횟수와 시간 패턴을 명시**하는 형태로 바꿨다.
트레이스는 span을 빼지 않고 **표현만 재인코딩**했다.

검증은 단위 테스트로 **"무엇이 안 접히는지"** 를 고정했다(앱 프레임 · 수치 · 경계 ±1 ·
스레드명). 저장된 원본을 픽스처로 써서 네트워크가 필요 없다.

### 5.6 절감 결과

| 데이터 | 기존 | 변경 | 감소 |
|---|---:|---:|---:|
| 로그 (Loki 원본 112건) | 3,237,421 B | 1,390,968 B | **-57.0%** |
| 트레이스 (238건 · span 1,992) | 1,863,242 B | 1,305,152 B | **-30.0%** |

> **주의 — 저장 원본 전수 기준이고, 실행 컨텍스트 귀속은 분리되지 않았다.**
> 접기를 켠 회차 5에서 문항별 컨텍스트 토큰이 -34.5 ~ -54.5% 줄었지만
> **창과 주입이 회차마다 달라 그 감소분을 접기에 전량 귀속시킬 수 없다.**
> `enabled=false/true` 두 팔을 같은 창에 고정한 A/B는 **미실행**이다.

### 5.7 반례가 규칙을 고쳤다

여섯 문항 중 **AU-3만 -5.9%**, 비용은 오히려 **+12.2%**였다.

첫 판단은 *"창이 35분으로 넓어서"* 였다. 문항을 가로질러 창 폭 오름차순이 절감 폭
내림차순과 대응했기 때문이다. **같은 문항끼리 재보니 반대였다.**

| AU-3 | 회차 3 (창 40분) | 회차 5 (창 35분) | 델타 |
|---|---:|---:|---:|
| 로그 ERROR/WARN | 108,802 B | 75,158 B | -31% |
| 메트릭 | 258,019 B | 234,686 B | -9% |
| **트레이스** | 82,057 B / 87 spans | **129,827 B / 167 spans** | **+58%** |

창은 오히려 12.5% 좁아졌다. **접기는 작동했다** — 수집 원본 합계는 5.5% 늘었는데
컨텍스트는 18.3% 줄었으니, 접기가 없었으면 컨텍스트도 늘었어야 한다.
**트레이스 +58%가 접기 효과를 거의 다 먹었다.** 범인은 리포트가 스스로 지목했다 —
기동 시 `alter table` DDL 27건이 나가는 트레이스가 **80KB / 119 spans의 반복**이었다.

접기·요약이 채널마다 다르게 들어가 있었고 **트레이스만 아무것도 버리지 않는다.**
-> B-36(반복 span 접기, 36.3% 절감 실측 · **미구현**).

## 6. RCA 성능을 어떻게 믿을 것인가

### 6.1 평가 장치 네 가지

| 장치 | 내용 |
|---|---|
| **Anchor 박제** | 기준 답안을 **주입 전에** 확정한다. 결과를 보고 고치면 그 회차는 무효, 개정은 다음 회차부터 |
| **자유 대조 금지** | 앵커에 없는 잣대를 끌어오면 채점자 재량이 된다 |
| **Blind** | 리포트 생성 경로에 정답지를 두지 않는다. 리포트 안에서 점수를 만들게 하지 않는다(자기 채점 무효) |
| **N >= 2 · 편차 +-10** | 문항당 최소 2회. 평균 +- 최대편차로 기록하고 편차가 10을 넘으면 인용 보류 |
| **채점 불가** | 주입이 성립하지 않았거나 앵커 요건 대상이 부재하면 **점수를 만들지 않는다** |

### 6.2 왜 이런 장치가 필요한가

> **평가 인프라가 오염되면, 재는 것은 RCA 성능이 아니라 평가 환경의 결함이다.**

실제로 채점 불가가 초기 4건 나왔고 **전부 에이전트가 아니라 앵커의 결함**이었다.
기준 부적합률을 추적 지표로 삼아 67% -> 33%로 내렸다.

### 6.3 자가 바뀌었으므로 Before/After를 쓰지 않는다

루브릭이 v1(근본 40 / 근거 30 / 오귀인 20 / 조치 10)에서 **v3**(원인 40 / 근거 25 /
**탐색 15** / **영향 10** / 오귀인 5 / 조치 5)로 바뀌었다. 이유는 실측이다 —

- `근본 40`이 원인·영향 두 가지를 담고 있었다(CH-1 감점 20 **전액이 영향 오판**)
- `오귀인 20`은 **11회 전부 만점**이라 척도가 아니었다. v3에서 *"후보로 올리되 자력 반증"*
  중간 구간을 넣자 **12회 만에 첫 비만점(3/5)** 이 나왔다 — 항목 설계가 변별력을 만든 실증

**그래서 총점 v1 -> v3를 개선으로 인용하지 않는다.** 비교는 **같은 자 · 같은 문항 ·
같은 입력 모델의 N=2 쌍**으로만 한다.

### 6.4 제시 가능한 결과

| 문항 | N=2 결과 | 무엇이 재현됐나 |
|---|---|---|
| CH-2 | **100 +- 0** | 여섯 항목 전부 앵커 문언만으로 결정, 채점자 판정 0건 |
| IN-2 | **99 +- 1** | 갈린 하나가 후보 **배치 형식** 차이이고 판단은 동일 |
| AP-3 | 97.5 +- 2.5 | 다섯 항목 편차 0, 갈린 하나가 4) 영향 |
| CH-1 | **93 +- 7** (회차 5) | 편차의 원인이 능력이 아니라 **채널 운** — §9 |
| AU-4 | 85.5 +- 2.5 | 1) 원인 30이 다섯 회차 연속 재현 |
| AU-2 | **85 +- 0** (회차 5) | 여섯 항목 전부 동일. 앞선 회차 2 구성은 **65 +- 11로 인용 보류**였다 |
| CH-3 | **4 +- 0** | 탐색이 주입을 1초 차이로 잘라 산출물이 없다 |

**편차 0이 곧 안정성이 아니다.** CH-3의 0은 능력이 아니라 **막힘의 재현**이고,
CH-2의 0은 **신호가 전부 도달한 상태의 재현**이다. 그래서 채점표에
*"정답 신호가 컨텍스트에 도달했는가"* 를 편차와 **함께** 남기도록 서식을 바꿨다.

### 6.5 만들지 않은 지표

Top-1 적중률 · Evidence Recall · 탐색 정밀도는 **정의만 해 두고 값을 비웠다.**
정상 구간(장애 없음) 문항을 **아직 0회** 돌렸기 때문에 "없는 원인을 지어내지 않는가"를
잰 적이 없고, 정밀도 없는 재현율은 지표가 아니다.

## 7. 측정 자체도 검증 대상이었다

### 7.1 오버헤드는 상수가 아니었다

CLI 고정 오버헤드를 상수로 두고 빼고 있었다. 실측하니 07-26~27 약 22,000 ->
07-28 **26,626** -> 07-29 **21,247**로 움직였다. **하루 만에 -20%** 이고 감소분 대부분이
툴 정의(23,201 -> 10,762)였다. **소급 추정이 불가능하므로** 조사마다 1자 프롬프트로
직접 재는 프로브를 넣었다(남은 오차 +-320 tok, 1.5%).

### 7.2 `chars / 4`를 폐기했다

토큰 추정에 쓰던 `chars/4`(계수 0.250)가 실측과 어긋났다 — **2.1배 과소**였다.
실측 계수는 **0.524**(범위 0.511~0.532)다. 그리고 그 추정치조차 실측과 구별해 표기하도록
문서 규칙을 만들었다(`실측` / `추정`을 섞어 쓰지 않는다).

### 7.3 프로브가 깨진 회차

회차 5의 한 실행에서 **CLI가 자동 갱신(2.1.221 -> 222)되며 프로브가 실패**해 그 실행의
토큰 축을 잃었다. 점수는 N=2로 성립했지만 **토큰은 N=1로 기록**했다.

### 7.4 하네스 자체의 버그

측정 하네스를 먼저 검증했더니 **42,774 토큰이 `2`로 기록되고 있었다.**

> **지표를 만들었다고 그 지표를 믿은 것이 아니라, 지표의 타당성을 따로 검증했다.**

## 8. 평가 시스템이 틀렸다는 것을 발견했을 때

### 8.1 피험자가 시험지를 읽고 있었다

LLM provider로 Claude CLI를 쓰는 구성에서 서브프로세스가 **JVM의 작업 디렉터리를 물려받고**
있었고, CLI는 그 디렉터리의 `CLAUDE.md`와 스킬 파일을 자동으로 읽는다. 즉 평가 대상이
**관측 라벨과 쿼리 결함이 적힌 프로젝트 문서를 읽은 상태로** 시험을 보고 있었다.

중립 임시 디렉터리로 격리한 뒤, **오염의 크기를 숫자로 확정**했다 —
격리 **26,603** ↔ 레포 루트 **32,747** (**+6,144 · +23%**), 차이는 전부 `cache_creation`에서 났다.
격리 전에 실행된 회차는 **폐기하고 재실험**했다.

### 8.2 장애 주입 자체가 실패한 경우

CH-1 한 회차에서 Mongo 다운은 사양대로 났는데 **트리거 댓글 2건이 전부 401**이었다
(다른 문항의 시크릿 드리프트 잔존). 알림 이벤트·DLQ·재처리가 **0건**이라 앵커 만점 요건
네 개가 **대상 부재**였다.

**점수를 만들지 않고 "채점 불가"로 등재했다** — 0점도 아니다. 0점은 에이전트를 잰
숫자지만 이건 관측 자체가 없다. (덧붙이면 **에이전트는 실제 전개를 맞혔다** —
1순위가 *"401 -> 알림 트리거 미발생"* 이었고 Mongo 인과를 자력 반증했다. 정성 기록으로만 남겼다.)

### 8.3 예측의 반증

로그 채널 두 결함(B-1·B-2)을 고치면서 **+25점**을 예측했다. 같은 자로 잰 실제 결과는
**-10점**이었다(AP-2 53). 원인은 **셋째·넷째 결함**이었다 — 라인 필터가 스택을 배제하고,
traceId 미선정 시 Tempo를 통째 skip한다. 둘 다 실측으로 잡았고, 예측과 실제의 차이를
그대로 기록했다.

이후 규칙을 하나 더 박았다 — **수정안에는 "이 신호가 실제로 도달하는가"를 확인한 결과를
함께 적는다.** 확인 없이 세운 인과 예측이 두 회차 연속 반증됐기 때문이다.

## 9. 같은 조건인데 86과 100이 나왔다 — CH-1 회차 5

같은 주입 데이터를 **18분 간격으로 두 번** 조사했다. 문안·도구·모델 전부 동일.

**86 ↔ 100.** 갈린 항목은 2) 근거(18↔25) · 4) 영향(5↔10) · 5) 오귀인(3↔5)이고,
앞의 둘(12점)은 **트레이스 하나**에 걸려 있다 — 발행 -> 실패 4회 -> DLQ 발행 -> 재처리
성공이 **한 traceId에 다 들어 있는** 그것이다.

Tempo `/api/search`가 같은 트레이스를 두 실행에 다르게 내려줬다.

| | 실행 1 | 실행 2 |
|---|---|---|
| `durationMs` | **3505144756** (40.5일 · 깨짐) | **31370** (31.4초 · 정상) |
| `startTimeUnixNano` | 정상 | 동일 |
| `spanSet.spans[].durationNanos` | 정상 (30.06초) | 동일 |
| 후보 선정 | **탈락** | 선택 |
| traceId 로그 채널 | 37줄 · **전부 헬스체크** | 132줄 · **DLQ 발행 1 · 재처리 성공 1 · 실패 4** |

```
깨진 durationMs 한 필드
      -> 후보 필터에서 정답 트레이스 탈락
      -> 그 traceId의 로그가 통째로 미수집
      -> 발행/재시도/DLQ/재처리 구간 증발
      -> 86 ↔ 100
```

**코드가 주석과 반대로 동작하고 있었다.** `SurveyResult` 주석은 *"버리면 그 트레이스에
도달할 길이 없으므로 `trusted=false`로 남기고 **정렬과 창 계산에서만 뺀다**"* 인데,
`TriageService:150`이 **수집 후보 목록에서도** 빼고 있었다.

검증은 주입 없이 된다 — 깨진 값이 든 **그 원본 응답 파일이 그대로 있으므로** 단위 테스트
입력으로 쓰고, 성공 기준은 *"후보 목록에 그 traceId가 들어오는가"* 하나다.
**상태: 원인 특정 완료 · 미구현(B-40, 다음 회차 1순위).**

> 함께 잡힌 것 — 두 실행 다 로그가 `limit=1000` + `direction=forward`라
> 수집 창 44.4분 중 **앞 22.9분만 들어오고 뒤 34%가 잘렸다**(B-39).
> **장애 조사에서 잘리는 뒤쪽은 언제나 복구·도착 구간이다.**

### 핵심

> **단일 실행 점수는 성능이 아니다.**
> 같은 조건에서 **한 필드의 일시적 파손**이 14점을 만들었다.
> N >= 2와 편차 기준, 그리고 "감점마다 신호 존재를 직접 확인한다"는 규칙이
> 왜 필요한지를 이 사례가 증명한다.

## 10. Engineering Findings

| | |
|---|---|
| **1** | **RCA 성능의 상한은 LLM이 아니라 Signal Quality가 정할 수 있다** — 막힌 채널 수와 점수가 정렬됐다(0개: 100·90 / 1개: 88 / 2개 이상: 76·53) |
| **2** | **Observability Data와 Evidence는 같지 않다** — 백엔드에 있어도 쿼리·필터·상한 어디서든 사라진다 |
| **3** | **Context 양보다 정답과 관계있는 Signal의 비중이 중요하다** — 창 ×2.26에 컨텍스트 +72.2%, 점수 불변. 늘어난 것은 메트릭이었다 |
| **4** | **탐색과 판단을 분리하는 것이 유리하다** — 못 찾은 것과 찾고도 못 푼 것은 처방이 정반대라, 한 점수로 합치면 무엇을 고칠지 정할 수 없다 |
| **5** | **측정 지표 역시 검증 대상이다** — 상수인 줄 알았던 오버헤드가 하루에 20% 움직였고, 토큰 회계에 버그가 있었으며, 프로브가 깨진 회차가 있었다 |
| **6** | **단일 실행 점수는 성능이 아니다** — 동일 조건에서 한 필드 파손이 86 ↔ 100을 만들었다 |

> 표본 크기를 함께 밝힌다. Finding 1의 정렬은 문항 5개이므로 상관을 주장하지 않고
> **다음 회차의 반증 대상**으로 등록해 뒀다 — 채널을 고친 뒤에도 해당 문항이 오르지
> 않으면 이 해석이 틀린 것이다.

### 지금의 한계

  에이전트가 이 모순을 자력으로 잡아내고 결론의 확신도를 낮췄다

## 이 문서가 말하는 것

```
가설 -> 구현 -> 실험 -> 실패 -> 원인 역추적 -> 가설 반증
     -> 설계 변경 -> 측정 방법 검증 -> 재검증
```

- 창이 좁아서 실패한 줄 알았는데 **신호가 없었다** (§4)
- 도구를 고치면 +25점일 줄 알았는데 **-10점이었다** (§8.3)
- 절감이 안 나온 이유가 창인 줄 알았는데 **트레이스 채널이었다** (§5.7)
- 처방이 틀린 줄 알았는데 **하한 숫자가 틀린 것이었다** (§4.5)
- 오버헤드가 상수인 줄 알았는데 **하루에 20% 움직였다** (§7.1)

**점수를 높게 보이게 만드는 것보다, 측정하지 않은 것을 측정하지 않았다고 쓰는 것을
우선했다.** 그래서 이 문서에는 Top-1 적중률도, Before/After 총점 비교도 없다.
