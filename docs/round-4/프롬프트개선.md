# 회차 4 — 관측 개선에서 출력 계약 개선으로

## 1. 문제 정의

회차 2 → 3에서 조사 도구를 개선한 결과, 동일 문항 기준 평균 점수가 **79.0 → 92.1점(+13.1)**으로 상승했다.

이를 통해 주요 병목이 **관측 데이터 부족**이었다는 점을 확인했다.

하지만 회차 3의 리포트를 다시 검토하면서 새로운 문제가 발견됐다.

> **필요한 데이터와 판단은 이미 존재하지만, 판단이 평가되는 위치에 명시되지 않아 감점이 발생하고 있었다.**

대표적으로 다음 세 가지 문제가 있었다.

* 측정값을 제시했지만 최종 상태까지 연결하지 않음
* 근거에서 판단한 내용을 권장 조치에 반영하지 않음
* 배제한 후보가 원인 후보 랭킹에 다시 포함됨

따라서 이번 회차에서는 **관측 도구와 컨텍스트는 고정하고, 출력 계약만 변경**했다.

---

## 2. 개선 방향

RCA 결과를 다음 세 단계로 분리했다.

```text
관측 데이터
    ↓
판단
    ↓
리포트 배치
```

회차 2 → 3에서는 `관측 데이터 → 판단`을 개선했다면,
회차 4에서는 `판단 → 리포트 배치`를 개선하는 것을 목표로 했다.

| 구분    | 회차 2 → 3     | 회차 3 → 4          |
| ----- | ------------ | ----------------- |
| 주요 문제 | 관측 데이터 부족    | 판단의 출력 위치 불안정     |
| 변경 대상 | 조사 도구 / 컨텍스트 | System Prompt     |
| 핵심 목표 | 필요한 증거 확보    | 판단을 평가 가능한 위치에 명시 |

---

## 3. 출력 계약 개선

### C-4. 측정값을 최종 상태까지 연결

단순히 대기 시간과 타임아웃 값을 나열하는 것이 아니라,

```text
실측 대기 시간
    ↓
타임아웃 상한과 비교
    ↓
타임아웃 만료 여부 판정
    ↓
최종 상태 명시
```

하도록 출력 계약을 구체화했다.

최종 상태는 `성공 / 실패 / 재시도 / 폐기` 중 하나를 명시하고,
근거가 부족한 경우에는 임의 판단 대신 **판정 불가**를 사용하도록 했다.

### C-5. 권장 조치를 세 영역으로 분리

조치 항목을 다음 세 가지로 강제했다.

1. **이미 발생한 피해** — 복구 가능 여부와 복구 방법
2. **재발 방지** — 원인에 대한 개선 방법
3. **복구 확인** — 조치가 정상 적용됐는지 확인하는 방법

해당 사항이 없으면 `해당 없음 + 근거`를 명시하도록 했다.

### C-6. 반증된 후보 분리

반증된 후보를 원인 랭킹에 포함하지 않고 별도의 **배제된 후보** 영역으로 분리하도록 했다.

다만 검증 과정에서 이 변경이 오히려 원인 랭킹의 의미를 변화시키는 부작용을 확인하여 **최종 프롬프트에서는 폐기했다.**

---

## 4. 검증 결과

관측 데이터, 모델, 조사 도구, 분석 창을 고정하고 **프롬프트 변경만 단일 변수로 적용**했다.

### CH-3 — 85 → 100

C-4 적용 후 대기 시간과 타임아웃의 관계가 명시적으로 출력됐다.

```text
Mongo 대기 상한 : 30,000ms
실측 대기       : 약 22.5s
                 ↓
타임아웃 미만
                 ↓
최종 상태 : 성공
```

또한 `DLQ lag = 0`, FCM 성공 등의 근거를 바탕으로 **복구 조치가 불필요하다는 영향 판정**까지 명시됐다.

| 평가 항목  |   회차 3 |    회차 4 |
| ------ | -----: | ------: |
| 원인 적중  |     30 |  **40** |
| 근거     |     25 |      25 |
| 탐색     |     15 |      15 |
| 영향 판정  |      5 |  **10** |
| 오귀인    |      5 |       5 |
| 조치     |      5 |       5 |
| **합계** | **85** | **100** |

**85 → 100점으로 상승하며 C-4가 의도한 출력 위치에서 효과가 확인됐다.**

---

### IN-2 — C-5는 의도대로 동작, C-6는 부작용 확인

C-4 + C-5 + C-6 적용 시 **98 → 90점**으로 하락했다.

그러나 세부 항목을 분리해 확인한 결과 C-5와 C-6가 목표했던 항목은 개선됐다.

| 평가 항목  |     기존 | C-4+C-5+C-6 |
| ------ | -----: | ----------: |
| 원인 적중  |     40 |      **30** |
| 근거     |     25 |          25 |
| 탐색     |     15 |          15 |
| 영향 판정  |     10 |          10 |
| 오귀인    |      3 |       **5** |
| 조치     |      3 |       **5** |
| **합계** | **96** |      **90** |

C-6의 부작용을 확인하기 위해 **C-6만 제거하고 동일 조건으로 재실행**했다.

그 결과 원인 적중이 다시 40점으로 회복되며 **최종 100점**을 기록했다.

```text
C-4 + C-5 + C-6 → 90
C-4 + C-5       → 100
```

분석 결과 C-6는 반증된 후보를 제거하는 과정에서 비어버린 랭킹을 다른 가설이 아니라 **하나의 인과 사슬을 여러 단계로 분해하는 방식으로 채우게 만드는 부작용**을 일으켰다.

즉, 모델은 본문에서 실제 원인을 올바르게 설명하고 있었지만 **랭킹 구조만 잘못 배치하는 현상**이 발생했다.

따라서 **C-6는 최종 구성에서 폐기했다.**

---

## 5. 최종 결과

최종 프롬프트는 **C-4 + C-5만 유지**했다.

| 문항   |        회차 3 | 회차 4 최종 구성 |
| ---- | ----------: | ---------: |
| CH-3 |          85 |   **100*** |
| IN-2 | 98 (96/100) |    **100** |

* CH-3의 100점은 C-6가 포함된 실행에서 측정되었으며, 최종 구성(C-4+C-5)에서의 재검증은 아직 완료되지 않았다.

따라서 현재 결과는 **"출력 계약 개선의 효과가 확인됐다"**는 수준이며, 최종 구성의 재현성까지 검증된 상태는 아니다.

---

## 6. 핵심 발견

이번 실험을 통해 다음을 확인했다.

### ① 관측 데이터가 충분하면 출력 계약만으로도 평가 결과를 개선할 수 있다

CH-3에서 기존에 존재하던 대기 시간, 타임아웃, 성공 여부 등의 데이터를 새로 수집하지 않고도 출력 계약을 변경하는 것만으로 **85 → 100점**을 기록했다.

즉,

> **관측 부족과 출력 구조 문제는 별개의 병목으로 다뤄야 한다.**

### ② 출력 지시는 평가 항목별로 분리해서 검증해야 한다

C-4와 C-5는 각각 목표한 평가 항목을 개선했다.

반면 C-6는 의도하지 않은 **원인 적중 항목을 40 → 30점으로 하락**시켰다.

이를 통해 단순히 전체 점수만 비교하는 것보다 **변경 항목과 평가 항목을 1:1로 대응시키는 검증 방식**이 필요하다는 점을 확인했다.

### ③ "무엇을 하지 말라"는 지시만으로는 출력 구조를 안정화하기 어렵다

C-6는 반증된 후보를 원인 랭킹에서 제거하도록 했지만, 제거된 자리를 어떻게 구성할지는 정의하지 않았다.

그 결과 모델은 빈 자리를 새로운 경쟁 가설이 아니라 기존 원인의 하위 단계로 채웠다.

> **출력 계약을 제한할 때는 제거할 항목뿐 아니라 그 자리를 어떻게 채울지도 정의해야 한다.**

---

## 7. 한계 및 후속 검증

이번 실험은 출력 계약의 효과를 분리하기 위해 **관측 도구와 컨텍스트를 변경하지 않았다.**

다만 다음 검증은 아직 완료되지 않았다.

* 최종 구성(C-4+C-5)으로 CH-3 재실행
* IN-2 최종 구성 N=2 검증
* 프롬프트 변경에 따른 실행 간 점수 편차 측정
* Claude CLI `2.1.220 → 2.1.221` 변경에 따른 토큰 지표 영향 검증

특히 `cacheReadTokens` 변화로 인해 기존 `inputTokens` 기반 비용 지표가 실제 컨텍스트 크기를 정확하게 나타내지 않는 문제도 발견했다.

따라서 이번 회차에서는 토큰 비용보다 **`contextChars`와 `cacheCreationTokens`를 중심으로 컨텍스트 크기를 비교**해야 한다는 판단을 내렸다.

---

## 8. 결론

회차 3에서 **"필요한 데이터를 확보하는 것"**을 개선했다면,
회차 4에서는 **"확보한 판단을 평가 가능한 형태로 출력하는 것"**을 개선했다.

실험 결과:

```text
관측 데이터 부족
      ↓
조사 도구 개선
      ↓
판단 가능한 수준의 데이터 확보
      ↓
출력 계약 개선
      ↓
판단을 명시적인 상태·조치로 연결
```

이번 회차의 가장 중요한 결과는 단순한 점수 상승이 아니다.

> **RCA 품질은 관측 → 판단 → 출력의 세 단계로 분리해서 개선하고 검증해야 한다는 것을 실험적으로 확인했다.**

또한 출력 계약을 강화할수록 **의도하지 않은 평가 항목까지 영향을 받을 수 있음**을 확인했다. 따라서 향후 프롬프트 변경은 전체 점수만 비교하지 않고, **변경 지시 → 대상 평가 항목 → 비대상 항목의 부작용**을 분리해 검증하는 방식으로 진행한다.
