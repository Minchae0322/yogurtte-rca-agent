## 0이 정상인 지표를 이상으로 읽었다 — B-30 ✅ **적용 완료 (2026-08-03)**

**변경군 B (조사 도구).** [CH-1 회차 4](../ch-1/round-4.md)에서 **단일 변수로 검증 완료.**

### 상황

| | |
|---|---|
| 계기 | CH-1 회차 3의 분석 컨텍스트가 **363,268자**(프로젝트 최대) · 비용 $2.78(최고)로 튀었다 |
| 원인 | 좁힌 창이 **스윕 창 전체 60분** — 후보 INC-1(`kafka_consumergroup_lag`)의 구간이 창 전체였다 |
| 후보 내부 실측 | 신호 **41줄 중 36줄이 창 시작(13:36:09Z)부터**, **37줄이 "…가 0이었다"**. 값이 변한 것은 **4줄뿐**이고 그 4줄이 정답(`partition=3: 0→1→23`, `dlq: 0→1→0`) |
| 예고 | [AP-1 회차 3](../ap-1/round-3.md)이 *"`zeroRuns()`가 60분짜리 후보를 만든다… **함께 골랐다면 창이 60분이 됐다**"* 로 예측해 뒀다 |

### 무엇이 일어났나

`zeroRuns()`가 **지표 성격을 가리지 않고** "0인 구간"을 이상 신호로 만들고 있었다.
`up`·`mongodb_up`·`kafka_brokers`는 0이 곧 다운이지만, **`kafka_consumergroup_lag`는 0이 정상**
(컨슈머가 안 밀림)이고 `websocket_active_users`도 0이 정상(접속 없음)이다.

그래서 **한 시간 내내 멀쩡했던 파티션마다 60분짜리 "이상 구간"** 이 생겼다.
군집 키가 `채널 | 리소스 | 지문`이고 **시리즈 라벨은 키에 넣지 않으므로**(의도된 설계 —
넣으면 44개 시리즈가 44개 후보로 흩어진다) 정상 파티션 36개와 진짜 신호가 **후보 하나로 뭉쳤고**,
후보 구간은 신호들의 합집합이라 **창 전체**가 됐다.

**손해가 비용만이 아니었다.** 창이 안 좁혀지니 지목 traceId가 20건으로 불어 수집 상한을 채웠고,
**정답인 DLQ 재처리 트레이스가 밀려나** 4) 영향 판정이 5점이 됐다.
**$2.78이라는 비용과 −5점이 같은 뿌리**에서 나왔다.

### 변경 내용

| 층위 | 무엇을 |
|---|---|
| 구조 개선 | `rca.survey.zero-is-abnormal` 설정 신설. **목록에 있는 지표만** 0 구간을 신호로 만든다 (기본 `up`·`mongodb_up`·`kafka_brokers`) |
| 유지 | **값 변화·결측 탐지는 전 지표 그대로** — CH-1의 정답이 값 변화(`0→1→23`)다 |
| 안전 | 기본값은 `null`(미설정)일 때만 채운다. 빈 목록이면 0 신호가 전부 사라져 **"설정 누락"과 "일부러 껐다"가 구별되지 않는다** |

**왜 코드가 아니라 설정인가** — 0의 의미는 **관측 대상의 성질**이지 알고리즘이 아니고,
지표가 늘어도 코드를 안 고치며, 무엇보다 **감사 가능**하다(블라인드 규정상 코드에 정답을
심는 것과 구분된다).

### 검증 결과 — 단일 변수 실험

**같은 주입 데이터 · 같은 창 · 같은 문안 · 같은 모델, 바뀐 것은 이 코드 한 곳뿐이다.**

|---|---:|---:|---|

| 메트릭 바이트 | 368,010 | **142,791** | −61% |
| 로그 traceId 채널 | 33,232 | **58,213** | **+75%** |
| 컨텍스트 | 363,268자 | 406,133자 | **+12%** |

**🔴 결함 11이 해소됐다** — 창이 좁아지자 traceId 로그 채널이 정답 트레이스를 잡아

**"무엇이 들어 있느냐가 점수를 정한다"** 이다.

### 반증 조건 — 아직 남아 있다

- **🔴 CH-2가 반증 시험이다.** lag이 정답인 문항인데 `zero-is-abnormal`에서 lag을 뺐다.
  *"lag이 0에서 상승"* 은 값 변화로 잡히지만, **"0이어야 하는데 0이 아니다"의 반대 방향**

## 영향 범위는 원본이 아니라 집계로 온다 — 넓은 창 카운트 쿼리 (B-29)

**변경군 B (조사 도구).** [B-13](../round-3/README.md)을 흡수하고 그 진단을 정정한다.

### 상황

| | |
|---|---|
| 계기 | AP-3 회차 3의 **감점 5점 전액**이 4) 영향 판정이고, 사유가 *"영향 범위(실패율·영향 사용자 수) 판단은 **데이터 부족**"* 이었다 |
| 에이전트가 든 근거 | ⓐ *"조회 창이 13분 43초뿐"* ⓑ *"`POST /feeds`는 1건이며 그 1건이 실패 — 성공/실패 비율을 산출할 표본이 없다"* ⓒ *"**5xx 카운터는 애초에 수집 목록에 없다**"* |
| 구조적 딜레마 | 원인 규명은 **좁은 창 + 원본**이 필요하고, 영향 범위는 **넓은 창 + 총계**가 필요하다. 넓은 창의 원본을 다 실으면 컨텍스트가 감당이 안 된다 |
| 현재 상태 | **미착수.** `metric-queries`에 5xx 카운터가 없고, 있는 401 쿼리는 3회 연속 "no series" |

### 무엇이 일어났나

첫 판단은 *"창을 넓히면 된다"* 였다. [round-3 §조사 창 설계](../round-3/README.md)가 이미 그것을
반증했다 — AP-3 회차 2b에서 창이 2.3배가 되자 컨텍스트가 1.7배로 불었고 점수는 오르지 않았다.

**해법은 창 확대가 아니라 해상도 분리다.** 좁힌 창에는 지금처럼 원본을 싣고,
**사용자가 말한 원래 창(스윕 창)에는 카운트 쿼리만** 던진다. 영향 범위를 판정하는 데
필요한 것은 로그 원문이 아니라 **숫자 두 개(실패 건수 · 전체 건수)** 뿐이기 때문이다.

**실측으로 확인했다 (2026-08-03, AP-3 회차 3과 같은 창 `07-29 00:03:43~01:03:43Z`).**

첫 단계는 라벨이 실재하는지였다. B-13이 *"라벨 오류"* 로 기록해 둔 그 지점이다.

```promql
count by (status, uri, application) (http_server_requests_seconds_count{application="content-service"})
→ 33개 시리즈. status·uri 라벨 실재. 그중 500 | /feeds 가 있다.
```

**`status="500"` · `uri="/feeds"` 시리즈가 실재한다.** 즉 신호는 처음부터 있었고
**수집 목록에 넣지 않았을 뿐**이다.

| 쿼리 | 실측 결과 | 응답 크기 |
|---|---|---:|
| `sum(increase(...{uri="/feeds", status="500"}[1h]))` | **1.0169** (≈1건) | **119 B** |
| `sum by (status) (increase(...{uri="/feeds"}[1h]))` | 500 → 1.02 · **200 → 2.03** | **202 B** |
| 카운터 차분(`max_over_time − min_over_time`) | **500 → 1.0 · 200 → 2.0** (정수) | 유사 |

**에이전트가 "표본이 없다"고 한 그 숫자가 202바이트로 온다.** 60분 창에서 피드 작성
**3건 중 1건 실패(33%)** 이고, 이것이 4) 영향 판정 만점 요건인 *"요청에 한정"* 을 닫는 데
필요한 전부다. 회차 3의 분석 컨텍스트가 119,761자였으므로 **증가분은 0.2% 미만**이다.

> **`increase()`는 소수로 나온다** — 카운터 외삽 때문에 1.0169다. 건수를 정수로 원하면
> **`max_over_time − min_over_time` 차분**을 쓴다(실측 1.0 · 2.0). 어느 쪽이든 모델이 읽을 수
> 있으나, *"1.02건 실패"* 라는 표현이 리포트에 나가면 어색하므로 **차분 방식을 권장**한다.

### B-13의 진단이 틀렸다 — 라벨 오류가 아니었다

3회 연속 실패한 401 쿼리를 같은 창에서 분해해 봤다.

```promql
sum by (uri) (increase(http_server_requests_seconds_count{application="content-service", status="401"}[1h]))
→ 시리즈 2개 존재 (/rewards/me, /rewards/me/badges), 값은 둘 다 0.0
```

**시리즈는 있고 값이 0이다.** 즉 *"라벨이 틀렸다"* 가 아니라 **그 창에 401 트래픽이 없었다**는
뜻이고, `rate([1m])`가 0인 구간을 "no series"로 떨궈 실패처럼 보인 것이다.
**B-13을 "쿼리 교정"으로 적어 둔 것은 오진이고, 실제 처방은 ⓐ 0을 실패가 아니라 사실로
보고하기 ⓑ 필요한 시리즈(5xx)를 수집 목록에 넣기다.**

이것은 회차 3 리포트가 스스로 지적한 것이기도 하다 — *"시리즈 부재가 '401이 0건'인지
'메트릭 라벨/스크랩 자체가 없음'인지 구분할 수 없다"*.

### 회차 4에서 바꿀 것

**① 변경 표**

| 층위 | 무엇을 |
|---|---|
| 신호 공급 | **스윕 창(넓은 창) 기준 카운트 쿼리를 새 채널로 추가.** `sum by (status) (max_over_time(...) − min_over_time(...))` 를 대상 서비스·주요 uri에 대해. 좁힌 창이 아니라 **사용자가 말한 원래 창**에 던진다 |
| 신호 공급 | `metric-queries`에 **5xx 카운터 추가** — 지금 목록에 없다 |
| 구조 개선 | 컨텍스트에 **`# 영향 범위 (넓은 창 집계)`** 절 신설. 좁힌 창 원본과 **명시적으로 구분**해 싣는다 — 모델이 두 창을 섞으면 4) 영향과 1) 원인이 오염된다 |
| 진단 교정 | 값이 0인 시리즈를 **"수집 실패"가 아니라 "0건"으로 보고**. 지금은 둘이 같은 문구로 나가 모델이 공백으로 읽는다 |

**② 신호 도달 확인** — **실시 완료.** 위 표가 그 실측이다. 라벨 실재·응답 크기·정수 건수까지
같은 창에서 확인했다. **이 항목은 [round-3 §3.1](../round-3/README.md)이 요구한
*"신호가 실제로 도달하는가"* 를 착수 전에 통과한 첫 항목이다.**

**③ 검증 설계** — 한 번에 하나만 바꾼다.
1. 카운트 채널만 추가하고 컨텍스트 증가분 측정 (예측: **1KB 미만**)
2. **AP-3를 같은 창·같은 문안으로 재조사** — 4) 영향이 5 → 10으로 가는지가 유일한 관전 지점이다.
   다섯 항목이 이미 만점이라 **다른 항목의 잡음이 없는 깨끗한 단일 변수 실험**이다
3. 통과하면 AP-1(4) 영향 5점 · 같은 사유)에 적용해 재현 확인

**④ 반증 조건** — 카운트를 줬는데도 4) 영향이 5점이면 원인은 신호가 아니라 **앵커 문언**이거나
프롬프트다(그 경우 변경군 C로 넘긴다). 넓은 창 집계를 실었더니 1) 원인이 흔들리면 두 창이
섞인 것이므로 절 구분을 강화한다. 응답이 1KB를 넘으면 uri 목록을 상위 N개로 제한한다.

**⑤ 현재 상태** — **미착수·미측정(코드).** 완료된 것은 **신호 도달 실측**이다:
`status`·`uri` 라벨 실재 확인(33 시리즈) · `500 | /feeds` 존재 · 60분 창 실패 1 / 성공 2 ·
응답 119~202 B · 정수 건수를 얻는 쿼리 형태 확정 · **B-13 오진 정정**(라벨 오류가 아니라 무트래픽).
코드 반입과 재조사는 회차 4다.

## 관측 백엔드 교체 가능성 — 인터페이스를 어디에 두어야 진짜 seam인가

**변경군 B (조사 도구).** 단, Scouter 도입은 계측 교체를 동반하므로 **변경군 A도 걸린다** —
아래 "축이 하나 비어 있다" 참조.

### 상황

| | |
|---|---|
| 계기 | 관측 소스가 나중에 **서버 로그 디렉터리** 또는 **Scouter APM**으로 바뀔 수 있다는 요구 |
| 지금 구조 | `TempoClient` · `LokiClient` · `MimirClient` 구현 클래스를 `Collector`·`Surveyor`가 **직접 필드로** 들고 있다 |
| 쿼리가 사는 곳 | `CollectProperties.errorWarnQuery/traceIdQuery` · `SurveyProperties.traceQuery/slowTraceQueryFor/logQueryFor/metricQueries` — **호출부가 쿼리 문자열을 만들어 클라이언트에 넘긴다** |
| 응답이 쓰이는 곳 | 원본 JSON 문자열이 `CollectedData`·`SurveyResult`에 그대로 담겨 **LLM 컨텍스트까지 간다** |
| 현재 상태 | **미착수.** 인터페이스 없음, 구현 하나뿐 |

### 무엇이 일어났나

첫 판단은 "`LlmClient`·`Notifier`가 이미 인터페이스 + `@ConditionalOnProperty`로 갈아끼우게 돼
있으니 클라이언트 셋도 똑같이 하면 된다"였다. 확인해 보니 **그 자리는 seam이 아니다.**

현재 시그니처는 `queryRange(correlationId, label, logql, start, end, limit)` 다. 다른 소스에
`logql` 문자열을 넘기면 그쪽은 그것을 실행할 수 없다. 같은 자리에 인터페이스를 세우면 **구현을
갈아끼울 수 있는 것처럼 보이지만 계약은 여전히 LogQL**이다.

두 번째로 응답 형식이다. Loki/Tempo/Prometheus의 JSON 봉투를 푸는 코드가 클라이언트 패키지
**밖에 6곳** 있다 — `TraceSpans:61` · `Collector:186` · `SurveyResult:83` · `Signal:301` ·
`EvidenceExtractor:199` · `LokiLogDedup`. 즉 교체 비용은 클라이언트 클래스가 아니라
**쿼리 방언과 응답 봉투** 두 가지에 있고, 메서드 단위 인터페이스는 그중 어느 것도 못 건드린다.

**세 번째가 "지금 넣지 않는다"를 결정했다.** 진짜 seam(의도 단위)으로 가면 쿼리 생성이 구현체
안으로 들어가는데, 지금 실패 문구가 쿼리 원문을 품고 있다 —
`probe("Tempo 에러 검색 '" + surveyProperties.traceQuery() + "'", ...)` ·
`probe("Metric '" + query + "'", ...)`. 이 문구들은 `SurveyContextAssembler`의
`# 무신호/실패 목록`으로 **모델에게 그대로 실려 간다**
(`SurveyResult.failures` javadoc: *"지우지 않고 그대로 모델에게 보인다"*).
따라서 의도 단위로 옮기면 **모델이 보는 텍스트가 바뀌고** 그 회차 점수는 이전 회차와 비교할 수 없다.

### Scouter를 실제로 대보면 — 축이 하나 비어 있다

Scouter Web API 문서(v1) 기준 대응이다. **2026-08-03 문서 확인이며 실물 연동은 미실시.**

| 지금 축 | Scouter 대응 | 판정 |
|---|---|---|
| Tempo 트레이스 조회 (`fetchTrace`) | `GET /v1/xlog-data/{yyyymmdd}/gxid/{gxid}` + `GET /v1/profile-data/{yyyymmdd}/{txid}` | 대응됨. **`gxid`가 traceId 자리**에 온다 |
| Tempo 검색 (`search`) | `GET /v1/xlog-data/{yyyymmdd}` (기간·필터) | 대응됨. TraceQL은 없고 필터 파라미터다 |
| Mimir 메트릭 (`queryRange`) | `GET /v1/counter/{counter}/...` | **부분 대응.** PromQL 식이 아니라 **카운터 이름**이다 — `min_over_time(up[5m])` 같은 식은 성립하지 않는다 |
| Loki 로그 (`queryRange`) | **없음** | **애플리케이션 로그 엔드포인트가 없다.** XLog는 트랜잭션 기록이지 로그가 아니다 |

이것이 설계를 바꾼다.

1. **로그 축은 Scouter가 못 채운다.** Scouter를 쓰더라도 로그는 파일 디렉터리 등 **다른 소스**에서
   와야 한다. 따라서 `provider=scouter` 같은 **전역 스위치는 틀렸다** — 축마다 독립적으로
   갈아끼워야 한다(`rca.source.trace=scouter` · `rca.source.log=file` · `rca.source.metric=scouter`).
2. **PromQL이 카운터 이름으로 바뀐다.** `SurveyProperties.metricQueries()`가 식 목록인 전제가
   깨진다 — 의도 단위 인터페이스가 필수인 근거가 하나 더 늘었다.
3. **날짜 파티션.** 경로에 `{yyyymmdd}`가 있어 **자정을 넘는 창은 호출을 쪼개야 한다.**
   현재 인터페이스가 `start`/`end`를 그대로 넘기므로 구현체가 흡수할 수 있다 — 인터페이스 변경 불필요.
4. **봉투가 완전히 다르다.** `{"status":200,"resultCode":0,"message":"success","result":[...]}`.
   Loki/Prometheus 봉투로 변환하는 어댑터가 필요하다.
5. **인증이 다르다.** IP 허용목록 · Bearer 토큰이고 Grafana 토큰 헤더가 아니다 —
   `GrafanaProperties.restClient()` 파생이 그대로는 안 맞는다.
6. **Scouter는 자바 에이전트다.** 도입하면 앱 계측(Brave/OTel)이 교체된다 —
   그건 **변경군 A**라 이 항목(B)과 같은 회차에 넣으면 안 된다.

### 회차 4에서 바꿀 것

**① 변경 표**

| 층위 | 무엇을 |
|---|---|
| 구조 개선 | `TraceSource` · `LogSource` · `MetricSource`를 **의도 단위**로 정의. `queryRange(logql, ...)`이 아니라 `errorWarnLogs(services, window, limit)` · `logRateCurve(services, window, step)` · `logsForTrace(traceId, ...)` · `searchErrorTraces(window, limit)` |
| 구조 개선 | 쿼리 생성을 각 구현체로. `LokiLogSource`가 LogQL 템플릿을 읽고, `ScouterTraceSource`는 `{yyyymmdd}` 분할과 gxid 매핑을 안에서 처리한다 |
| 배선 | **축별** `@ConditionalOnProperty` — 전역 provider 스위치가 아니다(로그 축을 Scouter가 못 채우므로) |
| 계약 명시 | **응답 형식을 인터페이스 계약으로 문서화.** 새 구현체는 기존 봉투로 **변환해서** 돌려준다 |
| 관측 보존 | 실패 문구가 쿼리 원문 대신 소스가 노출하는 `label()`을 쓰도록. 문구가 바뀌므로 **단독 회차**여야 한다 |

**왜 봉투를 유지하나** — 파서 6곳을 아끼려는 것이 아니라 **모델이 보는 것을 고정**하려는 것이다.
컨텍스트 형식이 바뀌면 이전 회차 점수 전부가 비교 불가가 된다. 새 소스가 자기 형식을 내놓게
하려면 그건 별도 회차의 별도 변경군이다.

**② 신호 도달 확인** — **부분 실시.** Scouter Web API에 트레이스·카운터 엔드포인트가 있고
**로그 엔드포인트가 없다**는 것까지 문서로 확인했다(위 표). 실물 서버 대조는 미실시 —
Scouter 인스턴스가 생기면 `GET /v1/xlog-data/{yyyymmdd}`가 서비스명·시각·에러·elapsed를
실제로 채워 주는지, 그 값으로 `Signal`을 만들 수 있는지를 먼저 잰다.

**③ 검증 설계** — 한 번에 하나만 바꾼다.
1. 인터페이스만 추출하고 구현은 Loki/Tempo/Mimir 하나씩 그대로 (행동 불변, 테스트로 고정)
2. 쿼리 생성을 구현체로 이관 (실패 문구 변경 — **여기서 회차를 끊는다**)
3. 두 번째 구현체는 실제 대상이 정해진 뒤에. 로그 축과 트레이스/메트릭 축은 **다른 소스**가 되므로 따로 붙인다

**④ 반증 조건** — 1단계 후 전 테스트가 통과하는데도 신호 산출이 달라지면 추출 위치가 틀린 것이다.
2단계 후 같은 문항 점수가 ±10을 넘게 움직이면 실패 문구가 채점에 영향을 준 것이고, 그 자체가 발견이다.
Scouter를 붙였을 때 `gxid` 하나로 서비스 간 연결이 복원되지 않으면 — 즉 상·하류가 다른 gxid를
갖는다면 — 이 프로젝트의 traceId 전제가 깨지므로 수집 단위부터 다시 설계해야 한다.

**⑤ 현재 상태** — **미착수·미측정.** 인터페이스는 없고 구현도 하나뿐이다.
완료된 것은 조사뿐이다: 쿼리 방언·응답 봉투·실패 문구의 모델 노출을 코드에서 확인했고,
Scouter 대응 축을 문서로 대조해 **로그 축이 비어 있다**는 것을 확인했다.
그 결과가 "지금 넣지 않는다"와 "전역 스위치가 아니라 축별 스위치"의 근거다.

## 캐시 미스 로그가 없어서 AU-4가 4번 연속 −10점

**변경군 A (앱 계측 · toy-content) · 미착수**

### 한 줄로

피드 목록은 작성자 정보를 **일괄**로 가져오는데, **그 경로에만 캐시 미스 로그가 없다.**
그래서 *"캐시가 만료돼 auth로 직행했다"* 를 쓸 근거가 **관측에 존재하지 않는다.**

### 어떻게 알았나

AU-4의 1) 원인은 네 번 연속 30점이고 감점 사유가 매번 같다 — 캐시 만료 미언급.
처음엔 프롬프트 문제로 봤는데, **도구를 전부 갈아끼운 회차 3에서도 30**이라 관측을 직접 뒤졌다.

| 확인한 것 | 결과 |
|---|---|
| 폴백이 난 요청의 전체 로그 | **1줄** (폴백 ERROR 그것뿐) |
| 그 구간의 캐시 로그 | **0건** |
| **단건** 조회 경로 (`getUserInfo:68`) | 미스 로그 **있음** — `[user-cache] 캐시 MISS - userId: …` |
| **일괄** 조회 경로 (`getUserInfos:115`) | 미스 ID를 세어 놓고 **로그 없이** API 호출 ← **여기** |

AU-4의 증상 경로(피드 → 작성자 N명)는 **전부 일괄**이라, 이 문항에서만 신호가 통째로 빈다.

**A-1이 이 구멍을 키웠다.** 회차 3에서 *"캐시 미스 INFO는 의도적으로 제외 — 접두사를 붙이면
프로브가 정상 동작을 폴백으로 집계한다"* 고 뺐는데, **접두사를 나누면 둘 다 만족한다.**

### 고칠 것

`ExternalUserInfoService.getUserInfos`의 `missingIds` 산출 직후에 한 줄:

```java
log.info("[user-cache-miss] 캐시 미스 {}/{} → 원격 조회: userIds={}",
         missingIds.size(), validUserIds.size(), missingIds);
```

- **접두사를 `[user-cache-miss]` 로 분리한다** — 프로브가 세는 `[user-fallback]`·`[user-cache]`
  어느 쪽에도 안 걸려 A-1이 걱정한 오집계가 안 난다
- 단건 경로도 같은 접두사로 맞춘다 — 두 경로가 다른 이름을 쓰면 검색이 또 깨진다
- **사실만 적는다.** *"캐시 만료로 auth 직행"* 같은 결론 문구는 넣지 않는다 — 그건 앵커
  만점 문언이고, 로그에 심으면 정답을 주는 것이다(§4 블라인드)

### 도달은 이미 확인됐다

INFO는 **traceId 일치 채널**로 들어온다(레벨 필터가 없다). AP-1 회차 3 컨텍스트에
`[user-cache] 캐시 HIT - userId: 1, elapsed: 4ms` 가 실제로 실렸다.
**찍기만 하면 온다.**

### 순서를 지켜야 한다

```
① 로그 추가 → 배포 → AU-4 재주입 → 재조사
      ↓ 안 오르면
② C-3 (프롬프트 인과 사슬) 넣고 다시
      ↓ 그래도 안 오르면
③ 앵커 개정 ㅎ (캐시 만료를 발현 조건으로 보고 1)에서 제외)
```

**성공 기준은 점수가 아니라 인용이다** — 리포트가 미스 로그를 근거로 캐시 만료를 말하는가.
말하면 1)이 30 → 40이다.

**주입도 함께 고쳐야 한다** — 폴백이 보이는 창은 `다운 시간 − 캐시 TTL(10분)`이다.
회차 3은 11분 30초 다운이라 창이 **1분 30초**뿐이었고 폴백이 1건만 찍혔다.
**20분 이상 유지 + 후반부 트래픽**이 필요하다([au-4/round-3.md](../au-4/round-3.md)).

## 탐색 후보의 지문 — 로그 채널만 판별력이 0이다

**변경군 B (조사 도구).**

### 상황

| | |
|---|---|
| 계기 | *"유사 장애가 섞이면 후보 목록만으로 그 장애를 골라낼 수 있는가"* |
| 후보의 지문 | `key() = 채널 \| 리소스 \| 지문`. 지문은 Tempo=엔드포인트명, Mimir=지표명, **Loki=항상 `ERROR/WARN`** |
| Loki 후보가 들고 있는 것 | 서비스명 · 건수 · 5분 구간. **그게 전부다** |
| 스윕 Loki 쿼리 | `sum by (service_name) (count_over_time({service_name=~"..."} \|~ "ERROR\|WARN" [5m]))` |
| 현재 상태 | **미착수.** 회차 3은 이 상태로 baseline이 된다 |

### 무엇이 일어났나

첫 판단은 *"후보가 부실하면 원본 JSON이 메운다"* 였다. 탐색 컨텍스트에는 후보 목록과 원본이
함께 실리므로 요약이 흘린 것을 원본이 받아낼 것이라고 봤다.

**실측으로 반증됐다.** 저장된 스윕(`scan-1785312796`)에서 채널별로 재 보니 원본이 후보보다
더 주는 것은 **Mimir 시리즈 라벨**과 **파손된 트레이스 행** 둘뿐이었고, **Loki는 0**이었다.

| 채널 | 원본에만 있는 것 | 크기 |
|---|---|---|
| Mimir | `topic`·`consumergroup`·`partition` 라벨 · 전체 값 곡선 | 32 KB |
| Tempo | `trusted=false` 행 · `serviceStats` · span 속성 | 1.4 KB |
| **Loki** | **없음** | **0** |

Loki 원본 4,223 B 중 실제 데이터는 **146 B**이고, 그 146 B가 곧 후보에 적힌 건수다.
나머지 4,077 B는 Loki가 붙이는 쿼리 성능 통계(`stats`)다.

```text
실제 데이터 (146 B):
[{"metric":{"service_name":"auth-service"},   "values":[[1785315300,"4"]]},
 {"metric":{"service_name":"content-service"},"values":[[1785315300,"4"]]}]
```

즉 **로그에 답이 있는 장애는 원본을 줘도 탐색이 구별할 수 없다.** 후보 포맷 문제가 아니라
**스윕 쿼리가 `sum by`로 내용을 지운 결과**이고, 구조적이다.

Mimir 라벨 쪽은 회차 3에서 이미 해소했다(설명 문구에 시리즈 라벨 편입, 지문에는 넣지 않음 —
키에 넣으면 44개 시리즈가 44개 후보로 흩어진다). **남은 것이 Loki다.**

### 회차 4에서 바꿀 것

**① 변경 표**

| 층위 | 무엇을 |
|---|---|
| 신호 공급 | 스윕 Loki 채널에 **대표 에러 라인 샘플**을 함께 싣는다. 발생률 곡선은 그대로 두고, 버킷마다 1~2줄 |
| 구조 개선 | `Signal.Series.logSignature()`가 샘플에서 예외 클래스를 뽑아 지문으로 쓴다 (현재는 `exc` 라벨 폴백뿐) |

**② 신호 도달 확인** — **미실시.** 다음을 먼저 재야 한다.

- 같은 창에 `limit=2`·`direction=forward`로 라인 조회를 걸면 응답이 얼마인가 (추정 4 KB, 실측 필요)
- 그 라인에서 예외 클래스가 **문자열로 뽑히는가.** 평문 Logback + ANSI 이스케이프라
  `logfmt` 파서가 안 먹는다는 것이 이미 확인돼 있다 — 라인 필터·정규식으로 잡아야 한다
- 스택 줄이 딸려 오면 **버킷당 1줄 전제가 깨진다**(스택은 traceId 없는 별개 엔트리다)

**③ 검증 설계** — 한 번에 하나만 바꾼다.
1. 샘플 라인만 추가하고 지문은 `ERROR/WARN` 유지 → **컨텍스트 증가분만** 측정
2. 지문 분해를 켠다 → 후보 개수가 늘어나므로 **군집이 과분할되는지** 확인
3. 로그에 답이 있는 문항(AP-2 계열)에서 탐색 선택이 바뀌는지 본다

**④ 반증 조건** — 샘플을 실었는데도 탐색 선택이 안 바뀌면 문제는 정보량이 아니라 프롬프트다.
지문 분해 후 한 서비스의 후보가 5개를 넘으면 과분할이므로 예외 클래스가 아니라
**최상위 프레임**으로 축약해야 한다. 컨텍스트 증가분이 10 KB를 넘으면 버킷당 1줄로 줄인다.

**⑤ 현재 상태** — **미착수·미측정.** 완료된 것은 진단뿐이다:
채널별로 원본과 후보의 정보량 차이를 실측했고(Loki 0), 원인이 후보 포맷이 아니라
스윕 쿼리의 `sum by`라는 것을 코드에서 확인했다. **회차 3은 이 결함을 안은 채 baseline이 된다.**

## 탐색 입력의 원본 94% — "빼고 재 본다"가 아니라 요약을 먼저 완성한다

**변경군 B (조사 도구).** 위 "탐색 후보의 지문" 항목이 **선행 조건**이다.

### 상황

| | |
|---|---|
| 계기 | 2단(탐색·분석) 구조 평가(2026-08-03)에서 탐색 호출이 **오버헤드가 페이로드보다 큰 호출**로 확인됐다 — AP-1 회차 3 실측: 오버헤드 29,430 tok vs 컨텍스트 몫 26,090 tok |
| 원본의 몫 | 스윕 원본 JSON이 탐색 컨텍스트의 **약 94%** (38,445B 중 36KB). 산출은 사실상 후보 번호 하나다 |
| 스위치 | `rca.survey.include-raw` (기본 `true` = A팔). `false`(B팔)면 후보 목록·후보 못 된 트레이스·채널별 도달 요약·무신호 목록만 싣는다. 저장 스윕 재생 실측 **45,991자 → 7,697자 (−83%)** |
| B팔이면 | 탐색 컨텍스트 몫이 약 4,000 tok대로 내려가 호출의 **약 85%+가 CLI 오버헤드**가 된다 |
| 목표 | **요약본(후보 목록)만으로 장애 후보 판별이 성립**하게 만든 뒤, 기본값을 B팔로 전환한다 |
| 현재 상태 | **미착수.** 스위치·계측(`triage.rawIncluded`)만 코드에 있고 **A/B 대조는 0회**다 |

### 무엇이 일어났나

첫 판단은 *"산출이 후보 번호 하나이니 원본을 빼고 재 보면 된다"* 였다.
[관측개선.md](../round-3/관측개선.md)의 한계 문구가 그 순서를 막았다 — 지금 B팔에서
나빠지면 **원본 부재 탓인지 후보 지문 부실 탓인지 갈리지 않는다.** 실제로 위 지문 항목의
채널별 실측이 후보 부실을 이미 확정해 놨다: 원본이 후보보다 더 주는 것이 Mimir 라벨·값
곡선(32KB)과 Tempo 파손 행·serviceStats·span 속성(1.4KB)이고 **Loki는 0**이다.
이 중 라벨·파손 행·채널별 도달 요약은 회차 3 적용분(`bed40a2`)에서 요약으로 옮겨졌다.

남은 갭도 실측으로 좁혀졌다. 회차 3 탐색이 INC-1·2를 기각한 인용문이
*"13개 샘플 전 구간 0… 지연이라 부를 수 없으며"* 인데, 후보 설명(`Signal.what()`)은
`"lag 가 0이었다 (from ~ to)"` — **구간만 있고 샘플 수·곡선 통계가 없다.**
"13개 샘플"은 원본에서만 셀 수 있다. 즉 **회차 3의 기각 품질은 원본에 기대고 있었고**,
이 상태로 B팔 전환부터 하면 프로젝트 최초의 후보 기각 능력이 무너질 수 있다.

그래서 순서를 뒤집었다: 원본을 빼는 것이 아니라 **원본에서만 얻을 수 있던 판단 재료를
요약으로 옮긴 다음**, A/B 대조로 원본의 잔여 기여도를 재고, 기여가 없으면 기본값을 바꾼다.

### 회차 4에서 바꿀 것

**① 변경 표**

| 층위 | 무엇을 |
|---|---|
| 신호 공급 | **Loki 대표 에러 라인 샘플 + 지문 분해** — 위 지문 항목 그대로. 이 항목의 선행 조건 |
| 신호 공급 | Mimir 신호 설명에 **곡선 요약 통계**를 붙인다 — 샘플 수·0/결측 비율·신호 구간 전후 값 (예: `lag 가 0이었다 (from ~ to · 13/13 샘플 · 창 전체)`) |
| 신호 공급 | Tempo 원본에만 남는 1.4KB(serviceStats·span 속성) 중 후보 설명에 넣을 것을 실측 선별 |
| 구조 개선 | 위가 끝난 뒤 `include-raw` 기본값 `false` 전환. 설정 한 줄이라 되돌림도 한 줄이다 |

**② 신호 도달 확인** — Loki 몫은 지문 항목 ②와 같다(미실시). Mimir·Tempo 몫은 새 조회가
필요 없다 — `SurveyResult`에 이미 담겨 오는 값을 세는 것이라 저장 스윕 재생으로 확인된다.

**③ 검증 설계** — 한 번에 하나만 바꾼다.
1. 요약 강화를 **A팔 유지** 상태로 넣고 컨텍스트 증가분만 잰다 (지문 항목 1·2단계 포함)
2. **저장 스윕 재생으로 A/B 탐색만 대조한다** — 같은 입력에서 chosen/dismissed/창이
   일치하는가. 주입도 조사 완주도 필요 없고 탐색 호출 2회 비용이다
3. 일치하면 기본값을 B팔로 바꾸고, 다음 실 회차에서 탐색 컨텍스트 몫(in − overhead)이
   26,090 → 약 4,000대로 내려가는지 확인한다

**④ 반증 조건** — 강화 후에도 B팔 선택이 A팔과 갈리면 원본의 어느 정보가 갈랐는지
역추적해 요약으로 옮긴다. 역추적으로 특정이 안 되면 차이는 정보가 아니라 실행 변동성이므로
같은 팔 반복(N=2)으로 편차를 먼저 잰다. B팔 전환 뒤 탐색 축(15점) 점수가 떨어지면 기본값을
되돌린다. 요약 강화 후 B팔 컨텍스트가 A팔의 절반을 넘으면 그건 요약이 아니라 원본을 옮겨
적은 것이다 — 통계 줄을 줄인다.

**⑤ 현재 상태** — **미착수·미측정.** 완료된 것: 스위치·계측 반입과 1차 요약 편입(회차 3
적용분, `bed40a2`) · B팔 크기 재생 실측(−83%) · 채널별 갭 실측(지문 항목, Loki 0) ·
기각 인용문의 샘플 수가 후보 설명에 없음을 코드로 확인(`Signal.what()`은 구간만 만든다).
미측정: 원본의 선택 기여도(A/B 대조 0회) · Loki 샘플 도달(지문 항목 ②).
