## 무엇을 더 봤나 — 딱 두 가지

### ① 발행측이 정상이라는 증거 (1) +10)

실행 2는 **발행 성공 로그를 직접 인용**했다:

> *"14:25:15Z content-service `[notify] **알림 발행 성공**: userId=7, type=BATTLE_ITEM_COMMENT,
> partition=3, offset=1045`"*

앵커 1)의 만점 조건이 *"컨슈머 부재로 적체 **+ 발행측 정상 판단**"* 인데, 실행 1은 앞엣것만
했다. 이 로그는 **두 실행의 창에 모두 있었지만**(14:25:15Z는 양쪽 창 안), 실행 1은
인용하지 않았다 — 복구를 못 본 상태에서 *"파드가 사라졌는지"* 를 확정하는 데 서술이
집중됐기 때문으로 보인다.

### ② 알림이 결국 도착했다는 증거 (4) +5)

실행 2는 **DLQ 재처리 성공부터 FCM 발송까지** 타임라인으로 복원했다:

```
14:25:15Z  발행 성공 (offset=1045)
14:25:45 / 14:26:16 / 14:26:47 / 14:27:18Z  처리 실패 1~4회차 (각 30초 Mongo 타임아웃)
14:27:18Z  DLQ 발행
14:30:20Z  DLQ 재처리 성공 — insert 3.6ms · FCM tokens=1, success=1, failure=0
           → 발행에서 실제 전달까지 5분 5초 지연
```

그리고 결론을 이렇게 냈다: *"최소한 푸시 채널로는 (지연되긴 했으나) **도달했다**."*

앵커 4)의 만점이 *"**지연이지 유실 아님** + 복구 시 백로그 일괄 도착"* 이고, 0점 사유가
*"'유실'로 판정"* 이다. 실행 1은 1순위 제목에 *"DLQ 유실"* 이라 썼는데, 실행 2는
**도착을 관측으로 확정**했다.

**lag도 소진까지 봤다** — 탐색 evidence에 *"`…partition=3` 0→1→11→25→26→**0**, 14:29~14:44
누적 후 **해소**"*. 실행 1의 창은 lag 25에서 끝나 소진을 볼 수 없었다.

## 이 회차가 처음 잰 것 — 조사 시점이 점수를 만든다

이 프로젝트가 지금까지 통제해 온 변수는 **문항 · 자 · 입력 모델 · 도구** 넷이다.
이번 쌍은 그 넷을 전부 고정하고 **조사 시각만** 바꿨다.

**결과: 15점.** 그리고 감점의 성격이 능력이 아니었다 —

- 실행 1이 *"복구 시 백로그 도착"* 을 안 쓴 것은 **그 창에 복구가 없었기 때문**이다
- 실행 1이 *"발행측 정상"* 을 안 쓴 것은 그 로그가 창에 있었으므로 **능력 문제에 가깝지만**,
  복구 미관측 상태에서 서술 초점이 *"파드가 정말 사라졌나"* 로 쏠린 정황이 있다

**§8.1 적용에 함의가 있다.** 지금 규칙은 *(문항 × 자 × 입력 모델)* 이 같으면 N=2로 묶는데,
**조사 시점이 다르면 관측 가능한 사실 자체가 다르다.** 이 쌍을 평균 내면 92.5인데
그 숫자는 어느 능력도 나타내지 않는다.

→ **§8.1에 "조사 창이 장애의 복구까지 덮는가"를 조건으로 추가할지 검토** (아래 대기열).
