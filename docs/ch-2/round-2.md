### 채점자 정정 — 처음에 "채점 불가"로 판정했다가 뒤집었다

**최초 판정은 "채점 불가(문항 격리 실패)"였다. 근거가 틀렸다.**

앵커의 문항 설명에 이런 산문이 있다.

> *"탐색 최난도 문항이다. **이상 트레이스가 존재하지 않는다** … 에러 검색으로는 0건이 나오고,
> 그 0건이 곧 '여기가 아니다'라는 정보다."*

이번 회차엔 에러 트레이스가 3건 나왔고(Mongo 타임아웃), **그것을 "앵커 전제가 깨졌다"고 읽어
탐색을 판정 불가로 처리했다.** 그러나 저 문단은 **문항 난도를 서술한 산문이지 채점 문언이 아니다.**
실제 요건은 *"S = lag 상승 구간 **또는** WS 급락 구간"* 택일이고 **에이전트는 lag로 충족했다.**

**앵커에 없는 잣대를 끌어온 것이므로 그 판정이 §8상 무효였다.** 산문과 요건을 가르는 것이
채점자의 일이다.

> **더 근본적인 지적이 있었다** — *"운영에서 장애 여러 개 발생하면 분석 안 할 거야?"*
> 겹친 장애는 실운영의 정상 조건이다. **겹친 창을 못 재는 자가 문제지 겹친 채록이 문제가 아니다.**
> 이번 회차는 CH-2 단독보다 **어려운 문항**이었고, 에이전트가 통과했다.

## 회차 조건 — 회차 1과 N=2로 묶지 않는다

**점수는 유효하지만 조건이 다르다.**

| | 회차 1 | 회차 2 |
|---|---|---|
| 입력 모델 | traceId 직접 | **자연어** |
| 자 | v1 4항목 → **채점 불가**(앵커 부적합·유형 B) | **v3 6항목 · anchors-v2** → **100** |
| 창 안 원인 | **1개** (chat 단독) | **2개** (Mongo + chat) |
| 에러 트레이스 | 0건 | **3건** |

**회차 1은 점수가 없어 델타가 성립하지 않는다.** 100은 **CH-2 최초의 실제 점수**다.
그리고 다음 회차를 N=2로 쓰려면 **같은 조건**(단독 주입 또는 복합 주입)으로 맞춰야 한다 —
복합 창은 난도가 다르다.

> **회차 2 대기열의 예측이 적중했다.** *"CH-2 → B-3로 `kafka_consumergroup_lag`·
> `websocket_active_users` 추가 → 만점 3종이 전부 범위 안 → **채점 성립**"*.
> lag는 실제로 만점의 핵심 근거가 됐고, WS는 값이 0이라 못 썼지만 **앵커가 인정한
> 메트릭 고고학으로 대체**됐다.

## 에이전트가 잘한 것

**복합 장애를 층으로 갈랐다.**

| 순위 | 무엇 | 역할 규정 |
|---|---|---|
| 1 | MongoDB 다운 | **근본 원인** |
| 2 | chat 소비 공백 9분 | **피해 확대 요인** |
| 3 | DLQ 복구 경로도 같은 Mongo 의존 | **지속 시간 증폭 요인** |

근거가 정교하다.

- **Connection refused를 네트워크 차단과 구별** — *"같은 호스트 IP 172.31.46.124의 redis:6379는
  정상(0.6ms), `up{job=redis}`·`up{job=kafka}`·`up{job=node-infra}` 모두 1 → 호스트/네트워크 장애가
  아닌 **mongod 프로세스 단독 다운**"*
- **30.01초 반복을 드라이버 상수와 대조** — `serverSelectionTimeout` 기본 30초.
  *"1건 처리에 30초×4회 ≈ 124초 동안 partition 3 소비 정지"*
- **exporter와 프로세스를 갈랐다** — *"`up{job=mongodb}`(exporter 자체)는 전 구간 1 → mongod만
  죽고 exporter는 살아있었음. 후보 1과 배치되는 것이 아니라 **'호스트 전체 장애' 해석을 반증**하는 값"*
- **DLQ 재처리 실패까지 추적** — `[KAFKA-RETRY] … cause=MongoTimeoutException` 2회.
  DLQ lag가 0으로 떨어진 시각(05:04:30)이 Mongo 복구(05:03:45) **이후**임을 대조

### 파드 소멸 원인은 절반만 맞았다 — 네 회차 연속 패턴

에이전트는 chat 파드 교체를 *"actuator health가 30초 블로킹 → readiness/liveness probe 실패 →
파드 축출"* 로 추정했다(확신도 중간, "추정"이라 명시).
