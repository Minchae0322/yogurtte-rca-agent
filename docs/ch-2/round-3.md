## 🔴 에이전트가 채점자의 측정을 정정했다

조사 전에 채점자가 `up{job=~".*chat.*"}` 를 `step=30`으로 재고 이렇게 기록했다:

> *"chat 전면 부재: 14:25:06Z ~ 14:29:36Z (4분 30초)"*

**틀렸다.** 리포트가 짚었다:

> *"`up{chat-service}`가 **0으로 관측된 적은 없다**(결측일 뿐). 파드 재시작/OOMKill 이벤트는
> 수집되지 않아 '파드가 사라졌다'고 단정할 수 없다."*

그리고 **메커니즘까지 댔다**:

> *"수집된 chat-service 트레이스 20건 중 대부분이 `secured request`가 **정확히 30.00초**
> … `MongoReactiveHealthIndicator: Mongo health check failed` + `Health contributor (mongo)
> took 30002ms to respond` 와 1:1 대응. `nio-8090-exec-1`~`exec-10` **전 스레드가 이 30초
> 대기에 사용됨** → actuator/health 요청이 톰캣 스레드를 전부 점유 → readiness 실패·**scrape
> 실패**로 이어질 조건이 갖춰졌다."*

즉 14:25~14:29의 chat 메트릭 공백은 **파드 부재가 아니라 Mongo 다운의 2차 효과**였다.
채점자는 시계열 공백만 보고 "부재"로 읽었고, 에이전트는 **트레이스·로그로 그 공백의 원인을
복원**했다. **이 문서의 §채점은 에이전트의 해석을 채택했다.**

### 1) 원인 적중 — 40점 만점

| 점수 | 요건 |

| 0 | 발행측·브로커 지목 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| 컨슈머 부재로 적체 | 충족 | 후보 2 — *"Mongo 회복 이후에도 chat-service의 `user.notifications` **소비가 멈춤** → partition=3 **lag 25건 적재(미소비)**"* · lag 시각별 값까지(14:33:44=8 → 14:37:29=25) |

> **이 항목은 개정 대기열 ㅈ가 지목한 구조 문제에 걸린다** — *"1) 원인 40에 10점 구간이
> 없다(40/30/20/0)"*. 실제 결과가 문언 사이에 떨어져 **판정을 강요당한 사례가 또 하나** 늘었다.

**1순위가 Mongo인 것은 감점하지 않았다.** 창에 실제로 두 장애가 있었고, 리포트가
후보 2에 *"최근 8분간 알림 미수신을 설명하는 **현재 진행 중** 원인"* 이라고 **시간대를 갈라
명시**했다. 0점 사유(발행측·브로커 지목)도 피했다.

## 비용 — 이 세션 최대

컨텍스트가 **362,008자**로 오늘 조사 중 가장 컸고 비용도 **$2.8151**로 최고다.

| 구성 | 크기 |
|---|---:|
| 메트릭 (원본) | 365,542 B → 요약 적재 |
| 로그 ERROR/WARN | **216,545 B** |
| 트레이스 (20건) | 98,114 B |
| 로그 traceId 일치 | 33,165 B |

**로그가 216KB인 것이 이번 회차의 특징이다** — Mongo 다운으로 chat ERROR가 68건/5분까지
치솟았고(평시 4건), 그것이 전부 실렸다. B-25가 메트릭을 접지 않았다면 컨텍스트가 70만 자를
넘었을 회차다.

**트레이스가 20건**인 것도 눈에 띈다(`max-traces` 10인데 초과) — 탐색이 후보를 7개 골라
후보별 창이 여럿이 됐고, 창마다 검색이 돌았기 때문으로 보인다. **확인이 필요하다**(아래).

## 🔴 회차 2(100)와 무엇이 달랐나

**주입은 같다.** 채점자 실측으로 **`scale 0` 약 9분**이 확인됐다(회차 2는 9분 30초).
차이는 주입이 아니라 **창의 조건 둘**이다.

| | 회차 2 (100) | **회차 3 (85)** |
|---|---|---|
| 주입 | `scale 0` 9분 30초 | **`scale 0` 약 9분** — 같다 |
| 같은 창의 다른 장애 | Mongo 다운 → **6~8분 뒤** chat 정지 (간격 넓음) | Mongo 다운 → **3분 뒤** chat 정지 + **Mongo가 chat scrape까지 죽임** |
| 복구 | **창 안에 있었다** | **창 밖이다** — 조사 창 종료 14:40:29Z, 복구 14:41:30Z (**1분 차이**) |
| 도구 | B-9·B-11·B-25 이전 | 전부 적용 |

**① 같은 모양의 공백이 창에 두 번 있었고 원인이 서로 달랐다.**
14:25~14:29 공백은 **scrape 실패**(Mongo 헬스체크가 톰캣 스레드 30초 점유), 14:32~14:41
공백은 **진짜 파드 부재**다. 앞의 것을 정확히 간파한 에이전트가 **뒤의 것도 같은 종류일 수
있다**고 유보한 것은 합리적이다 — 그 유보가 1)의 *"발행측 정상 판단"* 을 명시하지 못한
배경이기도 하다.

**② 복구가 1분 차이로 창 밖이었다.**
4) 만점 요건이 *"지연이지 유실 아님 + **복구 시 백로그 일괄 도착**"* 인데, **에이전트가 본
창에는 복구가 없다.** 회차 2는 복구까지 창 안이라 *"최대 9분 **지연 도착**"* 을 관측으로
말할 수 있었다. **4)의 −5는 능력 차가 아니라 진행 중인 장애를 조사한 결과다.**

**따라서 100 → 85는 성능 하락이 아니다.** 두 항목 모두 판정이고 둘 다 반대로 읽으면 100이며,
감점의 배경이 **관측 조건**으로 설명된다. 인용하려면 **복구까지 포함된 창**으로 N≥2가 필요하다.
