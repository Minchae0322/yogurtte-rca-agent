## 출발점 — 창을 좁혔는데 컨텍스트가 늘었다

회차 6은 신호 공급(B-44·B-45·B-46)만 켠 회차였다. 세 문항 모두 **조사 창이 좁아졌는데 컨텍스트가 늘었다.**

| 문항 | 좁힌 창 (5 → 6) | 컨텍스트 토큰 |
|---|---|---:|
| AP-1 | 14.2분 → **5.0분** (−65%) | 40,890 → **49,383** (+20.8%) |
| AP-2 | 15분 → 14분 | 42,482 → **75,116** (+76.8%) |
| AP-3 | 15분 → **9분** (−40%) | 43,119 → **60,654** (+40.7%) |

첫 판단은 *"B-44·B-45가 후보 설명을 늘린 탓"* 이었다. **탐색 단계 수치가 그것을 반증했다** —
탐색 컨텍스트는 세 문항 모두 +5~7%에 그쳤고 증가분은 전부 분석 단계에 있었다.

## 채널별로 분해하니 창은 손잡이가 아니었다

AP-1이 가장 깨끗한 표본이다(대상 단일, 창 −65%).

| 채널 | 회차 5 | 회차 6 | 창 −65%에 대한 반응 |
|---|---:|---:|---|
| 메트릭 | 105,113 B | 54,134 B | **−48% — 창을 따라간 유일한 채널** |

- **메트릭만 창에 비례한다.** 그런데 컨텍스트에 들어가기 전에 요약되므로(`metricSummarized`) 수집이 51 KB 줄어도 컨텍스트는 그만큼 안 준다.

**창에 반응하는 유일한 채널이 하필 컨텍스트 기여가 가장 작았다.**

## B-53 — 창의 96%가 잡트레이스였다

`max-traces: 10` 옆에 *"⚠ 근거 있는 값이 아니다: 창 안 트레이스가 실제로 몇 건인지 아직 안 세어 봤다"* 는
주석이 달려 있었다. **세었다.**

| AP-1의 5분 창 | |
|---|---:|
| 총 트레이스 | **470건** |
| `security filterchain before/after` | 360건 |
| `INFO` / `INFO 0` | 90건 |
| 스케줄러 `task …notify` | 2건 |
| **잡트레이스 소계** | **약 96%** |

잡트레이스의 정체는 **span 1개짜리 고아**다 — `security filterchain after`가 부모도 자식도 없이
홀로 트레이스를 이룬다(1건 약 2.2 KB). 계측이 필터체인 span을 HTTP 요청의 자식으로 붙이지 못해
생기는 것이라 원래는 앱 계측 결함이지만, 앱을 고치면 이후 모든 회차의 관측 조건이 바뀌므로
**조사 도구 쪽에서 막았다.**

그리고 Tempo는 **최신순**으로 주는데 후보 채우기에 관련도 정렬이 없다. 그래서
**AP-1·AP-2·AP-3 세 조사 모두 후보 검색 20건이 20건 다 잡트레이스**였다.

```
{}                                                    → 470건
{ rootName !~ "security filterchain.*|INFO.*" }       →  20건
{ rootName !~ "security filterchain.*|INFO.*|task .*" } → 10건  ← 전부 실제 요청
```

### 그런데 절감 예측이 반증됐다

같은 창에 B-53만 켜고 다시 돌렸다. 로그·메트릭은 바이트까지 같아 트레이스 채널 단독 A/B다.

| | B-53 off | **B-53 on** |
|---|---:|---:|
| 후보 검색 잡트레이스 | 20 / 20 | **0 / 10** |
| 트레이스 | 59,185 B | **136,608 B (+130.8%)** |
| 분석 컨텍스트 | 84,658 자 | **135,971 자 (+60.6%)** |

**예측은 −19,152 B였고 결과는 +77,423 B다.** 이유가 명확하다.

| 슬롯 8칸을 채운 것 | 1건 크기 |
|---|---:|
| 잡트레이스 (span 1개) | **2,250 B** |
| 실요청 (`POST /comments`, `POST /login`) | **12,072 B** |

**슬롯 단가가 5.4배 올랐다.** 노이즈 제거는 비용 절감이 아니라 **정보 밀도 개선**이었고,
`max-traces: 10`은 2.2 KB짜리가 들어가던 시절에 맞춰진 눈금이었다.

## B-55 — 설계대로 됐는데 효과가 없었다

후보 슬롯이 **선착순**이라 첫 창이 예산을 다 먹으면 뒤 창은 검색조차 안 나갔다.
AP-2 회차 6에서 실제로 그렇게 됐다 — w1(AP-1의 창)이 슬롯 4개를 다 채워서
**w2(팔로우 NPE, 조사 대상 그 자체)는 후보 검색이 아예 없었다.**

라운드로빈으로 고쳤고, w2가 처음으로 검색됐다.

```
traces collected: 10 (지목 6 + 창 후보 4 · slots=4 · 창 2개 [8, 11])
```

**그런데 팔로우 트레이스는 또 안 실렸다.** w2가 준 15건 중 정답이 **9·11·12·14번째**였다 —
팔로우 요청이 창의 가장 오래된 쪽(01:31~01:33)에 있고 Tempo는 최신순으로 주기 때문이다.

리포트가 회차 6과 같은 문장을 또 적었다 — *"실패 traceId `6a7bcd177ec7…`의 Tempo 트레이스 —
수집된 10건에 없음."* **컨텍스트만 +21.7% 늘었다.**

## B-47 — 대조군이 절감분을 통째로 먹고 있었다

B-57까지 넣고도 **회차 5 대비로는 안 줄었다**(AP-1 −1.4%, AP-2 +18.5%, AP-3 +1.2%).
트레이스를 하나씩 재 보니 원인이 나왔다.

| AP-1 트레이스 | 회차 5 | 회차 7 (B-57) |
|---|---:|---:|
| 정답 트레이스 | 8,761 B | 8,761 B |
| 잡트레이스 9건 | ≈24,654 B | 0 |
| **대조군** | **없음** | **31,272 B** |
| 합계 | 33,415 B | 40,033 B |

**회차 5에는 대조군이 없었다** — B-46은 08-11에 들어갔다. 버린 것(24.7 KB)보다
새로 얻은 것(31.3 KB)이 커서 순증이 났다.

**대조군이 큰 이유는 성공 트레이스라서다.** 실패는 예외 지점에서 끊기지만 성공은 완주한다.

```
정답:   요청 → 인증 → INSERT 실패 → 롤백 → 500          (끝)
대조군: 요청 → 인증 → INSERT 성공 → 커밋 → Kafka 발행
                → chat-service 수신 → 푸시 디스패치 → Mongo·Redis   (계속)
```

상위 span 15개 중 8개가 대조군의 하류였다. **대조에 필요한 것은 루트 경로의 차분**이므로
**루트 서비스 구간만** 남기게 했다.

```
contrast trace 6a7bcb12…   31,272 B → 18,747 B   (−40.1%)
```

**발행 span은 남는다** — `publish`는 발행자(루트 서비스) 쪽에 찍히므로, AP-1이 정합성 판정에 쓴
*"성공 트레이스에는 `publish user.notifications`가 있고 실패에는 없다"* 논증이 그대로 성립한다.
빠지는 것은 **수신 이후**다. 접었다는 사실은 수집 누락 절에 명시해 모델이 부재를 신호로 오독하지 않게 했다.

## 부수 발견 — 없는 재발 패턴을 만들고 있었다 (B-58)

채점 중 탐색과 분석이 서로 다른 말을 해서 Loki에 직접 물었다.

| 지문 | 탐색이 보고 | **실측** |
|---|---|---|
| `DataException` | x5회 · 평균 60초 간격 | **1건** (01:22:30.515) |
| `NullPointerException` | x4회 · 평균 60초 간격 | **2건** (01:32:07.271·.393 — **122ms 안**) |

원인은 집계 창과 해상도의 불일치다.

```
range=[5m] · step=1m   →  01:33=2  01:34=2  01:35=2  01:36=2   ← 같은 사건이 4번 세어짐
range=[1m] · step=1m   →  01:33=2                               ← 실제
```

`log-query`는 `[1m]`인데 **예외 지문 쿼리만 `[5m]`** 이다. *"집계 해상도 1m 전환 완결"* 커밋이
`application.yml`의 쿼리들을 바꿨는데 **이 쿼리 하나만 Java 상수(`SurveyProperties`)로 살아 있어 빠졌다** —
yml 주석이 *"중괄호가 `${}` 문법과 겹쳐 여기 적을 수 없다"* 고 그 이유를 적어 두고 있다.
**설정이 두 곳에 사는 구조가 만든 누락이다.**

**누락이 아니라 조작이라 위험하다.** 신호가 안 오면 리포트가 *"데이터 부족"* 으로 표시하지만
없는 재발 패턴은 그대로 근거가 된다 — AP-2 리포트가 *"단발 사고가 아니라 **조회할 때마다
재현되는 패턴**"* 이라고 썼는데 실제로는 122ms 안의 단발이었다.

**지금 고치지 않았다** ([§3.1](../CLAUDE.md)) — 회차 7이 이 상태로 채록·채점됐다. 회차 8을 전후 대조로 쓴다.

## 인용할 때 붙여야 할 단서 셋

**② B-47 적용 실행은 N=1이다.** 회차 7 본편은 N=2지만 그건 B-47 이전 구성이다.
**−10.6%는 단일 실행 값이다.**

**③ AP-1 한 문항이다.** AP-2는 대조군이 팔로우 경로 밖이라 접기 효과가 다르게 나올 수 있다.
