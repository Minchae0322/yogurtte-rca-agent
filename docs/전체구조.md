## 0. 한 장

```
POST /diagnose  {"question": "...", "from": ..., "to": ...}
   │
   ▼  TimeExpressionParser          ① 시간창 (코드, LLM 없음)
   ▼  Surveyor                      ② 스윕 — 집계 쿼리 9건
   ▼  SignalExtractor               ③ 응답 → Signal
   ▼  Incident.cluster()            ④ Signal → 후보
   ▼  SurveyContextAssembler        ⑤ 후보 목록 (원본 JSON 제외)
   ▼  ★ LLM ① 탐색                  후보 번호를 고른다
   ▼  Incident.window()             ⑥ 창·서비스·traceId 파생 (코드)
   ▼  Collector                     ⑦ 수집 — 원본 쿼리 4종 + 대조군
   ▼  ContextAssembler              ⑧ 정제·조립
   ▼  ★ LLM ② 분석                  원인·근거·조치
   ▼  ReportMarkdown / ReportStore  ⑨ 리포트
```

| 단계 | 주체 | 산출 |
|---|---|---|
| ① 시간창 | **코드** | 스윕 창 |
| ②~⑤ | **코드** | 후보 목록 |
| 탐색 | **LLM ①** | **후보 번호 하나** — 모델이 만드는 정보는 이것뿐 |
| ⑥ | **코드** | 조사 창 · 대상 서비스 · traceId |
| ⑦~⑧ | **코드** | 분석 컨텍스트 |
| 분석 | **LLM ②** | 자유 서술 |

> **핵심 경계**: 코드는 시간창·조회·신호·후보·조사 대상을 결정하고, LLM은 **후보 번호 선택**과 **분석 서술**만 맡는다. 자세한 기준은 [9. 경계](#9-경계--무엇을-코드가-정하나)에 있다.

## 1. 시간창 — 두 번 정해진다

### 1차 · 자연어 → 스윕 창 (`TimeExpressionParser`)

| 정책 | 값 |
|---|---|
| 우선순위 | **구간 > 시각 > 시간대 > 날짜 > 상대** |
| 시각만 있을 때 여유 | `POINT_PADDING = ±30분` |
| 미래 | `now`로 자른다 |
| 날짜 없는 시각 | **가장 가까운 과거** |
| 표현 없음 | `default-lookback-hours = 24` · `confidence = FALLBACK` |
| 상한 | `max-window-hours = 48` |
| 타임존 | `survey.zone = Asia/Seoul` |

`confidence`(EXACT / APPROX / FALLBACK)를 **값으로** 남긴다 — FALLBACK 회차를 분리 집계해야
*"창을 못 잡아 틀린 것"* 과 *"분석이 틀린 것"* 이 안 섞인다.

명시적 `from`/`to`가 **절반만 오거나 순서가 뒤집히면 400으로 거부**한다(결함 22 — 구 파서는
조용히 무시해 과거 재조사가 오늘 창을 조사했다).

### 2차 · 고른 후보 → 조사 창 (`Incident.window`)

```
창 = [첫 신호 − pad, 마지막 신호 + pad]   →  스윕 창으로 clamp
여러 개 골랐으면 unionWindow = min(start), max(end)
```

| 정밀도 | 어느 신호 | pad |
|---|---|---|
| Tempo | span 시각 (ms 정확) | **0** (`incident-pad-exact`) |
| Loki | `[ts − lookback, ts]` — 폭이 이미 구간에 있다 | **0** |
| Mimir | 샘플 시각 (점) — 전이·원복이 샘플 사이에 숨는다 | `incident-pad-bucket` — 미설정이면 **`step × 2`** (지금 2m) |

**pad는 정밀도가 아니라 채널에서 나온다 (2026-08-11).** 후보 하나는 채널 하나이므로
(클러스터 키가 `channel|resource|signature`) 애매함이 없다. 메트릭에만 여유를 남기는 이유는
**창을 신호 끝에서 딱 끊으면 원복 여부를 읽을 수 없기** 때문이고, 그 문제는 폭 없는 점
신호인 메트릭에서만 살아 있다.

## 2. 스윕 — 집계 쿼리 9건

전부 집계라 **응답 크기가 창 폭이 아니라 스텝 수로 결정된다**(`survey.step = 5m`).
순차 실행이고 채널별로 시간을 잰다(`tempoMs` · `lokiMs` · `mimirMs`).

| 구분 | 쿼리 수 | 이상을 보는 방식 |
|---|---:|---|
| Tempo | 2 | 에러 · 임계값 초과 지연 |
| Loki | 2 | ERROR/WARN 총량 · 예외 지문 |
| Mimir | 5 | 상태의 0 구간 · 값 변화 · 결측 |

> **읽는 법**: 아래 ①~⑨은 모두 스윕 단계의 집계 쿼리다. 원본 로그·트레이스는 [6. 수집](#6-수집--원본-쿼리) 단계에서 별도로 가져온다.

### ① Tempo 에러

```traceql
{ status = error }
```

`survey.trace-limit = 20`. **0건이면 그 사실이 문장으로 실린다** —
*"트레이스가 생성되지 않는 장애(컨슈머 전멸·파드 부재)이거나 에러가 아닌 형태의
장애(200 성공 + 지연)일 수 있으니 이 사실 자체를 근거로 쓸 것."*

### ② Tempo 지연

```traceql
{ duration > 3s && status != error }
```

**에러 채널과 따로 던진다** — 합치면 *"어느 채널로 도달했는지"* 가 사라지는데, 200 성공 +
지연 장애에서는 그것이 곧 장애 성격이다(CH-3는 에러 검색 0건).

> ⚠ 임계값이 어긋나 있다 — `application.yml`은 `3s`, `SurveyProperties` 기본값은 `2s`.
> yaml이 이겨서 실효는 **3s**이고, B-43이 2s로 내린 의도(Redis 2,000ms 지연 19건 포착)가
> **실효 없다.**

**받는 것 (①②공통)** — 트레이스당 한 줄. span은 안 온다.

```json
{"traceID":"6a7412…", "rootServiceName":"content-service",
 "rootTraceName":"http post /battles/{battleId}/items/{itemId}/comments",
 "startTimeUnixNano":"…", "durationMs":60080,
 "serviceStats":{"content-service":{"spanCount":15},
                 "chat-service":{"spanCount":10,"errorCount":4}}}
```

`serviceStats`가 **B-44**다 — 루트만 보면 `content` 문제인데 **에러는 chat에서 났다.**
저장 응답 645건 중 52건이 2개 이상.

### ③ Loki 총 건수

```logql
sum by (service_name) (
  count_over_time({service_name=~"content-service|auth-service|chat-service"} |~ "ERROR|WARN" [5m]))
```

| 조각 | 왜 |
|---|---|
| 라인 필터 `\|~` | `\| logfmt \| level=~`은 **0건**. 평문 Logback이라 `level` 필드가 안 생긴다(B-2) |
| 스택 패턴 **없음** | 세는 쿼리라 스택 30줄이면 **예외 1건이 31건** |

받는 것: `{"service_name":"chat-service"} : [[…,"28"],[…,"7"]]` — **개수만.**

### ④ Loki 예외 지문 (B-45 · 기본 on)

```logql
sum by (service_name, exc, cause) (count_over_time({service_name=~"%s"}
  |~ `^[a-z][\w.]*\.[A-Z][\w$]*(Exception|Error|Throwable)
     |^Caused by: [a-z][\w.]*\.[A-Z][\w$]*(Exception|Error|Throwable)
     |(ERROR|WARN).*[a-z][\w.]*\.[A-Z][\w$]*(Exception|Error|Throwable)`
  | regexp `(?P<cause>Caused by: )?(?P<exc>[a-z][\w.]*\.[A-Z][\w$]*(?:Exception|Error|Throwable))`
  | exc !~ `.*\.[a-z]\..*`  [5m]))
```

**라인 필터가 세 갈래인 이유 — 예외 클래스가 세 자리에 찍힌다.**

```
org.springframework.dao.QueryTimeoutException: …         ← ① 스택 첫 줄 (레벨 토큰 없음)
Caused by: io.lettuce.core.RedisCommandTimeoutException  ← ② 원인. 진짜 의존성이 여기
… WARN [traceId=…] com.mongodb.MongoTimeoutException: …  ← ③ 헤더 인라인 (실측 5건)
    at …LettuceExceptionConverter.convert(…)             ← 셋 다 안 걸린다
```

| 후처리 | 하는 일 |
|---|---|
| `regexp` | 매칭을 **`exc` 라벨로 승격** — 그래야 `sum by`가 쪼갠다. `cause`로 최상위/원인 구별 |
| `exc !~ ".*\.[a-z]\..*"` | Logback **축약 로거**(`mc.e.t.a.c.e.GlobalException`) 제거 — 유일한 오탐이었다 |

**③과 대체가 아니라 병렬**이다. ④만 쓰면 예외 없는 ERROR/WARN이 사라진다(08-05 창 78건 중 **42건**).
끄려면 `RCA_SURVEY_LOG_SIGNATURE_QUERY=off`.

### ⑤~⑨ Mimir

```promql
min_over_time(up[5m])                        # 프로세스 생사 — AU-2/AU-4
min_over_time(mongodb_up[5m])                # CH-1 · CH-3
min_over_time(kafka_brokers[5m])             # IN-2
max_over_time(kafka_consumergroup_lag[5m])   # CH-2
max_over_time(websocket_active_users[5m])    # CH-2
```

**집계 함수로 감싸는 것이 요점** — 순간값을 5분마다 찍으면 그 사이 단기 장애가 사라진다
(CH-3의 23초 다운이 `mongodb_up` 05:20:09=1 / 05:25:09=1 사이로 빠졌다).
**점 개수가 같아 응답 크기는 불변.** 상태 지표는 `min`, 누적 지표는 `max`.

## 3. 응답 → Signal (`SignalExtractor`)

```java
Signal(from, to, channel, precision, resource, signature, what, ref)
       └─ 언제 ─┘  └──── 키 3축 ────┘        └ 읽는 것 ┘ └ 되짚을 단서 ┘
```

> **Signal의 역할**: 채널마다 다른 응답 모양을 **공통 구조 하나**로 바꾼다. 그래야
> [4. 후보 묶기](#4-signal--후보-incidentcluster)가 채널을 몰라도 된다.

| 채널 | 이상의 정의 | from / to | resource | signature | ref |
|---|---|---|---|---|---|
| **TEMPO** | 검색에 걸린 **존재** | `startedAt` ~ `+durationMs` | `rootServiceName` | `rootTraceName` | **traceId** |
| **LOKI** | **0이 아닌 버킷** | **`버킷−5분`** ~ 버킷 | `service_name` 라벨 | `ERROR/WARN` 고정 | `"loki-rate"` |
| **MIMIR** | **0 구간 · 값 변화 · 결측** | 검출 구간 | `job`→`application`→`instance` | 지표명 | 쿼리 문자열 |

**임계값으로 판정하지 않는다** — 변화·부재·존재만 센다. 값의 크기는 판정이 아니라
`what` 문구에 담아 모델이 보게 한다. 이유 셋: ⓐ 평시 baseline이 없다 ⓑ 문항별 임계값은
**정답을 심는 것**이다 ⓒ 에이전트가 이미 같은 기준을 쓴다(*"전 구간 상수 — 무관"*).

### ① TEMPO — 검색 결과 한 줄 = Signal 하나

```json
{"traceID":"6a741223…", "rootServiceName":"content-service",
 "rootTraceName":"http post /battles/{battleId}/items/{itemId}/comments",
 "startTimeUnixNano":"1785991715896643000", "durationMs":60080,
 "serviceStats":{"content-service":{"spanCount":15},"chat-service":{"spanCount":10,"errorCount":4}}}
```

```java
new Signal(
    startedAt,                          // from
    startedAt.plusMillis(durationMs),   // to  ← 점이 아니라 구간이다
    Channel.TEMPO, Precision.EXACT,
    rootServiceName, rootTraceName,
    "content-service http post /battles/… 60,080ms (error 채널)  [지나간 서비스: chat-service 10 (err 4) · content-service 15]",
    traceId)                            // ref — traceId를 갖는 유일한 채널
```

**`trusted=false`는 신호가 안 된다.** Tempo가 `durationMs` 33일짜리나 시작 시각 0인 행을
내려준 적이 있어(CH-2 실측) 창 계산에 넣으면 그 행이 항상 1위가 된다. 다만 **후보 목록에는
남는다** — *"이 traceId를 지목하면 원본을 다시 받아 조사한다"*.

**두 검색을 합칠 때 먼저 온 채널을 유지한다** — 같은 트레이스가 error·slow에 다 걸리면
error로 남긴다. *"어느 채널로 도달했는가"* 가 그 자체로 정보다.

### ② LOKI — 0이 아닌 버킷 하나 = Signal 하나

```json
{"metric":{"service_name":"chat-service"},
 "values":[[1785991500,"28"], [1785991800,"7"], [1785992100,"0"]]}
```

```java
new Signal(
    at.minus(lookback),   // from = 버킷시각 − 5분   ★
    at,                   // to
    Channel.LOKI, Precision.BUCKET,
    series.service(), "ERROR/WARN",
    "ERROR/WARN 28건 (04:30:00Z ~ 04:35:00Z)",
    "loki-rate")
```

값이 `0`인 점은 거른다(`count_over_time`은 0건 구간에 샘플을 안 만들지만 와도 무시).

**`from`을 당기는 것이 핵심이다.** `[[1785991500,"28"]]`은 *"04:35에 28건"* 이 아니라
**"04:30~04:35 사이에 28건"** 이다. 점으로 읽으면 최대 5분 어긋나고, 실제로 버킷 시각을
사건 시각으로 읽은 회차 리포트가 있었다.

#### 지문 곡선(④)은 같은 파서를 타고 두 곳만 다르다

```json
{"metric":{"service_name":"chat-service",
           "exc":"io.lettuce.core.RedisCommandTimeoutException",
           "cause":"Caused by: "},
 "values":[[1785991500,"14"]]}
```

```java
signature = "ERROR/WARN"                                     // 총 건수 곡선과 같게 둔다
what      = "원인 예외 io.lettuce.core.RedisCommandTimeoutException 14건 (…)"
//           ↑ cause 라벨이 있으면 "원인 예외", 없으면 "예외"
```

**파싱 전에 한 번 거른다** — 같은 `(서비스, 버킷)`에 원인 예외가 있으면 최상위 시리즈에서
**그 버킷의 점만** 뺀다. 개수가 1:1이라 둘 다 실으면 두 배로 세기 쉽고, 최상위는
프레임워크 래퍼라 의존성을 말해주지 않는다.

```
chat | 04:30 | QueryTimeoutException 14건        ← 원인이 있으니 이 점은 뺀다
chat | 04:30 | RedisCommandTimeoutException 14건 ← 남긴다  ("Redis"라고 이름이 말한다)
auth | 04:40 | RestApiException 2건              ← 원인이 없으니 남긴다
```

### ③ MIMIR — 시리즈 하나에서 검출기 **셋**이 각각 Signal을 만든다

```json
{"metric":{"job":"kafka","instance":"infra-server"},
 "values":[[…,"1"],[…,"1"],[…,"0"],[…,"0"],[…,"1"]]}
```

**검출기 1 · 0 구간** (`zeroRuns`) — 연속된 0을 한 덩어리로.

```
값:  1  1  0  0  1
           └──┘   →  "kafka_brokers 가 0이었다 (04:49:55Z ~ 04:54:55Z)"
                      from = 첫 0,  to = 마지막 0
```

**`zero-is-abnormal` 목록(`up`·`mongodb_up`·`kafka_brokers`)에 있는 지표만** 이 검출기를
돈다. `lag=0`은 "안 밀림"이라 정상인데 신호로 세었더니 정상 파티션 36개가 각각 60분짜리
신호가 됐고 **조사 창이 스윕 창 전체로 벌어졌다**(컨텍스트 363,268자 · $2.78 ·
정답 트레이스가 수집 상한에 밀림).

**검출기 2 · 값 변화** (`valueChanges`) — 인접 쌍이 다르면.

```
값:  1  1  0  0  1
      ↕     ↕      →  "kafka_brokers 1 → 0" · "kafka_brokers 0 → 1"
   같음  1→0  0→1      from = 앞 점,  to = 뒤 점
```

> 첫 구현이 `Double != Double`(참조 비교)이라 **값이 같아도 매 쌍이 "변화"로 나가는**
> 잠복 버그가 있었다. 지금은 `doubleValue()`로 비교한다.

**검출기 3 · 결측** (`gaps`) — 샘플 간격이 step의 2배를 넘으면.

```
04:47:10 ●            ● 04:50:25
         └─ 3분 15초 ─┘   →  "kafka_brokers 시리즈가 … 구간에 없다 (스크레이프 대상 부재)"
```

**step은 설정값이 아니라 응답에서 추론한다**(`stepHint` — 첫 두 점의 간격). 설정과 실제가
다를 수 있다.

#### 지표명과 라벨을 가른다

```java
resource  = job → application → instance 폴백        // "kafka"
signature = metricNameOf(query)                      // "kafka_brokers" ← 집계 함수를 벗긴다
identity  = {consumergroup=…, topic=…, partition=3}  // what 문구에만
```

**집계 함수를 안 벗기면 지문이 `min_over_time_kafka_brokers_5m__`이 되고 `zero-is-abnormal`
목록과 안 맞는다** — 실제로 재생 도구가 소독된 파일명을 쿼리 키로 넘겨 이 함정에 빠졌고,
"0이었다" 신호가 사라져 후보가 13 → 14로 늘었다.

**시리즈 라벨을 지문에 안 넣는 이유**: 넣으면 44개 시리즈가 44개 후보로 흩어지고, 설명에서도
빼면 후보 목록의 36줄이 **글자 그대로 같은 줄**이 된다. 그래서 **키는 지표명, 설명은 라벨
포함**으로 갈랐다.

## 4. Signal → 후보 (`Incident.cluster`)

```
① 라벨 3축      key = 채널 | 리소스 | 지문      ← 시간이 안 들어간다
② 시간 간격     같은 키 안에서만, cluster-gap = 60s
③ ref 공유      → 병합                          ← 통을 넘는 유일한 경로
④ 시간 겹침     → related 표시                  ← 병합하지 않는다
```

### 값으로 따라가기

신호 6개를 예로 든다.

```
S1  TEMPO | content-service | POST /comments   04:48:35 ~ 04:49:36   ref=6a741223…
S2  TEMPO | content-service | POST /comments   04:46:50 ~ 04:46:52   ref=6a7411ba…
S3  LOKI  | chat-service    | ERROR/WARN       04:30:00 ~ 04:35:00   ref=loki-rate
S4  LOKI  | chat-service    | ERROR/WARN       04:35:00 ~ 04:40:00   ref=loki-rate
S5  LOKI  | chat-service    | ERROR/WARN       05:20:00 ~ 05:25:00   ref=loki-rate
S6  MIMIR | kafka           | kafka_brokers    04:49:55 ~ 04:59:55   ref=쿼리
```

**① 라벨로 통에 나눈다 (시간을 안 봄)**

```
TEMPO|content-service|POST /comments  →  S1  S2
LOKI |chat-service   |ERROR/WARN      →  S3  S4  S5
MIMIR|kafka          |kafka_brokers   →  S6
```

**② 통 안에서만 60초로 끊는다** — 기준은 직전 신호의 시작이 아니라 **`reach`
(지금까지 나온 끝 중 가장 먼 것)** 다. 신호가 점이 아니라 구간이라 시작만 비교하면
긴 구간 신호를 잘라먹는다.

```
LOKI chat:  S3 04:30──04:35   reach=04:35
            S4      04:35──04:40   시작 ≤ reach+60초  → 이어짐,  reach=04:40
            S5                       05:20 > 04:41    → 끊김
            → [S3 S4] · [S5]

TEMPO    :  S2 04:46:50──04:46:52   reach=04:46:52
            S1 04:48:35              > 04:47:52       → 끊김
            → [S2] · [S1]
```

**③ `ref`가 겹치면 합친다** — 통을 넘는 유일한 경로다.

```java
tempoRefs(signals)   // channel == TEMPO 인 것의 ref 만 모은다
sharesTraceWith(ids) // 빈 집합이면 무조건 false
```

```
[S1] {6a741223…}  ┐ 겹치는 게 없다 → 병합 0건
[S2] {6a7411ba…}  ┘
[S3 S4] {}   ← ref 가 "loki-rate"
[S6]    {}   ← ref 가 쿼리 문자열
             ↑ 빈 집합은 아무와도 안 이어진다
```

**시간 근접만으로는 절대 병합하지 않는다.** Mimir 신호와 Tempo 신호는 공유 식별자가 없어
코드가 인과를 알 수 없고, 토폴로지(*"chat이 Mongo를 쓴다"*)를 병합 근거로 쓰면
**채점 대상인 정답 구조를 코드에 심는 것**이다.

**④ 시각순 번호 + 겹치는 것 표시**

```
INC-1  [S3 S4]  04:30 ~ 04:40   LOKI  chat-service | ERROR/WARN
INC-2  [S2]     04:46:50        TEMPO content-service | POST /comments
INC-3  [S1]     04:48:35        TEMPO content-service | POST /comments
INC-4  [S6]     04:49:55        MIMIR kafka | kafka_brokers
INC-5  [S5]     05:20 ~ 05:25   LOKI  chat-service | ERROR/WARN

- 같은 시각의 다른 후보: INC-3, INC-4  (인과 여부는 판단하지 않았다)
```

### 후보가 들고 나가는 값

```java
firstAt()   = signals 의 from 최소            → 구간 시작
lastAt()    = signals 의 to   최대            → 구간 끝
precision() = 하나라도 BUCKET이면 BUCKET       → 창 여유 2분/5분을 가른다
traceIds    = TEMPO 신호의 ref 전부           → 딥 페치 대상
channel · resource · signature = 첫 신호의 것  → 통이 하나라 전부 같다
```

**접기** — 같은 `what`(숫자를 `#`로 정규화)이 3건 이상이면 한 줄로 접고
`[x13회 · 07:52:44~07:55:14 · 평균 10초 간격]`을 붙인다. 문구가 다르면 접지 않는다 —
다른 문구는 다른 사실이다.

**애매하면 나눈다.** 합쳐서 틀리면 창이 넓어지고 구별이 사라져 되돌릴 수 없지만, 나눠서
틀리면 고르지 않은 후보가 목록에 남아 되돌아갈 수 있다. **크기로 거르지도 않는다** —
CH-3의 결정적 로그 신호는 **1건**이었고 옆 버킷이 54건이었다.

> **한 문장**: 키는 `채널|리소스|지문` 셋이고, 시간은 그 안에서만 60초로 끊고,
> 통을 넘어 합치는 근거는 `ref`(traceId) 하나뿐이다.

## 5. 탐색 컨텍스트

```
# 탐색 대상        질문 · 스윕 창 · 창 해석 근거
# 장애 후보        Incident.describe()          ← 사실상 전부
# 후보 못 된 트레이스  시각·duration이 깨진 행
# 채널별 도달 요약   "조회했는데 0건" = 정상이었다
# 무신호/실패 목록
# 원본 관측 데이터   "이 회차는 싣지 않는다"      ← include-raw=false
```

원본이 이 단계 컨텍스트의 **94%**(38,445B 중 36KB)였는데 산출은 후보 번호 하나여서 뺐다.
**45,991자 → 7,697자(−83%)**, 산출은 동일(N=1).

> **탐색 단계의 산출물**: LLM은 이 요약을 보고 후보 번호 하나만 고른다. 원본 데이터와 원인 분석은 다음 수집·분석 단계의 몫이다.

## 6. 수집 — 원본 쿼리

> **수집 원칙**: 스윕은 후보를 찾기 위한 집계이고, 수집은 선택된 후보를 분석하기 위한 원본 조회다.

### Tempo

```
지목 traceId 전부       /api/traces/{id}         대표를 뽑지 않는다
대조군 (B-46)           { rootName = "..." }     루트 이름마다 가장 짧은 것 1건
창 안 후보 (B-9)        {}                       상태를 안 거른다
```

**대조군이 왜 따로 필요한가** — 정상 트레이스는 스윕의 두 필터(`status=error` ·
`duration > 임계값`)에 **구조적으로 안 걸린다**. B-9의 `{}` 검색이 메우라고 있었는데
Tempo가 최신순으로 주기 때문에 25분 창의 최신 20건이 전부 `security filterchain`
잡트레이스였다(IN-2 실측). 그래서 지목 검색으로 따로 가져온다.

**`max-traces` 밖에서 최대 3건** — 상한의 목적은 *무관한* 트레이스를 막는 것이고
대조군은 무관하지 않다. 없으면 *"대조군 없음"* 이 `failures`에 남는다.

### Loki

```
ERROR/WARN   {service_name=~"..."} |~ `ERROR|WARN|Exception|Caused by|\.java:[0-9]+\)`
traceId 일치 {service_name=~"..."} |~ "<id1>|<id2>" != "DEBUG"
```

**스윕과 반대로 스택을 넣는다** — 읽는 쿼리라 원인이 그 줄에 있다(`at FollowCondition.java:25`).
백틱 문자열인 것도 중요하다(큰따옴표는 이스케이프를 해석해 `\.`가 조용히 깨진다).

DEBUG만 뺀다 — INFO는 남긴다(도착·성공·복구 신호가 본질적으로 INFO). 실측으로 traceId 채널
79줄 중 chat DEBUG 45줄이 **107,932B로 전체의 92%**였고 리포트 인용은 **0회**였다.

### 창을 채널마다 다르게 쓴다

| 채널 | 창 | 왜 |
|---|---|---|
| 로그 · 후보 트레이스 검색 | **후보별 분할** | 점 사건이라 사이 구간에 정보가 없다 |
| 메트릭 | **합집합** | 시계열이 조각나면 *"그 사이에 회복했는가"* 를 잃는다 |

**나눠서 제일 많이 아낄 수 있는 채널(메트릭)이 나누면 제일 위험한 채널**이다.

## 7. 분석 컨텍스트

```
# 조사 대상 / # 수집 실패·누락
# 호출 그래프        ServiceGraphExtractor — span 관계를 엣지로 (추가지 대체 아님)
# 트레이스           TraceCompact — 재인코딩만, 값 손실 0 (−30.0%)
# 창 안 후보 트레이스
# 로그 ERROR/WARN    LogStackFold — 인용된 적 없는 것만 접기
# 로그 traceId 일치  LokiLogDedup — 두 채널 교집합의 두 번째 등장만
# 메트릭             metric-summary=true면 요약
```

**넷 다 원본을 대체하지 않는다.** `"이 span이 없다"`가 요건인 문항(AU-2류)에서 부재 근거가
죽으면 안 된다. 그래서 호출 그래프에 대해 **토큰 절감을 주장하지 않는다** — 오히려 커진다.

> **보존 원칙**: 호출 그래프·트레이스·로그·메트릭은 읽기 좋게 보조할 뿐, 원본 관측값을 지우거나 대체하지 않는다.

## 9. 경계 — 무엇을 코드가 정하나

| 정하는 것 | 주체 | 근거 |
|---|---|---|
| 시간창 해석 | **코드** | LLM에 맡기면 회차마다 다른 창이 나와 재현이 깨진다 |
| 무엇을 조회할지 | **코드** | 고정 쿼리 목록 |
| 무엇이 이상 신호인지 | **코드** | 변화·부재·존재만. **임계값 금지** — 문항별 임계값은 정답을 심는 것 |
| 후보를 어떻게 묶을지 | **코드** | 3축 + 60초 |
| **어느 후보인가** | **탐색 LLM** | **모델이 만드는 정보는 이것 하나** |
| 조사 창·서비스·traceId | **코드** | 고른 후보에서 파생. 모델이 시각을 써내도 무시 |
| 원인·근거·조치 | **분석 LLM** | 자유 서술 |

**하지 않는 것** — 정적 토폴로지를 코드에 넣지 않는다 · 탐색 집계에 스택을 넣지 않는다 ·
시간 근접만으로 채널 간 후보를 병합하지 않는다 · CLI를 레포 cwd에서 띄우지 않는다
(`CLAUDE.md` 자동 로드 = 블라인드 오염).
