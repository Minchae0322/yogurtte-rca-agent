# 조사 1회의 입력 토큰 — 회차 1 기준선

AI 장애원인분석 에이전트(`rca-agent`)가 조사 한 번에 읽어들이는 입력의 크기를 실측한 기록이다.
**개선 전 기준선(baseline)이며, 아직 전후 비교가 아니다.**

측정 기준의 정의는 [measurement.md](measurement.md), 정확도 점수는 [scoring/](scoring/README.md).

---

## 측정 기준

**측정 대상** — 조사 1회에 **에이전트가 조립해 넘긴 입력**의 토큰 수 (시스템 프롬프트 + 관측 데이터
컨텍스트). 보고된 `input_tokens` 총량이 아니다. 거기엔 Claude CLI 자신의 고정 오버헤드가 섞여 있다.

**조사 입력은 두 개다.** `traceId`가 수집 범위(Tempo·Loki·Mimir 조회와 시간창)를 정하고,
**자연어 질문**이 과업을 정한다. 재현하려면 둘 다 고정해야 한다.

**측정 방법** — 짝지은 두 실행의 차분(paired difference). 오버헤드가 무엇이든 상쇄된다.

```
A: 꼬리말만            → in_A = C + tail
B: 컨텍스트 + 꼬리말   → in_B = C + context + tail
──────────────────────────────────────────────
B − A                 = context 토큰   (C 소거)
```

**왜 차분인가** — 오버헤드 상수 `C`를 회귀로 *추정*하는 방식은 폐기했다. 6회 기록에 적합하면
95% 신뢰구간이 `[965, 23,345]`로 벌어지고, 한 점만 제거해도 추정치가 2.6배 흔들렸다.
차분은 추정이 아니라 소거다.

**통제 변수** — 모델 `claude-opus-5` 고정(`--model` 명시) · `num_turns = 1` 4회 전부 확인 ·
레포 밖 임시 디렉터리에서 실행(프로젝트 문서 컨텍스트 차단).

**입력 복원** — 과거 조사의 컨텍스트를 원본 API 응답 덤프에서 재구성했다. 재구성 길이가 그때
기록된 `contextChars`와 **4/4 바이트 단위로 일치**한다.

**측정 검증** — 재현한 `in`이 그때 기록과 격리 이후 회차에서 **±200 토큰(0.3%)** 내로 일치한다.
어긋난 1건은 원인이 규명됐다(아래 §4).

**반복 횟수** — **문항당 1회.** 토큰화는 결정적이므로(같은 입력 → 같은 토큰 수) 이 축에서는
N=1이 유효하다. 비결정성이 문제가 되는 *정확도 점수*는 별도 축이며 N≥2를 요구한다.

## 1. 조사 1회 입력 토큰

개선 지표는 `█` 하나다. `░`는 Claude CLI가 자기 시스템 프롬프트·툴 정의를 매 호출 싣는 고정

완주한 조사 **10회 전부**. 오버헤드는 **26,626으로 고정**했다 — 원본 덤프가 남아 있는 4회는
실측(`█`), 나머지 6회는 기록된 `in`에서 그 값을 뺀 추정(`▓`)이다. 추정의 한계는 바로 아래.

실측 4회의 총 `in`은 이번 재현값, 나머지는 그때 기록값이다.

> **AU4p가 왜 "채점만 폐기"인가.** 이 회차는 §8 앵커가 사실과 다른 상태에서 채록됐다 —
> 만점 요건이 "3s timeout"과 "fallback 로그"를 요구했는데, 실측은 **23.5ms connection refused**
> 였고(`.timeout(3s)`는 대기 상한이라 TCP RST에는 발동하지 않는다), fallback 로그는 존재하나
> `traceId=NONE`이라 traceId 기반 조사로 도달할 수 없다. 3개 요건 중 2개가 물리적으로 달성
> 불가라 채점이 성립하지 않았다([채점 대장](scoring/README.md) 유형 C).
>
> **에이전트 성능 문제가 아니다** — 오히려 에이전트가 "타임아웃이 아니라 TCP RST"라고 앵커를
> 정정했고, 채점 가능했던 3항목은 70/70 전부 만점이었다. 앵커를 v3로 고친 뒤 07-28에
> 재주입·재실행한 것이 유효 회차 1(AU4)이다.
>
> **채점 무효 ≠ 실행 무효.** 실제로 돌아간 조사이고 원본 덤프가 남아 있어 토큰 축에서는
> 정상 데이터 포인트다. 단 AU-4는 이 표에 두 번(AU4p·AU4) 나오므로, **점수 축에서는 AU4만
> 유효**하다는 점에 주의한다.

### 추정 6회의 한계 — 약 4,600 토큰 과소다

오버헤드를 오늘의 값(26,626)으로 고정한 편의적 처리이고, 회차 문서에 남아 있는
`contextChars`로 검산하면 **그 가정이 정확하지 않다**:

| 회차 | 기록 `in` | 기록 chars | C=26,626 가정 시 tok/char | 비율 0.524 가정 시 C |
|---|---|---|---|---|
| CH-1 회차1 | 44,798 | 43,387 | **0.419** | 22,063 |
| CH-1 회차2 | 47,503 | 49,404 | **0.423** | 21,615 |
| CH-2 회차1 | 45,935 | 45,434 | **0.425** | 22,128 |
| IN-2 구회차 | 39,202 | 32,221 | **0.390** | 22,318 |
| AU-4 회차1 | 56,325 | 65,353 | **0.454** | 22,080 |
| **측정된 4회** | | | **0.511 ~ 0.532** | **26,626 (실측)** |

26,626을 적용하면 tok/char가 **0.39~0.45**로 떨어진다. 실측 4회는 0.511~0.532 안에 4% 폭으로
모여 있으므로, 20~25% 이탈은 측정 노이즈가 아니다.

반대로 실측 비율을 고정하면 **C가 21,615~22,318로 다섯 회차 모두 3% 폭 안에 모인다.**

> **그때 오버헤드는 ~22,000이었고, 지금은 26,626이다.** 다섯 회차가 독립적으로 같은 값을
> 가리키므로 우연이 아니다. 원인은 CLI 버전 변경(툴 정의 증가) 또는 모델 변경인데,
> **그 회차들은 모델이 기록되지 않아 확정할 수 없다.**
>
> 이것이 `--model` 고정과 `llmModel`·`num_turns` 기록을 도입한 직접적 이유다 —
> 지금 겪는 것이 정확히 그 부재의 대가다.

**따라서 `▓` 막대는 컨텍스트를 약 4,600 토큰씩 과소평가한다** — 오버헤드를 실제보다
크게(26,626 대신 ~22,000이어야 할 것을) 빼기 때문이다. 예를 들어 CH-1 회차1은 표가 18,172을
가리키지만 실제는 22,700 근처였을 것이다.

**회차 1은 러프한 기준선으로 두고, 회차 2부터는 모델이 고정된 상태로 전 문항을 실측**한다.
그때 `▓`는 전부 `█`로 대체된다.

## 2. 회색 칸의 내역 — 오버헤드 26,621 토큰은 무엇인가

Claude CLI에 빈 프롬프트를 주고 기능을 하나씩 끄며 잰 차분:

| 실행 | `in` | 차이가 말하는 것 |
|---|---|---|
| 현재 (전체) | 26,621 | — |
| `--tools ""` | 3,420 | 툴 정의 = **23,201** |
| `--system-prompt "…"` | 23,334 | 시스템 프롬프트 = **3,287** |
| 둘 다 | 182 | 잔여 = **182** |

**87%가 이 에이전트가 한 번도 호출하지 않는 툴의 설명서다.** `Bash`·`Read`·`Edit`·`Grep` 같은
코딩 도구의 JSON 스키마와 사용법이 매 호출 실린다. rca-agent는 텍스트를 넣고 텍스트를 받을
뿐이고, 네 회차 모두 `num_turns = 1`로 툴을 쓰지 않았음이 확인됐다.

크기 감각: **AP-2 회차의 실제 관측 데이터가 11,900 토큰인데, 쓰지 않는 툴 설명서가 그 두 배다.**

> `--tools ""` 한 줄이면 **모든 회차에서 23,201 토큰**이 사라지고 컨텍스트는 한 글자도 바뀌지
> 않는다 — AP-2 기준 총 입력의 60%다. 다만 입력이 바뀌면 답도 바뀔 수 있으므로,
> **같은 traceId + 같은 질문으로 재조사 → 정확도 점수 불변 확인**을 거친 뒤에 채택한다.
> **아직 적용하지 않았다.**

## 4. 측정 검증 — 재현한 입력이 그때 기록과 얼마나 맞나

복원한 컨텍스트로 다시 잰 `in`에서 그때 기록된 `in`을 뺀 값. 0에 붙을수록 복원과 측정이
정확하다는 뜻이다.

| 문항 | 그때 기록 | 이번 재현 | 차이 | 격리 |
|---|---|---|---|---|
| AU-2 회차 1 | 65,414 | 62,007 | **−3,407** | **적용 전** |
| AU-4 파일럿 | 61,528 | 61,713 | +185 | 적용 후 |
| AP-3 회차 1 | 45,885 | 45,751 | −134 | 적용 후 |
| AP-2 회차 1 | 38,662 | 38,526 | −136 | 적용 후 |

격리 이후 3회는 ±200 토큰 안이다. **어긋난 1건은 딱 그 회차만 격리 적용 전**이고, 차이
3,407 토큰은 그때 컨텍스트에 딸려 들어간 프로젝트 문서의 크기다.

독립 경로로도 같은 값이 나온다 — 빈 프롬프트 프로브(29,987) − 차분 실측(26,626) = **3,361**.
두 방법이 서로를 확인한다. 오염의 존재는 이전에 지적됐지만, 크기가 숫자로 확정된 것은 여기서다.

## 5. 측정값 전체

문자 수는 측정에 쓴 프롬프트 기준이라 리포트의 `contextChars`보다 시스템 프롬프트·꼬리말만큼 크다.

| 문항 | traceId | 질문 | 문자 | **컨텍스트 토큰** | tok/char | + 오버헤드 = 총 in | turns |

## 이 측정이 말하지 않는 것

- **개선 전후 비교가 아니다.** 네 조사는 서로 다른 장애 문항이라 서로 비교 대상이 아니다.
  이 표는 압축 개선을 적용하기 *전*의 기준선이고, 델타는 같은 문항을 다시 재야 나온다.
- **10회 중 4회만 토큰이 실측이다.** 나머지 6회(`▓`)는 원본 API 응답 덤프가 없어 복원이
  불가능해, 오버헤드를 26,626으로 **가정**하고 기록된 `in`에서 뺀 값이다. 검산상 그때
  오버헤드는 ~22,000이었으므로 **약 4,600 토큰씩 과소평가**다. 회차 1은 러프한 기준선이고,
  **회차 2부터 모델 고정 상태로 전 문항을 실측**해 대체한다.
- **시스템 프롬프트는 현재 버전을 썼다.** 조사 당시 버전이 보존돼 있지 않다. 전체의 1%
  미만(597자)이며, 재현 오차 ±200 토큰의 대부분이 이것으로 설명된다.
- **비용은 실제 청구액이 아니다.** 이 프로젝트는 구독 계정으로 CLI를 호출하므로 달러 청구가
  없다. 리포트의 `total_cost_usd`는 API 환산 추정치이며, 그렇게 표기해야 한다.
- **정확도는 여기 없다.** 원인 적중 점수는 별도 루브릭으로 채점되며 문항당 N≥2를 요구한다.
