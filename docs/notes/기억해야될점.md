# 기억해야 될 점

면접·포트폴리오에서 헷갈리면 안 되는 설계 이유를 모아두는 노트.
회차 기록(round-N)이 아니라 "왜 그렇게 만들었나"의 개인 정리다.

---

## 1. 왜 장애 후보를 여러 개 만들어 LLM에게 고르게 하나 — 창 절단 사고가 출발점

### 사고의 전말 (CH-3)

- TimeParser가 만든 초기 창(04:50~05:50) 안에 실제 장애(05:22:01~05:22:38, 23초)가
  **들어 있었다.** 데이터가 없던 게 아니다.
- LLM이 조사 창을 04:57~05:22로 직접 좁혔고, **장애 발생 1초 전에 창이 끝났다.**
  원인 미도달.
- 첫 판단은 "창을 넓히자"였는데 실험으로 반증됐다 — 2.26배 확대에서 컨텍스트 +72%,
  비용 +39%, **성능 개선 없음.** 범위 확대는 답이 아니었다.
- 진짜 원인은 신호 부족 + 단일 후보 구조였다: 장애가 에러가 아니라 23초 **지연**이라
  에러 트레이스 검색에 안 걸렸고, 5분 순간값 메트릭의 샘플 **사이**로 빠졌고, 로그도
  무신호였다. 후보를 만들 재료가 없으니 모델이 다른 구간을 골랐고, 한 번 고르면
  복구 구조가 없었다.

### 그래서 바뀐 구조

```
Surveyor          창 전체를 집계값으로 스윕 (판단 없음)
SignalExtractor   존재·변화·0 구간·결측만 기계적으로 추출 (임계값 없음)
IncidentClusterer 신호를 후보 여러 개로 묶는다 (하나로 접지 않는다)
탐색 LLM          후보 중에서 고르기만 한다
TriagePlan        창은 고른 후보의 관측 시각 + padding으로 코드가 계산
```

컨텍스트 지시문에 계약이 박혀 있다: **"시각을 직접 쓰지 말 것 — 조사 창은 고른 후보의
신호 시각에서 자동으로 계산된다."** 모델이 숫자를 지어낼 자리를 구조적으로 없앤 것이다.

### 기억할 원칙

1. **LLM은 받은 후보 목록 안에서만 고른다.** 목록에 없는 장애는 모델에게 존재하지 않는다.
   그래서 코드의 역할은 "정확히 고르기"가 아니라 **"정답을 절대 후보에서 빠뜨리지 않기"**다.
   지연 채널(`duration > 3s`) · `min_over_time` · 결측 감지 · 임계값 없음 — 전부
   "정답이 명단에 못 오르는 경로"를 하나씩 막은 것.
2. **실패는 비대칭이다 — 복구되는 방향으로만 틀리게 한다.**
   - 너무 잘게 나눔(과분할): 복구된다. 모델이 여러 후보를 묶어 고를 수 있다
     (`chosenIncidentIds` 복수 — 07-29 Kafka 조사에서 실제로 그랬다).
   - 너무 크게 합침(과병합): 복구 불가. "둘이었다"는 정보가 전달 자체가 안 된다
     (CH-1·CH-2가 같은 traceId를 답한 사고).
   - 그래서 규칙이 "애매하면 나눈다"이고, 병합은 traceId 공유라는 결정적 근거가
     있을 때만, 시간 겹침은 병합이 아니라 related 표시만.
3. **묶는 축의 순서: 라벨(채널·리소스·지문) 먼저, 시간은 같은 키 안에서만.**
   시간으로 먼저 묶으면 20분짜리 신호 하나가 그 시간대의 다른 장애를 전부 흡수한다
   (CH-3의 lag 신호). 토폴로지 지식으로 병합하면 채점 대상인 정답 구조를 코드에
   심는 것이라 금지(블라인드).
4. **"다 때려넣기 + 후보"를 병행한다.** 스윕 원본 JSON도 전부 컨텍스트에 들어간다 —
   후보는 정보 축약이 아니라 **인터페이스**다. 후보 단위가 필요한 이유 넷:
   - 창 계산 계약 (모델이 고르면 코드가 계산 — 시각 지어내기 차단)
   - 기각 기록 (`dismissedIncidentIds` — "다른 걸 골랐어야 했나"의 사후 검증)
   - 출력 파싱 견고성 ("INC-3" 선택은 기계 파싱 가능)
   - 실패 분해 측정 (신호 문제 / 묶기 문제 / 선택 문제를 단계별로 검증 —
     코드는 픽스처 테스트로 박제, 모델 그룹핑은 실행마다 달라 회귀 검증 불가)

### 면접 화법

> "LLM이 알아서 골라주는 게 아니라, LLM이 고르기만 하면 되는 상태를 코드가 만들어
> 줍니다. 코드는 판단을 안 하는 대신 정답을 절대 안 빠뜨리는 쪽으로, 틀려도 되돌릴 수
> 있는 쪽으로만 틀리게 설계했습니다."

예상 꼬리질문:

| 질문 | 답 |
|---|---|
| 그럼 클러스터링 로직은 왜 필요한가 | 안 나누면 과병합이라는 복구 불가 실패가 남는다. 창이 넓어지고 "장애가 둘"이라는 정보가 소멸한다 |
| LLM이 후보를 잘못 고르면 | dismissed 기록으로 검증 가능하고, 버린 후보가 남아 있어 되돌아갈 수 있다 |
| 창을 왜 모델이 안 정하나 | CH-3에서 모델이 정한 창이 장애 1초 전에 끝났다. 창 확대 실험(+72% 컨텍스트)도 효과가 없어, 판단 위치를 옮겼다 |
| 임계값 없이 노이즈는 어떻게 하나 | 걸러내기는 LLM이 잘하는 일이라 맡긴다. 크기로 거르면 1건짜리 정답 신호가 탈락한다 (CH-3: 결정적 신호 1건 vs 옆 버킷 54건) |

## 2. IncidentClusterer가 꼭 필요한가 — 대안 비교로 답한다

"어차피 원본도 다 넣고 모델이 고르는데, 묶는 코드가 왜 필요한가"라는 도전에 대한 답.
결론부터: **클러스터러는 판단하는 코드가 아니라 불변식을 지키는 코드**다 —
"후보 하나 = 사건 하나 = 완전한 시간 구간"을 결정적으로 보장하는 것이 전부다.

### 대안 세 개와 각각이 무너지는 지점

| 대안 | 무너지는 지점 |
|---|---|
| ① 후보 없이 원본만 주고 모델이 창을 출력 | 이미 반증됨 — 사고 A(창 1초 전 절단)가 이 구조에서 났다 |
| ② 묶지 않고 신호 낱개를 후보로 | 아래 세 가지 |
| ③ 묶기까지 모델에게 맡김 | 실행마다 다르게 묶임(비결정) · 픽스처 테스트 불가 · 탐색 실패 시 "묶기 문제 vs 선택 문제" 분해 불가 — 측정 프로젝트에 치명적 |

대안 ②(낱개 후보)가 진짜 경쟁자인데, 세 함정이 있다:

1. **부분 선택이 창을 자른다 — 사고 A의 축소판.** 한 장애가 신호 4개(up 0 구간 ·
   결측 · 60초 트레이스 · 에러 버킷)로 오는데 모델이 2개만 고르면 창은 그 2개
   구간에서만 계산된다. 60초 트레이스만 골랐다면 복구 구간이 잘린다.
   클러스터러의 reach 기반 구간 합집합이 보장하는 것: **후보 하나를 고르면 그 사건의
   전체 구간이 통째로 따라온다.** 창 완전성을 모델의 꼼꼼함에 맡기지 않는다.
2. **선택지 폭발.** 시끄러운 창은 신호가 수십~수백 개다. "200개 중 정합한 부분집합"은
   "6개 중 하나"보다 훨씬 잘 틀리는 과제다.
3. **기각 기록이 무의미해진다.** "INC-2(mongo)를 버렸다"는 검증 가능하지만
   "신호 47개 중 31개를 안 골랐다"는 아무것도 말해주지 않는다.

클러스터러 자체는 판단·임계값·도메인 지식 없이 기계적 사실(라벨 동일성 · 시간 인접 ·
traceId 공유)만 쓰는 약 150줄 — 뺄 수 있는 최소한에 이미 가깝다.

### 정직한 한계 — 필요성의 증명은 아직 절반

- 지금까지의 논거는 전부 설계 논증 + 반사실 하나(클러스터러 없던 시절 CH-1·CH-2가
  같은 traceId를 답한 사고)다. **순방향 실증은 미측정.**
- B-20 등재 시 박제된 성공 기준: **같은 두 질문을 재조사했을 때 서로 다른 traceId를
  고르는 것.** 이 델타 측정이 대기 중이다.
- 이 구조의 강점: 클러스터러를 끄고 낱개 신호를 후보로 흘리는 A/B가 쉬워서
  "꼭 필요하냐"를 실험으로 답할 수 있다. 재조사에서 점수가 안 갈리면 빼는 게 맞다.

### 면접 화법

> "클러스터러는 판단하는 코드가 아니라 불변식을 지키는 코드입니다 — 모델이 무엇을
> 고르든 '고른 것의 시간 구간은 완전하다'를 보장하는 게 전부고, 그 보장이 없던 시절의
> 사고 두 건이 존재 이유입니다. 효과는 재조사 델타로 검증할 계획이고, 안 갈리면
> 빼는 게 맞습니다."

마지막 문장(반증 가능성)까지 붙이는 게 오히려 강하다 — 필요성을 신앙이 아니라
반증 가능한 주장으로 두는 것.
