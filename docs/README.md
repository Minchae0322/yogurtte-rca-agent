## 0. 한 줄 정의

관측 데이터(트레이스·로그·메트릭)만으로 장애 원인을 지목하는 AI 에이전트를 만들고,
**실제로 장애를 주입해 정확도를 채점하는** 프로젝트다.
에이전트를 만드는 것보다 **성능을 측정 가능하게 만드는 것**이 이 프로젝트의 목적이다.

| | 2026-07-28 기준 |
|---|---|
| 정의된 장애 시나리오 | **12개** (실행 8 · 미실행 4, 별도 보류 1) |
| 조사 완주 | **9회** |
| 유효 채점 | **5회** — 평균 **82** / 100 |
| 채점 불가 · 유보 | 3회 + 1회 (+ 폐기 1회) — **전부 채점 기준의 결함** |
| **인용 가능한 점수** | **0개** — 규정상 문항당 N≥2인데 전부 N=1 ([왜](#33-이-점수를-아직-인용하지-않는다)) |
| 누적 비용 | 약 **$9.2** (구독 계정 사용 · **API 환산 추정치**, 실제 청구액 아님) |
| findings | NF 12건 · DF 1건 · AE 6건 |

## 1. 무엇을 만들었나

traceId 하나를 주면 Tempo·Loki·Mimir를 모아 LLM이 원인 후보를 랭킹하고,
근거·확신도·반증·다음 조치를 담은 리포트를 만든다.

```
api → service → collector(client) + analyzer → llm → notify → report
```

- **v0 = 도구 없는 단일 패스.** 코드가 결정적으로 수집·조립하고 LLM을 **1회만** 호출한다.
  에이전틱 루프를 안 쓴 이유는 [ADR-002](decisions/adr-002-single-pass-baseline.md) — 대조군이 먼저다.
- 인터페이스는 `LlmClient`·`Notifier` 둘뿐이고 `@ConditionalOnProperty`로 구현체 하나만 뜬다.
- 시스템 프롬프트는 코드가 아니라 `prompts/system-prompt.md` 파일이고 **조사할 때마다 다시 읽는다** —
  재시작 없이 튜닝하고 리포트의 `promptSource`로 버전별 비교한다.
- 한 소스가 죽어도 조사는 완주하고, 실패 사실을 컨텍스트에 명시해 확신도를 낮추게 한다.

**실행·설정** → 루트 [README.md](../README.md) · 관측 파이프라인 실측 인벤토리(23 타깃)와
알려진 공백 → [monitoring.md](monitoring.md)

### 1.1 이 시스템의 경계 — 설명 엔진이지 탐색 엔진이 아니다

현재 버전은 **traceId를 입력으로 받는다.** "이 요청이 왜 이렇게 됐는가"에는 답하지만
"어젯밤 오류를 찾아줘"에는 답하지 못한다. 조회 시간창이 입력 트레이스에서 파생되는 구조라
traceId 없이는 쿼리 자체를 만들 수 없다.

이는 구현 누락이 아니라 **측정을 먼저 세우기 위한 의도된 범위 설정**이다. 다만 실무에서 장애가
나면 traceId를 아는 사람이 없고, **그것을 뒤져서 찾는 행위가 원인 분석의 절반**이다.
따라서 **현재 점수는 성능의 반쪽만 재고 있다.**

→ 탐색 단계 설계와 진입 게이트는 [strategy.md Phase 4.5](strategy.md#phase-45--장애-탐색triage-어젯밤-오류-찾아줘에-답한다)

## 2. 어떻게 측정하나

정확도와 비용, 두 축을 따로 잰다. **자가 흔들리면 그 자로 잰 개선 주장이 전부 무너지므로
지표 정의를 코드보다 먼저 고정했다.**

### 2.1 정확도 축 — 장애 주입 블라인드 채점

| 항목 | v1 배점 | v3 배점 (회차 2부터 병행) |
|---|---|---|
| 원인 적중 | 40 | 40 |
| 근거 시그널 경로 | 30 | 25 |
| **탐색 타당성** | — | **15 (신설)** |
| **영향 판정** | 근본 40에 혼입 | **10 (분리)** |
| 오귀인 없음 | 20 | 5 |
| 조치 타당성 | 10 | 5 |

운영 규칙 다섯 가지:

1. **블라인드.** 에이전트에겐 traceId와 자연어 질문만 준다. 정답지·채점 기준을 에이전트가 읽는
   경로에 두지 않는다. 자기 채점은 무효다.
2. **기준 선박제.** 채점 앵커는 장애 주입 **전에** 확정한다. 결과를 보고 기준을 고치면 그 회차는
   무효이고 개정은 다음 회차부터 적용한다.
3. **앵커 기준 채점.** 정답지와의 자유 대조는 금지 — 앵커에 없는 잣대를 끌어오면 채점자 재량이 된다.
4. **반복 측정.** 문항당 최소 2회, 평균 ± 최대편차. 편차 ±10 초과면 인용 보류.
5. **도구 제약을 면제하지 않는다.** 조사 도구가 신호를 못 모아 만점이 불가능해도 그대로 감점한다.
   면제하면 도구를 고쳤을 때 개선폭이 측정되지 않는다.

→ 주입 하네스 [toy-content `docs/chaos/`](../../toy-content/docs/chaos/README.md) (문항·정답지·실행기) · 루브릭 [rubric-v3.md](scoring/rubric-v3.md) ·
문항별 요건 [anchors.md](scoring/anchors.md)(회차 1) · [anchors-v2.md](../../toy-content/docs/chaos/anchors-v2.md)(회차 2~) ·
회차별 판정 근거 [scoring/README.md](scoring/README.md)

### 2.2 비용 축 — `contextTokens`

개선 지표는 리포트의 `in`이 아니라 **`coverage.contextTokens`**(시스템 프롬프트 + 조립 컨텍스트의
실측 토큰)다. `in`에는 Claude CLI 자신의 고정 오버헤드 **26,626 토큰**이 섞여 있고, 그중 **87%가
이 에이전트가 한 번도 호출하지 않는 툴 정의 스키마**다.

폐기한 방법 둘: `in − C` 뺄셈(회귀 추정 C의 95% CI가 `[965, 23,345]`), `chars/4` 추정(실측 대비 2.1배 과소).
채택한 방법은 **짝지은 두 실행의 차분** — 추정이 아니라 소거다.

→ 기준 정의 [measurement.md](measurement.md) · 회차 1 실측 [round-1-input-tokens.md](round-1-input-tokens.md)

### 3.2 배운 것 — 에이전트보다 자(尺)가 먼저 문제였다

**채점 불가 4건은 전부 에이전트가 아니라 채점 기준의 결함이었다.**

| 유형 | 회차 | 무슨 일이 |
|---|---|---|
| A. 전개 갈래 미상정 | CH-1 1회차 · AU-2 | 조건에 따라 신호가 안 나오는데 한 갈래만 기술 |
| B. 입력 범위 무시 | CH-2 | 요구한 신호가 조사 도구의 수집 채널에 없음 |
| C. 코드 독해를 실측으로 착각 | AU-4 파일럿 | 설정 상수 보고 "3초 타임아웃" → 실제 23.5ms 연결 거절 |
| D. 기준 부재 | AP-2 | 기준이 **아예 없는 상태로** 주입 실행 |

부적합률을 추적 지표로 삼아 **67% → 33%**로 낮췄고, 대응을 유형별로 갈랐다 —
A·B·C는 [기준 작성 체크리스트](scoring/report.md#54-기준-작성-체크리스트) 7항목으로,
D는 하네스 **실행 전 자동 게이트**로 막는다.

**공교롭게도 채점 불가 회차들이 질적으로는 가장 인상적인 조사였다.** CH-2는 근본 원인 만점,
AU-2는 트레이스 완전 무신호에서 메트릭 단절만으로 정답 도달, AU-4 파일럿은 채점된 3항목이
70/70이었다. **측정하지 못한 것이 곧 못한 것은 아니다.**

### 3.3 이 점수를 아직 인용하지 않는다

- **반복 부족** — 유효 5회가 전부 1회차다. 같은 버전이 같은 장애에서 **75점과 약 95점**을 냈고,
  차이는 버전이 아니라 출력 분량이었다(2,980 vs 10,511 tok).
- **한 항목이 변별력을 잃었다** — 오귀인 20점이 9회 전부 만점이라 실질 만점이 80이다.
  원인은 항목 설계가 아니라 **정상 상황을 한 번도 준 적 없는 문항 세트**에 있다.
- **측정 범위가 절반이다** — §1.1의 탐색 단계가 아직 측정되지 않았다.

## 5. 알아둘 함정 (실측 확정)

**관측 데이터 라벨 체계가 시그널마다 다르다.** 틀리면 조용히 빈 결과가 나온다.

| 시그널 | 라벨 | 값 |
|---|---|---|
| Loki (로그) | `service_name` | `content-service` / `auth-service` / `chat-service` |
| Prometheus (메트릭) | `application` | 위와 동일 |

`application` 라벨은 **Loki에 존재하지 않는다**(Micrometer common tag는 메트릭 전용).
조사 6회가 로그 0건이던 원인은 **독립된 두 결함**이었다 — ① 셀렉터가 존재하지 않는 `app` 라벨을
쓰고 있었고, ② `| logfmt | level=~`가 평문 Logback에서 `level` 필드를 못 만들었다.
둘 다 고쳤고 회차 2부터 적용한다.

**빌드·실행 함정** — JDK 21 필수(전역 `JAVA_HOME`이 낮으면 빌드 자체가 안 된다) ·
`bootRun`은 `.env`를 자동으로 읽지 않는다(`scripts/run-local.ps1`이 메운다).
자세한 것은 [CLAUDE.md](../CLAUDE.md).

## 6. 블라인드를 지키는 규칙

**에이전트는 피험자다.**

- 리포트 생성 경로(`RcaService` → `ReportStore`)에 앵커·정답지를 넣지 않는다.
- 리포트 안에서 점수를 생성하게 만들지 않는다 — 자기 채점은 무효다.
- 프롬프트를 수정할 때 특정 문항의 정답을 암시하는 문장이 들어가지 않는지 확인한다.
- **서브프로세스 cwd를 격리한다** — `claude-cli` provider가 JVM의 cwd를 물려주면 Claude Code가
  레포의 `CLAUDE.md`와 `.claude/skills/`를 자동 로드한다. 실측으로 **3,407 토큰**의 오염이
  확인됐고 차단했다(`31e2a85`).
- 개선 수단은 **`prompts/system-prompt.md` 하나로만** 들어가야 측정이 성립한다.

> ⚠️ **정답지는 이 레포에 두지 않는다 (2026-07-28 확정).** chaos 하네스를 잠시 이 레포로
> 옮겼다가 되돌렸다 — 옮기면 **정답지(`scenarios/*/answer.md`)가 피험자의 cwd 안으로
> 들어오기 때문**이다. 지금은 toy-content `docs/chaos/`에 있다. 다만 위치 분리는 부분적
> 방어일 뿐이고(CLI는 상위 경로도 읽는다) **cwd 격리가 여전히 본 방어선**이다.
