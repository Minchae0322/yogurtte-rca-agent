# 측정 기준 (Measurement Standard)

이 문서는 **"어떤 숫자를 개선의 근거로 쓰는가"**를 고정한다. 자가 흔들리면 그 자로 잰 모든 개선
주장이 무너지므로, 지표 정의·통제 변수·비교 규칙을 코드보다 먼저 여기에 박아둔다.

관련: [strategy.md](strategy.md) (왜 측정이 먼저인가) · [scoring/](scoring/README.md) (정확도 축) ·
[v0.1-plan.md](v0.1-plan.md) (개선 항목)

> **정확도 축은 여기 없다.** §8 루브릭 채점은 [채점 대장](scoring/README.md)이 관장한다.
> 이 문서는 **토큰·비용·시간** 축만 다룬다.

## 1. 기록되는 필드

### 1-a. LLM 호출 (`RcaReport` 최상위)

| 필드 | 정의 | 주의 |
|---|---|---|
| `llmModel` | 응답을 만든 모델 | **회차 비교의 전제.** 다르면 비교 불가 |
| `llmTurns` | LLM 왕복 횟수 | **1이 아니면** "도구 없는 단일 패스" 전제가 깨진 것 |
| `inputTokens` | `input_tokens + cache_read + cache_creation` | **CLI 오버헤드 포함** — 개선 지표 아님 |
| `cacheReadTokens` | 그중 캐시에서 읽은 몫 (정가의 0.1배) | 미보고 provider는 −1 |
| `cacheCreationTokens` | 그중 캐시에 쓴 몫 (5분 TTL 기준 1.25배) | 미보고 provider는 −1 |
| `outputTokens` | 답변 길이 | **줄이지 않는다** — 4절 참조 |
| `costUsd` | CLI가 보고한 실제 청구액 | 캐시 상태·모델에 따라 크게 요동 |

### 1-b. 입력 구성 (`coverage`)

| 필드 | 정의 |
|---|---|
| **`contextTokens`** | **개선 지표.** 시스템 프롬프트 + 컨텍스트의 실측 토큰. 못 재면 −1 |
| `promptChars` | 시스템 프롬프트 길이 (`contextChars`에 **미포함**이므로 따로 셈) |
| `contextChars` | 조립된 컨텍스트 길이 |
| `traceBytes` / `traceSpans` | 트레이스 JSON 크기와 span 수 |
| `errorWarnLogBytes` / `traceIdLogBytes` | 로그 두 쿼리의 응답 크기 |
| `metricsBytes` | 메트릭 응답 크기 |

`traceBytes + 로그 2종 + metricsBytes ≈ contextChars`가 되어야 한다. 남는 몫은 어셈블러 헤더다.
**`metricsBytes`가 없던 시절에는 컨텍스트의 약 11%가 미분류로 떠 있었다** — 어디를 줄여야 할지
가리키지 못하는 계측이었다.

## 2. 개선 지표는 왜 `contextTokens`인가

### 문제: `in`은 내가 만든 것이 아니다

`RCA_LLM_PROVIDER=claude-cli`면 에이전트는 `claude -p`를 서브프로세스로 띄운다. CLI는 호출마다
자기 시스템 프롬프트·툴 정의 스키마를 컨텍스트에 싣는다. **컨텍스트를 하나도 주지 않은 프로브가
약 30,000 토큰을 보고했다.** 그러므로 `in`은 "내가 밀어넣은 관측 데이터의 크기"가 아니다.

`in`을 지표로 쓰면 두 방향으로 손해다 — 실제 개선폭보다 작아 보이고, "그 3만은 뭔가요"에 답을
못 한다. 나아가 [strategy.md](strategy.md) Phase 3의 채택 기준(**토큰 ≥20% 절감**)이 실질적으로
1.25~1.95배 엄격해져, **성공한 개선이 기준 미달로 기각될 수 있다.**

### 폐기한 대안 ①: `in − C` (뺄셈)

오버헤드 상수 `C`를 빼는 방식을 검토했고 **폐기했다.** 기록된 6회로 `in = C + k × contextChars`를
적합하면 R² = 0.960으로 그럴듯해 보이지만:

| 검정 | 결과 |
|---|---|
| SE(C) | 4,031 |
| 95% 신뢰구간 | [965, **23,345**] |
| 99% 신뢰구간 | [−6,404, **30,713**] ← 음수와 프로브값을 동시에 포함 |
| 한 점 제거 시 C | 5,993 ~ 15,725 (**2.6배 진폭**) |
| 옛 4점만 적합 | R² = **0.998**, C = 23,474 (더 좋은 적합, 전혀 다른 계수) |

R² = 0.960은 근거가 아니라 **설계의 산물**이다. x값이 32~49k와 65k 두 덩어리로 갈려 있어
두 구름 사이에 선 하나 긋는 건 언제나 된다.

기울기가 결정타다. k = 0.767 tok/char를 성립시키려면 컨텍스트의 한글 부분이 **2.0~2.36 tok/char**
여야 하는데 그런 텍스트는 없다. C ≈ 30,000을 가정하면 1.15~1.30 tok/char — 한글에 맞는 값이다.
**아래에서 위로 쌓은 구성 검증이 회귀를 기각한다.**

> **원칙: 피감수의 오차가 결과보다 크면 뺄셈은 성립하지 않는다.** 빼지 말고 직접 재라.

### 폐기한 대안 ②: `chars/4` 추정

`RcaService`가 `context.length() / 4`로 `estimatedContextTokens`를 만들던 필드는 **제거했다.**
영어권 휴리스틱을 한글 + OTLP JSON 혼합에 적용한 값이라 실측 대비 **약 3.8배 과소**였다
(리포트 한 장 안에서 16,341 vs 61,528). 필드의 목적이 "provider usage와 대조"였는데 대조가
4배로 실패했고, 테스트가 그 계수를 고정하고 있어 오류가 회귀 방지 대상으로 굳어 있었다.

**추정치를 지어내느니 −1(측정 안 됨)이 낫다.**

### 채택: 직접 측정

`TokenCounter`가 조립 직후 `/v1/messages/count_tokens`에 **조사에 쓴 모델로** 질의한다.

- CLI 오버헤드가 애초에 섞이지 않는다 → 뺄셈 불필요
- 캐시 상태·턴 수를 타지 않는다 → 회차 간 비교가 성립
- 결정적이다(같은 입력 = 같은 값) → 분산 0
- 토크나이저가 모델과 일치한다

**한계 2가지 (명시):**
1. `ANTHROPIC_API_KEY`가 없으면 −1이다. claude CLI 경로는 구독 계정으로 도는 구성이라 키가
   선택 사항이다. 키가 없으면 **이 지표는 존재하지 않는다** — 0으로 채우지 않는다.
2. count_tokens는 system + user 2블록으로 세지만 CLI는 둘을 한 덩어리로 stdin에 넣는다.
   메시지 프레이밍 차이만큼(수 토큰) 어긋난다. 회차 간 비교에는 영향이 없다.

### 키가 없을 때: 차분 측정 (현재 이 레포의 실제 경로)

이 레포는 `ANTHROPIC_API_KEY`가 비어 있다(구독 계정 + claude CLI). 그래서 `TokenCounter`는
−1을 반환하고, **토큰은 차분으로 잰다** — `scripts/measure-contexts.ps1`.

```
A: 꼬리말만          -> in_A = C + tail
B: 컨텍스트 + 꼬리말 -> in_B = C + context + tail
B - A                = context 토큰
```

**전역 상수 C를 추정하는 것과 다르다.** 짝지은 두 실행은 같은 모델·같은 CLI 버전·같은 분에
돌므로 오버헤드가 무엇이든 그대로 상쇄된다. 추정이 아니라 소거다. 실측 결과는 7-b/7-c.

> **비용 주의.** 구독 계정이면 달러 청구가 없고 사용량(rate limit)만 소모한다.
> 리포트의 `total_cost_usd`는 **실제 청구액이 아니라 API 환산 추정치**다 —
> 누적 "$8.2" 같은 수치를 포트폴리오에 쓸 때 반드시 그렇게 밝힌다.

## 3. 통제 변수

### 3-a. 모델 — 반드시 고정

`ClaudeCliLlmClient`는 `--model`을 **항상** 넘긴다 (`rca.llm.claude-cli.model`, 기본
`claude-opus-5`). 생략하면 CLI가 그날의 기본 모델로 돈다.

**이게 왜 치명적인가.** 모델이 바뀌면 ① 답의 품질이 바뀌어 §8 점수 비교가 무너지고
② 토크나이저가 바뀌어 토큰 비교가 무너진다. "같은 v0인데 점수가 갈렸다"는 관찰이 모델 차이일
가능성을 배제할 수 없게 된다.

응답이 보고한 모델은 `llmModel`에 그대로 기록한다. 요청값과 대조할 수 있어야 한다.

### 3-b. 턴 수 — 기록하고 감시

`llmTurns > 1`이면 CLI가 자체 도구 루프를 돌았다는 뜻이고, 그러면 `usage`가 마지막 턴만 담고
`total_cost_usd`는 전 턴 합계일 수 있다. 즉 **`in`이 "조사 1회의 입력"이 아니게 된다.**
`RcaService`가 이 경우 WARN을 남긴다. 해당 회차의 토큰·비용은 그대로 비교하지 않는다.

### 3-c. 캐시 — 지우지 말고 기록

프롬프트 캐시는 **비울 수 없다**(플러시 API 없음). 통제는 기록으로 한다.

| 재는 것 | 캐시 영향 | 대응 |
|---|---|---|
| §8 점수 | 없음 (모델이 보는 프롬프트가 동일) | 통제 불필요 |
| `contextTokens` | 없음 (조사와 별개 호출) | 통제 불필요 |
| `inputTokens` 합계 | 없음 (버킷만 갈릴 뿐 합은 동일) | — |
| **비용·소요시간** | **직접 흔듦** | 3분해를 기록해 사후 정규화 |

비용을 회차 간 비교해야 하면 **가중 유효입력**으로 정규화한다:

```
유효입력 = input_tokens×1.0 + cache_creation×1.25 + cache_read×0.1
```

> 회차 1 실측 결과를 포트폴리오용으로 정리한 것: [round-1-input-tokens.md](round-1-input-tokens.md)

> **캐시를 일부러 식히지 말 것.** 실사용은 콜드가 아니다. "조사 1회 $0.28"을 주장하려면 그
> 수치가 실제 운영 조건이어야 한다. 콜드를 강제하면 비용을 과대평가한다.

`cacheReadTokens`는 **접두사 동일성 tripwire**로도 쓴다 — 같은 입력을 연달아 돌렸는데 0이면
프롬프트가 실제로는 달라졌다는 신호다.

## 5. before/after 비교가 성립하는 조건

아래 넷을 **전부** 만족해야 델타를 개선 근거로 인용한다.

- [ ] **같은 모델** — `llmModel`이 일치
- [ ] **같은 입력** — 같은 traceId + 같은 질문 문구
- [ ] **같은 자** — 앵커 버전 동일 (정확도 축), 지표 정의 동일 (토큰 축)
- [ ] **N ≥ 2** — 조건당 최소 2회, 평균 ± 최대편차로 기록 (§8.1과 동일 규율)

변경군은 섞지 않는다. **앱 계측(A)과 조사 도구(B)를 한 회차에 같이 넣으면 점수가 올라도 원인을
가릴 수 없다.** B는 주입 없이 기존 traceId 재조사로 검증되므로 먼저 한다.

### 과거 회차(2026-07-26 ~ 28)의 지위

**점수 기록은 그대로 유효하다.** [채점 대장](scoring/README.md)의 판정은 손대지 않는다.

다만 **토큰 차트의 before로는 쓸 수 없다.** 그 7회는 `llmModel`을 기록하지 않았고 모델도
고정되지 않았으므로, 어떤 모델이 만든 수치인지 사후에 확인할 방법이 없다. 토큰 축의 baseline은
**모델을 고정한 뒤 재측정한 값**으로 새로 만든다.

## 6. 실행 순서

```
① 계측 확정   ← 완료: 모델 고정 · 턴/캐시 3분해 기록 · contextTokens 직접 측정
② 프로브      ← scripts/cli-probe.ps1 (C 실측 + 캐시 경계 판별)
③ baseline    ← 보유 traceId × 2회, 고정 모델로 재측정
④ 개선        ← 트레이스 압축 렌더링 등
⑤ 재조사      ← 같은 traceId × 2회 -> 델타
```

**②·③을 건너뛰면 ⑤의 델타가 성립하지 않는다.** ①이 토큰 회계를 바꿨으므로 baseline은 반드시
① 이후에 재야 한다.

### 채택 규칙

`contextTokens` **−20% 이상** AND §8 점수 **하락 없음** → 채택.
점수가 떨어지면 압축이 정보를 잃은 것이므로 **즉시 롤백**한다.

## 7. 실측 기록

### 7-a. 컨텍스트 구성 (AU-4 파일럿, 65,366 chars)

| 구성 | bytes | 비중 |
|---|---|---|
| **트레이스 JSON** (66 spans, span당 760B) | **50,180** | **76.8%** |
| 로그 (errwarn 3,961 + traceId 3,962) | 7,923 | 12.1% |
| 메트릭 + 어셈블러 헤더 | 7,263 | 11.1% |

→ **개선 1순위는 트레이스다.** 나머지를 전부 0으로 만들어도 23%밖에 못 줄인다.
압축 렌더러(`TraceSpans.topByDuration`)는 이미 있으나 `maxTraceBytes` 초과 시에만 쓰인다.

> ⚠️ 이 표는 **폐기된 파일럿 회차(07-27)** 기준이다. 유효 AU-4 회차 1은 07-28(65,353 chars)이고
> 그 리포트 JSON은 `reports/`에 없다(Markdown만 존재). ③ baseline 재측정 때 다시 잰다.

**주의: span 개수로 자르지 말 것.** CH-2·AU-2에서 결정적이었던 신호가 "짧은 span"과 "**없는
span**"이었다. 줄일 것은 **표현 형식**이지 span 개수가 아니다.

### 7-b. 과거 회차 토큰 실측 (2026-07-28)

API 키가 없어 `count_tokens`를 못 쓰므로 **차분 측정**으로 냈다. 원본 덤프(`reports/raw/`)에서
컨텍스트를 복원하고(`ContextRebuildTool`, **4/4 바이트 일치**), 짝지은 두 실행의 `in` 차이를
취한다 — 오버헤드가 무엇이든 정확히 상쇄된다.

```
A: 꼬리말만          -> in_A = C + tail
B: 컨텍스트 + 꼬리말 -> in_B = C + context + tail
B - A                = context 토큰
```

| 문항 | traceId | chars | **tokens** | tok/char |
|---|---|---|---|---|
| AU-2 회차 1 | `6a66b2c4…` | 66,562 | **35,381** | 0.532 |
| AU-4 파일럿(폐기) | `6a67077c…` | 65,970 | **35,087** | 0.532 |
| AP-3 회차 1 | `6a6804f0…` | 36,691 | **19,125** | 0.521 |
| AP-2 회차 1 | `6a680b56…` | 23,269 | **11,900** | 0.511 |

*chars는 시스템 프롬프트(597자)와 측정용 꼬리말을 포함한 값이라 리포트의 `contextChars`보다 크다.*

**tok/char = 0.524 [0.511 ~ 0.532].** 코드가 쓰던 `chars/4`(0.250)는 **약 2.1배 과소**였다.
비율이 컨텍스트 크기와 무관하게 안정적인 것은 내용 구성(OTLP JSON + 한글)이 비슷하기 때문이고,
구성이 바뀌면 다시 재야 한다.

남는 ±200은 시스템 프롬프트 버전 차이(현재 파일을 썼다)로 설명된다.

레포 `CLAUDE.md`다. 프로브(29,987) − 차분(26,626) = 3,361과 **독립적으로 일치한다.**
[v0.1-plan.md](v0.1-plan.md) 0절이 오염을 지적했을 때 추정만 했던 크기가 여기서 숫자로 확정됐다.

**부수 확인: `num_turns = 1`.** 네 측정 전부 단일 왕복이었다. "도구 없는 단일 패스"라는 v0의
대조군 전제가 이 구성에서 실제로 성립한다는 첫 실측이다.

> `C`는 **개선 지표에 쓰이지 않는다**(`contextTokens`가 대체). 리포트의 `in` 중 내 것이 아닌
> 몫을 설명하는 보조 수치이고, 차트에는 스택 막대의 회색 칸으로만 등장한다.
> 편차가 0이므로 스택 막대를 써도 되지만, **프로브를 다시 돌려 편차를 재확인한 뒤** 쓴다.

## 8. 포트폴리오 차트 사양

| 차트 | Y축 | 계열 | 비고 |
|---|---|---|---|
| **정확도** | §8 점수 (0~100) | 문항별 v0 / v0.1 | 오차막대 = 최대편차. N≥2 아니면 **미게재** |
| **토큰** | `contextTokens` | 조사별 before / after | 단일 막대. C를 곁들이면 스택 2칸 |
| **비용·시간** | $ / 초 | 조사별 | 캐시 warm/cold 라벨 병기 |
| **앵커 부적합률** | % | 앵커 버전별 | 측정 도구 자체의 개선 곡선 |

**차트에 반드시 병기할 것:**
- 모델명 (`llmModel`) — 모든 막대가 같은 모델임을 보이는 캡션
- N과 편차 — N=1은 게재하지 않는다
- `contextTokens`가 CLI 오버헤드를 **제외한** 값이라는 한 줄

**하지 말 것:** 오차막대 없는 스택 막대. 회색 칸("CLI 오버헤드")을 실측처럼 그리면 읽는 사람은
그걸 측정값으로 받아들인다. C의 불확실성이 남아 있는 동안에는 단일 막대가 정직하다.
