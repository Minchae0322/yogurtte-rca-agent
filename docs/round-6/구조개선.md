# 탐색 범위를 넓혔더니 컨텍스트가 폭발했다
### 탐색 범위 확대에 따른 장애 증거 누락 및 컨텍스트 증가 개선

### 탐색 범위를 넓혔더니 장애 증거는 찾았지만, 컨텍스트가 폭발했다

**문제는 장애 증거가 실제로 존재하는데도 탐색 조건과 검색 상한 때문에 누락되고 있었다는 것이었습니다.** Redis 장애의 실제 timeout은 2초였지만 탐색 기준이 `duration > 3s`여서 약 2.09초의 관련 트레이스 19건을 모두 놓쳤습니다.

**임계값을 2초로 낮추자 이번에는 검색 상한이 병목이 됐습니다.** 기존 상한 20건은 그동안 수집한 전체 정상·장애 구간에서 대부분 20건 이내였기 때문에 사용했지만, 조건 변경 후 **전체 조사 데이터를 다시 실측한 결과 최대 61건**까지 발생했습니다. 이에 특정 장애에 맞춰 임의로 조정하지 않고 **실측 최대치의 약 3배인 200건으로 재설정**해 장애 증거가 잘리지 않도록 했습니다.

하지만 검색 범위를 넓히자 후보 컨텍스트가 **1,318자 → 7,378자(+460%)**로 급증했습니다. 원인을 추적해보니 동일 장애의 반복 신호를 건별로 출력하고 있었고, 이를 단순 제거하면 **발생 횟수와 주기라는 RCA 근거까지 사라지는 문제**가 있었습니다. 따라서 반복 신호를 **`xN회 + 시간 범위 + 평균 간격 + 대표 traceId`** 형태로 접어 의미는 유지하고 표현량만 줄였습니다.

그 결과 **장애 신호는 8 → 66건, 목표 장애 증거는 0 → 19건으로 복구**하면서 후보 컨텍스트는 **1,687자(+28%)**로 억제했고, 확대된 데이터의 **94%를 압축**했습니다.

**결국 단순히 검색 범위를 넓힌 것이 아니라, 전체 조사 데이터를 실측해 탐색 범위를 재설계하고, 증거를 버리지 않으면서 정보 밀도를 높이는 구조로 개선했습니다.** 또한 이 과정에서 로그·트레이스·후보 목록에 공통적으로 존재하던 **“절삭 후 압축” 문제를 발견해 “의미 보존 → 압축 → 필요한 경우 절삭”이라는 공통 원칙으로 확장**했습니다.

## 문제 상황

RCA Agent가 장애 원인을 찾기 위해 Tempo에서 **에러 트레이스와 장시간 트레이스**를 탐색하고 있었지만, 실제 장애의 일부가 탐색 단계에서부터 누락되고 있었습니다.

Redis 장애를 재현한 조사에서 `chat-service`의 관련 트레이스가 하나도 수집되지 않았습니다.

그런데 Tempo를 직접 확인하자 장애 시간대에 다음과 같은 트레이스가 **19건 존재**했습니다.

```text
chat-service
duration ≈ 2.09s
Redis 장애 구간에서 19회 반복
```

원인은 탐색 조건이었습니다.

```text
기존 탐색 조건
duration > 3s
```

실제 Redis command timeout은 **2초**였고, 장애 트레이스는 timeout + 네트워크/처리 오버헤드로 약 2.09초에 형성되고 있었습니다.

즉,

```text
Redis timeout 2s
      ↓
실제 장애 지연 ≈ 2.09s
      ↓
탐색 조건 > 3s
      ↓
장애 트레이스 0건
```

**검색 조건 자체가 장애의 지연 패턴을 놓치고 있었습니다.**

---

## 1. 단순히 임계값만 낮추면 해결되지 않았다

시스템의 timeout 설정을 조사한 결과 Redis command timeout이 가장 짧은 **2초**였습니다.

따라서 탐색 임계값을 3초에서 2초로 낮췄습니다.

그 결과 장애 트레이스는 제대로 발견되기 시작했습니다.

하지만 새로운 문제가 발생했습니다.

| 조건                 | 검색 결과 | chat 장애 트레이스 |
| ------------------ | ----: | -----------: |
| 기존 `>3s`, limit 20 |    8건 |       **0건** |
| `>2s`, limit 20    |   26건 |       **6건** |
| `>2s`, limit 200   |   66건 |      **19건** |

임계값을 낮추자 전체 후보가 **8건 → 66건**으로 증가했고 기존 검색 상한 20건을 초과했습니다.

결국 임계값만 낮추는 것은

> **장애를 찾는 문제를 해결한 대신, 검색 상한 때문에 찾은 증거를 다시 잃어버리는 문제를 만들었습니다.**

특히 목표였던 `chat-service` 장애 증거도 **19건 중 6건만 전달**되고 있었습니다.

따라서 문제는 단순히 임계값이 아니라,

**“어디까지 검색하고, 검색 결과를 어떻게 압축해서 전달할 것인가”**

까지 함께 설계해야 했습니다.

---

## 2. 검색 범위를 넓히자 컨텍스트가 폭발했다

실측 결과 최대 61건의 트레이스가 발생했기 때문에 검색 상한을 **20 → 200**으로 확대했습니다.

이렇게 하면 실제 장애 증거 19건을 모두 확보할 수 있었습니다.

하지만 후보를 LLM에 전달하는 과정에서 또 다른 문제가 발견됐습니다.

기존 `Incident.describe()`는 같은 장애 후보의 반복 신호를 그대로 출력하고 있었습니다.

```text
- content-service task ... 2,003ms
- content-service task ... 2,000ms
- content-service task ... 2,002ms
- content-service task ... 2,010ms
- content-service task ... 2,000ms
- content-service task ... 2,000ms
- traceId: ...
```

실제로는 하나의 장애 패턴인데도 **발생 횟수만큼 같은 형태의 텍스트를 반복**하고 있었습니다.

그 결과:

```text
기존
20건 / 3s
→ 후보 목록 1,318자

변경
200건 / 2s
→ 후보 목록 7,378자

+459.8%
```

즉,

> **탐색 정확도를 높이기 위해 검색 범위를 넓혔더니, 이번에는 분석 컨텍스트가 4.6배 증가했습니다.**

---

## 3. 버리는 대신 반복을 접었다

여기서 단순히 중복을 제거하면 안 된다고 판단했습니다.

RCA에서 반복 횟수 자체가 중요한 증거이기 때문입니다.

예를 들어 다음 두 결과는 의미가 다릅니다.

```text
1회 발생
```

과

```text
6회 발생
평균 24초 간격
04:33:00 ~ 04:35:02
```

후자는 **일회성 오류가 아니라 반복되는 장애 패턴**이라는 정보를 제공합니다.

따라서 반복 신호를 삭제하지 않고 **통계적 의미를 보존한 상태로 접었습니다.**

### Before

```text
- task ... 2,003ms
- task ... 2,000ms
- task ... 2,002ms
- task ... 2,010ms
- task ... 2,000ms
- task ... 2,000ms
```

### After

```text
- task ... 2,000~2,010ms
  [x6회 · 평균 24초 간격]
```

traceId 역시 전부 나열하지 않고 대표값과 추가 개수만 유지했습니다.

```text
traceId: abc123…, def456… (+4건)
```

핵심은 **데이터를 삭제한 것이 아니라, 판단에 필요한 정보의 밀도를 높인 것**입니다.

## 4. 결과 — 탐색 범위는 8.3배, 컨텍스트는 1.28배

동일한 장애 구간에서 변경 전후를 비교했습니다.

|            |     기존 |         최종 |
| ---------- | -----: | ---------: |
| 지연 임계값     |     3s |     **2s** |
| 검색 상한      |     20 |    **200** |
| 수집 트레이스    |      8 |     **66** |
| 후보         |      2 |      **4** |
| 목표 chat 신호 |  **0** |     **19** |
| 후보 목록      | 1,318자 | **1,687자** |
| 후보 목록 증가   |      - | **+28.0%** |

가장 중요한 변화는 이것입니다.

```text
탐색 신호
8 → 66개
(+725%)

컨텍스트
1,318 → 1,687자
(+28%)
```

검색 범위를 크게 넓혀 **실제 장애 증거를 복구하면서도**, 반복 접기를 통해 컨텍스트 증가를 대부분 흡수했습니다.

특히 상한 확대가 추가한 **6,060자 중 5,691자(94%)를 반복 접기로 흡수**했습니다.

---

## 5. 하지만 예상은 틀렸다

처음에는 다음과 같이 예상했습니다.

> **“반복 접기로 추가된 후보의 컨텍스트 증가까지 흡수할 수 있을 것이다.”**

그러나 실제 결과는 **+28%**였습니다.

따라서 이 가설은 반증됐습니다.

원인은 명확했습니다.

```text
반복 신호 감소
        ↓
기존 후보의 컨텍스트 절감

하지만

새로운 장애 후보 증가
        ↓
후보별 제목 / 시간 / 요약 / 대표 traceId
        ↓
고정 비용 발생
```

즉, **신호 하나당 비용은 크게 줄였지만 후보가 새로 생길 때 발생하는 고정 비용은 고려하지 않았습니다.**

이 결과를 억지로 성공으로 해석하지 않고, 해당 가설은 폐기하고 다음 판단 대상으로 분리했습니다.

이 과정에서 중요한 것은 **개선 결과만 남긴 것이 아니라 실패한 가설과 반증 조건까지 기록했다는 점**입니다.

## 6. 추가로 발견한 구조적 문제

이번 문제를 해결하면서 한 단계 더 올라가 보니 동일한 문제가 파이프라인 여러 곳에서 반복되고 있었습니다.

| 영역    | 기존 처리       |
| ----- | ----------- |
| 로그    | **자른 후 접음** |
| 트레이스  | **자르기만 함**  |
| 후보 목록 | **자르기만 함**  |

공통점은 모두

> **“무엇을 버릴지 판단하기 전에 먼저 잘라버린다.”**

는 것이었습니다.

이 방식은 단순한 데이터 축소에는 유효하지만 RCA에서는 문제가 됩니다.

반복되는 데이터 자체가 **장애의 패턴·빈도·주기·서비스 간 관계를 판단하는 증거**이기 때문입니다.

따라서 공통 원칙을 다음과 같이 정리했습니다.

```text
기존

원본
 ↓
상한으로 절삭
 ↓
남은 데이터 접기


개선

원본
 ↓
반복/공통 정보 접기
 ↓
정보 밀도 증가
 ↓
필요한 경우 상한 적용
```

**버리기 전에 의미를 보존하면서 압축한다**는 원칙입니다.

## 7. 최종 변경

이번 회차에서 적용한 변경은 세 가지입니다.

### ① 장애 탐색 임계값 조정

```text
3s → 2s
```

시스템의 최소 timeout인 Redis 2초보다 큰 임계값으로 인해 장애 신호가 누락되는 문제를 제거했습니다.

### ② Tempo 검색 상한 확대

```text
20 → 200
```

실측 최대 61건을 기준으로 약 3배의 여유를 두었습니다.

또한 Tempo 원본은 LLM 컨텍스트에 직접 포함하지 않기 때문에 **검색 상한 확대 자체가 모델 입력 토큰을 증가시키지는 않음**을 확인했습니다.

### ③ 후보 신호 반복 접기

```text
N개의 반복 신호
↓
발생 횟수
+ 시간 범위
+ 평균 간격
+ 대표 traceId
```

반복 데이터를 삭제하지 않고 **RCA에 필요한 의미를 보존하면서 표현량만 줄였습니다.**

## 8. 문제 해결에서 얻은 것

이번 개선의 핵심은 `3초 → 2초`가 아닙니다.

처음에는 단순히 **“장애 신호를 더 많이 찾자”**는 문제였지만, 실제로는 다음 세 문제가 연결되어 있었습니다.

```text
탐색 임계값이 너무 높음
        ↓
장애 신호 누락
        ↓
임계값 하향
        ↓
검색 결과 증가
        ↓
검색 상한 초과
        ↓
상한 확대
        ↓
분석 컨텍스트 폭증
        ↓
반복 데이터의 정보 밀도 개선 필요
```

따라서 한 단계씩 문제를 해결하면서 **검색 정확도와 컨텍스트 비용을 함께 최적화하는 구조**로 변경했습니다.

최종적으로:

* 장애 신호: **8 → 66건**
* 목표 chat 장애 신호: **0 → 19건**
* 후보 목록: **1,318 → 1,687자**
* 신호 증가: **8.3배**
* 컨텍스트 증가: **1.28배**
* 상한 확대에 따른 추가 데이터의 **94%를 접기로 흡수**

라는 결과를 얻었습니다.

다만 **“최종적으로 컨텍스트가 줄어들었다”는 가설은 실제 측정에서 반증됐기 때문에 채택하지 않았습니다.**

현재 확정된 것은 **장애 신호 누락을 해결한 것과 반복 접기가 정보 밀도를 크게 개선했다는 사실**이며, 신규 후보 증가에 따른 고정 비용까지 포함한 최종 컨텍스트 최적화는 별도의 검증 과제로 남겼습니다.
