# 탐색 범위를 넓혔더니 컨텍스트가 폭발했다
### 탐색 범위 확대에 따른 장애 증거 누락 및 컨텍스트 증가 개선

### 탐색 범위를 넓혔더니 장애 증거는 찾았지만, 컨텍스트가 폭발했다

**문제는 장애 증거가 실제로 존재하는데도 탐색 조건과 검색 상한 때문에 누락되고 있었다는 것이었습니다.** Redis 장애의 실제 timeout은 2초였지만 탐색 기준이 `duration > 3s`여서 약 2.09초의 관련 트레이스 19건을 모두 놓쳤습니다.

**임계값을 2초로 낮추자 이번에는 검색 상한이 병목이 됐습니다.** 기존 상한 20건은 그동안 수집한 전체 정상·장애 구간에서 대부분 20건 이내였기 때문에 사용했지만, 조건 변경 후 **전체 조사 데이터를 다시 실측한 결과 최대 61건**까지 발생했습니다. 이에 특정 장애에 맞춰 임의로 조정하지 않고 **실측 최대치의 약 3배인 200건으로 재설정**해 장애 증거가 잘리지 않도록 했습니다.

하지만 검색 범위를 넓히자 후보 컨텍스트가 **1,318자 → 7,378자(+460%)**로 급증했습니다. 원인을 추적해보니 동일 장애의 반복 신호를 건별로 출력하고 있었고, 이를 단순 제거하면 **발생 횟수와 주기라는 RCA 근거까지 사라지는 문제**가 있었습니다. 따라서 반복 신호를 **`xN회 + 시간 범위 + 평균 간격 + 대표 traceId`** 형태로 접어 의미는 유지하고 표현량만 줄였습니다.

그 결과 **장애 신호는 8 → 66건, 목표 장애 증거는 0 → 19건으로 복구**하면서 후보 컨텍스트는 **1,687자(+28%)**로 억제했고, 확대된 데이터의 **94%를 압축**했습니다.

**결국 단순히 검색 범위를 넓힌 것이 아니라, 전체 조사 데이터를 실측해 탐색 범위를 재설계하고, 증거를 버리지 않으면서 정보 밀도를 높이는 구조로 개선했습니다.** 또한 이 과정에서 로그·트레이스·후보 목록에 공통적으로 존재하던 **“절삭 후 압축” 문제를 발견해 “의미 보존 → 압축 → 필요한 경우 절삭”이라는 공통 원칙으로 확장**했습니다.

## 문제 상황

RCA Agent가 장애 원인을 찾기 위해 Tempo에서 **에러 트레이스와 장시간 트레이스**를 탐색하고 있었지만, 실제 장애의 일부가 탐색 단계에서부터 누락되고 있었습니다.

Redis 장애를 재현한 조사에서 `chat-service`의 관련 트레이스가 하나도 수집되지 않았습니다.

그런데 Tempo를 직접 확인하자 장애 시간대에 다음과 같은 트레이스가 **19건 존재**했습니다.

```text
chat-service
duration ≈ 2.09s
Redis 장애 구간에서 19회 반복
```

원인은 탐색 조건이었습니다.

```text
기존 탐색 조건
duration > 3s
```

실제 Redis command timeout은 **2초**였고, 장애 트레이스는 timeout + 네트워크/처리 오버헤드로 약 2.09초에 형성되고 있었습니다.

즉,

```text
Redis timeout 2s
      ↓
실제 장애 지연 ≈ 2.09s
      ↓
탐색 조건 > 3s
      ↓
장애 트레이스 0건
```

**검색 조건 자체가 장애의 지연 패턴을 놓치고 있었습니다.**

---

## 1. 단순히 임계값만 낮추면 해결되지 않았다

시스템의 timeout 설정을 조사한 결과 Redis command timeout이 가장 짧은 **2초**였습니다.

따라서 탐색 임계값을 3초에서 2초로 낮췄습니다.

그 결과 장애 트레이스는 제대로 발견되기 시작했습니다.

하지만 새로운 문제가 발생했습니다.

| 조건                 | 검색 결과 | chat 장애 트레이스 |
| ------------------ | ----: | -----------: |
| 기존 `>3s`, limit 20 |    8건 |       **0건** |
| `>2s`, limit 20    |   26건 |       **6건** |
| `>2s`, limit 200   |   66건 |      **19건** |

임계값을 낮추자 전체 후보가 **8건 → 66건**으로 증가했고 기존 검색 상한 20건을 초과했습니다.

결국 임계값만 낮추는 것은

> **장애를 찾는 문제를 해결한 대신, 검색 상한 때문에 찾은 증거를 다시 잃어버리는 문제를 만들었습니다.**

특히 목표였던 `chat-service` 장애 증거도 **19건 중 6건만 전달**되고 있었습니다.

따라서 문제는 단순히 임계값이 아니라,

**“어디까지 검색하고, 검색 결과를 어떻게 압축해서 전달할 것인가”**

까지 함께 설계해야 했습니다.

---

## 2. 검색 범위를 넓히자 컨텍스트가 폭발했다

실측 결과 최대 61건의 트레이스가 발생했기 때문에 검색 상한을 **20 → 200**으로 확대했습니다.

이렇게 하면 실제 장애 증거 19건을 모두 확보할 수 있었습니다.

하지만 후보를 LLM에 전달하는 과정에서 또 다른 문제가 발견됐습니다.

기존 `Incident.describe()`는 같은 장애 후보의 반복 신호를 그대로 출력하고 있었습니다.

```text
- content-service task ... 2,003ms
- content-service task ... 2,000ms
- content-service task ... 2,002ms
- content-service task ... 2,010ms
- content-service task ... 2,000ms
- content-service task ... 2,000ms
- traceId: ...
```

실제로는 하나의 장애 패턴인데도 **발생 횟수만큼 같은 형태의 텍스트를 반복**하고 있었습니다.

그 결과:

```text
기존
20건 / 3s
→ 후보 목록 1,318자

변경
200건 / 2s
→ 후보 목록 7,378자

+459.8%
```

즉,

> **탐색 정확도를 높이기 위해 검색 범위를 넓혔더니, 이번에는 분석 컨텍스트가 4.6배 증가했습니다.**

---

## 3. 버리는 대신 반복을 접었다

여기서 단순히 중복을 제거하면 안 된다고 판단했습니다.

RCA에서 반복 횟수 자체가 중요한 증거이기 때문입니다.

예를 들어 다음 두 결과는 의미가 다릅니다.

```text
1회 발생
```

과

```text
6회 발생
평균 24초 간격
04:33:00 ~ 04:35:02
```

후자는 **일회성 오류가 아니라 반복되는 장애 패턴**이라는 정보를 제공합니다.

따라서 반복 신호를 삭제하지 않고 **통계적 의미를 보존한 상태로 접었습니다.**

### Before

```text
- task ... 2,003ms
- task ... 2,000ms
- task ... 2,002ms
- task ... 2,010ms
- task ... 2,000ms
- task ... 2,000ms
```

### After

```text
- task ... 2,000~2,010ms
  [x6회 · 평균 24초 간격]
```

traceId 역시 전부 나열하지 않고 대표값과 추가 개수만 유지했습니다.

```text
traceId: abc123…, def456… (+4건)
```

핵심은 **데이터를 삭제한 것이 아니라, 판단에 필요한 정보의 밀도를 높인 것**입니다.

---

## 4. 결과 — 탐색 범위는 8.3배, 컨텍스트는 1.28배

동일한 장애 구간에서 변경 전후를 비교했습니다.

|            |     기존 |         최종 |
| ---------- | -----: | ---------: |
| 지연 임계값     |     3s |     **2s** |
| 검색 상한      |     20 |    **200** |
| 수집 트레이스    |      8 |     **66** |
| 후보         |      2 |      **4** |
| 목표 chat 신호 |  **0** |     **19** |
| 후보 목록      | 1,318자 | **1,687자** |
| 후보 목록 증가   |      - | **+28.0%** |

가장 중요한 변화는 이것입니다.

```text
탐색 신호
8 → 66개
(+725%)

컨텍스트
1,318 → 1,687자
(+28%)
```

검색 범위를 크게 넓혀 **실제 장애 증거를 복구하면서도**, 반복 접기를 통해 컨텍스트 증가를 대부분 흡수했습니다.

특히 상한 확대가 추가한 **6,060자 중 5,691자(94%)를 반복 접기로 흡수**했습니다.

---

## 5. 하지만 예상은 틀렸다

처음에는 다음과 같이 예상했습니다.

> **“반복 접기로 추가된 후보의 컨텍스트 증가까지 흡수할 수 있을 것이다.”**

그러나 실제 결과는 **+28%**였습니다.

따라서 이 가설은 반증됐습니다.

원인은 명확했습니다.

```text
반복 신호 감소
        ↓
기존 후보의 컨텍스트 절감

하지만

새로운 장애 후보 증가
        ↓
후보별 제목 / 시간 / 요약 / 대표 traceId
        ↓
고정 비용 발생
```

즉, **신호 하나당 비용은 크게 줄였지만 후보가 새로 생길 때 발생하는 고정 비용은 고려하지 않았습니다.**

이 결과를 억지로 성공으로 해석하지 않고, 해당 가설은 폐기하고 다음 판단 대상으로 분리했습니다.

이 과정에서 중요한 것은 **개선 결과만 남긴 것이 아니라 실패한 가설과 반증 조건까지 기록했다는 점**입니다.

## 6. 추가로 발견한 구조적 문제

이번 문제를 해결하면서 한 단계 더 올라가 보니 동일한 문제가 파이프라인 여러 곳에서 반복되고 있었습니다.

| 영역    | 기존 처리       |
| ----- | ----------- |
| 로그    | **자른 후 접음** |
| 트레이스  | **자르기만 함**  |
| 후보 목록 | **자르기만 함**  |

공통점은 모두

> **“무엇을 버릴지 판단하기 전에 먼저 잘라버린다.”**

는 것이었습니다.

이 방식은 단순한 데이터 축소에는 유효하지만 RCA에서는 문제가 됩니다.

반복되는 데이터 자체가 **장애의 패턴·빈도·주기·서비스 간 관계를 판단하는 증거**이기 때문입니다.

따라서 공통 원칙을 다음과 같이 정리했습니다.

```text
기존

원본
 ↓
상한으로 절삭
 ↓
남은 데이터 접기


개선

원본
 ↓
반복/공통 정보 접기
 ↓
정보 밀도 증가
 ↓
필요한 경우 상한 적용
```

**버리기 전에 의미를 보존하면서 압축한다**는 원칙입니다.

---

## 7. 최종 변경

이번 회차에서 적용한 변경은 세 가지입니다.

### ① 장애 탐색 임계값 조정

```text
3s → 2s
```

시스템의 최소 timeout인 Redis 2초보다 큰 임계값으로 인해 장애 신호가 누락되는 문제를 제거했습니다.

### ② Tempo 검색 상한 확대

```text
20 → 200
```

실측 최대 61건을 기준으로 약 3배의 여유를 두었습니다.

또한 Tempo 원본은 LLM 컨텍스트에 직접 포함하지 않기 때문에 **검색 상한 확대 자체가 모델 입력 토큰을 증가시키지는 않음**을 확인했습니다.

### ③ 후보 신호 반복 접기

```text
N개의 반복 신호
↓
발생 횟수
+ 시간 범위
+ 평균 간격
+ 대표 traceId
```

반복 데이터를 삭제하지 않고 **RCA에 필요한 의미를 보존하면서 표현량만 줄였습니다.**

## 8. 문제 해결에서 얻은 것

이번 개선의 핵심은 `3초 → 2초`가 아닙니다.

처음에는 단순히 **“장애 신호를 더 많이 찾자”**는 문제였지만, 실제로는 다음 세 문제가 연결되어 있었습니다.

```text
탐색 임계값이 너무 높음
        ↓
장애 신호 누락
        ↓
임계값 하향
        ↓
검색 결과 증가
        ↓
검색 상한 초과
        ↓
상한 확대
        ↓
분석 컨텍스트 폭증
        ↓
반복 데이터의 정보 밀도 개선 필요
```

따라서 한 단계씩 문제를 해결하면서 **검색 정확도와 컨텍스트 비용을 함께 최적화하는 구조**로 변경했습니다.

최종적으로:

* 장애 신호: **8 → 66건**
* 목표 chat 장애 신호: **0 → 19건**
* 후보 목록: **1,318 → 1,687자**
* 신호 증가: **8.3배**
* 컨텍스트 증가: **1.28배**
* 상한 확대에 따른 추가 데이터의 **94%를 접기로 흡수**

라는 결과를 얻었습니다.

다만 **“최종적으로 컨텍스트가 줄어들었다”는 가설은 실제 측정에서 반증됐기 때문에 채택하지 않았습니다.**

현재 확정된 것은 **장애 신호 누락을 해결한 것과 반복 접기가 정보 밀도를 크게 개선했다는 사실**이며, 신규 후보 증가에 따른 고정 비용까지 포함한 최종 컨텍스트 최적화는 별도의 검증 과제로 남겼습니다.

# 조사 창이 실제 장애의 56배였다 — 그런데 줄일 것이 없었다

## 문제 상황

CH-3(Mongo 23초 다운)을 자연어로 조사시키고 좁혀진 창을 봤습니다.

| 항목 | 값 |
|---|---|
| 스윕 창 | 2026-08-06T00:36:05Z ~ 01:36:05Z (60분) |
| 실제 주입 | `docker stop mongodb` **약 23초** (00:53:34~00:53:57Z) |
| 좁힌 창 | 00:37:41 ~ 01:00:00 — **22분 19초** |
| 배율 | **56배** |

코드가 만든 후보 9건 중 **INC-8이 00:53:34.957~00:53:59.030**으로 주입과 초 단위로 일치합니다.
정답은 이미 후보 하나로 정확히 분리돼 있었습니다. 그런데 창은 22분이었습니다.

## 원인 ① — 창은 pad가 아니라 고른 후보의 시각 범위가 정한다

```
00:37:41 ┤ pad 2m
00:39:41 ████████████████████ INC-2  content 댓글 API — 트레이스 하나가 8분 35초
00:47:00               ██     INC-3  chat 로그
00:47:44               ▌      INC-4  chat filterchain
00:49:00  ─────────────  빈 구간 4분  ─────────────
00:53:00                      █████ INC-6  chat 로그
00:53:34                      ▌     INC-8  ★ 정답 — Mongo 23초
00:53:42                      ▌     INC-9  chat filterchain
00:58:00                            ┤ pad 2m
01:00:00                            ┤
```

```
22분 19초 = 신호 18분 19초 + pad 4분
```

**pad를 0으로 해도 18분입니다.** 실제로 pad를 5m에서 `step × 2`(2m)로 줄여 A/B를 돌렸고,
줄어든 것은 뒤쪽 3분뿐이었습니다(앞쪽은 Tempo `EXACT`라 원래 2m).

| 좁힌 창 | 25분 19초 | **22분 19초** | −3분 |

`reports/scan-1785976661-20260811T062757` · `-20260811T090625`

**창 축소는 토큰 지표가 아닙니다.** 분석에 실린 트레이스 10건 중 9건은 탐색이 `traceId`로
못 박은 것이라 창과 무관하고, 그 101KB가 컨텍스트의 81%입니다.

## 원인 ② — 탐색 LLM은 INC-8만 고를 수 없다

앞 클러스터(00:39~00:49)는 **CH-2**(`chat-service scale 0` 6분)라는 **별개의 주입**입니다.
창 안에 주입이 둘이었습니다.

```
INC-2   댓글 API  515,150ms = 8분 35초    ← 압도적으로 큰 지연
INC-8   댓글 API   24,073ms =   24초      ← 실제 정답
```

질문은 *"앱이 **잠깐** 버벅였다"* 입니다. 같은 엔드포인트에서 8분 35초짜리와 24초짜리가
나왔을 때 **8분짜리를 버리는 것은 정답을 미리 아는 사람만 할 수 있는 판단**입니다.
회차 5는 둘 다 골라 23초를 1순위, 8분을 2순위로 세우고 **100점**을 받았습니다.

`prompts/triage-prompt.md`도 그렇게 지시합니다.

```
11행: 확신이 없으면 여러 개를 고른다. 하나만 고르고 틀리면 그 조사는 끝나지만,
      여러 개를 고르면 조사 범위가 그만큼만 넓어진다.
35행: 한 장애가 여러 후보로 쪼개져 보이면 함께 고른다. 창은 합집합이 된다.
```

**"하나만 고르라"는 방향은 위험합니다** — INC-2를 버리게 만드는 지시이고, CH-2가 정답인
회차에서는 그대로 오답이 됩니다.

## 해결 — 이미 되어 있었다

*"union이 빈 구간까지 덮으니 `List<TimeWindow>`로 바꾸자"* 가 첫 판단이었는데, 코드를 열어
보니 **그 구조가 이미 있었습니다.**

```java
// TriageService — 후보별 창을 따로 실어 보낸다
List<TimeWindow> candidateWindows = chosenIncidents.stream()
        .map(i -> i.window(padding.exact(), padding.bucket(), window)).toList();
Scope scope = plan.toScope().withCandidates(candidates).withWindows(candidateWindows);

// Collector — 로그·트레이스는 창 목록으로 나눠 조회한다 (메트릭은 합집합)
List<TimeWindow> logWindows = scope.logWindows(window);
```

`plan.window()`(합집합)는 표시와 메트릭 조회에만 쓰이고, **로그와 트레이스는 이미 후보별로
나눠서 조회하고 있습니다.** 메트릭만 합집합인 것은 의도적입니다 — 시계열이 조각나면
*"그 사이에 회복했는가"* 를 잃습니다.

## 결과 — 이 창에서는 분할이 걸리지 않고, 그것이 맞다

원본 응답 파일에 `-w1`·`-w2` 접미가 없습니다. 분할이 발동하지 않았습니다. 이유는 계산에 있습니다.

```
INC-3 로그 끝  00:49:00 + pad 2m = 00:51:00
INC-6 로그 시작 00:53:00 − pad 2m = 00:51:00
                                    ↑ 정확히 맞닿는다 → 하나로 접힌다
```

**빈 4분은 양쪽 pad 2m + 2m이 정확히 메웁니다.** 그리고 그 pad는 버킷 해상도에서 나온
*"이 신호가 언제인지 모르는 폭"* 이므로, 그 구간을 안 긁겠다는 것은 우리가 필요하다고
정한 여유를 스스로 부정하는 것입니다.

```
분할이 값을 하는 조건:  후보 사이 간격 > 2 × pad
이번 경우:              간격 4분 = 2 × 2분   → 값이 없다
```

회귀 검증으로 남겼습니다 — `ScopeWindowsTest.옛_pad로는_두_사건이_맞닿아_하나로_접혔다`,
CH-3의 실제 후보 6건 좌표를 그대로 넣었습니다.

## 그래서 pad를 채널에서 유도하도록 바꿨다

### 원인 — pad는 "딱 끊었을 때 원복됐는지 알 수 없다"는 문제에 대한 답이었다

pad를 넣은 이유는 처음부터 하나였습니다. **신호가 끝난 지점에서 창을 딱 끊으면, 그 뒤에
복구가 됐는지 아닌지를 알 수 없습니다.** 이상 구간만 잘라서 보여주면 *"장애가 계속되고
있다"* 와 *"끝나고 회복했다"* 가 구별되지 않고, 시작 쪽도 마찬가지로 *"언제부터 이상해졌나"* 의
직전 정상 상태가 없으면 전이 시점을 짚을 수 없습니다.

그래서 정밀도(`EXACT` / `BUCKET`) 두 단계로 나눠 각각 2분·5분을 붙였습니다.

### 문제 — 실측해 보니 세 채널 중 둘은 그 여유가 필요 없었다

창이 22분으로 잡힌 것을 뜯어보다가 `SignalExtractor`가 채널마다 **다른 구간**을 만들고
있다는 것을 확인했습니다.

```java
// 로그  SignalExtractor:96   "구간은 [ts - lookback, ts] 다. ts 하나로 두면 최대 lookback만큼 어긋난다"
point.at().minus(lookback), point.at()      → 1분 폭이 이미 구간 안에 있다

// 메트릭 SignalExtractor:194
finding.from().at(), finding.to().at()      → 샘플 시각 그대로. 폭이 없다
```

| 채널 | 신호 구간 | 남은 불확실성 | pad가 필요한가 |
|---|---|---|---|
| Tempo | span 시각 (ms 정확) | 없다 | **아니오** |
| Loki | `[ts − lookback, ts]` | **없다 — 폭이 이미 구간에 있다** | **아니오** |
| Mimir | 샘플 시각 (점) | 앞뒤로 최대 1 step | **예** |

**Loki와 Mimir를 `BUCKET` 하나로 묶은 것이 잘못이었습니다.** 이름은 같은 "흐린 신호"인데
코드가 이미 로그에만 폭을 넣어 두었고, 거기에 pad를 또 얹으니 **한 번 덮은 불확실성을 두 번
덮고** 있었습니다.

메트릭은 반대로 폭이 없습니다. 첫 이상 샘플이 00:39:05면 전이는 00:38:05~00:39:05 어디서든
일어났을 수 있고, 마지막 이상 샘플 뒤의 회복 시점도 최대 1 step 뒤입니다. **원복 여부를
읽으려면 여기에는 여유가 반드시 있어야 합니다.**

### 해결 — 정밀도가 아니라 채널로 가른다

```java
// Incident.window()
Duration pad = switch (channel()) {
    case MIMIR -> bucketPad;        // step × 2 (지금 2분) — 전이·원복이 샘플 사이에 숨는다
    case LOKI  -> Duration.ZERO;    // [ts - lookback, ts]로 폭이 이미 구간에 있다
    case TEMPO -> exactPad;         // 기본 0 — span 시각에 불확실성이 없다
};
```

`incident-pad-exact` 기본값을 `2m` → `0s`로 내렸습니다. `incident-pad-bucket`은 그대로
`step × 2`(2분)이고, 이제 **메트릭에만** 적용됩니다.

### 결과 — 창이 좁아지고, 분할이 비로소 걸린다

같은 CH-3 후보 6건(전부 Tempo·Loki)을 새 규칙으로 계산하면:

| | 옛 규칙 (전 채널 2분) | 채널별 pad |
|---|---|---|
| 좁힌 창(합집합) | 22분 19초 | **18분 19초** |
| 조회 구간 | 22분 19초 (한 창) | **14분 19초** (두 창) |
| 두 사건 사이 | 맞닿아 접힘 | **4분 간격 유지 → 분할** |

```
채널별 pad 적용 후
  [00:39:41 ─ 00:49:00]   INC-2·3·4   9분 19초
  [00:53:00 ─ 00:58:00]   INC-6·8·9   5분      ← 정답 INC-8이 여기
```

`ScopeWindowsTest.채널별_pad로는_두_사건이_둘로_갈린다`로 박제했습니다.

**토큰은 여전히 안 줄어듭니다.** 빈 4분에 ERROR/WARN이 **0줄**임을 실측했고(아래), 분석에
실리는 트레이스는 탐색이 `traceId`로 못 박은 것이라 창과 무관합니다.

```
00:47 x1   00:48 x2   [00:49~00:52  ERROR/WARN 0줄]   00:53 x92
```

`reports/raw/scan-1785976661-20260811T090209-loki-error-warn.json`

**얻는 것은 근거 시각의 정확도입니다** — 리포트가 인용하는 구간이 실제 신호 구간에 붙습니다.
그리고 그 정확도를 **메트릭에서는 사지 않았습니다.** 원복 판정이 걸려 있기 때문입니다.

### 반증 조건

* CH-3 재실행에서 좁힌 창이 18분 19초가 아니거나, 원본 응답에 `-w1`·`-w2`가 안 생기면 틀린 것입니다.
* 메트릭이 정답 채널인 문항(CH-2·AU-2)에서 창이 온셋 앞을 못 덮으면 `incident-pad-bucket`이
  부족한 것이고, 그때는 `step × 2`를 다시 재야 합니다.
* **아직 안 돌렸습니다** — 위 표의 18분 19초·14분 19초는 실제 후보 좌표로 계산한 값이고
  라이브 재실행 실측이 아닙니다.

## 이 절에서 얻은 것

```text
창이 실제 장애의 56배다
        ↓
pad가 범인일 것이다        → 반증. pad를 5m→2m으로 줄여도 3분, 토큰 −19
        ↓
union이 빈 구간을 덮는다   → 반증. 이미 후보별로 나눠 조회하고 있었다
        ↓
탐색이 하나만 골라야 한다  → 기각. 정답을 알아야 가능한 판단이고, 회차 5는
                             둘 다 골라 100점을 받았다
        ↓
창의 폭은 "고른 후보가 실제로 걸친 시간"이고, 그것은 낭비가 아니다
```

**확정된 것**

* pad 기본값을 `step × 2`로 유도하도록 고쳤고(상수 `5m`이 유도를 죽이고 있었습니다),
  창은 25분 19초 → 22분 19초가 됐습니다.
* 그 축소가 **토큰을 줄이지 않는다**는 것을 실측으로 확인했습니다(−19 tok, −0.03%).
  창 축소의 값은 근거 시각의 정확도이지 비용이 아닙니다.
* 창 분할 구조는 이미 동작하며, 옛 pad에서 발동하지 않은 것이 정상 동작임을 테스트로 박제했습니다.
* pad를 **정밀도가 아니라 채널에서** 유도하도록 바꿨습니다. Loki는 신호 구간이 이미
  `[ts − lookback, ts]`라 여유가 중복이었고, Tempo는 ms 정확이라 필요가 없었습니다.
  **메트릭에만 남긴 이유는 "딱 끊으면 원복 여부를 알 수 없다"** 는 원래 문제가 거기서만
  살아 있기 때문입니다.

**미측정으로 남긴 것**

* 컨텍스트의 81%를 차지하는 **지목 트레이스 9건의 인코딩** — 창이 아니라 여기가 토큰의 병목입니다.
* 채널별 pad를 적용한 **라이브 재실행**. 창 18분 19초·분할 두 창은 후보 좌표에서 계산한
  값이고 실측이 아닙니다.
* 메트릭이 정답 채널인 문항(CH-2·AU-2)에서 `step × 2`가 온셋을 덮는지.
