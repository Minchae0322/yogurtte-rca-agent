## 트레이스 채널만 접기가 안 걸려 있다

### 상황

| | |
|---|---|
| 주입 | 회차 5 여섯 문항 (AP-1·AP-2·AP-3·AU-2·AU-3·AU-4) |
| 증상 | AU-3만 컨텍스트 토큰 **−5.9%**, 비용 **+12.2%**. 나머지 다섯은 −34~55% |
| 관측 특성 | 회차 5는 **B-34 로그 접기 · B-35 트레이스 압축**이 처음 켜진 회차다 |
| 첫 판단 | *"AU-3은 창이 35분으로 넓어서 절감이 죽었다"* |
| 결과 | **그 판단이 반증됐다** — 아래 |

### 무엇이 일어났나

처음에는 창 탓으로 읽었다. AU-3의 좁힌 창이 35분으로 다른 문항(14~20분)보다 넓었고,
문항을 가로질러 **창 폭 오름차순이 절감 폭 내림차순과 대응**했기 때문이다.

**같은 문항끼리 재보니 반대였다.**

| AU-3 | 회차 3 (창 40분) | 회차 5 (창 35분) | 델타 |
|---|---:|---:|---:|
| 로그 ERROR/WARN | 108,802 B | 75,158 B | −31% |
| 로그 traceId | 8,833 B | 5,600 B | −37% |
| 메트릭 | 258,019 B | 234,686 B | −9% |
| **트레이스** | 82,057 B / 87 spans | **129,827 B / 167 spans** | **🔴 +58%** |
| → 분석 컨텍스트 | 224,231 자 | 183,110 자 | −18.3% |

**창은 오히려 12.5% 좁아졌고 로그·메트릭도 다 줄었는데 트레이스만 58% 늘었다.**
건당 8.2KB → **13.0KB**, span 87 → **167**. 회차 5 쪽에는 `(상위 span만)` 표시까지 붙어 있으니
**`max-trace-bytes` 절삭이 걸린 뒤가 그 크기**다.

**그리고 접기 자체는 작동했다.** 수집 원본(트레이스+로그) 합계는 199,692B → **210,585B로
5.5% 늘었는데** 컨텍스트는 224,231 → 183,110자로 **18.3% 줄었다.** 접기가 없었으면
컨텍스트도 늘었어야 한다. **트레이스 +58%가 접기 효과를 거의 다 먹은 것이다.**

**범인은 리포트가 스스로 지목했다.**

> content-service 기동 시 운영 DB에 `alter table` DDL **27건**이 나갑니다(trace `6a72c240…`)

저장된 트레이스 231건 전수에서 반복 span을 세어 보니 **그 트레이스가 1위**다 —
**80KB / 119 spans**가 반복이다.

### 왜 이 채널만 비었나

접기·요약이 채널마다 다르게 들어가 있고, **트레이스만 "아무것도 버리지 않는다"** 다.

| 채널 | 무엇이 걸려 있나 | 크기 상한 |
|---|---|---|
| 로그 | **B-34 접기** — 라이브러리 프레임 · 반복 블록 · 줄 안 잡음 | `log-limit` 1000줄 |
| 메트릭 | **B-25 요약** — 값 범위 · 0 구간 · 균등 표본 | (요약이 상한 역할) |
| **트레이스** | **B-35 재인코딩만** — span·속성 하나도 안 뺀다 | 개별 `max-trace-bytes` · **합계 상한 없음** |

B-35가 그렇게 설계된 이유는 정당했다 — AU-2류의 *"span이 없다"* 가 요건인 문항에서
부재 근거가 죽는 것을 막으려 했다. **그러나 반복 접기는 버리는 것이 아니다.**
로그에서 이미 같은 판단을 했고(`[x47회 · 시각 범위 · 평균 간격]`), AP-1 회차 5에서
**그 표식의 부재가 판단 근거로 쓰이기까지 했다**(*"`xN회`가 없어 다발 발생 근거가 없다"*).

| 트레이스 (수집) | **없음** | `max-trace-bytes` | 자르기만 | 반복 span이 절감을 상쇄 (AU-3 +58%) → B-36 |
| **후보 목록 (탐색)** | **없음** | `trace-limit` 20 · **Tempo 최신순** | **자르고 안 접는다** | **정답 축이 밀린다** ← 여기 |

**증상.** IN-1 회차 5에서 Redis 다운으로 chat에 **2,083~2,097ms 트레이스 19건**이 생겼는데
(04:32:52~04:35:44 · 앵커 2)①이 요구하는 *"Lettuce span 실패"* 의 트레이스 근거),
**수집이 0건**이었다. 리포트가 스스로 *"호출 그래프에 chat 관련 엣지 없음"* 이라 적었다.

**원인 두 가지가 다른 자리에 있다.**

| | 위치 | 무엇을 잃나 | 토큰 |
|---|---|---|---|
| ⓐ **묶기 전에 자름** | `Surveyor` — Tempo 검색 `limit=20`, **최신순** | 같은 지문 19건이 슬롯 19개를 먹어 `/feeds/scroll` 16.4초가 밀린다 | **무관** (원본은 `include-raw:false`로 LLM 미적재) |
| ⓑ **묶고도 안 접음** | `Incident.describe()` — `signals.forEach(...)` 한 신호당 한 줄 + traceId 전량 나열 | — | **19줄 + traceId 19개 ≈ 1,800자** |
| ⓒ **임계값** | `slow-trace-threshold: 3s` | 2,09x ms가 탈락 | — |

**ⓒ의 근거 — 임계값이 시스템 타임아웃 상수보다 크다.**

| 상수 | 값 | 어디 |
|---|---:|---|
| **Redis 커맨드** | **2,000ms** | content·chat `application-prod.yml` (기본값 아님, 명시 설정) |
| **auth HTTP 호출** | **3,000ms** | `ExternalUserApiClient.TIMEOUT` |
| Hikari connection | 10,000 / 20,000ms | content / chat |
| Mongo serverSelection | 30,000ms | 드라이버 기본 |
| Kafka `max.block.ms` | 60,000ms | 기본 |

현재 임계값 **3,000ms**는 최소 상수(2,000)보다 크고 두 번째(3,000)와 같다 → **둘 다 구조적으로 못 본다.**

> **규칙: 탐색 지연 임계값은 시스템에서 가장 짧은 타임아웃 상수보다 작아야 한다.**
> 그렇지 않으면 그 타임아웃이 만드는 지연은 원리적으로 안 보인다.
> ⚠️ **문항 이름(Redis 등)을 조건에 넣지 않는다** — 그것은 답에 자를 맞추는 것이라 §8상 무효다.
> 그리고 **기술적으로도 불가능하다**: 타임아웃이라 Redis span이 생성되지 않아
> 트레이스에 `db.system`조차 없다(실측 — `{ span.db.system != nil && duration > 2s }` **0건**).

**하한은 실측으로 정했다** — 정상 창(주입 없음, 20분 × 2회)의 노이즈 바닥.

| 임계값 | 정상 창 A | 정상 창 B | **장애 창** |
|---|---:|---:|---:|
| 300ms | 2건 | 4건 | — |
| 500ms | 1건 | 1건 | — |
| **700ms~1s** | **0건** | 0~1건 | 62건 |
| 2s | 0건 | — | 60건 |
| 3s (현재) | 0건 | — | **2건** |

```
500ms ──────── 1,500ms ──────── 2,000ms ──── 3,000ms
노이즈 바닥     안전 구간        Redis 상수    auth 상수 · 현재값
```

**→ 1,500ms.** 정상 창 오탐 0건, Redis·auth 지문 둘 다 포착.
(2,000ms로 잡으면 실측된 **2,000.8ms** 지문이 경계 밖이라 마진이 0.8ms다.)

**왜 앱 타임아웃을 올리지 않나** — 검토했고 기각했다. Redis 2s → 3s로 올리면
`/feeds/scroll`이 **16.4초 → 24.6초**(4명 × 2회 × 3초)로 사용자 피해가 커지고,
회차 2·3과 시스템이 달라져 비교가 깨지며, auth 3초 구멍은 그대로 남는다.
**에이전트 자신의 조치 3번이 정반대 방향**이었다(*"2초는 캐시 용도로 과도, 200~300ms급으로"*).

**구현 0 · 검증 0.** ⓐⓑⓒ는 **한 묶음으로만 성립한다** — ⓒ만 넣으면 후보가 밀리고,
ⓑ만 넣으면 도달 범위가 그대로다.

**🔴 B-18 정정 — 처방은 맞았고 하한 숫자가 틀렸다 (2026-08-06, CH-3 회차 5)**

`reports/raw/scan-1785913763-*-tempo-search.json`이 **깨진 값이 든 바로 그 응답**이다.
이 파일을 입력으로 단위 테스트를 쓰고 **성공 기준은 후보 목록에 `6a72ec0260…`이 들어오는 것**이다.

**반증 조건.** 필터를 뺐더니 창 안 무관 트레이스가 후보를 잠식해 **컨텍스트가 눈에 띄게 늘거나
정답 트레이스가 `max-traces` 상한에 밀리면**, 원인은 필터가 아니라 상한이므로 **B-37과 묶어 다시 짠다.**

**B-36 규칙안** (로그 B-34의 반복 블록 접기를 그대로 이식)

```
같은 이름 · 같은 부모 span이 N개(N≥3)
  → 첫 벌 + 끝 벌 + [xN회 · 총 1,842ms · 평균 68ms · 최대 389ms]
```

**지켜야 할 것 둘.**

- **duration 통계를 반드시 남긴다** — 총합·평균·최대. 이 채널의 값어치가 거기 있다.
  AP-3 회차 5가 span 13단계를 **시각순으로 재구성**해 dedup 부재를 도출했고, B-35가
  **시작 시각을 절대값으로 남기기로 한 결정**이 그 추론의 전제였다. 접기가 그것을 깨면 안 된다.
- **error span은 접지 않는다** — 반복 중 하나만 실패한 경우가 **정확히 AP-3**다
  (매핑 insert 성공 → 성공 → **실패**). 실패한 것은 무조건 원문으로 남긴다.

### ② 신호 도달을 미리 확인한 실측

**§3.1이 요구하는 것** — *"이 신호가 실제로 도달하는가를 확인한 결과를 함께 적는다."*
확인 없이 세운 인과 예측이 AP-1·AP-2에서 연속으로 반증됐기 때문이다.

`reports/raw/` 저장 트레이스 **231건 전수**:

```
총 2.00 MB · span 2,266개
같은 이름 3회 이상 반복 중 첫/끝만 남기면
  → 0.73 MB 절감 (36.3%) · 994 spans (전체 span의 44%)
```

반복이 큰 트레이스 상위:

| 트레이스 | 접히는 몫 |
|---|---|
| `6a72c240515fe3ce1bdd0c0fc9830077` | **80 KB / 119 spans** ← AU-3을 부풀린 그것 |
| `6a66b2c439929c47d4c8f275d8cc6986` | 39 KB / 54 spans |
| `6a67077c87b8b863f15cc6ee1ac95fbb` | 39 KB / 54 spans |

⚠️ **이 36.3%는 거친 모델이다** — *"같은 이름 3개 이상이면 첫/끝만"* 으로만 쟀다.
실제 구현은 **부모 span까지 보고 error span을 제외**하므로 값이 내려간다.
**B-34 때처럼 `TraceCompactMeasureTool`에 규칙을 넣고 전수로 다시 재는 것이 선행 조건**이다.

### ③ B-38(관련도 랭킹)을 보류하는 이유

**제안**: 지금은 `Collector`가 TraceQL `{}` 검색 결과를 **순서대로** 10건 채운다
(`LinkedHashSet`에 담을 뿐 정렬이 없다). 이것을 탐색 LLM이 **관련도 상위 10건**으로 고르게 한다.

**문제가 셋이다.**

1. **정답이 정상 트레이스인 문항이 있다.** 수집이 `{}`(상태 안 거름)인 이유가 그것이다 —
   AU-2의 정답은 *"정상 요청에 auth 호출 span이 **없다**"* 라 에러·지연 어느 채널에도 안 걸린다.
   관련도로 고르면 **정상 트레이스가 먼저 밀린다.**
2. **레포가 이미 같은 실패를 겪었다.** `CollectProperties.maxTraces` 주석 —
   *"상한을 두면 **정답 트레이스가 순위에 밀려 안 실릴 수 있다.** 상한이 3이던 시절에는
   대표 1건 + 후보 2건이 전부였고 … 순서에는 아무 의미가 없었다."* 상한을 3 → 10으로
   올린 것이 그 대응이다.
3. **탐색 컨텍스트를 다시 키운다.** 탐색 LLM이 고르려면 창 안 트레이스 목록을 봐야 하는데,
   지금 탐색 컨텍스트는 후보만 실어 **3,275자**다(`include-raw=false`, 회차 4 성과).

**그래서 순서가 있다: B-36을 먼저 하면 B-38이 필요 없을 수 있다.**
지금 문제는 *"무관한 것이 온다"* 가 아니라 *"무거운 것이 슬롯을 먹는다"* 이고,
**접기는 고르는 판단을 건드리지 않고 크기만 잡는다.** 반복 span이 접히면 무거운 트레이스가
가벼워지므로 10건 상한을 유지해도 바이트가 안 터진다.
**B-36 델타를 재고, 그래도 부족하면 B-38을 다시 꺼낸다.**

### 무엇이 일어났나

첫 판단은 *"상류를 보려면 span을 받아야 하고, 그건 탐색 단계에 너무 비싸다"* 였다.
**실측으로 반증됐다** — Tempo `/api/search` 응답에 `serviceStats`가 이미 들어 있다.
트레이스마다 서비스별 `spanCount`·`errorCount`를 주고, **파싱만 안 하고 있었다.**

```json
"serviceStats": { "auth-service": {"spanCount":4},
                  "chat-service": {"spanCount":14},
                  "content-service": {"spanCount":28} }
```

저장 응답 전수 확인(`reports/raw/*tempo-search*`): **트레이스 645건 중 52건이 2개 이상.**
새 쿼리도, 추가 토큰도 필요 없다.

Loki는 사정이 다르다. 지문이 하나인 원인은 후보 포맷이 아니라 **스윕 쿼리의 `sum by`가
내용을 지운 것**이고 구조적이다(회차 4 진단). `Series.logSignature()`는 이미 `exc` 라벨을
읽고 있으므로 **쿼리가 그 라벨을 만들어 주면 코드는 그대로 돈다.**

스윕 필터 |~ "ERROR|WARN"  →  헤더 줄만 통과  →  클래스 줄은 regexp 에 닿지도 못한다

그래서 예외 클래스는 지금 구조에서 **구조적으로 못 얻는다.**

잡힌 9건도 뜯어보면 갈린다.

|---|---|---|
| `com.mongodb.MongoTimeoutException` (7건) | 헤더 줄에 클래스가 함께 찍힌 경우 | 진짜 |
| `mc.e.t.a.c.e.GlobalException` (2건) | Logback이 축약한 **로거 이름** | **오탐** |

**결론: 지금 쿼리 형태로는 판별력이 거의 안 생긴다.** 켜도 후보가 한두 개 갈릴 뿐이다.
세 갈래가 남는다 — ⓐ 앱이 헤더 줄에 예외 클래스를 찍게 한다(**변경군 A**, B와 섞지 않는다)
ⓑ Alloy multiline 스티칭으로 스택을 한 엔트리로 묶는다(관측 파이프라인 · 과거 데이터로 검증 불가)
ⓒ 스윕에 라인 조회를 따로 건다(응답 크기 미측정 · `include-raw=false`로 -83%를 만든 직후다).
**어느 것도 착수하지 않았다.**

**③ 검증 설계 — 한 번에 하나만**

2. B-45를 켠다 → 후보 개수가 늘어나므로 **군집 과분할** 확인
3. 로그에 답이 있는 문항(AP-2 계열)에서 탐색 선택이 바뀌는지 본다

**④ 반증 조건**

- B-44로 후보 **개수**가 변하면 지문에 새어 들어간 것이다 — 테스트 `지문에는_넣지_않는다`가 그 회귀를 잡는다
- 상류가 보이는데도 탐색 선택이 안 바뀌면 문제는 정보량이 아니라 프롬프트다
- B-45 켠 뒤 한 서비스 후보가 5개 초과면 예외 클래스가 아니라 **최상위 프레임**으로 축약한다
- 지문 쿼리가 비어도 후보가 사라지면 안 된다 → 총 건수 곡선으로 자동 복귀 (테스트 박제)

**⑤ 현재 상태**

- **B-44 적용 완료 · 점수 효과 미측정.** 테스트 5건 박제(`CrossServiceSignalTest`), 픽스처는 저장 응답 원본
- **B-45 코드 적용 · 기본 꺼짐(`log-signature-query` 빈 값) · 쿼리 도달 확인 완료 · 효과 없음이 실측됐다.**
  쿼리는 돌지만 라벨이 붙는 비율이 **5.5%(진짜 예외는 4.3%)** 이고 다른 창은 **0%** 였다.
  **켜지 않는다** — 판별력이 안 생기는데 후보 구조만 흔든다. 테스트 4건은
  *"exc 라벨이 오면 어떻게 갈리는가"* 를 박제한 것이고, 라벨을 만드는 쪽이 위 ⓐ~ⓒ로 남았다
- **로그의 traceId는 손대지 않았다.** 로그 줄에 `[traceId=…]`가 있어 채널 간 병합
  근거로 쓸 수 있지만, **집계 쿼리로는 못 가져온다**(라인 조회가 따로 필요). 아래 별항
- `./gradlew test` 전체 통과

### 별항 — 로그의 traceId로 채널을 이을 수 있는가 (미착수)

지금 채널 간 병합 근거는 **traceId 하나뿐이고, 그것은 Tempo 신호에만 있다**
(`Incident.tempoRefs()`가 `channel == TEMPO`만 걸러 모은다). 그래서 Mimir·Loki 후보는
시간이 겹쳐도 `related` 표시에서 멈춘다.

로그 줄에는 traceId가 **있다.**

```
14:23:11.416 ERROR [traceId=6a68c522…,spanId=…,userId=…] MongoSocketOpenException: Connection refused
```

못 쓰는 이유는 존재가 아니라 **쿼리 형태**다. 스윕은 `count_over_time`으로 개수만 세므로
줄이 없고, 줄이 없으니 traceId도 없다. 쓰려면 라인 조회를 따로 걸어야 하고 그것은
탐색 컨텍스트/응답 크기를 다시 키운다(`include-raw=false`로 -83%를 만든 직후다).

**미착수인 채로 남기는 이유**는 셋이다.

1. 라인 조회의 응답 크기가 미측정 — 스택 줄이 딸려 오면 버킷당 1줄 전제가 깨진다
2. 실측상 traceId가 `NONE`인 줄이 많다(Reactor 이벤트 루프 · NF-09). 병합 근거로 쓰려면
   `NONE`을 반드시 걸러야 하고, 거른 뒤 남는 비율이 미측정이다
3. 채널 간 병합이 켜지면 **후보 하나는 한 채널**이라는 현재 불변식이 깨진다.
   `Incident.channel`이 첫 신호 기준이라 표기부터 손봐야 한다

**예측(미측정):** 로그 후보가 Tempo 후보와 결정적 근거로 합쳐지면 CH-1류에서 후보 수가
줄고 LLM이 인과를 잇는 부담이 준다. **반증 조건:** 합쳐진 뒤 후보가 3개 미만으로 내려가면
과병합이고, 그때는 창이 넓어져 컨텍스트가 다시 커진다 — 그 시점에 되돌린다.

## 대조군이 컨텍스트에 없었다 — 앵커 B 요건이 네 회차 연속 미수행이던 진짜 이유 (B-45 후속 · B-46)

**변경군 B (조사 도구).** 2026-08-11 · IN-2 창을 실제로 돌려 확인했다.

### 상황

| | |
|---|---|
| 계기 | B-45를 켠 뒤 IN-2(`2026-08-06T04:04:55Z~05:04:55Z`)를 종단 실행하고 앵커 v2·루브릭 v3로 채점 |
| 결과 | 총점 **97** — 3) 탐색만 15 중 **12** |
| 깎인 이유 | 앵커 B 요건 *"정상 구간 producer span과 대조 — 정상 발행이 몇 ms인지"* 미수행 |
| 관측 특성 | 그 창에 정상 발행 트레이스가 **실재했다**(`6a7411ba…` 1,237ms) |

### 무엇이 일어났나

첫 판단은 *"모델이 대조를 안 했다"* 였다. **실측으로 반증됐다** — 대조할 것이 컨텍스트에
아예 없었다. 수집된 호출 그래프의 messaging 엣지가 **하나뿐**이었다(실패한 발행).

원인이 두 겹이다.

```
① 스윕이 못 본다     정상 발행은 1,237ms · 에러 아님
                     { status = error }           → 안 걸림
                     { duration > 3s && !error }  → 1.2초 < 3초 → 안 걸림
                     → 후보 목록에 애초에 안 올라온다

② B-9가 못 메운다    창 안 후보 검색 {} 이 메우라고 있는데,
                     Tempo 검색은 최신순 limit만큼이라 25분 창의 최신 20건이
                     전부 security filterchain 잡트레이스였다(실측).
                     문제의 04:48 트레이스도 정상 발행도 그 안에 없었다.
```

**즉 B-9의 "남는 자리 채우기"는 트래픽이 있는 창에서 구조적으로 최신 잡트레이스만 담는다.**

### 무엇을 바꿨나 (B-46)

| 층위 | 무엇을 |
|---|---|
| 신호 공급 | 지목된 트레이스의 **루트 이름마다** 지목 검색(`{ rootName = "..." }`)으로 **가장 짧은 것 1건**을 딥 페치 |
| 구조 | `max-traces` **밖**에서 받는다(최대 3). 상한의 목적은 *무관한* 트레이스를 막는 것인데 대조군은 무관하지 않다 |

**정답을 심지 않는다** — 루트 이름은 탐색 LLM이 고른 트레이스에서 읽고, "정상"의 정의도
새로 만들지 않는다. 같은 이름 중 **가장 짧은 것**을 쓸 뿐이다.

루트 이름을 **하나만** 쓰면 안 된다는 것도 실측으로 나왔다 — 첫 구현이 `traces` 첫 번째의
이름만 썼는데, 탐색이 INC-4(스케줄러)까지 고른 실행에서 **스케줄러의 대조군**이 왔고 정작
발행 트레이스는 비교 대상이 없었다.

### 실측 — 같은 창 4회 실행

| 실행 | 대조군 | messaging 엣지 | spans | 컨텍스트 | 3) 탐색 |
|---|---|---|---:|---:|---:|
| 1차 (B-45만) | 없음 | 1 (실패만) | 30 | 76,204자 | **12** |
| 2차 (검색 결과 기반 대조군) | 안 붙음 | 1 | 30 | 76,217자 | 12 |
| 3차 (첫 트레이스 이름만) | **엉뚱한 것** (스케줄러 1ms) | 1 | 79 | — | 12 |
| **4차 (루트 이름마다)** | **`6a7411ba…` 1,237ms** | **2** (실패 발행 + 정상 receive) | 65 | 98,027자 | **15** |

리포트가 실제로 쓴 문장이다.

> *"**대조군(정상 트레이스)** `6a7411ba…` (04:46:50.592Z, **장애 시작 13초 전**, 동일 엔드포인트):
> `publish user.notifications` **16.7ms 성공** → chat-service `receive`(offset=1158, partition=3)"*

| `publish user.notifications` | 실측 | 상한 | 판정 |
|---|---:|---:|---|
| 장애 트레이스 | 60,016ms | 60,000ms(`max.block.ms`) | 만료 |
| **대조군** | **16.7ms** | 60,000ms | 미만료 · 성공 |

부수 효과로 **소비 경로 전체가 정상임을 관측으로 확인**했다(`receive → mongo insert →
WebSocket`), 그래서 "소비단 문제" 후보를 데이터 부족으로 남기되 배제 논증을 붙였다.

### 반증 조건

- 대조군이 붙었는데도 리포트가 절대값만으로 판단하면 병목은 수집이 아니라 **프롬프트**다
- 같은 루트 이름의 정상 사례가 창에 없으면 **"대조군 없음"이 `failures`에 남는다** —
  그 문구가 안 뜨는데 대조군도 없으면 지목 검색이 깨진 것이다
- 컨텍스트 증가분이 트레이스당 수십 KB를 넘으면 되돌린다 (실측 +29%, 67,872B)

### 남는 것

- **상한이 비대칭이다.** 트레이스는 1건당 102,400B로 잘리는데 **합계 상한이 없고**,
  로그도 쿼리당 1,000줄뿐 총량 상한이 없다. 이번 실행에서 로그가 151,193B로 가장 컸다
- `slow-trace-threshold`가 yaml `3s` / Java `2s`로 어긋나 **B-43 의도가 실효 없다**.
  2s로 낮춰도 이번 대조군(1,237ms)은 여전히 안 걸리므로 B-46과는 별건이다
