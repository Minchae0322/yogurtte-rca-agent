## 트레이스 채널만 접기가 안 걸려 있다

### 상황

| | |
|---|---|
| 주입 | 회차 5 여섯 문항 (AP-1·AP-2·AP-3·AU-2·AU-3·AU-4) |
| 증상 | AU-3만 컨텍스트 토큰 **−5.9%**, 비용 **+12.2%**. 나머지 다섯은 −34~55% |
| 관측 특성 | 회차 5는 **B-34 로그 접기 · B-35 트레이스 압축**이 처음 켜진 회차다 |
| 첫 판단 | *"AU-3은 창이 35분으로 넓어서 절감이 죽었다"* |
| 결과 | **그 판단이 반증됐다** — 아래 |

### 무엇이 일어났나

처음에는 창 탓으로 읽었다. AU-3의 좁힌 창이 35분으로 다른 문항(14~20분)보다 넓었고,
문항을 가로질러 **창 폭 오름차순이 절감 폭 내림차순과 대응**했기 때문이다.

**같은 문항끼리 재보니 반대였다.**

| AU-3 | 회차 3 (창 40분) | 회차 5 (창 35분) | 델타 |
|---|---:|---:|---:|
| 로그 ERROR/WARN | 108,802 B | 75,158 B | −31% |
| 로그 traceId | 8,833 B | 5,600 B | −37% |
| 메트릭 | 258,019 B | 234,686 B | −9% |
| **트레이스** | 82,057 B / 87 spans | **129,827 B / 167 spans** | **🔴 +58%** |
| → 분석 컨텍스트 | 224,231 자 | 183,110 자 | −18.3% |

**창은 오히려 12.5% 좁아졌고 로그·메트릭도 다 줄었는데 트레이스만 58% 늘었다.**
건당 8.2KB → **13.0KB**, span 87 → **167**. 회차 5 쪽에는 `(상위 span만)` 표시까지 붙어 있으니
**`max-trace-bytes` 절삭이 걸린 뒤가 그 크기**다.

**그리고 접기 자체는 작동했다.** 수집 원본(트레이스+로그) 합계는 199,692B → **210,585B로
5.5% 늘었는데** 컨텍스트는 224,231 → 183,110자로 **18.3% 줄었다.** 접기가 없었으면
컨텍스트도 늘었어야 한다. **트레이스 +58%가 접기 효과를 거의 다 먹은 것이다.**

**범인은 리포트가 스스로 지목했다.**

> content-service 기동 시 운영 DB에 `alter table` DDL **27건**이 나갑니다(trace `6a72c240…`)

저장된 트레이스 231건 전수에서 반복 span을 세어 보니 **그 트레이스가 1위**다 —
**80KB / 119 spans**가 반복이다.

### 왜 이 채널만 비었나

접기·요약이 채널마다 다르게 들어가 있고, **트레이스만 "아무것도 버리지 않는다"** 다.

| 채널 | 무엇이 걸려 있나 | 크기 상한 |
|---|---|---|
| 로그 | **B-34 접기** — 라이브러리 프레임 · 반복 블록 · 줄 안 잡음 | `log-limit` 1000줄 |
| 메트릭 | **B-25 요약** — 값 범위 · 0 구간 · 균등 표본 | (요약이 상한 역할) |
| **트레이스** | **B-35 재인코딩만** — span·속성 하나도 안 뺀다 | 개별 `max-trace-bytes` · **합계 상한 없음** |

B-35가 그렇게 설계된 이유는 정당했다 — AU-2류의 *"span이 없다"* 가 요건인 문항에서
부재 근거가 죽는 것을 막으려 했다. **그러나 반복 접기는 버리는 것이 아니다.**
로그에서 이미 같은 판단을 했고(`[x47회 · 시각 범위 · 평균 간격]`), AP-1 회차 5에서
**그 표식의 부재가 판단 근거로 쓰이기까지 했다**(*"`xN회`가 없어 다발 발생 근거가 없다"*).

## 회차 6에서 바꿀 것

### ① 변경 표

| ID | 층위 | 변경 | 상태 |
|---|---|---|---|
| 🔴 **B-39** | **로그 상한** | `limit=1000` + `direction=forward` → **창 앞/뒤 분할 상한**(발단 500 + 복구 500). **점수가 걸린 유일한 항목이라 이것이 1순위** | **실측 확인 · 미구현** |
| **B-36** | 트레이스 접기 | 같은 이름·같은 부모 span이 N개(N≥3)면 **첫 벌 + 끝 벌 + 통계 표식**으로 접는다 | **절감 실측 완료 · 미구현** |
| **B-37** | 수집 상한 | `max-traces`(건수) → **합계 바이트 예산 + 후보별 균등 배분 + 절삭 명시** | 설계만 |
| B-38 | 후보 선정 | 창 안 후보 트레이스를 **관련도 순으로** 고른다 | **보류** — ③ 참조 |

**🔴 B-39 — 절삭이 복구 구간을 먹는다 (2026-08-05, [CH-1 회차 5 실행1](../ch-1/round-5-run1.md)에서 확인)**

`LokiClient`([:25-26](../../src/main/java/com/yogurtte/rca/client/LokiClient.java))가
`limit=1000` + **`direction=forward`** 다. 창이 넓으면 **앞에서부터 1000줄을 채우고 뒤를 버린다.**

| CH-1 회차 5 실행1 실측 | |
|---|---|
| 수집 창 | 07:25:00 ~ 08:09:23Z (**44.4분**) |
| 실제 수집 | 07:31:40 ~ **07:54:34**Z (**22.9분**) · 정확히 **1000줄** |
| 버려진 것 | **DLQ 발행(ERROR)** · 재시도 2~4회차 · **DLQ 재처리 성공(INFO)** |
| 결과 | 4) 영향 **10 → 5**, 2) 근거 재시도 N 미확정 — **감점 10 중 7** |

**장애 조사에서 잘리는 뒤쪽은 언제나 복구·도착 구간이다.** [round-5 §2](../round-5/README.md)가
*"1000줄이 약 106초만 커버 · 복구 시점이 잘린다"* 고 예고했고, **점수로 확인된 것이 이번이 처음**이다.

- ⓐ `direction=backward` — 복구는 살지만 **발단이 죽는다.** 단독으로는 답이 아니다
- **ⓑ 창을 앞/뒤로 쪼개 각각 상한을 준다 — 유력.** 발단과 복구를 둘 다 남기는 유일한 방식
- ⓒ **접기 후 상한** — 지금은 1000줄을 **접기 전에** 자른다. B-34와 순서만 바꾸는 것이라 싸다

**검증은 주입 없이 된다** — `reports/raw/scan-1785914700-*-loki-error-warn.json`이 그대로 있으므로
같은 창을 ⓑ·ⓒ로 재수집해 *"DLQ 발행·재처리 성공 두 줄이 들어오는가"* 만 보면 된다.
**성공 기준은 바이트가 아니라 그 두 줄의 존재다.**

**B-36 규칙안** (로그 B-34의 반복 블록 접기를 그대로 이식)

```
같은 이름 · 같은 부모 span이 N개(N≥3)
  → 첫 벌 + 끝 벌 + [xN회 · 총 1,842ms · 평균 68ms · 최대 389ms]
```

**지켜야 할 것 둘.**

- **duration 통계를 반드시 남긴다** — 총합·평균·최대. 이 채널의 값어치가 거기 있다.
  AP-3 회차 5가 span 13단계를 **시각순으로 재구성**해 dedup 부재를 도출했고, B-35가
  **시작 시각을 절대값으로 남기기로 한 결정**이 그 추론의 전제였다. 접기가 그것을 깨면 안 된다.
- **error span은 접지 않는다** — 반복 중 하나만 실패한 경우가 **정확히 AP-3**다
  (매핑 insert 성공 → 성공 → **실패**). 실패한 것은 무조건 원문으로 남긴다.

### ② 신호 도달을 미리 확인한 실측

**§3.1이 요구하는 것** — *"이 신호가 실제로 도달하는가를 확인한 결과를 함께 적는다."*
확인 없이 세운 인과 예측이 AP-1·AP-2에서 연속으로 반증됐기 때문이다.

`reports/raw/` 저장 트레이스 **231건 전수**:

```
총 2.00 MB · span 2,266개
같은 이름 3회 이상 반복 중 첫/끝만 남기면
  → 0.73 MB 절감 (36.3%) · 994 spans (전체 span의 44%)
```

반복이 큰 트레이스 상위:

| 트레이스 | 접히는 몫 |
|---|---|
| `6a72c240515fe3ce1bdd0c0fc9830077` | **80 KB / 119 spans** ← AU-3을 부풀린 그것 |
| `6a66b2c439929c47d4c8f275d8cc6986` | 39 KB / 54 spans |
| `6a67077c87b8b863f15cc6ee1ac95fbb` | 39 KB / 54 spans |

⚠️ **이 36.3%는 거친 모델이다** — *"같은 이름 3개 이상이면 첫/끝만"* 으로만 쟀다.
실제 구현은 **부모 span까지 보고 error span을 제외**하므로 값이 내려간다.
**B-34 때처럼 `TraceCompactMeasureTool`에 규칙을 넣고 전수로 다시 재는 것이 선행 조건**이다.

### ③ B-38(관련도 랭킹)을 보류하는 이유

**제안**: 지금은 `Collector`가 TraceQL `{}` 검색 결과를 **순서대로** 10건 채운다
(`LinkedHashSet`에 담을 뿐 정렬이 없다). 이것을 탐색 LLM이 **관련도 상위 10건**으로 고르게 한다.

**문제가 셋이다.**

1. **정답이 정상 트레이스인 문항이 있다.** 수집이 `{}`(상태 안 거름)인 이유가 그것이다 —
   AU-2의 정답은 *"정상 요청에 auth 호출 span이 **없다**"* 라 에러·지연 어느 채널에도 안 걸린다.
   관련도로 고르면 **정상 트레이스가 먼저 밀린다.**
2. **레포가 이미 같은 실패를 겪었다.** `CollectProperties.maxTraces` 주석 —
   *"상한을 두면 **정답 트레이스가 순위에 밀려 안 실릴 수 있다.** 상한이 3이던 시절에는
   대표 1건 + 후보 2건이 전부였고 … 순서에는 아무 의미가 없었다."* 상한을 3 → 10으로
   올린 것이 그 대응이다.
3. **탐색 컨텍스트를 다시 키운다.** 탐색 LLM이 고르려면 창 안 트레이스 목록을 봐야 하는데,
   지금 탐색 컨텍스트는 후보만 실어 **3,275자**다(`include-raw=false`, 회차 4 성과).

**그래서 순서가 있다: B-36을 먼저 하면 B-38이 필요 없을 수 있다.**
지금 문제는 *"무관한 것이 온다"* 가 아니라 *"무거운 것이 슬롯을 먹는다"* 이고,
**접기는 고르는 판단을 건드리지 않고 크기만 잡는다.** 반복 span이 접히면 무거운 트레이스가
가벼워지므로 10건 상한을 유지해도 바이트가 안 터진다.
**B-36 델타를 재고, 그래도 부족하면 B-38을 다시 꺼낸다.**

### ④ 검증 설계 — 한 번에 하나만 바꾼다

| 순서 | 무엇을 | 어떻게 | 비용 |
|---|---|---|---|
| 0 | **회차 5의 접기 몫 분리** | `ContextRebuildTool`로 같은 raw 원본에 `fold on/off` 두 버전 재구성 → 문자 수 비교. **창 변수가 원리적으로 0** | **$0 · 오프라인** |
| 1 | B-36 절감 실측 | `TraceCompactMeasureTool`에 규칙 넣고 저장 231건 전수 | $0 · 오프라인 |
| 2 | B-36 정확도 | **AP-3**로 창 고정 A/B — span 시각순 재구성이 이 문항의 근거다. 접기가 그걸 깨면 즉시 드러난다 | ~$1.7 |
| 3 | B-37 | B-36 적용 후에도 합계가 큰지 보고 결정 | — |

**0번이 회차 5가 못 낸 답을 낸다** — *"접기가 실제로 얼마나 줄였나"*.
실제 조사 A/B보다 정확하다(창·트래픽이 완전히 동일한 데이터).

### ⑤ 반증 조건

- **B-36이 틀린 경우**: AP-3 A/B에서 **원인·근거 인용이 달라지면** 즉시 되돌린다.
  특히 *"같은 조회가 두 번, 첫 번째 0건 · 두 번째 1건"* 이라는 **순서 논증이 깨지면**
  접기 규칙이 span 순서를 훼손한 것이다.
- **B-36이 무의미한 경우**: 규칙을 정밀화(부모 일치 + error 제외)했을 때 실측 절감이
  **10% 아래로 내려가면** 36.3%는 과대추정이었고, 그때는 B-37만 남긴다.
- **진단 자체가 틀린 경우**: 0번(오프라인 A/B)에서 회차 5의 절감 대부분이 **접기가 아니라
  창 축소**로 밝혀지면, 이 문서의 전제(*"트레이스 채널만 접기가 비어 있다"*)는 유지되지만
  **회차 5의 −34~55%를 접기 성과로 쓴 서술을 전부 정정해야 한다.**
