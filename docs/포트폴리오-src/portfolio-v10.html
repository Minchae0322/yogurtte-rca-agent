장애 원인 분석을 자동화한 Spring AI 기반 RCA 에이전트

정민채 · jmcabc0322@gmail.com · 2026. 08 · 개인 프로젝트
Java 21 · Spring Boot 3.5 · Spring AI · Grafana Tempo / Loki / Mimir · K3s · Kafka · Redis / MongoDB / MySQL

Trace · Log · Metric을 자동으로 수집하고 장애 원인을 분석하는 RCA 에이전트를 개발했습니다. 개발 과정에서 단순히 프롬프트를 개선하는 대신 "AI가 못 찾은 것인가, 데이터가 전달되지 않은 것인가"를 분리해 문제를 추적했고, 그 결과 개선의 대부분은 모델이 아니라 관측 파이프라인과 Evidence 구조에서 나왔습니다.

장애 질문 → 장애 구간 탐색 → Trace · Log · Metric 수집 → 필요한 정보 정리 → AI 분석 → 원인과 근거 출력

75 → 94점  회차 평균 RCA 정확도 (1 → 4회차) · 동일 기준 8문항 · 최대 개선 문항 4 → 100점

−33~−47%  조사당 비용 (컨텍스트 −34.5~−54.5%) · 로그 57% 압축에도 점수 하락 문항 0개

측정 근거 — MongoDB 23초 순단, Kafka DLQ 재처리 실패, 컨슈머 전멸, 팔로우 조회 NPE, 해시태그 중복 저장, 인증 서버 전면 다운, 인증 다운 중 익명 폴백, 인프라 복합 장애 등 12종을 직접 주입하고 8문항을 채점했습니다. 채점 기준(100점 만점)은 원인 40 · 근거 25 · 탐색 15 · 영향 10 · 오귀인 5 · 조치 5. 기준 답안(앵커)은 장애 주입 전에 고정하며 결과를 본 뒤의 앵커 수정은 그 회차를 무효로 합니다. 리포트 생성 경로에 정답지가 없는 블라인드 채점이고, 문항당 2회 이상 반복(평균 ± 최대편차, 편차 ±10 초과는 인용 보류)하며, 감점이 나오면 그 신호가 백엔드에 실재했는지 직접 쿼리로 확인합니다. 회차 평균은 앵커 개정으로 집계에서 제외한 2문항(AP-1 · AU-3)을 뺀 8문항 기준이고, 두 회차는 같은 앵커 · 같은 루브릭으로 채점해 직접 비교가 성립합니다.

01  내가 해결하려던 문제

RCA Agent가 원인을 못 찾았을 때, LLM이 추론에 실패한 것인지 관측 데이터 자체가 부족한 것인지 구분할 수 없었습니다. 구분할 수 없으면 다음 행동도 없습니다. 프롬프트를 고쳐야 할지, 수집을 고쳐야 할지, 계측을 추가해야 할지 정할 수 없기 때문입니다. 그래서 감점이 나올 때마다 원인을 층별로 확정하는 역추적 절차를 만들어 평가 규칙에 넣었습니다.

백엔드에 데이터가 있었나? → 쿼리가 가져왔나? → 필터가 제거했나? → 수집 · 변환 과정에서 버렸나? → 최종 Evidence에 도달했나?

이 절차를 실제로 돌려 보니, 같은 "로그가 안 들어온다"는 증상 하나에서도 층이 전부 다른 결함 넷이 나왔습니다. 쿼리 셀렉터 층은 존재하지 않는 라벨 참조로 매칭 스트림이 0개였고, 파서 층은 평문 로그에 logfmt 파서를 적용해 항상 빈 결과였으며, 필터 층은 라인 필터가 스택트레이스를 배제해 예외 원인이 소실됐고, 수집 변환 층은 parentSpanId 미파싱으로 호출 관계가 소실돼 있었습니다.

"백엔드에 데이터가 존재하는 것과, 에이전트가 그것을 Evidence로 쓸 수 있는 것은 다르다."

이 명제가 프로젝트 전체를 관통합니다. 이후의 모든 개선은 이 역추적이 가리킨 층에서 이루어졌고, 개선의 효과는 층을 섞지 않고 한 번에 하나씩 검증했습니다.

02  가장 큰 문제 해결 — 탐색 구조 재설계 (4 → 85 → 100)

MongoDB 23초 순단(CH-3) — 에러 없이 지연만 발생하는 장애를 탐색이 통째로 놓치던 문항입니다.

처음 판단. "분석 창이 좁아서 장애 신호를 놓쳤다." 초기 분석 창(04:50~05:50)은 장애 구간(05:22:01~05:22:38)을 포함했지만, 탐색이 창을 좁히며 장애 시작 1초 전에 끊었기 때문입니다.

실측. 창을 2.26배 확대하는 실험을 했습니다. 결과는 Context +72% / Cost +39% / 점수 변화 없음. 첫 판단이 틀렸다는 뜻이므로, Trace · Metric · Log를 채널별로 역추적했습니다.

원인. Trace는 error만 탐색해 지연 장애가 원리적으로 안 보였고, Metric은 5분 샘플링 사이로 23초 다운이 빠졌으며, Log에는 유효 신호가 부족했습니다. 창을 어떻게 잡아도 후보를 만들 Signal 자체가 없었던 것입니다. 문제는 LLM이 아니라 탐색 구조였습니다.

해결. duration 기반 지연 Trace 채널을 신설하고, Metric은 min/max_over_time 구간 집계로 단기 장애를 보존하고, 하나의 창 + 하나의 traceId 구조를 Signal → Incident 후보 → LLM 선택 구조로 재설계해 여러 후보를 유지한 뒤 LLM이 근거를 들어 선택하게 했습니다.

결과. CH-3 4 → 85 (후보 10건 전부가 신설 지연 채널에서 나왔고 그중 2건이 정답). 이어서 리포트에 수치는 다 있는데 결론 한 줄이 없는 것을 확인하고, 프롬프트에 "대기 시간을 타임아웃 상한과 대조하라" 한 문장을 추가해 85 → 100. 도구 개선(+81)과 프롬프트(+15)의 기여는 회차를 나눠 분리 검증했습니다.

반대 사례도 같은 방식으로 처리했습니다. 함께 넣은 다른 프롬프트 한 줄이 무관한 항목을 −10점 시키는 것을 단일 변수 재실험으로 확인하고 폐기했습니다. 얻는 것 없이 점수만 깎는 변경은 버립니다.

03  내가 설계한 핵심 구조 — Evidence 정제 계층

Raw Observability Data ≠ RCA Evidence

장애 원인에 필요한 정보는 Loki와 Tempo에 이미 있었습니다. 문제는 수집 · 가공 과정에서 일부가 누락되고, 관계가 손실되고, 같은 내용이 중복 전달된다는 것이었습니다. 개별 쿼리 수정으로 대응하는 대신, 원본 관측 데이터를 분석 가능한 Evidence로 변환하는 계층을 파이프라인에 추가했습니다.

Tempo / Loki / Mimir → Collector (원본 수집 · 원본 JSON 박제) → Evidence Normalization (Stack Trace 복원 · Call Graph · Dedup · Folding · Incident) → LLM 분석

Stack Trace 복원 — ERROR|WARN 헤더만 수집하던 규칙에 Exception · Caused by · 파일:라인 패턴을 추가했습니다. 실제 원인이던 FollowCondition.java:25가 처음으로 분석 컨텍스트에 도달했습니다.

Call Graph 생성 — 일렬 span 목록을 parentSpanId · db.system · messaging.system · client.name 기반의 호출 Edge로 집약했습니다(span 28개 → Edge 6개, 호출 횟수 · 최대 duration · error · rollback 부착). 원본 Trace는 유지하고 그래프를 추가 컨텍스트로 제공합니다.

Dedup — ERROR/WARN 조회와 traceId 조회가 같은 로그를 중복 전달(채널 기준 약 27%)하는 것을 확인하고, 두 채널은 유지한 채 어셈블 단계에서 (timestamp, line) 교집합만 제거했습니다.

관측 기준 통일 — 서비스마다 다르던 로그 정책(한 서비스는 1시간 2,300줄 중 ERROR/WARN 8줄, 다른 서비스는 401/500조차 무로그)을 "성공은 Trace, 4xx/5xx와 1초 초과만 Log"로 통일했습니다.

관측 공백 생성 — HTTP 200으로 숨어 있던 익명 폴백 장애(사용자 10명 저하, 에러율 정상)에 [user-fallback] 로그 규약, MDC 캡처 · 복원, user_fallback_total 메트릭을 추가해 애초에 신호가 없던 구간을 관측 가능하게 만들었습니다.

변환의 정확성은 저장된 트레이스 17건 기반 픽스처와 단위 테스트로 고정했습니다. RCA 점수에 대한 효과는 아직 측정 전이며, 변경군별 재조사로 분리 검증할 예정입니다.

04  성능 · 비용 최적화 — 쓰이는 증거 기준의 압축

무엇을 버릴지 감으로 고르지 않았습니다. 과거 RCA 리포트 44건이 실제로 인용한 코드 위치를 세어 공급과 수요를 비교했습니다. 라이브러리 프레임은 공급의 71%(903줄)인데 리포트 인용 0회, 애플리케이션 프레임은 공급의 3.7%(50줄)인데 12개 클래스에서 32회 인용이었습니다. 가장 많은 자리를 차지하는 것이 한 번도 쓰이지 않은 것입니다.

사용되지 않는 데이터가 아니라 "사용되는 증거"를 기준으로 압축했습니다. 라이브러리 프레임 · ANSI 코드 · 반복 로그는 지우지 않고 접었습니다. 반복 블록은 [x47회 · 평균 2초 간격]처럼 횟수와 주기를 명시해 오히려 정보를 늘렸고, 절대 접히면 안 되는 것(애플리케이션 프레임 · 예외 헤더 · 예외 메시지의 수치 · 경계 ±1 프레임)은 단위 테스트로 고정했습니다. 트레이스는 삭제 없이 반복 · 장황 표현만 축약했습니다. 서버가 늘어나면 지금 안 쓰이는 관계 정보가 필요해질 수 있기 때문입니다.

결과는 저장 원본 전수 기준 로그 −57.0%(3,237,421B → 1,390,968B) · 트레이스 −30.0%(1,863,242B → 1,305,152B), 전 문항 재측정에서 분석 컨텍스트 토큰 −34.5~−54.5%(예: AP-2 85,959 → 39,118 tok) · 조사당 비용 −33~−47%(예: $1.51 → $0.83)입니다. 점수가 내려간 문항은 하나도 없습니다(88 → 88, 85 → 85, 95 → 100). 결정적 검증 지점은 정답이 로그 스택에만 있는 유일한 문항(AP-2)으로, 로그를 54.5% 접고도 예외 원문 · 애플리케이션 프레임 4단계 · 줄 번호를 전부 인용하며 점수를 유지했습니다. 회귀 테스트 112건도 통과했습니다.

절감치는 회차마다 조건이 달라 접기의 순수 효과로 전량 귀속할 수 없으며, 동일 조건 A/B는 미실행으로 남겨 두었습니다. 효과는 과장하지 않습니다.

05  디버깅 — 같은 조건에서 86점과 100점이 나왔다

같은 주입 데이터를 18분 간격으로 두 번 조사했는데 86점과 100점이 나왔습니다. "LLM이라 편차가 있다"로 끝내면 다음 행동이 없습니다. 갈린 12점의 Evidence를 역추적했더니, 원인은 모델이 아니라 코드 한 줄이었습니다.

1  86점 실행에서 Tempo 응답의 durationMs가 3505144756(40.5일)으로 일시 파손
2  깨진 값을 이유로 해당 트레이스를 후보 목록에서 제거
3  정답 트레이스 유실 — 발행 → 실패 4회 → DLQ → 재처리가 든 한 건, 로그는 헬스체크 37줄만 잔존
4  주석과 구현의 불일치 발견 — "trusted=false로 남기고 정렬에서만 뺀다"는 주석과 달리 수집에서도 제외
5  필터 한 줄 제거 → 100점

검증에 새 장애 주입은 필요 없습니다. 깨진 값이 든 원본 응답이 그대로 박제돼 있어 단위 테스트 입력으로 쓰면 되고, 성공 기준은 "후보 목록에 그 traceId가 들어오는가" 하나입니다. 같은 역추적에서 로그 조회가 limit=1000 + direction=forward라 시간창 뒤쪽 34%(항상 복구 · 알림 도착 구간)가 잘리는 결함도 함께 잡았습니다.

단일 실행 점수는 성능이 아닙니다. 필드 하나의 일시적 파손이 14점을 만들었습니다. 그래서 평가 규칙에 문항당 N ≥ 2 반복과 "감점마다 신호의 실재를 직접 확인한다"를 넣었고, 이 사례가 그 규칙의 필요를 증명했습니다.

06  결과, 그리고 내가 얻은 것

집계 8문항의 회차 평균은 75점(1회차) → 94점(4회차)으로 올라왔습니다. 탐색이 놓치던 장애는 4 → 85 → 100으로 복구됐고, 컨텍스트와 비용을 절반 가까이 줄이면서 점수가 하락한 문항은 없었으며, 점수 편차조차 원인 코드까지 역추적해 제거 가능한 결함으로 바꿨습니다. 같은 기준(같은 앵커 · 같은 루브릭)으로만 비교했고, 변경은 한 번에 한 종류만 적용해 효과의 귀속을 유지했습니다.

데이터가 존재하는 것과 사용할 수 있는 것은 다릅니다. 데이터는 쿼리 · 필터 · 상한 · 해상도 · 수집 변환 어디서든 사라질 수 있고, 사라진 지점은 역추적으로만 찾을 수 있습니다.

LLM 성능보다 Signal Quality가 먼저입니다. 막힌 채널 수와 점수가 정렬됐습니다. 신호가 도달한 문항은 처음부터 90~100점이었고, 무너진 문항은 전부 채널이 막힌 문항이었습니다.

컨텍스트는 많이 넣는 게 아니라 Evidence 밀도를 높이는 것입니다. 공급의 71%가 한 번도 인용되지 않았고, 그것을 접어 57%를 줄여도 점수는 내려가지 않았습니다.

단일 실행 결과를 성능이라고 부르면 안 됩니다. 같은 조건에서 필드 하나의 파손이 14점을 갈랐습니다. 반복 측정과 감점 역추적이 없으면 이 차이를 능력 차이로 오독하게 됩니다.

Backend Engineer로서, 복잡한 시스템의 문제를 데이터 → 코드 → 실행 결과까지 추적하고 검증하는 능력을 키웠습니다.

이 문서에 없는 것: Top-1 적중률, 기준이 다른 두 시기를 이어 붙인 Before/After 비교. 측정하지 않은 값은 채우지 않고 비워 두었습니다. 남은 과제는 정상 문항 투입을 통한 정밀도 측정과 Code-aware RCA(Git diff · 배포 정보 연동)입니다.

본문의 모든 수치는 아래 측정 체계 안에서 만들어졌습니다. 요약만 남기고, 상세 기록은 저장소 문서 (docs/scoring, docs/changes.md, 회차별 · 문항별 기록, reports/raw 원본 박제)에 있습니다.

블라인드 채점 — 정답 앵커를 장애 주입 전에 고정하고, 결과를 본 뒤의 앵커 수정은 그 회차를 무효로 합니다. 리포트 생성 경로에는 정답지가 없습니다.
반복 측정 — 문항당 최소 2회, 평균 ± 최대편차로 기록하고 편차 ±10 초과 문항은 인용을 보류합니다. 측정 실패는 0점이 아니라 "채점 불가"로 구분합니다.
단일 변경군 — 변경을 앱 계측 / 조사 도구 / 프롬프트로 나눠 한 회차에 하나만 적용합니다. 결함을 발견해도 즉시 고치지 않고 다음 회차로 보내 baseline을 고정합니다.

측정 도구 자체의 결함도 세 번 찾아 고쳤습니다. 앵커 결함 — 초기 "채점 불가" 4건이 전부 정답지 쪽 결함이었습니다(기준 부적합률 67% → 33%). 루브릭도 개정했고, 개정 전후 점수는 나란히 비교하지 않습니다. 블라인드 오염 — LLM CLI가 JVM 작업 디렉터리의 프로젝트 문서를 자동으로 읽어, 평가 대상이 정답 힌트가 적힌 문서를 본 상태로 시험을 보고 있었습니다. 디렉터리를 격리하고 오염 크기를 실측(+23%)한 뒤 이전 회차를 전부 폐기 · 재실험했습니다. 토큰 지표 버그 — 하네스가 42,774 토큰을 2로 기록했고, 상수로 가정한 CLI 오버헤드는 하루 20% 변동했습니다. 조사마다 1자 프롬프트로 오버헤드를 실측하는 프로브로 대체했습니다.

본문에 싣지 않은 의사결정 · 사례 두 가지. OTel Agent 전환 검토 — 계측 사각지대를 겪고 zero-code 전환을 검토했으나, 48시간 A/B 대신 대표 사용자 흐름 3종의 E2E 트레이스 실측으로 먼저 검증했습니다. 현 구조가 RCA 데이터 요건을 충족함을 확인하고 전환 비용 (메모리 · CPU 오버헤드 · 운영 리스크)을 근거로 Brave 유지를 결정, 대신 Observation 체크리스트와 주기적 샘플링 검증을 운영 가이드로 추가했습니다. 스크레이프 간격 — 구간 집계로 단기 장애 보존을 끝냈다고 판단했으나 재조사에서 절반만 맞았음이 드러났습니다. 23.6초 다운의 포착 확률이 79%(간격 30초)라는 것을 count_over_time 실측으로 확인하고, 인프라 145개 시리즈만 10초로 낮추는 층 분리로 해결했습니다(앱 2,513개 시리즈는 무변경, 전후 실측 2 → 6 샘플/분). exporter가 연결 실패를 즉시 반영하는지는 다음 주입에서 확인할 미검증 항목으로 남겨 두었습니다.
