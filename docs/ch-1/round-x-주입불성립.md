## 1. 무엇이 일어났나

주입 자체는 두 조각이다 — **장애(Mongo 다운)** 와 **트리거(댓글 작성)**. CH-1은 둘이 만나야
성립하는 문항이다. 이번에는 장애만 성립했다.

| 조각 | 사양 | 이번 회차 | |
|---|---|---|---|
| Mongo 다운 | ≥5분 (갈래 B) | **5분 30초** (07:12:36~07:18:06Z) | 성립 |
| 트리거 댓글 작성 | 201 → `user.notifications` 발행 | **401 × 2건** | 🔴 **불성립** |
| 컨슈머 실패 → 재시도 소진 | 재시도 3~4회 | **0건** | 부재 |
| DLQ 적재 | `user.notifications.dlq` | **0건** | 부재 |
| 복구 후 재처리 도착 | 10분 내 | **판정 대상 없음** | 부재 |

### 401의 원인 — 🔴 **AU-3 시크릿 드리프트가 원복되지 않았다** (2026-08-05 정정)

같은 401 지문이 오늘 **04:52:23Z**(= [au-3/round-5.md](../au-3/round-5.md) 주입 시각)부터
찍히기 시작했고 07:12의 트리거도 같은 지문으로 거절됐다.

**"낡은 토큰을 재사용했다"는 첫 판단은 `chaos.sh`가 반증한다.** 트리거는 매번 새로 로그인한다:

```bash
measure_CH_1() { token && t1 "CH1-$PHASE"; ... }      # 트리거 직전 로그인
token() { TOKEN=$(curl -s -X POST "$BASE/auth/login" ... | jq -r '.accessToken // empty'); }
```

`token`이 실패하면 `&&`에서 끊겨 POST 자체가 나가지 않는다. **POST가 나갔다는 것이 곧
로그인 성공(= auth가 그 순간 새 토큰을 발급)의 증거**이고, content는 **그 새 토큰**을
서명 단계에서 거절했다.

**로그가 검증자 쪽 불일치임을 이중으로 못박는다** — 06:40:53~55의 같은 스윕:

| 서비스 | 같은 초의 판정 |
|---|---|
| **auth-service** | `JWT 만료 exp=Sat Aug 01 17:29:20 KST 2026` · 06:40:54.933 `userId=3` FCM 등록 **성공(INFO)** |
| **content-service** | 전부 `JWT 서명 검증 실패 — 위조 또는 시크릿 불일치` |

**만료 판정이 나오려면 서명 검증이 먼저 통과해야 한다.** auth는 그 키를 갖고 있고 content는
없다 → **content의 `JWT_SECRET`이 아직 chaos 값**이다.

**지금도 그렇다** — 이 조사 이후 **07:31:40~07:37:55에 댓글 POST 24건이 10초 간격으로 전부 401**,
그리고 **04:52:23Z 이후 content에 인증 성공 요청이 0건**이다.

**원복이 어디서 끊겼나** — `chaos.sh`에 실패 지점이 그대로 있다:

```bash
AU3_BK=/tmp/content-secret.backup.yaml
revert_AU_3() { [ -s "$AU3_BK" ] || { log "[중단] 백업 파일 없음 — 수동 복구 필요"; return 1; } ... }
```

백업이 **고정 경로 `/tmp`** 이고 없으면 원복이 중단된다. 더 나쁜 것은 그다음이다 —
원복 실패 상태에서 재주입하면 `inject_AU_3`가 **이미 드리프트된 시크릿을 백업으로 덮어써서**
이후의 원복은 *"chaos 값을 복원"* 하게 된다. **한 번 놓치면 자력 복구가 불가능한 구조다.**

## 3. 채점 불가 판정과, 그 안에서 관측된 것

### 판정: 채점 불가 — 주입 사슬 불성립 (앵커 결함 아님)

앵커 CH-1의 만점 요건은 *"Mongo 다운 → 컨슈머 실패 → 재시도 소진 → **DLQ 적재**"*(1)),
*"**DLQ producer span을 한 트레이스로 연결**"*(2)), *"**DLQ 경유 재처리로 10분 내 도착**"*(4)),
*"**DLQ 적재분 처리 방침**"*(6))이다. **네 요건의 대상이 이번 창에 부재**하므로 점수를 매기면
없는 사실을 요구하는 채점이 된다. §1.1에 따라 **점수를 만들지 않는다.**

**앵커 부적합(유형 A·B·C)과 다르다.** 앵커는 문언 그대로 유효하고, 깨진 것은 하네스다.
[AU-3 회차 2](../au-3/round-2.md)(하네스 크래시로 주입 0회 → 0점 등재)와도 다르다 —
거기서는 **조사가 돌지 않았고**, 여기서는 조사가 완주했고 장애도 실재했다.
그래서 **0점 등재도 하지 않는다**(에이전트를 잰 값이 아니고, 잰 값이 0도 아니다).
§8.1 평균·인용 집계에서 뺀다.

### 그럼에도: 에이전트가 실제 전개를 맞혔다 (정성 기록 · 점수 아님)

리포트 1순위가 **이번 창에서 실제로 일어난 그것**이다.

> **content-service의 댓글 작성 API가 JWT 서명 검증 실패로 401 반환 → 댓글 자체가 생성되지
> 않아 알림 트리거가 발생하지 않음**

그리고 Mongo를 2순위로 올린 뒤 **자기 손으로 인과를 끊었다**:

| 반증 | 리포트 원문 |
|---|---|
| 지연을 겪은 것이 알림 경로가 아님 | *"Mongo 타임아웃을 겪은 스팬은 **전부 액추에이터 헬스체크**다. 수집된 트레이스 20건이 `Health contributor …(mongo) took 30001ms` WARN의 traceId와 1:1로 일치… **알림 발송·댓글 처리 스팬은 단 하나도 없다**"* |
| 적체가 없었음 | *"`kafka_consumergroup_lag`이 notification·notification-processors·DLQ까지 **전 구간 0** — 밀린 게 아니라 **애초에 들어온 게 없다**"* |
| 창 길이 대비 설명력 | *"제보는 '최근 1시간', Mongo 장애는 **5분 15초**. 나머지 시간대는 설명하지 못한다"* |

**이것이 [AE-06](../findings/ae-06-rca-v0-au4-blind-eval.md)(앵커가 틀리고 에이전트가 맞은 사례)의
두 번째 유형이다** — 그때는 앵커가 틀렸고, 이번엔 **주입이 앵커대로 전개되지 않았는데
에이전트가 전개를 그대로 읽었다.** 앵커의 정답(Mongo → DLQ)을 그대로 답했다면 오답이었다.

**단 이것을 점수로 환산하지 않는다.** 채점은 박제된 앵커와만 대조하는데(§1.1),
이 전개를 재는 앵커는 존재하지 않는다. *"맞혔으니 100"* 은 자유 대조이고 그 회차는 무효다.

**약점도 같이 남긴다** — 확신도를 *"중간"* 으로 낮춘 사유가 `401 rate` 메트릭 결측이었고
(B-13 **여섯 회차 연속** 실패), *"성공한 댓글 POST 로그가 하나도 없다"* 를 **자기 후보를
약화시키는 방향으로** 읽었다. 실제로는 창 안 사용자 트래픽이 그 2건이 전부였으므로(실측 ④)
그 유보는 과했다.

## 5. 수집 실패 — B-13 **여섯 회차 연속**

```
Metric 'sum(rate(http_server_requests_seconds_count{application="content-service", status="401"}[1m]))'
returned no series in this window; skipped.
```

🔴 **이번엔 이 결측이 실제로 판단을 깎았다.** 창 안에 401이 **2건 실재**했는데 메트릭 시리즈가
없어 에이전트가 *"401이 전체 댓글 요청의 몇 %인지 확인 불가"* 로 1순위 확신도를 **중간**으로
낮췄다. 회차 3·4에서는 무해한 결측이었다(*"무트래픽이니 시리즈가 없는 게 맞다"* — [B-29](../round-4/README.md)).
**이번 사례가 그 진단을 부분 반증한다** — 트래픽이 있어도 시리즈가 없다.

1. 🔴 **주입 게이트에 "트리거 성공 확인"을 넣는다.** `chaos.sh`가 트리거 응답 코드를 확인하지
   않아, **장애는 정상 주입됐는데 문항이 성립하지 않은** 첫 사례가 나왔다.
   트리거가 2xx가 아니면 그 회차는 실행 전에 중단해야 한다.
   (AP-3 SoT 미커밋 · AP-2 앵커 부재에 이어 **게이트 누락 세 번째**다.)
2. 🔴 **AU-3 원복을 먼저 끝낸다 — 지금 클러스터가 드리프트 상태다.**
   **이걸 안 하면 인증이 필요한 모든 문항(CH-1·AP-1·AP-2·AP-3·AU-4·IN-*)이 조용히 무효가 된다.**

   ```bash
   # ⓪ 진단 — 두 시크릿을 나란히 본다 (master 노드, kubectl 되는 곳)
   kubectl -n default get secret auth-secret    -o jsonpath='{.data.JWT_SECRET}' | base64 -d; echo
   kubectl -n default get secret content-secret -o jsonpath='{.data.JWT_SECRET}' | base64 -d; echo
   #   content 쪽이 'Y2hhb3MtYXUzLWRyaWZ0…'(= base64 "chaos-au3-drift-not-a-real-secret-0000000000")면 드리프트 확정

   # ⓐ 백업이 살아 있고 값이 정상이면 스크립트로 한 번에
   grep -o 'JWT_SECRET: .*' /tmp/content-secret.backup.yaml   # 위 auth 값과 같아야 한다(다르면 ⓐ 쓰지 말 것)
   ./chaos.sh AU-3 off

   # ⓑ 백업이 없거나 오염됐으면 auth 값을 직접 복사한다 (이쪽이 안전한 기본)
   S=$(kubectl -n default get secret auth-secret -o jsonpath='{.data.JWT_SECRET}' | base64 -d)
   kubectl -n default patch secret content-secret -p "{\"stringData\":{\"JWT_SECRET\":\"$S\"}}"
   kubectl -n default rollout restart deploy/content-service
   kubectl -n default rollout status  deploy/content-service

   # ⓒ 확인 — 200이어야 한다
   T=$(curl -s -X POST https://yogurtte.com/api/auth/login -H 'Content-Type: application/json' \
        -d '{"email":"'"$EMAIL"'","password":"'"$PASSWORD"'"}' | jq -r .accessToken)
   curl -s -o /dev/null -w '%{http_code}\n' https://yogurtte.com/api/content/feeds/following -H "Authorization: Bearer $T"
   ```

   **chat-service도 같은 `JwtParser` 코드를 쓴다** — AU-3는 content만 패치하므로 정상일 것이나,
   ⓪에서 `chat` 시크릿도 함께 대조해 두면 다음 회차에서 같은 사고를 한 번 더 겪지 않는다.
   **원복 후에는 `/tmp/content-secret.backup.yaml`을 지운다** — 남아 있으면 다음 주입이
   그것을 "정상값"으로 오인할 여지가 있다.
3. 🔴 **`revert_AU_3`의 백업 구조를 고친다** — 백업이 고정 경로 `/tmp/content-secret.backup.yaml`
