## 4) 성능 · 비용 최적화 : 컨텍스트를 줄이되, 근거는 버리지 않았다

### 문제와 원인

회차를 거듭할수록 조사 한 번에 드는 토큰이 급격히 늘었습니다. 측정해 보니 입력 토큰의 98%가 분석 단계에 몰려 있었고, 그 대부분이 로그와 트레이스였습니다.

처음에는 "필요 이상으로 넓은 시간 범위를 조회해서"라고 판단하고 조회 범위를 좁혔습니다. 하지만 로그 크기는 전혀 줄지 않았습니다(0.0%). 추적해 보니 범위가 아니라 **조회 상한**이 크기를 정하고 있었습니다. 로그 조회가 쿼리당 1,000줄에서 끊기는데, 범위 안에 1,000줄 넘는 로그가 있으면 범위를 아무리 좁혀도 항상 1,000줄이 들어옵니다. 게다가 그 1,000줄이 실제로는 106초 분량밖에 안 돼서, 장애가 복구되는 시점의 로그는 통째로 잘려 있었습니다.

이 실패로 질문을 바꿨습니다. **"얼마나 가져올까"가 아니라 "가져온 것 중 무엇이 실제 판단에 쓰이는가"** 를 물었습니다.

### 해결 0 — 조사 구조부터 나눴습니다 : 넓게 볼 때는 요약으로, 원본은 좁힌 창에만

사용자가 "최근 1시간 안에 로그인이 느렸어요"처럼 물으면 조사 창은 60분입니다. 이 60분 전체를 원본 데이터(트레이스 전문 · 로그 · 메트릭)로 LLM에 실으면 컨텍스트가 창 크기를 따라 커집니다. 그래서 조사를 두 단계로 나누고, 단계마다 데이터를 보는 해상도를 다르게 설계했습니다.

- **탐색 단계** — 넓은 창 전체를 집계 쿼리 7회로만 훑습니다. 에러 발생률 · 지연 · 메트릭 변화 같은 요약 수치로 장애 사건 후보를 만들고, 탐색 LLM은 그중 조사할 사건을 **고르기만** 합니다. 분석 창은 LLM이 추정하지 않고 선택된 사건의 신호 구간에서 코드가 계산합니다(→ 본문 2)
- **분석 단계** — 선택된 사건의 좁힌 창에만 원본 데이터를 싣습니다

이 구조 덕에 원본 데이터가 실리는 범위가 "사용자가 말한 창"이 아니라 "장애가 실제로 있었던 구간"으로 한정됩니다. 실측으로 전체 입력 토큰 중 탐색 몫은 2%입니다 — 넓은 창은 싸게 훑고, 비싼 해상도는 좁힌 구간에만 씁니다.

탐색 단계 자체도 같은 원칙으로 줄였습니다. 처음에는 탐색 LLM이 후보를 고를 근거로 집계 원본 JSON까지 실었는데, 이것이 탐색 컨텍스트의 94%를 차지했습니다. 저장된 탐색 데이터를 원본 있음/없음 두 갈래로 재생해 **원본 없이도 후보 선택과 기각이 같게 나오는 것을 확인한 뒤** 요약만 싣도록 바꿨고, 탐색 컨텍스트가 82.8% 줄었습니다.

남는 문제는 98%를 차지하는 분석 단계였고, 아래가 그 이야기입니다.

### 해결 1 — 자를 것을 고르지 않고, 쓰인 것을 셌습니다

감으로 자를 대상을 고르는 대신 두 가지를 각각 세어 비교했습니다.

- **얼마나 실리는가** — 분석에 들어가는 로그 1,000줄을 종류별로 집계. 스택 트레이스의 라이브러리 내부 호출 줄이 전체의 71%, 실제 서비스 코드를 가리키는 줄은 3.7%
- **실제로 쓰이는가** — 지금까지의 RCA 리포트 44건이 어떤 줄을 근거로 인용했는지 집계. 서비스 코드 줄은 32회, 라이브러리 줄은 **0회**

**가장 많은 자리를 차지하는 정보가 한 번도 쓰이지 않았고, 가장 적은 자리의 정보가 가장 많이 쓰였습니다.** 그래서 로그를 통째로 자르는 대신, 쓰인 적 없는 라이브러리 호출 줄만 `… 4 frames` 같은 한 줄로 접었습니다. 원인 판단에 쓰이는 서비스 코드 · 예외 메시지 · 수치는 원문 그대로 두었습니다.

반복 로그도 같은 원칙으로 처리했습니다. 완전히 같은 로그가 반복되면 한 건만 남기고 "몇 회 · 어느 시간대 · 평균 몇 초 간격"이라는 통계로 바꿨습니다. 숫자만 다른 반복은 그 숫자 자체가 근거일 수 있어, 처음과 마지막 발생만은 원문으로 남겼습니다.

경계선도 측정이 정했습니다. 인용 2위가 뜻밖에 외부 라이브러리(분산 락)의 줄이었는데, "서비스 코드만 남긴다"는 규칙대로면 이 근거가 잘립니다. 그래서 서비스 코드와 맞닿은 줄은 외부 라이브러리라도 함께 남기도록 규칙을 고쳤습니다.

### 해결 2 — 트레이스 : 40.6%를 지울 수 있었지만, 지우지 않았습니다

트레이스도 같은 방식으로 쟀고, 결과도 로그와 같은 모양이었습니다. 리포트가 근거로 쓰는 것은 소요 시간(577회)과 상태 코드(119회)였고, 호스트 IP나 커넥션 풀 이름 같은 인프라 정보는 한 번도 인용되지 않았습니다. 로그와 같은 처방 — "안 쓰이는 값을 지운다" — 을 적용하면 40.6%가 줄어드는 것까지 확인했습니다.

**그런데 지우기 전에 하나를 더 물었습니다. "이 값은 원래 쓸모가 없는 것인가, 아니면 쓸 일이 아직 안 생긴 것인가?"** 같은 인용 0회인데 답이 반대였습니다.

- 로그의 라이브러리 줄 — 어떤 장애가 나든 원인 근거가 되는 것은 서비스 코드 줄입니다. **앞으로도 쓰일 일이 없으니** 접어도 됩니다
- 트레이스의 호스트 IP — 지금은 서버가 한 대라 모든 값이 같아 쓸 일이 없을 뿐입니다. 서버가 여러 대가 되는 순간 **"여러 대 중 한 대만 느리다"를 가려낼 유일한 단서**가 됩니다. 지우면 그날 장애 분석이 막힙니다

그래서 트레이스는 값을 하나도 지우지 않고 **적는 방법만** 바꿔 30.0%를 줄였습니다. 값 하나를 여러 겹으로 감싼 JSON 포장을 벗겨 한 줄로 적고, 1,992개 span에 똑같이 반복되는 값은 맨 위에 한 번만 적었습니다. 값이 하나라도 달라지면 자동으로 span마다 따로 남는 구조라, 서버가 늘어나는 날 코드를 고치지 않아도 필요한 값이 그대로 있습니다. span도 한 개도 빼지 않았습니다 — "이 호출이 없다"는 **부재 자체**가 원인 근거인 장애 유형이 있기 때문입니다.

**즉 40.6% 대신 30.0%를 선택한 것입니다.** 절감률을 조금 포기하고, 미래의 장애에서 근거가 사라지지 않는 쪽을 택했습니다.

### 해결 3 — 압축이 역효과를 내는 경우를 잡아 안전장치를 달았습니다

측정 중에 접었더니 오히려 커지는 반례가 두 번 나왔습니다. 로그와 모양이 같은 메트릭 집계 응답을 반복 로그로 오인해 접었다가 표식이 원문보다 길어졌고(+9.8%), 접을 것이 거의 없는 작은 응답에서는 "접었다"는 안내문이 절약분보다 컸습니다(+6.0%). 그래서 **접은 결과가 실제로 더 짧을 때만 적용**하는 안전장치를 넣었습니다. 비교는 바이트로 합니다 — 한글은 한 글자가 3바이트라 글자 수로 재면 줄었다고 판정해 놓고 실제로는 커질 수 있기 때문입니다. 적용 후 원본 112건 중 커진 응답은 0건입니다.

### 결과 (1차)

| 개선 | 결과 | 검증 |
|---|---|---|
| 로그 컨텍스트 | 57.0% 감소 (스택 많은 응답은 최대 83%) | 원본 112건 전수 |
| 트레이스 컨텍스트 | 30.0% 감소 (지운 값 0개, span 손실 0건) | 트레이스 238건 · 1,992 span 전수 |
| 압축 후 커진 응답 | 0건 | 안전장치 재검증 |

원본 데이터는 손대지 않고 분석 직전 조립 단계에서만 접었습니다. 압축을 끄면 이전과 바이트 단위로 같은 결과가 나오게 만들어, 전후 비교가 언제든 가능합니다.

### 2차 — 컨텍스트 크기를 정하는 것은 조회 범위가 아니라 채널별 규칙이었습니다

이후 회차에서 이상한 현상이 나왔습니다. 조사 범위를 65% 좁혔는데 컨텍스트가 오히려 20.8% 늘었습니다. 채널별로 쪼개 보니 이유가 보였습니다.

| 채널 | 범위를 65% 좁히자 | 크기를 정하는 것 |
|---|---|---|
| 메트릭 | −48% | 조회 범위 (유일하게 따라감) |
| 로그 | 0% | 사건의 크기 (스택 하나면 범위와 무관) |
| 트레이스 | **+77%** | **수집 건수 상한** (범위를 좁혀도 상한만큼 채움) |

**조회 범위는 컨텍스트를 조절하는 손잡이가 아니었습니다.** 가장 커진 트레이스 채널을 파고들었습니다.

- 조사 범위 안의 트레이스를 직접 세어 보니 **470건 중 96%가 노이즈**였습니다 — 계측 결함으로 생긴, 내용이 span 1개뿐인 빈 트레이스가 최신순 수집에 걸려 자리를 채우고 있었습니다
- 수집된 트레이스 10건과 리포트 인용을 대조하니, 정답 · 정상 대조군 2건 외에 **상한을 채우던 8건은 인용 0회**였습니다

노이즈를 거르는 쿼리를 넣자 예상(−19KB)과 반대로 +130.8% 늘었습니다. 노이즈가 빠진 자리를 훨씬 큰 실제 요청이 채웠기 때문입니다. 이 실측이 결론을 정해 줬습니다 — **후보를 더 잘 채우는 게 아니라, 인용되지 않는 공급 자체를 없애는 것이 답**이었습니다. 상한을 채우는 수집을 폐지했습니다. 또 정상-실패 비교용으로 가져오는 정상 트레이스는 실패와 달리 끝까지 완주해서 뒷단 span이 많다는 것을 확인하고, 비교에 실제로 쓰이는 앞부분 경로만 남기고 접었습니다.

그 결과 같은 조건에서 분석 컨텍스트 토큰이 10.6% 줄었고, 원인 판정과 점수는 그대로였습니다. 반대로 출력은 43% 늘었는데, 정상 대조군이 생기면서 이전 리포트에는 0회였던 "정상은 되는데 실패는 안 된다" 비교 논증이 6회 쓰인 결과입니다. **판단에 쓰이지 않는 입력은 줄이고, 판단의 근거가 되는 출력은 늘렸습니다.**

## 꼬리질문 방어

**Q. 1,000줄이나 온 건 필터가 너무 넓었던 것 아닌가? INFO까지 다 긁은 것 아닌가?**

- INFO는 안 들어간다. 분석용 조회의 라인 필터는 `ERROR|WARN|Exception|Caused by|\.java:[0-9]+\)` — ERROR/WARN 헤더와 **스택 프레임 줄**만 매칭한다. INFO가 포함되는 것은 지목된 traceId 조회뿐이고(DEBUG만 제외) 그쪽은 ~6KB 수준이다.
- 1,000줄을 채운 것은 스택이다. 스택 패턴은 예외 발생 위치를 컨텍스트에 도달시키려고 **일부러** 넣은 것이고(본문 3의 53→88점이 이 패턴 덕이다), 예외 1건이 ~221줄이라 같은 예외가 2초 간격으로 반복되는 장애 구간에서는 4~5건 만에 상한이 찬다. 실측: 1,000줄 중 라이브러리 프레임 903줄 · 고유 줄 191줄(중복률 81%) · 106초 소진.
- 그래서 처방이 "필터를 좁힌다"가 아니라 "접는다"였다 — 스택 도달은 점수를 만든 기능이므로 유지하고, 상한을 채우는 반복 스택 중 인용 0회인 부분만 접었다. 상한이 스택으로 차는 구조와 접기 −57%가 크게 먹힌 이유는 같은 사실의 양면이다.
- INFO는 오히려 반대 방향의 대기 항목이다. 도착·성공·복구 신호가 본질적으로 INFO라 수집 확충(B-16)이 대기 중이고, 실측상 INFO 전량은 ERROR/WARN의 약 287배(1시간 2,300줄 대 8줄)라 별도 설계가 필요해 미룬 상태다.

**Q. 스택을 도달시키려고 필터를 넓혀 놓고(B-11) 스택을 접으면(B-34) 모순 아닌가?**

- 접는 것과 남기는 것이 갈라져 있다. 접는 것은 인용 0회로 실측된 **라이브러리 내부 줄뿐**이고, B-11이 도달시킨 근거 — 앱 프레임(`…java:25`) · 예외 클래스명 · `Caused by` · 메시지 수치 — 는 전부 원문 보존이다. 앱 코드와 맞닿은 경계 프레임은 서드파티라도 ±1줄 남긴다(인용 2위 shedlock이 이 규칙으로 살아남았다).
- 접힌 자리에도 `… N frames (org.springframework, …)` 표식으로 지나간 패키지가 남고, 스위치로 끄면 바이트 단위로 복원된다. 테스트의 절반이 "접힌다"가 아니라 **"안 접힌다"(근거 줄 보존)를 고정**한다.
- 즉 B-11은 "근거를 컨텍스트에 도달시키는" 변경이고 B-34는 "도달한 것 중 쓰이지 않는 부분을 줄이는" 변경이라 층이 다르다.

**Q. 복구 시점이 잘리는 문제는 해결됐나?**

- 반만이다. 접기로 상한 도달 자체는 완화됐지만, `limit=1000 + direction=forward`가 창 뒤쪽(복구 시점)부터 자르는 구조는 남아 있다(B-39 · 대기, CH-1 감점 7점의 원인). "확인됐고 대기열에 있으며 전후 대조로 검증할 계획"까지가 정직한 답이다.

## 수치 인용 시 주의 (레포 규칙 대조)

- **"두 단계로 나눠서 N% 줄었다"고 쓰지 않는다** — 단일 LLM 구성으로 돌린 전후 A/B가 없다. 쓸 수 있는 것은 ⓐ 구조가 원본 실리는 범위를 좁힌 창으로 한정한다는 설명 ⓑ 단계별 비중 실측(탐색 2% · 분석 98%) ⓒ 탐색 원본 제외 −82.8%까지다.
- **탐색 −82.8%(원본 제외)는 저장 탐색 데이터 재생 A/B · N=1 · 창 하나**이고, 트레이스 없는 문항(CH-2·AU-2)은 미검증이다([workflow.md §7](../workflow.md)). "저장 데이터 재생으로 기각 품질 동등을 확인했다"까지만 쓴다.
- LLM이 분석 창을 잘못 좁힌 사례(CH-3)는 **2)절의 서사**다 — 4)절에서 다시 쓰면 문항이 섞이므로 "→ 본문 2" 참조로만 잇는다.
- **−10.6%는 AP-1 한 문항 · 단일 실행 값** ([토큰개선.md 단서 셋](../토큰개선.md#인용할-때-붙여야-할-단서-셋)). 입력은 재실행해도 거의 같아(4토큰 차) 인용 가능하지만, 본문에서는 "같은 조건에서"로 한정했다.
- 57.0% · 30.0%는 저장 원본(112건 · 238건) 기준이지 전체 실행 A/B가 아니다 — "원본 N건 검증" 표기 유지.
- 회차 5↔7 비교의 메트릭 −48.5%는 창 폭 차이지 도구 성과가 아니므로 **쓰지 않는다**.
- 점수는 "그대로였다"까지만 쓴다 — 점수 상승 주장은 N=2 이상만 가능(§1.1).
