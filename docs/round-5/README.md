# RCA Agent — 로그 구조 역설계로 분석 비용 절감 (실측 기반)

## 1. 문제 정의 — 어디서 비용이 발생하는가

RCA Agent의 토큰 사용량을 실제 실행 기준으로 분해했다.

| 단계 | 토큰 | 비중 |
|---|---:|---:|
| 탐색 | 5,576 | 2% |
| 분석 | 217,423 | 98% |

비용의 대부분이 분석 단계에서 발생하고 있었다.

분석 입력을 다시 분해하면 다음과 같다.

| 구성 | 크기 | 비중 |
|---|---:|---:|
| 트레이스 | 203KB | 47% |
| 로그 (ERROR/WARN) | 179KB | 42% |
| 기타 | 약 10% | |

로그가 분석 비용의 핵심 병목이었다.

---

## 2. 초기 가설과 반증

초기 접근은 단순했다.

시간 범위를 줄이면 로그도 줄어들 것이라는 가설을 세웠다.

### 실험

- Loki step: 5m → 1m
- 분석 창 길이: 약 17.6% 감소

### 결과

| 항목 | 변화 |
|---|---|
| 로그 크기 | 변화 없음 |
| 비용 | 약 3% 증가 |

### 원인

Loki 조회에는 `log-limit (1000줄)` 제한이 존재했다.

- 창 크기와 무관하게 항상 최대 1000줄이 수집됨
- 실제로 1000줄이 약 106초만 커버하는 상황 발생
- 장애 복구 시점이 로그에서 잘리는 문제 확인

이 실험을 통해 문제의 본질은 시간 범위가 아니라 로그 구조 자체임을 확인했다.

---

## 3. 접근 전환 — 공급이 아니라 수요 기준으로 판단

로그를 줄이는 대신, 실제로 사용되는 로그만 남기는 방향으로 전환했다.

이를 위해 두 가지를 직접 측정했다.

---

## 4. 공급 분석 — 실제 로그 구성

ERROR/WARN 로그 1000줄을 전수 분석했다.

| 구성 | 줄 수 | 비중 |
|---|---:|---:|
| 라이브러리 스택 프레임 | 903 | 71% |
| 애플리케이션 프레임 | 50 | 3.7% |
| 기타 로그 | 47 | 25% |

추가로 고유 로그는 191줄로, 중복률은 약 81%였다.

대부분이 라이브러리 프레임과 반복 로그로 구성되어 있었다.

---

## 5. 수요 분석 — 실제 RCA 리포트 사용 패턴

RCA 리포트 44건을 대상으로 LLM이 실제로 인용한 코드 위치를 집계했다.

- 총 인용: 32회 / 12개 클래스
- 전부 애플리케이션 코드

추가 확인 결과:

| 항목 | 인용 횟수 |
|---|---:|
| 애플리케이션 프레임 | 32 |
| 라이브러리 프레임 | 0 |
| 예외 클래스명 | 29 |

---

## 6. 핵심 인사이트

공급과 수요를 비교하면 다음과 같다.

| 요소 | 공급 비중 | 실제 사용 |
|---|---:|---:|
| 라이브러리 프레임 | 71% | 0% |
| 애플리케이션 프레임 | 3.7% | 핵심 근거 |

가장 많은 데이터를 차지하는 요소가 실제 분석에서는 사용되지 않고 있었다.

문제는 데이터 양이 아니라 정보 밀도였다.

---

## 7. 해결 전략 — 구조 재설계

### 7.1 스택트레이스 압축

- 애플리케이션 프레임은 유지
- 라이브러리 프레임은 요약 형태로 압축

```text
at com.example.Service.method(...)
… 14 frames (org.springframework, io.lettuce)
```

---

### 7.2 반복 로그 압축

동일한 로그 블록을 하나로 병합하고 통계 정보를 추가했다.

```text
[×47회 · 01:43:53 ~ 01:46:18 · 평균 2초 간격]
QueryTimeoutException ...
```

단순 제거가 아니라 발생 횟수와 시간 패턴을 명시적으로 제공하도록 구조를 변경했다.

---

## 8. 설계 기준

다음 정보는 반드시 유지하도록 했다.

- 애플리케이션 프레임 (Root Cause 추론 핵심)
- 예외 메시지 내 수치 값 (timeout, ms 등)

또한 라이브러리 프레임은 완전히 제거하지 않고 요약 형태로 유지하여, 필요 시 추가 탐색이 가능하도록 했다.

서드파티 코드라도 실제 로직 경계에 위치한 경우를 고려하여, 애플리케이션 프레임 기준 ±1 프레임은 함께 보존하도록 설계했다.

---

## 9. 검증 방법

- 단위 테스트로 규칙 고정 — **"무엇이 안 접히는지"** 를 고정한다 (앱 프레임 · 예외 메시지의
  수치 · 경계 ±1 프레임 · 스레드명). 저장된 원본을 픽스처로 쓰므로 네트워크가 필요 없다
- 저장된 원본 전수로 크기 실측 (`LogFoldMeasureTool` · `TraceCompactMeasureTool`)
- `enabled=false/true` 두 팔을 **같은 창에 고정**해 A/B — 주입 불필요. **미실행**

검증 기준: Root Cause와 근거 인용이 완전히 동일할 것 (점수 상승이 아니다)

## 11. 결론

이 작업은 로그를 줄이는 작업이 아니라, LLM이 실제로 사용하는 정보만 남도록 구조를 재설계한 작업이다.

데이터를 줄인 것이 아니라, 정보 밀도를 재구성했다.

## 12. 배운 점

- 비용 문제는 데이터 양이 아니라 정보 밀도의 문제였다
- 최적화는 추측이 아니라 실측과 반증을 기반으로 해야 한다
- 로그 시스템의 병목은 수집이 아니라 해석 단계에서 발생한다
