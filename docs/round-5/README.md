## B-33. 창을 좁혀 로그를 줄인다 — ❌ **기각 (실측으로 반증)**

**남기는 이유**: 같은 발상이 다시 나올 자리이고, **반증 과정이 진짜 원인을 찾아냈다.**

### 상황

로그 179KB가 사건과 무관하게 딸려온다고 판단했다. 확인해 보니 `Collector`는 **이미 사건별 창으로
나눠 조회**하고 있었고(겹치면 접는다), 이번 실행은 창 3개였다. 문제는 창 분할이 아니라
**LOKI 카드의 구간이 5분 단위로 부풀어 있는 것**이었다:

```
INC-8·9   01:40:00 ━━━━━━━━━━━━━━━ 01:50:00   ← Loki 집계 step 5분. 카드에도 "집계 해상도만큼 흐림"
INC-10            01:43:51 ━ 01:44:33          ← Tempo. 시각 정확
INC-11~15         01:43:57 ╸ 01:46:02
                  └── 실제 장애는 약 2분 11초 ──┘
```

그래서 **스윕 해상도를 5m → 1m**으로 올려 카드 구간을 좁히기로 했다.
`step` 하나만 바꾸면 각 점이 5분을 되돌아봐 더 번지므로 **`log-query`·메트릭 5종의 `[5m]`까지 함께** 바꿨다.

### 무엇이 일어났나

**창은 좁아졌는데 로그가 안 줄었다.**

| | 5m | 1m | |
|---|---:|---:|---:|
| 창 길이 | 1,022초 | **842초** | **−17.6%** |
| **로그 ERROR/WARN** | 179,080B | **179,070B** | **−0.0%** |
| 분석 컨텍스트 | 431,204자 | 431,138자 | −0.0% |
| 스윕 신호 | 31 | **83** | +168% |
| 후보 카드 | 15 | 18 | +20% |
| **탐색 컨텍스트** | 6,381자 | **15,538자** | **+143%** |
| **총 비용** | **$2.7001** | **$2.7813** | **+3.0%** |

**원인은 `log-limit`이다.** Loki 조회에 줄 수 상한(창당 1000줄)이 걸려 있어,
**창 안에 이미 1000줄이 넘게 있으면 창 크기와 무관하게 항상 1000줄**을 받는다.

실측이 그대로 보여준다 — **1000줄이 106초만 덮었다**(`00:43:17~00:45:03`).
그 구간의 다운은 `00:46:34`까지였으므로 **복구 시점이 통째로 잘렸다.**
CH-3 회차 3 리포트가 남긴 *"로그 수집이 09:45:03에서 잘렸다(1000줄 상한). 단절 **종료 시각은
관측되지 않았다**"* 가 같은 현상이다.

**원인 판정은 두 팔 다 Redis로 동일**해서 품질 손실은 없었다. 얻은 것이 없고 탐색만 비싸졌다.

### 현재 상태

**원복 완료** (`step: 5m`, `[5m]` 5종). 백업과 diff 0, 테스트 87건 통과.

## B-34. 🔴 스택트레이스 접기 — **이 회차의 본체**

**변경군 B.** B-33의 반증이 지목한 자리다.

### 상황

| | |
|---|---|
| 겨냥 | 분석 컨텍스트의 **42%**인 로그 절 |
| 실측 대상 | 최신 실행의 `error-warn` 응답 1000줄 / 142,841B |
| 현재 상태 | **미착수.** 완료된 것은 아래 구성 해부와 도구 조사뿐 |

### 전략을 어떻게 세웠나 — 공급이 아니라 수요에서 시작했다

*"스택트레이스는 길다"* 는 인상이지 근거가 아니다. **버릴 것을 고르지 않고, 쓰인 것을 세어
나머지를 버렸다.** 그러려면 두 번 재야 한다.

#### 측정 ① 공급 — 로그 1000줄에 무엇이 들었나

최신 실행의 `error-warn` 응답(1000줄 / 142,841B)을 패키지별로 집계했다.

```
at 프레임 패키지 상위
  org.springframework   627
  org.apache            185
  com.example            50   ← 앱 코드
  io.lettuce             42
  io.netty               21
  reactor.core           18
  jakarta.servlet        10
```

| 구분 | 줄 | 바이트 | 비중 |
|---|---:|---:|---:|
| **라이브러리 프레임** | **903** | **101,455B** | **71.0%** |
| **앱 프레임** (`com.example`) | 50 | 5,315B | **3.7%** |
| 예외 헤더 · 일반 로그 | 47 | 36,071B | 25.3% |

**고유 줄은 1000줄 중 191줄뿐이다**(중복률 81%). 다른 창에서는 **99/1000 (90.1%)** 이었다.

#### 측정 ② 수요 — 리포트 44건이 무엇을 인용했나

`analysis` 필드(LLM 산출물)만 대상으로 `클래스.메서드(File.java:NN)` 패턴을 **패키지 접두와
무관하게** 전수 집계했다. 증거 절과 섞이지 않게 json의 분석 텍스트만 봤다.

| 인용된 클래스 | 회 | | 인용된 클래스 | 회 |
|---|---:|---|---|---:|
| `FeedService` | 5 | | `UserService` | 2 |
| `RedisLockProvider` | 5 | | `FollowCondition$FollowerSearch` | 2 |
| `UserCacheStore` | 4 | | `ExpGrantService` | 2 |
| `FeedCommentService` | 3 | | `FollowRepositoryCustomImpl` | 1 |
| `FollowCondition$FollowingSearch` | 3 | | `UserController` | 1 |
| `UserNotificationService` | 3 | | `FeedCommentController` | 1 |

**총 32회 / 12개 클래스 — 전부 앱 코드다.**
**라이브러리 프레임 인용은 44건 전부에서 0회다.** 바이트의 71%를 차지하는
`LettuceExceptionConverter` · `CommandWrapper` · `ProtocolHelper` · `AbstractChannel`이
**단 한 번도 인용되지 않았다.** 예외 **클래스명**(헤더·`Caused by`)은 29회 인용됐다 — 그건 남긴다.

#### 두 측정을 겹치면 규칙이 나온다

| 구성요소 | **로그에서 차지** | **리포트가 인용** | → 처분 |
|---|---:|---:|---|
| **라이브러리 프레임** | **71.0%** (903줄) | **0회** | **접는다** |
| **앱 프레임** | 3.7% (50줄) | **32회** | **전부 남긴다** |
| 예외 헤더 · `Caused by` | ~5% | 29회 | 전부 남긴다 |
| 일반 로그 본문 | 25.3% | — | 남긴다 (반복만 접음) |
| (중복 블록) | 고유 191/1000 | — | `×N회`로 접는다 |

**71%를 공급하는데 수요가 0이고, 3.7%를 공급하는데 수요가 32회다.**
정보 밀도가 정확히 뒤집혀 있고, 이 한 줄이 전략의 전부다.

IN-1 회차 3의 최고 근거가 바로 그 3.7%였다:

> `UserCacheStore.getCachedValue(:49) → ExternalUserInfoService.lambda$getUserInfos$2(:108)
>  → FeedService.toListView(:138)`

이 세 줄로 *"유저 1명당 2초 직렬 반복"* 을 특정하고 **지연 = 4초 × 고유 유저 수**를 세웠다.

#### 수요 집계가 규칙을 하나 고쳤다 — 패키지 접두만으로는 안 된다

인용 공동 2위가 **`RedisLockProvider`(5회)** 인데 `net.javacrumbs.shedlock…` **서드파티**다.
앱이 직접 호출하는 지점이라 실질 앱 프레임인데, `app-packages: com.example` 접두 규칙만
쓰면 **잘려나간다.**

→ **`app-packages` + 앱 프레임 경계 ±1 프레임 보존**으로 간다.
Sentry도 같은 문제를 `stack.package` 매처 + `+app`/`-app` 액션으로 푼다.

### 기존 도구를 먼저 찾았다 — 셋 다 다른 자리를 겨냥한다

| 도구 | 무엇을 하나 | 왜 안 쓰나 |
|---|---|---|
| [**drain-java**](https://github.com/bric3/drain-java) (Drain3의 Java 포트, Java 11+) | **미지의** 로그 포맷에서 템플릿을 스트리밍 마이닝. 원 Python 대비 약 10배 빠름 | 우리 문제는 *"템플릿을 모른다"* 가 아니다. **Java 스택트레이스 문법은 이미 고정**이고 파싱 규칙을 안다. 게다가 Drain은 **줄 단위** 클러스터링이라 *"예외 헤더 + 프레임 N줄 = 한 블록"* 이라는 구조를 잃는다 |
| [**Sentry의 `in_app` 프레임**](https://docs.sentry.io/concepts/data-management/event-grouping/stack-trace-rules/) | 프레임을 앱/시스템으로 가르고 **앱 프레임으로만 그룹핑**. `stack.module`·`stack.package` 매처 + `+app`/`-app` 액션 | **개념을 그대로 채택한다.** 다만 SaaS 제품 규칙이라 코드로 가져올 것은 없다 |
| [**logstash-logback-encoder `ShortenedThrowableConverter`**](https://github.com/logfellow/logstash-logback-encoder/blob/main/src/main/java/net/logstash/logback/stacktrace/ShortenedThrowableConverter.java) | `maxDepthPerThrowable` · `maxLength` · `excludes` 정규식으로 스택을 줄여 **출력** | **생산자 측**(앱)에서 돈다. 우리는 Loki에서 **이미 렌더된 텍스트**를 받는다. 앱을 고치면 **변경군 A**라 관측 대상 자체가 바뀌어 baseline이 깨진다 |

**결론: 직접 구현한다.** 텍스트 후처리이고 문법이 고정이라 정규식 수준이면 된다.
다만 **파라미터 설계는 `ShortenedThrowableConverter`를, 프레임 구분은 Sentry의 `in_app`을 그대로 빌린다.**

### 회차 5에서 바꿀 것

**① 변경 표**

**접기는 두 방향이다 — 세로(프레임)와 가로(반복).**

| 층위 | 무엇을 |
|---|---|
| 구조 개선 | **① 프레임 접기(세로)** — `at` 프레임을 앱/라이브러리로 가르고 라이브러리는 한 줄로 접는다. **앱 프레임 + 그 경계 ±1은 전부 남긴다** |
| 구조 개선 | **② 반복 접기(가로)** — 같은 지문의 블록을 1건으로 접고 `×N회 · 첫 시각 ~ 끝 시각 · 평균 간격`을 붙인다 |
| 위치 | `analyzer` 패키지, `LokiLogDedup` 옆. **어셈블 단계에서만** 접는다 — `reports/raw/`는 채점자 감사 자료라 손대지 않는다 (B-10이 세운 제약) |
| 설정 | `rca.collect.log-fold.app-packages` (기본 `com.example`) · `.enabled` (기본 on, 대조군 스위치) |

**②는 정보를 빼는 게 아니라 더한다.** 지금은 모델이 원문을 세어서 *"2초 간격"* 을 알아내는데,
세어서 주면 더 정확하고 싸다. IN-1 회차 3이 실제로 그 계산을 손으로 했다.

접은 결과는 이런 모양이다:

**②의 `×47회`는 정보를 빼는 게 아니라 더한다.** 지금은 모델이 원문을 세어서 *"2초 간격"* 을

**② 절대 잃으면 안 되는 것 — 실측으로 확정된 두 가지**

| **예외 메시지의 상수** | *"Command timed out after **2 second(s)**"* · *"Remaining time: **29999 ms**"* — [round-4 C-4](../round-4/README.md)가 통째로 이 값들 위에 서 있다 |

→ **메시지의 숫자를 정규화하지 않는다.** 지문 판정은 **정확 일치**로 한다.
고유 줄이 191/1000, 99/1000인 것을 보면 정확 일치만으로 충분하다.
(Drain류 템플릿 마이닝이 하는 *"숫자를 `<*>`로 치환"* 이 여기서는 **독이다.**)

**③ 검증 설계 — 한 번에 하나만**

1. **단위 테스트 먼저.** 저장된 `reports/raw/*-loki-error-warn*.json`을 입력으로 고정하고
   접기 전후 바이트·앱 프레임 보존·상수 보존을 assert한다. **네트워크 불필요**
2. `enabled=false/true` 두 팔을 **같은 창 고정**으로 A/B (B-32와 같은 방법, 주입 불필요)
3. 성공 기준: **1순위 원인과 근거 인용이 같을 것.** 점수보다 이것이 먼저다
4. 통과하면 **남은 예산으로 `log-limit`을 올린다** — 접기의 진짜 이득은 크기가 아니라 **커버 구간**이다

**④ 반증 조건**

- 접었더니 1순위 원인이나 근거가 달라지면, **어느 줄이 필요했는지 역추적**해 접기 규칙에서 뺀다
- ~~라이브러리 프레임이 실제로 인용된 적이 있는지 먼저 확인할 것~~
  → ✅ **해소됨.** 리포트 **44건 전수**로 확인: 프레임 인용 32회 전부 앱 코드, **라이브러리 0회**.
  이 항목이 접기의 최대 리스크였고, 이제 규칙을 공격적으로 가도 된다
- 접은 뒤 로그 절이 절반 아래로 안 내려가면 원인은 프레임이 아니라 **일반 로그 본문**(36,071B)이다
- **인용 집계는 과거 회차 기준이다** — 라이브러리 프레임이 근거가 되는 문항이 앞으로 나올 수 있다.
  그래서 접힌 자리에 `… 14 frames (org.springframework, io.lettuce)`처럼 **무엇이 접혔는지 표식을
  남긴다.** 모델이 "더 필요하다"고 판단할 수 있어야 하고, 대조군 스위치도 그래서 남긴다

**⑤ 현재 상태** — **미착수.** 완료된 것은 다음 셋이다:

| | 결과 |
|---|---|
| 공급 측정 | 라이브러리 프레임 **71.0%** · 앱 프레임 3.7% · 고유 줄 191/1000 |
| **수요 측정 (리포트 44건 전수)** | 프레임 인용 **32회 전부 앱 코드 · 라이브러리 0회** · 예외 클래스명 29회 |
| 도구 조사 | drain-java · Sentry `in_app` · logstash-logback-encoder — 셋 다 다른 자리를 겨냥 |

**예상치는 예상치일 뿐이다**: 로그 절 142,841B → 약 40,000B, 분석 컨텍스트 −23% 수준.
코드는 한 줄도 안 썼다.
