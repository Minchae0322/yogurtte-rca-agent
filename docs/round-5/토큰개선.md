# 분석 컨텍스트 토큰 절감 — 데이터를 줄인 것이 아니라 정보 밀도를 재구성했다



RCA 에이전트의 **2회차 대비 급증한 토큰 사용량**을 개선하기 위해 단계별 비용을 분석한 결과, 전체 토큰의 98%가 분석 단계에 집중되어 있었고 특히 로그와 트레이스가 대부분의 컨텍스트를 차지하고 있음을 확인했습니다. 단순히 데이터를 줄이는 대신, **기존 RCA 리포트에서 실제로 어떤 정보가 근거로 사용되었는지를 역추적하여 공급 데이터와 실제 수요를 비교**했습니다. 로그에서는 라이브러리 프레임이 전체의 71%를 차지했지만 실제 리포트에서는 한 번도 인용되지 않은 반면, 3.7%에 불과한 애플리케이션 프레임은 반복적으로 원인 근거로 사용되고 있음을 확인했습니다. 이를 바탕으로 라이브러리 프레임·ANSI·중복 식별자·반복 로그는 선택적으로 접고, 애플리케이션 프레임과 예외 메시지·수치는 원문을 보존했습니다. 트레이스는 로그처럼 데이터를 삭제하는 방식으로 줄이지 않았습니다. 지금 사용하지 않는 정보라도 **서버가 여러 대로 늘어나면 장애 원인을 찾는 데 필요할 수 있기 때문입니다.** 그래서 트레이스 데이터 자체는 그대로 유지하면서, 반복해서 들어가는 정보나 불필요하게 길게 표현된 부분만 더 짧은 형태로 바꿨습니다. 그 결과 로그는 323만 B에서 139만 B로 **57.0%**, 트레이스는 186만 B에서 131만 B로 **30.0%** 줄였습니다. 또한 원본 데이터는 그대로 보관하고, 데이터를 줄인 뒤에도 **기존과 동일한 장애 원인과 근거를 확인할 수 있는지 검증할 수 있도록 구성했습니다.**



> 로그는 **쓰인 적 없는 것을 접어** -57.0%, 트레이스는 **아무것도 버리지 않고 표기만 바꿔** -30.0%.
> 같은 방법(공급을 세고 수요를 센다)에서 처방이 갈린 이유가 이 문서의 본체다.

## 문제

RCA 에이전트의 토큰을 단계별로 분해하면 **비용이 한쪽에 몰려 있습니다.**

| 단계 | 컨텍스트 토큰 | 비중 |
|---|---:|---:|
| 탐색 | 5,576 | 2% |
| **분석** | **217,423** | **98%** |

분석 입력 431,204자를 다시 분해하면 다음과 같습니다.

| 절 | 크기 | 무엇이 크기를 정하나 |
|---|---:|---|
| 트레이스 16건 | 203,488B (47%) | traceId — 사건이 좁혀준다 |
| **로그 ERROR/WARN** | **179,080B (42%)** | **줄 수 상한(1000줄)** — 사건과 무관하다 |
| 로그 traceId 일치 | 22,996B (5%) | 같음 |
| 메트릭 9종 | 요약 후 적재 | 고정 목록 |

트레이스는 조사 대상이 정해지면 크기도 정해지지만, 로그는 **상한이 정해준 만큼** 들어옵니다.
줄이려면 로그부터입니다.

---

## 1. 첫 가설은 틀렸습니다 — 창을 좁혀도 로그는 안 줄었습니다

로그가 사건과 무관하게 딸려온다고 판단해 **조회 창을 좁혔습니다.**
Loki 스윕 해상도를 5분에서 1분으로 올리고, 카드 구간을 만드는 `[5m]` lookback 5종도 함께 바꿨습니다.

```text
창 길이   1,022초 ─────────▶ 842초   (-17.6%)
로그      179,080B ────────▶ 179,070B (-0.0%)
비용      $2.7001 ─────────▶ $2.7813  (+3.0%)
```

**창은 좁아졌는데 로그가 그대로였습니다.** 원인은 `log-limit`이었습니다.

```text
창을 아무리 좁혀도
├─ Loki 조회는 창당 1000줄에서 끊긴다
└─ 창 안에 1000줄이 넘게 있으면 항상 1000줄이 온다

실측: 1000줄이 106초만 덮었다 (00:43:17 ~ 00:45:03)
      그 구간의 장애는 00:46:34까지였다 → 복구 시점이 통째로 잘렸다
```

원인 판정은 두 팔 모두 Redis로 같았으므로 품질 손실은 없었지만, **얻은 것도 없었습니다.**
이 반증이 문제를 다시 정의했습니다 — **양이 아니라 밀도입니다.**

## 2. 버릴 것을 고르지 않고, 쓰인 것을 셌습니다

*"스택트레이스는 길다"* 는 인상이지 근거가 아닙니다. 그래서 두 번 쟀습니다.

### 공급 — 로그 1000줄에 무엇이 들었나

`error-warn` 응답 1000줄(142,841B)을 패키지별로 전수 집계했습니다.

| 구분 | 줄 | 바이트 | 비중 |
|---|---:|---:|---:|
| **라이브러리 프레임** | 903 | 101,455B | **71.0%** |
| 앱 프레임 (`com.example`) | 50 | 5,315B | 3.7% |
| 예외 헤더 · 일반 로그 | 47 | 36,071B | 25.3% |

고유 줄은 1000줄 중 **191줄**이었습니다(중복률 81%). 다른 창에서는 99/1000(90.1%)이었습니다.

### 수요 — RCA 리포트 44건이 무엇을 인용했나

저장된 리포트의 `analysis` 필드(LLM 산출물)만 대상으로 `클래스.메서드(File.java:NN)` 패턴을
패키지 접두와 무관하게 전수 집계했습니다.

| 인용 대상 | 횟수 |
|---|---:|
| **앱 프레임** | **32회 / 12개 클래스** |
| **라이브러리 프레임** | **0회** |
| 예외 클래스명 (`Caused by` 포함) | 29회 |

### 두 측정을 겹치면 규칙이 나옵니다

```text
              공급(바이트)        수요(인용)
라이브러리 프레임  ████████████ 71%      0회      → 접는다
앱 프레임         ▌ 3.7%              32회      → 전부 남긴다
예외 헤더·메시지   ██ 5%               29회      → 전부 남긴다
```

**71%를 공급하는 쪽의 수요가 0이고, 3.7%를 공급하는 쪽의 수요가 32회입니다.**
정보 밀도가 정확히 뒤집혀 있었고, 이 한 줄이 설계의 전부입니다.

IN-1 회차 3의 최고 근거가 바로 그 3.7%였습니다.

```text
UserCacheStore.getCachedValue(:49)
  → ExternalUserInfoService.lambda$getUserInfos$2(:108)
  → FeedService.toListView(:138)
```

이 세 줄로 *"유저 1명당 2초 직렬 반복"* 을 특정하고 **지연 = 4초 × 고유 유저 수**를 셌습니다.

## 3. 접는 방향을 셋으로 나눴습니다

```text
                    Loki 원본 (reports/raw — 손대지 않는다)
                              │
                      ContextAssembler
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ① 세로 접기      ② 줄 안 잡음      ③ 가로 접기
      라이브러리 프레임    ANSI·중복 id      반복 블록
              │               │               │
              └───────────────┼───────────────┘
                              ▼
                        분석 컨텍스트
```

### ① 세로 — 라이브러리 프레임 접기

```text
before                                    after
java.lang.NullPointerException            java.lang.NullPointerException
  at com.example…FollowCondition:25         at com.example…FollowCondition:25
  at com.example…FollowRepository:35        at com.example…FollowRepository:35
  at org.springframework.aop.AopUtils:352   at org.springframework.aop.AopUtils:352
  at org.springframework…Reflective:196     … 3 frames (org.springframework, reactor.core)
  at org.springframework…CglibAop:720       at net.javacrumbs.shedlock…Advisor:74
  at reactor.core…MonoFlatMap:158           at com.example…ExpGrantService:88
  at net.javacrumbs.shedlock…Advisor:74     …
  at com.example…ExpGrantService:88
```

**앱 프레임 경계 ±1 프레임을 함께 남깁니다.** 인용 공동 2위가 `RedisLockProvider`(5회)인데
`net.javacrumbs.shedlock…` 서드파티였습니다 — 앱이 직접 호출하는 경계라 실질 앱 프레임인데,
접두 목록(`com.example`)만 쓰면 잘려나갑니다. Sentry가 같은 문제를 `in_app` 프레임으로 푸는 방식을
개념만 빌렸습니다.

### ② 줄 안 — 정보량이 0인 것

한 줄을 그대로 펼치면 실제 메시지는 뒤쪽 일부입니다.

```text
\e[2m2026-08-03T23:25:45\e[0;39m \e[33m WARN [traceId=6a70a4cb…,spanId=fcf6a78d…]\e[0;39m
  \e[2m--- [chat-service] [ntainer#5-1-C-1] [6a70a4cb…-fcf6a78d…] \e[0;39m
  \e[36mc.e.t.app.config.KafkaConsumerConfig    \e[0;39m : [config] 처리 실패 1회차: …
  └── 색코드 ── 서비스명 ── 같은 id 두 번째 ── 정렬 공백 ──┘
```

전체 로그 바이트에서 재보면 다음과 같았습니다.

| 뺀 것 | 비중 | 왜 안전한가 |
|---|---:|---|
| ANSI 색코드 | 4.0% | 터미널 색 지정. 정보량 0 |
| 두 번째 `traceId-spanId` | 2.4% | 같은 줄 앞의 `[traceId=…,spanId=…]`에 그대로 있다 |
| `--- [service]` | 1.1% | 스트림 라벨 `service_name`과 같은 값이다 |
| 로거명 정렬 공백 | 0.3% | 3칸 이상만 줄인다 |

**스레드명은 남깁니다** — `[reactor-http-epoll-1]`처럼 스레드가 곧 근거인 문항이 있습니다(AU-4).

### ③ 가로 — 반복 블록

```text
[x47회 · 01:43:53.163 ~ 01:46:18.503 UTC · 평균 2.0초 간격 · 글자까지 같아 한 벌만 싣는다]
org.springframework.dao.QueryTimeoutException: Redis command timed out
  …
```

**횟수와 시각 범위는 정보를 빼는 것이 아니라 더하는 것입니다.** 지금은 모델이 원문을 세어
*"2초 간격"* 을 알아냅니다 — IN-1 회차 3이 실제로 손으로 셌습니다. 세어서 주면 더 정확하고 쌉니다.

숫자만 다른 근사 반복(카프카 재시도 WARN 405줄 등)은 **첫 벌과 끝 벌을 원문 그대로 싣고
가운데만** 접습니다.

```text
처리 실패 1회차 … Remaining time: 29999 ms   ← 원문
[x5회 … 숫자만 다른 반복이라 첫 벌과 끝 벌만 싣는다]
처리 실패 5회차 … Remaining time: 29995 ms   ← 원문
```

값이 근거인 문항에서 **양 끝을 잃지 않기 위해서**입니다. Drain류 템플릿 마이닝이 하는
*"숫자를 `<*>`로 치환"* 은 여기서는 독입니다 — 회차 4의 근거가
`Command timed out after 2 second(s)` · `Remaining time: 29999 ms` 같은 상수 위에 서 있습니다.
숫자는 **반복을 판정할 때만** 무시하고, 실리는 텍스트는 언제나 원문입니다.

## 4. 실측 결과

저장된 Loki 원본 응답 **112건 전수**에 대해, 어셈블 단계 출력의 UTF-8 바이트를 규칙별로 쌓아
가며 쟀습니다.

| | 바이트 | 누적 감소 |
|---|---:|---:|
| 접기 전 | 3,237,421 | — |
| + ① 프레임 접기 | 1,855,161 | **-42.7%** |
| + ② 줄 안 잡음 | 1,596,446 | -50.7% |
| + ③ 반복 접기 | **1,390,968** | **-57.0%** |

규칙별 기여도는 **프레임 -42.7% · 잡음 -13.9% · 근사반복 -12.9%** (각각 직전 상태 대비)입니다.

대표적인 개별 응답:

| 원본 | 접기 전 | 접기 후 | |
|---|---:|---:|---:|
| `loki-error-warn.json` (스택 다수) | 218,203B | 36,604B | **-83.2%** |
| `loki-error-warn.json` (다른 창) | 216,825B | 36,277B | **-83.3%** |
| `loki-trace-id.json` (스택 없음) | 61,256B | 45,584B | -25.6% |
| `loki-survey-error-rate.json` (집계) | 4,434B | 4,434B | 0.0% |

**스택이 많은 응답일수록 크게 줄고, 스택이 없는 응답은 잡음 제거분만 줄어듭니다.**
이 분포 자체가 규칙이 의도한 자리에서만 작동한다는 근거입니다.

## 5. 반례 둘이 규칙을 고쳤습니다

측정 도중 **접었더니 커진** 경우가 두 번 나왔고, 둘 다 가드로 막았습니다.

**(1) 메트릭 응답을 로그로 읽었습니다 — +9.8%**

Loki 집계 응답(`matrix`)은 로그(`streams`)와 같은 `values` 배열 모양인데 내용이
`[ts, "4"]` 같은 집계값입니다. 줄로 읽으니 같은 값이 반복이라며 접혔고, 표식이 길어
오히려 커졌습니다. → `resultType == "streams"` 일 때만 접습니다.

**(2) 안내문이 절약분보다 컸습니다 — +6.0%**

접었다는 사실을 알리는 안내문 한 줄에도 값이 듭니다. 접을 것이 거의 없는 작은 응답에서는
안내문이 절약분을 넘겼습니다(6,104B → 6,468B). → **접은 쪽이 실제로 더 짧을 때만 접습니다.**
바이트로 비교합니다 — 한글은 글자당 3바이트라 글자 수로 재면 줄었다고 판정하고도 커집니다(+2.3%).

가드를 넣은 뒤 **112건 중 커진 응답은 0건**입니다.

## 6. 잃지 않는다는 것을 어떻게 고정했나

접기의 위험은 크기가 아니라 **근거 손실**이므로, 테스트의 절반은 *"접힌다"* 가 아니라
*"안 접힌다"* 를 고정합니다.

| 고정한 것 | 근거 |
|---|---|
| 앱 프레임 전부 남는다 | IN-1 회차 3이 그 세 줄로 원인 기전을 특정했다 |
| 앱 프레임 경계 ±1은 서드파티라도 남는다 | 인용 2위 `RedisLockProvider`가 shedlock이다 |
| 예외 클래스명·`Caused by` 남는다 | 인용 29회 |
| 메시지의 수치는 원문 그대로 | `2 second(s)` · `29999 ms` 위에 회차 4 근거가 서 있다 |
| 홀로 있는 라이브러리 프레임은 안 접는다 | 표식으로 바뀔 뿐 이득 없이 문맥만 잃는다 |
| 스레드명은 남는다 | `[reactor-http-epoll-1]`이 근거인 문항(AU-4) |
| 끄면 **바이트 단위로** 접기 이전과 같다 | 대조군 팔이 같아야 토큰 축 비교가 성립한다 |
| 깨진 JSON이면 원문을 그대로 돌려준다 | 접기는 최적화다 — 데이터 손실이 더 나쁘다 |

원본은 건드리지 않습니다. 접기는 **어셈블 단계에서만** 일어나고 `reports/raw/`는 그대로입니다 —
채점자가 *"이 신호가 실제로 도달했는가"* 를 감사하는 자료이기 때문입니다.

```text
Loki ──▶ RawResponseStore ──▶ reports/raw/   (원본 · 감사용 · 불변)
              │
              └────────────▶ ContextAssembler ──▶ 접힌 컨텍스트 ──▶ LLM
```

대조군 스위치는 세 층 모두에 남겼습니다.

```yaml
rca.collect.log-fold:
  enabled: true            # 전체 끄기 — 끄면 접기 이전과 바이트 단위로 같다
  app-packages: com.example
  min-run: 2               # 접을 최소 연속 프레임 수
  strip-line-noise: true   # ② 줄 안 잡음
  near-repeat-min: 3       # ③ 근사 반복 (0 = 끄기)
```

## 7. 트레이스 — 같은 방법으로 쟀고, 결론은 반대였습니다

로그를 접고 나면 남는 것은 트레이스입니다(컨텍스트의 47%, 203,488B). 같은 방법으로 두 번 쟀습니다.

### 공급 — span 하나가 935B인데 절반이 포장지였습니다

| 무엇 | 비중 | 정체 |
|---|---:|---|
| OTLP 속성 래퍼 | **17.9%** | `{"key":"status","value":{"stringValue":"200"}}` ← 실제 정보는 `"status":"200"` |
| resource 블록 반복 | 10.3% | k8s 파드명·노드명·호스트명·OS가 배치마다 통째로 |
| base64 traceId/spanId | 9.3% | `"amdu29B6S5ZtAzMOMY72HQ=="` 가 span마다 |
| `net.host.ip` | 6.2% | span 1,992개 전부에 붙음 |
| `jdbc.datasource.driver`·`pool` | 7.7% | 커넥션 span마다 같은 값 |

### 수요 — 리포트 36건이 인용한 것

```text
많이 인용             전혀 인용 안 함 (0회)
duration/ms  577회    net.host.ip · jdbc.datasource.driver/pool · net.transport
status       119회    k8s.pod.name · node.name · host.name · os.type
error         36회    base64 id · parentSpanId
uri           30회
outcome       28회
exception     26회
```

로그와 **같은 역전**입니다. 그래서 처음에는 로그와 같은 처방 — *"인용 0회 속성을 제외 목록에
넣는다"* — 을 세웠고, 그러면 -40.6%까지 갔습니다.

### 그 처방을 폐기한 이유 — 파드가 하나라는 가정에 기대고 있었습니다

`net.host.ip`는 인용 0회에 바이트의 6.2%라 가장 먼저 지울 후보였습니다. 그런데 그 값이
**언제 필요해지는지**를 생각하면 판단이 뒤집힙니다.

```text
레플리카 1개 → IP는 어차피 하나       → 인용될 이유가 없다
레플리카 N개 → "5개 파드 중 하나만 느리다"를 가르는 유일한 값이 된다
```

즉 **인용 0회는 "쓸모없다"가 아니라 "아직 그 상황이 안 왔다"** 였습니다. 실제로 데이터를 보면
지금은 앞쪽 상황입니다 — 트레이스 238건 중 한 서비스가 IP 두 개로 나타난 트레이스가 **0건**
(파드명 해시가 다른 것은 동시 레플리카가 아니라 재배포였습니다). 제외 목록으로 얻는 -40.6%는
**"지금 파드가 1개"라는 조건에 의존하는 절감**이었습니다.

### 그래서 지우는 대신 옮겼습니다

```text
before — span 1,992개 전부에 반복
  span 1: { "net.host.ip":"10.42.1.43", "jdbc.datasource.pool":"HikariPool-1", … }
  span 2: { "net.host.ip":"10.42.1.43", "jdbc.datasource.pool":"HikariPool-1", … }

after — 값이 하나뿐일 때만 위로 한 번
  commonSpanAttributes: { "net.host.ip":"10.42.1.43", "jdbc.datasource.pool":"HikariPool-1" }
  span 1: { … 값이 갈리는 것만 … }
```

**판단을 코드가 아니라 데이터에 맡기는 구조입니다.** 값이 하나뿐이면 올라가고(반복만 사라짐),
하나라도 갈리면 올라가지 않고 span마다 남습니다 — 파드가 늘어나는 순간 자동으로 그렇게 됩니다.

### 시간값은 손대지 않았습니다

성능 회차 간 비교와 로그·메트릭 시각 대조의 기준점이라, **시작 시각은 절대값(나노초) 그대로**
둡니다. 바꾼 것은 끝 시각뿐이고 그것도 버리는 게 아니라 소요시간으로 옮깁니다.

```jsonc
"startTimeUnixNano": "1785163483856936000"   // 그대로
"endTimeUnixNano":   "1785163484031205000"   →  "durNs": 174269000
```

`시작 + 소요 = 끝`이라 정보량은 같고, 나노초 정수라 **반올림도 없습니다**. 지금은 모델이 19자리
숫자 두 개를 빼서 duration을 구하는데, 그 계산이 사라집니다.

span id를 8자 hex로 줄이는 안도 검토했지만 **기여가 -0.8%p뿐이라 폐기했습니다** — 위험 대비
이득이 없습니다.

### 실측

| | 트레이스 JSON | 감소 |
|---|---:|---:|
| 원본 (238건 · span 1,992개) | 1,863,242B | — |
| ① OTLP 래퍼 평탄화 + 빈 `status:{}` 생략 | 1,389,928B | **-25.4%** |
| ② + 끝 시각 → `durNs` | 1,344,099B | -27.9% |
| ③ + 배치 공통 속성 호이스팅 (237개) | **1,305,152B** | **-30.0%** |

표기가 바뀐 것을 알리는 안내문까지 넣은 **절 전체로는 -21.2%** 이고, 커진 절은 **0건**입니다.

**세 규칙 모두 값을 하나도 버리지 않습니다.** 그래서 이 압축에는 "무엇을 지울지" 설정이 아예
없고 켜고 끄는 스위치만 있습니다.

### 왜 요약하지 않았나

회차 5 문서는 트레이스를 뒤로 미루면서 이렇게 적었습니다 — *"가장 크지만 가장 위험하다.
AU-2류의 **span이 없다**가 요건인 문항에서 부재 근거가 죽는다."*

```text
요약    span 16개 → 상위 5개만 싣기      ← 부재 근거가 죽는다. 위험한 것은 이쪽
재인코딩 span 16개 → span 16개 (포장지만)  ← 부재 근거 그대로
```

**span은 한 개도 빼지 않았습니다.** 그래서 *"auth 호출 span이 없다"* · *"정상 트레이스와 다르다"*
같은 근거가 그대로 남습니다. 위험한 것은 트레이스를 건드리는 것 자체가 아니라 **고르는 것**이었습니다.

### 남겨 둔 것

같은 이름·속성의 span이 3벌 이상 반복되는 구간이 **16.8%** 더 있습니다(`query` 153벌,
`result-set` 109벌). 로그처럼 첫 벌·끝 벌 + `x153회 · 합계 4,830ms · 최대 62ms`로 접을 수
있지만, **지연 문항의 근거가 그 반복 자체**입니다(IN-1의 *"유저 1명당 2초 직렬 반복"*).
위험도가 다르니 같은 회차에 섞지 않습니다 — 섞으면 점수가 움직여도 무엇 때문인지 증명할 수 없습니다.

## 8. 현재 상태 — 무엇이 측정됐고 무엇이 아직인가

**측정된 것**

| | 결과 |
|---|---|
| 로그 공급 측정 | 라이브러리 프레임 71.0% · 앱 프레임 3.7% · 고유 줄 191/1000 |
| 로그 수요 측정 (리포트 44건 전수) | 앱 프레임 인용 32회 · 라이브러리 0회 · 예외 클래스명 29회 |
| **로그 접기 (원본 112건 전수)** | **3,237,421B → 1,390,968B (-57.0%)**, 스택 많은 응답 -83.3% |
| 트레이스 공급·수요 측정 | 래퍼 17.9% · resource 10.3% · id 9.3% / duration 인용 577회, 인프라 속성 0회 |
| **트레이스 압축 (원본 238건 전수)** | **1,863,242B → 1,305,152B (-30.0%)**, 절 전체 -21.2% · 커진 절 0건 |
| 회귀 | 테스트 112건 통과 (도구 4건 skip) |

**아직 측정되지 않은 것 — 여기를 넘겨 말하지 않습니다**

- **전체 실행은 아직 한 번도 돌지 않았습니다.** 위 수치는 저장된 원본을 어셈블 단계에 통과시킨
  것이지, 접기·압축을 켠 채 조사를 완주한 결과가 아닙니다.
- **분석 컨텍스트 전체의 절감률은 산술 추정입니다.** 로그 47% · 트레이스 47%에 각각의 실측
  비율을 적용하면 컨텍스트가 절반 가까이 빠집니다. 실측은 다음 조사에서 나옵니다.

  ```text
  431,204자  →  로그 접기 후 약 277K (-36%)  →  트레이스 압축까지 약 234K (-46%)
  ```
- **점수 효과는 미측정입니다.** 성공 기준은 점수 상승이 아니라 **1순위 원인과 근거 인용이
  이전과 같을 것** 이고, `enabled=false/true` 두 팔을 같은 창에 고정해 대조합니다(주입 불필요).
  로그와 트레이스는 **한 회차에 하나씩** 켭니다 — 같이 켜면 무엇이 점수를 움직였는지 갈리지 않습니다.
- **인용 집계는 과거 회차 기준입니다.** 라이브러리 프레임이 근거가 되는 문항이 앞으로 나올 수
  있어, 접힌 자리에 `… 14 frames (org.springframework, io.lettuce)` 표식을 남겼고 스위치도 남겼습니다.

**반증 조건** — 접었더니 1순위 원인이나 근거 인용이 달라지면, 어느 줄이 필요했는지 역추적해
규칙에서 뺍니다. 로그 절이 절반 아래로 안 내려가면 범인은 프레임이 아니라 일반 로그 본문이고,
트레이스에서 모델이 `durNs`를 잘못 읽으면(지연 수치가 리포트에서 어긋나면) 끝 시각을 되돌립니다.

## 9. 결론 — 같은 방법, 다른 처방

두 채널에 같은 방법(공급을 세고 수요를 센다)을 썼는데 **처방은 반대로 나왔습니다.**

```text
로그   무엇이 쓰이나 → 쓰인 적 없는 것을 접는다        3,237,421B → 1,390,968B  (-57.0%)
        ├─ 라이브러리 프레임 71% → … N frames (표식은 남김)
        ├─ 색코드·중복 id 7.8%  → 제거
        ├─ 반복 블록            → [xN회 · 시각 범위 · 평균 간격]  ← 통계로 승격
        └─ 앱 프레임·예외 메시지 → 수치까지 원문 보존

트레이스 무엇이 쓰이나 → 아무것도 안 버리고 표기만 바꾼다  1,863,242B → 1,305,152B  (-30.0%)
        ├─ OTLP 래퍼           → "key":"value" 로 평탄화
        ├─ 끝 시각             → durNs (시작 시각은 절대값 그대로)
        └─ 값이 하나뿐인 속성   → commonSpanAttributes 로 한 번만
```

**갈린 지점은 "인용 0회"를 어떻게 읽느냐였습니다.** 로그의 라이브러리 프레임은 *스택 문법상
언제나 라이브러리*라 앞으로도 인용될 이유가 없지만, 트레이스의 파드 IP는 *레플리카가 늘면*
곧바로 근거가 됩니다. 같은 "0회"인데 뜻이 달랐습니다.

## 배운 것

- **비용 문제는 데이터 양이 아니라 정보 밀도의 문제였습니다.** 창을 좁히는 첫 시도는 -0.0%였고,
  그 반증이 진짜 원인(`log-limit`)을 찾아냈습니다.
- **버릴 것을 고르기 전에 쓰인 것을 세야 합니다.** 인상으로 골랐다면 라이브러리 프레임을
  전부 지웠을 것이고, 그러면 shedlock 경계 프레임을 잃었을 것입니다.
- **"지금 안 쓰인다"와 "앞으로도 안 쓰인다"는 다릅니다.** 트레이스에서는 그 구분 때문에
  -40.6%짜리 제외 목록을 버리고 -30.0%짜리 호이스팅을 택했습니다. 후자는 파드가 늘어도
  코드를 고칠 필요가 없습니다.
- **최적화는 커질 수도 있습니다.** 접기가 오히려 키운 사례가 로그에서 둘(집계 응답 +9.8%,
  작은 절 +6.0%), 트레이스에서 하나(작은 트레이스 24건) 나왔고, 재보고 짧은 쪽을 고르는
  가드가 없었다면 그대로 나갔을 것입니다.

# 10. 창을 좁혀 봤습니다 — 창은 좁아졌고, 토큰은 안 줄었습니다 (2026-08-11)

앞의 §1~9는 **실린 것을 어떻게 접을까**였습니다. 이 절은 반대쪽 — **애초에 덜 싣게
범위를 좁히면 어떤가**입니다. 결과부터 적으면 **창은 32% 좁아졌는데 분석 토큰은
0.0% 움직였고**, 그 반증이 진짜 병목을 찾아냈습니다.

## 10.1 문제 — 3분짜리 장애의 조사 창이 25분이었습니다

IN-2(Kafka 브로커 다운)를 종단으로 돌려 창을 분해했습니다. 실제 장애는
`04:47:25~04:50:22` **3분**인데 조사 창은 **25분**이었습니다.

```
실제 장애                    04:47:25 ─ 04:50:22        3분

INC-7  댓글 POST (Tempo)     04:48:35 ─ 04:49:35        1분   ← 정확하다
INC-6  content ERR (Loki)    04:45 ──────── 04:55      10분
INC-5  up (Mimir)            04:44:55 ────────── 04:59:55  15분  ★
                             └──── 신호 합집합 15분 ────┘
                           + pad ±5분 × 2 = 10분
                             └──────── 25분 ────────┘
```

**정확한 신호(1분)가 있는데도 흐린 신호가 창을 지배합니다.** 원인이 둘로 갈렸습니다.

**① 5분 샘플이 3분을 15분으로 부풉니다.** 값 변화 신호는 *"앞 샘플 ~ 뒤 샘플"* 이 구간입니다 —
언제 꺾였는지 모르니 그 5분을 통째로 표시합니다. 그게 셋 물리면 15분입니다.

```
04:44:55 ●1   04:49:55 ●0   04:54:55 ●0   04:59:55 ●1
     └─ 1→0 ─┘    └ 0이었다 ┘    └─ 0→1 ─┘
       5분           5분           5분        = 15분
```

**② 로그 버킷도 같은 일을 합니다.** 5분 버킷으로는 `04:50 370건 · 04:55 51건`이라
10분처럼 보이는데, 1분 해상도로 다시 보니 **4분에 몰려 있었습니다.**

```
step 5m   content   04:50 ▉370      04:55 ▉51                    10분처럼 보인다
step 1m   content   04:48 ▉119  04:49 ▉124  04:50 ▉127  04:51 ▉51
                    └────────── 실제로는 4분 ──────────┘
```

Kafka 다운 구간과 초 단위로 맞습니다. **5분 버킷이 4분을 10분으로 뭉갠 것**입니다.

## 10.2 고친 것 — step과 range와 pad를 같이 내렸습니다

**셋이 같은 전제에서 나와야 합니다.** 하나만 바꾸면 조용히 어긋납니다.

| 층 | 전 | 후 | 안 바꾸면 |
|---|---|---|---|
| `survey.step` | 5m | **1m** | — |
| 쿼리 range (7군데) | `[5m]` | **`[1m]`** | 값은 "직전 5분"인데 `Signal.from`은 1분만 당겨져 **구간이 실제보다 좁게 표시된다** |
| `incident-pad-bucket` | 5m 상수 | **`step × 2`** | 신호만 좁아지고 pad는 옛 전제로 남아 **창의 59%가 여유**가 된다 |

`Signal`의 `lookback`은 `survey.step`에서 파생되므로 자동으로 따라옵니다.

### pad를 줄여도 되는 이유가 생겼습니다

pad가 5분이던 원래 근거는 **CH-3에서 창이 주입 1초 전에 끊겨 세 회차 연속 4점**이던
사고입니다. 그런데 그때는 **모델이 창을 직접 써냈습니다** — 어디서 끊길지 알 수 없으니
여유를 크게 줄 수밖에 없었습니다.

지금은 코드가 신호 시각에서 계산합니다. **pad가 덮어야 하는 것은 샘플 사이 불확실성
하나**이고, 그것은 정확히 `step`만큼입니다. 앞뒤로 버킷 하나씩이면 `step × 2`입니다.

```java
// 상수를 없앤 것이 요점입니다 — step 을 되돌리든 더 내리든 자동으로 맞습니다
padBucket = stepDuration().multipliedBy(2)   // 1m → 2분 · 5m → 10분
```

## 10.3 실측 — 창은 좁아졌는데 토큰이 안 줄었습니다

같은 창(IN-2 `04:04:55~05:04:55Z`)을 두 팔로 종단 실행했습니다.

| 항목 | step 5m | step 1m | 변화 |
|---|---:|---:|---:|
| **조사 창** | 25분 | **17분** | **−32%** |
| 후보 수 | 8 | 12 | +50% |
| 탐색 컨텍스트 | 3,943자 | 7,433자 | **+88.5%** |
| 탐색 `in` | 34,077 | 36,407 | +6.8% |
| **분석 컨텍스트** | 98,027자 | **98,023자** | **−0.0%** |
| ├ 로그 ERROR/WARN | 151,209B | 151,200B | **−0.0%** |
| ├ 트레이스 | 67,872B | 67,872B | 0.0% |
| └ 메트릭 | 159,914B | 113,317B | −29.1% |
| 분석 `in` | 84,398 | 84,417 | 0.0% |
| 비용(추정) | $0.8553 | $0.8681 | **+1.5%** |

**창이 32% 좁아졌는데 로그가 0.0% 움직였습니다.** 이유는 하나였습니다.

```
log-limit = 1000  (쿼리당)
25분 창도 1,000줄,  17분 창도 1,000줄   →  바이트가 같다
```

**151KB는 창 폭이 아니라 상한이 만든 값이었습니다.** 창을 줄여도 상한 아래로 내려가야
비로소 줄어듭니다. 메트릭 원본은 −29.1%로 줄었지만 `metric-summary=true`라 요약해서
싣기 때문에 컨텍스트에는 거의 반영되지 않았습니다.

**즉 이 변경만 놓고 보면 순손실입니다** — 탐색 컨텍스트 +88.5%, 총비용 +1.5%.

## 10.4 그래도 되돌리지 않는 이유

**창이 좁아진 것 자체는 성공했고, 그 값은 다른 곳에서 쓰입니다.**

메트릭 신호가 실제로 정확해졌습니다.

```
step 5m   up 04:44:55 ──────────── 04:59:55   15분
step 1m   up 04:46:55 ──── 04:51:55            5분   ← 실제 장애 3분에 근접
          kafka_brokers    04:47:55 ─ 04:51:55  4분
          lag              04:47:55 ─ 04:50:55  3분  ← 거의 정확
```

**후보 목록에 적히는 시각이 곧 리포트의 근거 시각**이므로, 이 정확도는 채점의
2) 근거·4) 영향 판정에 직접 걸립니다. 토큰이 아니라 **판정 품질** 쪽 개선입니다.

그리고 남은 낭비가 어디인지가 드러났습니다.

```
step 5m   신호 15분 + pad 10분 = 25분     ← 신호가 문제였다
step 1m   신호  7분 + pad  4분 = 11분급   ← 이제 신호가 실제 폭에 가깝다
                                            (실측 17분은 로그 신호가 04:54까지 실제로 이어져서다)
```

## 10.5 반증 조건 검증 — CH-3

pad 축소의 위험은 하나였습니다: **정답이 창 밖으로 나가는 것.** CH-3로 확인했습니다 —
23초 장애에 신호가 얇아 pad가 실제로 일하는 문항입니다.

| | 창 | 폭 |
|---|---|---:|
| 회차 5 (step 5m · pad 5m) | 00:37:41 ~ 01:00:00 | 22분 |
| 지금 (step 1m · pad 2m) | 00:37:41 ~ **01:03:00** | **25분** |

**줄지 않았고 오히려 늘었습니다.** 후보를 5개에서 6개로 더 골랐고, 신호 자체가
`00:39~01:01`에 실제로 흩어져 있었기 때문입니다(반복 버벅임 문항이라 신호가 원래 넓습니다).

```
INC-2  댓글 POST 515,150ms   00:39:41 ~ 00:48:16   ← 8분 30초짜리 span 하나
INC-9  filterchain          00:53:42 ~ 00:53:58
```

**pad 축소가 후보 선택이나 창 계산을 무너뜨리지 않는다는 것까지 확인됐습니다.**
다만 이 실행은 *"pad를 줄여도 안전한가"* 를 봤을 뿐, **CH-3의 원래 주입(05:22:01)을 덮는지는
검증하지 않았습니다** — 창이 다른 회차 것입니다.

두 문항을 나란히 놓으면 pad 개선이 어디서 먹히는지가 분명합니다.

| | IN-2 | CH-3 |
|---|---|---|
| 신호 합집합 | 7분 | 22분 |
| pad 몫 | 10분 → **창의 59%** | 4분 → 창의 16% |
| pad 축소 효과 | **크다** | 거의 없다 |

**짧은 장애 + 흐린 신호에서만 먹힙니다.** 신호가 실제로 넓으면 창도 넓은 것이 맞습니다.

## 10.6 다음 — 병목은 `log-limit`입니다

이 절의 산출물은 절감이 아니라 **진단**입니다.

| | |
|---|---|
| 확인됨 | 조사 창 −32% · 메트릭 신호가 실제 폭에 근접 · pad 축소가 안전 |
| 반증됨 | *"창을 줄이면 분석 토큰이 준다"* — 로그가 **−0.0%** |
| **드러남** | 분석 컨텍스트 최대 몫(151KB)은 **창이 아니라 `log-limit = 1000`이 정한다** |
| 대가 | 탐색 컨텍스트 +88.5% · 총비용 +1.5% |

§1~9에서 로그를 **접어서** −57.0%를 얻었는데, 그 위에 남은 151KB는 **상한이 만든 바닥**입니다.
다음 후보는 셋입니다 — ⓐ `log-limit`을 낮춘다(정보 손실 위험) ⓑ 창별 분할 조회에서
창마다 1,000이 아니라 **총량**으로 상한을 건다 ⓒ 접기를 더 공격적으로.

**어느 것도 아직 재지 않았습니다.**
