## 🔴 왜 재현됐나 — AU-4와 정반대이고, 그 이유가 중요하다

| | AU-4 | **AP-2** |
|---|---|---|
| 두 실행의 총점 | **75 ↔ ~100 (25점 차)** | **53 ↔ 53 (0점 차)** |
| 정답 신호가 | **도달했다** (client span · fallback 로그) | **도달하지 못한다** — NPE 스택이 라인 필터에 잘린다([결함 3](../round-3/README.md)) |
| 실행 간 차이를 만든 것 | 받은 신호를 **쓰느냐 마느냐** | — (쓸 신호가 없다) |

**가설: 도구가 막은 문항은 편차가 0이고, 신호가 도달한 문항은 편차가 크다.**

에이전트는 이번에도 자기가 막힌 지점을 정확히 알고 있었다 —
*"로그에 **예외 클래스·스택트레이스·요청 URI·HTTP 상태코드가 전혀 없음**"*,
그리고 조치 1로 **정확한 우회 쿼리**를 냈다:

```
{service_name="auth-service"} |= "6a69bf80068eadb430b349f4a5a18a81"    ← 레벨 필터 없이
→ handleAllException이 삼킨 예외 클래스·스택트레이스·요청 URI 확보
```

**이 조치는 회차 2에서도 나왔다.** 두 실행이 독립적으로 같은 우회로를 제안했다는 것은,
**막힌 지점이 에이전트에게 명확하고 재현적**이라는 뜻이다 — [B-11](../round-3/README.md)의 근거가 하나 더 늘었다.

> ### ⚠️ §8.1의 해석을 하나 바꿔야 한다
>
> 지금까지 *"편차 ±10 초과 = 문항 불안정 = 인용 보류"* 로만 읽어 왔다.
> **그 역은 성립하지 않는다** — 편차 0이 곧 "이 점수가 능력을 정확히 잰다"가 아니다.
> AP-2의 53은 **도구가 만든 천장**이고, 천장에 눌린 값은 분산이 없다.
>
> **편차와 함께 "천장에 닿았는가"를 같이 기록해야 한다.** 그 판정 근거는
> *"정답 신호가 컨텍스트에 도달했는가"* 이고, 채점자가 직접 쿼리해 확인할 수 있다.

## ⚠️ 조건 차이 1건 — 창에 AP-1이 섞였다

**회차 2와 완전히 같지는 않다.** 이번 창에는 AP-2 주입 93초 전(08:51:47Z)에
**AP-1 주입이 만든 500 트레이스**가 있었다.

| | 회차 2 (07-28) | 2차 실행 (07-29) |
|---|---|---|
| 창 안 에러 트레이스 | **0건** | **1건** — `http post /feeds/{feedId}/comments`(AP-1) |
| 탐색 대상 | `auth-service` 단독 | `auth-service` + **`content-service`** |

**그런데 점수에 영향이 없었다** — 에이전트가 AP-1을 **명시적으로 배제**했기 때문이다:

> *"content-service의 500 에러는 무관. `Data truncation: Data too long for column 'content'`
> … 댓글 **작성(POST)** 요청이고 원인이 입력 길이 초과로 명확하다.
> 팔로우 목록 **조회**와 연결할 근거 없음."*

**이것은 결함 15(Incident 구분 불가)에 대한 반례가 아니라 경계 사례다.**
CH-2에서는 스윕 후보가 전부 다른 Incident 것이라 **분석이 끌려갔고**,
여기서는 후보가 1건뿐이고 traceId를 안 골라서 **분석이 로그로 갔다.**
→ **traceId를 고르지 않은 것이 오히려 오염을 막았다.**
