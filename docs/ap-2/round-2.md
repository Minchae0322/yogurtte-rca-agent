## 🔴 세 번째 결함 — 라인 필터가 스택트레이스를 잘라낸다

**회차 1이 세운 델타 가설은 결함이 둘이라고 봤다.** 실측 결과 셋이다.

| | 결함 | 회차 2에서 | |
|---|---|---|---|
| B-1 | 셀렉터 `{app=~"content\|auth\|chat"}` | ✅ **고쳐졌다** — `service_name` / `*-service`로 로그가 들어옴 | |
| B-2 | `\| logfmt \| level=~` (평문 Logback) | ✅ **고쳐졌다** — 라인 필터 `\|~ "ERROR\|WARN"`로 4줄 확보 | |
| **B-?** | **라인 필터 자체가 예외 본문을 배제한다** | 🔴 **미인지 · 미수정** | **신규** |

**채점자 실측** (조사 후, `{service_name="auth-service"}` 15:35:30~15:36:45Z):

```
# 라인 필터 없이 — 나온다
java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because "this.size" is null
    at com.example.toyauth.app.user.controller.dto.FollowCondition$FollowingSearch.limit(FollowCondition.java:25)
    at com.example.toyauth.app.user.controller.dto.FollowCondition$FollowerSearch.limit(FollowCondition.java:45)

# 에이전트가 실제로 쓴 쿼리 — 0줄
{service_name="auth-service"} |~ `ERROR|WARN` |= `NullPointer`   →   lines: 0
```

**원인**: Logback이 스택트레이스를 **줄마다 별개 Loki 엔트리**로 보내는데, 그 줄들에는
`ERROR`·`WARN` 문자열이 없다. 라인 필터는 헤더 줄(`... WARN ... handleAllException`)만 통과시키고
**예외 타입·메시지·스택 전부를 버린다.** 그리고 이 앱의 `handleAllException` 헤더 줄에는
메서드명 말고 아무 정보가 없다 — 에이전트가 *"예외 클래스/메시지/요청 URI/응답 코드가
로그에 전혀 남아있지 않아 5xx 단정이 불가합니다"* 라고 쓴 그대로다.

> **AP-1 회차 2에서 이 결함이 안 드러난 이유**: 거기서는 예외 정보가 **헤더 줄 자체에**
> 있었다(`SQL Error: 1406, SQLState: 22001` / `Data truncation: Data too long...`).
> **"로그가 들어온다"와 "예외를 읽을 수 있다"는 다른 문제**인데, 한 문항만으로는 갈리지 않았다.

**수정 방향**: 예외 문맥을 잡으려면 라인 필터가 아니라 ① traceId 단위 전량 조회
(에이전트가 조치 1로 제안한 바로 그것) 또는 ② `... |~ "ERROR|WARN|Exception|\\tat "` 같은
스택 포함 패턴이 필요하다. **①이 정확하다** — ②는 무관한 스택까지 끌어온다.

## 🔴 네 번째 결함 — 탐색이 traceId를 안 넘기면 **트레이스 증거가 통째로 사라진다**

에이전트의 후보 3은 *"로그에는 traceId가 찍히는데 Tempo 트레이스가 0건 → **샘플링 설정 또는
OTLP export 파이프라인 결함** 가능성"* 이라고 썼다.

**채점자 실측으로 반증됐다 — 트레이스는 Tempo에 멀쩡히 있다.**

```
GET /api/traces/6a68cc475f93de92df7ee7e4f4819181
  span=http get /user/{userid}/following    svc=auth-service  status=UNSET
  span=security filterchain before / secured request / security filterchain after
  total spans: 4                                    ← 6a68cc47…3ec5 는 /followers, 동일 구조
```

**에이전트가 못 본 이유는 유실이 아니라 도구 경로다.**

1. 탐색 스윕은 Tempo를 **`{ status = error }`로만** 검색한다. 이 트레이스들은 `status=UNSET`이라 안 잡힌다 (= 앵커가 말한 `exception=none`).
2. `Scope`에 traceId가 없으니 심층 수집이 **Tempo 조회를 통째로 건너뛴다** (리포트 `trace: 0B / 0 spans`, `tempo 0ms`).

**결과가 뼈아프다.** 에이전트가 *"판단 불가"* 로 명시한 첫 항목이
**"팔로우 목록 엔드포인트를 어느 서비스가 소유하는지 주어지지 않았습니다"** 인데,
그 답(`http get /user/{userid}/following`, `auth-service`)이 **Tempo에 있었다.**
스팬 이름 하나만 있었으면 원인 적중이 20에서 더 올라갔을 개연성이 크다.

> **이건 AP-2만의 문제가 아니다.** 앵커 감사가 *"정답 신호가 트레이스에 아예 없다"* 고 분류한
> **CH-2 · AU-2 · AP-2 세 문항이 전부 이 경로**를 탄다. 셋 다 에러 트레이스가 없어 traceId가
> 안 잡히고, 그래서 **정상 트레이스까지 함께 버려진다.**
>
> **수정**: 탐색이 `(창 + 서비스)`만 주고 traceId가 없을 때, 수집기가 **status 무관 ·
> 서비스+창 기준으로 Tempo를 검색**해야 한다. `Scope`가 traceId를 선택값으로 설계된 취지
> (strategy.md §4.5)가 수집 단계에서 지켜지지 않고 있다.

**리포트의 수집 실패 문구가 오해를 부추겼다.** 현재 문구는
*"탐색이 트레이스를 찾지 못했거나 **트레이스가 생성되지 않는 장애다**"* 인데,
실제로는 *"에러 트레이스만 검색했고 정상 트레이스는 조회하지 않았다"* 가 맞다.
**에이전트는 이 문구를 근거로 인프라 결함 가설을 지어냈다.**

## 토큰 — [기준](../round-1-input-tokens.md)대로 오버헤드를 분리한다

`coverage.contextTokens`는 **`-1`(측정 안 됨)** 이다. 구독 CLI 계정이라 `count_tokens` API
키가 없고, 이는 **구조적 조건이지 이번 회차의 사고가 아니다**(CLAUDE.md에 확정 기록).
따라서 아래는 전부 **`▓` 추정**이다.

**CLI 고정 오버헤드 `C`는 조사 당일 실측했다** — 상수가 아니기 때문이다.

```
프로브 3회 (CLI 2.1.220 · 격리 cwd · claude-opus-5 · 1자 프롬프트)
  21,331  ██████████  2회
  21,651  █████       1회        → C = 21,331 채택 (최빈)
```
문서 §2.1의 07-29 재측정값(21,247 / 21,567)과 **+84 차이** — 같은 CLI 버전이고 편차가
문서의 Δ320보다 작으므로 같은 구간으로 본다.

| 단계 | 총 `in` | 문자 | ① `in − 21,331` | ② `chars × 0.524` | 격차 |
|---|---|---|---|---|---|
| 탐색 | 42,735 | 39,299 (컨텍스트 38,103 + 프롬프트 1,196) | **21,404** | **20,593** | +3.9% |
| 분석 | 68,418 | 84,564 (컨텍스트 83,989 + 프롬프트 575) | **47,087** | **44,312** | +6.3% |
| **합계** | **111,153** | **123,863** | **≈ 68,491** | **≈ 64,905** | +5.5% |

- **AP-1 회차 2가 남긴 계측 공백이 메워졌다.** 그 회차는 *"탐색 단계는 `contextChars`를
  기록하지 않아 ② 경로를 아예 계산할 수 없다"* 고 적었는데, **이번엔 탐색도 두 경로가 다 나온다.**
  `RcaReport.Triage`에 필드가 추가된 결과다.
- 두 경로 격차가 **+3.9% / +6.3%** 로 AP-1 회차 2(+7.0%)보다 좁다. 새 `C`가 독립 경로와
  더 가깝다는 §2.1의 관찰과 일치한다.
- 출력은 `out 11,476`(탐색 3,053 + 분석 8,423). 분석 out은 회차 1(8,773) 대비 **−4%** 로,
  **AU-4에서 25점 차를 만든 분량 변수가 이번엔 통제됐다.** 델타 −10을 분량으로 설명할 수 없다.

## 탐색 단계 (별도 채점 대상)

| 항목 | 값 | 판정 |
|---|---|---|
| 시간창 해석 (T) | "최근 1시간" → `14:43:16Z ~ 15:43:16Z` (결정적 파싱) | ✅ 주입(15:35:35Z) 포함 |
| 스윕 | Tempo 1건 · Loki 곡선 · Mimir 5/5 · **실패 0** | ✅ |
| 대상 선정 (S) | `auth-service`, 창 `15:34:00~15:43:16Z` | ✅ **정답 서비스**, 주입 61초 구간 포함 |
| traceId | **미선정** | ✅ **정답** — 이 문항은 에러 트레이스가 존재하지 않는다 |
| 대조군 (B) | 없음 | — 앵커 미요구 |
| 오탐 | content-service 15:05Z 에러 트레이스(**AP-1 회차 2의 주입**)를 **명시적으로 기각** | ✅ "쓰기 경로라 증상과 불일치" |

**이 회차의 탐색은 AP-1 회차 2보다 어려웠고, 더 잘했다.**

- AP-1 회차 2는 *"1시간 창에 에러 트레이스가 1건뿐"* 이라 난도 최저였다.
  **이번엔 그 1건이 오답으로 창 안에 남아 있었고**(같은 창에 AP-1 주입이 30분 전에 있었다),
  에이전트는 그것을 골라 들어가지 않고 **경로 불일치를 근거로 기각**했다.
- **"넘길 traceId가 없는 문항"에서 traceId를 지어내지 않았다.** strategy.md §4.5의 정정
  (*후단은 traceId가 아니라 `(창+서비스+신호 종류)`를 받아야 한다*)이 실전에서 처음 확인됐다.
- **채널 판정**: 앵커 감사가 *"Loki 채널이 켜져 있는지를 이 문항 하나로 판정할 수 있다"* 고
  한 시험을 **통과**했다. 로그 채널로 갔고, 로그를 받았다.

> **그런데 분석 단계가 탐색 단계를 반박한다.** 리포트는
> *"조회 창이 질문과 불일치합니다 … 실제 수집 창은 9분 16초뿐"* 이라며 창을 넓히라고 권고한다.
> **좁힌 것은 탐색이 의도적으로 한 일이고 결과도 옳았는데**(주입을 정확히 포함),
> 분석 단계에는 *왜 좁혔는지*가 전달되지 않는다. 어셈블 컨텍스트에 탐색의 선정 이유를
> 넣어야 한다 — 지금은 리포트에만 있고 모델에는 안 간다.
