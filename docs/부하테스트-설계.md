세 서비스(auth · content · chat)에 걸친 부하 시험을 설계했습니다. 시나리오를 늘리는 대신, 각 시험이 **어느 자원에서 깨지는지를 서로 겹치지 않게** 나누는 것을 기준으로 삼았습니다. 부하 지점은 추정하지 않고 실제 코드에서 확인한 것만 대상으로 했고, 원인이 부하량인지 구조인지 갈리는 시험에는 대조군을 함께 설계했습니다. 스크립트 14개와 실행 규칙을 작성했으며, 문법 검증까지 완료하고 실제 서비스 대상 실행은 아직 하지 않았습니다.

### 설계 원칙

- **한 시험은 한 자원만 겨눈다 -** 시나리오가 겹치면 어느 쪽이 포화됐는지 사후에 가릴 수 없습니다. 예를 들어 채팅은 메시지 처리 부하와 연결 유지 부하를 각각 다른 스크립트로 분리했습니다.
- **부하 지점은 코드에서 확인한 것만 쓴다 -** "느릴 것 같은 곳"이 아니라 락·타임아웃·인증 경계처럼 실제로 확인한 지점만 대상으로 삼았습니다.
- **원인이 갈리는 시험에는 대조군을 붙인다 -** 같은 VU·같은 시간에 조건 하나만 바꿔 돌려야 원인이 부하량이 아니라 구조라는 것이 성립합니다.
- **정상 부하를 먼저 잰다 -** 기준선 없이 극한만 재면 "몇 배 느려졌다"를 말할 수 없습니다.

### 시험 사다리

# 1)  시나리오를 그대로 쓸 수 없었던 이유 - 코드가 규약을 정한다

## 문제와 원인

처음 준비한 시나리오는 일반적인 REST · WebSocket 형태였습니다. 그대로 돌렸다면 세 시험 모두 실패하거나, 더 나쁘게는 **실패한 줄 모른 채 통과했을** 것입니다. 실제 코드를 따라가며 확인한 차이는 세 가지였습니다.

- **로그인 경로 -** `/api/auth/login` 이 아니라 `/api/login` 입니다. 컨트롤러 매핑은 `/login` 이고 context-path 가 `/api` 입니다.
- **인증 키 -** 요청 DTO의 필드명은 `email` 이지만, 인증은 `findByUsernameAndProvider(username, COMMON)` 으로 조회합니다. 이메일만 맞추고 username 이 다르면 전부 실패합니다.
- **WebSocket 규약 -** 서버는 raw WebSocket 이 아니라 SockJS + STOMP 입니다. 임의 JSON 을 보내면 브로커가 조용히 버리고, 연결은 101로 성립하므로 **스크립트는 성공으로 집계합니다.**

## 해결

엔드포인트·인증 규약·페이로드를 전부 코드에서 확인해 맞췄습니다.

- WebSocket 은 SockJS 의 raw transport 경로(`/api/ws/websocket`)로 접속하고, `CONNECT` → `SUBSCRIBE` → `SEND` 프레임을 직접 조립했습니다. `CONNECT` 에 `Authorization: Bearer` 와 `X-Device-Id` 가 없으면 서버가 연결을 끊기 때문에 두 헤더를 필수로 넣었습니다.
- 연결 성립(101)만 확인하면 STOMP 인증 실패를 못 잡으므로, `CONNECTED` 프레임 수신을 별도 체크로 두었습니다.
- 계정은 회원가입 API(이메일 인증코드 필요) 대신 인증 없이 열려 있는 `POST /api/user` 로 시드하고, username 과 email 을 같은 값으로 맞춰 인증 키 문제를 해소했습니다.

## 결과

스크립트 14개 모두 문법 검증(`k6 inspect`)을 통과했고, 세 서비스의 포트·context-path·인증 헤더가 코드와 일치하는 상태로 정리됐습니다. 다만 이는 정적 검증이며, 실제 응답 코드 확인은 스모크 시험에서 이루어집니다.

# 2)  평상시 부하를 두 모델로 나눈 이유

## 문제와 원인

정상 부하 시험을 경로별로 구성했더니(읽기 30 VU · 로그인 5 VU · 채팅 20 VU) 경로별 기준선은 얻을 수 있었지만, 실제 트래픽 형태와는 달랐습니다. 사용자는 경로를 따로 호출하지 않고 하나의 세션 안에서 이어서 사용하며, 무엇보다 **응답이 오자마자 다음 요청을 보내지 않습니다.**

think time 이 빠지면 VU 수와 실제 동시 사용자 수가 서로 다른 값이 됩니다. think time 없는 50 VU 는 사람 50명이 아니라 수백 명분의 요청을 만들고, 그 상태로 "50명에서 느려진다"고 말하면 용량 산정이 통째로 틀어집니다.

## 해결

정상 부하를 두 모델로 나눠 각각 다른 것을 재도록 했습니다.

%cols 2000 3900 4000
| 구분 | 경로별 기준선 | 사용자 여정 |
|---|---|---|
| 단위 | 경로 (읽기 · 로그인 · 채팅 분리) | 세션 (반복 1회 = 방문 전체) |
| 부하 모델 | VU 고정 | 도착률 (초당 N명 진입) |
| think time | 1~3초 고정 | 2~10초 랜덤 |
| 목적 | 경로별 SLO 기준선 | 실제 사용 패턴에서의 체감 성능 |

여정은 앱 진입 → 무한스크롤 2~3장 → 상세 열람 → 일부만 리액션 → 배틀 목록 → 소수만 채팅방 접속으로 구성하고, 사용자 구성을 읽기 70% · 반응 20% · 채팅 10% 로 두었습니다. 로그인도 매 세션이 아니라 10%만 실제로 수행합니다. 나머지는 살아있는 토큰을 재사용하는데, 실제 앱의 동작이 그렇기 때문입니다.

## 결과

여정 시험에만 `iteration_duration` 을 임계값에 넣었습니다. 세션 하나가 끝나는 데 걸리는 시간이 개별 API 지연보다 사용자 체감에 가깝고, 특정 경로가 느려졌을 때 세션 전체가 얼마나 길어지는지를 하나의 값으로 볼 수 있기 때문입니다.

# 3)  극한 시나리오는 대조군과 함께 설계했다

## 문제와 원인

쓰기 경로를 강하게 때리면 대체로 느려집니다. 문제는 그것이 **부하량 때문인지 구조 때문인지** 결과만으로는 구분되지 않는다는 점입니다. 구분하지 못하면 다음 행동도 정할 수 없습니다. 서버를 늘려야 할지, 락을 걷어내야 할지 정할 수 없기 때문입니다.

실제 코드에서 확인한 지점은 두 가지였습니다.

- **리액션 토글 -** 피드 행을 비관적 락으로 잠그고 갱신합니다. 같은 피드에 몰리면 DB 행 하나에서 직렬화됩니다.
- **배틀 스와이프 -** 로그인 없이 호출됩니다. 비로그인은 쿠키로 식별되며, 요청 1건이 swipe insert 와 두 개의 카운터 update 를 발생시킵니다.

## 해결

두 시험 모두 조건 하나만 바꾼 대조군을 함께 설계했습니다.

- **핫키 락 -** 실험군은 피드 1건에 집중, 대조군은 여러 피드로 분산합니다. 같은 VU·같은 시간에 처리량과 p99 가 갈리면 원인은 부하량이 아니라 락입니다. 관측 대상은 커넥션 풀 대기 시간과 락 대기 타임아웃 로그입니다.
- **무인증 쓰기 -** 기본은 고정 게스트 ID로 멱등 덮어쓰기(update) 경로를, 옵션은 매 요청 새 게스트 ID로 insert 폭증을 만듭니다. 앞은 같은 행 경합, 뒤는 테이블 증가를 봅니다.

## 결과

두 시험은 실행 전이지만, 설계 단계에서 **"느려졌다"가 아니라 "락 때문에 느려졌다"를 증명할 수 있는 형태**가 확보됐습니다. 대조군에서도 같은 폭으로 느려진다면 락 가설은 기각되고, 그때는 원인을 커넥션 수나 인덱스에서 다시 찾게 됩니다.

# 4)  서비스 간 전파는 별도 시험으로 분리했다

## 문제와 원인

content 는 작성자 정보를 auth 에서 가져옵니다. 타임아웃은 3초이고, 실패하면 예외 대신 익명으로 폴백하며 별도 카운터를 올립니다. 이 구조는 auth 가 죽어도 content 가 버티도록 설계된 것이지만, **실제로 그렇게 동작하는지는 auth 가 느릴 때만 드러납니다.** 정상 상태에서는 캐시가 히트해 호출 자체가 발생하지 않기 때문에, 다른 시험으로는 이 경로를 밟을 수 없습니다.

## 해결

auth 를 로그인 폭주로 먼저 포화시키고, 30초 뒤 content 읽기를 얹는 순서로 설계했습니다. 판정 기준은 세 신호가 **함께** 움직이는지입니다.

- auth 응답 시간 상승
- content 의 auth 호출이 3초 타임아웃 근처까지 지연
- 폴백 카운터 증가

## 결과

세 신호의 조합으로 결론이 갈립니다. 폴백 카운터 없이 앞의 두 개만 오르면 폴백이 작동하지 않은 것이고, 폴백 카운터만 오르면 원인은 auth 가 아니라 캐시나 네트워크입니다. content 쪽 임계값이 깨지면 격리 자체가 실패한 것으로 판정합니다. 이 시험만 두 서비스에 동시에 부하를 겁니다. 전파를 보는 것이 목적이므로 의도적으로 겹쳤습니다.

# 5)  한계 탐색 - 모양은 다르게, 대상은 같게

## 문제와 원인

한계를 재는 방법은 하나가 아닙니다. 계단식으로 올려서 깨지는 지점을 찾는 것, 순간 폭주 후 회복을 보는 것, 오래 돌려 누수를 보는 것은 각각 다른 것을 잡아냅니다. 이것들을 서로 다른 대상에 걸면 결과를 비교할 수 없습니다.

## 해결

세 가지 부하 모양을 하나의 스크립트로 묶고, 대상은 옵션으로 고정할 수 있게 했습니다.

- **breakpoint -** RPS 를 계단식으로 올리다 임계값이 깨지면 스스로 중단합니다. 중단 시점의 RPS 가 한계 처리량입니다.
- **spike -** 10초 만에 최대로 올렸다 급하강한 뒤 3분을 관측합니다. 임계값으로 돌아오기까지 걸린 시간이 회복 시간입니다.
- **soak -** 저부하로 1시간 돌립니다. 힙 사용량 기울기와 커넥션 수의 우상향 여부를 봅니다. 짧은 시험으로는 보이지 않는 종류입니다.

여기에 요청 수가 아니라 **연결 수**와 **요청 크기**로 깨지는 경로를 각각 분리했습니다. 연결 폭주 시험은 메시지를 하나도 보내지 않고 연결만 유지해 세션 레지스트리와 소켓 자원을 봅니다. 업로드 시험은 업로드 시간 동안 스레드가 점유되는 문제를 봅니다. 파일 크기 상한이 1GB 로 열려 있어 요청 수 기준 시험으로는 잡히지 않는 한계입니다.

## 결과

같은 대상을 세 가지 모양으로 재기 때문에, 한계 RPS·회복 시간·장기 안정성을 하나의 축에서 비교할 수 있습니다. 연결 폭주 시험은 마지막 1분의 일제 해제 구간에서 정리 누락(세션·Redis 키 잔존)을 함께 봅니다.

# 부록

## 실행 규칙

- **한 번에 하나만 돌립니다.** 동시에 돌리면 세 서비스의 지표가 섞여 어느 쪽 포화인지 가릴 수 없습니다. 서비스 간 전파 시험만 예외입니다.
- **읽기 먼저, 쓰기 나중에 돌립니다.** 쓰기 시험 뒤에는 테이블이 커진 상태라 앞서 잰 기준선과 조건이 달라집니다.
- 회차 사이에 2~3분을 둡니다. 로그·메트릭 상에서 구간이 분리돼야 나중에 트레이스를 뽑을 수 있습니다.
- 회차마다 남길 것: 부하 모양과 VU/RPS, k6 요약(p95 · p99 · RPS · 실패율), 서버측 지표 캡처, **깨진 시점의 traceId**.

## 시험에서 제외한 것

- **이메일 인증코드 · FCM 발송 -** 외부 SMTP 와 푸시로 실제 발송이 나가고 레이트리밋에 걸립니다. 부하로 재려면 목(mock)을 먼저 붙여야 합니다.
- **피드 생성 -** 썸네일 첨부가 선행돼야 해서 준비 비용이 큽니다. 쓰기 부하는 리액션과 스와이프로 대체했습니다.

## 시험 준비 중 확인된 결함

- 채팅방 생성 API 가 인증 주체를 `Long` 으로 받는데 실제 주체 타입이 달라 바인딩되지 않습니다. 생성자 ID 가 비어 요청이 거부됩니다. 채팅 시험은 이 경로를 우회하도록 기본값을 잡았고, 결함 자체는 수정 대기열로 넘겼습니다.

## 현재 상태

- 완료: 시나리오 설계, 스크립트 14개 작성, 문법 검증(`k6 inspect`) 전량 통과, 실행 규칙 문서화
- 미측정: **모든 성능 수치.** 스모크로 응답 코드를 확인한 뒤 기준선 → 여정 → 극한 순으로 실행할 예정입니다.
- 선행 필요: 계정 시드, 그리고 피드·배틀 데이터. 콘텐츠 조회와 쓰기 시험은 기존 데이터가 없으면 준비 단계에서 중단됩니다.

> 문서의 임계값은 관측 목표를 정하기 위한 초기값이며, 기준선 측정 후 실측에 맞춰 조정할 예정입니다. 조정 전후 값은 회차 기록에 함께 남깁니다.
