# Ⅰ. 자연어 입력 전환

## 1. 탐색 채널을 구현 전에 감사했다

RCA 에이전트의 입력을 **사람이 고른 traceId 하나에서 자연어 질문 하나로** 확장하면서,
"어느 구간을 볼지"를 스스로 정하는 탐색(triage) 단계를 신설해야 했습니다.

초기 설계는 *"에러 트레이스를 검색해 대표 traceId를 뽑고 기존 분석 경로로 넘긴다"* 였습니다.
이것을 구현한 뒤 문항별로 재는 대신, **12개 장애 시나리오의 정답 신호가 어느 관측 채널에
존재하는지를 먼저 전수 분류**했습니다. 시나리오별 정답과 실제 주입 결과가 이미 문서화돼
있었으므로 코드 없이 가능한 검증이었습니다.

**감사 결과**

- Trace의 에러 검색만 구현하면 **12문항 중 6문항이 원리적으로 탐지 불가**
- 그중 **3문항은 정답 신호가 트레이스에 아예 생성되지 않음** — 컨슈머가 전멸해서(트레이스를
  만들 주체가 없다), ingress가 끊겨서, 예외가 로그에만 남아서
- 나머지 3문항은 트레이스에 있으나 `status=error`로는 안 걸림 — 401 응답, 200 성공인데 지연,
  메트릭 이탈

**결정**. 탐색 단계의 출력 인터페이스를 *"대표 traceId"* 가 아니라
**`(시간창 + 대상 서비스 + 신호 종류)`** 로 바꾸고 traceId는 있으면 딸려가는 값으로 내렸습니다.
수집은 3채널(Trace 에러 · Log 광역 · Metric 이상) 동시 스윕을 최소 요건으로 확정했습니다.

**남은 리스크**. 감사는 채널 *종류*만 봤고 **시간 해상도**는 축에 없었습니다. 실제로 23초짜리
장애 한 건이 5분 간격 메트릭 격자에 한 샘플도 안 걸려 탐색이 통째로 실패했고, 이 축을 뒤늦게
추가했습니다. **커버리지는 "어느 채널"과 "어느 해상도"의 곱이라는 것을 사후에 배웠습니다.**

## 2. 점수 차이를 모델 탓으로 돌리지 않았다

자연어 입력 회차에서 문항별 점수가 **100~4점**으로 크게 갈렸습니다. 모델 성능 차로 정리하면
설명은 되지만 다음 행동이 나오지 않으므로, **감점된 항목마다 "그 근거 신호가 관측 백엔드에
실제로 존재했는가"를 채점자가 직접 쿼리해 확인**했습니다.

**확인 결과, 감점이 특정 도구 결함 두 개에 몰려 있었습니다.**

| 결함 | 발현 | 막은 것 |
|---|---|---|
| 선정한 트레이스 1건 외에는 수집하지 않음 | 5문항 | 문항마다 다른 항목 — 어디선 대조군, 어디선 근거 자체 |
| 로그 라인 필터가 스택트레이스를 배제 | 1문항 | 정답이 로그에만 있는 문항의 근거 전량 |

- 예: 한 문항은 앵커가 요구한 *"정상 요청에 auth 호출 span이 없다"* 가 **문언 그대로 트레이스에
  존재**했는데, 수집기가 선정 트레이스 1건만 가져와 컨텍스트에 0바이트로 도착했습니다.
- **막힌 항목 수와 점수가 정렬**됐습니다 — 0개(100·90) → 1개(88) → 2개 이상(76·53).

**결정**. 프롬프트 개선보다 **수집 범위 수정을 우선순위로** 두고, 변경을 세 군(앱 계측 / 조사 도구 /
프롬프트)으로 나눠 **한 회차에 한 군만** 넣기로 했습니다. 이전 회차에서 도구 수정과 입력 모델
변경을 같이 넣어 델타를 귀속시키지 못한 전례가 있었습니다.

**한계를 함께 적었습니다.** 표본이 문항 몇 개라 상관을 주장할 수 없으므로 이 해석 자체를
**다음 회차의 반증 대상**으로 등록했습니다 — 결함을 고친 뒤에도 해당 문항들이 오르지 않으면
이 진단이 틀린 것입니다. 실제로 직전 회차에서 *"출력 분량이 부족해서 감점됐다"* 는 진단을
같은 방식으로 세웠다가, 분량이 **2.7배**가 됐는데 점수가 동일해 기각한 적이 있습니다.

## 3. 단일 실행 점수를 인용하지 않기로 했다

같은 문항을 같은 조건으로 두 번 돌렸는데 **총점이 25점 벌어진** 사례를 확인했습니다.
그 시점까지의 모든 점수가 N=1이었으므로, **문항당 최소 2회 실행 전까지 점수를 인용하지 않고
평균 ± 최대편차로만 기록**하는 규칙을 도입했습니다.

**4개 문항에서 N=2를 확보한 결과**

| 문항 | 결과 | 무엇이 재현됐나 |
|---|---|---|
| A | 4 ± 0 | **바닥에 눌린 재현** — 탐색이 주입을 1초 차이로 잘라 산출물이 없다 |
| B | 53 ± 0 | **도구가 만든 천장** — 정답 신호가 필터에 잘려 쓸 데이터가 없다 |
| C | 90 ± 0 | 항목까지 완전 동일 (18시간 간격 · 다른 주입 데이터) |
| D | **97.5 ± 2.5** | 여섯 항목 중 **다섯은 편차 0, 하나만 갈렸다** |

**여기서 편차 0을 "안정적"으로 읽으면 안 된다는 것이 드러났습니다.** A·B의 편차 0은 능력이
아니라 **막힘의 재현**입니다. 그래서 채점 기록에 *"정답 신호가 컨텍스트에 도달했는가"* 를
편차와 **함께** 남기도록 서식을 바꿨습니다.

**분산의 출처를 특정했습니다.** D에서 갈린 항목 하나는 배점 구간이 만점/부분/0 **세 단계뿐**이라
실제 결과가 문언 사이에 떨어지는 항목이었고, 두 실행 모두 그 자리에서 채점자 판정을
강요당했습니다. **즉 관측된 분산 전량이 모델이 아니라 채점 기준의 해상도 부족에서 나왔습니다.**

**결정**. 배점이 큰 3구간 항목에 중간 구간을 신설하되, **이미 채점된 회차에는 소급 적용하지
않습니다** — 자를 바꾸면 그 자로 매긴 기존 점수와 비교가 성립하지 않기 때문입니다.
편차를 0으로 만들려고 판정을 맞추지 않았고, 갈린 판정과 **반대 판정 시의 총점을 함께** 기록했습니다.

## 4. 오버헤드 상수를 폐기하고 회차마다 측정한다

개선 지표로 쓸 "컨텍스트 토큰"을 정의하면서, API 응답의 총 input 토큰을 그대로 쓰면
**CLI 고정 오버헤드(시스템 프롬프트 + 툴 정의)가 섞인다**는 것을 확인했습니다.
처음에는 그 오버헤드를 한 번 재서 상수로 빼려 했습니다.

**그 전제가 실측으로 깨졌습니다.**

```
07-26~27   약 22,000
07-28         26,626
07-29         21,247   (CLI 버전 동일)
07-29         26,576   9시간 반 뒤 복귀
```

같은 CLI 버전에서 하루 만에 **−20% 움직였다가 되돌아왔고**, 감소분 대부분이 툴 정의
(23,201 → 10,762)였습니다. 클라이언트가 안 바뀌었으므로 원인은 **서버가 내려주는 것**이고,
단조 드리프트가 아니라 **진동**입니다.

**결정**. 문서화된 상수를 빼는 방식을 폐기하고, **조사마다 1자 프롬프트 프로브로 그 회차의
오버헤드를 직접 측정**하도록 바꿨습니다. 앱 내장 프로브와 별도 셸에서 돌린 독립 프로브가
Δ27(0.1%)로 일치해 서로를 확인했고, 남는 오차는 프로브 자체의 **±1.5%** 입니다.

**중요한 귀결**: 과거 회차의 오버헤드는 **소급 추정이 불가능**합니다. 그래서 프로브가 실패한
회차는 값을 지어내지 않고 **"추정"으로 강등해 표기**하도록 했고, 실제로 그런 회차가 한 번
나왔습니다. 문자 수 기반 보조 추정식(`chars × 0.524`)도 함께 유지하는데, 이 식이
**매번 그날 프로브 값을 지지한다**는 것이 상수 폐기 결정의 독립 검증이 됐습니다.

## 5. 조회 창을 넓힌 비용을 채널별로 분해했다

같은 문항을 두 번 실행했는데 탐색이 고른 **조회 창 길이만** 달랐습니다(10분 43초 ↔ 24분 16초).
의도한 실험은 아니었지만 **창 길이 외 모든 변수가 고정된 자연 실험**이 됐습니다.

| | 짧은 창 | 넓은 창 | |
|---|---:|---:|---|
| 창 | 10분 43초 | 24분 16초 | ×2.26 |
| 분석 컨텍스트 | 115,328자 | 198,644자 | **+72.2%** |
| 비용 | $1.3628 | $1.8900 | **+38.7%** |
| 점수 | 100 | 95 | **안 올랐다** |

**증가분을 채널별로 분해**하니 거의 전부 메트릭이었습니다 — 8종 × 98포인트 × 다중 시리즈로
**164,988B**인데, 같은 창의 로그는 **16줄**, 트레이스는 **18,908B**였습니다.
**창을 넓힐 때 선형으로 부는 것은 메트릭 하나뿐**입니다.

**결정**. 창을 좁히도록 강제하는 대신 — 넓게 잡고 좁혀 들어가는 것은 정당한 전략입니다 —
**메트릭 적재 방식**을 고치기로 했습니다. 전 포인트 나열 대신 변화 구간 요약으로 싣고,
전 구간 상수인 시리즈(이 실행에서 25개)는 한 줄로 접습니다.

**단, 순서를 강제했습니다.** 앞서 5분 간격 샘플링이 23초짜리 장애를 통째로 삼킨 사례가 있어,
**요약이 짧은 이상 구간을 지우면 같은 실패가 재발합니다.** 그래서 집계 함수 교정
(`min_over_time` 등, 응답 크기 불변)을 **먼저** 넣고 요약 적재를 그 뒤에 두는 것으로 정리했습니다.

# Ⅱ. 관측 기반과 v0 설계

## 6. OTel Agent 전환 검토 → Brave 계측 유지

AI 기반 RCA 시스템으로 확장하기 위해서는, AI가 분석할 관측 데이터(Trace, Metric, Log)의
**커버리지가 구조적으로 보장되어야 한다**고 판단했습니다.

기존 Brave 기반 라이브러리 계측 방식은 개발자가 명시적으로 추가한 구간만 수집되기 때문에,
실제로 Kafka observation 누락을 경험하며 **계측 사각지대가 존재할 수 있음**을 확인했습니다.

이에 따라 zero-code 기반으로 커버리지를 보장하는 OTel Agent 전환을 검토했습니다. 초기에는
48시간 A/B 실험을 설계했으나, 전환 이전에 더 낮은 비용으로 검증 가능한 방법을 우선
적용했습니다. 대표 사용자 흐름(댓글 작성)을 기준으로 다음 시나리오를 구성하여 E2E 트레이스를
실측했습니다.

- 정상 요청 흐름 (HTTP → Service → Kafka Producer → Consumer → DB)
- 에러 발생 흐름 (예외 발생 및 retry 포함)
- 비동기 이벤트 처리 흐름 (fan-out 포함)

**검증 결과** (트레이스 `6a5dc9c1…`, 2 services / 30 spans / 1.26s):

- 전체 구간에서 trace context propagation이 유지됨을 확인
- span 누락 없이 실행 시간, 에러 정보, 서비스 간 연결 관계가 모두 수집됨을 확인
- security filterchain(1.21ms) · JDBC 쿼리(2~5ms, query/result-set/generated-keys 분리) ·
  Redis GET(689μs)까지 계측 밀도 확인
- Kafka 경계를 건너 chat-service `receive`(1.11s)까지 **하나의 traceId로 연결**됨을 확인
- RCA 분석에 필요한 데이터 요건 충족

이로 인해 OTel Agent 전환으로 얻을 수 있는 추가적인 관측 이점은 제한적인 반면,
**Pod당 메모리 사용 증가 · CPU 경합 환경에서의 오버헤드 · 운영 및 전환 리스크**와 같은
비용이 실재한다고 판단했습니다.

따라서 **현재 구조에서는 Brave 기반 계측을 유지하는 것이 합리적**이라고 결론 내렸습니다.
48시간 A/B는 수행하지 않았습니다 — 더 낮은 비용의 검증으로 의사결정에 필요한 정보가 이미
확보되었기 때문입니다.

단, 라이브러리 기반 계측의 특성상 누락 리스크는 존재하므로,

- 신규 기능 개발 시 Observation 체크리스트 적용
- 주요 사용자 흐름에 대한 주기적 트레이스 샘플링 검증

을 운영 가이드로 추가하여 지속적으로 커버리지를 관리하고 있습니다.

**남은 리스크는 이후 실제로 현실화됐습니다.** 실전 조사에서 `push-dispatcher#dispatch`가
소비한 996ms 중 **994ms가 자식 span 없이 비어 있었고**, 원인은 계측되지 않은 FCM 동기
호출이었습니다. 이는 결정이 틀렸다는 뜻이 아니라 — zero-code 전환으로도 서드파티 SDK 내부
호출은 잡히지 않았을 가능성이 높습니다 — **라이브러리 계측의 잔여 리스크를 코드 인지 RCA로
보완해야 한다는 근거**가 되었습니다. 결정과 리스크와 보완 계획이 한 줄로 이어집니다.

→ [ADR-001](decisions/adr-001-brave-over-otel.md) · [NF-02](findings/nf-02-fcm-call-no-timeout-no-span.md)

## 7. v0를 "도구 없는 단일 패스"로 설계

에이전트를 만들 때 유행하는 형태는 tool-calling 루프입니다 — LLM에게 Tempo/Loki/Mimir 조회
도구를 주고 스스로 탐색하게 하는 방식입니다. 처음부터 그렇게 만들지 않았습니다.

핵심 논거는 **대조군 확보**입니다. "에이전트 루프가 더 낫다"는 주장은 **루프가 없는 기준선이
있어야만 증명 가능**합니다. 루프부터 시작하면 유연하지만 실행마다 경로가 달라 재현이
어렵고, 무엇보다 비교할 대상이 없습니다.

부수적으로 단일 패스는 실패를 세 유형으로 분류할 수 있게 해줍니다 —
**(a) 컨텍스트에 신호가 있는데 모델이 놓침 / (b) 신호 자체가 수집되지 않음 / (c) 신호를 보고도
확정 불가.** 이 분류가 "다음 투자를 프롬프트에 할 것인가, 수집 쿼리에 할 것인가, 코드 연동에
할 것인가"를 정하는 판단 기준이 됩니다.

**실측 결과** (동일 트레이스 3회):

| 항목 | 값 |
|---|---|
| 소요 | 76~84초 (대부분 LLM 75~81초) |
| 토큰 | in 42,651~42,774 / out 4,950~5,056 — **입력 편차 ±0.3%** |
| 비용 | 조사당 $0.42~0.43 |

분석 품질도 확인됐습니다. content 동기 응답(129.8ms)은 정상으로 배제하고, Kafka 뒤 chat의
`dispatch` 996ms 중 994ms가 자식 span으로 설명되지 않는 갭임을 1순위로 특정했으며,
GC pause와 커넥션 pending이 0인 것을 들어 경쟁 가설을 반증하고, 로그 부재를 이유로 확신도를
스스로 낮췄습니다.

**한계도 그대로 드러났습니다** — 위치는 특정했지만 원인은 확정하지 못했습니다. 이것이 위
(c) 유형 실패의 실측 사례이고, **코드 인지 RCA로 확장하는 근거**가 되었습니다.
"필요해서 확장한다"를 인상이 아니라 숫자로 뒷받침한 것입니다.

## 8. 장애를 실제로 주입해 AI 정확도를 채점했다

"리포트가 좋아 보인다"는 인상 비평으로는 개선을 증명할 수 없다고 판단했습니다.
**평가란 정답(ground truth)이 있는 데이터셋을 만드는 일**이라고 관점을 바꾸고,
개선을 시작하기 전에 평가 체계부터 만들었습니다.

프로덕션 클러스터에 실제로 장애를 주입해 정답을 만드는 방식으로 **12개 시나리오**를 정의했고
(MongoDB 중단, Kafka 브로커 중단, 인증 서버 다운, 소비자 전멸, 앱 계층 결함 등),
100점 루브릭(원인 40 · 근거 30 · 오귀인 20 · 조치 10)으로 채점했습니다.

운영 규칙은 다섯 가지입니다.

- **블라인드** — 에이전트에게는 traceId와 자연어 질문만 준다. 자기 채점은 무효로 처리한다
- **기준 선박제** — 채점 기준은 장애 주입 **전에** 확정한다. 결과를 보고 고치면 그 회차는 무효다
- **반복 측정** — 시나리오당 최소 2회, 평균 ± 최대편차
- **도구 제약 면제 없음** — 조사 도구가 신호를 못 모아 만점이 불가능해도 그대로 감점한다.
  면제하면 도구를 고쳤을 때 개선폭이 측정되지 않기 때문이다
- **근거는 개수가 아니라 충분성으로** — 같은 사실을 담은 로그와 트레이스는 동치로 취급하고,
  어느 경로로 도달하든 같은 점수를 준다

**결과: 9회 조사, 유효 채점 5회, 평균 82점.**

**그런데 가장 중요한 발견은 에이전트 점수가 아니었습니다 — 채점 불가 4건이 전부 에이전트가
아니라 채점 기준의 결함에서 나왔습니다.** 기준이 조건에 따라 갈리는 전개를 한 갈래만 기술했거나,
에이전트의 수집 범위 밖 신호를 요구했거나, 코드의 설정 상수를 실측으로 착각했거나
(기준은 "3초 타임아웃"을 요구했고 실제 관측은 23.5ms 연결 거절이었습니다 — **에이전트가
옳았고 기준이 틀린 사례**), 아예 기준 없이 주입이 실행됐습니다.

그래서 **기준 부적합률 자체를 추적 지표로 삼아 67% → 33%로 낮췄고**, 대응을 원인별로 갈랐습니다
— 기준 작성 오류는 체크리스트 7항목으로, 기준 부재는 **실행 전 자동 게이트**로 막습니다.

**남은 리스크와 그것을 밝히는 방식.** 유효 5회가 전부 1회차라 규정상 이 점수는 아직 인용할 수
없습니다. 같은 버전의 에이전트가 같은 장애에서 75점과 약 95점을 낸 사례가 있고, 차이는 버전이
아니라 출력 분량이었습니다. 또한 오귀인 항목 20점이 9회 전부 만점이라 변별력이 없는데, 원인은
항목 설계가 아니라 **정상 상황을 한 번도 준 적이 없는 문항 세트**에 있습니다.
**점수를 제시할 때 이 한계를 함께 밝히는 것을 규칙으로 두었습니다.**

## 9. 개선 지표를 "뺄셈"에서 "차분"으로 바꿨다

컨텍스트 압축으로 토큰을 줄이는 개선을 하려는데, 무엇을 재야 하는지가 먼저 문제였습니다.
리포트의 입력 토큰 `in`에는 **Claude CLI 자신의 고정 오버헤드가 섞여 있습니다** —
컨텍스트를 하나도 주지 않은 프로브가 약 30,000 토큰을 보고했습니다.

`in`을 그대로 쓰면 두 방향으로 손해입니다. 실제 개선폭보다 작아 보이고, 채택 기준(토큰 20%
절감)이 실질적으로 1.25~1.95배 엄격해져 **성공한 개선이 기준 미달로 기각될 수 있습니다.**

**검토 ① 회귀로 오버헤드 상수 C를 추정해서 빼기.** 기록된 6회로 적합하면 R² = 0.960으로
그럴듯해 보였지만, 검정을 붙이자 무너졌습니다.

| 검정 | 결과 |
|---|---|
| 95% 신뢰구간 | [965, **23,345**] |
| 한 점 제거 시 추정치 | 5,993 ~ 15,725 (**2.6배 진폭**) |
| 기울기 | 0.767 tok/char — 성립하려면 한글 구간이 2.0 tok/char여야 하는데 그런 텍스트는 없다 |

R² 0.960은 근거가 아니라 **설계의 산물**이었습니다. x값이 두 덩어리로 갈려 있어 그 사이에 선
하나 긋는 건 언제나 됩니다. **기각했습니다.**

**검토 ② `chars/4` 추정.** 영어권 휴리스틱을 한글 + OTLP JSON 혼합에 적용한 값이라 실측
대비 **2.1배 과소**였습니다(0.250 vs 실측 0.524 tok/char). 필드를 제거했습니다 —
**추정치를 지어내느니 "측정 안 됨"이 낫습니다.**

**채택: 짝지은 두 실행의 차분.** 같은 모델·같은 CLI 버전으로 "꼬리말만" 보낸 실행과
"컨텍스트 + 꼬리말"을 보낸 실행의 차를 취하면, 오버헤드가 무엇이든 그대로 상쇄됩니다.
**추정이 아니라 소거입니다.** 기준선 2회의 편차는 0이었습니다.

**결과.** 오버헤드가 **26,626 토큰**으로 확정됐고, 기능을 하나씩 끄며 분해하자
**그중 87%(23,201 토큰)가 이 에이전트가 한 번도 호출하지 않는 툴 정의 스키마**였습니다.
실제 관측 데이터가 11,900 토큰인 회차에서, 쓰지 않는 툴 설명서가 그 두 배였습니다.
한 줄 설정으로 총 입력의 60%가 사라지지만, **입력이 바뀌면 답도 바뀔 수 있으므로 같은
traceId로 재조사해 정확도 불변을 확인한 뒤에 적용**하기로 했습니다.

> **원칙: 피감수의 오차가 결과보다 크면 뺄셈은 성립하지 않는다. 빼지 말고 직접 재라.**

## 10. 측정 하네스 자체를 먼저 검증했다

전략의 대원칙이 "모든 개선을 before/after 숫자로 증명한다"였기 때문에, 하네스가 내는 숫자를
먼저 의심했습니다. 실측 중 명백한 이상값이 나왔습니다 — **41,055자 컨텍스트를 보냈는데
입력 토큰이 `2`로 기록**되고 있었습니다.

원인은 프롬프트 캐시였습니다. CLI의 usage는 입력을 `input_tokens` +
`cache_creation_input_tokens` + `cache_read_input_tokens` 세 필드로 쪼개는데, 대형 컨텍스트는
거의 전부 캐시 필드로 계상되므로 첫 필드만 읽으면 입력이 사실상 0으로 보입니다.
셋을 합산하도록 수정하자 **2 → 42,774**가 됐습니다.

같은 맥락에서 계측 결함을 두 건 더 찾았습니다.

- **모델이 고정돼 있지 않았습니다.** 서브프로세스 호출에 `--model`이 없어 CLI 기본값으로
  돌고 있었습니다. 회차마다 다른 모델이 채점됐을 수 있고, 토크나이저도 달라 토큰 비교까지
  무너집니다. 모델을 고정하고 응답이 보고한 모델과 왕복 횟수를 리포트에 기록했습니다 —
  **왕복이 1이 아니면 "도구 없는 단일 패스"라는 대조군 전제가 깨진 것**이므로 경고를 남깁니다.
- **캐시 3분해가 합산에 묻혀 있었습니다.** cache read는 정가의 1/10이라 같은 입력 토큰이라도
  비용이 열 배 갈립니다. 분해해서 병기했습니다.

**그리고 이 결함들의 대가를 실제로 치렀습니다** — 과거 7회는 모델이 기록되지 않아 점수 기록은
유효하지만 **토큰 차트의 before로는 쓸 수 없습니다.** 토큰 축의 기준선은 모델을 고정한 뒤
새로 만들기로 했습니다.

> **측정이 틀리면 이후 모든 개선 판단이 틀린다.**

## 11. Consumer lag은 broker-side exporter로 관측한다

조사 리포트마다 같은 수집 실패가 반복 기록되고 있었습니다 —
`kafka_consumer_fetch_manager_records_lag returned no series`.

"이 시간창에 데이터가 없다"가 아니라 **메트릭 계열 자체가 존재하지 않을** 가능성을 라벨 API로
실측했습니다. 클러스터에 존재하는 kafka 메트릭은 4개뿐이었고, 전부 앱이 아니라
**브로커에 직접 질의하는 별도 exporter**가 내는 것이었습니다.

여기서 단순한 이름 교체가 아니라 **관점의 차이**가 드러났습니다.

| | 클라이언트 메트릭 (앱) | broker-side exporter |
|---|---|---|
| 측정 주체 | 컨슈머 앱 자신 | 브로커에 질의하는 별도 프로세스 |
| **컨슈머가 죽으면** | **메트릭도 함께 소멸** | **계속 관측 — lag 상승이 그대로 보인다** |

**"알림이 안 온다 → 컨슈머가 죽었나?"가 전형적인 장애 시나리오인데, 정확히 그 순간
클라이언트 메트릭은 앱과 함께 사라집니다.** 장애 분석 도구가 의존할 신호로는 실격입니다.

**원칙: 장애 분석에 쓸 신호는 관측 주체가 장애 대상과 분리되어 있어야 한다.**
이는 항목 6에서 얻은 교훈("앱 내 계측은 앱과 운명을 같이한다")의 메트릭 버전입니다.

**이 예측은 이후 실제 장애 주입에서 검증됐습니다.** 소비자를 전부 중단시킨 시나리오에서
앱 메트릭이 소비자와 함께 사라져, 채점 기준이 요구한 신호 2종이 **구조적으로 관측 불가**가
됐습니다. 그 회차는 채점 불가로 기록됐고, 결정의 근거가 실측으로 뒷받침됐습니다.

## 12. 평가 오염을 차단했다 — 피험자가 시험지를 읽고 있었다

LLM provider로 Claude CLI를 쓰는 구성에서, 서브프로세스가 **JVM의 작업 디렉터리를 그대로
물려받고** 있었습니다. 그런데 Claude Code는 작업 디렉터리의 `CLAUDE.md`와 `.claude/skills/`를
자동으로 읽습니다. 즉 **평가 대상이 관측 라벨·쿼리 결함·문항 관련 사실이 적힌 프로젝트 문서를
읽은 상태로 시험을 보고 있었습니다.**

대응은 두 단계였습니다. 먼저 CLI를 **중립 임시 디렉터리에서 기동**하도록 고치고, 프로브로
차단을 검증했습니다. 그다음 **오염의 크기를 숫자로 확정**했습니다.

원본 응답 덤프에서 과거 조사의 컨텍스트를 복원해(기록된 문자 수와 4/4 일치) 다시 측정하자,
격리 이후 회차는 **±200 토큰(0.3%) 안에서 재현**됐고 **격리 전 회차 하나만 −3,407**이었습니다.
그 차이가 곧 컨텍스트에 딸려 들어갔던 프로젝트 문서의 크기입니다.

독립적인 경로로도 같은 값이 나왔습니다 — 빈 프롬프트 프로브(29,987) − 차분 실측(26,626) =
**3,361**. 두 방법이 서로를 확인했습니다.

**오염의 존재는 이전에도 지적됐지만, 크기가 숫자로 확정된 것은 여기서입니다.**
격리 전에 실행된 회차는 폐기하고 재실험했습니다.

> **후속 실측 (자연어 회차)**: 같은 프로브를 실수로 레포 루트에서 한 번 돌려 **직접 대조**를
> 얻었습니다 — 격리 26,603 ↔ 레포 루트 **32,747(+6,144, +23%)**. `cache_read`는 양쪽이 같고
> 차이가 전부 `cache_creation`에서 났습니다. 위 3,407은 과거 응답 덤프로부터의 **역산**이고
> 이것은 **동시 대조**이며, 그사이 CLI 오버헤드 자체가 진동했으므로(항목 4) 두 값을 같은
> 자로 비교하지 않습니다. **샌드박스가 매 조사 막고 있는 오염의 크기가 직접 측정된 것**입니다.
> (레포 cwd에서는 CLI가 도구를 쓰기 시작해 3턴까지 가기도 했습니다.)

이후 블라인드 유지를 규칙으로 성문화했습니다 — 리포트 생성 경로에 정답지를 넣지 않고,
리포트 안에서 점수를 생성하게 만들지 않으며(자기 채점은 무효),
**개선 수단은 프롬프트 파일 하나로만** 들어가야 측정이 성립합니다.

## 13. 제품 경계를 명확히 했다 — 설명 엔진과 탐색 엔진

성능 점수를 정리하다가 입력 모델을 다시 봤습니다. API가 traceId를 필수로 요구하고, 더
근본적으로 **로그·메트릭의 조회 시간창이 입력 트레이스에서 파생**됩니다. traceId가 없으면
*언제*를 볼지가 정해지지 않아 쿼리 자체를 만들 수 없습니다.

그런데 **실무에서 장애가 나면 traceId를 아는 사람이 없습니다.** 조사는 알람이나 사용자 증상에서
시작하고, 담당자가 대시보드에서 *시간대 + 에러 조건*으로 뒤져 traceId를 찾아냅니다.
**그 뒤지는 행위가 원인 분석의 절반이고, 현재 시스템은 그 절반이 끝난 상태를 입력으로 받습니다.**

즉 현재 버전은 "이 요청이 왜 이렇게 됐는가"에 답하는 **설명 엔진**이지, "어젯밤 오류를 찾아줘"에
답하는 **탐색 엔진이 아닙니다.**

**이것을 구현 누락이 아니라 의도된 범위 설정으로 유지하되, 점수를 제시할 때 함께 밝히기로
했습니다.** 시간창이 트레이스에서 파생되는 구조 덕분에 수집이 결정적이고 회차 간 재현이
성립합니다 — 측정을 먼저 세우기 위한 선택이었습니다. 다만 **현재 점수는 대상이 주어진 상태의
정확도이므로 성능의 반쪽만 재고 있습니다.**

확장 설계에서 지킨 원칙 세 가지입니다.

- **기존 측정을 깨지 않는다** — 탐색은 traceId 입력을 *대체*가 아니라 *추가*한다.
  두 진입점이 공존하므로 기존 회차의 분석 점수는 그대로 살아 있다
- **배점을 재분배하지 않는다** — 탐색을 기존 100점의 5번째 항목으로 넣으면 과거 9회와 비교가
  끊긴다. 탐색은 자체 루브릭을 갖는 별도 트랙으로 두고, 인용은 end-to-end 하나로 한다
- **분해는 귀인을 위한 것** — 한 점수로 합치면 점수가 떨어졌을 때 *못 찾은 것*인지 *찾고도 못
  푼 것*인지 알 수 없어 무엇을 고칠지 정할 수 없다. 처방이 정반대이기 때문이다

부수적으로 **이 확장은 장애 주입 없이 평가할 수 있습니다.** 과거 9회의 정답(주입 시각, 실제
traceId, 정답 원인)이 이미 기록돼 있어 회고 평가가 가능하고, **정상 시간대를 함께 던지면
오탐 검증(항목 8의 남은 리스크)까지 같은 트랙에서 해결**됩니다.

> **판단을 정정한 기록도 남깁니다.** 처음에는 "입력 모델을 바꾸면 기존 baseline이 무효가 된다"고
> 적었으나 틀렸습니다. 탐색은 대체가 아니라 추가이므로 기존 측정은 무효가 되지 않습니다.

2. **자를 먼저 의심한다** — 하네스의 토큰 회계, 채점 기준, 오염 여부를 각각 실측으로 검증했고
   **셋 다 결함이 나왔다**. 심지어 **관측된 분산 전량이 자에서 나온 경우**도 있었다(항목 3)
3. **싼 검증을 먼저 한다** — 48시간 A/B 대신 E2E 트레이스 3종, 구현 대신 채널 전수 감사(항목 1),
   장애 주입 대신 기존 traceId 재조사
4. **그럴듯한 근거를 기각한다** — R² 0.960도, "출력이 짧아서 감점됐다"도 근거가 아니다.

5. **원인을 도구에 귀속시키되, 그 귀속도 반증 대상으로 남긴다** — 감점마다 "그 신호가 실제로
   존재했는가"를 직접 쿼리해 확인하고(항목 2), 확인 결과 자체를 다음 회차의 예측표에 올린다
