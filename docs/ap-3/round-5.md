## 이번 회차의 근거가 회차 3보다 강하다 — span 시각순 재구성

리포트가 **한 커넥션 span 안의 JDBC 흐름을 시각순 표로 복원**했다.

```
.296 select tb_hashtags where name=?   → .299 row-count 0   (없다)
.309 insert tb_hashtags                → .313 hashtag id=178
.326 insert tb_feed_hashtags           → .328 id 232        (1회차 매핑 성공)
.340 select tb_hashtags where name=?   → .342 row-count 1   (이번엔 있다 — 방금 만든 그 행)
.352 insert tb_feed_hashtags           → ERROR Duplicate entry '163-178'
```

**같은 조회가 두 번 실행되고 첫 번째는 0건, 두 번째는 1건**이라는 것, 그리고 충돌 키 `'163-178'`이
1회차에 만든 feed 163 + hashtag 178 조합 그대로라는 것 — 리포트의 표현대로
*"저장 로직이 dedup하지 않는다는 결론이 **데이터에서 직접 따라 나온다**"*.

**트레이스 압축이 켜진 상태에서 span 13개의 순서·시각·이벤트가 전부 살아남았다.**
B-35가 *"span도 속성도 하나 안 버린다"* 고 한 주장이 **시각 정밀도를 요구하는 추론에서**
검증된 셈이다. 시작 시각을 절대값으로 유지하기로 한 결정(끝 시각만 `durNs`로 바꿈)이
이 재구성을 가능하게 했다.

덤으로 **예외 표면화 지점까지 짚었다** — `DataIntegrityViolationException`이 던져진 곳이
해시태그 저장 코드가 아니라 `ExpGrantService.isDuplicate(:225)`이고, 그 조회가 Hibernate의
보류 중이던 insert를 **auto-flush** 시켜 위반이 드러났다는 것. 앵커에 없는 관측이다.

## 이번 회차에서 처음 관측된 것

1. **🔴 트레이스 압축 상태에서 span 시각순 재구성이 성립했다.** 13개 span의 순서·시각·이벤트로
   dedup 부재를 도출했다. **B-35가 시작 시각을 절대값으로 남기기로 한 결정**(끝 시각만
   `durNs`로 치환)이 이 추론의 전제였다.
2. **B 요건의 세 번째 형태** — 같은 요청 안의 성공 단계 ↔ 실패 단계 대조. AP-1(부재 신호) ·
   AP-2(별도 정상 요청)와 합쳐 **세 문항이 각각 다른 경로로 B를 충족**했다.
3. **회차 3의 유일한 감점이 해소됐다** — 4) 영향 5 → 10. 해소 방식이 C-5의 형태다.
4. **AP-1과 5)의 응답 강도가 갈렸다** — 같은 *"DB는 제약을 지켰다"* 요건에 AP-3는 명시
   옹호, AP-1은 우회 표현(판정). **앵커 문언 정리의 근거가 두 회차에서 나왔다.**
