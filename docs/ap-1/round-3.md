## 이번에 확인된 것 3건

### ① 🔴 traceId 로그 폭증의 범인은 traceId 개수가 아니라 **계측 DEBUG 덤프**였다

②번 실행에서 이 채널이 18KB → 130KB로 튀었을 때 첫 진단은 *"대표를 없애 traceId가 10개가
됐기 때문"* 이었는데, **틀렸다.** 창 후보 8건은 `Scope`에 들어가지 않아 로그 조회 대상이
아니었다 — 이 채널은 그때도 **탐색이 지목한 2건만** 보고 있었다.

원본을 열어 실측한 결과는 이렇다:

| 서비스 · 레벨 | 줄 | 바이트 | 줄당 |
|---|---:|---:|---:|
| **chat-service DEBUG** | **45** | **107,932** | **2,398** |
| content-service INFO | 15 | 3,099 | 206 |
| chat-service INFO | 13 | 5,062 | 389 |
| 나머지(ERROR·WARN·auth) | 6 | 1,370 | ~230 |

**45줄이 채널의 92%를 먹었다.** 내용은 장애 정보가 아니라 Micrometer 옵저베이션 내부 상태
덤프다 — `context=name='jdbc.connection' … map=[class io.micrometer.core.instrument…]` 가
한 줄에 최대 4.6KB. **분석 리포트가 이 45줄에서 인용한 것은 하나도 없었다.**

진짜 차이는 **탐색이 고른 `services`** 였다: ① `[content, auth]` → ② `[content, auth, chat]`.
Loki 셀렉터가 서비스로 좁히므로 chat이 들어온 순간 그 서비스의 DEBUG가 딸려 왔다.
**탐색의 판단은 옳았다** — 그 요청이 실제로 chat-service를 14 span 지나갔고 탐색은
*"하류 지연 여부만 확인한다"* 고 이유까지 적었다. 대상 선정이 아니라 **그 서비스의 로그가
뚱뚱했던 것**이다.

처방은 `traceIdQuery`에 `!= "DEBUG"` 하나. **INFO는 남긴다** — 도착·성공·복구 신호가
본질적으로 INFO이고(B-16), 실제로 이번 분석도 `[push] 멀티캐스트 결과`·`[kafka] 알림 처리
완료` 같은 INFO를 근거로 썼다.

### ② B-25는 판별력을 깎지 않았다

메트릭 적재분이 89,649B → 약 25,000자(**−72%**)인데, 탐색의 기각 2건이 **전부 요약값으로**
이뤄졌다 — *"37개 시계열 전부가 창 전체에서 lag=0으로 평탄"*, *"websocket_active_users가
05:41부터 06:41까지 계속 0인 평탄한 값"*. 분석도 *"`up` 전 구간 1, `hikaricp` 전 구간 0"* 으로
인프라를 배제했다. **전 구간 상수를 한 줄로 접은 것이 오히려 기각 논거가 됐다.**

### ③ 탐색이 세 번 연속 같은 판단을 했다

창(`06:30:00~06:41:15Z`)·후보(INC-3·4·5)·기각 2건이 **세 실행 모두 동일**하다. 도구가 네 번
바뀌고 컨텍스트가 절반 아래로 줄었는데도 탐색 산출이 흔들리지 않았다 — 이 단계가
**결정적으로 설계된 부분**(창은 코드가 신호 시각에서 계산)이 실측으로 확인된 셈이다.

## §8 채점 근거 (항목별)

### 1) 원인 적중 — 40점 만점 · **두 자로 채점**

| | 구 앵커 | 개정 앵커 (ㅌ · 이 회차부터 유효) |
|---|---|---|
| 만점 요건 | 앱 검증 구멍(**`@Size` 부재**) + 책임 분리 | **앱 계층에 입력 길이 검증이 없다** + 책임 분리 |
| 20점 | 검증 구멍 도달했으나 확정 못 함 | 길이 초과로 500까지만 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| 500까지 정확 | 충족 | *"컬럼 정의를 초과 → MySQL 1406(Data truncation) → 트랜잭션 롤백 → HTTP 500"* |
| **입력 길이 검증 부재** | 충족 | 1순위 원인 문장 안에 **"(애플리케이션 단 입력 길이 검증 부재 포함)"** · 스택으로 `JwtFilter` 통과 → `FeedCommentController:53` → `FeedCommentService:64` 도달을 보임 |
| 앱/DB 책임 분리 | 충족 | *"인증·인가는 정상, **순수 데이터 계층 실패**"* · 인프라를 수치로 배제 · *"전용 핸들러가 없어 … **400이 아니라 500**"* |
| `@Size` 부재 확정 | **미충족** | 조치 1이 *"컬럼 정의 확인"* 으로 남아 있고, 조치 4는 처방이지 현 상태 확정이 아니다 |

**→ 개정 앵커 40점 / 구 앵커 30점.** 갈리는 지점이 정확히 **구현 이름 한 칸**이다.
구 자로는 세 실행이 모두 같은 자리에서 30에 멈췄고, 그것이 개정 ㅌ의 근거였다.
**개정 앵커 기준이 기록값이다** — 이 조사가 돌기 전에 박제됐다(§1.1).

> **판정 성격을 밝힌다.** 문언 충족은 명확하나, 검증 부재 논증의 밀도는 ②번 실행이 더 두꺼웠다
> (*"검증이 있었다면 DB까지 가지 않는다"* 라는 반사실 논증). 이번은 원인 문장에 명시하고
> 스택으로 경로를 보이는 방식이다. **문언은 "명시"를 요구하므로 40으로 읽었다.**
