## 이 회차의 관측 조건 — 한 창에 세 주입이 들어 있다

**회차 5와 다른 점이 도구만이 아니다.** 이번 채록은 AP-1·AP-2·AP-3을 같은 시간대에 주입한 뒤
문항별로 따로 물었다. 그래서 AP-1의 스윕 창(60분) 안에 다른 두 문항의 신호가 함께 있다.

| 창 안에 있던 것 | 시각 | AP-1 리포트가 한 처리 |
|---|---|---|
| AP-1 — 댓글 `Data too long` | 01:22:30Z | 선택 (INC-3 · 트레이스 / INC-2 · 로그 지문) |
| AP-2 — 팔로우 `NullPointerException` | 01:31~01:36Z | **기각** — INC-4로 후보에는 올랐다 |
| AP-3 — 피드 `uk_feed_hashtag` 중복 | 01:35:08Z | 창 밖 (좁힌 창이 01:27에서 끝남) |

**기각 문언 원문**: *"auth-service NullPointerException은 01:31~01:33으로 댓글 실패 시각(01:22)보다
9분 뒤이고, 그 시각에 댓글 엔드포인트 트레이스 오류가 없어 이번 제보와 시각이 맞지 않는다 —
별건으로 남겨 둔다."*

**회차 5보다 어려운 조건이 아니다 — 오히려 더 깨끗했다.** 회차 5도 창에 주입이 둘이었다
([AP-2 회차 5](../ap-2/round-5.md): *"AP-1 회차 5가 … auth 3.23초 건을 `content→auth 엣지 없음`으로 기각"*).

| | 회차 5 | **회차 6** |
|---|---|---|
| 좁힌 창 | 02:00~02:14Z | 01:22~01:27Z |
| 창 안 주입 | **2건** — AP-1(02:09:25) · AP-2(02:11:42) | **1건** — AP-1(01:22:30) |
| 남의 주입 처리 | 분석 단계에서 기각 | **탐색 단계에서 기각**(INC-4) — 좁힌 창이 아예 안 덮음 |

**즉 이번 회차는 남의 신호를 더 이른 단계에서 잘라냈다.** 이것을 능력 향상으로 읽으면 안 된다 —
주입 시각 간격이 회차 5는 2분 17초, 회차 6은 9분 37초라 **창 좁히기만으로도 갈린다.**
**조건 차이로만 기록하고 점수 해석에 반영하지 않는다.**

**회차 6은 AP-1을 더 비싸게 풀었다.** 이것은 회귀가 아니라 **설계상 예정된 방향**이다 —
B-44·B-45·B-46은 전부 *신호를 더 싣는* 변경이고, 회차 6 대기열이 겨냥한 절감 항목

**절감 없이 공급만 켠 중간 상태의 수치**다.

### 창이 좁아졌는데 수집이 늘었다

| | 회차 5 | **회차 6** |
|---|---:|---:|
| 좁힌 창 | 14.2분 (02:00:00~02:14:12Z) | **5.0분** (01:22:00~01:27:00Z) |
| 트레이스 (수집) | 33,415 B / 26 spans | **59,185 B / 59 spans** |
| 로그 ERROR/WARN | 37,139 B | 37,139 B |
| 로그 traceId | 6,327 B | 6,329 B |
| 메트릭 | 105,113 B | 54,134 B |
| **→ 분석 컨텍스트** | **68,839 자** | **84,658 자** |

**창은 65% 좁아졌는데 트레이스는 77% 늘었다.** span이 26 → 59다. 늘어난 자리는 특정된다 —
B-46 대조군 1건(`6a7bcb12…`, 정상 댓글 POST 64.4ms)과 그 트레이스가 끌고 온 알림 발행 경로
(`publish user.notifications` → chat-service `receive` 407ms)다. 대조군은 **성공 경로라서
span이 온전하다** — 실패 트레이스는 INSERT에서 끊기지만 성공 트레이스는 커밋·발행·소비까지 이어진다.

**즉 B-46의 비용은 "트레이스 1건"이 아니라 "성공 경로 전장"이다.** 이 문항에서는 그것이
근거로 쓰였으므로 값을 했지만(아래 3)·4)), **비용 항목으로는 B-37(트레이스 바이트 예산)의
측정 지점**이 된다.

### 로그 채널 37,139 B는 캡이 아니다 — 확인함

회차 5와 회차 6의 `errorWarnLogBytes`가 **37,139로 완전히 같다.** 다른 날 · 다른 창인데
같은 값이라 절삭 아티팩트를 의심해 원본을 열어 봤다.

| 원본 파일 | 엔트리 | 시각 범위 |
|---|---:|---|
| 회차 5 `…-loki-error-warn.json` | 221 | 2026-08-05T02:09:25.704Z ~ **.745Z** (41ms) |
| 회차 6 `…-loki-error-warn.json` | 221 | 2026-08-12T01:22:30.470Z ~ **.517Z** (47ms) |

**캡이 아니라 같은 스택트레이스다.** 두 회차의 ERROR/WARN 채널은 전부 **단일 예외 하나의
스택 221줄**이고, 같은 `DataIntegrityViolationException`이라 줄 수가 같다. 창 폭과 무관한 것도
당연하다 — 이 창에서 ERROR/WARN을 낸 사건이 그 하나뿐이다.

> **다만 이것 자체가 비용 항목이다** — 예외 1건이 로그 채널 37 KB를 전부 차지한다.
> B-34 로그 접기가 켜진 뒤의 수치이므로, **접기가 앱 프레임 보존 규칙 때문에 스택 대부분을
> 남기고 있다**는 뜻이다. 근거로 쓰인 프레임은 `FeedCommentService:64`·`FeedCommentController:53`
> 둘뿐인데 221줄을 실었다 → 회차 7 대기열 후보 ([다음 회차로 넘기는 것](#다음-회차로-넘기는-것) ②).

| 정합성 훼손 없음(롤백) | 충족 | *"트랜잭션이 `rollback`으로 종료되어 DB에 부분 데이터가 없다 — `tb_feed_comment` INSERT, `tb_feed.comment_count` 갱신, `tb_exp_history` 적립 모두 미반영이며 정합성 훼손은 없다"* |
| 한정된 실패 (전면 장애 아님) | 충족 | 대조군으로 논증 — *"코드/스키마 상태가 아니라 **요청 본문에 따라 갈리는** 실패다"* |
| 단건으로 특정 | 충족 | *"피해 범위(확인된 것): userId=1의 feedId=145 댓글 작성 1건 실패, 알림 미발행"* |
| *"200자 초과"* 수치 | **판정** | 수치를 못 썼다. 컬럼 폭이 관측에 없다 |

**→ 10점.** 5점 문언은 *"범위 유보"* 인데 리포트는 유보하지 않고 한정했다. *"200자"* 라는
숫자는 앵커 자신이 **Phase 4(코드 인지) 델타 측정 지점**으로 지정한 항목이라 관측만으로
도달 불가이고, 이것을 요건으로 읽으면 이 회차에서 원리적으로 못 받는 점수가 된다.

**반대 판정 시 5점 → 총점 95.** 리포트가 *"'1시간 동안의 모든 실패가 이 원인'은 중간으로
낮춘다"* 고 확신도를 내린 것을 범위 유보로 읽으면 그렇게 된다.

### 5) 오귀인 — 5 (판정)

| 점수 | 요건 |
|---|---|
| 5 | DB·인프라 오진 안 함 + **"DB는 제약을 지켰다"** 명시 |
| 3 | 후보로만 |
| 0 | DB 확정 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| 인프라 오진 안 함 | 충족 | 6종을 수치로 배제 — Hikari active/pending 전 구간 0 · `up`/`mongodb_up`/`kafka_brokers` 불변 · lag 0 · GC 1.67e-5 · 필터체인 12/12 통과 |
| 다른 문항 신호 오귀인 안 함 | 충족 | 같은 창의 AP-2 NPE(INC-4)를 *"댓글 실패 시각보다 9분 뒤 … 별건으로 남겨 둔다"* 로 기각 |
| *"DB는 제약을 지켰다"* 명시 | **판정** | 직접 문장은 없다. 대신 *"검증 없이 INSERT까지 내려가 **DB가 데이터 절단 오류로 거부**"* 로 DB가 정상 동작했음을 서술 |

**→ 5점.** 3점 문언은 *"후보로만"* — DB를 후보에 올려 두고 배제 논증을 안 한 경우다. 리포트는
배제를 수치로 했고, DB의 거부를 *결함이 아니라 정상 동작*으로 서술했다.

**반대 판정 시 3점 → 총점 98.** 후보 3(컬럼 폭 부족)을 "DB를 후보로 남긴 것"으로 읽으면 그렇다.

### 6) 조치 — 5

| 점수 | 요건 |
|---|---|
| 5 | `@Size(max=200)` + `DataIntegrityViolation` → 400 매핑 |
| 3 | 둘 중 하나 |

| 요건 | 판정 | 리포트가 쓴 것 |
|---|---|---|
| 길이 검증 추가 | 충족 | *"댓글 생성 DTO에 `@Size(max=…)`(= 컬럼 길이와 동일 값) + 컨트롤러 `@Valid`"* |
| 400 매핑 | 충족 | *"`GlobalExceptionHandler`에 `DataIntegrityViolationException` 전용 핸들러를 추가해 400 + 사유 응답. `handleAllException` 포괄 처리에서 빠지게 한다"* |

**→ 5점.** 판정 없음. 앵커에 없는 것도 하나 붙였다 — 포괄 핸들러로 떨어진 것을
Loki 로그(`handleAllException`)로 **관측해서** 지목했고, 그것을 후보 2(피해 확대 요인)로
독립 등재했다.
