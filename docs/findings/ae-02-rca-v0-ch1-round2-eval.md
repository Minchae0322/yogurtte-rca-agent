## AE-01 대비 무엇이 달라졌나

**원인 1줄을 확신도 높음으로 맞혔다**: "MongoDB 인스턴스 다운 — mongod가 리스닝하지 않아 Connection refused, 4회 실패 후 DLQ". 근거 경로도 모범적이다:

- 소비 4회가 각각 정확히 30.0초 = `serverSelectionTimeoutMS` 기본값과 대조 — 설정값을 근거로 쓴 추론.
- `Connection refused`(즉시 거절)와 timeout을 구분해 "호스트 생존, 27017 리스너 부재"까지 좁힘.
- **같은 호스트의 Redis(6379)가 0.5ms 정상**인 span을 반증으로 써서 호스트/네트워크 전면 장애를 배제 — 회차 1의 "다중 신호 대조" 능력이 원인 계층 분리로 확장됨.
- Kafka 배제(발행 14ms + 소비 4회 정상 수신), JDBC `acquired→rollback` 이벤트로 트랜잭션 결말까지 읽음.

회차 1과의 차이는 모델이 아니라 **입력 데이터의 질**이다: toy-chat `cdca2a5`/`5eecb0a`(Mongo 명령 트레이싱, 재시도/DLQ rethrow + 관측 로그) 이후 trace에 error span 4개와 예외 원문이 실렸다. 회차 1은 "무자식 공백 23초"뿐이라 가설(후보 2, 확신도 낮음)에 머물렀다 — **같은 장애도 계측이 자백하면 v0 단발 호출로 충분히 확정된다**는 대조 데이터.

또한 AE-01 결함 3(절대 시각 -120s 밀림)은 이번 리포트에서 **재발하지 않았다** (publish 08:21:31.410 = 실측 일치). 결정적 결함이 아니라 LLM 앵커링 변동일 가능성 — 어셈블 컨텍스트에 절대 시각을 명시하는 보강은 여전히 유효.

## 오판 1건 — 영향(impact) 판정

리포트: "알림은 지연이 아니라 **미발송(유실) 상태**" + "DLQ 재처리 컨슈머가 없다면 수동 재발행 필요". 실제: 재처리 리스너가 존재하고 08:25:07 성공, 유실 0. 오판의 원인은 에이전트가 못 보는 데이터 두 겹:

1. **DLQ 경계 trace 단절** ([NF-08](nf-08-dlq-trace-discontinuity.md)) — 재처리 사건들이 전부 `traceId=NONE`이라 원본 trace의 마지막 장면이 "DLQ 발행"이다.
2. **Loki 셀렉터 결함 지속** (AE-01 결함 1, 미수정) — `[Kafka] DLQ 알림 재처리` INFO 로그가 실재했지만 로그 0건으로 조사.

에이전트 스스로 조치 6에서 "예외 4회에 로그 0건은 수집 문제"라고 두 번째 항목을 짚었다. 신규 관측: chat pod의 Hikari 메트릭이 08:21:46 이후 끊김(타 서비스는 지속) — 회차 1에서도 동일 패턴, 원인 미규명 항목으로 남김.
