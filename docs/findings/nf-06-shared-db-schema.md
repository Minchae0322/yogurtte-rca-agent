# NF-06. chat 서비스가 `content` DB 스키마에 접속한다 — 서비스 경계 공유 의심

- 심각도: **중간** (아키텍처 경계 문제 — 즉각 장애 아님) | 상태: 로컬 설정 확정, prod 미확정
- 발견 경위: rca-agent **리뷰 모드가 "가설"로 제기** → 코드 확인으로 승격된 사례

## 관측

리뷰 모드가 트레이스에서 chat-service의 JDBC datasource 이름이 `content`인 점을 발견하고
"서비스 경계 침범 의심 (가설)"로 보고했다. 코드로 확인한 결과:

```yaml
# toy-chat/src/main/resources/application-local.yml:18
url: jdbc:mysql://localhost:3306/content?...     # chat 서비스가 content 스키마 사용
```

prod는 `${DB_HOST}/${DB_NAME}` env 주입이라 코드만으로는 미확정이다 — 다만 트레이스의
datasource 표기가 prod에서 관측된 값이므로 prod도 같은 스키마일 가능성이 높다.

## 왜 문제인가 (확정 시)

MSA에서 두 서비스가 한 스키마를 공유하면: 스키마 변경이 두 서비스의 동시 배포를
강제하고, 한 서비스의 슬로우 쿼리·락이 다른 서비스의 지연으로 전파되며(NF-04의 hot-row
락이 chat 알림 처리에 영향을 줄 수 있는 경로), 서비스별 독립 스케일링·장애 격리가
무너진다. "물리적으로는 MSA, 데이터로는 모놀리스" 상태다.

## 확인 방법

- [ ] prod의 `DB_NAME` env 값 확인 (k8s secret/configmap)
- [ ] chat이 접근하는 테이블 목록 추출 — content 소유 테이블을 직접 읽는지, 자기
      테이블(chat_*)만 같은 스키마에 두는지 구분 (후자는 심각도 낮음)
- [ ] 직접 읽는다면: 해당 데이터의 소유권 정의 후 API/이벤트 경유로 전환 검토

## 기록 이유

에이전트가 **트레이스 메타데이터에서 아키텍처 경계 문제를 가설로 제기**하고, 사람이
코드로 승격 확인한 흐름 자체가 리뷰 모드의 가치 증명이다 — 성능 수치만이 아니라 구조
신호도 잡는다.
