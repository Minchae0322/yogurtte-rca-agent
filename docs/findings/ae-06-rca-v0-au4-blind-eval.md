## 잘한 것

- **원인을 계층으로 분리했다.** 후보1 = 직접 원인("Connection refused → 작성자 배치 조회 실패
  → content가 삼킨 채 익명 폴백 렌더링", 확신도 높음), 후보2 = 상위 원인("auth 파드/엔드포인트
  부재 — 후보1의 상위 원인", 중간). 5회까지의 조사에서 없던 구조다.
- **timeout과 RST를 구별했다.** "구간 `.329514 ~ .353060` = **23.5ms 즉시 실패**(타임아웃이
  아니라 TCP RST)". **앵커가 요구한 "3s timeout"을 찾는 대신 그것이 틀렸음을 정정한 셈**이다.
  CH-1 회차2의 "`Connection refused`는 타임아웃이 아니라 즉시 거절" 추론이 재현됐다.
- **캐시 미스를 방아쇠로 특정했다.** 실패 직전 Redis `GET` 4건이 조회 대상 4명(`3,7,9,56`)과
  개수가 일치함을 근거로 "캐시 미스 4건 → 원격 배치 조회 → 실패"를 재구성. **문항의 핵심
  변별점(캐시 만료가 AU-2와 AU-4를 가른다)에 데이터로 도달했다.**
- **메트릭 부재를 대조군과 함께 제시했다.** "3종 메트릭 전부에서 auth-service 시리즈가 단 한
  개도 없다. chat·content는 전 구간 17개 데이터포인트가 모두 채워져 있다" — AU-2·CH-2에 이어
  세 번째. **부재 신호 활용은 이제 재현되는 능력이다.**
- **자기 한계를 정확히 표명했다.** ① "'실패 → `사용자{id}` 문자열 생성'이라는 마지막 고리는
  코드/로그로 확인되지 않은 추론", ② "대상 ID가 `3,7,9,56`으로 제보된 `사용자123`과 직접
  일치하지 않는다 — **제보 건 자체를 관측한 것은 아니다**", ③ "`hikaricp_connections_active=0`은
  15초 샘플링이라 122ms짜리 커넥션 점유를 놓친 값이다 — '트래픽 없음'의 근거로 쓰면 안 된다".
  ③은 **자기가 인용하는 지표의 해상도 한계를 스스로 제한**한 것으로, 이전 회차에 없던 수준이다.
- **핵심 발견을 독립적으로 도출했다.** 조치 9: "현재는 외부 의존성이 완전히 죽어도
  `200 SUCCESS`로만 관측되어 알림이 전혀 울리지 않습니다. 이번 건의 실질적 재발 방지 항목입니다."
  — 우리가 실측으로 확인한 "조용한 fallback"과 같은 결론이다.
- **부수 발견**: 실패한 `http get` span의 부모가 JDBC `connection` span이다 → **DB 커넥션을
  쥔 채 외부 HTTP 호출**. 이번엔 23.5ms라 무해했지만 auth가 *느려지는* 장애였다면 풀 고갈로
  번졌을 구조. [NF-01](nf-01-consumer-holds-connection-during-dispatch.md)과 같은 계열이
  content 읽기 경로에도 있음을 에이전트가 먼저 지적했다.

## 못한 것

**없다고 봐야 한다.** 채점된 3항목이 전부 만점이고, 채점 불가한 근거 경로 항목도 에이전트
귀책이 아니다(앵커가 틀렸다).

굳이 꼽자면 후보3(Redis negative caching)이 이번 증상의 원인이 아니지만, 이는 "auth 복구
후에도 익명이 잔존하는가"라는 **별개 증상**에 대한 확신도 낮음 가설이고, 스스로 "이 트레이스에
Redis 쓰기 스팬이 없다"고 반증까지 붙였다. 오귀인으로 볼 수 없다.

## 이 회차가 드러낸 앵커 결함

v1·v2 앵커 모두 근거 경로 만점 요건이 **사실과 다르다**:

| 앵커 요건 | 실측 |
|---|---|
| user client span **timeout(3s)** | ❌ **23.5ms connection refused**. `.timeout(3s)`는 대기 상한이라 RST에는 발동조차 안 함 |
| **fallback 로그** | ⚠️ 로그는 **존재한다**(`ExternalUserApiClient.java:130` `.doOnError`). 그러나 **`traceId=NONE`**(리액티브 스레드로 MDC 미전파)이라 traceId 기반 조사로는 도달 불가. 하네스 프로브 정규식도 실제 메시지와 불일치 → [NF-09](nf-09-user-fallback-no-traceid.md) |
| `GET user-service` client span (RUNBOOK) | ❌ span 이름은 `http get`, 서비스 식별은 `client.name` 속성 |

원인은 **앵커를 코드 상수만 보고 쓴 것**이다. [AE-05](ae-05-rca-v0-au2-blind-eval.md)에서
"앵커 작성 전 소급 채록이 선행되어야 한다"고 교훈을 적어놓고 AU-4에서 반복했다.
상세는 [채점 대장 결함 ⑩](../scoring/README.md).

## 6회 조사로 갱신된 패턴

1. **"부재 신호를 못 쓴다"는 폐기한다.** CH-2·AU-2·AU-4 세 회차 연속으로 부재 신호(시계열
   소멸·span 부재·로그 0건)를 대조군과 함께 근거로 사용했다. AE-03이 3회 기준으로 세운
   명제는 더 이상 유효하지 않다.
2. **비용이 내려가고 있다.** $1.0845 → $1.02 → $0.9040 → $0.9237 → $0.8357 → **$0.7089**.
   프롬프트·모델은 동일하므로 컨텍스트 구성과 캐시 히트율의 영향으로 보이며,
   이번엔 cwd 격리(CLAUDE.md 제거)가 더해졌다. **P4 부분 검증** — AU-2와 컨텍스트 크기가
   거의 같은데(65,366자 vs 65,958자) 입력 토큰이 3,886 줄었다. 다만 두 조사의 컨텍스트가
   정확히 같지 않아 순수 비교는 아니다.
3. **Loki 셀렉터 결함 6회 연속.** 다만 이번 문항에서는 셀렉터를 고쳐도 fallback 로그는
   나오지 않는다 — **앱에 로그가 없기 때문**이다. 도구 결함과 계측 공백을 구별해야 한다.
4. **`-120s` 시각 밀림 미재발** (6회 중 3회 재발). 이번 리포트는 raw ns를 정확히 변환했다.
