# NF-05. 같은 리소스가 두 게이트웨이 경로에서 서로 다른 응답을 반환한다

- 심각도: **중간** (API 표면 모호성 — 기능 장애는 아님) | 상태: 관측 확정, 원인 미해명
- 위치: 게이트웨이 라우팅 (`/api/auth/**` vs `/api/user/**`)

## 관측 (API 순회, 2026-07-24, 각 200 OK)

| 경로 | 응답 크기 |
|---|---|
| `GET /api/user/1/profile` | **6,641 B** |
| `GET /api/user/user/1/profile` | **6,641 B** (위와 동일) |
| `GET /api/auth/user/1/profile` | **504 B** (다른 응답) |

세 경로 모두 200인데, 두 가지 이상이 겹쳐 있다:

1. **같은 프리픽스에서 경로 중복 허용**: `/api/user/1/...`과 `/api/user/user/1/...`이
   동일 응답 — 게이트웨이 rewrite가 중복 세그먼트를 허용하는 것으로 보인다.
2. **다른 프리픽스에서 다른 응답**: `/api/auth/user/1/profile`은 크기가 13배 작은 별개
   응답이다. auth 서비스에 별도의 축소된 profile 엔드포인트가 있거나, 라우팅이 의도치
   않은 컨트롤러에 닿고 있다.

## 왜 문제인가

기능은 "동작"하지만, **어떤 클라이언트가 어느 경로를 쓰든 200이 나온다**는 것이 위험이다.
잘못된 경로가 조용히 성공하면 (a) 클라이언트마다 다른 형태의 profile을 보게 되고,
(b) 권한·필드 노출 정책이 경로에 따라 갈라질 수 있으며, (c) 훗날 라우팅 정리 시 어떤
클라이언트가 깨질지 파악할 수 없다. API 표면은 좁고 명시적이어야 한다.

## 확인 방법 (미해명 부분)

- [ ] 두 응답 body를 diff — 504B 응답이 어떤 DTO인지, 민감 필드 차이가 있는지
- [ ] 게이트웨이(nginx/인그레스) 라우팅 규칙에서 `/api/auth/**`, `/api/user/**`의
      rewrite 대상 서비스 확인
- [ ] auth 서비스에 `/user/{id}/profile` 컨트롤러가 실제로 존재하는지
      (toy-auth-user-region `UserController`는 `/user` 매핑 — 존재 가능성 높음)
- [ ] toy-client가 실제 쓰는 경로 확정 후, 나머지 경로는 404/301로 닫기

## 개선 검증 방법

정리 후 api-sweep 재실행 시 표준 경로 1개만 200, 나머지는 404 — sweep 스크립트에 세
경로가 모두 들어 있어 회귀 확인이 자동으로 된다.
