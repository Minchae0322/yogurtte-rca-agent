content의 `JWT_SECRET`만 auth와 어긋난 상태. auth는 시크릿 A로 서명하고 content는 B로

## 1. 문항 정의

| | |
|---|---|
| **주입** | content 시크릿의 `JWT_SECRET`만 교체 + `rollout restart` |
| **전개** | auth는 정상 서명 → content가 다른 키로 검증 실패 |
| **결말** | **로그인은 성공**, 인증이 필요한 API만 전부 실패 |
| **사용자 영향** | **전 사용자** — RUNBOOK 권장 순서가 이 문항을 맨 마지막에 두는 이유 |
| **질문 문안** (박제) | `"<시각>부터 앱이 자꾸 로그인 화면으로 튕긴다는 문의가 많아요"` |
| **hop** | 1 |

## 2. 이 문항이 어려운 이유 — **전제가 반증됐다**

앵커의 설계 의도는 *"어느 한 채널도 단독으로 답을 주지 않는다"* 였다. trace는 상태만,
로그는 실패 지점만, rate는 범위만 준다 — 그래서 **"무엇을 봤는가"가 아니라 "무엇을
배제했는가"**로 요건을 썼다.

| 요건 | 죽이는 가설 | 채널 |
|---|---|---|
| ⓐ 필터 단계에서 끊김 | **앱 버그** | trace |
| ⓑ 실패 사유가 서명/키 불일치 | **토큰 만료** ← 핵심 함정 | Loki |
| ⓒ 전역 급증 | **개별 요청·사용자 문제** | Mimir |

**그런데 회차 2 게이트에서 이 전제가 무너졌다.** 앱이 서명 예외를 못 잡아 401이 아니라
**500**을 냈고, 그러면 `status=error`로 Tempo에 걸리며 `exception=SignatureException`이
span에 **축자로 실린다**. 핵심 함정("만료 오판")이 함께 소멸해 AP-3급 문항이 된다.

**처방은 앵커가 아니라 앱이었다.** 다른 앵커 결함들은 *"관측이 앵커를 못 따라간다"* 라
요건을 낮추는 쪽이지만, 이건 *"앱이 앵커대로 동작하지 않았다"* 였다.
수정([round-3 A-0](../round-3/README.md))으로 401이 복구되면 앵커 v2가 **원래 문언 그대로
성립한다** — 그래서 개정하지 않고 검증 후 재확인한다.
