## 참고 채점 — 83 / 100 (§1.1상 정식 아님)

**이 점수는 채점 대장에 올리지 않는다.** 세 가지가 정식 요건에 걸린다:
① 앵커가 채록 **뒤에** 박제됐다(사후 앵커 채점은 §1.1상 무효),
② 질문 문안("어젯밤(8월 17일) 밤 11시 전후로 …")이 박제본과 다르다,
③ N=1이라 §8.1상 인용 보류다.
그럼에도 숫자를 남기는 이유는 하나 — **회차 2 baseline의 예측치**가 되기 때문이다.

## 사슬 대조 — 에이전트가 찾은 것과 못 찾은 것

| 정답 사슬 | 도달 | 리포트가 쓴 것 |
|---|---|---|
| 재로그인 폭주 (트리거) | 도달 | 후보 2 "동시성 급증" — 톰캣 스레드 exec-2→148 단조 증가, 대기행렬 포화의 전형으로 추론 (확신도 중간) |
| CPU 포화 | **미도달** | 후보 자체에 없음. "auth 파드 CPU/스로틀링" 계측을 재발 방지 1순위 공백으로 요구 |
| 건당 점유 시간 증가 | 도달 | 후보 3 — Little의 법칙(190/30 ≈ 6.3 req/s, 커넥션 10개 → 약 1.6초/건)으로 평시 147ms와 불일치 논증 (확신도 낮음) |
| 풀 고갈 → pending 190 → 30초 타임아웃 → 500 | 도달 | 후보 1 확정 — active=10 상수 + pending 곡선 + `Connection is not available, request timed out after 30000ms` 원문 + 만료 3건 500 / 미만료 17건 200 분해 |
| 톰캣 스레드 전점유 → 전체 경화 | 도달 | "190개 요청이 30초씩 스레드를 점유해 장애를 증폭" + bulkhead·빠른 실패 제안 |

**미도달 한 고리는 추론 실패가 아니라 신호 공급 실패다.** `metric-queries`에 CPU 지표가
없어 컨텍스트에 실리지 않았고, 신호는 같은 Mimir에 실재한다(위 실측). 점유 시간 팽창이라는
**그림자는 계산으로 봤으면서** 그 원인에 이름을 붙이지 못한 것 — CH-2(메트릭 미수집으로
채점 불가)와 같은 구조의 재현이다. → **B-59**.

이 회차가 덤으로 해결한 것: T2-A가 미해결로 남긴 "실패 666건이 CF 504인가 서버 500인가"에
부분 답 — `[HTTP] POST /api/login 500 - 30210ms`류 서버측 로그로 최소 일부는 Hikari
타임아웃발 진짜 500임을 확인했다.
