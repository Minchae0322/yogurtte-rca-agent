# ADR-006. 조사마다 토큰·비용·수집범위를 리포트에 기록한다 (+ 토큰 회계 버그 수정)

- 날짜: 2026-07-22
- 상태: 채택 (구현·실측 검증 완료)
- 관련: `RcaReport.Coverage`, `LlmResult`, `ClaudeCliLlmClient.parse()`

## 배경

전략의 대원칙은 "모든 개선을 before/after 숫자로 증명한다"이다. 그러려면 조사 한 건이
**무엇을 얼마나 읽고, 몇 토큰을 쓰고, 얼마가 들었는지**가 리포트에 남아야 한다.
초기 리포트에는 토큰 수가 있었지만 실측 중 명백한 이상값을 발견했다: 41,055자
컨텍스트를 보냈는데 `in=2`로 기록되고 있었다.

## 토큰 회계 버그 — 원인과 수정

claude CLI의 usage는 프롬프트 캐시를 쓰면 입력을 세 필드로 쪼갠다:
`input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens`.
대형 컨텍스트는 거의 전부 캐시 필드로 계상되므로 `input_tokens`만 읽으면 입력이
사실상 0으로 보인다. 셋을 합산하도록 수정하고 CLI가 보고하는 `total_cost_usd`도
함께 기록했다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 입력 토큰 | **2** | **42,774** |
| 출력 토큰 | 4,499 | 5,056 |
| 비용 | (미기록) | $0.4272 |

측정이 틀리면 이후 모든 개선 판단이 틀린다 — 하네스 자체를 먼저 검증해야 한다는
사례로 남긴다.

## Coverage 설계 — "무엇을 읽었나"를 리포트의 1급 데이터로

품질/비용을 개선하려면 결과(분석 텍스트)만이 아니라 **입력의 범위**가 비교 가능해야
한다. 조사마다 다음을 기록한다:

- 조회 시간창 (start/end/초)
- 트레이스: 바이트, span 수, 크기 초과로 상위 span만 넣었는지(trimmed)
- 로그: 쿼리별 바이트 (ERROR/WARN, traceId 매칭)
- 메트릭: 수집된 쿼리 목록 vs 누락된 쿼리 목록
- 컨텍스트: 문자 수 + 러프 토큰 추정치(chars/4)

리포트는 `.json`(기계 분석용)과 `.md`(사람이 읽는 보고서)로 동시 저장되고,
`promptSource`로 어떤 프롬프트 버전이 쓰였는지 추적된다. 실측 재현성: 동일 조사
2회에서 입력 토큰 42,774 vs 42,651 (편차 ±0.3%) — 비교 지표로 쓸 만큼 안정적이다.

## 관찰 — 추정치와 실측의 4배 괴리 (후속 과제)

컨텍스트 41,017자에서 추정 토큰은 10,254(4자/토큰 가정)인데 실측 입력은 42,774다.
가설 두 가지: (1) 한국어·JSON 혼합 텍스트는 토큰 밀도가 4자/토큰보다 훨씬 낮다,
(2) claude CLI가 자체 시스템 프롬프트/도구 정의를 얹으며 이것이 캐시 생성 토큰으로
계상된다. 어느 쪽이 지배적인지는 미확인이며, 추정치는 하한선으로만 취급한다.
API provider(순수 입력만 계상)와의 비교 실측이 이 괴리를 분해해 줄 것이다 —
Phase 3에서 확인할 항목으로 남긴다.
