# AI 장애 원인분석 에이전트 — 장애 시나리오별 평가 보고서

작성일 2026-07-28 · 대상 `rca-agent` v0 (baseline)

---

## 1. 요약

관측 데이터(트레이스·로그·메트릭)만으로 장애 원인을 지목하는 AI 에이전트를 만들고,
**실제로 장애를 주입해 정확도를 채점했다.** 이 문서는 12개 장애 시나리오의 정의와
채점 기준, 그리고 현재까지의 결과를 정리한 것이다.

| 항목 | 현황 |
|---|---|
| 정의된 장애 시나리오 | 12개 (실행 8 · 미실행 4) |
| 조사 완주 | 9회 |
| 유효 채점 | 5회 — 평균 **82점** / 100점 |
| 채점 불가 | 3회 (+ 폐기 1회) — 전부 **채점 기준의 결함** |
| 채점 유보 | 1회 — 기준 미확정 상태에서 실행 |

**핵심 결론 세 가지.**

**첫째, 에이전트의 정확도보다 평가 기준의 품질이 먼저 문제가 됐다.** 채점 불가 4건은
모두 에이전트가 아니라 채점 기준(앵커)의 결함에서 발생했다. 기준 부적합률을
추적 지표로 삼아 **67%에서 33%로 개선**했다.

**둘째, 현재 점수는 대외 인용이 불가능하다.** 시나리오당 최소 2회 반복이 규정인데
유효 채점 5회가 전부 1회차다. 같은 버전의 에이전트가 같은 장애에서 **75점과 95점**을
낸 사례가 있어, 반복 없는 단일 점수는 신뢰할 수 없다.

**셋째, 점수를 올린 것은 에이전트 개선이 아니라 조사 도구 수정이었다.** 로그 조회가
6회 연속 0건이던 원인을 찾아 고치자, **채점 기준을 한 줄도 바꾸지 않은 채로**
5개 시나리오가 채점 가능 상태로 전환됐다.

### 1.1 이 시스템의 경계 — 무엇을 만들었고 무엇이 아닌가

**현재 버전은 traceId를 입력으로 받는다.** "이 요청이 왜 이렇게 됐는가"에 답하는
**설명 엔진**이고, "어젯밤 오류를 찾아달라"에 답하는 **탐색 엔진은 아니다.**

이는 구현 누락이 아니라 **의도된 범위 설정**이다. 트레이스·로그·메트릭의 조회 시간창이
입력 트레이스에서 파생되는 구조이며, 그 덕분에 수집이 결정적이고 회차 간 재현이 성립한다.
측정을 먼저 세우기 위한 선택이었다.

**다만 실무에서 장애가 나면 traceId를 아는 사람이 없다.** 조사는 알람이나 사용자 증상에서
시작하고, 담당자가 대시보드에서 *시간대 + 에러 조건*으로 뒤져 traceId를 찾아낸다.
**그 뒤지는 행위가 원인 분석의 절반이고, 현재 시스템은 그 절반이 끝난 상태를 입력으로 받는다.**

| | 현재 | 다음 단계 |
|---|---|---|
| 입력 | traceId + 자연어 질문 | **자연어만** ("어젯밤 알림이 안 왔어요") |
| 시간창 | 트레이스에서 파생 | 자연어에서 파싱 |
| 대상 선정 | 사람이 지정 | 창 안을 훑어 이상 후보 랭킹 |
| 원인 분석 | 구현 완료 | 그대로 재사용 |

**탐색은 부가 기능이 아니라 성능의 절반이며, 채점 대상이다.** 이 프로젝트의 북극성 지표는
"원인 적중률(Top-1)"인데, **현재 점수는 대상이 주어진 상태의 적중률이므로 반쪽만 재고 있다.**
자연어에서 시작해 원인에 도달하는 비율이 제품의 성능이고, 그것이 최종 인용 숫자가 되어야 한다.

```
자연어 질문 → [탐색] 대상 선정 → [분석] 원인 랭킹 → 정답 도달 여부
                                                    = 원인 적중률(Top-1)
```

**단 두 단계는 분해해서 기록한다 — 덜 중요해서가 아니라 귀인 때문이다.** 한 점수에 합치면
점수가 떨어졌을 때 *못 찾은 것*인지 *찾고도 못 푼 것*인지 알 수 없어 무엇을 고칠지
정할 수 없다. 인용은 end-to-end로, 진단은 두 트랙으로 한다.

탐색이 틀렸을 때도 **에이전트가 실제로 고른 대상으로 분석 점수를 매긴다.**
"엉뚱한 걸 골랐지만 그 안에서는 제대로 분석했다"와 "잘 골랐는데 분석을 망쳤다"는
end-to-end로는 똑같이 실패지만 **처방이 정반대**이기 때문이다.

**현행 배점(40·30·20·10)은 건드리지 않는다.** 탐색을 5번째 항목으로 넣어 100점을
재분배하면 기존 9회와 비교가 끊긴다. 탐색은 자체 루브릭을 갖는 별도 트랙으로 둔다.

**그리고 탐색은 장애 주입 없이 평가할 수 있다.** 과거 9회 조사의 정답이 이미 기록돼 있다 —
주입 시각(`timeline.log`), 실제 traceId(회차 리포트), 정답 원인(`answer.md`).
*"이 시각 무렵에 이상이 있었는데 찾아달라"*를 던져 실제 traceId가 후보 상위에 뜨는지 보면 된다.
정상 구간을 함께 던지면 **오탐 검증(§5.2)까지 같은 트랙에서 해결된다.**

→ 설계와 진입 조건은 [strategy.md Phase 4.5](../strategy.md).

## 2. 평가 체계

### 2.1 배점

| 항목 | 배점 | 무엇을 보는가 |
|---|---|---|
| 1) 근본 원인 정확도 | 40 | 진짜 원인에 도달했는가. 증상이 아니라 원인인가 |
| 2) 근거 시그널 경로 | 30 | 어떤 관측 데이터로 그 결론에 이르렀는가 |
| 3) 오귀인 없음 | 20 | 무관한 컴포넌트를 원인으로 지목하지 않았는가 |
| 4) 조치 타당성 | 10 | 제시한 조치가 실제 원인에 대응하는가 |

### 2.2 운영 원칙

**블라인드 평가.** 에이전트에게는 traceId와 자연어 질문만 준다. 정답지와 채점 기준은
에이전트가 읽는 경로에 두지 않는다. 자기 채점은 무효로 처리한다.

**기준 선박제.** 채점 기준은 장애 주입 **전에** 확정한다. 결과를 보고 기준을 고치면
그 회차는 무효이고, 개정은 다음 회차부터 적용한다.

**반복 측정.** 시나리오당 최소 2회. 점수는 평균과 최대편차로 기록하고,
편차가 ±10을 넘으면 해당 시나리오를 불안정으로 보고 인용을 보류한다.

**도구 제약을 면제하지 않는다.** 조사 도구가 특정 신호를 수집하지 못해 만점에
도달할 수 없어도 요건을 유지하고 그대로 감점한다. 면제하면 도구를 고쳤을 때
개선폭이 측정되지 않기 때문이다.

**근거는 개수가 아니라 충분성으로 잰다.** 요건은 확인할 신호의 목록이 아니라
"원인을 확정하기에 충분한 근거 집합"으로 작성한다. 같은 사실을 담은 로그와
트레이스는 동치로 취급하고, 어느 경로로 도달하든 같은 점수를 준다.

## 3. 장애 시나리오 총괄

시스템은 3개 서비스로 구성된다 — **콘텐츠**(피드·댓글), **인증**(로그인·사용자 정보),
**채팅**(실시간 알림). 이들은 Kafka로 이벤트를 주고받고, Redis를 캐시로,
MySQL과 MongoDB를 저장소로 공유한다. 장애는 이 중 한 곳에 주입한다.

### 3.1 실행 완료

| ID | 주입한 장애 | 시스템에서 일어나는 일 | 사용자 증상 | 결과 |
|---|---|---|---|---|
| **CH-1** | MongoDB 4.5분 중단 | 알림 저장이 실패하고 소비자가 재시도를 소진해 실패 큐(DLQ)로 넘긴다. DB 복구 후 재처리되어 결국 도착한다 — **유실이 아니라 지연**이다 | 알림이 뒤늦게 도착 | **80** |
| **CH-2** | 알림 소비자 전부 중단 | 발행측은 정상이라 메시지는 계속 쌓이는데 **가져가는 쪽이 없어** 적체된다. 소비자 복구 시 밀린 알림이 한꺼번에 처리된다 | 알림이 한동안 안 오다가 몰려서 옴 | 채점 불가 |
| **IN-2** | Kafka 브로커 7분 21초 중단 | 댓글은 DB에 정상 저장되지만, **커밋 이후 발행되는** 알림 이벤트가 실패한다. 재시도 경로가 없어 그대로 사라진다 | 댓글은 잘 달렸는데 상대방에게 알림이 안 감 | **80** |
| **AU-2** | 인증 서버 전면 중단 | 로그인은 503으로 실패한다. 그런데 콘텐츠 서비스는 **사용자 정보 캐시가 살아 있어** 인증 서버를 아예 호출하지 않으므로 멀쩡히 동작한다 | 로그인은 안 되는데 앱은 정상으로 보임 | 채점 불가 |
| **AU-4** | 인증 서버 중단 + **캐시 TTL 10분 경과** | 캐시가 비자 콘텐츠 서비스가 인증 서버를 직접 호출하는데 서버가 없어 **23.5ms 만에 연결이 거절**된다. 대체 로직이 작동해 작성자명을 익명으로 채운다 — **의도된 품질 저하** | 댓글 작성자가 전부 "사용자123" 같은 익명으로 표시 | **75** |
| **AP-1** | 250자 댓글 등록 | 애플리케이션에 길이 검증이 없어 201자가 통과하고, DB 컬럼 한계(200자)에 걸려 INSERT가 실패한다. **DB 장애가 아니라 앱의 검증 누락**이다 | 긴 댓글을 쓰면 500 오류 | **75** |
| **AP-2** | 팔로우 목록 조회 (파라미터 생략) | 페이지 크기 파라미터의 기본값이 적용되지 않아 `null`이 전달되고, 계산 과정에서 NPE가 난다. **DB에 가기도 전에 죽는다** | 팔로우 목록이 500 오류 | 채점 유보 |
| **AP-3** | `coffee`와 `COFFEE`를 함께 등록 | 앱이 소문자로 정규화하므로 둘은 같은 값이 되는데, **중복 제거를 하지 않아** 같은 행을 두 번 INSERT해 유니크 제약을 위반한다 | 게시글 등록이 500 오류 | **100** |

### 3.2 실행 예정

| ID | 주입할 장애 | 시스템에서 일어나는 일 | 시험 목적 |
|---|---|---|---|
| **CH-3** | MongoDB **20~25초** 중단 | 드라이버 대기 상한(30초) 안에 복구되어 **첫 시도가 예외 없이 성공**한다. 재시도도 DLQ도 발동하지 않는다 | **오류가 하나도 없는 장애.** 유일한 신호는 설명되지 않는 시간 공백이다. CH-1과 쌍으로 지연/유실 구별을 시험 |
| **IN-1** | Redis 중단 | 콘텐츠는 캐시 미스로 인증 서버 직접 호출이 늘고, 채팅은 접속 상태 관리가 깨진다. **서비스마다 증상이 다르다** | 표면상 별개인 장애 3건을 **단일 근원으로 수렴**시키는가 |
| **IN-3** | 부하로 DB 커넥션 풀 고갈 | 요청이 커넥션을 얻지 못해 대기한다. **DB 서버는 정상**이고 대기는 쿼리 앞에서 발생한다 | "DB가 느림"과 "커넥션을 못 얻음"을 구별하는가 — 처방이 정반대다 |
| **AU-3** | 콘텐츠 서비스의 JWT 시크릿만 변경 | 인증 서버는 기존 키로 서명하고 콘텐츠는 새 키로 검증하므로 **로그인은 성공하는데 인증 API는 전부 401** | 설정 드리프트를 **토큰 만료와 구별**하는가. 사용자 증상이 동일해 관측으로만 갈라야 한다 |

### 3.3 보류

| ID | 장애 | 보류 사유 |
|---|---|---|
| AU-1 | 인증 서버 CPU 기아 | **증상 재현이 노드 부하에 좌우됨.** CPU 제한값이 응답을 타임아웃 임계(3초) 너머로 밀어낼 보장이 없고, 못 넘기면 증상 자체가 발생하지 않는다. 주입 강도와 증상이 비선형이라 반복 측정이 성립하지 않는다 |

## 4. 장애별 상세

### CH-1 — MongoDB 다운에 따른 알림 지연

**장애 상황.** 알림 저장소인 MongoDB를 4.5분간 중단시켰다. 알림 소비자가 저장에
실패하고 재시도를 소진한 뒤 DLQ(처리 실패 큐)에 적재했다. MongoDB 복구 후
재처리되어 알림은 10분 안에 도착했다. **댓글 작성 API 자체는 200으로 정상 응답한다.**

**함정.** API가 정상이므로 "장애 없음"으로 결론짓기 쉽다. 그리고 DLQ에 들어간 것을
"유실"로 오판하기 쉽다. 실제로는 지연이지 유실이 아니다.

| 항목 | 만점 요건 | 부분점 |
|---|---|---|
| 1) 근본 원인 40 | MongoDB 다운 → 소비자 실패 → 재시도 소진 → DLQ 적재 → **복구 후 재처리로 10분 내 도착** 판정까지 | 30: 도착 여부 미판단 / 20: 오판 |
| 2) 근거 경로 30 | MongoDB 예외 → 재시도 N회(각 30.0초를 드라이버 설정값과 대조) → DLQ 발행 구간을 **한 트레이스로 연결** + 재처리 도착 근거 | 20: DLQ까지만 / 10: 로그만 |
| 3) 오귀인 20 | 댓글 200을 "장애 없음"으로 오판하지 않음 + Kafka 미지목 | — |
| 4) 조치 10 | MongoDB 복구 + DLQ 적재분 처리 방침 | 5: 복구만 |

**결과 — 80점 (회차 2)**

| 항목 | 점수 | 판정 |
|---|---|---|
| 근본 원인 | 20 / 40 | 4개 요건 중 3개 충족. **"유실 없음"을 정반대로 오판** |
| 근거 경로 | 30 / 30 | 예외 → 30.0초 × 4회 → DLQ 구간을 한 트레이스로 연결. 재시도 간격을 드라이버 설정값과 대조한 것은 요건 이상의 정밀도 |
| 오귀인 | 20 / 20 | Kafka 자체 장애를 발행 성공 14ms를 근거로 배제 |
| 조치 | 10 / 10 | MongoDB 복구 + DLQ 재처리 방침 |

**감점 20점 전액이 영향 판정에서 나왔다.** 원인 규명과 근거 추적은 정확했으나,
"사용자에게 어떤 영향이 갔는가"를 반대로 판단했다. 원인 분석과 영향 판정이
별개 역량임을 보여주는 사례다.

### AU-2 — 인증 서버 전면 다운

**장애 상황.** 인증 서비스를 완전히 내렸다. 로그인은 503으로 실패한다.
그런데 콘텐츠 서비스는 **사용자 정보 캐시가 살아 있어 정상 동작한다.**
피드도 댓글도 실명으로 정상 노출된다.

**함정.** 이 시나리오는 **트레이스로는 원리적으로 도달할 수 없다.** 인증 파드가

콘텐츠 트레이스는 평시와 구조적으로 동일하다 — 캐시 히트라 인증 서버를

| 3) 오귀인 20 | 콘텐츠 미지목(200 유지·지연 무변화 근거) + 게이트웨이 오인 안 함 |

### AU-4 — 인증 서버 다운 + 캐시 만료

**장애 상황.** AU-2와 같은 인증 서버 다운이되, **캐시 TTL 10분이 만료될 때까지
유지했다.** 캐시가 비자 콘텐츠 서비스가 인증 서버를 직접 호출하고,
파드가 0개라 **23.5ms 만에 TCP 연결이 거절된다.** 대체 로직이 작동해
작성자 이름이 "사용자N" 익명으로 표시된다. HTTP는 200을 유지한다.

**함정.** 익명 표시는 **장애가 아니라 대체 로직이 의도대로 버틴 결과다.**
이를 붕괴로 오판하면 감점된다. 또한 실패 방식이 타임아웃이 아니라 즉시 거절이라는
점이 AU-1(느려짐)과의 감별 지점이다.

| 항목 | 만점 요건 |
|---|---|
| 1) 근본 원인 40 | 인증 전면 다운 + **캐시 만료**로 직접 호출 발생 → 대체 로직 발동. **두 조건의 결합**까지 |
| 2) 근거 경로 30 | (a) **실패 방식 구별**(즉시 거절 vs 타임아웃) (b) 대체 로직 진입 로그 (c) 익명 전환 |
| 3) 오귀인 20 | 콘텐츠·Redis 미지목 + **익명 표시를 "정상 동작"으로 인식** |
| 4) 조치 10 | 인증 복구 + **캐시 TTL·워밍 검토** |

**결과 — 75점**

| 항목 | 점수 | 판정 |
|---|---|---|
| 근본 원인 | 30 / 40 | 인증 다운은 확정. **캐시 만료라는 발현 조건 미언급** — 관측 불가가 아니라 놓친 것 |
| 근거 경로 | 20 / 30 | 3종 중 2종. 실패 방식 구별 충족, 익명 전환 충족 |
| 오귀인 | 20 / 20 | 200을 품질 저하(graceful degradation)로 정확히 프레이밍 |
| 조치 | 5 / 10 | 인증 복구만 — 캐시 TTL·워밍 검토 없음 |

**이 시나리오는 반복 측정의 필요성을 실증했다.** 같은 버전의 에이전트가 두 번
실행됐는데 **75점과 약 95점으로 벌어졌다.** 원인은 버전 차이가 아니라 출력 분량이었다
(2,980자 vs 10,511자). 짧게 답한 실행이 요건을 빠뜨렸다. **단일 실행 점수는
에이전트의 능력이 아니라 그날의 서술 분량을 재고 있을 수 있다.**

또한 이 시나리오는 **채점 기준이 틀리고 에이전트가 맞은 첫 사례**를 남겼다.
초기 기준은 "3초 타임아웃"을 만점 요건으로 요구했으나, 실제 관측은 23.5ms 연결
거절이었다. 에이전트가 리포트에서 "타임아웃이 아니라 TCP 거절"이라고 지적했고,
확인 결과 에이전트가 옳았다. 기준은 코드의 설정 상수만 보고 작성돼 있었다.

### AP-1 — 길이 제한 초과 댓글

### AP-2 — 파라미터 기본값 누락에 의한 NPE

언박싱 NPE가 발생해 500이 난다. **DB는 관여하지 않는다 — SQL이 실행되기 전에 죽는다.**

**함정.** 이 시나리오의 핵심 함정은 **DB 구간이 트레이스에 없다는 사실**이다.
이를 "DB 호출이 실패했다"로 읽으면 정반대 결론에 도달한다. 실제로는
"DB까지 가지도 못했다"는 뜻이다.

| 1) 근본 원인 40 | 파라미터 기본값 누락 → 언박싱 NPE 특정 + **DB 무관(SQL 미실행)** 명시 |
| 2) 근거 경로 30 | 오류 트레이스의 위치(DB 구간 부재) + **NPE 스택의 해당 메서드 지목** |
| 3) 오귀인 20 | DB·커넥션·데이터 오진 안 함 (**이 시나리오의 핵심 함정**) |

| 근거 경로 | 15 / 30 | 세 신호를 모두 인용했으나 **DB 구간 부재를 반대 방향으로 해석** |
| 오귀인 | 20 / 20 | **핵심 함정에 걸리지 않았다** — 구간 부재를 DB 장애로 오독하지 않음 |
| 조치 | 10 / 10 | 운영 우회 조치를 제시 |

**절대 점수는 인용할 수 없다.** 채점 기준이 확정되지 않은 상태에서 주입이 실행됐기
때문이다. 이는 앞선 3건(기준이 있었으나 부적합)과 성격이 다른 실패이며,
**실행 전 기준 존재 여부를 자동 검증하는 게이트**로 대응한다.

**다만 이 회차는 개선 측정의 기준선으로는 유효하다.** 기준이 유효하고 4개 항목이
모두 판정됐으므로, 같은 자를 다음 회차에 대면 차이가 나온다.
**이 시나리오는 정답이 로그에만 존재하는 유일한 케이스**이고 (트레이스에는
예외 정보가 남지 않는다), 로그 조회 결함을 고친 효과가 **전량 여기에 걸려 있다.**
예상 개선폭 +25점이며, 로그가 무관한 AP-1을 대조군으로 함께 재조사해
기여도를 분리한다.

### AP-3 — 중복 해시태그에 의한 유니크 제약 위반

**장애 상황.** 게시글에 `coffee`와 `COFFEE`를 함께 입력했다. 애플리케이션이
정규화(소문자 변환)를 수행하므로 둘은 같은 값이 되는데, **중복 제거를 하지 않아
두 행을 INSERT**해 유니크 제약을 위반하고 500이 발생했다.

**함정.** AP-1과 쌍을 이루는 시나리오다. 둘 다 "DB에서 500이 났다"로 보이지만
원인이 다르며, **예외 원문이 지문 역할을 한다** — `Data too long`(길이)과
`Duplicate entry`(중복)로 갈린다.

| 항목 | 만점 요건 |
|---|---|
| 1) 근본 원인 40 | **애플리케이션 중복 제거 누락** + **책임이 DB가 아니라 앱** 분리 |
| 2) 근거 경로 30 | INSERT 구간 오류 + **예외 원문**(`Duplicate entry ... uk_feed_hashtag`) + 로그 병기 |
| 3) 오귀인 20 | 길이·문자셋·인프라·동시성 오진 안 함 + **"DB는 유니크 제약을 지켰다"** |
| 4) 조치 10 | 정규화 후 중복 제거 + 예외를 409로 매핑 |

**결과 — 100점**

| 항목 | 점수 | 판정 |
|---|---|---|
| 근본 원인 | 40 / 40 | 중복 제거 누락 + 책임 분리 네 요소 전부. 오답 후보 4종 어디에도 귀인하지 않음 |
| 근거 경로 | 30 / 30 | `Duplicate entry` 지문 + 생성 키 역추적 + 영향 행 수 0→1 변화 + 롤백 |
| 오귀인 | 20 / 20 | 메트릭 스크레이프 해상도로 인한 아티팩트까지 정확히 해석 |
| 조치 | 10 / 10 | 정규화 후 중복 제거 + 409 매핑 둘 다 |

**최초의 만점이자, 채점 기준 부적합이 0인 첫 회차다.** 다만 인용에는 유보가 붙는다.
1회차이고, 출력이 11,070자로 장황한 편이었으며, **원인이 예외 문구에 그대로
자백되는 v0 최적 조건의 시나리오**였다.

주목할 점은 **로그가 실재했으나 조회 결함으로 못 봤는데도 만점**이라는 것이다.
트레이스만으로 충분했다는 뜻이며, **이 시나리오에서는 로그 수정이 점수를 올릴
자리가 없다.** 개선 효과를 측정하려면 대상 시나리오를 골라야 한다는 근거가 된다.

### CH-3 — MongoDB 단시간 다운에 의한 지연 흡수 (실행 예정)

**장애 상황.** MongoDB를 20~25초간 중단시키고, 중단 직후 알림을 발생시킨다.
드라이버의 서버 선택 대기 상한이 30초이므로, **대기 중에 복구되어 첫 시도가
예외 없이 성공한다.** 재시도도 DLQ도 발동하지 않는다. 결과는 지연 도착이며 유실은 0이다.

**시험 목적.** **오류 구간이 하나도 없는 장애**를 읽어내는가. 예외도, 실패한
구간도, 오류 로그도 없다. 유일한 신호는 **"자식 구간의 합으로 설명되지 않는 시간 공백"**이다.
CH-1과 쌍을 이뤄 지연과 유실을 구별하는 능력을 시험한다.

| 항목 | 만점 요건 |
|---|---|
| 1) 근본 원인 40 | MongoDB 미가용 + **첫 DB 작업 직전** 대기 + **대기 중 복구로 첫 시도 성공** + **지연이지 유실 아님** |
| 2) 근거 경로 30 | 공백의 **정량화**(총 시간 − 자식 구간 합) + 공백의 **위치** + 업스트림 정상 대조 |
| 3) 오귀인 20 | 커넥션 풀·GC·Kafka 지표 배제 + **"장애 없음"으로 결론짓지 않음** |
| 4) 조치 10 | 가용성 확인 · **재처리 불필요** 명시 · 계측 추가 중 둘 이상 |

**설계 배경.** 이 시나리오는 원래 CH-1의 한 갈래였다. CH-1 1회차가 73초 다운으로
실행됐는데 재시도도 DLQ도 발동하지 않아, **기준이 요구한 신호가 물리적으로
발생하지 않았고 채점 불가가 났다.** 같은 주입이 다운 시간에 따라 전혀 다른
전개를 보인다는 것이 확인되어 별도 시나리오로 분리했다.

### IN-1 — Redis 다운 (실행 예정)

**장애 상황.** 공유 캐시인 Redis를 중단시킨다. **서비스마다 다른 증상이 나타난다.**
콘텐츠 서비스는 사용자 캐시 미스로 인증 서버를 직접 호출하기 시작하고,
채팅 서비스는 접속 상태(프레즌스) 관리가 깨진다.

특히 웹소켓 프레즌스에서 **쓰기와 읽기의 처리가 다르다.** 온라인 상태 기록은
예외를 삼키고 오류 로그만 남기므로 **연결은 성공한 것처럼 보이고**, 상태 조회는
예외를 그대로 전파해 구독 처리가 실패한다. 결과적으로 사용자에게는
**"접속은 됐는데 남들 눈에는 오프라인"**으로 나타난다.

**시험 목적.** **서비스별로 다르게 아픈 증상을 단일 근원으로 수렴**시키는가.
표면만 보면 별개 장애 세 건이다.

| 항목 | 만점 요건 |
|---|---|
| 1) 근본 원인 40 | 서비스별 상이한 증상을 **Redis 단일 근원으로 수렴** + Redis 자체 응답 불가 명시 |
| 2) 근거 경로 30 | 아래 4종 중 **둘 이상 + 교차 서비스성** 명시 |
| 3) 오귀인 20 | 개별 장애 3건으로 쪼개지 않음 + **인증 서버를 근원으로 지목하지 않음** |
| 4) 조치 10 | Redis 복구 + 캐시 재적재 확인 |

근거 경로 4종:

| | 신호 | 무엇을 말해주는가 |
|---|---|---|
| (a) | Redis 명령 구간의 실패 — 콘텐츠·채팅 양쪽 | 캐시 미스가 아니라 **저장소 자체가 응답 불가** |
| (b) | Redis 실패 로그가 **서로 다른 서비스에서 동시에** | 서비스별 개별 장애가 아니라 **공통 의존성 하나** |
| (c) | 캐시 미스 직후 인증 서버 직접 호출로 전환 | 캐시 계층의 이탈 |
| (d) | **웹소켓 세션은 정상인데 프레즌스만 붕괴** | 채팅 프로세스·네트워크 문제 **배제** |

**(b)는 특정 문구를 요구하지 않는다.** 콘텐츠 캐시 로그든, 채팅 캐시 로그든,
프레즌스 로그든 어느 것으로 도달해도 같은 점수다. 채점은 "어떤 로그를 봤는가"가
아니라 **"Redis 실패가 두 서비스 이상에서 동시에 관측됨을 보였는가"**로 판정한다.

**(d)가 이 시나리오의 배제 논증이다.** 웹소켓 접속자 수 지표는 파드 로컬 세션을
세므로 **Redis와 무관하게 평시 수준을 유지한다.** "세션은 멀쩡한데 프레즌스만
깨졌다"는 채팅 서비스 자체의 문제로는 설명되지 않고, 공유 저장소 하나를 가리킨다.

**두 번째 함정은 인증 서버 오귀인이다.** Redis가 죽으면 캐시 미스로 인증 서버
호출이 급증해 인증이 느려 보인다. AU-2(인증 다운)와 증상이 겹치되 인과가 반대라,
**결과를 원인으로 착각하기 좋은 구조**다. 둘을 가르는 것이 (a)다.

### IN-3 — 커넥션 풀 고갈 (실행 예정)

**장애 상황.** 부하를 걸어 DB 커넥션 풀을 고갈시킨다. 요청은 커넥션을 얻지 못해
대기하고, 응답이 느려진다. **DB 서버는 정상이다.**

**시험 목적.** **"DB가 느림"과 "커넥션을 못 얻음"을 구별**하는가. 둘 다 응답이
느려지지만 처방이 정반대다. 결정적 차이는 **대기가 쿼리 구간 안이 아니라 앞에서
발생한다**는 점이다.

| 항목 | 만점 요건 |
|---|---|
| 1) 근본 원인 40 | **DB가 아니라 커넥션 풀 대기** + 슬로우 쿼리가 커넥션을 점유하는 구조까지 |
| 2) 근거 경로 30 | 풀 대기 수치가 0 초과 + **쿼리 구간 앞의 시간 공백** |
| 3) 오귀인 20 | DB 서버 장애로 오진하지 않음 |
| 4) 조치 10 | 풀 조정 · 쿼리 개선 |

### AU-3 — JWT 시크릿 불일치 (실행 예정)

**장애 상황.** 콘텐츠 서비스의 JWT 시크릿만 변경한다. 인증 서버는 기존 키로
서명하고 콘텐츠 서비스는 새 키로 검증하므로 **로그인은 200으로 성공하는데
인증이 필요한 API는 전부 401이 된다.** 설정 드리프트다.

**함정.** **토큰 만료와 증상이 구별되지 않는다.** 사용자 입장에서는 둘 다
"로그인은 되는데 아무것도 안 된다"이다. 결정적 차이는 **재로그인해도 그대로 401**이라는
점인데, **에이전트는 traceId 하나만 받으므로 재로그인 실험을 할 수 없다.**
관측만으로 가려야 한다.

| 항목 | 만점 요건 | 부분점 |
|---|---|---|
| 1) 근본 원인 40 | 시크릿 불일치 + **"로그인은 되는데 검증만 실패"의 구조**까지 | 30: 검증 실패로 좁혔으나 원인 미도달 / 20: "401이 많다"까지 / **10: 토큰 만료로 오판** |
| 2) 근거 경로 30 | **대안 가설을 관측으로 죽인다 — 셋 전부** | 20: 셋 중 둘 / 10: 셋 중 하나 |
| 3) 오귀인 20 | 로그인 성공을 근거로 인증 서버 배제 + **토큰 만료로 결론짓지 않음** | 10: 배제했으나 근거 없음 |
| 4) 조치 10 | 시크릿 **재동기화 + 재배포** | 5: 재시작만 |

**근거 경로를 신호 목록이 아니라 배제 논증으로 설계했다.** 어느 한 채널도
단독으로 답을 주지 않기 때문이다. 트레이스는 *401이라는 사실*만, 로그는
*실패 지점*만, 메트릭은 *범위*만 준다.

| 요건 | 죽이는 가설 | 채널 |
|---|---|---|
| (a) 인증 필터 단계에서 중단 — 컨트롤러·DB 구간 부재 | **애플리케이션 버그** | 트레이스 |
| (b) 실패 사유가 서명·키 불일치 계열 | **토큰 만료** — 핵심 함정 | 로그 |
| (c) 401 발생률이 전역적으로 급증 | **개별 요청·사용자 문제** | 메트릭 |

셋이 죽으면 남는 것이 설정 드리프트다. **(b)가 결정적이다** — 만료와 가를 수 있는
유일한 관측 지점이 로그에 남는 실패 사유이며, 이는 AP-1(`Data too long`)과
AP-3(`Duplicate entry`)를 같은 예외의 *지문*으로 가른 것과 동일한 구조다.

**이중 감점 방지 규정.** (b)를 충족하지 못한 것이 3) 오귀인 감점으로도 이어지려면
**만료라고 확정**해야 한다. 사유를 확인하지 못했을 뿐이면 2)에서만 감점한다.

## 5. 결과 종합

### 5.1 점수

| 상태 | 회차 | 비고 |
|---|---|---|
| 유효 채점 5회 | AP-3 **100** · CH-1 **80** · IN-2 **80** · AP-1 **75** · AU-4 **75** | 평균 **82** |
| 채점 불가 3회 | CH-1 1회차 · CH-2 · AU-2 (+ AU-4 파일럿) | 채점 기준 부적합 |
| 채점 유보 1회 | AP-2 (참고 60~65) | 기준 미확정 상태로 실행 |

### 5.2 이 점수를 아직 인용하지 않는 이유

**반복 부족.** 유효 5회가 전부 1회차다. 규정은 시나리오당 최소 2회이며,
같은 버전이 같은 장애에서 75점과 95점을 낸 사례가 있다.

**한 항목이 변별력을 잃었다.** 오귀인 항목 20점은 **9회 전부 만점**이다.
상수가 붙는 항목은 척도가 아니므로, 실질 만점은 80점이고 회차 간 차이는 나머지
세 항목에서만 발생한다. 원인은 현재 시나리오가 전부 원인이 뚜렷한 주입이고,
**오탐을 시험하는 시나리오(장애 주입 없이 장애 질문)가 아직 0회**이기 때문이다.
장애 상황만으로 평가하면 "항상 무언가 원인을 찾아내는" 에이전트가 만점을 받는다.
**정상 상황에서 원인을 지어내지 않는 능력은 실무 신뢰의 절반이다.**

> 이 문제는 §1.1의 탐색 트랙에서 함께 해소된다. 정상 시간대를 던져 "이상 없음"이라고
> 답하는지 보는 것이 곧 오탐 대조군이며, **장애 주입 없이 실행 가능하다.**

**측정 범위가 절반이다.** 위 두 가지가 해소돼도 이 점수는 **대상이 주어진 상태의 정확도**다.
자연어에서 대상을 찾는 단계(§1.1)는 아직 측정되지 않았다. **점수를 제시할 때 이 경계를
함께 밝힌다.**

### 5.3 채점 불가 4건은 전부 기준의 문제였다

| 유형 | 회차 | 무슨 일이 |
|---|---|---|
| A. 전개 갈래 미상정 | CH-1 1회차 · AU-2 | 조건에 따라 신호가 안 나오는데 한 갈래만 기술 |
| B. 입력 범위 무시 | CH-2 | 요구한 신호가 조사 도구의 수집 채널에 없음 |
| C. 코드 독해를 실측으로 착각 | AU-4 파일럿 | 설정 상수를 보고 "3초 타임아웃" → 실제 23.5ms 연결 거절 |
| D. 기준 부재 | AP-2 | 기준이 **아예 없는 상태로** 주입 실행 |

**공교롭게도 채점 불가 회차들이 질적으로는 가장 인상적인 조사들이다.**
CH-2는 근본 원인 40점 만점, AU-2는 트레이스 무신호에서 정답 도달,
AU-4 파일럿은 채점된 3항목이 70점 만점에 70점이었다.
**측정하지 못한 것이 곧 못한 것은 아니다.**

부적합률은 **67%에서 33%로** 내려갔다. 대응은 유형별로 다르다 —
A·B·C는 기준 작성 체크리스트로, D는 실행 전 자동 게이트로 막는다.

### 5.4 기준 작성 체크리스트

만점 요건 한 줄마다 아래를 통과해야 한다.

1. **실물 확인** — 이 신호를 실제 관측에서 본 적 있는가. 코드의 상수·로그문은 근거가 아니다
2. **채널 확인** — 이 신호가 에이전트의 수집 범위 안에 있는가. 밖이면 요건에서 빼거나 개선 측정 지점으로 명시한다
3. **갈래 확인** — 조건에 따라 이 신호가 안 나올 수 있는가. 그러면 갈래를 나눈다
4. **대체 경로** — 같은 결론에 다른 경로로 도달하면 부분점을 줄 자리가 있는가
5. **충분성 기준** — 요건이 확인할 신호의 목록이 아니라 원인 확정에 충분한 근거 집합으로 쓰여 있는가
6. **증상과 근거의 구별** — 이 요건이 질문에 이미 적힌 증상을 되풀이하게 만드는가. 그렇다면 에이전트는 아무것도 조사하지 않고 그 점수를 가져간다
7. **반증도 실측으로** — 요건을 "도달 불가"로 뺄 때의 근거도 실측인가. **다른 시나리오의 실측을 옮겨 쓰는 것은 근거가 아니다**

### 5.5 시나리오 선정 기준

**주입 강도와 증상이 선형이어야 한다.** AU-1을 보류하며 확립한 기준이다.
기준 자체는 성립했으나, CPU 제한값이 응답을 타임아웃 임계 너머로 밀어낼지가
그때의 노드 부하에 달려 있었다. 넘으면 증상이 나오고 못 넘으면 아무 일도 없다 —
중간이 없다.

**반복 측정을 요구한다는 것은, 재현되지 않는 주입은 애초에 시나리오가 될 수 없다는
뜻이다.** 평균과 편차를 내려면 두 회차가 같은 장애여야 하는데,
증상이 갈리면 그것은 편차가 아니라 다른 시나리오 둘이다.
