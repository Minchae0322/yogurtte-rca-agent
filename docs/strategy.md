# rca-agent 전략 — AI 기반 RCA 시스템 구축·검증·개선 로드맵

이 문서는 "무엇을 만들 것인가"의 목록이 아니라, **어떤 순서로 왜 그렇게 갈 것인가에
대한 논증**이다. 각 단계는 이전 단계의 실측 결과를 진입 근거로 삼고, 다음 단계로
넘어가는 게이트를 숫자로 정의한다. 원칙은 하나다:

> **모든 개선 주장은 고정된 장애 시나리오 셋에 대한 before/after 숫자로만 말한다.**
> 측정할 수 없는 개선은 하지 않고, 측정된 실패 없이 확장하지 않는다.

## 0. 목표

장애 상황에서 traceId 하나를 입력하면, 관측 데이터(트레이스·로그·메트릭)와 —
최종적으로는 소스 코드까지 — 근거로 **원인 후보를 랭킹하고, 근거·확신도·반증을 명시한
보고서**를 만들어내는 시스템. 사람이 대시보드 세 개를 오가며 하던 상관분석을 API 호출
하나로 줄이는 것이 실용 목표이고, 그 과정을 측정 가능한 개선 이터레이션으로 남기는
것이 방법론적 목표다.

북극성 지표는 세 개다. 목표 수치는 baseline(Phase 2) 측정 후 확정한다.

- **원인 적중률(Top-1)** — 주입한 장애 원인을 1순위 후보로 지목하는 비율
- **조사당 비용** — 토큰·USD (하네스가 자동 기록, ADR-006)
- **조사 소요시간**

## Phase 0 — 관측성 기반 (완료)

AI RCA에서 LLM의 입력은 관측 데이터가 전부이므로, 계측 커버리지가 분석 품질의 상한을
구조적으로 결정한다. 그래서 에이전트를 만들기 전에 두 가지를 먼저 끝냈다.

하나는 **수집 파이프라인 구축**이다. Grafana Cloud(Tempo/Loki/Mimir)와 Alloy 수집 허브,
그리고 미들웨어별 전용 exporter까지 — 현재 실측 기준 23개 스크레이프 타깃이 돌고 있다.
"무엇이 어디서 수집되는가"의 전체 인벤토리와 실측으로 확인된 관측 공백 목록은
[monitoring.md](monitoring.md)에 있다.

다른 하나는 **계측 방식 결정**이다. Brave 라이브러리 계측에서 Kafka observation 누락을
실제로 겪은 뒤 zero-code OTel Agent 전환을 검토했고, 48시간 A/B 대신 대표 흐름 3종의
E2E 트레이스 실측이라는 더 싼 검증을 먼저 수행해 "RCA 데이터 요건은 이미 충족"임을
확인, Brave를 유지했다. 이 결정의 전체 과정·수치·그리고 **이후 실제로 현실화된
리스크**(FCM 미계측 갭)까지 [ADR-001](decisions/adr-001-brave-over-otel.md)에 기록되어
있다. 그 리스크가 바로 Phase 4(코드 인지 RCA)의 존재 이유가 된다.

남은 액션 하나: 트레이스 resource attribute에 `service.version`이 없다는 것이 실측으로
확인되었다 (monitoring.md 한계 3번). "장애 시점에 어떤 커밋이 돌고 있었나"를 pin할 수
없다는 뜻이고, Phase 4c에서 해소한다.

## Phase 1 — v0 에이전트 + 측정 하네스 (완료)

에이전트의 첫 형태를 tool-calling 루프가 아니라 **도구 없는 단일 패스**로 만들었다.
이유는 대조군이다 — 루프가 더 낫다는 주장은 루프 없는 기준선이 있어야만 증명되고,
단일 패스는 실패를 세 유형((a) 신호가 있는데 놓침 / (b) 신호가 없음 / (c) 보고도 확정
불가)으로 분류하게 해줘 이후 투자처 판단의 근거가 된다. 논증과 실측은
[ADR-002](decisions/adr-002-single-pass-baseline.md).

측정 하네스도 이 단계의 산출물이다: 조사마다 토큰(캐시 합산)·비용·수집범위(coverage)·
단계별 소요·프롬프트 버전이 `.md`+`.json` 리포트에 남는다. 하네스 자체의 검증 과정에서
입력 토큰이 `in=2`로 기록되던 회계 버그를 잡았고(실제 42,774), 이 경험은 "측정이
틀리면 모든 개선 판단이 틀린다"는 원칙의 실례로 남았다
([ADR-006](decisions/adr-006-measurement-harness.md)).

실전 검증 1건이 이미 있다. 실제 prod 트레이스에서 에이전트는 content 동기 응답
(129.8ms)을 정상으로 배제하고 chat의 `push-dispatcher#dispatch` 996ms 중 **994ms가
자식 span으로 설명되지 않는 갭**임을 1순위로 특정했으며, 로그 부재를 이유로 확신도를
스스로 낮췄다. 위치는 맞혔지만 원인은 확정하지 못했다 — 사람이 코드를 열어 FCM 동기
호출(타임아웃 미설정)임을 확인했다. **이 "특정했으나 확정 못 함"이 (c) 유형 실패의
실측 사례**이고, Phase 4의 진입 티켓이다.

주목할 점: 이 조사는 장애가 아니라 **정상 상황**이었다(댓글도 알림도 성공). 그런데도
수동 코드 리뷰까지 합쳐 개선점 4건이 확정되었고, 이 목록이 그대로 Phase 2 정상
트랙(N1)의 정답지가 된다 — 평가 설계에 정상 트랙을 두는 실측 근거다.

## Phase 2 — 평가 하네스: 정상·카오스 2트랙으로 정답지를 만든다 (다음 단계)

여기서부터가 계획이다. 개선을 시작하기 전에 평가부터 만든다.

**관점 전환이 핵심이다: 평가란 정답(ground truth)이 있는 데이터셋을 만드는 일이다.**
정답을 아는 상황에 에이전트를 넣어야 답을 채점할 수 있고, 그래야 이후의 모든 변경이
"리포트가 좋아 보인다"는 인상 비평이 아니라 "적중률 X%p, 토큰 Y% 변화"로 평가된다.

정답을 확보하는 방법이 두 가지이므로 **트랙도 두 개**다. 카오스 트랙은 원인을 직접
주입해서 정답을 만들고, 정상 트랙은 사람이 코드·트레이스를 먼저 리뷰해서 정답지를
만든다. 정상 트랙을 두는 근거는 실측이다 — 유일한 실전 조사가 정확히 정상 상황이었고
(댓글도 알림도 성공), 그런데도 개선점 4건(FCM 동기 블로킹·무타임아웃, Redis `KEYS`,
dispatch 동안 커넥션 1.1s 점유, 댓글 1건에 쿼리 9회)이 나왔다. 실무에서 에이전트가
받을 질문의 다수도 "죽었다"가 아니라 "왜 느려?"다.

**두 트랙은 과업이 다르므로 지표도 다르다.** 카오스는 "주입한 원인 하나를 맞혀라"
(Top-1 적중률), 정상은 "알려진 개선점 집합을 얼마나 회수하나"(정답지 대비 재현율)다.
이 둘을 한 숫자로 합치지 않는다 — 합치면 개선이 어느 능력에서 왔는지 사라진다.

### C-트랙: 카오스 시나리오 (주입 = 정답)

시나리오는 이 스택이 실제로 겪을 장애 모드에서 도출하고, 각각을
{주입 방법, 예상 관측 신호, 정답 라벨}로 정의한다. 예상 신호는 monitoring.md의
실측 인벤토리에 존재하는 것만 쓴다 — 관측되지 않는 신호를 정답으로 삼으면 평가가
아니라 함정이 된다.

| ID | 시나리오 | 주입 | 정답 신호 (에이전트가 인용해야 할 것) |
|---|---|---|---|
| C1 | 컨슈머 정지 | chat deployment scale 0 | `kafka_consumergroup_lag` 상승 + chat consume span 부재 |
| C2 | 느린 컨슈머 | 리스너 지연 플래그(env로 sleep) | consume span 지연, lag 점진 상승 |
| C3 | 외부 API(FCM) 지연 | push provider 지연 주입 | dispatch span 미계측 갭 — 실전 관측된 유형 |
| C4 | DB 커넥션 고갈 | 커넥션 N초 점유 | `hikaricp_connections_pending` 상승 |
| C5 | Redis 지연 | redis pause / tc delay | redis span 지연 |
| C6 | 예외 버스트 | 예외 발생 플래그 | Loki ERROR 로그 + error span |
| C7 | **오탐 대조군** | 주입 없음 + **장애 질문** | "이상 없음/장애 근거 없음"이라고 말하는가 — **오탐률** |

C7을 강조해 둔다. 장애 시나리오만으로 평가하면 "항상 뭔가 원인을 찾아내는" 에이전트가
만점을 받는다. 정상 상황에서 원인을 지어내지 않는 능력은 실무 신뢰의 절반이다.

주입 도구는 앱 내 chaos 플래그(env 토글) + kubectl(scale/delete) + tc로 충분하다.
Litmus/ChaosMesh 같은 전문 도구는 개인 K3s 규모에 과하며, 이 단계의 가치는 도구가
아니라 **라벨의 정확성**에서 나온다.

### N-트랙: 정상 시나리오 (수동 리뷰 = 정답지)

정상 시나리오는 주입이 없으므로 정답이 공짜로 생기지 않는다. **평가에 쓰기 전에
사람이 코드와 트레이스를 리뷰해 finding 목록을 확정하고, 그 목록이 정답지가 된다.**
이 큐레이션 비용 때문에 트랙 규모를 3개로 제한하고 나머지는 백로그로 둔다
(성능 리뷰 에이전트라는 별개 제품으로 번지는 것을 막는 스코프 경계).

시나리오는 세 레포(toy-content / toy-chat / toy-auth-user-region)의 실제 코드에서
도출했다:

| ID | 흐름 | 진입점 (실코드) | 정답지 상태 |
|---|---|---|---|
| N1 | 댓글 작성 → 알림 | `POST /feeds/{feedId}/comments` → Kafka → chat → FCM | **확정 완료** — 정답지는 [findings/](findings/README.md) NF-01~04 (코드 위치·검증 방법 포함) |
| N2 | 피드 목록 조회 | `GET /feeds/scroll`·`/hot`·`/following` | 큐레이션 필요 — 목록 조회는 N+1의 고전 서식지 |
| N3 | 채팅 메시지 fan-out | STOMP 발행 → `ChatRelay`/`ChatStorage`/`ChatNotification` 컨슈머 3분기 | 큐레이션 필요 — 3-consumer 처리 비대칭 |
| 백로그 | 로그인/재발급, S3 파일 업로드(외부 API — FCM과 같은 사각지대 유형), 스케줄러 5종의 DB 경합 | | 트랙 정착 후 |

**질문이 트랙을 가른다는 점이 중요하다.** 같은 정상 트레이스라도 "장애 원인을 찾아라"
(C7)와 "성능·구조 개선점을 리뷰하라"(N-트랙)는 정답이 다르다. C7에서 KEYS를 지적하면
오탐이지만, N1에서 지적하면 정답이다. 질문 문구를 시나리오 정의에 고정해 이 경계가
흐려지지 않게 한다. N-트랙은 시스템 프롬프트도 리뷰 과업용 변형이 필요할 수 있는데,
이는 promptSource로 추적되므로 트랙별 프롬프트 분리가 측정을 해치지 않는다.

### 채점과 실험 규율

공통 자동 기록: 토큰·비용·소요시간·coverage (하네스, ADR-006).

- **C-트랙 채점**: Top-1/Top-3 적중(주입 원인을 몇 순위로 지목), 근거 품질(정답 신호
  인용 여부), 캘리브레이션(맞을 때 확신도 "높음", 데이터 공백 시 "데이터 부족" 명시),
  환각 건수.
- **N-트랙 채점**: 정답지 대비 재현율(알려진 finding 중 몇 개를 찾았나), 정밀도
  (에이전트가 낸 finding 중 정답지 밖·근거 없는 것의 비율), 심각도 순위의 타당성.

규율 세 가지. LLM은 비결정적이므로 **시나리오당 최소 3회** 실행해 평균±편차로 보고한다
(하네스 실측 기준 입력 토큰 편차는 ±0.3%로 안정적이지만, 분석 텍스트의 결론은 요동칠
수 있다). 질문 파라미터에 정답 힌트를 넣지 않는다 — "왜 알림이 늦었어?"는 되고
"Kafka lag 때문인가?"는 평가 오염이다. 채점은 초기엔 체크리스트 수동으로 하고, 반복이
잦아져 자동화(LLM-judge)하더라도 judge에게 정답 라벨을 기준으로 준다.

**이 Phase의 산출물은 baseline 결과표(C 7종 + N 3종, 각 3회)이며, 이후 모든 Phase는
이 표와의 diff로만, 트랙별로 분리해서 성과를 주장한다.**

## Phase 3 — 컨텍스트·프롬프트 최적화 (코드 연동 전에)

코드 연동이 최종 목표라면 왜 바로 가지 않는가. baseline의 실패를 앞의 세 유형으로
분류해 보면 답이 나온다. (a) 신호가 컨텍스트에 있는데 모델이 놓쳤다면 프롬프트와
컨텍스트 구조의 문제고, (b) 신호 자체가 없다면 수집 쿼리의 문제다. 코드가 해결하는
건 (c) "보고도 확정 불가"뿐이다. (a)(b)를 코드 연동으로 풀려 하면 토큰만 늘고 적중률은
제자리다. **싼 레버부터 당기고, 실패 분류가 (c)를 가리킬 때만 비싼 레버로 간다.**

실험은 독립적으로 하나씩 돌리고, 각각 채택/기각을 숫자로 기록한다:

- **E1 프롬프트 튜닝** — `prompts/system-prompt.md`는 조사마다 다시 읽히고 리포트에
  `promptSource`가 남으므로, 버전별 적중률 비교가 이미 가능하다. 출력 구조 강제,
  반증 요구 강화 등을 실험한다.
- **E2 컨텍스트 다이어트** — 로그 dedup(동일 패턴 접기), 메트릭 시계열의 통계 요약화,
  트레이스의 표 형식 변환. 토큰 절감이 적중률을 해치는지가 관전 포인트다.
- **E3 수집 정합성** — 존재하지 않는 `kafka_consumer_fetch_manager_records_lag`를
  실존하는 `kafka_consumergroup_lag`로 교체([ADR-005](decisions/adr-005-kafka-lag-exporter-metric.md)
  — 결정은 끝났고 적용을 여기서 평가와 함께 한다), 시나리오별 유효 쿼리 확충.

채택 규칙은 미리 못 박는다 (수치는 baseline 후 확정하되 형태는 이렇다):
적중률이 떨어지지 않으면서 토큰 ≥20% 절감이면 채택. 적중률 +5%p 이상이면 토큰 +30%까지
허용. 그 외는 기각하고 결정 로그에 남긴다. 과적합 방지를 위해 **hold-out 시나리오
1개는 튜닝에 쓰지 않고 최종 평가에만** 쓴다.

프롬프트를 claude 스킬(SKILL.md) 형태로 패키징하는 것은 배포 형태의 문제로, 측정이
끝난 뒤의 일이다. 측정 하네스 밖으로 로직이 나가면 before/after 비교가 무너지므로,
개선 기간 동안 프롬프트·조립 로직은 하네스 안(코드 + md 파일)에 유지한다.

## Phase 4 — 코드 인지 RCA (핵심 개선 서사)

진입 게이트: (c) 유형 실패가 실측으로 존재할 것. 이미 실전 1건(dispatch 994ms 미계측
갭 — 위치 특정, 원인 확정 실패)이 있고, C3(카오스)와 N1(정상)이 이를 재현 가능하게
만든다.

관측 데이터는 "어디서 느린가"까지 답한다. "왜"는 코드에 있다 — 실전 사례에서 원인은
`sendEachForMulticast()` 동기 호출과 **타임아웃 미설정이라는 설정 부재**였고, 이는
트레이스 어디에도 없었다. 다만 코드를 어디서 얼마나 읽을지는 자명하지 않으므로,
세 이터레이션으로 나눠 각각을 측정한다.

### Iter 4a — 의도된 strawman: 소스 전체 덤프 (1회 측정 후 폐기)

가장 단순한 방법 — 의심 서비스(chat) 소스 전체를 컨텍스트에 덤프 — 을 **먼저 실측**한다.
C3 시나리오 3회로 토큰·비용·적중률을 잰다. 예상은 토큰 폭발과 노이즈로 인한 품질
저하지만, 예상을 근거로 쓰지 않는다. **"전체를 읽으면 안 되는 이유"를 가정이 아니라
숫자로 기각**해야 4b의 타깃 방식이 논증이 되기 때문이다. 이 실행은 1회로 끝내고
폐기한다.

### Iter 4b — 타깃 슬라이스

측정된 strawman을 근거로, 필요한 것만 읽는 방식으로 간다. 실현 가능성은 이미 부분
검증되었다:

- **span → 코드 매핑**: span 명명 규칙 `bean#method`를 kebab→PascalCase로 풀면 클래스가
  나온다. `push-dispatcher#dispatch` → `PushDispatcher.dispatch(Long, PushPayload)`
  매핑을 로컬 레포에서 실확인했다.
- **콜그래프 1~2홉 결정적 순회**: 순회는 LLM이 아니라 코드가 한다. dispatch →
  `sendToTokens` → `FcmPushNotificationProvider.sendEachForMulticast`(동기, 타임아웃
  없음, 예외 삼킴)까지 2홉에 실제 원인이 나오는 것을 확인했다 — 1홉(메서드 하나)으로는
  부족하다는 것도 함께 확인된 셈이다.
- **설정 슬라이스**: 지연의 근본 원인은 로직보다 배선(타임아웃·풀·`@Bean`·yml)인
  경우가 많고 토큰이 싸다. 콜패스 위 메서드 + 관련 설정만 첨부한다.

발동에는 게이트를 건다: "자식 span으로 설명되지 않는 갭" 또는 확신도가 높음 미만일
때만 코드 단계를 켠다. 오탐 대조군(C7)과 관측 데이터로 충분한 케이스는 코드 세금을
내지 않는다. coverage에 `codeFilesRead`/`codeBytes`를 추가해 측정 일관성을 유지하고,
4a 대비 토큰 절감률과, C3의 확정률(plausible → confirmed 전환) 및 N1 정답지 재현율
변화를 성과 지표로 삼는다.

### Iter 4c — 버전·변경 상관

로컬 HEAD와 prod 배포 코드가 다르면 4b는 없는 코드를 읽고 오진한다. 실측으로 트레이스
resource에 버전 정보가 전무함을 확인했으므로, 앱에 `service.version=$GIT_SHA` 태깅을
추가한다(설정 한 줄, Phase 0의 남은 액션). 이것이 되면 두 가지가 열린다 — 읽을 코드
버전의 pin, 그리고 의심 파일의 `git log`를 장애 시각과 상관시키는 **네 번째 증거 축**
("이 커밋 배포 후 증상 시작"은 트레이스·로그·메트릭 어디에도 없는 정보다). 검증용으로
"성능 저하 커밋을 배포"하는 시나리오 C8을 추가한다.

### Phase 5 (조건부) — agentic 루프

4b의 정적 슬라이스로도 확정하지 못하는 케이스가 **실측으로 남을 때만** 진입한다.
"더 fancy하니까"는 진입 사유가 아니다. 진입하더라도 동일 시나리오 셋으로 루프의 추가
비용 대비 적중률 증분을 재고, 증분이 비용을 정당화하지 못하면 되돌린다.

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| LLM 비결정성으로 평가 요동 | 시나리오당 ≥3회, 평균±편차 보고 |
| 프롬프트의 시나리오 과적합 | hold-out 시나리오 1개 + 실전 트레이스 병행 평가 |
| 정답 누설로 평가 오염 | question 중립 유지, 시나리오명 미노출 |
| 비용 폭주 | 조사당 비용 상한, strawman은 1회 한정 |
| 로컬 HEAD ≠ prod 코드 | 4c의 version 태깅으로 해소, 그전까지 컨텍스트에 "HEAD 기준" 경고 명시 |

## 이 순서가 설득력을 갖는 이유 (요약)

1. **측정 없이 개선 없다** — 정답 라벨(평가 하네스)이 모든 개선보다 먼저 온다
2. **싼 레버 먼저** — 실패 유형 분류((a)/(b)/(c))가 프롬프트→수집→코드의 순서를 정한다
3. **strawman도 측정한다** — "전체 덤프는 안 된다"를 가정이 아니라 숫자로 기각한다
4. **모든 확장에 게이트** — 코드 슬라이스 발동도, agentic 루프 진입도, 측정된 실패가
   존재할 때만 한다
