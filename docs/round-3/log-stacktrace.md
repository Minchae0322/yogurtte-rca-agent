# 로그 필터가 스택트레이스를 잘라내고 있었다

팔로우 목록 NPE 문항(AP-2)이 **53점**이었습니다. 정답이 로그 스택에만 있었는데 그것이
컨텍스트에 도착하지 않았습니다.

---

## 무엇이 잘렸나

기존 쿼리는 이랬습니다.

```logql
{service_name=~"..."} |~ "ERROR|WARN"
```

같은 예외 하나가 로그에 이렇게 남습니다.

```
ERROR [traceId=6a68b1] c.e.t.FollowService : 팔로우 목록 조회 실패      ← 잡힌다
java.lang.NullPointerException: Cannot invoke "Integer.intValue()"      ← 안 잡힌다
	at com.example.FollowCondition.getSize(FollowCondition.java:25)     ← 안 잡힌다  ★정답
	at com.example.FollowService.list(FollowService.java:88)            ← 안 잡힌다
```

**라인 필터는 그 문자열이 있는 줄만 가져옵니다.** 헤더 줄에만 `ERROR`가 있고 스택 줄에는
없습니다. 그래서 *"로그가 들어왔다"* 와 *"예외를 읽을 수 있다"* 가 다른 문제였습니다.

## 왜 다른 문항에서는 안 드러났나

| 문항 | 예외 | 정보가 어디에 |
|---|---|---|
| AP-1 (varchar 초과) | `DataIntegrityViolationException: Data too long...` | **헤더 줄에** — 읽혔다 |
| AP-3 (중복 해시태그) | `DataIntegrityViolationException: Duplicate entry...` | **헤더 줄에** — 읽혔다 |
| **AP-2 (팔로우 NPE)** | `NullPointerException` | **스택에만** — 메시지가 비어 있다 |

NPE는 메시지가 없거나 빈약해서 **정보가 전부 스택에 있습니다.** 정답이
`FollowCondition.java:25` 였습니다.

## traceId 쿼리로도 안 됐습니다

코드에 **레벨 필터 없는** 쿼리가 이미 있었습니다.

```logql
{service_name=~"..."} |= "<traceId>"
```

레벨 무관인데도 스택이 안 옵니다. **스택 줄에는 traceId가 붙지 않기 때문**입니다 —
Logback 패턴은 로그 이벤트의 **첫 줄에만** 적용되고, 수집기가 줄 단위로 받으면 스택은
traceId 없는 **별개 엔트리**가 됩니다.

**실측으로 확인됐습니다.** JWT 게이트 트레이스로 채널을 감사한 결과입니다.

| 쿼리 | 결과 |
|---|---|
| traceId 전량 | **실패** — `GET /api/feeds/following 200 - 4ms` INFO 한 줄뿐 |
| `\|~ "Signature\|Jwt"` | **성공** — 스택 전문 + `JwtParser.validateToken(JwtParser.java:31)` |

문자열 검색으로는 나오고 traceId로는 안 나옵니다.

> 그래서 round-3에 적혀 있던 처방(*"traceId 단위 전량 조회"*)은 **그것만으로는 스택에
> 도달하지 못합니다.** 이 문서가 그 정정입니다.

---

## 무엇을 고쳤나

분석 단계 라인 필터에 스택을 식별하는 패턴을 더했습니다.

```logql
{service_name=~"..."} |~ `ERROR|WARN|Exception|Caused by|\.java:[0-9]+\)`
```

| 패턴 | 잡는 줄 |
|---|---|
| `ERROR\|WARN` | 헤더 줄 |
| `Exception` | `java.lang.NullPointerException: ...` |
| `\.java:[0-9]+\)` | `at ...(FollowCondition.java:25)` ← **정답** |
| `Caused by` | 중첩 예외 |

`(Foo.java:25)` 형태는 **자바 스택 프레임에만** 나오는 모양이라 일반 로그를 오탐하지 않습니다.

패턴을 **백틱 문자열**로 넘깁니다. LogQL의 큰따옴표 문자열은 이스케이프를 해석해서 `\.` 를
두 번 겹쳐 써야 하고, 그 자리에서 정규식이 조용히 깨집니다.

## 양은 안 늘어납니다

INFO를 전부 받는 것과 **성질이 다릅니다.**

| | 증가 |
|---|---|
| INFO 전량 수집 | 1시간 2,300줄 중 ERROR/WARN 8줄 → **약 287배** |
| 스택 줄 추가 | 예외 8건 × 스택 20~50줄 → **8줄 → 200~400줄** |

**스택 줄은 예외가 난 만큼만 존재합니다.** 정상 요청에는 아예 없습니다.

## 스윕 쿼리는 건드리지 않았습니다

로그 쿼리가 두 개이고 성격이 다릅니다.

| 단계 | 쿼리 | 바꿨나 |
|---|---|---|
| **분석** | `{...} \|~ ...` — 원본 라인 | **바꿨다** |
| **스윕** | `sum by (service_name) (count_over_time({...} \|~ "ERROR\|WARN" [5m]))` — 발생률 | **안 바꿨다** |

스윕에 스택 패턴을 넣으면 **에러 건수가 수십 배로 부풀어** 발생률 신호가 망가집니다.
*"54건"* 이 *"1,600건"* 이 되고 버킷 간 비교가 무의미해집니다.

---

## 이것으로 안 풀리는 것

**CH-1의 도착 로그는 여전히 안 옵니다.**

```
INFO [traceId=NONE] c.e.t.NotificationConsumer : [Kafka] DLQ 알림 재처리 성공
```

INFO이고 예외도 스택도 없어서 위 패턴 어디에도 안 걸립니다. *"유실인가 지연인가"* 를 판정
못 해 5점 잃은 게 이것입니다.

처방이 다릅니다.

| 안 | 방법 | |
|---|---|---|
| 가 | 결말 어휘를 라인 필터에 추가 — `\|~ "...\|재처리\|복구\|성공"` | 싸다. **한국어 문자열에 의존**하는 게 약점 |
| 나 | 그 로그에 traceId를 붙인 뒤(앱 수정) traceId 전량 조회 | 근본이지만 배포가 선행 |
| 다 | *"실패 로그가 끊긴 시각"* 을 부재 신호로 | 도착의 간접 증거 |

**두 문항의 처방이 다르므로 한 회차에 같이 넣지 않습니다.** 묶으면 어느 쪽이 효과인지
못 가립니다.

## 근본 해결은 따로 있습니다

**수집기에서 multiline 스티칭** — 스택을 한 엔트리로 묶으면 traceId가 붙고, 기존 쿼리가
그대로 작동합니다. 다만

- **관측 파이프라인 변경**이라 별도 사이클
- **과거 데이터는 이미 잘려 저장돼 있어** 재조사로 검증이 안 된다 → **새로 주입해야 한다**

AP-2 재조사가 주입 불필요였는데 스티칭으로 가면 필요해집니다. 그래서 라인 필터 확장이
먼저입니다.

## 현재 상태

| | |
|---|---|
| 코드 | **적용 완료** — `CollectProperties.errorWarnQuery()` |
| 테스트 | **통과** — 헤더·예외줄·스택프레임·`Caused by` 를 잡고 평범한 INFO는 안 잡는다 |
| 스윕 쿼리 | **의도적으로 그대로** |
| 효과 | **미측정** — AP-2 재조사 필요 (주입 불필요) |
| 예측 | 스택이 컨텍스트에 도달 → NPE 원문과 `FollowCondition.java:25` 를 읽을 수 있다 |
| 반증 조건 | 스택이 왔는데도 점수가 안 오르면 **병목은 신호가 아니라 추론**이다 |

**주장 범위**: *"스택이 어느 쿼리로도 도달하지 못하던 원인을 특정하고, 분석 단계에서 도달하게
고쳤다"* 까지입니다. 점수 변화는 재조사 후에만 인용합니다.
