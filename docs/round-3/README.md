# 회차 3 변경 대기열

회차 2(자연어 입력) 5회에서 확정한 결함과 그 수정안. **이 문서 하나로 "회차 2에서 무엇을
배웠고 회차 3에 무엇을 고치는가"가 닫힌다.**

- 적용 규칙: `round-N/`은 **회차 N에 적용할 변경**이고, 내용은 **회차 N−1에서 나온 것**이다
  (CLAUDE.md "개선 사항은 그것을 적용할 회차 폴더에 모은다").
- 회차별 발견 원문: [AP-1](../ap-1/round-2.md) · [AP-2](../ap-2/round-2.md) ·
  [AP-3](../ap-3/round-2.md) · [AU-2](../au-2/round-2.md) · [AU-4](../au-4/round-2.md) ·
  [CH-2](../ch-2/round-2.md) · [CH-1](../ch-1/round-2.md)
- 직전 대기열: [round-2/](../round-2/README.md) — 인용 규율과 변경군 분리 원칙을 여기서 승계한다

# 1. 회차 2는 무엇이었나

입력 모델을 **traceId에서 자연어 한 줄로** 바꾼 첫 회차다. 5문항을 완주했고 전부
루브릭 v3(6항목)·앵커 v2로 채점했다.

| 문항 | 점수 | 한 줄 |
|---|---|---|
| AP-3 | 100 | 앱 dedup 구멍 도달. 탐색이 주입 트레이스를 자력 선정 |
| AP-1 | 90 | 앵커 재배치 미완으로 4항목 채점 |
| AU-4 | 88 | refused를 timeout과 구별. 캐시 만료 결합은 미도달 |
| AU-2 | 76 | auth 전면 부재 확정. content 축 전부 결손 |
| AP-2 | 53 | NPE·`size` 미도달 |

**점수 차를 능력 차로 읽으면 안 된다.** 다섯 문항이 같은 자를 통과했지만
**에이전트가 받을 수 있었던 증거의 양이 달랐다.**

| 문항 | 정답 신호가 어디 있나 | 도구가 막은 항목 | 점수 |
|---|---|---|---|
| AP-3 | 예외 원문이 span error 태그와 Loki 헤더 줄에 둘 다 | 탐색 B (메트릭으로 자력 대체 성공) | 100 |
| AP-1 | 예외 원문이 트레이스에 자백 | 없음 | 90 |
| AU-4 | client span의 `Connection refused` + fallback 로그 | 원인 | 88 |
| AU-2 | auth는 메트릭 소멸, content는 정상 트레이스의 span 부재 | 원인·근거·영향·조치 | 76 |
| AP-2 | 로그의 스택트레이스에만 | 근거·원인 | 53 |

**막힌 항목 수와 점수가 대체로 정렬된다** — 0개(100·90) → 1개(88) → 2개 이상(76·53).
표본 5개라 상관을 주장할 수는 없고, **회차 3의 반증 대상**으로 삼는다.
결함을 고친 뒤 AP-2·AU-2·AU-4가 오르지 않으면 이 해석이 틀린 것이다.

**못 받은 신호는 전부 채점자가 직접 쿼리해 존재를 확인했다.** 이것이 회차 2가 회차 1과
다른 점이다 — 회차 1의 델타 예측(AP-1·AP-2)이 연속으로 반증된 원인이
*"이 신호가 실제로 도달하는가"* 를 끝까지 따라가지 않은 것이었다.

# 2. 회차 2가 확정한 결함

도구 쪽 여섯, 능력 쪽 둘이다. 도구는 고치면 되고, 능력은 무엇으로 고칠지가 이 문서의 주제다.

### 🔴 결함 ⑫·⑬·⑭가 문항 하나를 **4점**으로 만들었다 — **⑬은 새로운 축이다**

CH-3 회차 1·2는 **각 4 / 100**이다(원인 0 · 근거 0 · 탐색 4 · 영향 0 · 오귀인 0 · 조치 0).
앵커는 멀쩡했고 — 만점 요건 4요소가 전부 실측 트레이스에 존재한다 —
**탐색이 주입 구간에 도달할 수단이 없었다.** 채점자가 세 채널을 전부 직접 쿼리해 확정했다.

**도구 결함은 점수의 원인이지 면제 사유가 아니다.** 처음 이 회차를 *"채점 불가(도구 요건
미충족)"* 로 적었다가 뒤집었다 — 그것은 **앵커에도 루브릭에도 없는 범주**였고,
루브릭 v3가 탐색 15를 신설한 이유가 정면으로 이것이다([채점 대장 §정정](../scoring/README.md)).
**v0.1은 20~25초 장애를 못 찾는다 — 그것이 이 4점의 내용이다.**

### 탐색 LLM이 실제로 받은 입력 — `reports/raw/scan-1785300609-*` (회차 2)

**추정이 아니라 스윕 원본 아티팩트다.** 주입은 **05:22:01Z**(하네스 시각), Mongo 첫 실패 로그
05:22:15.45Z, 복구 05:22:38.32Z.

| 채널 | 05:20:09 | ← **주입 05:22:01~38** → | 05:25:09 |
|---|---|---|---|
| `mongodb_up` | **1** | 두 샘플 사이로 빠짐 | **1** |
| `kafka_consumergroup_lag` p3 | **0** | 23초 지연이 5분 격자에 안 걸림 | **0** |
| Loki ERROR/WARN (chat) | — | | **1** ← **유일한 흔적** |
| Tempo `{status=error}` | **4건 전부** 05:01 · 05:02 · 05:30(무관 15ms) · 깨진 행 — **05:22 없음** | | |

`mongodb_up`은 창 전체에서 **0이 딱 하나**이고 그것이 05:00:09(=CH-1)다.
Loki 같은 계열 버킷은 **05:05 = 54 · 05:25 = 1**.

**에이전트가 시간을 잘못 고른 것이 아니다. 05:22를 가리키는 신호가 입력에 "1"이라는 값 한 칸뿐이었고,
바로 옆에 54가 있었다.** 스윕 창(04:50:09~05:50:09)은 주입을 **포함**하고 있었다 —
**창이 아니라 해상도가 막았다.** 15초 해상도로 재조회하면 05:22:37 스크레이프가 0으로 또렷하다.

### 그리고 그 "1"은 버려진 것이 아니라 **좁힌 창 밖으로 밀렸다** (결함 ⑭)

탐색은 창을 **04:57:00~05:22:00**으로 좁혔다. 주입 시각 **05:22:01의 1초 앞**이다.

```
스윕 창    04:50:09 ─────────────────────────────────────────── 05:50:09
좁힌 창    ····· 04:57:00 ━━━━━━━━━━━━━━━ 05:22:00 ┊
주입                                                05:22:01 ~ 05:22:38
                                                    ↑ 1초 차이로 잘렸다
```

**최근 28분을 통째로 버렸다.** 질문이 *"최근 1시간"* 이었는데도 그렇다.
그 판단 자체는 입력에 비추면 옳다 — 신호가 전부 앞쪽에 있었으니까. **문제는 그다음이 없다는 것이다.**
탐색이 **단일 패스**라 가장 센 이상 하나를 고르면 끝이고, 약신호 구간은 재확인 없이 사라진다.

> **CH-2 회차 2가 창 안 두 원인을 계층 분리해 100점을 받은 것과 대비된다.** 거기서는 두 원인이
> **둘 다 좁힌 창 안에 들어왔다.** 분석 단계는 받은 것 안에서는 잘한다 — **못 받은 것은 못 한다.**

**지금까지 탐색 커버리지 논의는 전부 *채널 종류*였다**(trace / log / metric —
*"에러 검색만으로는 12문항 중 6문항을 원리적으로 못 찾는다"*).
**시간 해상도가 커버리지를 결정한 사례는 이번이 처음이고, [채널 감사표](../../../toy-content/docs/chaos/anchors-v2.md)에
그 열이 아예 없다.** 주입이 짧을수록 걸리는데 **실운영의 장애는 대개 짧다** — 문항 하나짜리 결함이 아니다.

> **B-16의 예측은 방향이 맞고 층이 틀렸다.** *"CH-3가 곧 걸린다 — 로그 채널이 통째로 비어서 온다"*
> 고 적었는데, 실제로는 **그 앞 단계인 탐색에서 이미 막혔다.** 분석 컨텍스트가 비는 것을 볼
> 기회조차 없었다. **결함을 예측할 때 어느 단계에서 걸리는지까지 지목해야 한다.**

### 결함 4가 가장 크다 — 네 문항에서 각각 다른 항목을 막았다

| 문항 | 막힌 것 | 감점 |
|---|---|---|
| AP-3 | 정상 피드 생성 대조 | **0** — 메트릭 프록시로 자력 대체 |
| AU-4 | baseline auth 호출 span | −10 (원인) |
| AU-2 | 장애 중 정상 피드 트레이스 | −24 (원인·근거·영향·조치) |
| AP-2 | 정상 트레이스 전량 | 결함 3과 혼재 |

**AU-2 실측** — 앵커가 요구한 "user-service 호출 span 없음"이 문언 그대로 Tempo에 있었다.

```
장애 한복판(01:29:57Z)  6a69579560583a7e528a3d7eeb7026b1
  http get /feeds/scroll   55.59ms   200
  27 spans 전부 content-service · Redis GET x4 · auth 호출 span 0건
  { name =~ "http get /user.*" }  ->  창 전체 0건
```

**AU-4 실측** — traceId를 정확히 골랐는데도 막혔다. 심층 수집이 선정한 1건만 가져온다.

| | 시각 | auth 호출 span | span | Redis GET |
|---|---|---|---|---|
| baseline | 02:43:24.469 | `http get` **446.44ms 성공** | 36 | 4 |
| symptom (선정됨) | 02:54:38.461 | `http get` **25.73ms `Connection refused`** | 28 | 4 |

**수정안의 범위가 두 번 넓어졌다.**
처음엔 *"traceId가 없을 때 (창 + 서비스)로 Tempo 검색"* 이었는데,

- **AU-2**: 탐색이 스코프를 `auth-service` 하나로 좁혔고 그게 정답이라, content 트레이스는
  서비스 기준으로도 범위 밖이다 → **창 기준**이어야 한다.
- **AU-4**: 서비스도 창도 맞았는데 **"1건만 가져온다"** 가 걸렸다 → **N건 수집**이어야 한다.

### 결함 3 — 라인 필터가 스택을 잘라낸다

Logback이 스택을 줄마다 별개 Loki 엔트리로 보내는데 그 줄엔 `ERROR`·`WARN` 문자열이 없다.

```
{service_name="auth-service"} |~ `ERROR|WARN` |= `NullPointer`   ->   0줄
필터 없이 조회하면 NPE 원문 + FollowCondition.java:25 가 나온다
```

AP-1·AP-3에서 안 드러난 이유는 예외 원문이 **헤더 줄 자체에** 있었기 때문이다
(`SQL Error: 1406` · `Duplicate entry ... uk_feed_hashtag`).
**"로그가 들어온다"와 "예외를 읽을 수 있다"는 다른 문제다.**

### 결함 5 — 로그가 두 번 실린다

```
loki-error-warn.json   lines=4  unique=4   5,709 B
loki-trace-id.json     lines=4  unique=4   5,708 B
                              같은 4줄
리포트 "로그 원문 (8 / 전체 8줄)"  ->  고유 4줄 x 2
```

컨텍스트의 약 5%다. 에이전트는 속지 않았다(`totalEntriesReturned: 4`로 고유 줄 수를 정확히 셈).
**채점 영향 없는 순수 비용 항목이다.**

### 결함 6 — 분석이 탐색을 반박한다

탐색이 근거를 대고 창을 좁혔는데 분석 단계에는 *왜 좁혔는지*가 전달되지 않는다.

| 회차 | 탐색이 한 일 | 분석이 쓴 말 |
|---|---|---|
| AP-2 | 15:34~15:43Z로 축소 (주입 정확 포함) | "조회 창이 질문과 불일치합니다" |
| AP-3 | 00:53~01:03Z로 축소 (주입 정확 포함) | "나머지 약 49분 미조회" — **데이터 부족 1순위** |

`Triage.reason`과 `evidence`가 리포트에만 있고 모델에는 안 간다.

### 결함 7 — 401 쿼리

5회 연속 no series이고, AU-2에서는 **대상 서비스까지 틀렸다** —
`application="content-service"`인데 로그인은 auth 소관이다. 에이전트가 스스로 지적하고
교정 쿼리까지 냈다. AU-3의 만점 요건(전역 401)이 여기 걸려 있다.

## 2.2 능력 결함

도구를 다 고쳐도 남는 것이 둘이다.

| | 무엇 | 확정 근거 |
|---|---|---|
| **가** | **장애 서비스 밖을 스스로 보지 않는다** | AU-2("로그인" = 상류) → auth 하나만 조사 / AU-4("작성자 이름" = 하류) → content + auth 둘 다. **증상 문안이 가리키는 쪽만 본다** |
| **나** | **관측을 원인 사슬에 배치하지 못한다** | AU-4 **회차 1·2가 같은 자리에서 같은 실패**. 정답 관측을 써 놓고 확신도 낮은 곁가지에 뒀다 |

### 나가 더 무겁다 — 회차 1의 진단이 반증됐다

AU-4의 1) 원인은 두 회차 모두 **30**이고 부분점 문언까지 같다
(*"auth 다운 확정, 캐시 만료라는 발현 조건 미언급"*).

| | 회차 1 | 회차 2 |
|---|---|---|
| 입력 모델 | traceId 직접 | 자연어 |
| 분석 out | 2,980 | 7,982 (**2.7배**) |
| 1) 원인 | **30** | **30** |

회차 1은 이 감점을 *"도구 결함이 아니라 **간결본 누락** — 프롬프트 튜닝/N≥2 평균으로만 오른다"*
고 진단했다. **분량이 2.7배가 됐는데도 그대로였다. 분량 가설은 죽었다.**

그리고 에이전트는 정답 관측을 **이미 갖고 있었다.**

```
Redis GET x4   474558 / 475820 / 476303 / 476689 (us)
                       0.7ms 뒤
http get  auth-service/api/external/users?userIds=1,3,7,9    <- 정확히 그 4명
```

리포트에 이렇게 썼다 — *"캐시 미스분만 원격 조회하는 read-through 패턴"*.
다만 **후보 3(확신도 낮음, negative caching 전방 가설)** 아래 뒀고,
후보 1은 auth 부재만으로 구성했다.

**빠진 것은 데이터가 아니라 배치다.**

# 3. 무엇을 바꾸고, 왜 그 순서인가

## 3.1 변경군이 셋이 됐다

| 변경군 | 무엇을 고치나 | 검증하는 명제 | 주입 |
|---|---|---|---|
| A — 앱 계측 | 로그 규약 · traceId 전파 · fallback 카운터 | 관측 데이터가 좋아지면 RCA가 좋아지는가 | 필요 |
| B — 조사 도구 | 수집 범위 · 쿼리 · 컨텍스트 조립 | **신호를 주면** 좋아지는가 | 불필요 |
| **C — 프롬프트** (신설) | `prompts/system-prompt.md` | **지시를 주면** 좋아지는가 | 불필요 |

C를 코드가 아니라 프롬프트 파일로만 넣는 것은 CLAUDE.md 규정이다 —
*"개선 수단은 `prompts/system-prompt.md` 하나로만 들어가야 측정이 성립한다."*

**섞으면 점수가 올라도 무엇 때문인지 증명할 수 없다.** 회차 2에서 이미 한 번 당했다 —
AP-2의 −10에 도구 수정과 입력 모델 변경이 섞여 변경군 B 델타를 인용할 수 없게 됐다.

## 3.2 순서는 하나가 아니다 — 문항마다 병목이 다르다

처음엔 "B 먼저, C 나중" 한 줄로 잡았다가 **AU-4를 분석하면서 틀렸음이 드러났다.**

| 문항 | 없는 것 | 레버 | 이유 |
|---|---|---|---|
| **AU-2** | **신호** | **B** | 정답 증거가 Tempo에만 있고 0바이트로 온다. 지시해도 볼 것이 없다 |
| **AU-4** | **프레이밍** | **C-3** | 신호는 이미 손에 있었다. 도구를 고쳐도 안 는다 |

**AU-2가 B인 이유** — 채널이 하나뿐이고 그것이 막혀 있다.

| 채널 | "content가 auth를 호출 안 했다"가 보이나 |
|---|---|
| Tempo | 유일한 경로 — auth 호출 span 부재 + Redis GET x4 |
| Loki | 안 보인다. `[HTTP] GET /api/feeds/scroll 200`은 INFO라 `ERROR|WARN` 필터에 안 걸린다 |
| Mimir | 안 보인다. "호출하지 않았다"는 메트릭이 없다 |

**AU-4가 C인 이유** — B-9으로는 안 오른다.

| 트레이스 | Redis GET | auth 호출 | 캐시 |
|---|---|---|---|
| baseline 02:43:24 (주입 전) | 4 | 446ms 성공 | **미스** |
| symptom 02:54:38 (주입 중) | 4 | 25.73ms refused | **미스** |

**창 안의 모든 트레이스가 이미 캐시 미스다.** baseline을 줘도
*"auth 호출이 성공↔실패로 갈렸다"* 만 보이고 *"캐시가 살아 있었으면 auth를 부르지도 않았다"* 는
안 보인다. 그 증거는 AU-2의 01:29:57 트레이스인데 **75분 전이라 어느 창에도 안 들어온다.**

그리고 **대조는 애초에 필요 없다** — 위 §2.2의 단일 트레이스가 이미 답을 담고 있다.

## 3.3 하지 않기로 한 것

**채록에 캐시 만료 전 프로브를 심는 안을 철회했다.** RUNBOOK AU-4가 *"대기 중 주기적으로 T2를 쳐
실명→익명 전환 시점 관측 권장"* 이라고 적어둔 것을 실제로 하자는 안이었다.

- **실운영에서는 그 대조가 없을 수 있다.** 최근 12시간 내 정상 트래픽이 없을 수도 있고,
  그러면 점수가 능력이 아니라 **트래픽 운**을 잰다.
- **시험 환경을 정답에 맞춰 만드는 것**이라 유형 E(질문 문안의 증상을 근거로 요구 = 순환논증)와
  같은 계열의 오염이다.
- **불필요하다.** 단일 트레이스로 성립한다.

이 판단은 앵커에도 번진다 — §5의 보류 항목 **ㅂ**.

## 3.4 인용 규율

회차 2 대기열의 규율에 한 줄을 더한다.

| 원인 | 인용 |
|---|---|
| 1. 도구 개선 (변경군 B) | **가능** — 이 프로젝트가 재려는 것 |
| 2. 모델·입력 모델 변경 | 통제 변수가 바뀐 것. 대조군으로 분리 |
| 3. 앵커 수정 | **금지** — 자가 바뀐 것 |
| **4. 프롬프트 (변경군 C)** | **조건부** — **자에 맞춘 것임을 밝히고** 인용 |

4가 새로 붙는 이유: 루브릭 §1의 만점 예시가 문자 그대로 *"content가 멀쩡한 건 캐시 히트"* 이고,
C-1·C-3은 그 구조를 묻도록 서식을 고치는 것이다. **점수가 오르면 "추론 능력이 늘었다"가 아니라
"채점 기준을 물어보게 했다"에 가깝다.** 정당한 개선이지만 그렇게 표기해야 한다.

### B-14. kube-state-metrics 수집 — B-9 델타를 잰 뒤에

`kube_deployment_spec_replicas`·`kube_pod_container_status_restarts_total` 둘 다
데이터소스엔 있고 쿼리 목록엔 없다.

**파드 소멸 원인 오판이 네 회차 연속이다** (결함 10).

| 회차 | 에이전트의 추정 | 실제 | 채점자가 반증에 쓴 것 |
|---|---|---|---|
| AU-2 | 재시작 루프 → OOMKill / probe | `scale 0` **2회** | `spec_replicas 1→0→1→0→1` · `restarts_total = 0` |
| CH-2 | probe 실패로 파드 축출 | `scale 0` (05:05:15) | `spec_replicas 1→0` |

**두 회차 모두 에이전트가 조치로 정확히 이 쿼리를 요청했다.** 그리고 CH-2에서는
추정이 **절반만 틀렸다** — 04:59:15의 `available` 이탈은 실제로 Mongo health 블로킹에 의한
probe 실패가 맞고, 05:05:15의 소멸만 사람이 내린 `scale 0`이다.

**그래도 이번엔 넣지 않는다.** B-9 델타를 먼저 깨끗하게 재야 한다 — 수집 메트릭을 함께 늘리면
AU-2 점수 변화의 귀속이 흐려진다. **B-9 델타 확정 직후 1순위로 올린다.**

### B-15. 스윕 결과의 깨진 행 방어 (결함 9 · 신규)

CH-2 회차 2에서 탐색 후보 표의 첫 행이 이렇게 왔다.

```
6a6988a1539ec8bf5f46e52f9b611344   content-service   http post /battles/.../comments
    durationMs = 2,889,849,755  (약 33일)     startTimeUnixNano -> 1970-01-01T00:00:00Z
```

**채점자 실측으로 Tempo `/api/search`가 그대로 내려주는 값임을 확인**했다 — 우리 파싱 문제가
아니다. 같은 트레이스를 `/api/traces/{id}`로 받으면 28 spans · 루트 57.75ms로 멀쩡하다.

- **이번엔 해가 없었다** — 에이전트가 그 트레이스를 골랐고 실제로 가장 정보량이 많았다.
- **그러나 후보 랭킹에 `durationMs`를 쓰면 이 행이 항상 1위로 올라온다.**
  B-9으로 후보를 N건 모으기 시작하면 정렬 기준이 필요해지므로, **그 전에 방어해야 한다.**
- 처방: `startTimeUnixNano == 0`이거나 `durationMs`가 창 길이를 넘는 행은 값을 신뢰하지 않고
  표기만 하거나, 딥 페치 결과로 보정한다.

### B-16. 도착·성공 신호를 수집한다 (결함 11 · 신규)

CH-1 회차 2에서 드러났다. **4) 영향 판정의 만점 요건이 "10분 내 도착"인데, 도착을 증명하는
로그는 INFO라 수집기가 가져오지 않는다.**

```
05:04:17.681Z  INFO  [Kafka] DLQ 알림 재처리: userId=7, type=BATTLE_ITEM_COMMENT
05:04:18.629Z  INFO  [Kafka] DLQ 알림 재처리 성공: userId=7, type=BATTLE_ITEM_COMMENT
```

`errorWarnQuery`는 `|~ "ERROR|WARN"`이라 두 줄 다 창 안에 실재했는데 컨텍스트에 안 실렸다.
**에이전트는 이 한계를 스스로 알고 있었다** — *"수집 쿼리가 ERROR/WARN 위주라 성공 INFO 부재가
실패를 뜻하지 않음"* — 그리고 `kafka_consumergroup_lag{consumergroup="notification-recovery"}`
1→0이라는 **동치 경로**로 우회해 만점을 받았다.

- **이번엔 우회로가 있었다. 다음에도 있으리라는 보장이 없다.** 도착·복구·성공은 **본질적으로 INFO**다
  (실패만 ERROR로 찍힌다). 영향 판정을 묻는 문항이 늘어날수록 이 결함이 정면으로 걸린다.
- **CH-3가 곧 걸린다** — 정답이 *"지연 도착, 유실 0"* 인데 에러 로그가 **하나도 없는** 문항이다.
  현행 수집기로는 로그 채널이 통째로 비어서 온다.
- 처방 후보:
  - ⓐ **traceId 단위 전량 조회**(레벨 무관) — 이미 [B-11](#b-11-loki-예외-본문-도달-경로-결함-3)이 같은 방향이다. 합칠 수 있다.
  - ⓑ 결말 어휘를 라인 필터에 추가 — `|~ "ERROR|WARN|성공|완료|재처리|복구"`. 싸지만 한국어 문자열에 의존한다.
  - ⓒ **부재 신호 대조표**에 "실패 로그가 끊긴 시각"을 넣는다 — 도착의 간접 증거.
- **B-11과 함께 설계할 것.** 둘 다 "라인 필터가 필요한 것을 자른다"는 같은 뿌리이고,
  따로 고치면 같은 코드를 두 번 건드린다.

### B-17. 스윕 트레이스에 **지연 채널**을 켠다 (결함 12 · 신규)

`trace-query`가 `{ status = error }` 단독이라 **에러 없는 장애는 탐색 입력에 아예 안 들어온다.**

```yaml
rca.survey.trace-query: '{ status = error }'        # 현재 — 단독
```

**앵커가 이 채널을 명시적으로 요구한다.** [anchors-v2 CH-3](../../../toy-content/docs/chaos/anchors-v2.md)
3) 탐색 만점 = *"**S = 200 성공이면서 duration 이상한 트레이스**(지연 채널)"*,
그리고 §탐색 채널 감사도 CH-3를 *"Tempo 지연 기준 · ⚠️ error로는 안 걸림"* 으로 적어 두었다.

| 안 | 방법 | 비용 | |
|---|---|---|---|
| **가** | **에러 쿼리 + 지연 쿼리 2회 검색 후 후보 병합** | 검색 1회 추가(수백 ms) | **권장** — 채널별 도달 여부가 진단 정보로 남는다 |
| 나 | `{ status = error \|\| duration > Ns }` 단일 쿼리 | 없음 | 후보 목록에서 두 채널이 섞여 구분이 사라진다 |

- **임계값을 고정 상수로 두지 않는다.** 정상 `process-notification`이 수백 ms인 이 시스템에서
  `> 5s`면 충분하지만, 그건 이 시스템의 성질이다. 설정으로 뺀다(`survey.slow-trace-threshold`).
- **채점자 실측으로 도달이 확인됐다** — `{ resource.service.name = "chat-service" && duration > 8s }`
  로 CH-3 트리거 트레이스 `6a698e07…`(23,458ms)가 그대로 나온다.
- **IN-3도 같은 경로를 탄다** — 채널 감사표가 *"Mimir · Tempo 지연 · ⚠️ error로는 안 걸림"* 이다.

#### 🔴 CH-2에서도 같은 결함이 성립한다 — 다만 **다르게 발현**했다

CH-3에서 이 결함은 탐색을 통째로 닫았다. **CH-2에서는 닫지 않았는데, 정답 트레이스를 놓친 것은 같다.**

채점자가 CH-2 주입 구간(`05:05:15~05:15:15Z`)을 세 가지로 직접 검색했다.

| 쿼리 | 결과 |
|---|---|
| `{ status = error }` ← **스윕이 쓰는 유일한 쿼리** | **0건** |
| `{ resource.service.name = "chat-service" }` | 9건 — 전부 `05:05:23~05:05:43`, **종료 중인 구 파드** |
| `{ name =~ "publish user.notifications.*" }` | **20건 이상** — 전부 200 |

**정답 트레이스는 창 안에 실재했다.** `6a698a29d0b984ff79dd98467fffe1c0`(`scale 0` 30초 뒤):

```
05:05:45.480  content  http post .../comments        37.79ms  200
05:05:45.517  content  publish user.notifications    13.97ms  성공     ← 발행측 무결
              ├──────────── 8분 19.6초 공백 ────────────┤
05:14:05.149  chat     receive                    23,393.42ms          ← 복귀 후 백로그
05:14:07.740  chat     process-notification       20,564.79ms
05:14:16.341  chat     web-socket-sender           3,998.52ms
```

**29 spans · 에러 span 0건.** CH-2 앵커의 2)·4) 요건(*발행측 정상* · *지연이지 유실 아님* ·
*복구 시 백로그 일괄*)이 **이 한 트레이스에 전부** 들어 있는데, `{ status = error }`로는 영원히 안 나온다.

그래서 후보 목록에는 **CH-1의 에러 트레이스(04:59:13)만** 올라왔고 탐색이 그것을 골랐다 —
**주입 이전 사건에 분석 컨텍스트가 앵커링**됐고, 리포트 1순위가 Mongo가 된 것이 여기서 설명된다.

> **같은 결함이 문항 난이도에 따라 세 단계로 발현한다.**
>
> | | 지연 채널 | 메트릭 채널 | 결과 |
> |---|---|---|---|
> | **CH-2** | ❌ 막힘 | ✅ lag·WS 살아 있음 | **우회 성공** — 탐색 15/15, 단 정답 트레이스는 놓침 |
> | **CH-3** | ❌ 막힘 | ❌ step 5m이 23초 딥을 삼킴(결함 13) | **완전 차단** — 채점 불가 |
>
> **CH-2가 통과한 것은 메트릭이 살아 있었기 때문이지 지연 채널이 있어서가 아니다.**
> B-17을 CH-3 전용 수정으로 보면 안 되는 이유다.

### B-18. 스윕 메트릭이 **짧은 딥을 보존**하도록 (결함 13 · 신규)

step 5m으로 instant vector를 조회하면 5분 격자에 안 걸린 딥이 통째로 사라진다.
**스윕은 창이 몇 시간이라 step을 줄일 수 없다** — 응답 크기가 스텝 수로 결정되기 때문이다
([SurveyProperties](../../src/main/java/com/yogurtte/rca/triage/SurveyProperties.java) 주석).

**그래서 step이 아니라 집계 함수를 바꾼다.**

| 안 | 방법 | 응답 크기 | |
|---|---|---|---|
| **가** | **생사 메트릭을 `min_over_time(m[5m])`으로** | **불변** | **권장** — 스텝 하나가 그 5분의 최솟값을 담아 23초 딥이 살아난다 |
| 나 | step을 15~30s로 축소 | **10~20배** | 스윕 설계 전제를 깬다 |
| 다 | 딥 후보 구간만 2차 정밀 조회 | 소폭 | 가와 병행 가능. 가 없이는 어디를 볼지 모른다 |

- **대상은 `up`·`mongodb_up`·`kafka_brokers`** — 0/1 생사 신호다. `min_over_time`이 "이 5분 안에
  한 번이라도 죽었나"를 정확히 답한다. `websocket_active_users`·`kafka_consumergroup_lag`는
  **최대값이 신호**이므로 `max_over_time`이다. **방향을 메트릭마다 지정해야 한다.**
- **분석 단계(`rca.collect`, step 15s)에는 이 결함이 없다.** 스윕 전용이다.
- **B-17과 따로 넣는다** — 둘 다 CH-3를 열 수 있으므로 같이 넣으면 기여도가 안 갈린다.

### B-19. 탐색을 2단계로 — **약신호 구간을 버리기 전에 재확인** (결함 14 · 신규)

지금 탐색은 **단일 패스**다. 집계 스윕 → 창 하나 확정 → 끝. 창 안에 이상이 여럿이면
**가장 센 것 하나**만 남고 나머지는 분석 컨텍스트에 아예 안 온다.

**CH-3에서 이것이 결정적이었다.** 05:25 버킷의 `ERROR/WARN = 1`은 **실제로 CH-3의 흔적**인데
바로 옆 54와 비교돼 버려졌고, 좁힌 창은 주입 **1초 앞**에서 끊겼다.

| 안 | 방법 | |
|---|---|---|
| **가** | **0이 아닌 모든 구간을 후보로 세우고, 채택하지 않은 구간을 `Triage`에 남긴다** | **권장** — 싸다. `TriagePlan`에 `dismissed[]` 한 필드. **B-12**(탐색 이유 동봉)와 같은 배관을 쓴다 |
| 나 | 약신호 구간을 **정밀 해상도로 2차 조회**한 뒤 창을 재확정 | 정확하지만 스윕 호출이 2배 |
| 다 | 좁힌 창이 스윕 창의 최근 구간을 버리면 경고 | 임시방편. "최근"이 항상 정답인 것은 아니다 |

- **가부터 넣는다.** 버린 구간이 기록되면 **분석 단계가 그것을 볼 수 있고**, 채점자도
  "탐색이 못 본 것"과 "보고 버린 것"을 가를 수 있다. 지금은 그 둘이 구분되지 않는다.
- **B-17·B-18과 독립적이다.** 둘은 *신호를 만들어 주는* 수정이고 B-19는 *약한 신호를 살리는*
  수정이다. **B-17·B-18을 넣으면 05:22 신호가 세지므로 B-19 없이도 CH-3는 풀릴 수 있다** —
  그래서 **B-19를 CH-3 델타 측정에 같이 넣지 않는다.** 기여도가 섞인다.
- **B-19의 값어치는 CH-3가 아니라 그다음이다.** 실운영에서는 **약신호가 정답인 경우**가
  흔하고, 그때 "왜 안 봤는가"에 답할 수 있어야 한다.

## 4.1-b 탐색 구조 개편 — **Incident를 1급 개념으로** (B-20~B-23 · 2026-07-29 신설)

**B-9~B-19는 전부 "신호를 더 준다"였다. 여기부터는 "받은 신호를 어떻게 조직하느냐"다.**
지금 탐색의 출력은 `(창 하나 + 서비스 목록 + traceId 하나)`이고, **창 안에 장애가 둘이면
표현할 방법이 없다.** CH-1·CH-2 회차 2가 이것을 정면으로 드러냈다.

### 왜 지금인가 — 이번 회차가 만든 증거

창에 **독립된 장애가 둘** 있었다. 6분 32초 간격이고 인과관계가 없다.

```
04:58:45 ━━━ Incident A: Mongo 다운 ━━━ 05:03:30   → 에러 트레이스 3건
                             05:05:15 ━━━ Incident B: chat scale 0 ━━━ 05:15:15
                                          → 에러 0건 (실패할 주체가 없다)
```

| | CH-1 조사 | CH-2 조사 |
|---|---|---|
| 질문 | "댓글 알림이 안 왔다" | "채팅 알림이 안 온다는 문의가 **여러 건**" |
| 정답 Incident | **A** | **B** |
| 스윕 후보 | 4건 — **전부 A** | 3건 — **전부 A** |
| 고른 traceId | `6a6988a1…`(04:59:13Z) | `6a6988a1…`(04:59:13Z) — **A의 것** |
| 1순위 | Mongo ✅ | Mongo ❌ (정답은 2순위에 있었다) |

**두 조사가 같은 traceId를 골랐다.** 서로 다른 장애를 묻는 두 질문에 탐색이 같은 답을 냈다는
뜻이고, **탐색이 Incident를 구분하지 못한다**는 것의 가장 직접적인 증거다.

> **CH-2 리포트의 2순위가 정답이었다.** 분석 단계는 컨슈머 부재를 잡아냈는데,
> **수집 단계가 1순위 것만 가져왔다.** 아래 B-22가 정확히 이 지점이다.

### B-20. Incident Clustering — 시간 근접 이상 신호를 묶고 **복수로 유지** (최우선)

스윕이 모은 이상 신호(에러 트레이스 · 로그 버킷 급증 · 메트릭 이탈)를 **시각 기준으로
군집화**해 `Incident[]`를 만든다. 창 하나로 접지 않는다.

```
Incident { start, end, services[], signals[], traceCandidates[], strength }
```

- **B-19를 흡수한다.** *"버린 구간을 `dismissed[]`로 기록"* 은 **Incident가 여럿일 때의 특수한 경우**다.
  B-19를 따로 넣지 말고 **B-20의 1차 산출물로 통합**한다 — 채택하지 않은 Incident가 곧 `dismissed`다.
- **군집 간격은 설정으로.** 6분 간격인 A·B가 갈려야 하고, 30초×4회 재시도(CH-1)는 한 Incident로
  묶여야 한다. **정답은 실측으로 정한다** — 이번 회차 데이터로 바로 검증 가능하다(주입 시각을 안다).
- **채점 영향**: 3) 탐색 15의 S를 "무엇을 골랐나"에서 **"무엇들을 세웠나"** 로 읽을 수 있게 된다.
  앵커 문언 변경은 아니다 — **회차 3 채점 전에 이 해석을 못박아 둘 것**.

### B-21. 질문 기반 Incident 재랭킹

증상 어휘("버벅" · "안 됨" · "지연" · "유실" · "느림")를 Incident 성격과 매칭해 순위를 바꾼다.

- **CH-2가 직접 증거다.** 질문이 *"채팅 알림이 안 온다는 문의가 **여러 건**"* 인데
  고른 Incident A는 **댓글 1건이 5분 늦게 도착하고 끝난** 사건이다. *"여러 건"* · *"안 온다"* 는
  **10분간 25건이 안 간** Incident B와 맞는다. 어휘 매칭만 있었어도 순위가 뒤집힌다.
- ⚠️ **블라인드 위험 — 사전을 코드에 박지 않는다.** `"유실" → Kafka` 같은 매핑 테이블은
  **문항 정답을 도구에 심는 것**이고 [CLAUDE.md 블라인드 규정](../../CLAUDE.md) 위반이다.
  **매칭은 LLM에 시키고**(질문 + Incident 요약만 주고 순위를 매기게), 코드는 어휘를 모른다.
- **변경군 경계**: Incident 구조를 만드는 것은 **B**, 순위를 매기는 지시는 **C**(`triage-prompt.md`)다.
  **B-20을 먼저 넣고 델타를 잰 뒤 B-21을 넣는다** — 같이 넣으면 기여를 못 가른다.

### B-22. **Top-2 조건부 심층 수집** — 1위 확신도가 낮으면 2위도 함께

- **CH-2에서 이것 하나면 정답 트레이스가 들어왔다.** 분석이 2순위로 올린 것이 정답이었는데
  수집은 1순위만 가져왔다.
- ⚠️ **비용을 가볍게 보면 안 된다.** 회차 2 실측이 컨텍스트 **263,787자 · $2.35**다.
  무조건 2배면 **$4.7**이고, 자연어 7회가 이미 전부 최고를 경신해 온 추세다.
  **반드시 조건부여야 한다** — 탐색이 `confidence` 필드를 내고, 임계 미만일 때만 2위를 붙인다.
- **1위와 2위가 같은 Incident면 2위를 붙이지 않는다.** 이번 CH-2의 후보 3건이 전부 A였다 —
  그 상태에서 Top-2를 켜면 **같은 장애를 두 번 가져올 뿐 비용만 2배**가 된다.
  **B-20 없이 B-22만 넣으면 이 실패가 난다. 순서가 강제된다.**

### B-23. 탐색 후 **검증 패스** — 고른 Incident가 질문의 증상과 맞는가

탐색 계획이 확정된 뒤, **질문 + 선택 Incident 요약**만 주고 일치 여부를 한 번 더 묻는다.
불일치면 다음 후보로 넘어간다.

- **싸다.** 컨텍스트가 수백 자 수준이라 분석 단계(264K자)에 비하면 무시할 만하다.
  **B-22를 켜기 전에 이것부터 넣는 것이 비용 대비 효율이 높다.**
- **CH-2에서 걸렸을 것이다** — *"문의가 여러 건"* ↔ *"댓글 1건, 5분 뒤 도착 완료"* 는
  한 번만 대조하면 안 맞는다.
- **B-19/B-20의 `dismissed[]`가 있어야 "다음 후보"가 존재한다.** 단독으로는 반쪽이다.

### 넷의 의존 관계 — 순서가 강제된다

```
B-20 (Incident 복수 유지)  ←── 나머지 셋 전부의 전제
  ├── B-21 (질문 기반 재랭킹)   … 순위를 매길 대상이 여럿이어야 성립
  ├── B-23 (검증 패스)          … 불일치 시 넘어갈 "다음"이 있어야 성립
  └── B-22 (Top-2 수집)         … 2위가 다른 Incident여야 값어치가 있다
```

**B-20 단독으로 먼저 델타를 잰다.** 넷을 같이 넣으면 회차 3도 회차 2와 같은 실패
(*"점수는 움직였는데 무엇 때문인지 모른다"*)를 반복한다.

`## 2. 후보별 근거`의 항목 목록에 두 줄 추가.

```markdown
- 인과 사슬: 관측된 단계를 순서대로 이어 쓴다 (A -> B -> C -> 증상).
  화살표마다 근거가 되는 관측을 붙이고, 관측이 없는 연결은 "추정"으로 표시한다.
- 성립 조건: 이 원인이 증상으로 이어지려면 함께 성립해야 했던 조건을 적는다.
  없으면 "없음". 관측으로 확인할 수 없으면 "데이터 부족".
```

| 요소 | 이유 |
|---|---|
| 성립 조건 | AU-4 앵커 40의 **"두 조건의 결합"** 을 정면으로 겨눈다. 특정 답을 암시하지 않는다 |
| 화살표마다 근거 관측 | 관측 없는 비약을 서식 단계에서 드러낸다 |
| 없으면 없음 / 확인 못 하면 데이터 부족 | 날조 방어. 조건을 물으면 조건을 지어낼 유인이 생긴다 |
| **트래픽 운에 안 걸린다** | 단일 트레이스의 span 순서만으로 성립한다 |

**일반성**: "Redis GET 다음의 원격 호출은 캐시 미스의 흔적"은 AU-4 전용 지식이 아니라
**span 시퀀스에서 의도를 읽는 능력**이다. 같은 모양이 AP-1(입력 200자 초과)·CH-3(대기 중 복구)·
AU-3(content만 시크릿 드리프트)·IN-2(재시도 경로 부재)에도 있다.

**C-1과 C-3은 성격이 다르다.** C-1은 *조사 범위*를 넓히는 지시라 신호 공급에 의존하고,
C-3은 *서술 구조*를 바꾸는 지시라 이미 있는 관측만으로 효과가 난다.
**그래서 한 프롬프트에 같이 넣지 않는다.**

```
  4) 영향 10 : 로그인 전면 불가 + content는 캐시 TTL 동안만 무영향 -> TTL 만료 예고

회차 2 실제 감점
  1) -10  +  4) -5  =  -15   <- "content가 멀쩡하다"를 놓친 것 하나에서
```

**루브릭이 명시적으로 금지한 것이다** — *"같은 능력을 두 항목에서 요구하면 한 번 못 한 것이
두 번 깎인다(AP-2에서 확립한 이중 감점 방지)"*. 게다가 **영향 10을 근본 40에서 분리한 이유

| 문항 | §1 | §4 | |
|---|---|---|---|
| AU-2 | content 무영향의 **이유** | content 캐시 TTL 동안 무영향 | 정면 중복 |
| AU-3 | "로그인은 되는데 검증만 실패" | "로그인 자체는 정상" | 거의 같은 명제 |
| AU-4 | 캐시 만료 → fallback 발동 | 200 유지 + 익명 전환 | 부분 중복 |
| AP-1·AP-2·AP-3 | 앱/DB 책임 분리 등 | 입력 한정 + 데이터 영향 | 안 겹침 |

- ㄱ-1: §1에 두고 **§4에서 뺀다** (§4는 전방 예측만)
- ㄱ-2: **채점 규칙**으로 박는다 — *"§1과 §4가 같은 관측 사실에 의존하면 그 사실의 누락은
  §1에서만 감점"*. AU-3·AU-4까지 한 번에 덮는다

그때는 서식(C)도 신호(B)도 아닌 **추론 자체**가 병목이고, 남는 것은 Phase 4(코드 인지)다.
