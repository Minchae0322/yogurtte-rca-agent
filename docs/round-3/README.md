# 회차 3 변경 대기열

회차 2(자연어 입력) 5회에서 확정한 결함과 그 수정안. **이 문서 하나로 "회차 2에서 무엇을
배웠고 회차 3에 무엇을 고치는가"가 닫힌다.**

- 적용 규칙: `round-N/`은 **회차 N에 적용할 변경**이고, 내용은 **회차 N−1에서 나온 것**이다
  (CLAUDE.md "개선 사항은 그것을 적용할 회차 폴더에 모은다").
- 회차별 발견 원문: [AP-1](../ap-1/round-2.md) · [AP-2](../ap-2/round-2.md) ·
  [AP-3](../ap-3/round-2.md) · [AU-2](../au-2/round-2.md) · [AU-4](../au-4/round-2.md)
- 직전 대기열: [round-2/](../round-2/README.md) — 인용 규율과 변경군 분리 원칙을 여기서 승계한다

# 1. 회차 2는 무엇이었나

입력 모델을 **traceId에서 자연어 한 줄로** 바꾼 첫 회차다. 5문항을 완주했고 전부
루브릭 v3(6항목)·앵커 v2로 채점했다.

| 문항 | 점수 | 한 줄 |
|---|---|---|
| AP-3 | 100 | 앱 dedup 구멍 도달. 탐색이 주입 트레이스를 자력 선정 |
| AP-1 | 90 | 앵커 재배치 미완으로 4항목 채점 |
| AU-4 | 88 | refused를 timeout과 구별. 캐시 만료 결합은 미도달 |
| AU-2 | 76 | auth 전면 부재 확정. content 축 전부 결손 |
| AP-2 | 53 | NPE·`size` 미도달 |

**점수 차를 능력 차로 읽으면 안 된다.** 다섯 문항이 같은 자를 통과했지만
**에이전트가 받을 수 있었던 증거의 양이 달랐다.**

| 문항 | 정답 신호가 어디 있나 | 도구가 막은 항목 | 점수 |
|---|---|---|---|
| AP-3 | 예외 원문이 span error 태그와 Loki 헤더 줄에 둘 다 | 탐색 B (메트릭으로 자력 대체 성공) | 100 |
| AP-1 | 예외 원문이 트레이스에 자백 | 없음 | 90 |
| AU-4 | client span의 `Connection refused` + fallback 로그 | 원인 | 88 |
| AU-2 | auth는 메트릭 소멸, content는 정상 트레이스의 span 부재 | 원인·근거·영향·조치 | 76 |
| AP-2 | 로그의 스택트레이스에만 | 근거·원인 | 53 |

**막힌 항목 수와 점수가 대체로 정렬된다** — 0개(100·90) → 1개(88) → 2개 이상(76·53).
표본 5개라 상관을 주장할 수는 없고, **회차 3의 반증 대상**으로 삼는다.
결함을 고친 뒤 AP-2·AU-2·AU-4가 오르지 않으면 이 해석이 틀린 것이다.

**못 받은 신호는 전부 채점자가 직접 쿼리해 존재를 확인했다.** 이것이 회차 2가 회차 1과
다른 점이다 — 회차 1의 델타 예측(AP-1·AP-2)이 연속으로 반증된 원인이
*"이 신호가 실제로 도달하는가"* 를 끝까지 따라가지 않은 것이었다.

# 2. 회차 2가 확정한 결함

도구 쪽 여섯, 능력 쪽 둘이다. 도구는 고치면 되고, 능력은 무엇으로 고칠지가 이 문서의 주제다.

## 2.1 도구 결함

| 번호 | 결함 | 확정 회차 | 상태 |
|---|---|---|---|
| 3 | Loki 라인 필터가 예외 본문·스택을 배제한다 | AP-2 | 미수정 |
| **4** | **선정한 트레이스 1건 외에는 안 온다** | AP-2 → AP-3 → AU-2 → AU-4 (**4문항**) | 미수정 · **최우선** |
| 5 | 같은 로그가 컨텍스트에 두 번 실린다 | AP-3 | 미수정 |
| 6 | 분석 단계가 탐색 단계를 반박한다 | AP-2 → AP-3 | 미수정 |
| 7 | `401 rate` 쿼리가 계속 빈다 (**5회 연속**) | 전 회차 | 미수정 |
| 8 | CLI 오버헤드 `C`가 같은 버전에서 진동한다 | AP-3 | **대응 완료** (회차별 프로브) |

### 결함 4가 가장 크다 — 네 문항에서 각각 다른 항목을 막았다

| 문항 | 막힌 것 | 감점 |
|---|---|---|
| AP-3 | 정상 피드 생성 대조 | **0** — 메트릭 프록시로 자력 대체 |
| AU-4 | baseline auth 호출 span | −10 (원인) |
| AU-2 | 장애 중 정상 피드 트레이스 | −24 (원인·근거·영향·조치) |
| AP-2 | 정상 트레이스 전량 | 결함 3과 혼재 |

**AU-2 실측** — 앵커가 요구한 "user-service 호출 span 없음"이 문언 그대로 Tempo에 있었다.

```
장애 한복판(01:29:57Z)  6a69579560583a7e528a3d7eeb7026b1
  http get /feeds/scroll   55.59ms   200
  27 spans 전부 content-service · Redis GET x4 · auth 호출 span 0건
  { name =~ "http get /user.*" }  ->  창 전체 0건
```

**AU-4 실측** — traceId를 정확히 골랐는데도 막혔다. 심층 수집이 선정한 1건만 가져온다.

| | 시각 | auth 호출 span | span | Redis GET |
|---|---|---|---|---|
| baseline | 02:43:24.469 | `http get` **446.44ms 성공** | 36 | 4 |
| symptom (선정됨) | 02:54:38.461 | `http get` **25.73ms `Connection refused`** | 28 | 4 |

**수정안의 범위가 두 번 넓어졌다.**
처음엔 *"traceId가 없을 때 (창 + 서비스)로 Tempo 검색"* 이었는데,

- **AU-2**: 탐색이 스코프를 `auth-service` 하나로 좁혔고 그게 정답이라, content 트레이스는
  서비스 기준으로도 범위 밖이다 → **창 기준**이어야 한다.
- **AU-4**: 서비스도 창도 맞았는데 **"1건만 가져온다"** 가 걸렸다 → **N건 수집**이어야 한다.

### 결함 3 — 라인 필터가 스택을 잘라낸다

Logback이 스택을 줄마다 별개 Loki 엔트리로 보내는데 그 줄엔 `ERROR`·`WARN` 문자열이 없다.

```
{service_name="auth-service"} |~ `ERROR|WARN` |= `NullPointer`   ->   0줄
필터 없이 조회하면 NPE 원문 + FollowCondition.java:25 가 나온다
```

AP-1·AP-3에서 안 드러난 이유는 예외 원문이 **헤더 줄 자체에** 있었기 때문이다
(`SQL Error: 1406` · `Duplicate entry ... uk_feed_hashtag`).
**"로그가 들어온다"와 "예외를 읽을 수 있다"는 다른 문제다.**

### 결함 5 — 로그가 두 번 실린다

```
loki-error-warn.json   lines=4  unique=4   5,709 B
loki-trace-id.json     lines=4  unique=4   5,708 B
                              같은 4줄
리포트 "로그 원문 (8 / 전체 8줄)"  ->  고유 4줄 x 2
```

컨텍스트의 약 5%다. 에이전트는 속지 않았다(`totalEntriesReturned: 4`로 고유 줄 수를 정확히 셈).
**채점 영향 없는 순수 비용 항목이다.**

### 결함 6 — 분석이 탐색을 반박한다

탐색이 근거를 대고 창을 좁혔는데 분석 단계에는 *왜 좁혔는지*가 전달되지 않는다.

| 회차 | 탐색이 한 일 | 분석이 쓴 말 |
|---|---|---|
| AP-2 | 15:34~15:43Z로 축소 (주입 정확 포함) | "조회 창이 질문과 불일치합니다" |
| AP-3 | 00:53~01:03Z로 축소 (주입 정확 포함) | "나머지 약 49분 미조회" — **데이터 부족 1순위** |

`Triage.reason`과 `evidence`가 리포트에만 있고 모델에는 안 간다.

### 결함 7 — 401 쿼리

5회 연속 no series이고, AU-2에서는 **대상 서비스까지 틀렸다** —
`application="content-service"`인데 로그인은 auth 소관이다. 에이전트가 스스로 지적하고
교정 쿼리까지 냈다. AU-3의 만점 요건(전역 401)이 여기 걸려 있다.

## 2.2 능력 결함

도구를 다 고쳐도 남는 것이 둘이다.

| | 무엇 | 확정 근거 |
|---|---|---|
| **가** | **장애 서비스 밖을 스스로 보지 않는다** | AU-2("로그인" = 상류) → auth 하나만 조사 / AU-4("작성자 이름" = 하류) → content + auth 둘 다. **증상 문안이 가리키는 쪽만 본다** |
| **나** | **관측을 원인 사슬에 배치하지 못한다** | AU-4 **회차 1·2가 같은 자리에서 같은 실패**. 정답 관측을 써 놓고 확신도 낮은 곁가지에 뒀다 |

### 나가 더 무겁다 — 회차 1의 진단이 반증됐다

AU-4의 1) 원인은 두 회차 모두 **30**이고 부분점 문언까지 같다
(*"auth 다운 확정, 캐시 만료라는 발현 조건 미언급"*).

| | 회차 1 | 회차 2 |
|---|---|---|
| 입력 모델 | traceId 직접 | 자연어 |
| 분석 out | 2,980 | 7,982 (**2.7배**) |
| 1) 원인 | **30** | **30** |

회차 1은 이 감점을 *"도구 결함이 아니라 **간결본 누락** — 프롬프트 튜닝/N≥2 평균으로만 오른다"*
고 진단했다. **분량이 2.7배가 됐는데도 그대로였다. 분량 가설은 죽었다.**

그리고 에이전트는 정답 관측을 **이미 갖고 있었다.**

```
Redis GET x4   474558 / 475820 / 476303 / 476689 (us)
                       0.7ms 뒤
http get  auth-service/api/external/users?userIds=1,3,7,9    <- 정확히 그 4명
```

리포트에 이렇게 썼다 — *"캐시 미스분만 원격 조회하는 read-through 패턴"*.
다만 **후보 3(확신도 낮음, negative caching 전방 가설)** 아래 뒀고,
후보 1은 auth 부재만으로 구성했다.

**빠진 것은 데이터가 아니라 배치다.**

# 3. 무엇을 바꾸고, 왜 그 순서인가

## 3.1 변경군이 셋이 됐다

| 변경군 | 무엇을 고치나 | 검증하는 명제 | 주입 |
|---|---|---|---|
| A — 앱 계측 | 로그 규약 · traceId 전파 · fallback 카운터 | 관측 데이터가 좋아지면 RCA가 좋아지는가 | 필요 |
| B — 조사 도구 | 수집 범위 · 쿼리 · 컨텍스트 조립 | **신호를 주면** 좋아지는가 | 불필요 |
| **C — 프롬프트** (신설) | `prompts/system-prompt.md` | **지시를 주면** 좋아지는가 | 불필요 |

C를 코드가 아니라 프롬프트 파일로만 넣는 것은 CLAUDE.md 규정이다 —
*"개선 수단은 `prompts/system-prompt.md` 하나로만 들어가야 측정이 성립한다."*

**섞으면 점수가 올라도 무엇 때문인지 증명할 수 없다.** 회차 2에서 이미 한 번 당했다 —
AP-2의 −10에 도구 수정과 입력 모델 변경이 섞여 변경군 B 델타를 인용할 수 없게 됐다.

## 3.2 순서는 하나가 아니다 — 문항마다 병목이 다르다

처음엔 "B 먼저, C 나중" 한 줄로 잡았다가 **AU-4를 분석하면서 틀렸음이 드러났다.**

| 문항 | 없는 것 | 레버 | 이유 |
|---|---|---|---|
| **AU-2** | **신호** | **B** | 정답 증거가 Tempo에만 있고 0바이트로 온다. 지시해도 볼 것이 없다 |
| **AU-4** | **프레이밍** | **C-3** | 신호는 이미 손에 있었다. 도구를 고쳐도 안 는다 |

**AU-2가 B인 이유** — 채널이 하나뿐이고 그것이 막혀 있다.

| 채널 | "content가 auth를 호출 안 했다"가 보이나 |
|---|---|
| Tempo | 유일한 경로 — auth 호출 span 부재 + Redis GET x4 |
| Loki | 안 보인다. `[HTTP] GET /api/feeds/scroll 200`은 INFO라 `ERROR|WARN` 필터에 안 걸린다 |
| Mimir | 안 보인다. "호출하지 않았다"는 메트릭이 없다 |

**AU-4가 C인 이유** — B-9으로는 안 오른다.

| 트레이스 | Redis GET | auth 호출 | 캐시 |
|---|---|---|---|
| baseline 02:43:24 (주입 전) | 4 | 446ms 성공 | **미스** |
| symptom 02:54:38 (주입 중) | 4 | 25.73ms refused | **미스** |

**창 안의 모든 트레이스가 이미 캐시 미스다.** baseline을 줘도
*"auth 호출이 성공↔실패로 갈렸다"* 만 보이고 *"캐시가 살아 있었으면 auth를 부르지도 않았다"* 는
안 보인다. 그 증거는 AU-2의 01:29:57 트레이스인데 **75분 전이라 어느 창에도 안 들어온다.**

그리고 **대조는 애초에 필요 없다** — 위 §2.2의 단일 트레이스가 이미 답을 담고 있다.

## 3.3 하지 않기로 한 것

**채록에 캐시 만료 전 프로브를 심는 안을 철회했다.** RUNBOOK AU-4가 *"대기 중 주기적으로 T2를 쳐
실명→익명 전환 시점 관측 권장"* 이라고 적어둔 것을 실제로 하자는 안이었다.

- **실운영에서는 그 대조가 없을 수 있다.** 최근 12시간 내 정상 트래픽이 없을 수도 있고,
  그러면 점수가 능력이 아니라 **트래픽 운**을 잰다.
- **시험 환경을 정답에 맞춰 만드는 것**이라 유형 E(질문 문안의 증상을 근거로 요구 = 순환논증)와
  같은 계열의 오염이다.
- **불필요하다.** 단일 트레이스로 성립한다.

이 판단은 앵커에도 번진다 — §5의 보류 항목 **ㅂ**.

## 3.4 인용 규율

회차 2 대기열의 규율에 한 줄을 더한다.

| 원인 | 인용 |
|---|---|
| 1. 도구 개선 (변경군 B) | **가능** — 이 프로젝트가 재려는 것 |
| 2. 모델·입력 모델 변경 | 통제 변수가 바뀐 것. 대조군으로 분리 |
| 3. 앵커 수정 | **금지** — 자가 바뀐 것 |
| **4. 프롬프트 (변경군 C)** | **조건부** — **자에 맞춘 것임을 밝히고** 인용 |

4가 새로 붙는 이유: 루브릭 §1의 만점 예시가 문자 그대로 *"content가 멀쩡한 건 캐시 히트"* 이고,
C-1·C-3은 그 구조를 묻도록 서식을 고치는 것이다. **점수가 오르면 "추론 능력이 늘었다"가 아니라
"채점 기준을 물어보게 했다"에 가깝다.** 정당한 개선이지만 그렇게 표기해야 한다.

# 4. 변경 목록

## 4.1 변경군 B — 조사 도구 (주입 없이 적용)

### B-9. 창 기준으로 트레이스를 N건 수집한다 (결함 4) — 최우선

traceId 선정 여부와 무관하게, **좁힌 창 안의 후보 트레이스를 N건까지** 가져온다.

| 안 | 방법 | AU-2 | AU-4 |
|---|---|---|---|
| 가 | 선정 서비스 + 그 하류를 스코프에 | 풀림 | 풀림 |
| **나** | **창 기준 전 서비스 · N건 수집** | **풀림** | **풀림** |
| 다 | 2단계 조사(가설 → 재수집) | 풀림 | 풀림 |

**나 권장.** 가장 싸고, `Scope`가 traceId를 선택값으로 설계된 취지(strategy.md §4.5)에 맞는다.
컨텍스트 증가는 B-10이 일부 상쇄한다. **CH-2·AP-2도 같은 경로를 탄다.**

### B-10. 어셈블 시 로그 dedup (결함 5)

`(timestamp, line)` 기준으로 접는다. **두 채널은 유지하고 합칠 때만 dedup**한다 —
채널별 도달 여부는 진단 정보다.

### B-11. Loki 예외 본문 도달 경로 (결함 3)

**traceId 단위 전량 조회가 정답**(에이전트가 AP-2 조치 1로 제안한 그것).
스택 포함 정규식(`ERROR|WARN|Exception|\tat `)은 무관한 스택까지 끌어오므로 차선.

### B-12. 어셈블 컨텍스트에 탐색 선정 이유 동봉 (결함 6)

`Triage.reason`·`evidence`를 어셈블 컨텍스트에 넣는다.

### B-13. `401 rate` 쿼리 교정 (결함 7)

`count by (status, uri) (http_server_requests_seconds_count{...})`로 실제 라벨과 status 값을
먼저 확인한 뒤 확정한다. **대상 서비스도 함께 바로잡는다.**

### B-4 (회차 2에서 승계). 수집 창이 복구를 담도록

AU-2 회차 2에서 복구 오판이 재발하지 않은 것은 **운이다** — 주입이 2회라 마지막 복구가
조사 시점에 2분밖에 안 떨어져 창에 담겼다. 1회 주입으로 돌아가면 다시 걸린다.

### B-14. kube-state-metrics 수집 — B-9 델타를 잰 뒤에

`kube_deployment_spec_replicas`·`kube_pod_container_status_restarts_total` 둘 다
데이터소스엔 있고 쿼리 목록엔 없다. AU-2에서 채점자가 이 둘로 에이전트의 "재시작 루프"
가설을 반증했고, **에이전트도 조치로 정확히 이 두 쿼리를 지목했다.**

**이번엔 넣지 않는다.** B-9 델타를 먼저 깨끗하게 재야 한다 — 수집 메트릭을 함께 늘리면
AU-2 점수 변화의 귀속이 흐려진다.

```markdown
## 3. 영향 범위
```

| 요소 | 이유 |
|---|---|
| 실패/지연/유실, 되돌릴 수 있는지 | rubric §4의 세 축을 **문항 중립적으로** 옮긴 것 |

| 데이터 부족으로 적는다 | **날조 방어.** "정상인 이유를 설명하라"는 지시는 없는 설명을 지어낼 유인을 만든다 |

에이전트가 **이미 하고 있다.** AU-2에서 *"`up`이 `0`으로 기록된 샘플은 한 건도 없습니다 —
스크레이프 실패가 아니라 타깃 자체가 사라지는 형태"* 를 짚고 `absent(up{...})==1` 알람까지 냈다.
AP-3에서도 Kafka producer span 부재를 근거로 썼다.
**지시가 필요 없는 것을 지시하면 델타만 흐려진다.**

### C-3. 원인을 레이블이 아니라 사슬로 쓰게 한다 (능력 결함 나)

`## 2. 후보별 근거`의 항목 목록에 두 줄 추가.

```markdown
- 인과 사슬: 관측된 단계를 순서대로 이어 쓴다 (A -> B -> C -> 증상).
  화살표마다 근거가 되는 관측을 붙이고, 관측이 없는 연결은 "추정"으로 표시한다.
- 성립 조건: 이 원인이 증상으로 이어지려면 함께 성립해야 했던 조건을 적는다.
  없으면 "없음". 관측으로 확인할 수 없으면 "데이터 부족".
```

| 요소 | 이유 |
|---|---|
| 성립 조건 | AU-4 앵커 40의 **"두 조건의 결합"** 을 정면으로 겨눈다. 특정 답을 암시하지 않는다 |
| 화살표마다 근거 관측 | 관측 없는 비약을 서식 단계에서 드러낸다 |
| 없으면 없음 / 확인 못 하면 데이터 부족 | 날조 방어. 조건을 물으면 조건을 지어낼 유인이 생긴다 |
| **트래픽 운에 안 걸린다** | 단일 트레이스의 span 순서만으로 성립한다 |

**일반성**: "Redis GET 다음의 원격 호출은 캐시 미스의 흔적"은 AU-4 전용 지식이 아니라
**span 시퀀스에서 의도를 읽는 능력**이다. 같은 모양이 AP-1(입력 200자 초과)·CH-3(대기 중 복구)·
AU-3(content만 시크릿 드리프트)·IN-2(재시도 경로 부재)에도 있다.

**C-1과 C-3은 성격이 다르다.** C-1은 *조사 범위*를 넓히는 지시라 신호 공급에 의존하고,
C-3은 *서술 구조*를 바꾸는 지시라 이미 있는 관측만으로 효과가 난다.
**그래서 한 프롬프트에 같이 넣지 않는다.**
