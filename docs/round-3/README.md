# 회차 2에서 내린 판단

> **포트폴리오·면접용 서술.** 아래 §1~§7이 "무엇을 고칠 것인가"라면 이 절은
> **"회차 2에서 무엇을 판단했고 왜 그렇게 판단했는가"** 다. 수치는 전부 실측이다.

## RCA 평가 체계 설계

### 상황

| | |
|---|---|
| 검증 대상 | 에이전트가 아니라 **평가 체계 자체** |
| 계기 | 같은 문항·같은 자·같은 입력으로 두 번 돌렸는데 **총점 25점 차** |
| 두 실행의 유일한 차이 | 리포트 출력 분량 2,980 ↔ 10,511 토큰(**3.5배**) |
| 당시 상태 | 모든 점수가 **N=1**, 채점 항목 4개(`근본 원인 40`에 원인·기전·영향이 섞여 있었다) |

### 무엇이 일어났나

RCA 에이전트의 성능을 개선하기에 앞서 평가 체계 자체의 신뢰성을 먼저 검증했습니다. 초기에는
프롬프트와 모델 성능을 개선하는 방향을 검토했지만, 동일 모델에서도 평가 결과의 편차가 크게
발생하는 현상을 확인했습니다. 이를 모델 문제로 단정하지 않고, 각 감점 항목이 실제
Trace·Log·Metric에서 관측 가능한 신호를 기반으로 평가되는지 역추적했습니다.

검증 결과 대부분의 오답은 모델의 추론 능력이 아니라 조사에 필요한 관측 신호가 부족한 구조적
한계에서 발생했습니다. 이에 개선 우선순위를 프롬프트 최적화에서 계측(App Instrumentation) →
데이터 수집(Collection) → 프롬프트(Prompt) 순으로 재설계하고, 각 요소를 독립 변수로 분리한
실험 체계를 구축하여 변경 효과를 객관적으로 검증했습니다.

또한 RCA 결과가 단순한 원인 레이블이 아니라 관측 → 인과 사슬 → 원인 → 복구 계획으로
이어지도록 평가 기준을 고도화했습니다. 인과 관계의 각 단계는 Trace·Log·Metric 등 관측 근거를
요구하고, 근거가 없는 연결은 '추정', 확인할 수 없는 조건은 '데이터 부족'으로 명시하도록
설계하여 AI의 근거 없는 추론을 줄이고, 결과의 검증 가능성과 재현성을 높였습니다.

### 근거 — 문장별 실측

| 서술 | 실측 근거 |
|---|---|
| "동일 모델에서도 평가 결과의 편차가 크게 발생" | 같은 문항·같은 채점 기준·같은 입력 모델로 두 번 실행했는데 **총점 75 ↔ 약 100 (25점 차)**. 두 실행의 유일한 차이는 리포트 출력 분량(2,980 ↔ 10,511 토큰, **3.5배**)이었다 |
| "각 감점 항목이 관측 가능한 신호에 기반하는지 역추적" | 감점된 항목마다 채점 기준이 요구한 근거를 **채점자가 Tempo·Loki·Mimir에 직접 쿼리**해 존재를 확인했다. 예: 한 문항의 요건 *"정상 요청에 auth 호출 span이 없다"* → `{ name =~ "http get /user.*" }` 창 전체 **0건**, 해당 트레이스 27 spans 중 Redis GET 4건 · auth 호출 span 0건이 **문언 그대로 실재** |
| "관측 신호가 부족한 구조적 한계" | 그 신호가 **컨텍스트에는 0바이트로 도착**했다. 수집기가 선정한 트레이스 1건 외에는 가져오지 않기 때문(결함 4, 5문항에서 발현). 또 다른 문항은 로그 라인 필터가 스택트레이스를 잘라 정답이 통째로 누락(결함 3) |
| "대부분의 오답이" | **막힌 항목 수와 점수가 정렬**됐다 — 0개(100·90) → 1개(88) → 2개 이상(76·53) → 전체(4) |
| "독립 변수로 분리한 실험 체계" | 변경을 **A(앱 계측) / B(조사 도구) / C(프롬프트)** 세 군으로 나누고 **한 회차에 한 군만** 적용. 이미 천장에 닿은 문항 2개를 **대조군**으로 고정. 회차마다 **예측과 반증 조건을 먼저 문서화**(§6) |
| "변경 효과를 객관적으로 검증" | 점수 인용 규칙을 **문항당 N≥2 · 평균 ± 최대편차**로 박았다. 4문항에서 N=2 확보 — **4 ± 0 · 53 ± 0 · 90 ± 0 · 97.5 ± 2.5** |
| "관측 → 인과 사슬 → 원인 → 복구 계획" | 채점 기준을 **6항목**(원인 40 · 근거 25 · 탐색 15 · 영향 10 · 오귀인 5 · 조치 5)으로 재편. 이전 기준은 `근본 원인 40` 한 칸에 원인·기전·영향 판정 **세 능력이 섞여** 있었고, 한 문항의 감점 20점 전액이 영향 오판이었는데 그것이 "원인" 점수로 기록되고 있었다 |
| "근거 없는 연결은 '추정', 확인 불가는 '데이터 부족'" | 리포트 서식에 **인과 사슬**(화살표마다 근거 관측을 붙이고, 관측 없는 연결은 "추정")과 **성립 조건**(확인 불가 시 "데이터 부족")을 요구하도록 프롬프트 사양을 작성 |

> **적용 시점을 구분해 둡니다.** 채점 기준 6항목과 N≥2 규칙은 **회차 2부터 적용**됐고,
> 리포트 서식의 인과 사슬·성립 조건은 **회차 3 대기열**(C-1·C-3)입니다. 아직 효과가 측정되지
> 않았으므로 이 서술은 **설계까지**를 주장합니다.

### 예상 꼬리질문과 답변

**Q1. "편차가 크다"는 게 몇 점입니까? 표본 몇 개로 그렇게 판단했습니까?**

같은 조건 두 실행에서 **25점**입니다. 이 관찰 하나로 결론을 내린 게 아니라, **이후 모든 점수에
N≥2를 강제**하는 규칙으로 바꿨습니다. 현재 4문항에서 N=2를 확보했고 3개는 편차 0, 1개가
±2.5입니다. **N=1 점수는 문서에 남기되 인용 금지**로 표시합니다.

**Q2. 편차 0이면 안정적인 것 아닙니까?**

아닙니다. 편차 0인 3개 중 **둘은 능력이 아니라 막힘의 재현**입니다 — 하나는 탐색이 주입
구간을 1초 차이로 잘라 산출물이 아예 없었고(4점), 다른 하나는 정답이 로그 필터에 잘려 쓸
신호가 없었습니다(53점). **천장이나 바닥에 눌린 값은 분산이 없습니다.** 그래서 채점 기록에
편차와 함께 *"정답 신호가 컨텍스트에 도달했는가"* 를 반드시 남기도록 서식을 바꿨습니다.

**Q3. "모델이 아니라 관측 신호 부족"이라는 진단, 반증 가능합니까?**

가능하도록 설계했습니다. 문항별로 **"이 변경 → 이 점수 → 안 오르면 이 진단이 틀린 것"** 을
예측표(§6)에 먼저 적어 둡니다. 예를 들어 한 문항은 *"수집 범위를 고치면 +10~+24, 안 오르면
신호가 아니라 지시가 병목"* 입니다. 실제로 **직전 회차에서 같은 방식으로 세운 가설을
기각한 전례**가 있습니다 — *"출력 분량이 짧아서 감점됐다"* 는 진단이었는데 분량을 **2.7배**로
늘렸더니 점수가 동일해서 폐기했습니다.

**Q4. 왜 계측 → 수집 → 프롬프트 순입니까? 실제로 계측부터 했습니까?**

**층위의 순서이지 실행 순서가 아닙니다.** 실행은 **검증 비용**으로 갈립니다 — 수집(B)은
기존에 저장된 관측 데이터를 다시 조사하면 되므로 **장애 주입 없이** 델타를 잴 수 있어 먼저
넣고, 계측(A)은 앱을 고쳐 **다시 주입해야** 하므로 별도 사이클로 뺐습니다. 프롬프트(C)는
**신호가 이미 도달한 문항에서만** 단독으로 재야 도구 변수가 섞이지 않아 마지막입니다.
층위상 계측이 최상류인 것은 맞지만, 그 순서대로 실행하면 회차당 비용이 몇 배가 됩니다.

**Q5. 독립 변수 분리가 실제로 지켜졌습니까?**

**한 번 실패했고, 그 실패 때문에 규칙이 생겼습니다.** 회차 2에서 도구 수정과 입력 모델 변경을
같이 넣는 바람에 한 문항의 −10이 어느 쪽 때문인지 귀속시키지 못했습니다. 이후로는 회차마다
**변경군을 문서에 명시**하고, 아무것도 바꾸지 않는 **대조군 문항**을 반드시 포함시킵니다 —
대조군이 움직이면 통제가 깨진 것입니다.

**Q6. "데이터 부족"으로 적으라고 하면 다 그렇게 도망가지 않습니까?**

그래서 **유보를 만점으로 인정하지 않습니다.** 영향 판정 10점에서 *"범위 유보"* 는 부분점(5점)
구간입니다. 실제로 한 회차가 *"영향 범위는 데이터 부족"* 으로 유보해 **5점을 받았고**, 같은
문항의 다른 실행은 범위를 확정해 10점을 받았습니다. **모르면 모른다고 쓰는 것이 지어내는
것보다 낫지만, 아는 것보다는 낮다** — 이 서열이 배점에 들어가 있습니다.

**Q7. 채점은 누가 합니까? 자기 채점 아닙니까?**

**에이전트는 피험자이고 채점은 분리돼 있습니다.** 리포트 생성 경로에 정답지를 넣지 않고,
리포트 안에서 점수를 생성하는 것도 금지합니다. 채점 기준은 **주입 전에 커밋으로 박제**하고
채점 시 커밋 시각과 주입 시각을 대조합니다(가장 최근 회차는 **17시간** 앞섰습니다).
검증 과정에서 **LLM CLI가 작업 디렉터리의 프로젝트 문서를 자동 로드**해 피험자가 정답 문서를
읽고 있던 것을 발견했고, 격리 샌드박스로 차단한 뒤 오염 크기를 **6,144 토큰(+23%)** 으로
직접 측정했습니다.

**Q8. 그래서 점수가 올랐습니까?**

**아직입니다. 그게 다음 회차의 내용입니다.** 지금까지 확정한 것은 baseline, 결함 목록,
변경 우선순위, 그리고 **변경별 예측과 반증 조건**입니다. 개선 효과를 주장하려면 같은
채점 기준으로 N≥2를 다시 잡아야 하고, 그 전까지는 *"무엇이 병목인지 특정했다"* 까지만
주장합니다.

### 회차 3에서 바꿀 것

| | 대상 | 변경 | 근거 |
|---|---|---|---|
| **ㄷ·ㄹ·ㅈ** | 채점 기준 | 배점이 큰 **3구간 항목에 중간 구간 신설** (탐색 15 · 영향 10 · 원인 40) | 실제 결과가 문언 사이에 떨어져 **판정을 6회 연속 강요**했다. 한 문항은 **관측된 분산 전량**이 여기서 나왔다 |
| **C-3** | 프롬프트 | 후보별 근거에 **인과 사슬 · 성립 조건** 요구 | 화살표마다 근거 관측을 붙이고, 관측 없는 연결은 **"추정"**, 확인 불가 조건은 **"데이터 부족"** |
| **C-1** | 프롬프트 | **영향 범위** 절 신설 | 채점 항목 6개 중 `영향 10`을 프롬프트가 **한 줄도 묻지 않는다.** 그 항목에서 점수를 잃은 회차가 둘 |

**검증 설계 — 자와 도구를 같은 회차에 바꾸지 않습니다**

- **C-3 단독 → AU-4.** 신호는 이미 도달했고 두 회차가 **같은 실패를 재현**(N=2)했으므로
  도구 변수 없이 프롬프트 효과만 잡힙니다. 예측 **원인 30 → 40**
- **C-1 → AU-2.** 단 **B 델타를 먼저 본 뒤** 넣습니다 — B로 올랐으면 병목이 신호였던 것이고,
  안 올랐을 때만 지시가 병목이라는 가설이 성립합니다
- **앵커 개정은 소급 적용하지 않습니다.** 자를 바꾸면 그 자로 매긴 기존 점수와 비교가
  성립하지 않습니다. 적용할 회차에는 **두 자로 동시 채점**해 이동 방향을 기록합니다

**반증 조건**

| 변경 | 안 오르면 |
|---|---|
| C-3 (서식) | 서식이 아니라 **추론 자체**가 병목이다 — 남는 것은 코드 인지 단계 |
| C-1 (영향 범위) | 감점 원인이 양식이 아니라 **관측 결손**이다 |
| 중간 구간 신설 | 판정이 계속 강요되면 구간 정의가 잘못된 것 |

> **현재 상태**: 채점 항목 6개 재편·N≥2 규칙·블라인드 격리는 **회차 2부터 적용 완료**.
> 프롬프트 서식(C-1·C-3)과 앵커 중간 구간은 **회차 3 대기열**이며, **효과는 미측정**입니다.

## 장애 탐색 채널 설계 — 채널은 켰는데 채널 안에서 또 잘린다

### 상황

| | |
|---|---|
| 입력 모델 변경 | 사람이 고른 **traceId 1개** → **자연어 질문 하나** |
| 신설 단계 | 장애 탐색(triage) — 창 파싱 → 스윕 → 대상 선정 |
| 초기 설계 | *"에러 트레이스를 검색해 대표 traceId 하나를 뽑아 기존 분석 경로로 넘긴다"* |
| 검증 대상 | 12개 장애 시나리오의 **정답 신호가 어느 채널에 있는가** |
| 검증 비용 | **0** — 시나리오별 정답과 실제 주입 결과가 이미 문서화돼 있어 코드 없이 가능 |

### 무엇이 일어났나

초기 설계를 구현한 뒤 문항별로 성능을 재는 대신, **12개 시나리오의 정답 신호가 어느 관측
채널에 존재하는지를 먼저 전수 분류**했습니다.

| 도달 채널 | 문항 수 | |
|---|---:|---|
| Tempo `status=error` 검색으로 잡힘 | 6 | 초기 설계로 도달 가능 |
| **에러로 안 잡힘 — 로그** | 2 | 트레이스는 `exception=none` / 401은 error가 아니다 |
| **에러로 안 잡힘 — 메트릭** | 3 | lag 상승 · 시계열 소멸 · 커넥션 pending |
| **에러로 안 잡힘 — 지연** | 1 | 200 성공 + 공백 |

**Trace의 에러 검색만 구현하면 12문항 중 6문항이 원리적으로 탐지 불가**하고, 그중 **3문항은
정답 신호가 트레이스에 아예 생성되지 않는다**는 것을 코드 작성 전에 확인했습니다 —
컨슈머가 전멸해서 트레이스를 만들 주체가 없고, ingress가 끊겨서, 예외가 로그에만 남아서입니다.

이에 탐색 단계의 출력 인터페이스를 *"대표 traceId"* 가 아니라 **`(시간창 + 대상 서비스 +
신호 종류)`** 로 설계하고 traceId는 있으면 딸려가는 값으로 내렸으며,
**Trace·Log·Metric 3채널 동시 스윕**을 최소 요건으로 확정해 구현했습니다.

**그런데 채널을 다 켜고 나니 각 채널 *안에서* 잘리는 것이 드러났습니다.**

| 채널 | 켜져 있는가 | 그런데 |
|---|---|---|
| Trace | 켜짐 | **선정한 트레이스 1건 외에는 안 가져온다** — 대조군도 다른 후보도 사라진다 (5문항 발현) |
| Log | 켜짐 | 라인 필터 `ERROR\|WARN`이 **스택트레이스 줄을 배제**한다. 도착·복구 로그는 **INFO라 아예 안 온다** |
| Metric | 켜짐 | 감별용 메트릭이 **수집 목록 밖**이다. 데이터소스엔 있고 에이전트가 매번 정확히 요청한다 |

**"채널이 있다"와 "그 채널로 필요한 것이 온다"는 다른 문제였습니다.**
그리고 이 감사는 채널 *종류*만 다뤘고 **시간 해상도**를 축에 넣지 않아, 23초짜리 장애가
5분 간격 메트릭 격자에 한 샘플도 걸리지 않는 사례를 예측하지 못했습니다.
**커버리지는 "어느 채널"과 "어느 해상도"의 곱**이라는 점을 축에 추가했습니다.

### RCA 에이전트 장애 미탐지 원인 분석 및 탐색 구조 개선

RCA 에이전트 검증 과정에서 **TimeParser가 생성한 초기 분석 시간 범위(04:50~05:50) 안에 장애 구간(05:22:01~05:22:38)이 존재했음에도 원인을 도출하지 못하는 문제가 발생했습니다.** 분석 결과, LLM이 초기 시간 범위에서 상세 조사 대상으로 축소한 Window(04:57~05:22)가 장애 발생 1초 전에 종료되면서 원인 분석에 필요한 신호가 제외되고 있었습니다.

처음에는 조사 범위를 확대하는 방식으로 해결할 수 있다고 판단했습니다. 그러나 조사 Window를 2.26배 확장한 실험에서도 컨텍스트는 72%, 비용은 39% 증가했지만 RCA 성능은 개선되지 않았습니다. 이를 통해 문제는 데이터 양이 아니라 **장애 후보를 생성하는 탐색 단계의 신호 부족**에 있음을 확인했습니다.

채널별로 역추적한 결과, 해당 장애는 HTTP 오류가 아닌 지연 형태로 발생해 에러 Trace 검색으로 탐지되지 않았고, 23초 동안 발생한 장애는 5분 단위 Metric 샘플링 사이에서 누락되었으며, Log 역시 유의미한 이상 신호가 부족했습니다. 즉 LLM이 잘못된 Window를 선택한 것이 아니라, **관측 가능한 신호가 부족해 올바른 장애 후보가 탐색 입력에 포함되지 않은 구조적 문제**였습니다.

이에 따라 개선 방향을 단순 데이터 확장이 아닌 **관측 신호 확보 → 장애 후보 생성 → 조사 범위 결정 → 원인 추론** 과정의 개선으로 재정의했습니다. 지연 기반 Trace 탐색, 단기 장애 보존 집계, 복수 Incident 후보 유지, Window 종료 보정 등 각 변경 사항을 독립 변수로 분리하고 단계별 실험을 통해 효과를 검증할 수 있도록 설계했습니다.


RCA 에이전트 검증 과정에서 **장애 구간이 존재함에도 원인을 도출하지 못하는 사례**가
발생했습니다.

분석 결과, 전체 스윕 Window(**04:50~05:50**)에는 장애 주입 구간(**05:22:01~05:22:38**)이
포함되어 있었지만, 이후 비용 최적화를 위해 생성한 좁은 조사 Window가 **05:22:00**에서
종료되면서 **장애 발생 1초 직전에서 핵심 신호가 누락**되는 상황을 확인했습니다.

```
스윕 Window   04:50:09 ─────────────────────────────────── 05:50:09
좁힌 Window   ···· 04:57:00 ━━━━━━━━━━━━━ 05:22:00 ┊
주입                                        05:22:01 ~ 05:22:38
                                            ↑ 1초 차이로 잘렸다
```

처음에는 **조사 범위를 확대하면 해결할 수 있는 문제**로 판단했습니다. 그러나 별도 문항에서
탐색이 조사 Window를 **2.26배**로 잡은 실행과 짧게 잡은 실행을 대조해 보니,
**Context가 72% · 비용이 39% 증가했는데 점수는 오르지 않았습니다.** 증가분을 채널별로
분해하니 거의 전부 메트릭이었고 같은 창의 로그는 16줄에 불과해, **범위 확대의 비용이
정보량이 아니라 적재 방식에서 나온다**는 것이 드러났습니다. 즉 단순히 더 많은 데이터를
전달하는 방향은 **효과가 확인되지 않은 채 비용만 늘리는** 선택이었습니다.

그리고 창을 좁힌 판단 자체는 **입력에 비추면 합리적이었습니다.** 그 구간을 가리키는 신호가
탐색 입력에 거의 도착하지 않았기 때문입니다.

| 채널 | 주입 구간(05:22)에서 | 원인 |
|---|---|---|
| Tempo `{status=error}` | **0건** | 200 성공 + 지연이라 에러로 안 걸린다 |
| `mongodb_up` (step 5m) | **샘플 없음** | 05:20:09 = 1, 05:25:09 = 1 — 23초가 격자 사이로 빠졌다 |
| Loki ERROR/WARN | **1** | 바로 옆 05:05 버킷이 **54** |

**"좁게 봐서 놓쳤다"가 아니라 "볼 게 없어서 좁혔다"** 입니다.

이후 조사 범위를 무작정 확대하는 대신, **제한된 범위 안에서도 장애 후보를 놓치지 않도록
후보 탐색 과정과 관측 신호 활용 구조를 개선**하는 방향으로 접근을 변경했습니다. 이를 위해
변경 요소를 분리해 검증 가능한 구조를 설계하고, RCA 성능 저하 원인이 모델이나 프롬프트가
아닌 **입력 신호 확보 과정**에 있는지 단계적으로 확인하는 방향으로 개선 우선순위를
재정의했습니다.

- **시작은 건드리지 않는다.** 실패가 전부 끝에서 났으므로 시작까지 넓히면 근거 없는 비용이다
- **파서는 이미 같은 원칙을 쓴다** — `clamp()`가 상한 초과 창을 **끝을 남기고 앞을 자르며**, 주석의 이유가 *"장애는 대개 창의 끝(최근)에 가깝다"* 다. **그 원칙이 좁히기 단계에만 없었다**

#### ⑤ 에이전트가 "안 풀린다"고 말하는데 아무 일도 안 일어난다 — B-20 · B-23

| | |
|---|---|
| **어디를** | 탐색 출력 구조(`TriagePlan`) 와 탐색 후 단계 |
| **왜** | **2b 리포트가 스스로 적었다** — *"'앱 버벅임'을 Mongo 다운만으로는 설명할 수 없음"*, 3순위로 *"헬스체크 30초 블로킹이 유력하나 **직접 계측값 없음**"*. **불일치를 감지했는데 다시 찾을 경로가 없다** — 창은 확정됐고 수집은 끝났다 |
| **어떻게** | **B-20** 시간 근접 신호를 `Incident[]`로 묶어 **복수 유지**하고 안 고른 것은 `dismissed[]`로 남긴다 · **B-23** 고른 Incident가 질문의 증상과 맞는지 대조하고 **불일치면 `dismissed`의 다음 후보로** |
| 비용 | B-23은 컨텍스트 수백 자 |

**⑤가 ④보다 근본적입니다.** ④는 놓칠 확률을 줄이는 가드레일이고, ⑤는 **틀렸다는 것을 알았을 때
되돌아가는 경로**를 만드는 것입니다. 지금은 그 판단이 리포트에 적히고 끝납니다.

**신호 도달은 미리 확인했습니다** — 지연 기준 쿼리
(`{ resource.service.name = "chat-service" && duration > 8s }`)로 정답 트레이스가 그대로
검색되고, 15초 해상도로 재조회하면 05:22:37 스크레이프가 **0으로 또렷**합니다.
*"이 신호가 실제로 도달하는가"* 를 확인하지 않은 채 세운 인과 예측이 이전 회차에서 연속
반증됐기 때문에, 이번에는 **처방마다 도달 여부를 먼저 실측**했습니다.

**검증 설계 — 한 번에 하나만 바꾼다**

```
B-17 단독  →  B-18 단독  →  둘 다   →  (안 풀리면) B-27  →  (그래도 안 풀리면) B-20·B-23
```

- **채점 불가가 풀리는 지점이 곧 병목의 위치**입니다
- **B-27을 먼저 넣지 않습니다** — ①②로 신호가 보이면 **창도 따라올 수 있고**(창은 보이는 이상을
  기준으로 정해진다), 그러면 꼬리 여유는 불필요한 비용입니다
- **B-20도 이 측정에 넣지 않습니다** — 1층만으로 풀리면 기여도가 섞입니다
- **반증 조건**: 후보에는 떴는데 창이 여전히 안 덮이면 병목은 신호 공급이 아니라 **좁히기 판단**이고,
  그때 B-27이 필요하다는 증거가 됩니다. B-27로도 안 되면 여유를 늘리지 말고 **끝 고정**으로 갑니다

> **현재 상태**: 원인 특정 · 처방 확정 · 도달 검증 · 실험 설계까지 완료.
> **실행과 효과 측정은 회차 3**이며, 그 전까지 주장하는 것은
> *"병목 후보를 넷으로 좁히고 각각을 가려낼 설계를 마쳤다"* 까지입니다.

## 복합 창 — 세 질문이 같은 traceId를 골랐고 점수가 4에서 100까지 갈렸다

### 장애 상황

같은 1시간 창에 **독립된 장애가 셋** 들어갔습니다. 인과관계가 없고 간격만 8분·9분입니다.

| | 주입 | 구간 | 관측 특성 |
|---|---|---|---|
| **CH-1** | MongoDB 다운 **5분 4초** | 11:54:10~11:59:14Z | 재시도 4회 소진 → DLQ 적재 → 복구 후 재처리 성공 |
| **CH-2** | chat-service `scale 0` **9분 30초** | 12:07:25~12:16:55Z | **에러 트레이스가 원리적으로 존재하지 않는다**(실패할 주체가 없다) |
| **CH-3** | MongoDB 다운 **약 23초** | 12:25:42~12:26:0x | 에러 0건 · 재시도 미발동 · **200 성공 + 공백**만 남는다 |

세 문항의 질문 문안은 다릅니다 — *"댓글 알림이 안 왔다"* / *"채팅 알림이 안 온다는 문의가
여러 건"* / *"앱이 잠깐 버벅였다"*.

### 무엇이 일어났나

**세 조사가 전부 같은 traceId를 골랐습니다.**

| 조사 | 좁힌 창 | 고른 traceId | 1순위 | 점수 |
|---|---|---|---|---|
| CH-1 | 11:53:00~12:04:31Z | `6a69ea20…` | MongoDB 다운 → DLQ (**정답**) | **95** |
| CH-2 | 11:52:00~12:21:11Z | `6a69ea20…` | MongoDB 다운 (**CH-1 것**) | **100** |
| CH-3 | 11:52:00~12:22:00Z | `6a69ea20…` | *"MongoDB 중단 11:54:45~11:59:45"* (**CH-1 주입**) | **4** |

**같은 관측 데이터, 같은 traceId인데 점수가 4에서 100까지 갈렸습니다.**
그리고 CH-3가 고른 그 트레이스는 **30분 전 CH-1 채점에서 정답으로 Top-1 선정돼 95점을 받은
바로 그 traceId**입니다.

**CH-2가 100을 받은 이유는 후보를 접지 않았기 때문입니다.**
1순위로 Mongo(CH-1 것)를 세우면서도 2순위에 chat 컨슈머 부재를 **확신도 높음**으로 유지하고,
*"'문의 여러 건'을 설명하는 건 이쪽이 더 큼"* 이라고 **질문 문안과 대조**했습니다.
3순위(Mongo가 프로브 실패를 유발했다는 연쇄 가설)는 **시점 불일치로 자력 반증**했습니다.
원인이 둘인 복합 창을 **근본·확대·증폭으로 계층 분리**한 것이고, 편차 0으로 재현됐습니다.

**CH-3가 4를 받은 이유는 하나로 접었기 때문입니다.**

```
스윕 창    11:29:20 ─────────────────────────────────── 12:29:20   <- 주입을 덮었다
좁힌 창    ···· 11:52:00 ━━━━━━━━━━━━━━━ 12:22:00 ┊
CH-3 주입                                    12:25:42
                                             ↑ 3분 42초 차이로 잘렸다
```

**회차 1·2와 실패 모양이 다릅니다.** 앞선 두 회차는 창 끝이 주입 **1초 앞**이라
*"해상도가 막았다"* 였는데, 이번엔 **스윕이 주입을 확실히 덮었는데 좁히기가 더 센 신호(CH-1)를
골라 버렸습니다.** 즉 *"못 본 것"* 이 아니라 **"보고 버린 것"** 이고,
결함 14(단일 패스가 약신호를 버림)·15(Incident 개념 부재)의 가장 깨끗한 실증입니다.

**그리고 CH-1은 반대 방향의 증거를 냈습니다.** 도착 근거인 `[Kafka] DLQ 알림 재처리 성공`은
**INFO이고 `traceId=NONE`** 이라 두 수집 쿼리 어디에도 안 걸립니다. 채점자가 수집 원본을
직접 검사하니 **`재처리 실패`는 1건 들어왔고 `재처리 성공`은 0건**이었습니다 —
**실패 절반만 받은 상태**입니다. 그런데도 에이전트는 유실을 단정하지 않고
*"최종 발송 도달 여부 미확인 — 데이터 부족"* 으로 3순위에 남겼습니다.
**감점(영향 −5)은 났지만 오판은 하지 않았습니다.**

### 회차 3에서 바꿀 것

| | 변경 | 이 창이 준 근거 |
|---|---|---|
| **B-20** | Incident를 1급 개념으로 — 시간 근접 신호를 `Incident[]`로 묶고 **복수 유지**, 채택하지 않은 것은 `dismissed[]` | **세 질문이 같은 traceId를 골랐다.** 출력이 `(창 1 + 서비스 + traceId 1)`이라 창 안에 장애가 셋이어도 **표현할 방법이 없다** |

**순서가 강제됩니다.**

```
B-20 (Incident 복수 유지)  <-- 나머지 전부의 전제
  +-- B-23 (검증 패스)      불일치 시 넘어갈 "다음"이 있어야 성립. 싸다(수백 자)
  +-- B-22 (Top-2 수집)     2위가 다른 Incident여야 값어치가 있다. 비용 최대 2배
```

**B-20 없이 B-22만 넣으면 같은 Incident를 두 번 가져올 뿐 비용만 2배**가 됩니다 —

**반증 조건**: 여전히 같은 traceId를 고르면 군집 간격이 틀린 것이고, 다른 것을 골랐는데도
CH-3 점수가 안 오르면 병목은 **선정이 아니라 그 뒤 수집·분석**입니다.

## RCA 에이전트의 한계 분석 및 관측 기반 인과 추론 구조 개선

RCA 에이전트 평가 과정에서 장애 원인을 식별하는 것과 장애 발생 과정을 설명하는 것은
별개의 문제라는 것을 확인했습니다.

기존 에이전트는 auth-service 장애라는 1차 원인은 정확히 식별했지만, 실제 사용자 증상인
"댓글 닉네임이 비정상적으로 표시되는 현상"까지 연결하지 못했습니다. 원인은 auth-service
장애였지만, content-service가 사용자 정보를 캐시하고 있으며 TTL 만료 이후 fallback 로직으로
임시 값을 반환하는 구조까지 추적해야 최종 증상을 설명할 수 있었습니다.

이를 통해 분산 시스템 환경의 RCA는 단순 원인 레이블(auth-service 장애)을 출력하는 것이
아니라, **관측 데이터 기반 인과 사슬(원인 → 서비스 영향 → 의존성 변화 → 사용자 증상)** 을
완성해야 한다는 결론을 도출했습니다.

이후 RCA 평가 기준을 변경하여 각 인과 연결 단계마다 Trace·Log·Metric 기반 근거를 요구하도록
개선했습니다. 근거가 없는 연결은 "추정", 관측으로 확인할 수 없는 부분은 "데이터 부족"으로
명시하도록 하여 AI가 존재하지 않는 원인을 생성하는 문제를 방지했습니다.

또한 개선 효과를 정확히 검증하기 위해 탐색 범위 확장, 데이터 수집, 출력 구조 변경을
독립적인 변경군으로 분리하고 하나의 변수만 변경하는 실험 체계를 설계했습니다. 이를 통해
단순히 프롬프트를 개선하는 접근에서 벗어나, RCA 성능 저하 원인이 신호 부족인지, 추론 구조의
문제인지, 표현 방식의 문제인지 분리하여 개선할 수 있는 평가 체계를 구축했습니다.

결과적으로 RCA 에이전트의 목표를 "장애 원인을 맞히는 시스템"에서 **"관측 근거를 기반으로
장애 발생 경로와 영향 범위를 설명하는 시스템"** 으로 재정의했습니다.

### 해결책 — 무엇을 어떻게 바꾸는가

**1. 출력 구조 — 원인 후보 랭킹에 인과 사슬과 성립 조건을 요구합니다.**

기존 리포트 서식은 "원인 후보 랭킹"만 요구했고, 후보 목록이라는 구조에는 원인과 증상을 잇는
과정을 넣을 자리가 없었습니다. 서식의 후보별 근거 항목에 두 줄을 추가합니다.

```markdown
- 인과 사슬: 관측된 단계를 순서대로 이어 쓴다 (A -> B -> C -> 증상).
  화살표마다 근거가 되는 관측을 붙이고, 관측이 없는 연결은 "추정"으로 표시한다.
- 성립 조건: 이 원인이 증상으로 이어지려면 함께 성립해야 했던 조건을 적는다.
  없으면 "없음". 관측으로 확인할 수 없으면 "데이터 부족".
```

이 서식이 강제하는 것은 "auth-service 장애"에서 멈추지 못하게 하는 것입니다.

```
기존:  auth-service 장애

개선:  auth-service 장애
         → content-service 사용자 정보 조회 실패   [근거: Connection refused span]
         → 캐시 미스 요청에서만 원격 조회 발생      [근거: Redis GET 4건 직후 동일 4명 조회]
         → fallback 실행 → 닉네임 비정상 표시      [근거: fallback 로그 원문]
       성립 조건: 장애 지속(11분) > 캐시 TTL(10분)  [근거 없으면 "추정"으로 표시]
```

사슬은 화살표를 가지므로 "auth 다운 → ? → 닉네임 이상"의 물음표가 서식 단계에서 드러나고,
성립 조건 칸이 있으므로 "왜 하필 그 시점부터인가"를 답하지 않고는 리포트가 완성되지 않습니다.

**2. 조사 범위 — 증상이 가리키는 서비스에서 멈추지 않게 합니다.**

리포트에 영향 범위 절을 신설합니다. 장애가 실패인지 지연인지 유실인지, 되돌릴 수 있는지,
어느 요청까지 미치는지에 더해 — **원인 서비스에 의존하는 다른 구성 요소의 상태를 반드시
확인**하고, 정상이라면 무엇이 그 영향을 막고 있는지와 그 조건이 언제까지 유지되는지를
관측으로 답하게 합니다. auth가 죽었는데 content가 멀쩡하다면 "무엇이 버티고 있는가(캐시)"와
"언제까지 버티는가(TTL)"가 곧 다음 장애의 예고이기 때문입니다.

**3. 수집 — 그 판단에 필요한 신호가 실제로 도달하게 합니다.**

서식만 바꿔서는 상류 증상 사례가 풀리지 않습니다 — content가 멀쩡한 이유를 보여주는
트레이스가 컨텍스트에 0바이트로 도착했기 때문입니다. 수집기를 "선정한 트레이스 1건"에서
**조사 창 기준 후보 N건**으로 바꿔, 탐색이 auth로 좁혀도 같은 창의 content 트레이스가
분석 입력에 포함되게 합니다. 해당 신호가 관측 백엔드에 실재함은 직접 쿼리로 확인해
두었습니다(오를 자리 최대 +24점).

**4. 검증 — 한 번에 하나만 바꿔 병목을 확정합니다.**

세 변경을 한 번에 넣으면 점수가 올라도 무엇 때문인지 알 수 없으므로, 단독 적용 순서와
반증 조건을 먼저 정했습니다.

| 순서 | 적용 | 검증 문항 | 기대 | 기대와 다르면 |
|---|---|---|---|---|
| 1 | 출력 구조(사슬·조건)만 | 캐시 만료 사례 | 캐시 조건이 1순위 사슬에 포함, 원인 30 → 40 | 병목은 서식이 아니라 **추론 자체** |
| 2 | 수집(N건)만 | 캐시 히트 사례 | 리포트에 "캐시" 언급 등장, +10~24 | 병목은 신호가 아니라 **지시** → 3 적용 |
| 3 | 영향 범위 절 | 2가 실패했을 때만 | 의존 서비스 상태가 리포트에 등장 | 감점 원인은 양식이 아니라 관측 결손 |

이때 프롬프트에 "캐시", "TTL", "fallback" 같은 정답 어휘는 넣지 않습니다. 특정 장애의 답을
지시문에 심으면 평가 변별력이 사라지므로, "의존하는 구성 요소" · "성립 조건" 수준의
문항 중립적 표현만 사용합니다.

**"분리"는 적용을 미루는 것이 아닙니다.** 최종 구성은 세 변경을 모두 합친 상태이고, 분리되는
것은 비교쌍입니다. 프롬프트는 조사할 때마다 다시 읽는 파일이고 코드는 커밋 단위로 전환되므로,
세 구성(수집만 / 서식만 / 둘 다)은 **같은 날 병행 측정이 가능합니다** — 서로 다른 문항을
재기 때문에 순차 대기도 없습니다. 단독 효과를 각각 확정한 뒤 마지막에 결합 구성을 한 번 더
측정해 **서로 간섭하지 않는지**까지 확인하고, 그것이 결합 적용의 근거가 됩니다.

## 개선 지표 정의 — 상수인 줄 알았던 값이 하루에 진동했다

### 상황

| | |
|---|---|
| 목적 | 개선 효과를 **토큰과 비용**으로 재려면 지표에서 노이즈를 먼저 분리해야 한다 |
| 문제 | API 응답의 총 input 토큰에 **CLI 고정 오버헤드**(시스템 프롬프트 + 툴 정의)가 섞여 있다 |
| 첫 접근 | 오버헤드를 **한 번 측정해 상수로 차감**한다 |
| 제약 | 구독 CLI 경로에는 `count_tokens` API 키가 없어 **보내기 전 예측이 불가능**하다 |

### 무엇이 일어났나

상수로 차감하려던 전제가 실측으로 깨졌습니다.

```
07-26~27   약 22,000
07-28         26,626
07-29         21,247   (CLI 버전 동일)
07-29         26,576   9시간 반 뒤 복귀
```

**같은 CLI 버전에서 하루 만에 20% 감소했다가 되돌아왔고**, 감소분 대부분이 툴 정의
(23,201 → 10,762)였습니다. 클라이언트가 안 바뀌었으므로 원인은 **서버가 내려주는 쪽**이고,
단조 드리프트가 아니라 **진동**입니다. 즉 **문서에 적힌 상수를 빼는 방식은 성립하지 않고,
과거 회차의 소급 추정도 불가능**합니다.

상수 차감을 폐기하고 **조사마다 1자 프롬프트 프로브로 그 회차의 오버헤드를 직접 측정**하도록
바꿨습니다. 앱 내장 프로브와 별도 셸의 독립 프로브가 **Δ27(0.1%)** 로 일치해 서로를 확인했고,
남는 오차는 프로브 자체의 **±1.5%** 입니다. 문자 수 기반 보조 추정식도 함께 유지하는데,
이 식이 **매번 그날 프로브 값을 지지한다**는 것이 상수 폐기 결정의 독립 검증이 됐습니다.

**지표가 안정되자 비용 구조를 분해할 수 있었습니다.** 같은 문항의 두 실행에서 조회 창
길이만 2.26배 달라진 자연 실험이 만들어졌는데, **Context가 72% · 비용이 39% 늘고 점수는
오르지 않았습니다.** 증가분을 채널별로 분해하니 —

| 채널 | 크기 |
|---|---|
| **메트릭** | **164,988B** (8종 × 98포인트 × 다중 시리즈) |
| 트레이스 | 18,908B |
| 로그 | **16줄** |

**창을 넓힐 때 선형으로 부는 것은 메트릭 하나뿐**이고, 그마저 **전 구간 상수인 시리즈가
25개**였습니다. 창 확대의 한계비용이 정보량이 아니라 **적재 방식**에서 나온다는 뜻입니다.

한편 계측 자체에도 결함이 나왔습니다. 프로브가 **처음으로 값을 못 낸 회차**가 발생했는데,
`-1`을 내는 경로가 셋(설정 off / 프로브 예외 / 프로브가 다턴으로 감)인데 리포트가 **셋을
구별하지 않아 원인이 미확정으로 남았습니다.** 그 회차 토큰은 실측에서 **추정으로 강등**했습니다.

### 회차 3에서 바꿀 것

| | 변경 | 방법 | 비용 |
|---|---|---|---|

요약은 **min/max와 변화 구간을 보존하는 형태**로만 합니다.

# 1. 회차 2 결과 — 점수 차는 능력 차가 아니다

입력 모델을 traceId에서 **자연어 한 줄**로 바꾼 첫 회차다. 루브릭 v3(6항목)·앵커 v2로 채점했다.

| 문항 | 점수 | 정답 신호가 어디 있나 | 도구가 막은 항목 |
|---|---:|---|---|
| AP-3 | 100 / 95 (N=2) | 예외 원문이 span error 태그와 Loki 헤더 줄에 둘 다 | 탐색 B (메트릭으로 자력 대체) |

| AU-2 | 76 | auth는 메트릭 소멸, content는 정상 트레이스의 span 부재 | 원인·근거·영향·조치 |
| AP-2 | 53 (N=2) | 로그의 스택트레이스에만 | 근거·원인 |
| CH-3 | 4 (N=2) | 200 성공 + 22초 공백 — 지연 채널에만 | 탐색 전체 |

**막힌 항목 수와 점수가 대체로 정렬된다** — 0개(100·90) → 1개(88) → 2개 이상(76·53) → 전체(4).
표본이 적어 상관을 주장하지 않고 **회차 3의 반증 대상**으로 삼는다.

**못 받은 신호는 전부 채점자가 직접 쿼리해 존재를 확인했다.** 회차 1의 델타 예측이 연속
반증된 원인이 *"이 신호가 실제로 도달하는가"* 를 끝까지 따라가지 않은 것이었다.

**창이 아니라 해상도가 막았다.** 스윕 창(04:50~05:50)은 주입을 포함했고, 15초 해상도로

  앵커에도 루브릭에도 없는 범주였다. **v0.1은 20~25초 장애를 못 찾는다. 그것이 이 4점의 내용이다.**

  그 열이 아예 없다. 주입이 짧을수록 걸리는데 **실운영의 장애는 대개 짧다.**

| 6 | 탐색이 근거를 대고 창을 좁혔는데 분석이 *"조회 창이 질문과 불일치"*(AP-2) · *"나머지 약 49분 미조회"*(AP-3, 데이터 부족 1순위)라고 쓴다. `Triage.reason`·`evidence`가 리포트에만 있고 모델에는 안 간다 |
| 7 | AU-2에서는 **대상 서비스까지 틀렸다** — `application="content-service"`인데 로그인은 auth 소관. 에이전트가 매번 교정 쿼리를 낸다 |
| 9 | Tempo `/api/search`가 그대로 내려주는 값(우리 파싱 문제 아님). 같은 트레이스를 `/api/traces/{id}`로 받으면 멀쩡하다. **후보 랭킹에 `durationMs`를 쓰면 이 행이 항상 1위** |

| 22 | 정규식이 접두 `(?:지난\|최근\|past\|last)?` 와 접미 `(?:전\|ago)?` 를 **둘 다 optional**로 둬서 **숫자+단위만으로 매치**된다. `"14시 20분"`은 `14`+`시`가 단위 목록에 없어 실패하고 엔진이 전진해 **`20`+`분`을 잡는다.** `"05:22쯤"`은 무매치라 fallback 24h로 가는데 **더 안전한 쪽이 우연히 나온 경우**다 — 콜론 앞뒤에 단위 글자가 없었을 뿐이다 |

## 2.2 능력 결함 — 도구를 다 고쳐도 남는 것

| | 무엇 | 확정 근거 |
|---|---|---|
| **가** | **장애 서비스 밖을 스스로 보지 않는다** | AU-2("로그인" = 상류) → auth 하나만 조사 / AU-4("작성자 이름" = 하류) → content + auth 둘 다. **증상 문안이 가리키는 쪽만 본다** |
| **나** | **관측을 원인 사슬에 배치하지 못한다** | AU-4 회차 1·2가 같은 자리에서 같은 실패. 정답 관측을 써 놓고 확신도 낮은 곁가지에 뒀다 |

**나가 더 무겁다 — 회차 1의 진단이 반증됐다.** AU-4의 1) 원인은 두 회차 모두 30이고 부분점
문언까지 같다. 회차 1은 이 감점을 *"간결본 누락 — 분량이 늘면 오른다"* 로 진단했는데
**분석 out이 2,980 → 7,982(2.7배)가 됐는데도 그대로였다. 분량 가설은 죽었다.**

그리고 정답 관측을 **이미 갖고 있었다** — `Redis GET ×4`(474558/475820/476303/476689 us) 직후
0.7ms 뒤 `http get auth-service/api/external/users?userIds=1,3,7,9`, **정확히 그 4명**.
리포트에 *"캐시 미스분만 원격 조회하는 read-through 패턴"* 이라고 썼다.
다만 **후보 3(확신도 낮음)** 아래 뒀고 후보 1은 auth 부재만으로 구성했다.

**빠진 것은 데이터가 아니라 배치다.**

### B-18. 스윕 메트릭이 짧은 딥을 보존하도록 (결함 13)

|---|---|---|---|
| CH-3 회차 1 | 05:20:00 | 05:22:01 | 2분 1초 |
| CH-3 회차 2 | 05:22:00 | 05:22:01 | **1초** |
| CH-3 2b | 12:22:00 | 12:25:42 | 3분 42초 |

**LLM은 지시대로 했다.** 회차 2의 선정 이유 원문이 *"다섯 신호가 같은 10분 구간에 겹치고
**05:20에 일제히 정상 복귀**하므로 앞뒤 여유를 둔 04:57~05:22"* 다 — **이상이 끝난 지점을
기준으로** 여유를 뒀다. 문제는 그 *"끝났다"* 는 판단이 **5분 격자에서 나왔다**는 것이다.

| 안 | 방법 | 회차 2 창 | |
|---|---|---|---|
| **가** | **꼬리 여유 강제** — `end = min(스윕 끝, LLM end + survey.step × 2)` | 25분 → **35분 (1.4배)** | **권장** — 세 회차 전부 덮인다 · 시작은 그대로 |
| 나 | 끝 고정 — `end = 스윕 창 끝` | 25분 → 53분 (2.1배) | 뭉툭하다. 가가 실패했을 때의 다음 단계 |
| 다 | 프롬프트에 정량 지시 | 0 | **준수 보장이 없다.** 그리고 CH-3는 근거를 요구해도 *"05:20에 복귀"* 를 댔을 것이다 — 그 근거 자체가 5분 해상도라는 게 문제 |

**여유 수치를 CH-3에 맞춰 고르지 않는다** — 스윕 격자가 5분이면 *"이상이 끝났다"* 는 판단의
해상도가 **±5분**이고, 그 판단으로 창을 닫으려면 **여유가 해상도보다 커야** 한다.
그래서 `survey.step × 2`로 유도하고 step이 바뀌면 함께 움직이게 둔다.
**B-18로 딥이 보존되면 이 해상도 논거가 약해지므로 여유를 재검토한다** — 두 항목이 연동된다.

**파서는 이미 같은 원칙을 쓴다.** `clamp()`가 상한 초과 창을 **끝을 남기고 앞을 자르며**,
주석의 이유가 *"장애는 대개 창의 끝(최근)에 가깝고, 앞을 남기면 정작 봐야 할 구간이 잘려나간다"* 다.
**그 원칙이 (1)에는 있고 (3)에는 없었다** — 그 비대칭이 이 결함이다.

**B-27을 먼저 넣지 않는다.** B-17·B-18로 이상이 보이면 **창도 따라올 수 있다**(창은 보이는 이상을
기준으로 정해진다). 그때는 꼬리 여유가 불필요한 비용이므로, **1층 델타를 잰 뒤 반증 조건이
성립했을 때만** 넣는다. 순서와 반증 조건은 §CH-3 절과 §7.

> **B-23과 역할이 다르다.** B-27은 **놓칠 확률을 줄이는 가드레일**이고, B-23은 **틀렸다는 것을
> 알았을 때 되돌아가는 경로**다. 후자가 더 근본적이다 — CH-3 2b 리포트가 이미
> *"'앱 버벅임'을 Mongo 다운만으로는 설명할 수 없음"* 이라고 스스로 적었는데
> **다시 찾을 수단이 없었다.**

### B-26. 자연어 시간창 파서를 다시 쓴다 (결함 22 · 신규)

`TimeExpressionParser`가 **애매한 입력에서 fallback으로 가지 않고 좁은 틀린 창을 확신 있게 만든다.**
그리고 그 오독은 **뒤에서 복구되지 않는다** — `TriagePlan.readWindow()`가 좁힌 창을 스윕 창
**안으로만** clamp하므로 LLM에게는 넓히는 경로가 없다. 창 밖 데이터는 그 조사에서 존재하지
않는 것과 같다(CH-3가 같은 구조로 4점).

**정규식이라서가 아니라 구조 셋이 문제다.**

| 무엇 | 코드 | 증상 |
|---|---|---|
| 첫 매치를 취한다 | `matcher.find()` | `"14시 20분쯤"` → **최근 20분** |
| 부분 문자열 검사 | `containsAny(text, "새벽")` | `"어제 새벽"` → **오늘** 새벽 (하루 밀림) |
| 후보를 결합하지 않는다 | 배타적 `if` 7개 | 날짜·시간대·시각이 동시에 있어도 하나만 쓴다 |

**요구사항을 다시 보면 규칙으로 충분하다** — (1)이 낼 것은 정확한 시각이 아니라
**장애를 반드시 포함하는 가능한 한 좁은 상한**이다(정밀은 (3)이 맡는다).
`"14시 20분쯤"` → `14:20 ± 30분`이면 되고 그건 규칙으로 확실히 된다.
단 "확신 없으면 무조건 넓게"는 답이 아니다 — 창 ×2.26에 컨텍스트 +72.2% · 비용 +38.7% ·
점수 불변이 이미 실측이다(결함 17). **절대 시각을 읽어 ±padding으로 좁히는 데 실익이 있다.**

| 안 | 방법 | 비용 | |
|---|---|---|---|
| **가** | **3층 파서 재작성** — 상대성 표지 필수화 + 절대 시각 패턴 + 분기 재정렬 | **0** | **권장** — 결정적, 토큰 0, 도메인 결정(`밤` = 18:00~06:00)이 코드에 남는다 |
| 나 | Duckling 사이드카 | 컨테이너 1 | 한국어 규칙은 있으나 `밤` 정의를 못 넣고 `confidence`·`expression`이 안 나온다. 한국어 커버리지·라이선스는 직접 확인 필요 |
| 다 | (1)에 LLM 1회 추가 | **+21,247 tok / 호출** · 초 단위 | 창이 회차마다 흔들려 **§8.1 편차의 귀속이 깨진다.** 그리고 **시간 산술은 LLM이 약한 종류** — CH-3에서 경계를 **1초** 틀린 실측이 이미 있다 |

**3층 구조 — 후보를 전부 뽑고, 결합하고, 우선순위로 가른다**

| 층 | 하는 일 |
|---|---|
| **L1 정규화** | 수사(`한`·`두`·`반`) · 오전/오후 · 조사(`쯤`·`정도`·`여`) 제거 |
| **L2 후보 전량 추출** | `ABS_DATE` · `ABS_TIME` · `DATE_WORD` · `DAYPART` · `RELATIVE` · `RANGE`. **첫 매치를 취하지 않는다** |
| **L3 결합** | 구체적인 것이 이긴다. 충돌하면 **넓은 쪽**을 택하고 기록한다. **미래는 `now`로 자른다** |

`RELATIVE`에 **상대 표지를 필수화**하는 것이 핵심이다 — 접두 `지난·최근·last·past` 또는
접미 `전·동안·안에·ago` 가 없으면 후보로 세지 않는다. 그러면 `"14시 20분"`의 `20분`이
`RELATIVE` 후보가 **아예 되지 않고** `ABS_TIME` 하나만 남는다.

| 결합 | 나오는 창 | 확신 |
|---|---|---|
| `RANGE` | A ~ B | EXACT |
| `DATE_WORD` + `DAYPART` | 그 날짜의 그 시간대 | EXACT ← **지금 버그가 여기** |
| `DATE_WORD`/`ABS_DATE` + `ABS_TIME` | 그 시점 ± padding | APPROX |
| `ABS_TIME` 단독 | **가장 가까운 과거**의 그 시각 ± padding | APPROX |
| `DAYPART` 단독 | 오늘의 그 시간대 (미래면 어제) | EXACT |
| `RELATIVE` | `now − N ~ now` | EXACT |
| 없음 | 기본 24시간 | **FALLBACK** |

**`Resolved`에 `confidence`를 값으로 남긴다.** `expression`은 이미 컨텍스트에 실려 가므로
(`시간창 해석 근거: …`) 확신도까지 실으면 LLM ①이 *"이 창은 추정이다"* 를 알고 좁히기를
보수적으로 한다. 채점에서는 **`FALLBACK`으로 떨어진 회차를 분리 집계**할 수 있다 —
지금은 그 구별이 문자열 매칭이라 집계가 안 된다.

**입력 검증도 이 항목에 포함한다** — 같은 메서드의 같은 성질(조용한 실패)이고, **회차 3의
재조사 작업이 여기에 정면으로 걸린다.**

| 지금 | 바꿀 것 |
|---|---|
| `from`만 주면 `from != null && to != null`에 걸려 **조용히 무시**되고 질문 파싱으로 떨어진다 | **거부하고 사유를 반환한다** |
| `from > to`는 `clamp()`가 음수 span을 상한과만 비교해 **그대로 통과**시킨다 | 거부. `TimeWindow`에 검증이 없다 |
| 미래 `end` | `now`로 자른다 |

**과거 데이터 재조사(단계 1-b·2)가 `from`/`to` 경로를 타기 때문이다.** 문안이 `최근 1시간 안에`
이므로 그대로 돌리면 **오늘 창**을 조사한다. `to`를 빼먹으면 리포트에 `상대 표현 '최근 1시간'`
이라고 찍히고 오염을 눈치채지 못한다 — **결함 22가 문항 문안이 아니라 채점자의 호출에서
먼저 터질 자리다**(CH-3 3회 + B-20 델타 2회 = 최소 5회 반복).

**쪼개지 않는다.** 3층 파서·`confidence`·입력 검증을 **한 덩어리로** 넣는다. 게이트가 통과하면
전체의 델타 기여가 0이므로 **쪼개서 얻을 귀속이 없고**, 나눠 넣으면 파서 상태가 회차 안에서
두 가지가 되어 재조사 5회의 조건이 서로 달라진다.

**게이트 — 넣기 전에 불변을 증명한다.** 박제 문안 12개가 전부 `최근 N시간`이라 `RELATIVE`
경로 하나에 걸린다. **12개의 창이 바뀌지 않음을 회귀 테스트로 고정한 뒤** 넣는다.
하나라도 바뀌면 회차 2와의 비교가 깨지므로 **그 회차에 넣지 않는다.**
이 게이트가 통과하면 B-26은 회차 3 델타에 기여가 **0임이 증명된 변경**이 되어 다른 B 항목과
같은 회차에 넣어도 귀속이 흐려지지 않는다.

**순서상 재조사보다 먼저 넣는다** — 재조사가 검증 없는 `from`/`to` 경로를 타므로 B-26이
뒤에 오면 안전장치 없이 5회를 돌리는 셈이 된다.

**반증 조건**: 파서를 고치고 **시각 표현 문안**으로 재실행했을 때 탐색 점수가 오르지 않으면
병목은 (1)이 아니라 (3)의 좁히기다. CH-3가 그 방향을 지지한다 — 그쪽은 **파서가 창을 정확히
덮었는데** LLM이 1초 차이로 잘랐다. 그렇다면 (1)에 LLM을 넣어도 같은 실패가 난다.

> **문안 변경은 이 항목이 아니다.** 시각 표현 문안(`"14시 20분쯤"` 류) 도입은 **입력 모델
> 변경**이라 §3.4상 대조군으로 분리해야 하고, 파서 수정과 같은 회차에 넣으면 둘 중 무엇이
> 점수를 움직였는지 못 가린다. → §7 *이번 회차에 넣지 않는 것*.

### B-24. 오버헤드 프로브 — 실패 사유 구별 + 1회 재시도 (결함 16 · 신규)

`ClaudeCliLlmClient.overheadTokens()`(`ClaudeCliLlmClient.java:70`)가 `-1`을 내는 경로가 셋인데
리포트는 **셋 다 같은 문구**를 찍는다. AP-3 회차 2 실행 2의 실패 원인이 **미확정으로 남았다.**

| 경로 | 지금 남는 흔적 |
|---|---|
| ㄱ `RCA_CLI_PROBE_OVERHEAD=false` | 기동 로그 `overhead probe: off` |
| ㄴ 프로브 예외 | 로그 `오버헤드 프로브 실패 —` |
| ㄷ `probe.numTurns() > 1` | 로그 `오버헤드 프로브가 N턴을 돌았다` |

**셋 다 JVM 로그에만 남고 리포트에는 안 간다** — 조사 산출물만 보관하는 회차에서는 복구 불가다.

1. `-1` 대신 **사유를 함께 반환**해 리포트 `coverage`에 찍는다 (`off` / `error` / `multi-turn`)
2. ㄴ·ㄷ이면 **1회 재시도**한다. 1자 프롬프트라 재시도 비용이 무시할 만하다
3. ㄷ이 반복되면 **프로브 설계 자체가 문항이 된다** — AP-3 실행 1이 *"레포 cwd 프로브는 3턴까지
   가기도 했다"* 를 이미 관측했다. 격리 샌드박스에서도 나면 `--max-turns 1` 같은 강제가 필요하다

점수와 무관한 계측 항목이지만, 이 값이 없으면 그 회차 토큰이 **실측에서 추정으로 강등**되고
**`C`가 진동하는 이상 소급 보정이 불가능하다**(결함 8).

### B-20. Incident Clustering — 시간 근접 이상 신호를 묶고 복수로 유지 (최우선)

> **문서 둘로 갈라 둔다.** 여기에는 **요지와 변경군 위치만** 둔다.
>

- **병합은 `traceId`·`serviceStats` 공유만.** 토폴로지를 병합 근거로 쓰면 AU-4의 정답 구조를

- **임계값은 시간 gap 하나뿐**(60초 근방). 크기 임계값을 두지 않는다 — CH-3의 Loki 신호는 **1건**이다

- **채점 영향**: 3) 탐색 15의 S를 "무엇을 골랐나"에서 **"무엇들을 세웠나"** 로 읽을 수 있게 된다.

- **선행 필수**: B-17 없이는 CH-3 Incident가 생기지 않는다(지연 트레이스가 스윕에 안 들어온다).

- **후속**: Loki는 스윕 집계라 **지문이 없다** → `B-29`(로그 예외 클래스를 라벨로) ·

### B-28. 트레이스에서 호출 그래프를 뽑는다 (서비스·인프라 의존)

> **문서 둘로 갈라 둔다.** 여기에는 요지만 둔다.

`TraceSpans`가 `parentSpanId`를 읽지 않아 **트레이스를 갖고도 누가 누구를 불렀는지 모른다.**
그래서 에이전트가 인과를 시각으로 추측하고, 의존 관계는 **프롬프트에 복붙된 한 문장**이 전부다.

- **AU-4에서 감점으로 실현됐다** — Redis GET 4건 직후 0.7ms 뒤 auth 호출, 정확히 그 4명을
  **맞췄는데** 근거가 정황이라 확신도 낮음(후보 3)에 뒀다. 원인 −10
- **IN-1은 수단이 없다** — 프롬프트 문장에 Redis·Mongo·MySQL이 아예 없어
  *"세 서비스가 Redis를 공유한다"* 를 알 방법이 없다

**데이터에는 이미 있다** (저장된 트레이스 실측): `spanId`·`parentSpanId`(base64) ·
`db.system=redis` · `jdbc.datasource.driver/.name` · `messaging.system=kafka` +
토픽·오프셋·파티션·`messaging.operation`. MongoDB는 `db.system=mongodb`(재확인 필요).

- **태그 이름은 Brave가 아니라 Micrometer 계측이 정한다**(ADR-001대로 OTel Agent를 안 쓴다).
  **계약이 아니라 관례**이므로 fallback 체인을 두고 **못 알아본 엣지는 버리지 않고 미분류로** 남긴다
- **거르지 말고 접는다** — `query`·`result-set`·`generated-keys` 15개가 같은 엣지라
  **23 span이 1줄**이 된다. blocklist가 없어 새 계측이 붙어도 안 깨지고, 엣지에 `error`·`events`를
  붙이면 **그래프 한 줄이 AP-3의 정답 지문을 담는다**
- **함정 둘 (실측)**: `peer.service=content` 는 서비스가 아니라 **MySQL DB 이름**이라
  순진하게 매칭하면 자기 참조 엣지가 생긴다(288건) · 필터 체인은 span 2개뿐이고 12개 필터는
  `events` 배열이다(span 이름만 grep하면 오독한다)
- **정적 토폴로지 맵은 만들지 않는다** — 코드에 박으면 IN-1의 정답을 심는 것이다.
  관측에서 유도하는 것만 한다
- **IN-1은 `B-9` 선행** — 한 트레이스는 그 요청 경로만 보여준다. N건에서 엣지를 누적해야
  공유 의존이 드러난다. **AU-4는 한 트레이스로 된다**
- **프롬프트의 토폴로지 문장을 같은 회차에 제거한다** — 안 빼면 그래프 덕인지 문장 덕인지 못 가린다
- **검증은 저장된 원본으로 지금 가능하다**(주입 불필요). 결과를 테스트 픽스처로 고정한다

### B-21. 질문 기반 Incident 재랭킹

증상 어휘("버벅"·"안 됨"·"지연"·"유실"·"느림")를 Incident 성격과 매칭해 순위를 바꾼다.

- **CH-2가 직접 증거다.** 질문이 *"문의가 여러 건"* 인데 고른 Incident A는 **댓글 1건이 5분 늦게
  도착하고 끝난** 사건이다. 어휘 매칭만 있었어도 순위가 뒤집힌다.
- **블라인드 위험 — 사전을 코드에 박지 않는다.** `"유실" → Kafka` 같은 매핑 테이블은
  **문항 정답을 도구에 심는 것**이고 [CLAUDE.md 블라인드 규정](../../CLAUDE.md) 위반이다.
  **매칭은 LLM에 시키고**(질문 + Incident 요약만 주고 순위를 매기게) 코드는 어휘를 모른다.
- **변경군 경계**: Incident 구조를 만드는 것은 **B**, 순위를 매기는 지시는 **C**(`triage-prompt.md`)다.

### B-22. Top-2 조건부 심층 수집 — 1위 확신도가 낮으면 2위도 함께

- **CH-2에서 이것 하나면 정답 트레이스가 들어왔다.**
- **비용을 가볍게 보면 안 된다.** 회차 2 실측이 컨텍스트 263,787자 · $2.35다. 무조건 2배면 **$4.7**.
  **반드시 조건부여야 한다** — 탐색이 `confidence`를 내고 임계 미만일 때만 2위를 붙인다.
- **1위와 2위가 같은 Incident면 붙이지 않는다.** CH-2의 후보 3건이 전부 A였다 — 그 상태로 Top-2를
  켜면 **같은 장애를 두 번 가져올 뿐 비용만 2배**다. **B-20 없이 B-22만 넣으면 이 실패가 난다.**

### B-23. 탐색 후 검증 패스 — 고른 Incident가 질문의 증상과 맞는가

탐색 계획 확정 후 **질문 + 선택 Incident 요약**만 주고 일치 여부를 한 번 더 묻는다. 불일치면
다음 후보로 넘어간다.

- **싸다** — 컨텍스트 수백 자. **B-22를 켜기 전에 이것부터 넣는 것이 비용 대비 효율이 높다.**
- **CH-2에서 걸렸을 것이다** — *"문의가 여러 건"* ↔ *"댓글 1건, 5분 뒤 도착 완료"* 는 한 번만
  대조하면 안 맞는다.
- **B-20의 `dismissed[]`가 있어야 "다음 후보"가 존재한다.** 단독으로는 반쪽이다.

> **CH-3 2b가 이 항목의 가장 강한 근거를 만들었다 — 에이전트가 이미 이 검증을 수동으로 했다.**
> 리포트가 스스로 *"사용자 요청 경로는 정상이었음 … → **'앱 버벅임'을 Mongo 다운만으로는
> 설명할 수 없음**"* 이라고 적고, 3순위를 *"헬스체크 30초 블로킹 — 유력 후보 메커니즘이나
> **직접 계측값 없음**"* 으로 세웠다.
> **즉 "받은 증거로 이 질문이 안 풀린다"를 정확히 진단했는데, 다른 구간을 다시 찾을 경로가 없다.**
> 창은 이미 확정됐고 수집은 끝난 뒤였다. **판단 능력이 아니라 제어 흐름이 없는 것**이므로,
> B-23은 새 능력을 넣는 게 아니라 **이미 하는 판단을 되돌아갈 수 있는 위치로 옮기는 것**이다.

### C-2. 부재 신호를 근거로 쓰라는 지시 — 넣지 않는다

에이전트가 **이미 하고 있다.** AU-2에서 *"`up`이 `0`으로 기록된 샘플은 한 건도 없습니다 —

**지시가 필요 없는 것을 지시하면 델타만 흐려진다.**

### C-3. 원인을 레이블이 아니라 사슬로 쓰게 한다 (능력 결함 나)

`## 2. 후보별 근거`의 항목 목록에 두 줄 추가.

```markdown
- 인과 사슬: 관측된 단계를 순서대로 이어 쓴다 (A -> B -> C -> 증상).
  화살표마다 근거가 되는 관측을 붙이고, 관측이 없는 연결은 "추정"으로 표시한다.
- 성립 조건: 이 원인이 증상으로 이어지려면 함께 성립해야 했던 조건을 적는다.
  없으면 "없음". 관측으로 확인할 수 없으면 "데이터 부족".
```

| 요소 | 이유 |
|---|---|
| 성립 조건 | AU-4 앵커 40의 **"두 조건의 결합"** 을 정면으로 겨눈다. 특정 답을 암시하지 않는다 |
| 화살표마다 근거 관측 | 관측 없는 비약을 서식 단계에서 드러낸다 |
| 없으면 없음 / 확인 못 하면 데이터 부족 | 날조 방어 |
| 트래픽 운에 안 걸린다 | 단일 트레이스의 span 순서만으로 성립한다 |

**일반성**: *"Redis GET 다음의 원격 호출은 캐시 미스의 흔적"* 은 AU-4 전용 지식이 아니라
**span 시퀀스에서 의도를 읽는 능력**이다. 같은 모양이 AP-1·CH-3·AU-3·IN-2에도 있다.

**C-1과 C-3은 성격이 다르다.** C-1은 *조사 범위*를 넓히는 지시라 신호 공급에 의존하고,
C-3은 *서술 구조*를 바꾸는 지시라 이미 있는 관측만으로 효과가 난다.
**그래서 한 프롬프트에 같이 넣지 않는다.**

### A-0. JWT 서명 예외 포착 + 사유별 로그 (결함 20) — 코드 완료 2026-07-30 · 배포·검증 미완

> **전문은 [jwt-exception-handling.md](jwt-exception-handling.md)**(서술) ·
> [jwt-exception-handling-spec.md](jwt-exception-handling-spec.md)(스펙).
>
> **정정**: 이 항목이 한동안 `선적용 완료`로 적혀 있었는데 **레포에는 반영돼 있지 않았다**
> (세 파일 모두 원래 `catch` 절, working tree 깨끗, 커밋 없음). 2026-07-30에 실제로 고치고
> 세 서비스 컴파일을 확인했다. **A군 항목은 `grep`으로 확인한 뒤 완료 표기한다.**

세 서비스가 **문자 그대로 같은 코드**였다(`toy-content`·`toy-chat`의 `JwtParser`,
`toy-auth-user-region`의 `JwtProvider`, 전부 jjwt 0.11.5).

```java
import io.jsonwebtoken.*;                 // io.jsonwebtoken.security 는 안 들어온다
catch (SecurityException | MalformedJwtException e) { }   // <- java.lang.SecurityException
```

던져지는 것은 `io.jsonwebtoken.security.SignatureException`이라 **미포착 → 필터 밖 전파 → 500**.
게다가 catch 블록이 **전부 비어 있어** 401이 나가도 사유가 안 남았다 — 앵커 ⓑ가 원리적으로
검증 불가였던 진짜 원인이다.
**적용 (2026-07-30)**: `SignatureException` 명시 import + 포착 · 사유별 `WARN` · 최후
`catch (JwtException)`. **세 서비스 컴파일 통과.**

- **`catch (JwtException)` 가 재발 방지 장치다** — jjwt 예외의 부모이고 `io.jsonwebtoken`
  패키지라 와일드카드에 잡힌다. 새 예외 타입이 생겨도 500으로 새지 않는다
- **이것만으로 401이 된다** — `validateToken()`이 `false`를 내면 `JwtFilter:77`이
  `sendError(401)` 로 간다. catch에 걸리는 예외는 이미 401이 나가고 있었다
- **남은 구멍**: `parseClaims()` 의 `throw new RuntimeException` 은 그대로다.
  HTTP 경로는 무사하지만 **WS CONNECT는 여전히 500** (→ `A-4`)

> **왜 "즉시 고치지 않는다"의 예외였나** — AU-3는 **회차 0회**라 깨질 baseline이 없고, 이 결함을
> 두면 앵커가 성립하지 않는다. **결함 18·19는 예외로 두지 않고 보존한다.**

**예측** (반증 가능 · 배포 후 서명 훼손 토큰 1회로 검증 · 주입 불필요)

| | 수정 전 (실측) | 수정 후 (예측) |
|---|---|---|
| 응답 | 500 | **401** — 앵커 v2 원 전제 복귀 |
| Tempo | `status=error` + `exception=SignatureException` 축자 자백 | **에러 신호 소멸** → 부재 신호만 |
| Loki | 스택은 있으나 `traceId=NONE` · 라인 필터 밖 | **`WARN` + traceId 정상** → 양쪽 채널 도달 |
| 만료 vs 서명 | 구별 불가(둘 다 무로그) | **다른 문구** → ⓑ 성립 |

**인과 주장이므로 신호 도달을 끝까지 따라가야 한다** — AP-1·AP-2에서 같은 형태의 예측이
연속 반증됐다. **미확인 전제: JwtFilter 시점에 MDC traceId가 실려 있는가.**

### A-1. 예외 경로에서 traceId를 보존한다 (결함 18) — 범위가 AU-3보다 크다

`dispatcherServlet`이 찍는 ERROR가 `traceId=NONE`이라 **예외가 난 요청일수록 traceId로 로그를
못 찾는다.** 조사 도구가 traceId 단위 조회에 의존하는 한 전 문항에 걸린다.

**B-11과 뿌리가 다르다** — B-11은 *필터*가 잘라내는 것이고 A-1은 *로그 자체에 키가 없는* 것이다.
**B-11을 고쳐도 A-1은 남는다.**

**채널 감사 실측** — 게이트가 만든 500 트레이스 `6a69e01bc0116147bba4b75907e9d57e`(11:12:27Z):

| 채널 | 쿼리 | 결과 |
|---|---|---|
| Tempo | `{ status = error }` | **Top-1.** `exception=SignatureException` · `status=500` · 중단 지점까지 |
| Loki | traceId 전량 | **실패** — `GET /api/feeds/following 200 - 4ms` INFO 한 줄뿐 (결함 18·19) |
| Loki | `\|~ "ERROR\|WARN"` | **부분** — `dispatcherServlet … threw exception` 헤더 줄만, JWT 언급 없음 |
| Loki | `\|~ "Signature\|Jwt"` | 성공 — 스택 전문 + `JwtParser.validateToken(JwtParser.java:31)` |

**같은 요청 하나가 채널마다 다른 이야기를 한다** — Tempo는 원인을 말하고, traceId 로그는
*"200 성공"* 이라 말하고, 에러 로그는 JWT를 언급조차 안 한다.

### A-2. `RequestLoggingFilter`의 상태 코드 오기 (결함 19) — 보존 검토

500을 `200`으로 찍는다. 고치면 관측이 정확해지지만 **"로그가 응답과 다른 값을 말하는" 문항**은
그 자체로 가치가 있다(오귀인 변별력 0을 푸는 재료).
**A-0 배포 후 401로 바뀌면 증상이 달라지므로 고치기 전에 재실측한다.**

### A-3. 하네스 서버 사본 동기화 — 선행 필수

`chaos.sh` 수정(결함 21)은 레포(`toy-content/docs/chaos/scripts/`)에만 반영됐다.
**실제로 도는 것은 서버 `~/chaos/scripts`다** — 동기화 전에는 같은 크래시가 재발한다.

### A-4. `StompConnectHandler`는 A-0의 보호 밖이다 — 미해결

toy-chat의 WS CONNECT는 `validateToken`을 거치지 않고 `getUserId()` → `parseClaims()`로 직행하며,
거기엔 `catch (Exception e) { throw new RuntimeException(...) }`가 있다.
**시크릿 드리프트 시 WS 경로는 여전히 예외를 던진다.** IN-1 앵커(WS 세션 정상 ↔ 프레즌스 붕괴)와
겹치므로 **IN-1 재실행 전에 별도로 판정한다.**

## 우선순위 상향 — 중간 구간 부재가 분산을 만들어냈다 (ㄷ·ㄹ·ㅈ·**ㅌ**)

지금까지 ㄷ·ㄹ은 *"채점자가 판정을 강요당해 불편하다"* 는 절차 문제였다.
**AP-3 회차 2의 N=2가 그것을 측정 문제로 바꿨다.**

| 항목 | 실행 1 | 실행 2 | 편차 |
|---|---:|---:|---:|
| 1 원인 · 2 근거 · 3 탐색 · 5 오귀인 · 6 조치 | 40·25·15·5·5 | 40·25·15·5·5 | **전부 0** |
| **4 영향** (10/5/0 — 중간 없음) | **10** (판정) | **5** (판정) | **5** |

**이 문항이 잰 실행 간 분산 전량이 중간 구간 없는 항목 하나에서 나왔다.**
다섯 항목은 채점자 재량 없이 문언만으로 결정됐고 편차가 0이다.

- **판정 강요는 8회 연속이다** — AP-2 회차2(탐색) · AP-3 회차2 실행1(영향) · AU-4 회차2 실행1(영향) ·
  AP-3 회차2 실행2(영향) · AU-2 회차2 실행2(원인·탐색) · AU-4 회차2 실행2(영향) · **IN-2 회차2 실행2(오귀인)**.
- **두 번째 문항이 같은 결론을 냈다 (AU-4).** 실행 1·2가 다섯 항목 편차 0이고 **갈린 하나가
  또 4) 영향**이다. 실행 1의 기록이 이미 *"반대 판정(5)이면 83"* 이라고 적어 두었으므로
  **판정을 통일하면 편차 0 · 밴드 83~88**이다. *"분산 전량이 중간 구간 부재에서 나온다"* 가
  **N=2 문항 두 개(AP-3 · AU-4)에서 재현**됐다.
- **"보류(나중에)"의 근거가 약해졌다.** 미루는 비용이 *"문서가 지저분하다"* 가 아니라
  **"§8.1 편차에 앵커 잡음이 섞인다"** 로 확인됐다.
- **개정 방향**: 3구간 항목 중 배점이 큰 것(탐색 15 · 영향 10)에 중간 구간 신설.
  4)는 *"세 축 중 둘을 확정하고 하나를 근거 있게 유보"* 자리가 비어 있다(**7~8점**).
- **대상에 1) 원인 40을 추가한다(ㅈ).** 루브릭 v3에 10점 구간이 **이미 있으므로** 앵커 표에
  옮기기만 하면 된다 — 새 잣대를 만드는 개정이 아니다.
- **대상이 4) 영향 밖으로 나갔다 (ㅌ).** IN-2 회차 2가 **인용 가능한 쌍 중 처음으로
  4) 영향이 아닌 항목에서 갈렸다** — **5) 오귀인**이다. (**보류인 AU-2 쌍도 같은 항목이
  5 → 3으로 갈렸다** — 그쪽은 1) 원인 30 → 10에 가려져 있었을 뿐이다. **같은 문언이 두 문항에서
  분산을 만들었다.**) 모양은 ㄷ·ㄹ·ㅈ과 같고(구간 사이에 실제 행동이
  떨어진다) 이번에는 **"자력 반증"이 그 자리**다. 실행 1은 chat을 "배제된 후보(참고)" 절에,
  실행 2는 랭킹 3번에 *"배제 목적으로 기재"* 로 올렸을 뿐인데 **5 ↔ 3**으로 갈렸다.
  **이미 세 문항이 같은 문언에 걸려 있다** — AU-4 실행1·2와 AP-2 회차2도 *"후보로 올리되
  자력 반증"* 으로 3점을 받았다. **AP-2에서 "v3가 변별력을 만들었다"고 기록한 그 구간이,
  변별이 아니라 판정을 만드는 자리이기도 하다.**
- **개정 문언 초안(ㅌ)**: 5 = 미지목 **또는 후보로 올리되 관측 수치로 자력 반증** ·
  3 = 후보로 올리고 **반증 없이 유지** · 0 = 확정. **이 개정은 5) 오귀인의 변별력을 없애지
  않는다** — AP-2가 처음 3점을 받은 사유는 *"DB 계열 후보 + 자력 반증"* 이므로 재검토가
  필요하고, **적용 시 두 자 동시 채점으로 그 회차를 다시 매겨 확인한다.**
- **비용이 한 단계 올라갔다.** ㄷ·ㄹ은 총점 밴드를 흔들었지만 **ㅈ은 §8.1 인용 가능 여부를
  뒤집는다** — AU-2는 판정 10이면 65 ± 11(보류), 20이면 70 ± 6(인용 가능)이다.
- **소급 적용하지 않는다**(§8.2). 이미 매겨진 점수는 그대로 두고 다음 회차부터 적용한다.

## ㄱ — 한 번의 누락이 두 번 깎였다

  4) 영향 10 : 로그인 전면 불가 + content는 캐시 TTL 동안만 무영향

>
> | | 원 회차 | 재조사 |
> |---|---|---|
> | 입력 경로 | 질문 문안 → 파서 | **`from`/`to` 명시** |
> | `Triage.시간창 해석` | `상대 표현 '최근 1시간'` | **`명시적 from/to`** |

>   기록이 달라진다 — §8.1로 N을 쌓을 때 "같은 입력 모델"이라고 쓰려면 이 줄이 있어야 한다
