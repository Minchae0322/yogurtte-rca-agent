# 로그 중복 접기 (B-10) — 같은 저장소에 두 번 물어서, 겹친 답을 둘 다 붙이고 있었다

> **상태: 코드 적용 완료 2026-08-02 · 테스트 6건 박제 · 컨텍스트 절감 효과는 미측정**
> (다음 재조사의 `contextChars`로 잰다).
> 결함 5 — AP-3 회차 2에서 채점자가 `reports/raw/` 원본으로 발견, 두 실행 재현(N=2).
> 이 문서는 결함의 구조를 처음 보는 사람 기준으로 설명한다. 대기열 원문은 [README §4.1](README.md).

## 요지

수집기는 로그를 Loki에 **두 번 물어서** 가져온다 — 넓은 그물(창 안 ERROR/WARN 전부)과
핀셋(선정 traceId가 찍힌 줄 전부). 장애의 핵심 줄은 ERROR이면서 traceId도 찍혀 있어
**두 질문에 다 걸리고**, 어셈블러가 두 답을 그대로 이어 붙여 같은 줄이 LLM 컨텍스트에
두 번 실렸다. 고친 것은 한 가지다: **합치는 순간에 두 번째 등장만 뺀다.**

## 1. 오해부터 정리 — Tempo가 아니라 전부 Loki다

컨텍스트의 두 로그 절 중 하나가 "traceId 일치"라서 트레이스(Tempo)에서 온 것처럼 읽히지만,
**둘 다 Loki 쿼리다.** "traceId 일치"는 로그 줄 텍스트 안에 찍힌 `[traceId=…]` 문자열로
거르는 것뿐이다.

```
1) 탐색 LLM   자연어 질문 → 스윕 결과를 보고 창·서비스·traceId 선정
2) 수집(코드)  Tempo: 선정 traceId 딥 페치 (+ B-9 후보 N건)
              Loki ①: 창+서비스 기준 ERROR/WARN     <- traceId와 무관하게 항상
              Loki ②: 선정 traceId가 찍힌 줄 전부    <- traceId를 골랐을 때만
              Mimir: 메트릭
3) 어셈블      위 결과를 텍스트 한 덩어리로 → 분석 LLM
```

| | 목적 | 쿼리 |
|---|---|---|
| ① 넓은 그물 | 조사 대상 **밖**의 이상까지 — 다른 장애, traceId 없는 에러 | `{service_name=~"…"} \|~ "ERROR\|WARN\|…"` |
| ② 핀셋 | 조사 대상 요청의 **전체 서사** — INFO까지 | `{service_name=~"…"} \|= "<traceId>"` |

## 2. 왜 겹치나

두 질문의 조건을 **동시에 만족하는 줄**이 있기 때문이다. 선정된 요청이 남긴 ERROR/WARN 줄은
레벨 조건(→ ①에 걸림)과 traceId 조건(→ ②에도 걸림)을 다 만족한다. Loki에 두 번 저장된 것이
아니라, **우리가 두 번 받아온 것이다.** 도서관에서 "빨간 표지 책 전부"와 "김 작가 책 전부"를
따로 부탁한 뒤 두 무더기를 그대로 쌓으면 김 작가의 빨간 책이 책상에 두 권 놓이는 것과 같다.

실물 — varchar 위반 조사(`reports/raw/6a68c522…-20260728T151128`)의 두 응답:

| 채널 | 반환 | 내용 |
|---|---|---|
| ① ERROR/WARN | 4줄 | WARN 2 + ERROR 2 |
| ② traceId 일치 | 5줄 | **위와 동일한 4줄** + INFO 1 (`RequestLoggingFilter`, 00:05:06.387) |

겹친 4줄 중 하나가 이 조사의 정답 지문이다:

```
00:05:06.416 ERROR [traceId=6a68c522…] SqlExceptionHelper
  - Data truncation: Data too long for column 'content' at row 1
```

이 줄이 컨텍스트의 `# 로그 - ERROR/WARN` 절에 한 번, `# 로그 - traceId 일치` 절에 또 한 번
실렸다. LLM은 9줄을 읽지만 고유한 정보는 5줄이다.

## 3. 왜 한쪽 쿼리를 없애면 안 되나

| 없애면 | 잃는 것 | 실측 근거 |
|---|---|---|
| ①을 없애면 | traceId가 **안 찍힌** 에러 전부와 창 안의 다른 장애 신호 | AU-2 실행(`6a69e7fe…`)의 ERROR 5줄이 전부 `traceId=NONE` — ②로는 0줄이었다. DLQ 리스너도 같은 문제였다([dlq-traceid.md](dlq-traceid.md)) |
| ②를 없애면 | 선정 요청의 INFO 서사 | CH-1의 도착 근거 `[Kafka] DLQ 알림 재처리 성공`은 INFO다 — ERROR/WARN만으로는 영향 판정이 안 된다(결함 11) |

그래서 결론은 "하나를 버린다"가 아니라 **"둘 다 유지하되 교집합의 두 번째 등장만 접는다"** 다.

## 4. 얼마나 낭비였나

| 실행 | 중복 크기 | 비고 |
|---|---|---|
| varchar 조사 (`6a68c522…`) | traceId 채널 6,317B → 4,621B, **순절감 약 1.6KB (채널의 27%)** | 이 문서의 실물 예. 표식 +102B 포함한 순값 |
| AP-3 회차 2 | **약 5.7KB — 컨텍스트의 약 5%** | 결함 5 발견 지점. [ap-3/round-2.md §⑤](../ap-3/round-2.md) |
| CH-2 회차 2 | errwarn 채널만 45.7KB | 로그가 많은 문항일수록 커진다 |

**정확도 문제는 아니다.** AP-3 회차 2의 에이전트는 *"창 내 ERROR/WARN 조회 결과는 총 4줄"* 로
고유 줄 수를 정확히 셌다 — 속지 않았고, 채점에도 영향이 없었다. 순수하게 **토큰을 두 번 내는
비용 결함**이다. 회차 3에서 중요해진 이유는 B-9(후보 트레이스 N건)가 컨텍스트를 늘리는데,
그 증가분을 B-10(로그)·B-25(메트릭 요약)가 상쇄한다는 설계이기 때문이다.

## 5. 어떻게 고쳤나 — 결정 셋

| 결정 | 내용 | 이유 |
|---|---|---|
| **어셈블 단계에서만 접는다** | 수집기·`RawResponseStore`는 무수정 | `reports/raw/` 원본은 채점자가 "신호가 실제로 도달했는가"를 감사하는 자료다. 거기서 지우면 감사 기록이 오염된다 |
| **ERROR/WARN 절은 원문 유지, traceId 절에서 뺀다** | 뺀 자리에 표식 한 줄 | 스윕 채널은 라인 필터 결함 전력(결함 3)이 있어 "실제로 무엇을 돌려줬나" 자체가 진단 정보다. 표식이 채널 도달 사실을 보존한다 |
| **채널 간 교집합만 접는다** | 같은 채널 안의 중복은 그대로 | 그건 별개 결함(로그 이중 적재, findings 등재 대기)이다. 여기서 같이 접으면 그 결함이 조용히 가려진다 |

세부 규칙 둘:

- **키는 `(timestamp, 줄 내용)` 쌍.** 줄 내용만 보면 재시도로 같은 문구가 다른 시각에 찍힌
  정당한 두 레코드까지 지운다. Loki 타임스탬프는 나노초라 같은 레코드만 정확히 겹친다.
- **파싱이 실패하면 원문을 그대로 반환한다.** dedup은 최적화다 — 깨진 JSON 때문에 데이터를
  잃는 쪽이 중복보다 나쁘다.

적용 후 컨텍스트 모습:

```
# 로그 - ERROR/WARN (Loki)
{원문 그대로 — 4줄}

# 로그 - traceId 일치 (Loki)
(4줄은 위 ERROR/WARN 절과 동일한 레코드라 생략했다 — 이 채널로도 도달했다)
{INFO 1줄만 남은 JSON}
```

코드: [`LokiLogDedup.java`](../../src/main/java/com/yogurtte/rca/analyzer/LokiLogDedup.java) 신설
(판단 근거는 클래스 주석에), [`ContextAssembler.java`](../../src/main/java/com/yogurtte/rca/analyzer/ContextAssembler.java)
의 traceId 절 조립부 한 곳에서 호출.

## 6. 검증

픽스처는 실물이다 — 위 varchar 조사의 원본 응답 2건을 `src/test/resources/loki/`에 박제했다
(`ServiceGraphExtractorTest`와 같은 방식). 기대값이 곧 실측 모양이다: 교집합 4줄 · 고유 INFO 1줄.

| 테스트 | 확인하는 것 |
|---|---|
| 겹친 레코드만 접힌다 | folded=4 · `Data too long` 줄이 traceId 절에서 사라지고 INFO는 남는다 |
| 겹침 0이면 원문 그대로 | 재직렬화도 하지 않는다 (동일 참조 반환) |
| 같은 줄·다른 timestamp는 안 접는다 | 재시도 레코드 보존 |
| null·빈 값·깨진 JSON이면 원문 유지 | 실패 안전 |
| 전부 겹치면 빈 result | 스트림째 제거, 표식이 사정을 설명 |
| 어셈블 통합 | 컨텍스트에 정답 지문 1회 + 표식 + INFO 잔존 |

`./gradlew test` 전체 52개 통과 (2026-08-02).

## 7. 효과 측정과 반증 조건

- **측정**: 다음 재조사(단계 2)의 `contextChars`를 회차 2 동일 문항과 대조한다. 단 같은 회차에
  B-9(후보 N건, 증가 요인)가 함께 실리므로 총량 비교로는 안 되고, **raw 파일에서 채널별 크기를
  분해**해 로그 절 절감분만 귀속시킨다.
- **예측**: 로그가 겹치는 문항에서 컨텍스트 3~5% 절감([README §우선순위](README.md)).
  로그가 적은 문항(varchar류)은 절대량이 작다 — 절감의 본체는 CH-2류 로그 과다 문항이다.
- **반증 조건**: 점수는 움직이지 않아야 정상이다 — 에이전트가 중복에 속지 않았음이 실측돼
  있으므로(§4), 표식 도입 후 로그 관련 오독이 새로 생기면 그건 절감 때문이 아니라
  **표식 문언이 유발한 것**이고 문언을 고친다. 대조군(AP-1·AP-3)이 움직여도 같다.
