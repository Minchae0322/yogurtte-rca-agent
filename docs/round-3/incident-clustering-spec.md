# 1. 실측 — 무엇이 잘렸나

## 1.1 세 회차 전부 창의 끝에서 잘렸다

| | 파서가 준 창 (스윕) | 주입 포함 | LLM이 좁힌 창 | 주입 포함 | 차이 |
|---|---|---|---|---|---|
| 회차 1 | 04:45:40 ~ 05:45:40 | 예 | 04:57:00 ~ **05:20:00** | 아니오 | 2분 1초 |
| 회차 2 | 04:50:09 ~ 05:50:09 | 예 | 04:57:00 ~ **05:22:00** | 아니오 | **1초** |
| 2b | 11:29:20 ~ 12:29:20 | 예 | 11:52:00 ~ **12:22:00** | 아니오 | 3분 42초 |

주입: 회차 1·2는 `05:22:01~05:22:38`, 2b는 `12:25:42`.
결과: **4 / 100 세 번**(탐색 4점 외 전 항목 0).

**시작을 잘못 잡아 놓친 사례는 0건이다.** 그리고 파서는 세 번 다 정확했다 —
문안이 `최근 1시간 안에`이고 `RELATIVE` 경로로 정확히 1시간을 만들어 주입을 덮은 상태로 넘겼다.

> **파서 결함(B-26)은 이 사건과 무관하다.** `"14시 20분쯤"` 같은 입력을 오독하는 별개 결함이며,
> 여기서는 발현하지 않았다. 다만 *"(1)이 틀리면 (2)~(4) 수정이 전부 무효화된다"* 는 상류 리스크로
> 남는다.

## 1.2 좁히기는 복구 경로가 없다


**넓히는 API가 없다.** 창 밖 데이터는 그 조사에서 존재하지 않는 것과 같다.

## 1.3 LLM은 지시대로 잘랐다

회차 2 리포트의 `선정 이유` 원문:

> *"`mongodb_up` 하락(**05:00:09**) · chat-service 에러 급증(**05:05** 피크 54건) · chat-service
> 파드 `up` 시계열 단절(**05:05:09~05:15:09**) · 30초 타임아웃 트레이스(**05:00~05:03**) ·
> notification 컨슈머 lag 적체(**05:10~05:15**)가 모두 같은 10분 구간에 겹치고
> **05:20에 일제히 정상 복귀**하므로, 앞뒤 여유를 둔 04:57~05:22 구간의 chat-service(및 그
> 호출자인 content-service)를 깊게 봐야 한다."*

프롬프트(`triage-prompt.md`)의 유일한 정량 지시:

```
- `windowStart`/`windowEnd`: UTC ISO-8601. 위 조회 시간창 안에서 좁힌다.
  이상 구간의 앞뒤로 여유를 조금 둔다.
```

**끝 `05:22:00` = 복구 확인(05:20:09) + 여유 2분.** 최소 폭도, 끝에 대한 제약도 없다.

# 4. 타입

```java
record Signal(
    Instant from, Instant to,   // 구간. 점 신호는 from == to
    Channel channel,            // TEMPO | LOKI | MIMIR
    Precision precision,        // EXACT (ms) | BUCKET (step)
    String resource,            // 라벨에서 추출
    String signature,           // 지문
    String what,                // "mongodb_up 1 -> 0" · "duration 23,458ms"
    String ref                  // traceId · 쿼리 · 스트림
) {}
```

## 4.1 구간으로 둔 이유

지금 LLM은 로그 응답의 `[[1785315300,"4"]]` 를 보고 *"08:55:00에 4건"* 으로 읽는다
(회차 리포트에 실제로 그렇게 적혀 있다). 그런데 쿼리가 `count_over_time(...[5m])` 이므로
그 값은 **08:50:00~08:55:00 사이에 4건**이라는 뜻이다. **최대 5분 오독**이고,
구간으로 표현하면 구조적으로 사라진다.

| 채널 | `from` | `to` |
|---|---|---|
| Tempo 검색 행 | `startTimeUnixNano` | `+ durationMs` |
| Loki 버킷 | `ts − lookback` | `ts` |
| Mimir 0 구간 | 첫 0 샘플 | 마지막 0 샘플 |
| Mimir 결측 | 마지막 샘플 | 재등장 샘플 |

## 4.2 라벨 추출

| | Tempo | Loki | Mimir |
|---|---|---|---|
| `resource` | `rootServiceName` | `stream.service_name` | `job` (없으면 `application`) |
| `signature` | `rootTraceName` (엔드포인트) | 예외 클래스 (**B-29 필요**) | 쿼리 이름 |

```java
record Incident(
```

## 4.4 LLM 출력

```json
{ "incidentIds": ["INC-2"],
  "reason": "질문의 '피드 작성 실패'와 엔드포인트가 일치한다",
  "evidence": ["..."],
  "dismissed": [{ "incidentId": "INC-1", "why": "댓글 작성 엔드포인트, 질문과 불일치" }] }
```

  틀릴 수 있지만 나머지가 `dismissed`에 남는다

# 5. 신호 판정 규칙

## 5.1 무엇을 세고 무엇을 안 세는가

| 신호로 센다 | 안 센다 |
|---|---|
| 값이 **변한** 지점 (`1 → 0` · `0 → 24`) | 전 구간 상수 |
| **0이었던** 구간 | 절대 크기 (*"54건은 많다"*) |
| 시리즈가 **사라진** 구간 (결측) | 평시 baseline 대비 비교 |
| 검색 결과의 **존재 자체** | |
| 버킷에 **값이 있는 것** | |

**임계값을 하나도 쓰지 않는다.** 근거 셋:

1. **baseline이 없다** — `architecture.md` 알려진 공백: *"평시 그래프를 대조군으로 들고 있어야 한다"*

   B-21에 같은 규율이 있다(*"어휘 사전을 코드에 박지 않는다"*)
3. **에이전트가 이미 이 기준을 쓴다** — 리포트 원문:
   *"`websocket_active_users=0`이 전 구간 상수 — **변화가 없으므로** 이번 증상과 무관"*

# 6. 분류 알고리즘

## 6.1 코드

```java
String key(Signal s) { return s.channel() + "|" + s.resource() + "|" + s.signature(); }

List<Incident> cluster(List<Signal> signals, Duration gap) {
    var groups = signals.stream()
        .collect(groupingBy(this::key))                 // ① 라벨 3축
        .values().stream()
        .flatMap(g -> splitByGap(g, gap))               // ② 같은 키 안에서 시간
        .toList();
    return linkRelated(mergeByTraceLink(groups));       // ③ 병합  ④ 관계 표시
}

/** 구간이 겹치거나 gap 이내로 이어지면 같은 군집. reach = 끝이 가장 먼 신호. */
private Stream<Incident> splitByGap(List<Signal> signals, Duration gap) {
    var sorted = signals.stream().sorted(comparing(Signal::from)).toList();
    var out = new ArrayList<Incident>();
    var current = new ArrayList<Signal>();
    Instant reach = null;

    for (var s : sorted) {
        if (reach != null && s.from().isAfter(reach.plus(gap))) {
            out.add(Incident.of(current));
            current = new ArrayList<>();
            reach = null;
        }
        current.add(s);
        reach = (reach == null || s.to().isAfter(reach)) ? s.to() : reach;
    }
    if (!current.isEmpty()) out.add(Incident.of(current));
    return out.stream();
}
```

`reach`가 핵심이다 — **끝이 가장 먼 신호**를 기준으로 이어붙이므로 구간 신호를 올바르게 다룬다.

## 6.2 축 넷 — 순서가 중요하다

| 축 | 무엇을 가르나 | 사건이 시간상 교차해도 되나 |
|---|---|---|
| 채널 | 신호 종류 | 무관 |
| **리소스** | 동시에 난 다른 서비스의 장애 | **완전히 면역** |
| **지문** | 같은 서비스의 다른 사건 | **완전히 면역** |
| 시간 gap | 같은 키의 다른 시각 사건 | 취약 — 그래서 마지막 |

### 시간만으로는 실패한다 (검산)

CH-3 회차 2의 신호를 시각 순으로 늘어놓으면 `lag` 신호 하나가 **05:00:09부터 05:20:09까지**
걸쳐 있다. 시간 간격만으로 묶으면 **04:55~05:25 전체가 한 덩어리**가 되고 정답이
CH-1·CH-2에 흡수된다. `lag`는 `resource=kafka`이므로 리소스 축이 그 브리지를 끊는다.

### gap 값의 근거

| 제약 | 값 | 방향 |
|---|---|---|
| CH-1 끝(05:03:30) ~ CH-2 시작(05:05:09) | **99초** | 이보다 **작아야** 갈린다 |
| CH-1의 30초 재시도 4회 (연속 약 2분) | — | **묶여야** 한다 |
| CH-3 Incident 독립 | **4분 51초** | 이보다 **작아야** 한다 |

**60초 근방**이고 안전 여유가 4배 이상이다. 리소스 축이 이미 서비스 간 분리를 하므로
gap을 키울 이유가 없다. 설정으로 빼고 회차 3 데이터로 검산한다.

## 6.3 창 계산 — B-27을 흡수한다

```java
TimeWindow window(SurveyProperties p, TimeWindow sweep) {
    var pad = switch (precision()) {
        case EXACT  -> p.incidentPad();          // 기본 2분
        case BUCKET -> parseStep(p.step());      // lookback 폭 = 5분
    };
    return clampTo(sweep, new TimeWindow(firstAt().minus(pad), lastAt().plus(pad)));
}
```

**여유를 임의로 정하지 않고 신호의 정밀도에서 가져온다.**

> **B-27(꼬리 여유 강제)이 여기 흡수된다.** B-27은 *"LLM이 만든 창 끝에 `step × 2`를 덧댄다"* 는
> 처방이었고 **추측을 추측으로 보정**하는 것이었다(창 1.4배). 창을 신호에서 유도하면 보정할
> 숫자가 없어지고, `BUCKET` 분기가 그 역할을 대신한다.
> **B-23(검증 패스)은 다르다** — 틀렸다는 것을 알았을 때 되돌아가는 경로이고 여전히 필요하다(§11).

## 6.4 병합은 결정적 근거만

| 채널 | 연결자 | 코드가 묶을 수 있나 |
|---|---|---|
| **Tempo** | `traceID` · `serviceStats`의 서비스 목록 | **예** |
| Loki (스윕) | 없음 — 집계라 라인 본문이 없어 traceId를 못 뽑는다 | 아니오 |
| Mimir | 없음 — 메트릭에 traceId가 없다 | **원리적으로 불가** |

한 트레이스가 여러 서비스를 담는 것은 응답에 그대로 있다. CH-3 회차 2의 실제 값:

```json
"serviceStats": { "chat-service":    { "spanCount": 17, "errorCount": 8 },
                  "content-service": { "spanCount": 15, "errorCount": 0 } }
```

**Mimir 신호와 Tempo 신호를 시간 근접만으로 병합하지 않는다.** 토폴로지를 병합 근거로 쓰면
*"auth가 죽으면 content가 영향받는다"* 를 코드에 심는 것이고, AU-4의 정답 구조에 가깝다.
겹치면 `related`로만 표시하고 묶는 판단은 LLM에 남긴다.

## 6.5 애매하면 나눈다

**과병합은 정보를 잃고, 과분할은 잃지 않는다.**

- 나누면 후보가 늘고 LLM이 고른다. 안 고른 것은 `dismissed`에 남아 되돌아갈 수 있다
- 합치면 창이 넓어지고 **구별 자체가 사라진다** — 지금 상태가 그렇다

**크기로 필터링하지 않는다.** CH-3의 Loki 신호는 **1건**이고 옆 버킷이 54건이다.
최소 건수 조건을 두면 그게 잘려나간다. 크기는 `Signal.what`에 담아 LLM이 보게 한다.

# 7. Slow Trace 채널 (B-17)

## 7.1 지금

```java
// Surveyor.java:56 — 검색 1회
traceSearch = tempoClient.search(correlationId, surveyProperties.traceQuery(),
                                 window.start(), window.end(), surveyProperties.traceLimit());
```

```yaml
trace-query: '{ status = error }'
trace-limit: 20
```

**200 성공인 지연 장애는 원리적으로 안 걸린다.** CH-3 창 안에서 이 쿼리가 찾은 4건은
`05:01` · `05:02` · `05:30` · **깨진 행**이었고 전부 다른 장애의 것이었다.

## 7.2 바꿀 것

```yaml
trace-query:            '{ status = error }'
slow-trace-query:       '{ duration > 3s && status != error }'
slow-trace-threshold:   3s
trace-limit:            20      # 채널별로 각각
```

검색 2회 후 후보 병합. **단일 쿼리로 합치지 않는다** —
`{ status = error || duration > Ns }` 로 쓰면 후보 목록에서 *어느 채널로 도달했는지*가 사라지고,
*"에러로는 안 잡히는데 지연으로 잡혔다"* 가 곧 장애 성격이다.
`status != error` 를 붙여 두 채널이 겹치지 않게 가른다.

비용: 검색 1회 추가(수백 ms). 스윕 전체가 921ms다.

## 7.3 `duration`이 정확히 무엇인가

**TraceQL의 `duration`은 span 하나의 소요 시간이다. 트레이스 전체가 아니다.**
검색 응답에 둘이 같이 들어 있어 확인된다.

```json
{ "traceID": "6a69c37f…",
  "durationMs": 76,                    ← 트레이스 전체 = 76ms
  "spanSet": { "spans": [
      { "spanID": "be307298167fb5f8",
        "durationNanos": "4332000" }], ← 매칭된 span = 4.33ms
      "matched": 1 },
  "serviceStats": { "content-service": { "spanCount": 23, "errorCount": 1 } } }
```

`{ duration > 3s }` 는 **그런 span이 하나라도 있는 트레이스**를 반환하고,
`spanSet`에 **어느 span이 걸렸는지**가 함께 온다.

장애 형태마다 필요한 것이 다르다.

| 형태 | 예 | span `duration` | 트레이스 전체 |
|---|---|---|---|
| **블로킹** | Mongo 대기 23초 · 커넥션 풀 대기 | **걸린다** | 걸린다 |
| **누적** | N+1 쿼리 · 재시도 4회 | 안 걸린다 (각각 짧다) | **걸린다** |
| **공백** | 부모 span 없는 비동기 경계 | 못 걸릴 수 있다 | 못 걸릴 수 있다 |

CH-3는 블로킹형이라 `duration`으로 잡혔다. **그러나 IN-3(커넥션 풀 고갈)이나 N+1 계열은
누적형**이므로 같은 쿼리로는 못 잡는다. → **트레이스 전체(`traceDuration`) 채널도 필요할 수 있다.**

**미확인**: CH-3 트레이스에서 **어느 span이 8초를 넘겼는지** 확인하지 않았다.
리포트 서술이 *"22.29초 공백"* 인데 공백은 span 사이가 빈 것이므로, 매칭시킨 것은
그 공백을 감싼 부모 span일 것이다. `spanSet`을 열어 확인해야 쿼리를 확정할 수 있다.

## 7.4 임계값 — 미확정

`8s`는 채점자가 확인용으로 쓴 값이고 **문항에서 역산한 값**이다(CH-3가 23초라 넉넉히 잡았다).
그대로 쓰면 정답을 보고 정한 임계값이 된다.

**정당한 근거는 정상 트래픽 분포다.** 장애 데이터를 보지 않고 정할 수 있다.

### 재는 방법 둘

**① 사용자 요청 지연 분포 (메트릭)**

```promql
histogram_quantile(0.99,
  sum by (le, application) (rate(http_server_requests_seconds_bucket[5m])))
```

`http_server_requests_seconds_count` 는 이미 쓰고 있으므로(401 쿼리) `_bucket` 도 있을 것이다.
장애 없는 1시간에 던져 서비스별 p99를 얻는다.

**② span 단위 최장 (WS·컨슈머 포함)**

메트릭에는 HTTP만 있으므로 Tempo로 계단식 확인이 필요하다.

```
{ duration > 1s }   → 건수 · 무엇이
{ duration > 3s }   → 건수 · 무엇이
{ duration > 5s }   → 건수 · 무엇이
```

### 판정 기준

| 정상 창의 후보 건수 | 판단 |
|---|---|
| 0~2건 | **좋다** — 장애 때만 반응한다 |
| 5~10건 | 애매. 무엇이 걸리는지 보고 제외 규칙 검토 |
| 20건 (limit 꽉) | **못 쓴다** — 정답이 밀려난다 |

### 측정 후 문서에 쓸 형태

> 장애 없는 1시간 창에서 사용자 요청 p99가 **[측정값] ms**, span 단위 최장이
> **[측정값] 초**(`[span 이름]`)였다. 3초는 그 **[N]배**이며 같은 창에 `{ duration > 3s }` 를
> 던졌을 때 후보가 **[N]건**이었다. **문항에서 역산하지 않았다.**

**현재 상태**: 이 측정은 **미실행**이다. `3s`는 사용자 체감 한계에서 온 잠정값이고,
*"정상 최대가 1.2초"* 같은 수치는 아직 재지 않았으므로 인용하지 않는다.

## 7.5 함께 걸리는 제약 둘

**① `trace-limit: 20`이 병목이 된다.** 임계값을 낮추면 후보가 늘고, 20건에서 잘리면 정답이
밀려난다. 채널별 limit과 **정렬 기준**이 함께 필요해진다.

**② 정렬을 duration으로 하면 깨진 행이 1위가 된다.** Tempo `/api/search`가 `durationMs` **33일**
짜리 행이나 `startTimeUnixNano == 0` 인 행을 그대로 내려준 사례가 있다(CH-2에서 관측,
같은 트레이스를 `/api/traces/{id}`로 받으면 멀쩡하다).

→ **B-15(깨진 행 방어)가 B-17보다 먼저다.** round-3 §7에 `B-15 → B-9` 순서가 있는데
**`B-15 → B-17`도 같은 이유로 강제된다.**

## 7.6 노이즈

`duration > 3s` 는 **정상적으로 오래 걸리는 것도 가져온다.** chat-service에
`rootTraceName='connection'`(WebSocket)이 있고, CH-3 창의 2건은 30초 타임아웃 에러였지만
**정상 WS 연결 span도 길 수 있다.**

완화 후보 (전부 **미검증**):

- `&& status != error` — 에러 채널과 겹치지 않게 가른다 (§7.2에 이미 반영)
- `&& kind = server` — 서버 처리 span으로 한정해 장수명 연결을 뺀다
- 장수명 span 이름 제외 목록

§7.4의 ② 측정이 이 판단의 입력이 된다.

# 8. 단기 장애 Metric 보존 (B-18)

## 8.1 지금

```java
mimirClient.queryRange(correlationId, query, window.start(), window.end(), "5m")
```

5분마다 **그 순간의 값**을 찍는다. 실측:

```
mongodb_up    05:20:09 = 1        05:25:09 = 1
                      +-- 이 사이 23초가 0이었다. 격자에 안 걸렸다 --+
```

## 8.2 step을 줄이는 것은 답이 아니다

스윕 창이 몇 시간이므로 step을 15초로 줄이면 **응답이 10~20배**가 된다.
*"스윕은 집계라 창이 넓어도 응답이 작다"* 는 설계 전제가 깨진다.

## 8.3 집계 함수 교체

```promql
up · mongodb_up · kafka_brokers             →  min_over_time(m[5m])
kafka_consumergroup_lag · ws_active_users   →  max_over_time(m[5m])
```

각 스텝이 그 5분의 최솟값(또는 최댓값)을 담으므로 23초 딥이 살아난다.
**점 개수가 같아 응답 크기는 불변이다.**

**방향을 메트릭마다 지정하는 이유** — 생사 신호는 **떨어진 것**이 신호고,
누적 신호는 **올라간 것**이 신호다.

## 8.4 도달 확인과 한계

**도달 실측**: 15초 해상도로 재조회하면 **05:22:37 스크레이프가 0**으로 또렷하다.

**한계**: 스크레이프 간격이 하한이다. 15초 간격이면 23초 장애는 1~2 샘플만 걸리고,
그보다 짧은 장애(예: 5초)는 샘플 자체가 없어 `min_over_time`으로도 안 보인다.

**B-17과 따로 넣는다.** 둘 다 CH-3를 열 수 있어 같이 적용하면 기여도가 안 갈린다.

## 8.5 부수 사실 — Mimir 격자는 `start`에 정렬된다

`mongodb_up` 원본이 `[[1785312796,…],[1785313096,…]]` 로 **`start + k×step`** 이다
(Loki는 벽시계 5분 배수에 정렬된다).

즉 **Mimir 샘플 시각은 질문한 시각에 따라 통째로 움직인다.**

1. 짧은 딥의 포착 여부가 질문 시각에 좌우된다 — `min_over_time`이 격자 위치와 무관해지는 이유
2. **재조사 때 `from`/`to`를 문자 그대로 맞춰야 한다.** 1초만 달라도 샘플 시각이 전부 옮겨간다
   → §12.2

# 9. Loki 지문 (B-29)

| 채널 | 지문 | 스윕 응답에 있나 |
|---|---|---|
| Tempo | `rootTraceName` + span `exception` 속성 | **있다** |
| Mimir | 쿼리 이름 | **있다** |
| **Loki** | 예외 클래스명 | **없다** — `sum by (service_name)` 이라 라인 본문이 없다 |

지금 Loki로는 *"chat-service에서 54건 났다"* 까지만 알고 **무엇이 났는지 모른다.**
같은 서비스에서 두 장애가 나면 Loki 신호로는 못 가른다.

```logql
sum by (service_name, exc) (
  count_over_time({service_name=~"..."} |~ "ERROR|WARN"
    | regexp "(?P<exc>[A-Za-z][\\w.]*(Exception|Error))" [5m])
)
```

- **여전히 집계다.** 응답 크기가 `(서비스 × 예외 종류 × 스텝)`으로만 늘고 라인 본문은 안 온다
- **어휘 사전이 아니라 구조 추출**이라 블라인드에 걸리지 않는다 —
  `"varchar"` 같은 문항 어휘가 아니라 *"클래스명 형태의 토큰"* 이라는 규칙만 쓴다
- **미확인**: 매치되지 않는 줄의 처리(LogQL `regexp` 파서가 `__error__`를 붙인다).
  예외명 없는 WARN 줄이 버려지면 안 되므로 **기존 쿼리와 병행**이 안전할 수 있다

**B-20 이후에 넣는다** — 지문 축을 늘리면 군집 결과가 바뀌므로 델타를 따로 재야 한다.

# 10. 코드가 못 가르는 것

## 10.1 같은 서비스 + 같은 엔드포인트 + 같은 예외

탐색 단계에서 원리적으로 못 가른다. 구별에는 로그 본문의 제약 이름이나 SQL문이 필요하고
스윕은 집계라 본문이 없다.

**그런데 탐색이 그걸 할 필요가 없다.** 창에 원인이 둘인 회차가 만점을 받았다.

| 회차 | 창 안 장애 | 점수 | 누가 갈랐나 |
|---|---|---|---|
| CH-2 회차 2 | Mongo + chat | **100 · 100** | **분석**이 근본·확대·증폭으로 계층 분리 |
| AP-3 회차 2 실행 2 | AP-1 + AP-3, 둘 다 content-service | **95** | **분석**이 URI·예외 지문으로 갈랐다 |

| 단계 | 목표 | 갖고 있는 것 |
|---|---|---|
| 탐색 | **안 놓치기** — 창이 후보를 덮는가 | 집계값 |
| 분석 | **가르기** — 무엇이 원인인가 | 원본 트레이스·로그 전문 |

**성공 기준은 "완벽한 분리"가 아니라 "정답이 후보 목록에 살아 있는가"다.**
CH-3가 실패한 지점이 그것이다 — 후보 3건이 전부 다른 장애의 것이었다.

## 10.2 서비스를 넘나드는 장애

auth가 죽어 content가 이상해지는 형태는 리소스 축이 **둘로 쪼갠다.**
그리고 Mimir↔Tempo는 연결자가 없어 코드가 합칠 수 없다(§6.4).

`architecture.md` 알려진 공백: *"서비스 그래프를 코드가 모른다. `TraceSpans`가 `parentSpanId`를
읽지 않아 트레이스를 갖고도 호출 그래프를 못 만든다."*

**대응은 두 층이다.**

| 층 | 무엇 | 항목 |
|---|---|---|
| B (구조) | 다른 리소스의 Incident를 **버리지 않고 `related`로** 남긴다 | B-20 |
| C (지시) | *"원인 서비스에 의존하는 다른 구성 요소의 상태를 확인하라"* | **C-1** |

이 능력은 문항마다 갈렸다 — AU-4는 상·하류 동시 스코프로 탐색 15/15,
AU-2는 auth 하나만 조사해 **감점 24가 전부 content 축**이었다(능력 결함 가).

`parentSpanId`를 읽으면 `serviceStats`보다 강한 연결자가 생기지만, 문서가 경계를 그어놨다 —
*"토폴로지 추가는 변경군으로 측정할 대상이지 슬쩍 끼울 것이 아니다."*
→ **B-28로 세워 B-20 델타를 잰 뒤.**

| ③ | CH-3 구간이 독립 후보로 생기는가 | 05:20~05:25 | **B-17 선행** |
| ④ | AP-1 / AP-3 쌍이 엔드포인트로 갈리는가 | 07-29 08:51 · 09:10 | — |

**주입이 필요 없다.** 보존기간 안이면 재조사로 확인된다.

## 12.2 재조사 시 필수 조건

문안이 `최근 1시간 안에`이므로 그대로 돌리면 **오늘 창**을 조사한다.

- **`from`/`to`를 명시하고 원 회차와 문자 그대로 일치시킨다** (CH-3 = `04:50:09~05:50:09Z`)
- 창이 조금이라도 다르면 스윕 후보 집합이 달라지고, **Mimir 격자가 `start`에 정렬되므로
  샘플 시각이 전부 옮겨간다**(§8.5)
- **`to`를 빼먹으면 조용히 오늘 창을 조사한다** — `resolve()`가 `from != null && to != null` 이라
  `from`만 주면 질문 파싱으로 떨어지고 리포트에는 `상대 표현 '최근 1시간'`이라고 찍힌다.
  **매 재조사 후 `시간창 해석` 칸이 `명시적 from/to`인지 확인한다**
- 선행으로 **B-26**(파서 재작성 + 입력 검증)을 통째로 넣는다

## 12.3 측정 순서

```
B-15  →  B-17 단독  →  B-18 단독  →  둘 다  →  B-20  →  B-23
(깨진 행)  (신호가 보이나)              (창이 맞나)  (되돌아가나)
```

- **B-15가 맨 앞** — 후보를 정렬하기 시작하면 깨진 행이 1위가 된다(§7.5)
- **B-20을 1층 앞에 넣지 않는다** — 신호가 없으면 만들 Incident가 없어 델타가 0으로 나온다
- **B-20 단독 델타는 CH-1·CH-2로 잰다.** 성공 기준은 **두 조사가 서로 다른 traceId를 고르는 것**
- **B-29는 B-20 이후** — 지문 축을 늘리면 군집 결과가 바뀐다

## 12.4 반증 조건

| 변경 | 개선이 없으면 |
|---|---|
| B-17 · B-18 | 신호 공급이 병목이 아니다 — 남는 것은 좁히기 판단 |
| B-20 | 후보를 남겨도 안 고른다면 병목은 **지시**다 → C-1 |
| B-29 | 같은 서비스 두 장애가 계속 뭉치면 **지문 정의**가 잘못됐다 |
| gap 60초 | ①~④ 중 하나라도 실패하면 값이 아니라 **축 설계**를 다시 본다 |

## 12.5 채점 영향

`rubric-v3` 3) 탐색 15의 S를 *"무엇을 골랐나"* 에서 **"무엇들을 세웠나"** 로 읽을 수 있게 된다.

| 실패 종류 | 지금 | 앞으로 |
|---|---|---|
| 후보를 **만들지 못했다** (CH-3) | 탐색 4점 | `incidents[]`에 없음 → **재현율 실패** |
| 후보에 있는데 **잘못 골랐다** (AU-2 실행2) | 탐색 15점 | `dismissed[]`에 정답 → **정밀도 실패** |

지금은 둘이 한 점수에 섞여 있다. **앵커 문언 변경은 아니지만 회차 3 채점 전에 이 해석을
못박아 둘 것.**

# 13. 열린 문제 — 창을 좁히면 대조군이 줄어든다

결함 4의 처방(**B-9**)이 *"창 안 후보 N건 수집"* 인데, 창이 4분이면 **그 안에 정상 트레이스가
몇 개 없을 수 있다.** AU-4가 baseline auth span이 없어 원인 −10을 받은 것이 그 문제였다.

**두 요구가 반대 방향이다** — 정확한 창은 좁고, 대조군은 넓은 창이 필요하다.

현재 판단은 *"창은 좁게, 후보 수집은 `related` Incident까지 포함"* 이지만 **미검증**이다.
