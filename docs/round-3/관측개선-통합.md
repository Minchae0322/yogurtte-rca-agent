# 관측 데이터를 RCA Evidence로 바꾸다

> 장애를 놓친 원인을 LLM의 추론력 부족으로 단정하지 않고, 관측 신호·후보 생성·증거 전달의 세 층으로 분해해 개선한 기록입니다.
>
> 이 문서는 [관측개선.md](관측개선.md), [evidence-pipeline-improvements.md](evidence-pipeline-improvements.md), [incident-clustering.md](incident-clustering.md), [incident-clustering-walkthrough.md](incident-clustering-walkthrough.md)를 포트폴리오용으로 통합·재구성한 SoT입니다. 세부 규칙은 [incident-clustering-spec.md](incident-clustering-spec.md), [service-graph-spec.md](service-graph-spec.md), [log-dedup.md](log-dedup.md)를 참조합니다.

## 프로젝트 요약

자연어 장애 제보를 받아 Loki·Tempo·Mimir의 데이터를 조사하고, 원인과 근거를 보고하는 RCA 에이전트를 개선했다. 핵심 문제는 데이터가 없어서가 아니라, **탐색 단계에는 결정적 신호가 도달하지 않고 분석 단계에는 관계와 원인 정보가 잘린 형태로 전달된다**는 것이었다.

CH-3의 MongoDB 단기 장애를 재현하며 문제를 역추적했다. 실제 장애(23.6초)는 최초 조사 범위 안에 있었지만, 에이전트는 무관한 신호를 근거로 조사 창을 장애 1초 전에서 닫아 원인을 놓쳤다. 범위를 넓히는 첫 해결책은 컨텍스트만 72%, 비용만 39% 늘리고 점수는 바꾸지 못했다. 이 반증을 출발점으로 탐색 구조와 Evidence 파이프라인을 다시 설계했다.

| 문제 | 원인 규명 | 해결 | 확인한 결과 |
|---|---|---|---|
| 23초 장애를 탐색하지 못함 | 오류가 아닌 성공 요청의 지연, 낮은 샘플링 밀도 | slow trace 채널과 구간 집계·10초 scrape | `mongodb_up` 2 → 6 샘플/분 |
| 하나를 잘못 고르면 조사 종료 | 단일 Window/traceId로 다음 후보를 버림 | Signal → Incident 후보군 → LLM 선택 | 저장 스윕에서 42개 신호 → 13개 후보 |
| 원인이 로그에 있어도 못 봄 | ERROR 헤더만 수집, stack line 누락 | 분석용 LogQL에 스택 패턴 추가 | 실제 코드 위치까지 Evidence에 포함 |
| 호출 관계를 모델이 추정함 | span을 목록으로만 전달 | 속성·부모 관계를 호출 그래프로 요약 | 28개 span → 의미 있는 엣지 6개 |
| 탐색 컨텍스트가 비대함 | 의사결정에 쓰지 않는 원본 JSON 포함 | 후보·도달 요약 중심으로 전환 | 45,991 → 7,697자(-83%), 선택 결과 동일(N=1) |

## 문제 상황: 시간창 안에 있던 장애를 왜 놓쳤는가

CH-3에서 TimeParser가 만든 초기 조사 범위는 `04:50~05:50`이었고, MongoDB 장애 주입 구간은 `05:22:01~05:22:38`이었다. 실제 장애는 처음부터 범위 안에 있었다. 그럼에도 에이전트는 원인을 제시하지 못했다.

실행을 따라가 보니 탐색 LLM은 초기에 같이 잡힌 MongoDB·서비스 오류 신호를 보고 조사 창을 `04:57~05:22`로 축소했다. 결과적으로 창의 끝이 장애 시작 1초 전이 되었다. 분석 단계는 잘못 좁혀진 범위만 수집하므로, 이후 LLM이 아무리 잘 추론해도 실제 장애의 trace·log·metric을 볼 수 없는 구조였다.

```text
초기 시간 해석: 04:50 ───────────────────────────────────── 05:50
실제 주입 구간:                              05:22:01 ~ 05:22:38
탐색이 축소한 창:     04:57 ──────────────────────────────── 05:22
                                                               ↑ 장애 1초 전 종료
```

이는 시간 표현 파서의 실패도, 분석 LLM이 증거를 잘못 읽은 실패도 아니었다. **탐색 단계가 실제 장애를 독립된 조사 후보로 만들지 못했고, 단일 선택이 이후 수집 범위를 고정한 실패**였다.

### 첫 해결책을 반증했다: 창 확대는 해결이 아니었다

처음에는 “탐색 창을 더 넓히면 장애를 포함할 수 있다”고 판단했다. 그러나 창을 2.26배로 넓힌 재실행에서 다음 결과가 나왔다.

| 측정 | 변화 | 해석 |
|---|---:|---|
| 컨텍스트 | +72% | 늘어난 정보의 대부분이 메트릭 시계열 |
| 비용 | +39% | 수집·분석 비용만 증가 |
| RCA 점수 | 불변 | 실제 장애를 가리키는 Signal은 여전히 없음 |

창이 넓어져도 같은 창의 로그는 16줄뿐이었고, 메트릭 8종 × 98점 × 다중 시리즈가 증가분 대부분을 차지했다. 따라서 “더 많이 보내면 모델이 찾을 것”이라는 가설을 버렸다. 이 실험은 문제를 **입력 크기**가 아니라 **Signal 품질과 후보 구조**의 문제로 바꾸는 결정적 근거였다.

### 채널별 역추적으로 원인을 분리했다

| 관측 채널 | 기존 방식 | 왜 CH-3를 놓쳤는가 | 개선 방향 |
|---|---|---|---|
| Tempo | `status = error`만 검색 | 장애는 HTTP 실패가 아닌 약 23초 지연 후 성공 | slow trace를 별도 채널로 탐색 |
| Mimir | 5분 시점값 | 장애가 샘플 사이에 있으면 0이 기록되지 않음 | 구간 집계와 수집 간격을 분리해 개선 |
| Loki | ERROR/WARN 집계 | 해당 구간의 유의미한 에러 로그가 희소 | 로그를 유일한 정답 채널로 가정하지 않음 |

이 진단은 “모델을 더 똑똑하게 만들자”가 아니라, **모델이 선택할 수 있는 증거 집합을 재현 가능하게 만들자**는 설계 전환으로 이어졌다.

## 설계: 두 LLM 호출의 책임을 분리했다

```
자연어 제보
  → 시간창 해석(코드) → 전체 관측 스윕(코드)
  → Signal 추출(코드) → Incident 후보화(코드)
  → 탐색 LLM: 후보 선택
  → 원본 수집(코드) → Evidence 정제·조립(코드)
  → 분석 LLM: 원인·근거·조치 서술
```

탐색과 분석은 같은 로그를 보더라도 목적이 다르다. 탐색 LLM은 **어디를 조사할지** 고르고, 분석 LLM은 **왜 발생했는지** 설명한다. 따라서 탐색에는 개수 곡선·후보·도달 요약만 전달하고, 분석에는 원본 로그·span·호출 그래프를 전달한다.

| 결정 | 책임 주체 | 이유 |
|---|---|---|
| 시간 표현을 범위로 해석 | 코드 | 같은 입력에서 다른 창이 생기면 재현성이 깨짐 |
| 조회 쿼리와 이상 신호 추출 | 코드 | 임계값이나 토폴로지로 정답을 심지 않기 위함 |
| 후보 생성·병합 규칙 | 코드 | 탐색 공간을 안정적으로 보존 |
| 조사할 후보 선택 | 탐색 LLM | 여러 관측 채널의 맥락을 비교 |
| 원인·근거·후속 조치 | 분석 LLM | 수집된 원본 Evidence를 종합 |

LLM이 조사 시간이나 서비스명을 자유롭게 만들어 내지 않도록 했다. 탐색 LLM의 출력은 후보 ID이고, 이후의 시간창·서비스·traceId는 선택된 후보에서 코드가 파생한다. 이 경계가 있어야 모델 판단의 품질과 파이프라인의 품질을 따로 검증할 수 있다.

## 해결 1: “오류”가 아닌 “지연”도 탐색 신호로 만들었다

기존에는 에러 트레이스만 검색했다.

```text
기존: status = error
개선: status = error
      duration > 2s && status != error
```

두 결과를 하나로 합치지 않고 오류·지연 채널을 분리했다. CH-3처럼 에러 검색 결과가 0건인 장애에서, “에러로는 관측되지 않았고 지연으로는 관측됐다”는 사실 자체가 장애 성격을 설명하는 Evidence이기 때문이다.

2초는 임의의 값이 아니다. 3초 기준에서는 Redis timeout이 만든 2,0xxms 지연 19건을 놓쳤고, 정상 트래픽의 노이즈 바닥은 약 500ms였다. 그 사이에서 2초가 오탐 없이 필요한 지연을 포착한 구간이었다.

### 메트릭의 두 가지 구멍을 구별했다

처음에는 `min_over_time`/`max_over_time`만 적용하면 단기 장애를 보존할 수 있다고 봤다.

```promql
min_over_time(mongodb_up[5m])
max_over_time(kafka_consumergroup_lag[5m])
```

이 방식은 쿼리가 여러 샘플 중 일부만 고르는 문제는 해결한다. 그러나 수집기가 30초마다 한 번만 측정하고 장애가 23.6초라면, 샘플 자체가 없을 수 있다. 이를 재조사에서 확인했고, “집계 함수의 문제”와 “관측 밀도의 문제”를 분리했다.

| 계층 | 변경 | 근거 |
|---|---|---|
| 인프라 exporter | 30초 → 10초 | 활성 시리즈 145개(5.5%)만 대상으로 단기 인프라 장애 포착률을 높임 |
| 애플리케이션 Micrometer | 60초 유지 | 활성 시리즈 2,513개(94%)까지 무차별 증폭하지 않음 |

결과적으로 `mongodb_up`은 분당 2개에서 6개 샘플로 증가했고, 앱 지표의 60초 주기는 유지됐다. 단, 23초 다운이 실제로 `0`으로 기록되는지는 다음 장애 주입에서 확인해야 한다. 이 경우에도 실패한다면 원인은 scrape 간격이 아니라 exporter의 상태 반영 방식이다.

## 해결 2: 단일 정답을 강제하지 않고 후보군을 보존했다

기존 구조는 `Window 1개 + traceId 1개`였다. 처음 선택이 틀리면 다른 가능성은 복구할 수 없었다. 이를 `Signal → Incident 후보 N개 → 탐색 LLM 선택`으로 변경했다.

### 왜 Signal을 그대로 쓰지 않고 Incident로 나누었는가

Signal은 “이상처럼 보이는 관측 한 조각”일 뿐, 바로 조사 범위가 될 수 없다. Tempo의 trace 한 건, Loki의 5분 버킷 한 점, Mimir의 값 변화 한 번은 서로 시간 단위와 식별자가 다르다. 이를 그대로 LLM에 넘기면 같은 사건의 반복 신호는 흩어지고, 서로 다른 사건은 시간순으로 섞인다. 반대로 전부를 하나의 Window에 모으면 무관한 구간의 원본이 수집 상한을 차지한다.

```text
Signal 그대로 전달
  - chat filterchain 30초 지연 ×13
  - mongodb_up 1→0→1
  - kafka lag 0→24→25→0
  - content ERROR/WARN 5분 버킷 ×5
       ↓
  모델이 수십 개 조각에서 “같은 사건/다른 사건”을 매번 다시 판단
       ↓
  한 번 틀린 Window 선택은 이후 수집에서 되돌릴 수 없음

Incident 후보화
  - 같은 성격의 반복은 하나의 조사 단위로 접어 패턴을 보존
  - 서비스·자원·지문이 다른 신호는 별도 후보로 남겨 선택지를 보존
  - 후보가 선택된 뒤에만 해당 범위의 원본을 수집
```

CH-3가 바로 이 구조적 문제를 드러낸 사례다. 실제 장애가 탐색 창에 있었는데도 하나의 Window만 남기는 구조에서는 다른 오류 신호가 선택되는 순간 23초 지연 trace가 후보 목록에서 사라졌다. “후보를 나눈다”는 것은 장애를 인위적으로 여러 개 만든다는 뜻이 아니라, **인과가 아직 확정되지 않은 관측 조각을 되돌릴 수 있는 조사 단위로 보존하는 것**이다.

분리 기준은 최소한의 관측 사실만 사용한다. 서비스가 다르거나, 자원이 다르거나, 지문이 다르거나, 같은 지문이라도 충분히 긴 시간 공백이 있으면 다른 Incident다. 코드가 “MongoDB down과 Kafka lag는 한 사건” 또는 “content와 chat은 같은 장애”라고 결정하지 않는다. 그 판단은 후보와 원본 Evidence를 본 탐색·분석 단계의 몫이다.

| 선택지 | 실제로 생기는 문제 | 채택 여부 |
|---|---|---|
| 모든 Signal을 한 Window로 수집 | 무관한 시간대가 포함되어 결정적 trace가 수집 상한에 밀림 | 미채택 |
| 시간 근접만으로 병합 | 동시 발생한 서로 다른 장애를 하나의 인과로 단정 | 미채택 |
| 정적 서비스 토폴로지로 병합 | 시스템 지식을 코드에 심어 평가의 정답을 누출 | 미채택 |
| 서비스·자원·지문·시간 공백으로 후보화 | 인과는 보류하되 재현 가능한 선택지를 유지 | 채택 |

### 후보를 만드는 규칙

후보는 코드가 다음 순서로 만든다.

1. `채널 | 리소스 | 지문` 세 축으로 먼저 분리한다.
2. 같은 축 안에서만 60초 이상 떨어진 구간을 나눈다. 이때 직전 시작점이 아니라 지금까지의 가장 늦은 끝점(`reach`)을 비교한다.
3. Tempo 후보끼리 traceId가 실제로 겹칠 때만 병합한다.
4. 시각만 겹치는 후보는 인과로 단정하지 않고 `related`로만 표시한다.

시간을 군집 키에 넣지 않아 교차 장애가 시간순으로 섞여도 서로 다른 서비스·자원·지문은 합쳐지지 않는다. 반대로 시간만 겹친 `mongodb_up=0`과 Kafka lag 상승을 코드가 합치지 않은 이유도 같다. “chat이 Mongo를 쓴다”는 정적 토폴로지를 코드에 넣는 순간 평가 대상의 정답을 심게 되기 때문이다.

| 채널 | Signal의 정의 | 보존하려는 의미 |
|---|---|---|
| Tempo | 검색에 걸린 trace의 존재 | 오류와 지연, traceId |
| Loki | 0이 아닌 5분 버킷 | 해당 기간의 로그 발생량 |
| Mimir | 0 구간·값 변화·결측 | 상태 저하와 추세 변화 |

`lag=0`처럼 정상일 수 있는 값은 이상 신호 목록에서 제외했다. 실제로 모든 정상 파티션의 0을 후보로 만들었을 때 36개 신호가 한 후보에 붙어 조사 창이 스윕 전체로 늘어났고, 결정적 트레이스가 수집 상한에 밀렸다. 이 사례를 통해 “더 많이 검출”보다 **의미 있는 후보를 잃지 않는 구조**를 우선했다.

### 실제 재생: 42개 신호를 13개 조사 단위로

CH-1 회차 5b의 저장 스윕을 재생했다.

```text
TEMPO 20개 + LOKI 12개 + MIMIR 10개 = Signal 42개
  → 라벨 축 분리 8통
  → 시간 간격 분할·traceId 병합
  → Incident 후보 13개
```

이 결과에서 같은 `security filterchain` 지연 13건이 `30,012~30,025ms`라는 한 줄의 지문으로 접혔다. 편차 12ms의 반복적인 30초 지연은 timeout 상한이라는 패턴을 드러냈고, 07:5x와 08:2x에 같은 지문이 재발한 것도 보존됐다. 반복을 지우는 대신 횟수·시각 범위·평균 간격으로 접은 이유다.

## 해결 3: 분석 LLM에 원인까지 닿는 Evidence를 전달했다

탐색 이후에는 선택된 범위의 원본을 수집한다. 이 단계의 병목은 신호 부족이 아니라 **이미 있는 정보를 잘라 버리거나 구조 없이 나열하는 것**이었다.

### 로그: 예외 헤더에서 실제 코드 위치까지

AP-2의 실제 원인은 `FollowCondition.java:25`였지만, 기존 LogQL은 ERROR/WARN 헤더만 가져왔다.

```text
ERROR FollowService : 팔로우 목록 조회 실패  ← 기존에도 수집
java.lang.NullPointerException               ← 기존에는 누락
    at FollowCondition.java:25               ← 실제 원인, 기존에는 누락
```

분석용 쿼리에 `Exception`, `Caused by`, `.java:<line>` 패턴을 추가해 stack line도 수집하게 했다. 탐색 집계에는 같은 변경을 적용하지 않았다. 예외 하나가 수십 개 stack line으로 세어져 발생량 곡선을 왜곡하기 때문이다. 동일 데이터라도 단계별 목적에 따라 쿼리를 분리한 사례다.

또한 Loki를 “창 전체 ERROR/WARN”과 “선택 traceId 일치”로 두 번 조회하면서 생기던 중복을 `(timestamp, line)` 기준으로 접었다. 실제 조사에서 4줄, traceId 조회 채널 기준 27%(약 1.6KB)가 중복이었지만, 한쪽 조회를 제거하지는 않았다. traceId 없는 장애 로그와 INFO 기반 요청 서사를 잃지 않기 위해서다.

### Trace: span 목록을 인과 추론 가능한 호출 그래프로

Tempo의 span에는 `parentSpanId`, `db.system`, `messaging.system`, `client.name`이 있었지만, 이전에는 이를 시간순 목록으로 전달했다. 모델이 서비스 관계를 추정해야 했고, AU-4에서는 정답에 도달하고도 근거가 약해 확신도가 낮아졌다.

그래프 추출 규칙은 메시지·DB·JDBC·클라이언트·부모 span 순으로 판별한다. `peer.service`는 마지막 수단으로만 사용한다. JDBC span의 `peer.service=content`를 서비스 호출로 오인하면 `content-service → content-service`라는 가짜 간선이 생기는 것을 저장 트레이스 17개 전수 검증에서 발견했기 때문이다.

```text
content-service → kafka/user.notifications       publish, 최대 16.6ms
kafka/user.notifications → chat-service          receive, 최대 30,108ms
  error: MongoSocketOpenException / Connection refused
chat-service → kafka/user.notifications.dlq      publish, 최대 1,300ms
chat-service → mysql/content                     jdbc, 최대 30,021ms
```

28개 span을 6개의 관계 요약으로 압축한 뒤에도 원본 span은 함께 보존했다. 요약은 원본의 대체물이 아니라 분석의 출발점이다. 검증 과정에서는 죽은 서비스가 span을 남기지 않아 부모 관계만으로는 간선이 사라지는 문제도 발견했고, `client.name` 기반의 보완 규칙을 추가했다. 반대로 MongoDB span은 17개 트레이스에서 0건으로 확인돼, 그래프가 모든 의존성을 보여 준다는 주장도 철회했다.

## 탐색 비용을 줄이되 판단 근거는 잃지 않았다

탐색 LLM의 산출은 후보 선택인데, 스윕 원본 JSON이 컨텍스트의 약 94%(38,445B 중 약 36KB)를 차지하고 있었다. 기본값을 `rca.survey.include-raw=false`로 바꾸고 후보 목록·채널별 도달 요약만 전달했다.

저장 스윕 A/B 재생 결과는 45,991자에서 7,697자로 83% 감소했고, 선택 후보(INC-7~15), 기각 후보(INC-1~6), 좁힌 창, 대표 traceId, 대상 서비스가 일치했다. 다만 표본은 1개 창이고 트레이스가 없는 문항에는 검증되지 않았다. 그래서 “토큰을 줄여도 항상 품질이 같다”가 아니라 **이 재생 범위에서는 원본 JSON이 후보 선택의 필수 근거가 아니었다**고만 결론 내렸다.

추가로 Tempo 검색 응답에 이미 있던 `serviceStats`를 파싱해 후보 설명에 관여 서비스를 붙였다(B-44). 645개 트레이스 중 52개가 두 개 이상 서비스에 걸쳐 있었지만, 별도 API 호출 없이 후보 13개·신호 42개는 그대로 유지됐다. 설명 증가분은 후보 2건에 124자(약 1.6%)였다.

로그 예외 클래스별 후보 분리(B-45)도 구현했으나 기본값은 껐다. 실제 Loki에서 164건 중 예외 클래스를 제대로 얻은 비율이 4.3%에 그쳤고, 한 다른 창에서는 552건 전부가 0%였다. 헤더 라인만 ERROR/WARN 필터를 통과하고 예외 클래스는 다음 stack line에 있기 때문이다. “구현했으니 켠다” 대신, **도달률이 낮아 후보만 과분할하는 기능은 비활성화**했다.

## 상세 기록: 관측 신호가 후보가 되는 과정

위 구조가 실제로 어떤 정보를 보존하는지, CH-1 회차 5b의 저장 응답으로 따라가 보았다. 이 섹션은 단순한 알고리즘 소개가 아니라, 후보화 규칙이 어떤 종류의 오판을 막는지 검증한 기록이다.

### 1. Tempo: 한 trace를 하나의 시간 구간으로 읽는다

Tempo 검색 결과의 한 행은 trace 하나에 대응한다. Signal에는 시작 시각, 종료 시각(시작+duration), 루트 서비스·이름, traceId를 넣는다. 오류와 지연 검색은 분리된 채널이므로 같은 엔드포인트라도 합치지 않는다.

```text
content-service  POST /.../comments  8,485ms   slow 채널
content-service  POST /.../comments 31,370ms   error 채널
```

CH-1에서 두 trace는 같은 댓글 API지만 5분 간격으로 서로 다른 채널에 나타났다. 후보를 하나로 합치면 “8.5초 지연이 31초 오류보다 먼저 나타났다”는 열화 순서를 잃는다. 그래서 탐색 LLM은 둘을 별개 후보로 받고, 필요하면 선행 신호와 결과로 해석한다.

### 2. Loki: 버킷 시각을 사건 시각으로 오해하지 않는다

Loki의 `count_over_time(...[5m])` 값은 그 시점 직전 5분 동안의 건수다. 예를 들어 `07:55`의 42건은 정확히 07:55에 42건이 발생했다는 뜻이 아니다. 따라서 Loki Signal의 시작은 버킷 시각이 아니라 `버킷-5분`으로 잡는다.

```text
잘못된 해석: 07:55에 ERROR/WARN 42건
올바른 구간: 07:50~07:55 사이 ERROR/WARN 42건
```

이 처리가 없으면 로그 후보가 실제 사건보다 최대 5분 뒤에 놓이고, Tempo·Metric 후보와의 시간 관계도 왜곡된다. 반대로 로그 집계에는 traceId가 없으므로 다른 채널의 후보와 시간만으로 병합하지 않는다.

### 3. Mimir: 값의 크기 대신 상태 변화를 Signal로 만든다

Mimir는 시리즈마다 `0 구간`, `값 변화`, `결측`을 별도 검출기로 읽는다. 어떤 값이 “얼마 이상이면 장애”라는 문항별 임계값은 두지 않았다. 평시 baseline이 없는 환경에서 고정 임계값은 불안정하고, 평가 문항에 맞춘 수치를 코드에 넣으면 정답 유출이 되기 때문이다.

다만 0이 곧 이상이라는 규칙도 모든 지표에 적용하지 않았다. `mongodb_up=0`, `kafka_brokers=0` 같은 상태 지표는 의미가 있지만 `kafka_consumergroup_lag=0`은 정상이다. 이 구분을 하지 않았을 때 정상 파티션 36개가 각각 60분짜리 Signal이 되었고, 후보 하나가 스윕 창 전체로 팽창했다. CH-1 회차 3에서는 컨텍스트가 363,268자·$2.78까지 커져 정답 trace가 수집 상한에 밀렸다.

### 4. 군집: 합치는 것보다 되돌릴 수 있는 분리를 택한다

후보를 만들 때 시간 근접만으로 모든 신호를 합치면 읽기에는 편해 보이지만, 잘못 합쳐진 뒤에는 어떤 신호가 원인이었는지 복구하기 어렵다. 반면 애매한 신호를 나눠 두면 선택되지 않은 후보가 목록에 남는다. 이 비대칭 때문에 군집 규칙은 보수적으로 설계했다.

```text
1) channel | resource | signature으로 분리
2) 같은 키 안에서만 60초 gap으로 분할
3) Tempo 후보끼리 공유 traceId가 있을 때만 병합
4) 시간 겹침은 related 표기만 하고 병합하지 않음
```

60초 분할은 단순히 바로 앞 Signal의 시작 시각을 비교하지 않는다. Signal은 점이 아니라 구간이므로, 현재까지 가장 늦은 종료 시각과 다음 Signal의 시작을 비교한다. 긴 Loki 구간이 이어지는 상황에서 시작 시각만 보면 실제로 겹치는 Evidence를 둘로 잘라 버리기 때문이다.

### 실제 결과: 42개의 신호가 13개의 조사 후보가 되기까지

```text
Signal 42개
  Tempo 20개: comment slow/error, chat filterchain 지연, root span 누락
  Loki  12개: content/auth/chat ERROR-WARN 발생량
  Mimir 10개: mongodb_up 변화, Kafka lag 변화

라벨 축으로 8개 통 생성 → 시간 분할 → traceId 병합 0건 → Incident 13개
```

최종 후보는 다음 13개다. 크기가 큰 후보만 남기거나, 시간상 가까운 후보를 임의로 합치지 않았다. 1건짜리 Signal도 원인이 될 수 있고, 같은 시간의 인프라 변화와 애플리케이션 오류는 인과가 확인되기 전까지 별도 조사 단위로 남겨야 하기 때문이다.

| 후보 | 채널 | 리소스 · 지문 | 구간 | 접힌 Signal |
|---|---|---|---|---:|
| INC-1 | Loki | content-service · ERROR/WARN | 07:30~07:55 | 5 |
| INC-2 | Loki | auth-service · ERROR/WARN | 07:40~07:45 | 1 |
| INC-3 | Loki | chat-service · ERROR/WARN | 07:40~08:00 | 4 |
| INC-4 | Mimir | mongodb · `mongodb_up` | 07:48~08:03 | 3 |
| INC-5 | Mimir | kafka · consumer lag | 07:48~08:03 | 4 |
| INC-6 | Tempo | content-service · 댓글 API 8,485ms slow | 07:52:24 | 1 |
| INC-7 | Tempo | chat-service · `security filterchain before` 약 30초 | 07:52~07:55 | 13 |
| INC-8 | Tempo | content-service · 댓글 API 31,370ms error | 07:57:12 | 1 |
| INC-9 | Loki | content-service · ERROR/WARN | 08:10~08:15 | 1 |
| INC-10 | Mimir | kafka · lag `0→24→25→0` | 08:13~08:28 | 3 |
| INC-11 | Loki | chat-service · ERROR/WARN | 08:20~08:25 | 1 |
| INC-12 | Tempo | chat-service · `security filterchain before` 22/14/4초 | 08:22 | 3 |
| INC-13 | Tempo | 알 수 없음 · `<root span not yet received>` | 08:22 | 2 |

표의 분리는 의도한 관측 보존 규칙을 보여 준다.

- INC-4와 INC-5는 정확히 같은 시간대지만 `mongodb_up`과 Kafka lag의 인과를 코드가 알 수 없으므로 병합하지 않았다.
- INC-6과 INC-8은 같은 댓글 API지만 slow/error 채널과 시각이 달라 분리했다. 이 차이가 “열화 후 오류”라는 해석의 근거가 된다.
- INC-7과 INC-12는 지문이 같아도 약 27분 떨어진 별도 에피소드라 나뉜다. 합치면 재발이 사라진다.
- INC-13은 깨진 루트 이름이라도 버리지 않는다. 데이터 품질 문제 자체가 조사에 필요한 사실이며, 후보가 되지 못한 trace는 별도로 도달 요약에도 남긴다.

특히 chat의 `security filterchain before` 지연 13건은 `30,012~30,025ms`로 접혔다. 접기는 원본을 삭제하는 기능이 아니라, `횟수·시각 범위·평균 간격`을 보존해 반복 패턴을 읽게 하는 표현 방식이다. 12ms 편차로 반복되는 30초는 timeout 상한의 강한 지문이었고, 07:5x와 08:2x의 두 에피소드가 합쳐지지 않아 재발도 확인할 수 있었다.

## 상세 기록: Evidence 품질을 검증하며 수정한 설계

### 호출 그래프 규칙은 저장 트레이스에서 두 번 반증됐다

처음 설계는 `parentSpanId`만 있으면 서비스 경계를 복원할 수 있다고 봤다. 저장 트레이스 17개를 전수 확인하면서 이 가설은 두 곳에서 틀렸다.

| 발견 | 왜 원안이 실패했나 | 수정 |
|---|---|---|
| 상대 서비스가 죽은 경우 | 상대 서비스는 span을 남기지 못하므로 부모 관계만으로 간선이 사라짐 | 호출 측 span의 `client.name`을 보완 근거로 사용 |
| Kafka receive 토픽명 | receive span은 `messaging.destination.name`이 아닌 `messaging.source.name`에 토픽이 있음 | 속성 판별 규칙 분리 |
| MongoDB 관측 | MongoDB span이 있을 것이라는 가정 | 17개 트레이스에서 0건. receive span의 error 텍스트만 근거로 사용한다고 한계 명시 |

`peer.service`는 가장 마지막에만 사용했다. 저장 트레이스 288건에서 JDBC span의 `peer.service=content`는 서비스명이 아니라 MySQL DB 이름이었다. 이를 우선 사용했으면 `content-service → content-service`라는 자기참조 간선을 대량으로 만들었을 것이다. 그래서 그래프의 노드도 모호한 이름 대신 `mysql/content`, `redis`, `kafka/<topic>`처럼 시스템과 대상을 분리해 표기했다.

### 탐색 단계의 경유 서비스 정보는 “이미 있던 데이터”에서 찾았다

B-44의 첫 가정은 상·하류 서비스를 보려면 span 원문을 추가로 조회해야 한다는 것이었다. 하지만 Tempo `/api/search` 원본을 살펴보니 이미 `serviceStats`가 있었다.

```json
{
  "rootServiceName": "content-service",
  "serviceStats": {
    "auth-service": {"spanCount": 4},
    "chat-service": {"spanCount": 14},
    "content-service": {"spanCount": 28}
  }
}
```

저장된 검색 결과 645건 중 52건이 두 서비스 이상을 지났지만, 기존 파서는 이 필드를 읽지 않았다. 새 쿼리·추가 API 호출·추가 토큰 없이 후보 설명에 관여 서비스와 에러 span 수를 덧붙였다. 다만 군집 키에는 넣지 않았다. 같은 엔드포인트가 통과한 서비스 조합별로 후보가 쪼개져, 후보 수가 바뀌면 개선의 인과를 검증할 수 없기 때문이다.

CH-1 5b 재생에서 Signal 42개와 후보 13개는 그대로였고, 후보 두 건의 설명에 총 124자만 추가됐다. 그중 31,370ms 오류 trace의 에러 10건이 루트 서비스(content)가 아니라 chat에서 발생했다는 정보를 탐색 단계에 처음 전달할 수 있었다. 이 정보가 실제 탐색 선택을 바꾸는지는 별도 실험 대상이며, 아직 점수 효과로 주장하지 않는다.

### 로그 지문은 구현보다 관측 도달률이 먼저였다

B-45에서는 Loki 로그를 `ERROR/WARN` 하나로 뭉치지 않고 예외 클래스별로 후보화하려 했다.

```text
기존: chat-service | ERROR/WARN                    23건
의도: chat-service | QueryTimeoutException         19건
      chat-service | MongoSocketOpenException        4건
```

코드는 `exc` 라벨이 오면 후보를 분리하고, 지문 쿼리가 비면 기존 총 건수로 되돌아가도록 구현했다. 그러나 라이브 Loki에서 헤더 기반 정규식의 진짜 예외 클래스 포착률은 164건 중 7건(4.3%)뿐이었다. ERROR/WARN은 헤더 줄에, 예외 클래스는 다음 stack line에 있어 같은 라인 필터를 동시에 만족시키지 못했기 때문이다.

이 기능은 “테스트가 통과했으니 활성화”하지 않았다. 도달하지 않는 라벨로 후보 수만 늘리면 `incidentLimit`에 걸려 다른 Tempo 후보가 잘릴 수 있다. 기본값을 비활성화하고, 앱 로그에 예외 클래스를 헤더에 남기거나 Alloy multiline을 적용하거나 별도의 라인 조회를 추가하는 선택지를 후속 과제로 남겼다.

## 관측 데이터가 아예 없는 경우: 앱 계측으로 공백을 만들지 않았다

앞 절의 개선은 Loki·Tempo·Mimir에 이미 있는 데이터를 더 잘 읽는 작업이었다. 하지만 AU-4에서는 데이터가 존재하지 않는 것이 진짜 문제였다. auth-service가 22분간 장애였지만 content-service가 사용자 조회 실패를 익명 사용자 fallback으로 흡수해 HTTP 200을 반환했다. 사용자 10명은 기능 저하를 겪었지만 에러율과 HTTP 상태만 보면 정상으로 보였다.

| 채널 | 기존 상태 | 왜 RCA가 원인을 찾을 수 없었나 |
|---|---|---|
| HTTP/Trace | HTTP 200 | 실패가 성공 응답으로 가려짐 |
| Loki | fallback 접두사 3종 혼용 | 하네스 검색이 0건이라고 오판 |
| traceId | Reactor callback에서 MDC 미전파 | 로그가 `traceId=NONE`으로 남아 요청과 연결 불가 |
| Metric/Alert | fallback 집계 없음 | 저하량을 추세·알람으로 볼 수 없음 |

이를 다음 세 가지로 보강했다.

```text
[user-fallback] 접두사 통일  → Loki가 본문 문구가 아니라 규약으로 검색
MDC 캡처·복원                → fallback 로그를 원 요청의 traceId와 연결
user_fallback_total          → rate(...) > 0 기반 Metric·Alert 생성
```

전역 Reactor 컨텍스트 훅 대신 해당 경로에서만 MDC를 캡처·복원했다. 전역 훅은 앱 전체 로그 동작을 함께 바꾸므로 효과의 귀속 범위를 알 수 없기 때문이다. 같은 로그 규약은 content 88개, chat 225개, auth 99개, 총 98개 파일의 412개 로그 지점에 확산했고 컴파일·테스트를 통과했다. 다만 아직 배포 전이므로, 이 변경의 효과는 AU-4를 다시 주입한 뒤에만 주장할 수 있다.

### 서비스별 로그의 역할도 다시 정의했다

관측 공백을 메우는 동시에 과잉 로그도 줄여야 했다. content는 한 시간 2,300줄 가운데 ERROR/WARN이 8줄뿐이었고, 나머지 성공 요청 로그는 Tempo trace와 거의 중복됐다. 반대로 chat은 요청 로그가 없어 401·500도 남지 않았으며, auth는 JWT 검증 실패가 일부 무로그 경로로 끝났다.

```text
성공 요청                 → Tempo trace
4xx / 5xx                 → Loki log
1초 초과 요청             → Loki log
집계·추세·알람            → Metric
```

여기서 “content 로그를 줄여 토큰을 절감했다”라고 주장하지 않았다. 에이전트의 기존 Loki 탐색 자체가 ERROR/WARN 필터였으므로, 성공 INFO 2,292줄 대부분은 애초에 분석 컨텍스트로 들어오지 않았다. 이 변경의 효과는 토큰 절감이 아니라, 세 서비스가 같은 관측 책임을 갖도록 만든 것이다.

## 분석 수집 범위: 절약보다 원인 판별에 필요한 맥락을 우선했다

후보를 여러 개 선택했을 때 모든 채널을 하나의 합집합 시간창으로 수집하면 후보 사이의 빈 구간까지 원본을 긁게 된다. 예를 들어 08:49의 INC-5와 09:12의 INC-6을 함께 분석할 때, 사이 15분에 Signal이 없는데도 로그·trace를 계속 수집하면 무관한 데이터가 상한을 차지한다.

하지만 모든 채널을 똑같이 자르면 안 된다.

| 수집 대상 | 창 정책 | 이유 |
|---|---|---|
| ERROR/WARN 로그 | 후보별 분할 | 점 사건이므로 빈 구간의 정보량이 낮음 |
| 후보 trace 검색 | 후보별 분할 | 무관한 trace가 수집 한도를 차지하지 않게 함 |
| Mimir 메트릭 | 합집합 유지 | 후보 사이에 정상으로 회복했는지라는 시계열 맥락이 필요 |

가장 많이 절약할 수 있는 메트릭을 오히려 분할하지 않은 이유가 여기에 있다. 비용만 최적화하면 “장애 뒤 회복했는가”를 잃어 원인 분석이 약해진다. 따라서 절약은 로그·trace에서 하고, 상태 변화가 중요한 메트릭은 연속성을 보존했다.

분석 컨텍스트의 절 순서도 Evidence의 성격에 맞췄다.

```text
# 조사 대상 / 수집 실패·누락
# 호출 그래프 (관계 요약)
# 선택 trace 원본 / 창 안 후보 trace
# ERROR/WARN 로그 (stack 포함)
# traceId 일치 로그 (중복은 접기)
# 메트릭 시계열
```

수집 실패나 누락을 숨기지 않고 맨 앞에 둔다. “로그가 없었다”가 정상의 증거인지, 조회 실패인지, trace가 늦게 도착한 것인지 모델과 검토자가 구별할 수 있어야 하기 때문이다.

## 검증 방식과 현재 상태

변경마다 구현 여부와 효과를 구분했다. 테스트 통과는 변환 규칙의 재현성을 뜻할 뿐, RCA 점수 향상을 뜻하지 않는다.

| 항목 | 상태 | 검증 범위 |
|---|---|---|
| slow trace, 구간 집계, Signal→Incident | 적용 | 저장 스윕·단위 테스트 |
| 인프라 scrape 10초 | 적용 | 샘플 밀도 증가 확인, 실제 23초 다운 포착은 미검증 |
| 원본 JSON 제외 | 적용 | 재생 A/B 1건에서 선택 결과 동일 |
| 스택트레이스 수집·호출 그래프·로그 중복 접기 | 적용 | 픽스처·저장 트레이스·단위 테스트, 점수 효과 미측정 |
| 후보별 로그/트레이스 창 분할 | 코드 반영 | 전체 실행 미수행 |
| B-44 서비스 경유 정보 | 적용 | 후보·신호 수 불변 재생 확인 |
| B-45 로그 지문 | 코드 반영, 기본 비활성 | 라이브 도달률 측정 결과 효과 없음 |
| 요청 로그 정리·익명 폴백 메트릭 | 코드 반영, 미배포 | 컴파일·테스트 통과, 배포 후 장애 주입 필요 |

다음 검증은 명확하다. 10초 scrape 환경에서 CH-3와 같은 23초 장애를 다시 주입해 `mongodb_up=0`이 남는지 확인하고, 스택트레이스·호출 그래프를 포함한 전체 파이프라인으로 AP-2/AU-4를 재조사한다. 개선이 실패하더라도 원인을 다음 층으로 좁힐 수 있게 반증 조건을 함께 남겼다.

| 변경 | 기대와 다른 결과가 나오면 알 수 있는 것 |
|---|---|
| short outage가 여전히 안 잡힘 | 쿼리 문제가 아니라 exporter의 상태 반영 또는 관측 자체의 문제 |
| stack line이 있어도 원인이 안 나옴 | Evidence 누락이 아니라 분석 추론·프롬프트의 문제 |
| 그래프가 있어도 AU-4가 개선되지 않음 | 관계 정보의 존재가 아니라 배치·표현 방식의 문제 |
| 경유 서비스가 보여도 후보 선택이 불변 | 정보량이 아니라 탐색 프롬프트의 문제 |

## 문제 해결 역량으로 남긴 원칙

1. **실패한 가설도 결과로 남긴다.** 창 확장은 효과가 없었고, 구간 집계만으로는 부족했으며, 로그 지문 분리는 도달률 부족으로 비활성화했다.
2. **증거 생성과 추론을 분리한다.** 코드가 재현 가능한 후보 공간을 만들고, LLM은 그 안에서 판단한다.
3. **정보를 많이 넣는 대신, 의사결정에 맞게 가공한다.** 탐색에는 후보와 요약을, 분석에는 원본과 관계 정보를 준다.
4. **정답을 코드에 심지 않는다.** 정적 토폴로지, 시간 근접만의 인과 병합, 문항별 임계값을 피하고 관측된 사실만 구조화한다.
5. **효과와 구현을 혼동하지 않는다.** 적용·재생 검증·점수 향상·배포 후 관측을 별도의 상태로 관리한다.

이 개선의 목표는 한 번의 데모 성공이 아니라, 장애를 놓쳤을 때 “모델이 못 맞혔다”로 끝내지 않고 어느 관측 계층에서 정보가 사라졌는지 다시 추적할 수 있는 RCA 시스템을 만드는 것이었다.
