# DLQ 재처리 로그에 traceId가 없던 이유 — 설정 한 줄

Mongo 다운 → DLQ 문항(CH-1)이 **97.5점**입니다. 깎인 5점이 *"유실인가 지연인가"* 판정이었고,
그 판정에 필요한 로그가 컨텍스트에 도착하지 않았습니다.

---

## 무엇이 없었나

에이전트는 **실패 절반만** 받았습니다.

| 로그 | 수집됐나 |
|---|---|
| `[Kafka] DLQ 알림 재처리 실패` | **1건 도착** (ERROR라 라인 필터에 걸린다) |
| `[Kafka] DLQ 알림 재처리 성공` | **0건** |

그래서 *"영구 유실이라고 단정할 수 없다"* 까지는 갔지만 **도착을 확정하지 못했습니다.**
(에이전트는 `lag 1→0` 이라는 동치 경로로 우회해 다른 실행에서는 만점을 받았습니다.
다음에도 우회로가 있으리라는 보장은 없습니다.)

## 왜 안 걸렸나 — 두 겹으로 막혀 있었다

```
INFO [traceId=NONE] c.e.t.NotificationConsumer : [Kafka] DLQ 알림 재처리 성공
     ^^^^^^^^^^^^^^ ^^^^
     traceId 없음    INFO
```

| 쿼리 | 왜 안 걸리나 |
|---|---|
| `\|~ "ERROR\|WARN\|..."` | **INFO다.** 도착·복구·성공은 본질적으로 INFO다(실패만 ERROR로 찍힌다) |
| `\|= "<traceId>"` (레벨 필터 없음) | **traceId가 `NONE`이다.** 에이전트가 가진 traceId와 매칭되지 않는다 |

**레벨 무관 쿼리가 이미 있었는데도 못 찾았습니다.** traceId가 없어서입니다.

## 원인 — 설정 플래그 하나가 빠져 있었다

`toy-chat`의 Kafka 리스너 팩토리 **6개 중 5개**에 이게 있었습니다.

```java
factory.getContainerProperties().setObservationEnabled(true);
```

`notificationDlqListenerFactory` **하나만** 없었습니다. 그리고 이 값의 **기본값이 `false`** 라서
명시하지 않으면 조용히 빠집니다.

같은 파일의 다른 팩토리 주석에 그 의미가 이미 적혀 있었습니다 —
*"producer가 헤더에 실어 보낸 trace 컨텍스트를 꺼내 consume span을 만든다 **(기본값 false)**"*.

```
observationEnabled = true   →  헤더의 trace context 추출 → consume span 생성
                            →  그 scope 안에서 MDC에 traceId 주입
                            →  로그에 [traceId=6a68…]

observationEnabled = false  →  span도 scope도 없음
                            →  MDC 비어 있음
                            →  [traceId=NONE]
```

## 무엇을 고쳤나

그 한 줄을 추가했습니다. 팩토리 6개 전부가 같은 설정이 됐습니다.

**컴파일 통과.** 배포는 아직입니다.

---

## 레벨을 WARN으로 올리는 안은 기각했다

*"복구 로그를 WARN으로 찍으면 기존 필터에 걸린다"* 는 방향을 검토했고 세 이유로 기각했습니다.

| | |
|---|---|
| **오염** | 채점 앵커가 그 로그를 요구하는데, **잡히게 하려고 레벨을 올리면** 순환논증이다. 채록에 프로브를 심는 안을 철회한 것과 같은 계열 |
| **오귀인 재료** | 에이전트는 WARN을 이상 신호로 읽는다. **성공을 이상으로 표시**하면 노이즈가 된다 |
| **운영에서 되돌아온다** | WARN 이상 알림을 걸어두면 복구할 때마다 알람이 울리고, 진짜 WARN이 그 안에 묻힌다 |

관례로 갈라보면 이렇습니다.

| 이벤트 | 맞는 레벨 |
|---|---|
| DLQ로 **보냈다** | WARN — 정상 경로가 아니다 (이미 ERROR로 찍힌다) |
| 재처리 **실패** | WARN 또는 ERROR (이미 그렇다) |
| 재처리 **성공** | **INFO** — 성공이다 |

**CH-1이 필요한 건 세 번째**이므로, 이 문항에서는 레벨 올리기가 관례상으로도 맞지 않습니다.

## 결말 어휘 추가(B-16 안 가)도 불필요해졌다

`|~ "...|재처리|복구"` 로 라인 필터를 늘리는 안이 있었는데, **한국어 문자열에 의존**하는 게
약점이었습니다. traceId가 붙으면 기존 `traceIdQuery`로 걸리므로 그 안은 필요 없어집니다.

---

## 완전히 풀리는지는 배포 후에 확인해야 한다

`traceId=NONE`은 확실히 사라집니다. 다만 **어느 traceId가 붙는지**가 남습니다.

`DeadLetterPublishingRecoverer`는 원본 record 헤더를 복사하므로 trace 헤더도 같이 갈
가능성이 높고, 헤더를 걷어내는 설정(`setHeadersFunction` 등)은 없습니다. 그런데
`KafkaTemplate`에도 `setObservationEnabled(true)` 가 걸려 있어 **발행 시점에 새 컨텍스트를
심을 수 있습니다.** 코드만 봐서는 어느 쪽이 이기는지 확정할 수 없습니다.

| 결과 | CH-1에 대한 의미 |
|---|---|
| **원본 traceId가 이어진다** | 원 요청 → DLQ 재처리가 **한 트레이스**. `traceIdQuery`로 그대로 걸린다 → **완전 해결** |
| **새 traceId가 생긴다** | `NONE`은 아니지만 에이전트가 가진 traceId와 다르다 → **부분 해결.** 그때는 결말 어휘 추가가 다시 필요하다 |

## 부수 이득

지금 **DLQ 재처리 구간이 트레이스에서 통째로 비어 있을 것**입니다. 이 플래그를 켜면 그 구간에
consume span이 생겨 *"복구가 언제 됐나"* 를 트레이스로도 볼 수 있게 됩니다.

## 검증 절차 — 배포 후 CH-1 한 번 주입

1. `DLQ 알림 재처리 성공` 로그에 `[traceId=...]` 가 붙는가
2. 그 traceId가 **원 요청과 같은가**
3. 트레이스에 DLQ 재처리 span이 보이는가

**기존 데이터로는 검증되지 않습니다** — 이미 `traceId=NONE`으로 저장돼 있습니다.
