# RCA 에이전트 장애 미탐지 원인 분석 및 탐색 구조 개선

> **이 문서는 기록입니다.** 통합본이 SoT입니다 → [관측개선-통합.md](관측개선-통합.md)
> (탐색 LLM 앞/뒤로 나눠 네 문서를 합쳤고, B-45 결론은 통합본이 최신입니다.)

## 문제 상황

RCA 에이전트 검증 과정에서 TimeParser가 생성한 초기 분석 시간 범위(04:50~05:50) 내에 실제 장애 주입 구간(05:22:01~05:22:38)이 포함되어 있었음에도 원인을 도출하지 못하는 문제가 발생했습니다. 분석 결과, LLM은 초기 범위 내 존재하던 MongoDB 장애 및 서비스 오류 증가 신호를 기반으로 조사 Window를 04:57~05:22로 축소했고, 이 과정에서 장애 발생 1초 전 종료되어 실제 장애 신호가 제외되었습니다. 처음에는 Window 확대가 해결책이라고 판단했지만, 2.26배 확장 실험에서 Context는 72%, 비용은 39% 증가했음에도 RCA 성능은 개선되지 않았습니다. 이후 Trace·Metric·Log를 채널별로 역추적한 결과, 해당 장애는 Error가 아닌 23초 지연 형태로 발생해 기존 Error Trace 탐색에서 누락되었고, Metric은 5분 단위 샘플링 간격 사이에서 장애 구간을 놓쳤으며, Log 역시 유의미한 이상 신호가 부족했습니다. 이를 통해 문제의 원인은 LLM 추론 성능이 아니라 탐색 단계에서 장애 후보를 생성할 Signal이 부족하고, 단일 후보 선택 구조로 인해 다른 가능성을 유지하지 못하는 구조적 한계임을 규명했습니다.

이를 해결하기 위해 단순히 조사 범위를 확대하는 방식이 아닌 Signal 기반 장애 후보 생성 구조로 RCA Pipeline을 재설계했습니다. 기존 Error Trace 중심 탐색에는 duration 기반 지연 Trace 탐색을 추가해 실패 없이 발생하는 성능 저하 장애를 탐지하도록 개선했고, 5분 단위 Metric 샘플링으로 누락되던 단기 장애는 min_over_time/max_over_time 기반 구간 집계 방식으로 보존하도록 변경했습니다. 또한 기존의 하나의 Window + 하나의 traceId 구조를 개선해 Signal → Incident 후보 → LLM 판단 → 분석 구조로 변경하고, 여러 장애 후보를 유지한 뒤 LLM이 근거 기반으로 선택하도록 설계했습니다. 이를 통해 장애를 놓친 원인을 데이터 부족이나 모델 성능 문제가 아닌 관측 신호 확보와 탐색 구조의 문제로 분리하고, 검증 가능한 RCA 구조로 개선했습니다.

---

# 원인 분석

Trace, Metric, Log 세 가지 관측 채널을 기준으로 장애 구간을 역추적했다.

## 1. Trace 탐색 문제

기존 Trace 탐색은 아래 조건만 사용했다.

```
status = error
```

하지만 해당 장애는 HTTP Error가 아닌 **23초 동안 발생한 지연 장애**였다.

따라서 요청 자체는 성공했지만 응답 시간이 증가하는 형태였고, 기존 Error Trace 탐색에서는 탐지되지 않았다.

확인 결과:

```
duration > 8s

→ 6a698e07...
→ duration 23,458ms
```

Slow Trace 조건에서는 실제 장애 Trace가 조회되는 것을 확인했다.

즉 기존 탐색 방식은 "실패한 요청"은 찾을 수 있었지만 "느려진 요청"은 찾을 수 없는 구조였다.

---

## 2. Metric 탐색 문제

기존 Metric 조회는 5분 단위 Sampling을 사용했다.

실제 장애:

```
05:22:01 ~ 05:22:38
(23초)
```

하지만 Metric 데이터는:

```
mongodb_up

05:20:09 = 1
05:25:09 = 1
```

으로 조회되었다.

즉 장애가 발생한 23초 구간이 Sampling Point 사이에 위치하면서 정상 상태로 관측되었다.

단순히 Sampling 주기를 줄이는 방법도 검토했지만, 스윕 범위가 긴 환경에서는 응답량이 급격히 증가하기 때문에 적절한 해결책이 아니라고 판단했다.

따라서 Sampling 주기는 유지하고 구간 내 상태를 보존하는 방식으로 변경하는 방향을 선택했다.

---

## 3. Log 탐색 문제

장애 발생 시점에는 의미 있는 ERROR/WARN 로그가 거의 발생하지 않았다.

따라서 Log 역시 단독 Signal로 장애 후보를 생성하기 어려웠다.

---

# 최종 원인

분석 결과 RCA 실패 원인은 다음 흐름으로 정리할 수 있었다.

```
관측 Signal 부족
        ↓
잘못된 장애 후보 생성
        ↓
LLM이 다른 장애 후보 선택
        ↓
잘못된 Window 생성
        ↓
원인 분석 실패
```

즉 LLM이 존재하는 데이터를 잘못 해석한 문제가 아니라, **LLM에게 전달되기 이전 단계에서 올바른 장애 후보가 만들어지지 않은 것이 핵심 원인**이었다.

---

# 개선 방향

기존 구조:

```
Signal 탐색
    ↓
하나의 장애 후보 선택
    ↓
분석
```

문제:

* 탐색 단계에서 후보가 하나로 고정됨
* 잘못 선택하면 이후 단계에서 복구 불가능
* Window 결정이 LLM 판단에 의존

---

개선 구조:

```
Signal 탐색
    ↓
Incident 후보 생성
    ↓
복수 후보 유지
    ↓
LLM 판단
    ↓
상세 분석
```

핵심 변경점은 **LLM이 장애 후보를 만드는 것이 아니라, 관측 데이터 기반으로 후보를 먼저 만들고 LLM은 판단 역할만 수행하도록 변경하는 것**이다.

---

# 개선 항목

## 1. Slow Trace 탐색 추가

기존:

```
status = error
```

변경:

```
status = error
+
duration 기반 탐색
```

목적:

* HTTP 오류 없이 발생하는 성능 저하 장애 탐지
* Error 장애와 Slow 장애를 별도 Signal로 유지

단일 Query로 합치지 않고 별도 탐색 후 후보 단계에서 병합한다.

이유:

"Error로 발견된 장애인지, 지연으로 발견된 장애인지" 자체가 장애 특성이기 때문이다.

---

## 2. 단기 장애 Metric 보존

기존:

```
metric step = 5m
```

문제:

5분 Sampling 사이에 발생한 짧은 장애 누락

변경:

```
up
mongodb_up
kafka_brokers

→ min_over_time()

lag
active_users

→ max_over_time()
```

목적:

* 상태 Metric은 낮아진 값 보존
* 누적 Metric은 증가한 값 보존

Sampling 개수는 유지하면서 구간 내 이상 상태를 보존한다.

---

## 3. Incident 후보 유지 구조

기존:

```
Window 1개
traceId 1개
```

문제:

동일 시간대 여러 장애가 존재해도 하나만 유지됨.

개선:

```
Signal
 ↓
Incident Cluster
 ↓
Incident 후보 여러 개
 ↓
LLM 선택
```

Incident 후보는 다음 기준으로 분리한다.

* 서비스(Resource)
* 장애 유형(Signature)
* 발생 시간 Gap

이를 통해 동시에 발생한 서로 다른 장애가 하나의 후보로 합쳐지는 문제를 방지한다.

---

# 결론

이번 분석을 통해 RCA 실패 원인을 모델 성능이나 Prompt 문제가 아닌 **탐색 단계의 관측 가능성과 후보 생성 구조 문제**로 정의했다.

개선 방향 역시 단순히 분석 범위를 확대하는 방식이 아니라,

```
관측 Signal 확보
        ↓
Incident 후보 생성
        ↓
조사 범위 결정
        ↓
원인 추론
```

순서로 Pipeline 구조를 변경하는 방향으로 재설계했다.

향후 개선 사항은 각 항목을 독립적으로 적용하며:

* 장애 후보 생성 여부
* RCA Score 변화
* Context 증가량
* 비용 변화

를 기준으로 효과를 검증할 예정이다.
