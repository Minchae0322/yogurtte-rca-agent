# 관측 데이터를 RCA Evidence로 정제


RCA 에이전트 검증 과정에서 TimeParser가 생성한 초기 분석 시간 범위(04:50~05:50) 내에 실제 장애 주입 구간(05:22:01~05:22:38)이 포함되어 있었음에도 원인을 도출하지 못하는 문제가 발생했습니다. 분석 결과, LLM은 초기 범위 내 존재하던 MongoDB 장애 및 서비스 오류 증가 신호를 기반으로 조사 Window를 04:57~05:22로 축소했고, 이 과정에서 장애 발생 1초 전 종료되어 실제 장애 신호가 제외되었습니다. 처음에는 Window 확대가 해결책이라고 판단했지만, 2.26배 확장 실험에서 Context는 72%, 비용은 39% 증가했음에도 RCA 성능은 개선되지 않았습니다. 이후 Trace·Metric·Log를 채널별로 역추적한 결과, 해당 장애는 Error가 아닌 23초 지연 형태로 발생해 기존 Error Trace 탐색에서 누락되었고, Metric은 5분 단위 샘플링 간격 사이에서 장애 구간을 놓쳤으며, Log 역시 유의미한 이상 신호가 부족했습니다. 이를 통해 문제의 원인은 LLM 추론 성능이 아니라 탐색 단계에서 장애 후보를 생성할 Signal이 부족하고, 단일 후보 선택 구조로 인해 다른 가능성을 유지하지 못하는 구조적 한계임을 규명했습니다.

이를 해결하기 위해 단순히 조사 범위를 확대하는 방식이 아닌 Signal 기반 장애 후보 생성 구조로 RCA Pipeline을 재설계했습니다. 기존 Error Trace 중심 탐색에는 duration 기반 지연 Trace 탐색을 추가해 실패 없이 발생하는 성능 저하 장애를 탐지하도록 개선했고, 5분 단위 Metric 샘플링으로 누락되던 단기 장애는 min_over_time/max_over_time 기반 구간 집계 방식으로 보존하도록 변경했습니다. 다만 이 집계만으로는 절반이었고, 재조사에서 **집계 아래 계층인 스크레이프 간격(30초)이 진짜 하한**임이 실측으로 드러나 인프라 exporter 간격을 10초로 낮춰 마무리했습니다(아래 문제 6). 또한 기존의 하나의 Window + 하나의 traceId 구조를 개선해 Signal → Incident 후보 → LLM 판단 → 분석 구조로 변경하고, 여러 장애 후보를 유지한 뒤 LLM이 근거 기반으로 선택하도록 설계했습니다. 이를 통해 장애를 놓친 원인을 데이터 부족이나 모델 성능 문제가 아닌 관측 신호 확보와 탐색 구조의 문제로 분리하고, 검증 가능한 RCA 구조로 개선했습니다.

RCA 에이전트를 검증하는 과정에서 장애 원인에 필요한 정보가 Loki와 Tempo에는 존재했지만, 현재 수집·가공 방식에서는 일부 정보가 분석 컨텍스트에 포함되지 않거나 관계 정보가 활용되지 않는 문제를 확인했습니다. 로그는 스택트레이스가 필터링되어 예외 원인이 누락되고 있었고, Trace는 Span 관계를 해석하지 않아 서비스 간 호출 구조를 복원하지 못했습니다. 이를 해결하기 위해 로그 수집 규칙과 Trace 표현 방식을 수정하여 기존 관측 데이터를 보다 완전한 Evidence로 활용할 수 있도록 개선했습니다.

## 문제

RCA 에이전트를 검증하면서 **장애에 필요한 관측 데이터가 없는 것이 아니라, Loki와 Tempo에 존재하는 데이터가 RCA가 분석할 수 있는 형태로 전달되지 않는 문제**를 발견했습니다.

실제 장애를 역추적한 결과 다음과 같은 문제가 확인됐습니다.

### 1. 로그 — 원인 정보가 잘려서 전달됨

팔로우 목록 NPE(AP-2)의 실제 원인은 `FollowCondition.java:25`였지만, 기존 LogQL은 `ERROR|WARN`이 포함된 헤더만 조회했습니다.

```logql
{service_name=~"..."} |~ "ERROR|WARN"
```

실제 로그는 여러 줄의 스택트레이스로 저장되어 있었기 때문에 다음과 같이 원인 정보가 누락됐습니다.

```text
ERROR FollowService : 팔로우 목록 조회 실패    ← 수집
java.lang.NullPointerException                  ← 누락
    at FollowCondition.java:25                  ← 누락 ★ 실제 원인
```

또한 스택 라인에는 `traceId`가 없어 traceId 기반 조회에서도 동일한 문제가 발생했습니다.

→ **예외는 관측되고 있었지만, RCA가 필요한 원인 정보까지 도달하지 못하는 상태였습니다.**

### 2. 로그 — 같은 정보가 중복 전달됨

로그 수집은

- 시간 범위의 `ERROR/WARN` 전체 조회
- 선정된 `traceId`의 전체 로그 조회

두 경로로 이루어졌습니다.

따라서 `ERROR`이면서 `traceId`도 존재하는 로그는 두 채널에 모두 포함됐습니다.

```text
Loki
 ├─ ERROR/WARN 조회 ─────┐
 │                       ├─ 동일 로그
 └─ traceId 조회 ────────┘
             ↓
       ContextAssembler
             ↓
       LLM에 중복 전달
```

실제 varchar 조사에서는 **동일 로그 4줄이 중복**됐고, traceId 채널 기준 약 **27%(1.6KB)**가 중복이었습니다.

한쪽 쿼리를 제거하면 traceId 없는 장애 로그 또는 INFO 기반의 요청 서사를 잃기 때문에, 두 채널은 유지하면서 **어셈블 단계에서 `(timestamp, line)` 기준으로 교집합만 제거**했습니다.

### 3. 로그 — 서비스마다 관측 기준이 달랐음

서비스별 로그 정책도 일관되지 않았습니다.

- content: 1시간 **2,300줄** 중 ERROR/WARN은 **8줄** → 성공 요청 로그 대부분이 Trace와 중복
- chat: HTTP 요청 로그 자체가 없어 **401/500도 기록되지 않음**
- auth: JWT 검증 실패 및 일부 예외 경로가 로그 없이 종료

이에 성공 요청은 Trace가 담당하고, **4xx/5xx 및 1초 초과 요청만 로그로 기록**하도록 기준을 통일했습니다.

```text
성공 요청 ──────────────▶ Tempo Trace
4xx / 5xx ──────────────▶ Loki
Slow > 1s ──────────────▶ Loki
집계/추세 ──────────────▶ Metric
```

### 4. Trace — 관계 정보가 있었지만 구조적으로 활용하지 못함

Tempo에는 `parentSpanId`, `db.system`, `messaging.system`, `client.name` 등의 관계 정보가 존재했지만 기존 RCA에는 Span이 **일렬 목록**으로 전달됐습니다.

```text
Span A
Span B
Span C
Span D
Span E
```

따라서 LLM이 `parentSpanId`와 timestamp를 직접 비교하며 서비스 호출 관계를 추론해야 했습니다.

이를 앱에서 먼저 관계를 해석하도록 변경했습니다.

```text
content-service
      │
      │ messaging
      ▼
kafka/user.notifications
      │
      │ messaging
      ▼
chat-service
      │
      ├── jdbc ──▶ mysql/content
      │
      └── db ────▶ redis
```

`parentSpanId`, `db.system`, `messaging.system`, `client.name` 등을 우선순위에 따라 판별해 **`출발 → 대상` Edge로 집약**하고, 각 Edge에 호출 횟수·최대 duration·error·rollback 등의 Evidence를 함께 붙였습니다.

원본 Span을 제거한 것이 아니라 **원본 Trace는 그대로 유지하면서 호출 그래프를 추가 컨텍스트로 제공**했습니다.

### 5. 애플리케이션 — 아예 관측 신호가 생성되지 않는 경우도 존재

AU-4에서는 `auth-service`가 22분간 장애였지만 `content-service`가 사용자 조회 실패를 익명 사용자로 fallback하여 HTTP 200으로 응답했습니다.

실제로 10명의 사용자가 저하됐지만:

```text
HTTP         → 200
Error Rate   → 정상
Fallback     → Metric 없음
```

로그 역시 접두사가 제각각이었고, Reactor 비동기 callback에서는 MDC가 전파되지 않아 실제 로그가 다음과 같이 기록됐습니다.

```text
ERROR [reactor-http-epoll-1]
[traceId=NONE,spanId=NONE,userId=NONE]
```

이를 애플리케이션에서 직접 보강했습니다.

```text
Fallback 발생
    │
    ├─ [user-fallback] 접두사 통일
    │          ↓
    │       Loki 검색
    │
    ├─ MDC 캡처/복원
    │          ↓
    │    traceId ↔ Log 연결
    │
    └─ user_fallback_total
               ↓
          Metric / Alert
```

즉, **존재하는 데이터를 잘 전달하는 문제뿐 아니라, 애초에 신호가 생성되지 않는 관측 공백까지 애플리케이션 계측에서 보완**했습니다.

### 6. Metric — 집계 쿼리로는 메울 수 없는 구멍이 하나 더 있었음

앞의 개선에서 5분 샘플링 문제를 `min_over_time` 구간 집계로 보존하도록 바꿨고, 그것으로 해결됐다고 판단했습니다. **CH-3(MongoDB 23초 다운)를 재조사하면서 그 판단이 절반만 맞았음이 드러났습니다.**

집계를 적용한 뒤에도 `mongodb_up`이 조사 구간 내내 `1`이었습니다. 에이전트는 리포트에서 *"~23초 중단은 잡혔어야 한다 — 익스포터가 stale일 가능성"* 이라며 관측 도구의 고장을 의심했습니다. 실제로 재보니 익스포터는 정상이었고, **원인은 쿼리가 아니라 그 아래 계층인 스크레이프 간격**이었습니다.

`count_over_time`으로 **실제 저장된 샘플 개수**를 세어 확인했습니다. 그래프의 점 개수는 쿼리 step이 만들어낸 격자일 뿐이고, 진짜 측정 횟수가 아니었습니다.

```text
실제 측정(30초):   ●─────────────●─────────────●
                 00:53:30      00:54:00      00:54:30
                    1             1             1

쿼리 출력(15초): ●──●──●──●──●──●──●──●──●
                1  1  1  1  1  1  1  1  1     ← 점은 9개, 측정은 3번

Mongo 실제:              ├──── 다운 23.6초 ────┤
                      00:53:34              00:53:57
```

**구멍이 두 개인데 집계 쿼리는 하나만 막습니다.**

| 구멍 | 증상 | `min_over_time`이 막나 |
|---|---|---|
| A. 쿼리가 건너뜀 | 샘플에는 `0`이 있는데 step이 `1`인 지점만 집음 | 막습니다 (앞의 개선이 한 일) |
| B. 애초에 측정 안 함 | 그 구간에 샘플 자체가 없음 | **못 막습니다** |

`min_over_time`은 *"그 구간에 존재하는 샘플들 중 최솟값"* 이므로 없는 샘플을 되살리지 못합니다. Grafana 패널의 Min도 같은 데이터에 대한 후처리라 결과가 같습니다. 실측으로도 `min_over_time(mongodb_up[1m])`을 3시간 15분에 걸쳐 조회했을 때 `0` 샘플이 하나도 없었습니다.

**포착 여부는 확률 문제였습니다.** 스크레이프 간격 `I`, 장애 길이 `D`일 때 `D ≥ I`이면 최소 한 샘플이 반드시 들어가고, `D < I`이면 포착 확률은 `D / I`입니다.

| 장애 | 간격 | 포착 확률 |
|---|---:|---:|
| CH-3 MongoDB 23.6초 | 30초 | **79%** — 이번 회차가 남은 21%에 걸렸습니다 |
| CH-1 MongoDB 5분 | 30초 | 100% |
| CH-2 컨슈머 부재 6~10분 | 30초 | 100% |
| IN-3 커넥션 풀 고갈(수십 초 예상) | **60초(앱 메트릭)** | 불확실 |

**"못 잡는다"가 아니라 "회차마다 5분의 1 확률로 사라진다"는 것이 더 나쁜 성질입니다.** 문항당 최소 2회 반복을 요구하는 평가 프로토콜에서 *"회차 A는 메트릭이 잡았고 B는 못 잡았다"* 가 되면, 점수 차가 능력 차인지 표본 운인지 구분할 수 없게 됩니다.

**조치 — 층을 나눠서 필요한 쪽만 낮췄습니다.**

간격을 재보니 두 층이 완전히 갈려 있었고, 설정상으로도 분리돼 있었습니다.

| 층 | 간격 | 활성 시리즈 | 설정 위치 |
|---|---:|---:|---|
| 인프라 exporter (`mongodb` · `kafka` · `redis`) | 30초 | **145** (5.5%) | Alloy `extraConfig`의 `prometheus.scrape "infra_external"` |
| 앱 (Micrometer) | 60초 | **2,513** (94%) | `annotationAutodiscovery` (chart 기본) |

인프라 층만 `scrape_interval`을 **30초 → 10초**로 낮췄습니다. 시리즈 수는 변하지 않아 요금제의 시리즈 한도와 무관하고, 샘플만 3배가 됩니다(환산 약 2,803 → 3,383 · 한도의 34%). **전체의 94%를 차지하는 앱 층은 건드리지 않았습니다.**

가용성 지표만 따로 떼어 더 자주 긁는 안도 검토했으나 기각했습니다. 같은 타겟을 두 블록에서 긁으면 라벨이 같은 중복 시리즈가 되어 깨지고, 피하려고 `instance` 라벨을 바꾸면 기존 쿼리·에이전트 설정·채점 앵커가 전부 갈라집니다. **145개를 3배로 만드는 편이 그 복잡도보다 쌉니다.**

**검증 — 전후를 실측했습니다.** (전환 2026-08-06 02:48~02:50Z)

| 지표 | 전 | 후 |
|---|---:|---:|
| `mongodb_up` | 2 샘플/분 (30초) | **6 샘플/분 (10초)** |
| `kafka_brokers` | 30초 | **10초** |
| `up{job="redis"}` | 30초 | **10초** |
| `up{job="chat-service"}` | 60초 | **60초 (의도대로 무변경)** |

**아직 검증하지 않은 것을 분명히 구분합니다.** 간격이 줄었다는 것과 *23초 다운이 실제로 `0`으로 기록된다*는 것은 다른 명제입니다. mongodb_exporter가 연결 실패를 즉시 반영하는지는 다음 주입에서 확인해야 하고, 그때도 `0`이 안 나오면 원인은 간격이 아니라 exporter 동작이므로 처방을 다시 세워야 합니다.

**그리고 이 문항은 메트릭 없이도 원인 규명에 성공했습니다.** 같은 조사에서 지연 Trace 탐색이 24초짜리 후보를 잡았고, Loki의 `InterruptedAtShutdown`·`Connection refused` 원문과 Span 공백 22.71초가 초 단위로 일치했습니다. 반대로 CH-2(컨슈머 부재)는 이상 Trace가 원리적으로 생성되지 않아 **메트릭만이 유일한 경로**였습니다. **같은 날 두 문항이 정반대 방향으로 깨졌다는 것이, 채널 하나에 의존하지 않는 다중 채널 탐색 구조의 실증 근거입니다.**

## 해결 방향

이 문제들을 개별 LogQL 수정이나 프롬프트 수정으로 보지 않고, **Raw Observability Data를 RCA가 사용할 수 있는 Evidence로 변환하는 계층의 문제**로 정의했습니다.

```text
                 Raw Observability Data
                         │
          ┌──────────────┴──────────────┐
          │                             │
        Loki                          Tempo
          │                             │
   ┌──────┼──────┐               Span 관계 해석
   │      │      │                      │
Stacktrace Dedup  로그 규칙        Service Call Graph
복원             통일                   │
   │      │      │                      │
   └──────┴──────┴──────────┬───────────┘
                            ▼
                     RCA Evidence
                            │
                            ▼
                     LLM Root Cause
```

핵심은 **LLM에게 더 많은 원본 데이터를 던지는 것이 아니라, 원본에 이미 존재하는 관계와 원인 정보를 손실·중복 없이 구조화해서 전달하는 것**이었습니다.

그 결과 RCA Pipeline을

> **수집 → LLM 전달**

에서

> **수집 → Evidence 정제 → 관계/원인 구조화 → LLM 분석**

으로 변경했습니다.

### 검증 결과

단순히 “개선했다”에서 끝내지 않고 실제 데이터로 검증했습니다.

- AP-2: 스택트레이스의 `Exception / Caused by / 코드 위치`까지 분석 컨텍스트에 포함
- B-10: 중복 로그 4줄 제거, 동일 timestamp·내용 기준으로 중복 제거 테스트 6건
- Trace: 저장된 **17개 Trace**를 대상으로 관계 추출 규칙 검증 후 테스트 픽스처 3건·테스트 5건 고정
- CH-1: **Span 28개 → 호출 Edge 6개**로 구조화하면서 error/rollback/duration 정보 유지
- AU-4: 죽은 `auth-service`에 대한 호출도 `client.name` 기반 Edge로 표현 가능하도록 보완
- 로그 정책: content **2,300줄 중 ERROR/WARN 8줄**이라는 실측을 기반으로 성공 요청 중복 로그 제거
- fallback: `[user-fallback]`, MDC 복원, `user_fallback_total`을 통해 기존에 없던 관측 신호 생성
- Metric 샘플링: `count_over_time`으로 **실제 저장 샘플 수**를 세어 인프라 30초 / 앱 60초를 확정하고, 인프라 층만 **10초로 낮춘 뒤 전후를 재측정**(`mongodb_up` 2 → 6 샘플/분, 앱 60초 무변경)

**단, RCA 점수 개선 효과는 아직 측정하지 않았습니다.** 현재 확인한 것은 관측 데이터가 실제로 원하는 형태의 Evidence로 변환되는지와 그 변환 과정이 테스트로 재현되는지까지이며, 점수 효과는 변경군별 재조사를 통해 별도로 검증할 예정입니다.
### Problem

> **관측 데이터는 존재하지만 RCA가 활용할 수 있는 형태로 정제되지 않았다.**

RCA 에이전트를 검증하면서 Loki와 Tempo에 장애 원인에 필요한 데이터가 존재함에도, 수집·가공 과정에서 일부 정보가 누락되거나 관계가 손실되고, 동일한 Evidence가 중복 전달되는 문제를 확인했습니다.

결과적으로 LLM은 이미 존재하는 관측 데이터를 그대로 활용하지 못하고, 여러 로그와 Span을 다시 조합하며 장애 원인을 추론해야 했습니다.

```text
Loki / Tempo
     │
     ▼
┌──────────────────────────────┐
│ 기존 수집·가공 과정          │
│                              │
│ Stack Trace ───→ 일부 누락   │
│ Span 관계 ─────→ 평면화      │
│ 로그 ──────────→ 중복 전달   │
│ 서비스별 로그 ─→ 기준 상이   │
└──────────────┬───────────────┘
               ▼
      RCA Context 품질 저하
               ▼
       LLM이 직접 재구성·추론
```

### Solution

관측 데이터를 단순히 더 많이 전달하는 대신, **RCA 분석 전에 Evidence를 정제하는 계층을 추가**했습니다.

```text
                 Loki / Tempo
                      │
                      ▼
           ┌──────────────────┐
           │ Evidence 정제    │
           └────────┬─────────┘
                    │
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
정보 완전성      관계 구조화      중복 제거
     │              │              │
Stack Trace    Span → Graph    Log Dedup
     │              │              │
     └──────────────┼──────────────┘
                    ▼
              RCA Evidence
                    │
                    ▼
               LLM Analysis
```

#### 1. 누락된 원인 정보 보강

기존 LogQL은 `ERROR|WARN` 헤더만 조회하여 **실제 예외 원인이 담긴 Stack Trace가 분석 Context에서 제외**되고 있었습니다.

```logql
# Before
{service_name=~"..."} |~ "ERROR|WARN"

# After
{service_name=~"..."} |~ `ERROR|WARN|Exception|Caused by|\.java:[0-9]+\)`
```

예외 클래스, `Caused by`, `파일:라인` 정보를 함께 수집하도록 변경하여 **장애 원인을 설명하는 Evidence가 분석 단계까지 전달**되도록 개선했습니다.

#### 2. 손실된 호출 관계 구조화

Tempo에 존재하던 `parentSpanId`, `db.system`, `messaging.system`, `client.name` 등을 활용해 **평면적인 Span 목록을 Service Graph로 변환**했습니다.

```text
Span 목록
   │
   ▼
ServiceGraphExtractor
   ├── parentSpanId
   ├── messaging.system
   ├── db.system
   └── client.name
   │
   ▼
┌─────────────────────┐
│ content → Kafka     │
│ Kafka → chat        │
│ chat → MySQL        │
│ content → Redis     │
└─────────────────────┘
```

이를 통해 LLM이 여러 Span의 시간과 속성을 조합하여 호출 관계를 추론하는 대신, **관측 데이터에서 관계를 먼저 구조화하여 분석 근거로 제공**하도록 변경했습니다.

#### 3. 중복 Evidence 제거

Loki의 ERROR/WARN 조회와 traceId 기반 조회가 동일한 로그를 반환하면서 **하나의 로그가 Context에 중복 포함되는 문제**를 확인했습니다.

두 조회 자체는 유지하되, 두 결과의 교집합에서 두 번째 등장하는 로그만 제거했습니다.

```text
Loki ERROR/WARN ──────┐
                      ├─→ Dedup → RCA Context
Loki traceId ─────────┘
```

Raw 데이터는 그대로 유지하고 분석 Context에서만 중복을 제거하여 **관측 원본의 감사 가능성은 유지**했습니다.

#### 4. 관측 기준 통일

서비스마다 HTTP 로그 정책이 달라 정상 요청이 과도하게 기록되거나 실패 요청이 기록되지 않는 문제도 함께 정리했습니다.

```text
HTTP Request
     │
     ├── 정상 요청 ────→ Trace
     │
     ├── 4xx / 5xx ────→ Log
     │
     └── > 1 sec ──────→ Log
```

서비스별 로그 정책을 동일한 기준으로 통일하여 **Trace와 Log의 역할을 명확하게 분리**했습니다.

### Result

```text
Before

Loki / Tempo
     ↓
Raw Data
     ↓
LLM이 관계·원인·중복을 직접 추론
     ↓
RCA


After

Loki / Tempo
     ↓
Evidence 정제
 ├─ Stack Trace 보강
 ├─ Service Graph 생성
 ├─ 중복 제거
 └─ 관측 기준 통일
     ↓
구조화된 RCA Evidence
     ↓
LLM Analysis
     ↓
RCA
```

> **핵심은 LLM을 개선한 것이 아니라, LLM이 판단하기 전에 관측 데이터를 분석 가능한 Evidence로 변환하는 구조를 만든 것입니다.**

관측 데이터의 부족이 아니라 `누락 · 관계 손실 · 중복 · 관측 기준 불일치`를 문제의 원인으로 분해하고, 각각을 수집·변환·조립 계층에서 해결했습니다.

## 전체 파이프라인 — 자연어 질문이 리포트가 되기까지 (실제 실행)

아래는 실제 실행 1건을 처음부터 끝까지 따라간 것입니다.
**2026-07-29, Kafka 브로커를 내린 상태에서 들어온 질문**이고, 모든 수치는 저장된
리포트(`reports/6a69f658…-20260729T130547.md`)의 실측입니다.

```text
POST /diagnose {"question": "..."}          api/RcaController
        │                                   └ 아래 [1]~[4]는 triage/TriageService가 묶는다
[1] 시간창 해석                              triage/window/TimeExpressionParser
        │
[2] 관측 스윕 (집계값만)                     triage/survey/Surveyor
        │                                     → client/{Loki,Tempo,Mimir}Client
[3] Signal → Incident 후보 생성 (코드)       triage/incident/Signal.extract
        │                                     → triage/incident/Incident.cluster
[4] 탐색 LLM — 후보 중 선택                  triage/plan/SurveyContextAssembler + LlmClient
        │  (좁힌 창 · 서비스 · traceId)        → triage/plan/TriagePlan.parse
        │                                   └ 여기부터 service/RcaService (v0 경로와 같은 코드)
[5] 원본 수집                                collector/Collector → client/*Client
        │                                    (client/RawResponseStore가 원본 JSON 박제)
[6] Evidence 정제·조립                       analyzer/ContextAssembler
        │                                      ├ analyzer/ServiceGraphExtractor → report/ServiceGraph
        │                                      └ analyzer/LokiLogDedup
[7] 분석 LLM                                 analyzer/SystemPromptLoader + llm/ClaudeCliLlmClient
        │
[8] 리포트·알림                              analyzer/EvidenceExtractor → report/RcaReport
                                             → report/ReportMarkdown → report/ReportStore
                                             → notify/Notifier
```

`triage` 아래는 단계별 하위 패키지로 나뉘어 있습니다 —
`window`(창 해석) · `survey`(스윕) · `incident`(신호·후보) · `plan`(탐색 LLM 입출력).
`TriageService`는 이 넷을 순서대로 호출한 뒤 `RcaService.investigate(scope, ...)`로 넘깁니다.

### 무엇을 코드가 정하고, 무엇을 LLM이 정하나

이 파이프라인의 설계 의도는 이 표 한 장입니다. **LLM은 두 번 부르고, 그중 탐색은 판단
하나만 합니다.**

| 정하는 것 | 주체 | 근거 |
|---|---|---|
| 시간창 해석 | **코드** | LLM에 맡기면 같은 질문이 회차마다 다른 창을 만들어 재현이 깨진다 |
| 무엇을 조회할지 | **코드** | 고정 쿼리 목록(`application.yml`). 회차 간 입력을 같게 유지 |
| 무엇이 이상 신호인지 | **코드** | 변화·부재·존재만. **임계값을 쓰지 않는다** — 문항별 임계값은 정답을 심는 것 |
| 후보를 어떻게 묶을지 | **코드** | `채널\|리소스\|지문` 3축 + 시간 근접 |
| **어느 후보인가** | **탐색 LLM** | **모델이 만드는 정보는 이것 하나뿐** |
| 조사 창 · 대상 서비스 · traceId | **코드** | 고른 후보에서 파생. 모델이 시각을 적어 내도 무시한다 |
| 원인 · 근거 · 조치 | **분석 LLM** | 자유 서술 |

### [0] 입력 — 자연어 한 문장

```text
POST /diagnose
{ "question": "최근 1시간 안에 댓글 알림이 안 왔다는 제보가 있다. 원인을 조사해줘" }
```

`RcaController`의 `/diagnose` 진입점이 받습니다. traceId를 아는 경우의 `/investigate`
(v0 경로)는 그대로 남겨 두었습니다 — 분석 능력만 따로 재려면 대상이 고정된 입력이
필요하고, 과거 회차와의 비교가 이 경로로만 성립하기 때문입니다.

### [1] 시간창 해석 — `TimeExpressionParser`

질문의 시간 표현을 스윕 창으로 바꿉니다. LLM 호출 없이 코드가 합니다.

```text
"최근 1시간" (상대 표현)
→ 스윕 창: 2026-07-29T12:02:25Z ~ 13:02:25Z
→ confidence = EXACT
```

인식(`time/TimeCandidates`)과 결합 정책(`TimeExpressionParser`)이 갈려 있습니다. 문장에서
무엇이 보이는지는 앞이, 그 후보로 창을 만드는 우선순위(**구간 > 시각 > 시간대 > 날짜 >
상대**)·미래 절단·±여유·상한은 뒤가 책임집니다.

`confidence`(EXACT/APPROX/FALLBACK)를 값으로 남겨 리포트 `triage.timeConfidence`에
적재합니다 — **FALLBACK 회차를 분리 집계**할 수 있어야 "시간창을 못 잡아서 틀린 것"과
"분석이 틀린 것"이 섞이지 않습니다.

명시적 `from`/`to`가 절반만 오거나 순서가 뒤집히면 **400으로 거부**합니다(B-26).
구 파서는 조용히 무시하고 질문 파싱으로 떨어져, **과거 데이터 재조사가 오늘 창을
조사하고도 눈치채지 못했습니다**(결함 22).

### [2] 관측 스윕 — `Surveyor` (1,496ms)

창 전체를 **집계값으로만** 훑습니다. 원본은 아직 가져오지 않습니다 — 창이 12시간이어도
응답 크기가 스텝 수로만 결정되기 때문에 이 단계는 창 폭에 거의 무관하게 쌉니다.

| 채널 | 쿼리 | 왜 이 모양인가 |
|---|---|---|
| Tempo 에러 | `{ status = error }` | |
| Tempo 지연 | `{ duration > 3s && status != error }` | **에러 채널과 따로 던진다.** 합치면 후보에서 "어느 채널로 도달했는지"가 사라지는데, 200 성공 + 지연 장애에서는 그것이 곧 장애 성격이다(CH-3는 에러 검색이 0건) |
| Loki | `sum by (service_name) (count_over_time({service_name=~"..."} \|~ "ERROR\|WARN" [5m]))` | 라인 필터를 쓴다 — 평문 Logback이라 `logfmt` 파서가 `level` 필드를 못 만든다. **스택 패턴은 넣지 않는다**: 발생률 쿼리라 스택 줄이 건수를 수십 배 부풀린다 |
| Mimir | `min_over_time(up[5m])` · `min_over_time(mongodb_up[5m])` · `min_over_time(kafka_brokers[5m])` · `max_over_time(kafka_consumergroup_lag[5m])` · `max_over_time(websocket_active_users[5m])` | **집계 함수로 구간 상태를 보존한다.** 순간값을 5분마다 찍으면 그 사이 단기 장애가 사라진다 — CH-3의 23초 다운이 `mongodb_up` 05:20:09=1 / 05:25:09=1 사이로 빠져 정상으로 관측됐다. 점 개수가 같아 **응답 크기는 불변**이다 |

**공백을 숨기지 않습니다.** 실패도 0건도 `failures`에 남습니다 — 이 조사에서 "없다"는
결측이 아니라 근거이고, 조용히 비면 다음 단계가 그것을 정상으로 읽습니다.

```text
"Tempo 에러 검색 '{ status = error }'이 이 창에서 0건이다. 트레이스가 생성되지 않는
 장애(컨슈머 전멸·파드 부재)이거나 에러가 아닌 형태의 장애(200 성공 + 지연)일 수 있으니
 이 사실 자체를 근거로 쓸 것."
```

### [3] 장애 후보 생성 — `Signal.extract` → `Incident.cluster`

스윕 원본에서 이상 신호(`Signal`)를 뽑고, 시간 근접한 신호를 장애 후보(`Incident`)로
묶습니다. **후보를 만드는 것은 코드이고 LLM은 다음 단계에서 고르기만 합니다.**

**신호를 뽑는 규칙이 채널마다 다릅니다.**

| 채널 | 무엇을 이상으로 보나 | 예 |
|---|---|---|
| TEMPO | 검색 결과의 **존재** (TraceQL이 이미 이상을 정의했다) | `content-service http post /feeds 119ms (error 채널)` |
| LOKI | 버킷에 값이 **있다** (`count_over_time`은 0건 구간에 샘플을 안 만든다) | `ERROR/WARN 4건 (08:50 ~ 08:55)` |
| MIMIR | **0 구간 · 값 변화 · 시리즈 결측** 셋 | `kafka_brokers 1 → 0` · `up 가 0이었다` · `시리즈가 없다(스크레이프 대상 부재)` |

여기에 두 가지 판단이 박혀 있습니다.

**① 점이 아니라 구간이다.** 로그 발생률 응답 `[[1785315300,"4"]]`을 시각 하나로 읽으면
틀립니다. 쿼리가 `count_over_time(...[5m])`이므로 그 값은 **직전 5분 사이에 4건**이고,
점으로 읽으면 최대 5분이 어긋납니다. 실제로 버킷 시각을 사건 시각으로 읽은 회차
리포트가 있었습니다. 그래서 `[ts - lookback, ts]` 구간으로 만듭니다.

**② 임계값으로 판정하지 않는다.** `errorRate > 5%` 같은 기준을 코드에 박지 않습니다 —
ⓐ 평시 baseline 데이터가 없고 ⓑ 문항별 임계값은 **정답을 심는 것**이며 ⓒ 값의 크기는
`what` 문구에 담아 모델이 보게 하면 됩니다.

**군집 키에 시간이 들어가지 않습니다.**

```java
key() = channel + "|" + resource + "|" + signature
```

라벨 3축으로 먼저 가르고, **같은 키 안에서만** 시간으로 끊습니다. 그래서 두 장애가
시간상 교차해도(1번-A → 2번-A → 1번-B) 섞이지 않습니다. 채널이 축인 이유는 지문의 성격이
채널마다 달라서입니다(Tempo는 엔드포인트, Loki는 예외 클래스, Mimir는 지표명).

이어서 ① traceId를 공유하면 병합하고 ② 시간이 겹치는 다른 후보는 **병합하지 않고
`related`로 표시만** 합니다 — *"인과 여부는 판단하지 않았다"*.

**Mimir 시리즈 라벨은 지문이 아니라 설명에 붙입니다.** 지문(군집 키)에 `topic`을 넣으면
44개 시리즈가 44개 후보로 흩어지고, 안 붙이면 후보 목록에서 36줄이 **글자 그대로 같은
줄**이 됩니다. 그래서 키는 지표명, 설명은 라벨 포함으로 갈랐습니다.

```text
- kafka_consumergroup_lag{consumergroup=notification-processors, topic=user.notifications} 가 0이었다
- kafka_consumergroup_lag{consumergroup=notification-recovery,  topic=user.notifications.dlq} 가 0이었다
```

### [4] 탐색 LLM — 후보 선택

`SurveyContextAssembler`가 조립해 `prompts/triage-prompt.md`와 함께 보냅니다
(이 실행 38,225자 · in 43,014 tok · 61.5s · $0.38). 컨텍스트 구성:

```text
# 탐색 대상                       (질문 · 스윕 창 · 시간창 해석 근거)
# 장애 후보                       ← Incident.describe()
# 후보가 되지 못한 트레이스        ← 시각·duration이 깨진 행. 버리지 않고 표기만 한다
# 채널별 도달 요약                 ← "조회했는데 신호 0" = 그 대상은 정상이었다
# 무신호/실패 목록                 ← "없다는 사실 자체가 신호일 수 있다"
# 에러 트레이스 검색 (Tempo)       ┐
# 지연 트레이스 검색 (Tempo)       │ 원본 JSON 전문
# 서비스별 ERROR/WARN 발생률 (Loki)│ ← rca.survey.include-raw=false 면 이 네 절이 빠진다
# 인프라 신호 (Mimir)              ┘
```

**모델이 만드는 정보는 후보 번호 하나입니다.** 나머지는 코드가 파생합니다.

```java
window   = Incident.unionWindow(chosen, ...)   // 여러 개 골랐으면 합친다
services = resourcesOf(chosen)
traceIds = TriagePlan.traceIdsOf(chosen)       // 대표를 뽑지 않는다 — 전부
```

프롬프트가 *"시각을 직접 쓰지 말 것"* 이라고 명시하고, 모델이 `windowStart`를 적어 내도
후보를 지목했으면 **무시합니다**. 이 실행에서 나온 계획:

```text
좁힌 창   12:44:00Z ~ 12:56:00Z   (60분 → 12분)
대상      content-service, chat-service
traceId   6a69f6581e1b5ce5c855e106cca6260c (60,003ms 발행 타임아웃 트레이스)
```

선정 이유(리포트 원문): *"Kafka 접점 단절(12:47)과 content-service의 60초 발행
타임아웃 트레이스·414건 에러가 같은 시각에 겹치고, 복구 후에도 컨슈머 lag이 0이어서
댓글 이벤트가 Kafka에 진입조차 못 한 구간으로 판단"*.

계획을 못 읽으면 **스윕 창 전체가 아니라 신호가 가장 많은 후보**로 떨어지고, 그 사실이
`notes`에 남습니다. 고르지 않은 후보(`dismissedIncidentIds`)와 후보 전문
(`incidentCandidates`)도 리포트에 실립니다 — 회고에서 *"다른 걸 골랐어야 했나"* 를
판단하려면 그때 무엇이 보였는지가 있어야 합니다.

> **대조군 스위치** — `rca.survey.include-raw`(기본 `true`). 탐색 LLM의 산출이 후보 번호
> 하나뿐인데 원본이 이 단계 컨텍스트의 약 94%를 차지합니다. 원본이 그 선택의 정확도에
> 기여하는지는 **아직 측정되지 않았습니다.** `false`로 두면 후보 목록만 싣습니다
> (저장된 스윕 재생 실측: **45,991자 → 7,697자, -83%**).
> ⚠ `false`에서 나빠져도 원인이 갈리지 않습니다 — 원본 부재 탓인지 후보 지문 부실 탓인지.
> 해석에 이 한계를 명시해야 합니다.

#### 후보를 여러 개 골랐을 때 — 채널마다 창이 다릅니다

탐색은 확신이 없으면 후보를 여러 개 고릅니다(프롬프트: *"하나만 고르고 틀리면 그 조사는
끝나지만, 여러 개를 고르면 조사 범위가 그만큼만 넓어진다"*). 그때 조사 창은
`Incident.unionWindow`의 **합집합**인데, 합집합은 **사이의 빈 구간까지 덮습니다.**

```text
합집합 하나로 긁으면
08:49 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 09:12   23분
      ■■■■                        ■■■■
      INC-5                       INC-6
           └────── 15분은 아무 신호도 없다 ──────┘
```

범위를 넓히는 것이 답이 아니라는 건 이미 실측돼 있습니다 — 창 2.26배 확장에서
**Context +72% · 비용 +39% · 점수 불변**이었고, 증가분이 **거의 전부 메트릭**이었습니다.

그래서 **채널 성격에 따라 갈랐습니다.**

| 채널 | 창 | 왜 |
|---|---|---|
| 로그 (ERROR/WARN · traceId 일치) | **후보별로 분할** | 점 사건이라 사이 구간에 정보가 없다 |
| 후보 트레이스 검색 (`{}`) | **후보별로 분할** | 빈 구간의 무관한 트레이스가 상한을 차지하지 않게 |
| 메트릭 | **합집합 유지** | 시계열이 조각나면 *"그 사이에 회복했는가"* 를 잃는다. CH-1의 재시도 4회가 사이 구간에 있으면 안 보인다 |

**나눠서 제일 많이 아낄 수 있는 채널(메트릭)이 나누면 제일 위험한 채널**이라는 것이
이 설계의 핵심입니다. 그래서 절약은 로그·트레이스에서만 취합니다.

구현에서 두 가지를 지켰습니다.

- **결과는 합쳐서 넘깁니다** (`Collector.mergeStreams` — `data.result` 배열만 이어붙임).
  창별 목록으로 바꾸면 `LokiLogDedup`·`EvidenceExtractor`·`ContextAssembler`가 전부 창을
  알아야 하는데, **그들이 하는 일에 창은 필요 없습니다.**
- **창이 하나면 원본 문자열을 그대로 돌려줍니다.** 재직렬화하면 바이트 수가 미묘하게 달라져
  토큰 축 비교가 흔들립니다 — 후보를 1개만 고르는 기존 경로는 **바이트 단위로 동일**합니다.

한계가 하나 남습니다. `INC-1`처럼 **후보 자체의 구간이 스윕 창 전체**면(`lag = 0`이 전
구간) 분할해도 60분입니다. 이건 창 설계가 아니라 `zeroRuns()`가 *"0이 정상인 지표"* 를
신호로 세지 않게 해야 풀립니다.

#### 창 안 후보 트레이스(B-9)에 두 가지 설계가 더 있습니다

① 후보 검색 TraceQL이 `{}` 입니다 — **상태를 거르지 않습니다.** 정답이 *정상 트레이스*인
문항이 실재하기 때문입니다(AU-2: *"정상 요청에 auth 호출 span이 없다"* 가 요건이라
error/slow 채널 어디에도 안 걸립니다).

② 고른 후보가 물고 있는 traceId는 **전부** 목록 앞에 놓습니다. 대표 하나만 전문 수집하고
나머지를 창 검색과 같은 줄에 세우면 **모델이 지목한 것이 상한에 밀릴 수 있습니다.**

상한은 `max-traces: 10`(0 이하 = 무제한)입니다. **근거 있는 값이 아닙니다** — 창 안
트레이스가 실제로 몇 건인지 아직 안 세어 봤고, 회차 3의 coverage를 보고 정합니다.

모든 원본 JSON은 `RawResponseStore`가 `reports/raw/`에 박제합니다(사후 검증·재실험용,
현재 304개 / 4.1MB). 저장은 **best-effort**입니다 — 실패해도 `log.warn`만 하고 조사를
멈추지 않습니다. 실패한 쿼리는 숨기지 않고 `failures`에 기록됩니다 — 이 실행에서도
401 rate 쿼리 1개가 "수집 실패/누락"으로 리포트에 남았습니다.
