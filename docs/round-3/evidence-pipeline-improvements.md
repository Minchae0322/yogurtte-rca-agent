# 관측 데이터 활용 구조 개선

> **구현 상태가 셋으로 갈립니다** — §1(로그 스택트레이스)은 **적용 완료**,
> §2(Trace 호출 그래프)는 **검증·구현·테스트 고정까지 완료 (2026-07-31) · 점수 효과 미측정**,
> §3(로그 기록 체계 통합)은 **규칙 제정 + 일부 코드 반영·미배포**입니다.
> §2의 상세 스펙·검증 기록은 [service-graph-spec.md](service-graph-spec.md). 자세한 상태는 맨 아래 표.

RCA 에이전트를 검증하는 과정에서 장애 원인에 필요한 정보가 Loki와 Tempo에는 존재했지만, 현재 수집·가공 방식에서는 일부 정보가 분석 컨텍스트에 포함되지 않거나 관계 정보가 활용되지 않는 문제를 확인했습니다. 로그는 스택트레이스가 필터링되어 예외 원인이 누락되고 있었고, Trace는 Span 관계를 해석하지 않아 서비스 간 호출 구조를 복원하지 못했습니다. 이를 해결하기 위해 로그 수집 규칙과 Trace 표현 방식을 수정하여 기존 관측 데이터를 보다 완전한 Evidence로 활용할 수 있도록 개선했습니다.

## 1. 로그 스택트레이스 수집 개선

### 문제

팔로우 목록 NPE(AP-2)는 실제 원인이 `FollowCondition.java:25`에 있었지만 기존 LogQL은 `ERROR|WARN`이 포함된 헤더 라인만 조회하고 있었습니다.

```logql
{service_name=~"..."} |~ "ERROR|WARN"
```

동일한 예외 로그는 다음과 같이 저장됩니다.

```
ERROR FollowService : 팔로우 목록 조회 실패      ← 조회됨
java.lang.NullPointerException ...             ← 제외됨
    at FollowCondition.java:25                 ← 제외됨 (실제 원인)
```

또한 traceId 기반 조회 역시 스택 라인에는 traceId가 기록되지 않아 동일한 문제가 발생했습니다. 즉 예외 로그는 수집되었지만 실제 원인을 담고 있는 스택 정보는 분석 컨텍스트에 포함되지 않았습니다.

### 개선

분석 단계의 LogQL을 다음과 같이 변경했습니다.

```logql
{service_name=~"..."} |~ `ERROR|WARN|Exception|Caused by|\.java:[0-9]+\)`
```

추가된 패턴은 다음 정보를 함께 수집합니다.

| 패턴 | 목적 |
|------|------|
| `Exception` | 예외 클래스 |
| `Caused by` | 중첩 예외 |
| `\.java:[0-9]+\)` | 실제 코드 위치 |

반면 장애 탐색 단계에서 사용하는 발생률 집계(Query Range)는 그대로 유지했습니다. 스택 라인까지 집계에 포함하면 하나의 예외가 수십 줄로 계산되어 장애 발생량이 왜곡되기 때문입니다.

수집량 증가는 **예외 발생 건수에 비례**합니다. 레벨 필터를 아예 없애 INFO까지 받는 것과는
성질이 다릅니다.

| | 증가 |
|---|---|
| INFO 전량 수집 | 1시간 2,300줄 중 ERROR/WARN 8줄 → **약 287배** |
| 스택 라인 추가 | 예외 8건 × 스택 20~50줄 → **8줄 → 200~400줄** |

스택 라인은 정상 요청에는 아예 존재하지 않습니다.

> **근본 해결은 따로 있습니다.** 수집기에서 **multiline 스티칭**으로 스택을 하나의 엔트리로
> 묶으면 traceId가 함께 붙어 기존 쿼리가 그대로 작동합니다. 다만 관측 파이프라인 변경이고,
> **과거 데이터는 이미 줄 단위로 저장돼 있어 재조사로 검증되지 않습니다**(새로 주입해야 한다).
> 그래서 지금은 라인 필터 확장을 택했습니다 — AP-2 재조사가 주입 없이 가능합니다.

## 2. Trace 관계 정보 활용 개선

### 문제

Tempo에는 `parentSpanId`, `db.system`, `messaging.system` 등 서비스 호출 관계를 복원할 수 있는 정보가 이미 저장되어 있었지만 기존 구현은 Span을 단순 목록으로만 사용하고 있었습니다.

그 결과

- 부모-자식 호출 관계를 알 수 없고
- 서비스 간 의존성을 시간 순서로만 추론해야 했으며
- Redis, MySQL, Kafka와 같은 공통 리소스를 하나의 장애로 연결하지 못했습니다.

즉 필요한 데이터는 존재했지만 분석 과정에서 활용되지 못하고 있었습니다.

### 개선

Trace를 단순 Span 목록이 아닌 호출 그래프로 변환하도록 구조를 변경했습니다.
Span마다 아래 판별 순서를 위에서부터 적용해 "이 Span은 어떤 호출인가"를 정하고,
같은 (종류, 출발, 도착) 엣지에 속한 Span들을 한 줄로 집약합니다.

```
① messaging.system                     → 메시징 (publish: 서비스→토픽 / receive: 토픽→서비스)
② db.system                            → 데이터베이스 (redis 등)
③ jdbc.datasource.*                    → 데이터베이스 (mysql/<풀 이름>)
④ client.name (아웃바운드 HTTP)         → 서비스 경계 — 상대 span이 없어도 나온다 (검증에서 추가)
⑤ parentSpanId (부모의 service.name 비교) → 서비스 경계
⑥ peer.service 만 있다                  → 미분류로 남긴다. 신뢰할 수 없기 때문이다
```

**`peer.service`를 마지막에 두는 것이 이 순서의 핵심입니다.** 같은 Span에 이렇게 들어옵니다.

```json
{"key":"jdbc.datasource.name","value":{"stringValue":"content"}},
{"key":"peer.service",        "value":{"stringValue":"content"}}     ← MySQL DB 이름이다
```

`peer.service=content`는 `content-service`가 아니라 **MySQL 데이터베이스 `content`** 입니다.
저장된 트레이스에서 288건이 이 형태였습니다. 표준 키보다 먼저 보면
**`content-service → content-service` 자기 참조 Edge**가 생기고, `-service` 접미를 떼어
비교하는 방식도 같은 함정에 빠집니다.

그래서 이름을 **시스템/대상** 형태로 짓습니다 — `mysql/content` · `redis` ·
`kafka/user.notifications`. 서비스와 DB가 문자열로 구별됩니다.

JDBC 세부 Span(query·result-set·connection)은 제거하지 않고 하나의 Edge로 집계하여
SQL 오류나 Kafka Publish 실패와 같은 핵심 정보는 유지하면서 노이즈만 줄입니다.

### 검증에서 배운 것 — 설계 그대로는 두 곳이 틀렸다

구현 전에 `reports/raw/`의 저장된 트레이스 **17개 전부**에 추출 규칙을 돌려 확인했습니다
(2026-07-31 · 주입/배포 불필요). 원안이 그대로 통과하지 못했고, 그 자체가 수확입니다.

| 발견 | 무엇이 틀렸었나 | 어떻게 고쳤나 |
|---|---|---|
| **죽은 서비스는 트레이스에 합류하지 못한다** | auth-service 다운 장애(AU-4)의 트레이스는 **66개 Span 전부가 content-service**다. 호출이 Connection refused로 끝나면 상대는 Span을 남길 수 없어, "부모 서비스 비교"(⑤)만으로는 이 엣지가 **조용히 사라진다** — 검증에서 실제로 사라졌다 | 판별 ④ 신설 — 부른 쪽 CLIENT Span에 남는 `client.name`으로 엣지를 만든다. 결과: `content-service → auth-service` 엣지에 `Connection refused` 오류까지 실린다 |
| **receive의 토픽명은 다른 키에 온다** | 원안의 `messaging.destination.name`으로는 receive 엣지가 `kafka/?`가 된다 | receive는 `messaging.source.name`을 읽는다 (CH-1 실측) |
| **MongoDB는 Span을 만들지 않는다** (반증) | "`db.system=mongodb`로 올 것"이라던 구두 확인이 틀렸다 — 17개 트레이스에 mongodb Span **0건** | Mongo 장애는 Kafka receive Span의 `error` 속성 텍스트로 온다. 엣지에 error를 붙이는 집약 설계 덕에 지문은 전달되지만, `chat → mongodb` 엣지는 관측상 만들 수 없다고 한계를 명시 |

### 실제 출력 — CH-1 트레이스: Span 28개 → 엣지 6줄

알림 미발송 장애의 저장된 트레이스에서 실제로 나온 출력입니다. **여섯 줄이 장애 서사
전체를 담습니다** — 발행은 정상(16.6ms), 소비가 30초씩 걸리며 그 Span에 Mongo 접속 거부
에러가 붙어 있고, 결국 DLQ로 갔다는 것까지.

```
content-service --messaging--> kafka/user.notifications   1회  최대 16.6ms  [publish]
kafka/user.notifications --messaging--> chat-service      4회  최대 30108.2ms  [receive]
    error: Timed out ... MongoSocketOpenException ... Connection refused ...:27017
chat-service --messaging--> kafka/user.notifications.dlq  1회  최대 1300.6ms  [publish]
chat-service --jdbc--> mysql/content (HikariPool-1)       4회  최대 30021.5ms
    events: acquired, rollback
content-service --jdbc--> mysql/content (HikariPool-1)    8회  최대 45.3ms
content-service --db--> redis                             1회  최대 0.6ms  [GET]
```

이전에는 모델이 Span 28개를 시각으로 짜맞춰야 나오던 결론입니다.

**부수 실측** — 위 넷째 줄이 뜻밖의 발견입니다. chat의 도메인 저장소는 MongoDB인데,
트레이스상 **chat의 JVM에 MySQL 풀(`HikariPool-1`, datasource명 `content`)이 실재**하고
알림 처리가 그 JDBC 트랜잭션 안에서 30초 점유 후 rollback합니다
(`receive → connection → process-notification` 부모 사슬로 확인). 메시지 1건당 MySQL
커넥션 30초 점유는 NF-10(커넥션 점유) 계열의 앱 쪽 관찰이며, toy 쪽 설정 확인 대상입니다.
그래프를 "chat은 원래 Mongo"라는 정적 지식으로 고치지 않습니다 — 관측이 말하는 것을
그대로 싣는 것이 이 설계의 원칙이고, 실제로 그 원칙이 이 발견을 만들었습니다.

**테스트 5건으로 박제**했습니다(`ServiceGraphExtractorTest`) — 접힘·자기참조 0건·죽은 서비스
엣지·Kafka 방향·빈 그래프. 기대값이 바뀌면 추출 규칙이 회귀한 것입니다. `./gradlew test` 통과.

### 파이프라인에서의 위치 — 탐색은 그대로, 분석이 바뀐다

전체 흐름에서 이 변경이 어디에 들어가는지입니다.

```
[1] 자연어 질문
      ↓  TimeExpressionParser
[2] 시간 창 계산
      ↓  Surveyor — Loki/Tempo/Mimir를 집계값으로 스윕
[3] Signal → Incident 후보 → LLM ①이 선택 (탐색)          ← 변경 없음
      ↓  창·서비스·traceId가 좁혀짐
[4] Collector — 그 범위의 트레이스 원본 + 로그 + 메트릭      ← 변경 없음
      ↓
[5] ContextAssembler — 컨텍스트 조립                        ← ★ 호출 그래프 절 추가
      ↓
[6] LLM ② — 원인 분석                                      ← ★ 영향을 받는 곳
      ↓
[7] 리포트 (관측 증거)                                      ← ★ 그래프 기록 추가
```

**[1]~[3] 탐색 단계는 이번 변경과 무관합니다.** 탐색은 집계값(에러율·트레이스 검색
결과·메트릭 이상)만 받고 트레이스 원본이 없어서, 그래프를 만들 재료 자체가 없습니다.

영향은 세 가지입니다.

1. **분석 단계 LLM의 입력 질이 바뀝니다.** 지금까지 [6]의 모델은 평평한 Span 목록에서
   *"Redis GET 직후 0.7ms 뒤에 auth 호출 — 아마 캐시 미스 보충"* 같은 **시각 기반 정황
   추론**을 해야 했고, AU-4에서 정답을 맞히고도 그 추론이 정황이라 확신도를 낮춰 감점됐습니다.
   이제 컨텍스트에 관측 사실 몇 줄이 먼저 옵니다 — **추론해야 했던 것이 읽으면 되는 것**이 됩니다.
2. **트레이스에 없던 신호가 생겼습니다.** 죽은 서비스는 Span을 못 남기므로 기존 목록에서는
   "auth가 호출됐다는 것" 자체가 안 보였습니다. 판별 ④(`client.name`) 덕에 *"auth를 불렀는데
   거부됐다"* 가 엣지 한 줄로 나옵니다.
3. **시스템 지식의 출처가 프롬프트에서 관측으로 바뀌었습니다 — 구조적으로 가장 큰 변화입니다.**
   토폴로지가 사람이 박아둔 문장이던 동안에는 (a) 문장에 없는 인프라(Redis·MySQL·Mongo)는
   모델이 알 수 없었고, (b) 점수가 움직여도 그래프 덕인지 문장 덕인지 가릴 수 없었습니다.
   문장을 지우고 관측 유도로 바꾸면서 둘 다 해소됩니다. 새 서비스·인프라가 붙어도
   프롬프트를 고칠 필요가 없어진 것은 부수 효과입니다.

**리스크 하나를 함께 적어둡니다.** 탐색 프롬프트([3])에서도 토폴로지 문장을 뺐는데,
탐색 단계는 그래프를 **받지 못하므로** 거기는 대체물 없이 지식만 줄었습니다.
탐색 점수가 떨어지면 이것이 첫 번째 용의자이고, 아래 반증 조건의 "프롬프트 문장 제거"
행이 이 경우를 잡습니다.

### 예상되는 성과 — 실측과 예측을 구분한다

**실측된 사실 (지금 말할 수 있는 것):**

| 사실 | 수치 |
|---|---|
| 집약 효과 | AP-3 트레이스 Span 23개 → 엣지 **1줄** (오류·rollback 유지) · CH-1 Span 28개 → **6줄** |
| 함정 회피 | `peer.service=content` Span 트레이스당 최대 60개 전부 정분류 — 자기참조 **0건** · 미분류 **0건** |
| 죽은 서비스 도달 | AU-4 트레이스에서 `content → auth-service` 엣지 + `Connection refused` 오류 — **이전에는 아예 없던 신호** |
| 컨텍스트 크기 | 그래프 절 추가분은 트레이스당 **수백 자** — 원본을 대체하지 않으므로 컨텍스트는 오히려 약간 커진다. **토큰 절감을 주장하지 않는다** |

**예측 (재조사 후 검증 — 미측정):**

- **AU-4 원인 항목 +10 회복.** 회차 2에서 에이전트는 read-through 패턴을 **정확히 맞히고도**
  근거가 "시각이 붙어 있고 사용자 ID가 같다"는 정황 추론이라 확신도 낮음(후보 3)에 뒀고
  원인에서 −10을 받았다. 그래프는 그 정황을 **관측 사실**(엣지 + 오류)로 바꾼다.
  주입 불필요 — 기존 traceId 재조사로 잰다.
- **프롬프트 문장 제거 후 점수 유지.** 그래프가 손으로 적은 문장을 대체할 수 있다는
  주장의 검증 조건이다. 유지되면 성공, 떨어지면 그래프가 그 문장만큼도 못 한 것이다.
- **IN-1 수렴 근거는 이번 범위 밖.** 한 Trace는 한 요청의 경로만 담으므로
  "세 서비스가 모두 Redis를 쓴다"는 `B-9`(후보 N건 수집) 후 여러 Trace 누적에서 나온다.
  여기서 미리 성과를 주장하지 않는다.

## 3. 로그 기록 체계 통합 (앱 계측 — 변경군 A)

한 일은 두 가지입니다.

| | 무엇 | 상태 |
|---|---|---|
| ① | 세 서비스의 **HTTP 요청 로그를 "실패한 것만 남기기"로 통일** | content·chat·**auth(toy-user)** **코드 반영 완료** (미배포) |
| ② | 세 서비스의 **로그 기록 형식 규칙을 문서로 제정** ([logging-format.md](../../../toy-content/docs/observability/logging-format.md)) | 규칙만 제정, **코드 적용은 안 함** |

### ① 요청 로그 통일 — content는 끄고, chat은 켰다

지금까지 서비스마다 제각각이었습니다.

- **content**: 성공한 요청까지 **전부** 로그로 남김 → 1시간에 2,300줄인데 그중
  ERROR/WARN은 8줄. 나머지는 Tempo 트레이스에 이미 있는 정보의 중복
- **chat**: 요청 로그가 **아예 없음** → 401이든 500이든 로그에 한 줄도 안 남음
- **auth (toy-user)**: 요청 로그 없음 + JWT 검증 실패 사유가 빈 catch에 삼켜짐 +
  `RestApiException`이 ControllerAdvice에서 무로그 처리

이걸 하나의 기준으로 맞췄습니다: **실패(4xx·5xx)와 느린 요청(1초 초과)만 남긴다.
성공한 요청은 트레이스가 이미 전부 기록하므로 로그에는 안 남긴다.**

```
[변경 전 content]                          [변경 후 content·chat 공통]
[HTTP] GET /api/feeds 200 - 12ms   INFO    (안 남김 — 트레이스에 있음)
[HTTP] GET /api/users 401 - 3ms    WARN    [HTTP] GET /api/users 401 - 3ms    WARN
[HTTP] POST /api/feeds 500 - 74ms  ERROR   [HTTP] POST /api/feeds 500 - 74ms  ERROR
[HTTP] GET /api/feeds 200 - 1840ms WARN    [HTTP-SLOW] GET /api/feeds 200 - 1840ms WARN
```

실제 코드 변경:

1. content `RequestLoggingFilter` — 성공 요청 INFO 한 줄 **삭제**
2. chat — 같은 필터를 **신설** (chat의 401·500이 처음으로 로그에 잡힘)
3. chat 설정 오타 수정 — `logging.level` 키가 존재하지 않는 패키지(`com.example.chat`)를
   가리켜 **헛돌고 있었음** → `com.example.toychat`으로 정정
4. auth(toy-user) — 같은 필터 **신설** + 무로그 실패 경로 셋 보강:
   JWT 검증 실패 사유(빈 catch → A-0과 동일한 사유별 WARN),
   JwtFilter의 "토큰 유효·사용자 없음" 500 경로,
   ControllerAdvice의 `RestApiException` 무로그·`handleAllException` WARN→ERROR.
   JWT 예외는 필터에서 나므로 ControllerAdvice에 **구조적으로 안 잡힌다**는 확인 포함
   (상세: [jwt-exception-handling-spec.md §7-b](jwt-exception-handling-spec.md) — 통합 필터 A-5는 보류 유지)

### ② 형식 규칙 제정 — 나중에 로그를 JSON으로 바꾸기 위한 준비

지금 로그는 평문이라 스택트레이스가 여러 줄로 찢어져 저장되고, 그래서 §1의 라인 필터
우회가 필요했습니다. 규칙 문서의 핵심은 **"로그 한 건 = JSON 한 줄"로 바꾸면
스택이 traceId와 같은 줄에 담겨 §1 우회 자체가 필요 없어진다**는 것입니다 —
§1 말미의 *"근본 해결은 따로 있습니다"* 가 이것입니다. 다만 **아직 규칙만 있고
코드는 안 바꿨습니다.**

### 성과 — 말할 수 있는 것과 없는 것

**실측된 사실 (지금 말할 수 있는 것):**

| 사실 | 수치 |
|---|---|
| content 로그의 구성비 | 1시간 2,300줄 중 ERROR/WARN **8줄** — 나머지 99.7%가 성공 INFO |
| 그 성공 INFO의 정보 가치 | Tempo(샘플링 1.0)와 **완전 중복** — 지워도 정보 손실은 userId 하나 |
| chat의 관측 공백 | 요청 로그 **0줄** (401·500 포함) — 필터 신설로 실패가 처음 기록됨 |
| 앵커 안전성 | `[HTTP]` INFO에 의존하는 채점 문항 0건 (전수 확인) |

**예측 (배포 후 검증 — 미측정):**

- 요청 로그 적재량 **약 1/287** (2,300줄 → 8줄+α). 실측 구성비에서 산술로 나오는
  예측이고, 배포 후 `count_over_time` 전/후 비교로 확정한다.
- Grafana Cloud Free 한도(로그 50GB/월) 여유 확보, 사람이 Grafana에서 실패만 보게 됨.

**과장 금지 — "토큰을 줄였다"는 그대로 쓰면 틀린다.** 에이전트의 에러 조회는
원래부터 `ERROR|WARN` 라인 필터라 **성공 INFO를 읽지 않았다.** 지운 2,292줄은
대부분 에이전트 컨텍스트에 들어가지도 않던 줄이다. 토큰 효과가 실재하는 경로는
traceId 전량 조회(요청당 `[HTTP]` 1줄 감소)뿐이라 크지 않고, 배포 후에나 잴 수 있다.

**그래서 포트폴리오 서사는 토큰이 아니라 이것이다:**

> 같은 사실이 로그와 트레이스에 이중 기록되고 있었다. **채널별 SoT를 정했다** —
> 성공 요청의 기록은 트레이스(전 요청 샘플링), 실패의 기록은 로그, 집계는 메트릭.
> 그 결과 로그 적재량의 99.7%를 차지하던 중복을 제거하면서 **정보 손실은
> userId 하나로 좁혀 명시했고**(span 태그로 복원 계획), 반대로 실패조차 기록되지
> 않던 서비스(chat)에는 같은 규칙으로 기록을 **추가**했다. 줄인 쪽과 늘린 쪽이
> 같은 원칙("실패와 저속만 로그에")에서 나온다.

### 왜 배포·적용을 미루나

- 이건 앱 쪽 변경(A군)이라, 조사 도구 변경(§1·§2, B군)과 같은 회차에 섞으면
  점수가 움직여도 뭐 덕분인지 못 가립니다. **배포는 회차 경계에서.**
- content의 성공 INFO를 지워도 되는지 확인했습니다 — 채점 앵커에 `[HTTP]` 줄을
  요구하는 문항이 없고, 과거 리포트가 인용한 `[HTTP]` 줄은 전부 500 ERROR라
  변경 후에도 그대로 남습니다.

## 결과

이번 개선은 새로운 데이터를 추가한 것이 아니라 **기존 Loki와 Tempo에 존재하던 관측 데이터를 분석 가능한 형태로 전달하는 것**에 목적을 두었습니다.

```
관측 데이터
        ↓
수집·표현 방식 개선
        ↓
분석 가능한 Evidence 생성
        ↓
LLM 기반 RCA 분석
```

로그에서는 예외 원인과 스택 정보를 분석 컨텍스트까지 전달할 수 있게 되었고, Trace에서는
서비스 간 호출 관계가 엣지 단위 그래프로 컨텍스트와 리포트에 실리게 되었습니다.
둘 다 **점수 효과는 재조사 전이므로 미측정**입니다.

## 하지 않기로 한 것

- **정적 토폴로지 맵을 코드에 넣지 않습니다.** `"Redis는 content·auth·chat이 공유한다"` 를
  박으면 IN-1의 정답을 심는 것이 됩니다. **관측에서 유도하는 것만** 합니다
- **탐색 단계 집계 쿼리에 스택 패턴을 넣지 않습니다**(§1에서 서술한 이유)
- **프롬프트의 토폴로지 문장**(`content → Kafka → chat`)은 그래프 구현과 **같은 날 제거했습니다**
  (2026-07-31, 세 프롬프트 전부). 안 빼면 그래프 덕인지 문장 덕인지 귀속되지 않습니다

## 반증 조건

| 변경 | 개선이 없으면 |
|---|---|
| 로그 스택 수집 | 스택이 도달했는데도 AP-2 가 안 오르면 병목은 신호가 아니라 **추론**이다 |
| Trace 호출 그래프 | AU-4 가 안 오르면 병목은 관계 정보가 아니라 **배치**다 |
| 프롬프트 문장 제거 | **분석** 점수가 떨어지면 그래프가 그 문장만큼도 못 한 것이다. **탐색** 점수가 떨어지면 성질이 다르다 — 탐색은 그래프를 받지 못하므로 대체물 없는 제거였고, 탐색 프롬프트에 한해 문장 복원을 검토한다 (§2 파이프라인 절의 리스크) |
| R1 JSON 전환 (§3) | 전환 후에도 스택이 traceId 쿼리에 안 오면 원인은 줄 분리가 아니라 **수집기(Alloy) 단**이다 |

**주장 범위**: 로그는 *"고쳤고 효과는 아직 재지 않았다"*, Trace 는 *"데이터에 관계 정보가
있는데 읽지 않고 있다는 것을 실측으로 확인하고, 저장된 원본 17개로 추출 규칙을 검증해
두 곳을 고친 뒤, 구현·테스트 박제까지 마쳤다"* 까지입니다. **두 쪽 다 점수 효과는
재조사(AP-2 · AU-4)가 답하며, 그 전에 효과를 주장하지 않습니다.**
