# 트레이스를 1건만 가져오던 수집기를 창 안 N건으로 (B-9)

## 파이프라인 어디의 이야기인가 — 후보 선택이 아니라 자료 수집

**"장애 후보를 여러 개 보낸다"가 아닙니다.** 후보 선택은 그대로 1개이고,
바뀐 것은 그 다음 **자료 수집 단계에서 트레이스 원본을 최대 3건 첨부**한다는 것입니다.

```
[1] 자연어 질문
[2] 시간 구간 추출
[3] 스윕 → 장애 후보 생성 → LLM①이 후보 "하나" 선택        ← 안 바뀜
      ↓  결과물: 좁힌 창 + 대상 서비스 + 대표 traceId 1개
[4] 수집 — 그 좁힌 창의 자료를 모은다                        ← ★ 여기가 바뀜
      로그: 창 전체 조회 (그대로)
      메트릭: 창 전체 조회 (그대로)
      트레이스: 대표 1건만 다운로드  →  창 안에서 최대 3건
[5] LLM② 분석 — [4]에서 모은 것 전부가 컨텍스트로 간다
```

비유하면: 어느 사건을 조사할지 고르는 것은 그대로인데, 그 사건을 조사할 때 지금까지는
**CCTV 한 대** 녹화본만 봤다면 이제 같은 시간대 **최대 세 대**를 보는 것입니다.

추가되는 2건은 어디서 오나 —
① [3]의 스윕이 이미 찾아놨던 트레이스 중 좁힌 창 안의 것(목록은 있었는데 다운로드를 안 했다),
② 그래도 모자라면 **Tempo에 "이 창 안 트레이스 아무거나" 검색을 한 번 더** 던져 채운다
(②가 왜 필요한지는 아래 "무조건 검색" 절).

## 문제 — 정답 근거가 "요청조차 하지 않은" 트레이스에 있었다

```
탐색: 후보 5건 발견 → 복수 유지          (B-20, 7-30에 해결)
         ↓  그중 1건 선정
수집: 선정된 그 1건만 딥 페치            ← 여기가 이번 변경 (B-9)
분석: 트레이스 원본이 1건뿐
```

## 이것 때문에 깎인 것 — AU-2 (감점 24 전량)

탐색이 auth-service로 좁힌 것은 **정답**입니다. 그런데 정답의 **근거**는 같은 창의
content 트레이스에 있었습니다 — *"정상 요청에 auth 호출 span이 없다"* (27 spans 중
Redis GET 4건 · auth 호출 0건, 채점자가 Tempo 직접 쿼리로 실재 확인). 그 트레이스는
선정되지 않았으므로 딥 페치가 안 됐고, **컨텍스트에 0바이트로 도착**했습니다.
리포트는 `trace: 0B / 0 spans`.

같은 결함이 5문항에서 발현됐습니다 (CH-2·AU-2 등 — traceId가 아예 없는 장애 포함).

## 무엇이 바뀌나

수집기가 **좁힌 창 안의 트레이스를 최대 N건**(선정 포함, 기본 3) 딥 페치합니다.

| 파일 | 변경 |
|---|---|
| `collector/Scope.java` | `candidateTraceIds` 필드 추가 — 탐색이 후보를 실어 보낸다 |
| `triage/TriageService.java` | 스윕 히트 중 **좁힌 창 안** 것을 후보로 전달. 신뢰 불가 행(B-15)은 제외 |
| `collector/Collector.java` | 후보 딥 페치 + 자리가 남으면 **창 기준 무조건 검색 `{}`** 로 보충 |
| `collector/CollectedData.java` | `candidateTraceJsons` (traceId → 원본 JSON) |
| `analyzer/ContextAssembler.java` | 컨텍스트에 "창 안 후보 트레이스" 절 — 트레이스별 크기 한도는 기존과 동일 |
| `analyzer/ServiceGraphExtractor.java` | 후보 span까지 합쳐 그래프 추출 — **여러 트레이스의 엣지가 자동 누적**된다 |
| `application.yml` | `rca.collect.max-traces` 기본 3 (`RCA_MAX_TRACES`) |

### 왜 "무조건 검색"이 필요한가

스윕은 error·slow 두 채널로만 찾습니다. 그런데 **AU-2의 정답은 정상 트레이스**입니다 —
에러도 아니고 느리지도 않아서, 이상 채널로는 **원리적으로 절대 후보에 오르지 않습니다**.
그래서 자리가 남으면 상태를 거르지 않는 `{}` 검색으로 창 안 트레이스를 보충합니다.

**서비스로도 거르지 않습니다.** 탐색이 정답 서비스(auth)로 정확히 좁힌 문항에서조차
필요한 트레이스는 **다른 서비스**(content) 것이었습니다 — 창 기준이어야 합니다.

### 부수 효과 둘

- **traceId가 없는 장애**(CH-2류 — 컨슈머 전멸이라 이상 트레이스가 안 만들어짐)에서도
  이제 창 안 트레이스가 근거로 실립니다. 이전에는 트레이스 절이 통째로 비었습니다.
- **호출 그래프 merge가 공짜로 해결됐습니다.** 그래프 추출기(B-28)가 선정+후보 span을
  전부 합쳐 엣지를 만들므로, *"content·auth·chat 셋이 모두 redis로 엣지를 갖는다"* 류의
  다중 트레이스 수렴(IN-1의 전제)이 별도 구현 없이 성립합니다.

## 바꾸지 않은 것

- **v0 직접 traceId 경로는 후보 수집을 하지 않습니다.** baseline 경로를 바꾸면
  두 진입점의 점수 비교가 무너집니다. 후보 수집은 창이 명시된(탐색 경유) 조사에서만.
- 후보 **선별·정렬 고도화는 안 했습니다** — 스윕 후보 우선, 나머지는 검색 응답 순서.
  N을 넘겨 버린 후보는 로그로 남습니다.
- Top-2 조건부 **심층** 수집(B-22)과는 다릅니다 — 그쪽은 2순위 Incident에 대해 로그·메트릭까지
  전부 다시 수집하는 것이고, 이쪽은 트레이스 원본만 더 싣는 것입니다.

## 비용

딥 페치 최대 +2회(수백 ms), 컨텍스트는 후보 트레이스만큼 커집니다(트레이스당 한도는
기존 `max-trace-bytes` 동일 적용). 토큰 증가분은 **미측정**이고, 로그 dedup(B-10)이
상쇄 수단으로 대기열에 있습니다.
