# v0.1 개선 계획 — 측정 기반

5회 블라인드 조사(CH-1 ×2 · CH-2 · IN-2 · AU-2)의 실측치에서 도출한 개선안. **추측이 아니라
감점·비용이 어디서 났는지 숫자로 확인된 것만** 싣는다. 각 항목에는 고치면 무엇이 어떻게
변해야 하는지 **검증 가능한 예측**을 붙였다 — 예측이 빗나가면 그 사실 자체가 다음 단서다.

관련 문서: [채점 대장](scoring/README.md) · [전략](strategy.md) · [STATUS](STATUS.md)

## 실측 기준선 (5회)

| 회차 | in tok | out tok | cost | elapsed | context |
|---|---|---|---|---|---|
| CH-1 회차1 | 44,798 | 9,162 | $1.0845 | 135.4s | 43,387자 |
| CH-1 회차2 | 47,503 | 6,756 | $1.0200 | 101.8s | 49,404자 |
| CH-2 회차1 | 45,935 | **5,083** | $0.9040 | **76.1s** | 45,434자 |
| IN-2 회차1 | 39,202 | 8,266 | $0.9237 | 123.4s | 32,221자 |
| AU-2 회차1 | **65,414** | **14,027** | $0.8357 | **209.2s** | 65,958자 |

**출력 토큰이 품질과 비례하지 않는다.** 최소 출력(CH-2, 5,083 tok / 76.1s)이 최단 시간에
본질 정답에 도달했고, 최대 출력(AU-2, 14,027 tok / 209.2s)도 정답이지만 2.8배를 썼다.
"길게 쓰면 정확하다"는 가정은 이 데이터로 지지되지 않는다.

## 0. 즉시 — 블라인드 오염 차단 (**최우선, 신규 결함**)

**`claude -p`가 레포의 `CLAUDE.md`를 컨텍스트로 읽는다.** `ClaudeCliLlmClient`가
`new ProcessBuilder(...)` 로 CLI를 띄우면 JVM의 작업 디렉터리(레포 루트)를 그대로 물려받고,
Claude Code는 cwd의 프로젝트 지침을 자동 로드한다.

실측 확인 (2026-07-27, 레포 루트에서 `claude -p` 직접 실행):

```
Q: 지금 컨텍스트에 프로젝트 지침 파일이 로드돼 있나? Loki 라벨 관련 사실 하나를 말해봐.
A: 네 — C:\sources\yogurtte-rca-agent\CLAUDE.md 가 로드돼 있습니다.
   Loki(로그)는 service_name 라벨을 쓰고 ... application 라벨은 Loki에 존재하지 않는다.
```

**영향 범위**

| 회차 | 실행일 | 오염 |
|---|---|---|
| CH-1 회차1·2, CH-2, IN-2 | 2026-07-26 | **없음** — `CLAUDE.md` 생성(07-27) 이전 |
| AU-2 회차1 | 2026-07-27 | **있음** |

`CLAUDE.md`에 **문항별 정답은 없다**(auth 다운·Mongo 다운 같은 원인은 어디에도 없다). 그러나
**관측 라벨 스키마와 `errorWarnQuery`의 `logfmt` 결함이 적혀 있다.** AU-2 회차 1에서 에이전트가
Loki 셀렉터 결함을 짚은 것은 자력 진단이 아니라 지침 복창일 수 있다.

→ [AE-05](findings/ae-05-rca-v0-au2-blind-eval.md)의 "자기 결함 진단이 진전했다" 항목은 **무효로
정정한다.** 반면 핵심 결과(메트릭 3계열 동시 단절 → auth 다운, 같은 `/24` 대역 파드로 노드
장애 배제)는 `CLAUDE.md`에 없는 내용이라 **유효하다.**

**수정**: 서브프로세스에 중립 작업 디렉터리를 준다.

```java
// ClaudeCliLlmClient.analyze()
var sandbox = Files.createTempDirectory("rca-cli-");
process = new ProcessBuilder(command, "-p", "--output-format", "json")
        .directory(sandbox.toFile())     // 레포의 CLAUDE.md / .claude/ 를 상속하지 않는다
        .start();
```

시스템 프롬프트는 Java가 읽어 stdin으로 넘기므로 cwd 변경의 영향을 받지 않는다.

> **이 결함은 SKILL.md 구상과 정면으로 충돌한다.** 레포에 스킬을 두면 그것도 같은 경로로
> 새어 들어간다. 개선 수단은 **의도한 통로(시스템 프롬프트 파일) 하나로만** 들어가야 하고,
> 그 통로가 아닌 모든 경로는 막아야 측정이 성립한다. → 3절 참조.

## 1. 정확도 — 감점 원인별

5회에서 실제로 잃은 점수와 놓친 판정의 원인은 전부 **수집 채널**이었다. 모델 추론 실패로
분류할 수 있는 것은 IN-2의 클러스터 ID 오독 1건뿐이다.

### 1-1. Loki 셀렉터 — **5회 연속 로그 0건**

`CollectProperties.java:20-27`이 만드는 쿼리가 두 군데 다 틀렸다.

| 쿼리 | 현재 | 문제 | 수정 |
|---|---|---|---|
| `traceIdQuery` | `{app=~"content\|auth\|chat"} \|= "<traceId>"` | 라벨명·값 둘 다 오류 | env var만으로 해결 |
| `errorWarnQuery` | `{...} \| logfmt \| level=~"ERROR\|WARN"` | 위 + **파싱 단계도 오류** | **코드 수정 필요** |

로그가 ANSI 색코드 섞인 평문 Logback이라(AU-2 소급 채록에서 실물 확인) `| logfmt`로는
`level` 필드가 생기지 않는다. 라인 필터로 바꿔야 한다.

```java
// CollectProperties.java:21
return "{%s=~\"%s\"} |~ \"ERROR|WARN\"".formatted(appLabel, apps);   // logfmt 파이프 제거
```
```bash
# .env
RCA_APP_LABEL=service_name
RCA_APPS=content-service|auth-service|chat-service
```

**예측**: CH-1 회차2 재조사 시 DLQ 재처리 로그 3줄(재처리 시도·실패·성공)이 수집된다 —
그 로그는 당시 수집 창(08:19:31~08:25:35Z) **안에** 실재했다. 영향 판정이 "유실"에서
"DLQ 경유 도착"으로 바뀌고, v2 앵커 기준 근거 경로가 **20 → 30**이 되어야 한다.

### 1-2. metric-queries — 인프라 상태 부재

현재 4개(hikaricp 2종·gc·spring kafka lag) 중 인프라 생사를 보는 건 0개다. 게다가
`kafka_consumer_fetch_manager_records_lag`는 **5회 전부 "no series"** — 소비자가 죽으면 함께
사라지는 앱 메트릭이라 CH-2에서 구조적으로 무용이다(AE-04).

```yaml
rca:
  collect:
    metric-queries:
      - "hikaricp_connections_active"
      - "hikaricp_connections_pending"
      - "rate(jvm_gc_pause_seconds_sum[5m])"
      - "kafka_consumergroup_lag"        # exporter 집계 — 소비자가 죽어도 남는다
      - "kafka_brokers"
      - "mongodb_up"
      - "up"
```

**예측**: IN-2 재조사 시 `kafka_brokers` 시계열 부재가 브로커 다운의 결정타가 되어, 랭킹
1위가 "토픽 부재"에서 "브로커 다운"으로 바뀐다. v2 앵커 기준 근본 원인 **20 → 40**.

### 1-3. 수집 창이 복구를 담지 못한다

AU-2에서 원복은 01:22:24인데 신 파드 첫 스크레이프가 01:25:28 — 창(~01:24:13) **밖 1분 15초**.
에이전트는 "복구되지 않음"으로 판정했고 데이터대로는 옳다.

**"10분 내 미도착" 판정이 채점 요소가 된 이상 창이 복구를 포함해야 한다.** `padding=120s`로는
불가능하다. 두 방법:

- (a) `RCA_WINDOW_PADDING_SECONDS`를 600으로 — 단순하나 컨텍스트가 커진다
- (b) **후행 창을 별도 수집** — 트레이스 종료 + 10분까지의 메트릭/로그만 추가. 컨텍스트
  증가가 작고 판정 목적에 정확히 대응한다. **(b) 권장**

### 1-4. 부재 신호가 "skipped" 한 줄로 끝난다

`Collector`는 시리즈가 없으면 `"...returned no series in this window; skipped."`만 남긴다.
**부재 자체가 단서인데 실패로 표기된다.** 어셈블 컨텍스트에서 부재를 대조군과 함께
제시해야 한다 — "이 쿼리는 A·B에는 시리즈가 있고 C에는 없다".

AU-2·CH-2에서 에이전트가 성공한 경로가 정확히 이 형태(다른 서비스는 연속인데 이 서비스만
끊김)였다. 지금은 그걸 **에이전트가 원본 JSON에서 직접 재구성**하고 있다.

### 1-5. span 절대 시각 미제공 → `-120s` 앵커링

**어셈블러 버그가 아니다**(AE-04 정정, AE-05 참조). `ContextAssembler`가 출력하는 사람이 읽는
절대 시각은 31행 `조회 시간창` **하나뿐**이고 span 시각은 raw ns로 넘어간다. LLM이
"트레이스 시작 = 조회창 시작"으로 앵커링해서 정확히 padding(120s)만큼 밀린다.
5회 중 3회 재발·2회 미재발이라는 비결정성도 코드 버그와 배치된다.

**수정은 "고치기"가 아니라 "추가하기"** — 어셈블 시 span별 절대 시각 표를 함께 넣어 LLM이
추론할 필요를 없앤다.

### 1-6. baseline 창 미제공 (§8.2 입력 패키징 위반)

RUNBOOK §8 절차 1은 "채록 창 + **직전 정상 창**"을 주라고 하는데 v0는 traceId 하나만 받는다.
IN-2 앵커의 "baseline producer span과 대조" 요건이 구조적으로 달성 불가였던 이유다
(v2에서 요건을 뺐지만, 근본 해결은 입력 설계 쪽이다).

`/investigate`에 `baselineTraceId`를 선택 파라미터로 추가하는 것이 최소 변경이다.

## 2. 토큰·비용 — 어디에 쓰이고 있나

### 2-1. 보고된 입력 토큰의 절반 가까이가 **CLI 오버헤드**다

RCA 컨텍스트를 **전혀 주지 않은** 프로브 실행의 실측:

```
in=2  cache_read=20,592  cache_creation=9,393  out=208  cost=$0.1101
→ 합산 입력 29,987 tok
```

`ClaudeCliLlmClient.parse()`가 `input_tokens + cache_read + cache_creation`을 합산하므로
리포트의 `in`에는 **CLI 자체의 시스템 프롬프트·툴 정의·CLAUDE.md가 전부 포함**된다.
AU-2의 in 65,414 중 약 30k가 이것이다.

**따라서 RCA 컨텍스트를 줄이는 것의 레버리지는 보이는 것보다 작다.** 반대로 0절의 cwd
격리는 오염 차단이면서 동시에 **CLAUDE.md 몫의 토큰을 걷어내는** 조치이기도 하다.

### 2-2. 캐시 분해를 기록하지 않아 최적화 여지가 안 보인다

```java
// ClaudeCliLlmClient.java:116-121 — 셋을 합쳐버린다
inputTokens = usage.get("input_tokens").asLong()
        + usage.path("cache_read_input_tokens").asLong(0)
        + usage.path("cache_creation_input_tokens").asLong(0);
```

합산은 총량 회계로는 옳지만(과거 in=2 버그의 수정), **캐시 히트율을 볼 수 없다.**
cache_read는 신규 입력의 약 1/10 비용이라, 회차별 비용 편차($0.8357~$1.0845)가 컨텍스트
크기가 아니라 캐시 히트율에서 왔을 가능성이 크다 — AU-2는 컨텍스트가 가장 큰데 비용이
가장 낮았다.

**수정**: `LlmResult`에 `cacheReadTokens`·`cacheCreationTokens`를 추가해 리포트에 병기.
측정 없이는 캐시 최적화를 논할 수 없다.

### 2-3. 컨텍스트의 75%가 원본 트레이스 JSON이다

AU-2: 컨텍스트 65,958자 중 트레이스 **49,266B**. 65 spans라 span당 약 758B — OTLP 중첩 JSON이
그만큼 장황하다. `maxTraceBytes=102400` 한도에 안 걸려 원본 그대로 들어갔다.

`TraceSpans.topByDuration`이라는 **압축 렌더러가 이미 있는데 한도 초과 시에만 쓴다.**
항상 압축 표(name·start·duration·status·핵심 속성)로 넣으면 정보 손실 없이 큰 폭으로 줄어든다.

**주의**: duration 상위 N개로 **자르는 것**은 위험하다. CH-2·AU-2에서 결정적이었던 신호가
"짧은 span" 또는 "**없는 span**"이었다. 줄일 것은 **표현 형식**이지 span 개수가 아니다.

### 2-4. 출력 토큰 — 상한을 재기 전에 자르지 말 것

CH-2가 5,083 tok으로 최고 효율을 냈고 AU-2는 14,027 tok을 썼다. 다만 AU-2는 트레이스가
무신호라 메트릭에서 추론을 길게 전개해야 했다 — **문항 난이도 차일 수 있다.** 출력 상한을
거는 개선은 **동일 문항 재조사로 품질 변화를 확인한 뒤** 판단한다.

## 3. 프롬프트 개선 — 안전선을 먼저 긋는다

### 통로를 하나로 고정한다

0절에서 확인했듯 개선 수단이 여러 경로로 새면 측정이 무너진다.

| 통로 | 허용 |
|---|---|
| `prompts/system-prompt.md` (Java가 읽어 stdin) | ✅ **유일한 통로** |
| 레포 `CLAUDE.md` | ❌ cwd 격리로 차단 (0절) |
| 레포 `.claude/skills/` | ❌ 같은 이유로 차단 |

**SKILL.md 형태로 개선하려면 그 내용을 시스템 프롬프트 파일에 넣어야 한다.** 스킬 파일을
레포에 두는 방식은 "무엇이 들어갔는지" 통제가 안 되므로 평가용으로 부적합하다.

### 안전한 개선안 (일반 방법론)

문항 정답을 암시하지 않으면서 5회에서 확인된 약점을 겨냥하는 문장들:

- **부재 신호 승격** — "수집 실패·시리즈 부재는 그 자체가 단서다. 어떤 대상의 시계열만
  끊겼다면 **같은 창에서 살아 있는 대상과 함께** 제시하라."
  (근거: CH-2·AU-2에서 성공한 경로가 정확히 이 형태)
- **설정 기본값 대조** — "반복되는 시간값(30.0s, 60s, 3s 등)이 보이면 드라이버·클라이언트
  기본 타임아웃과 대조하라."
  (근거: CH-1 회차2의 `serverSelectionTimeoutMS`, IN-2의 `max.block.ms` — 둘 다 만점 근거)
- **창 경계 명시** — "결론이 수집 창 경계에 걸려 있으면 그 사실을 밝혀라. 창 밖에서
  일어났을 수 있는 일을 단정하지 마라."
  (근거: AU-2의 복구 판정 오판)
- **입력 적합성 검증** — "주어진 traceId가 제보된 증상의 요청이 아닐 수 있다. 다르면
  먼저 밝히고, 무엇을 근거로 삼는지 한정하라."
  (근거: AU-2에서 에이전트가 스스로 한 행동 — 명문화해 재현성을 확보)

### 금지선

- ❌ "DLQ 이후 재처리를 확인하라" — CH-1 정답에 근접
- ❌ "브로커 다운을 토픽 부재보다 먼저 의심하라" — IN-2 정답
- ❌ 특정 서비스·컴포넌트명을 의심 대상으로 지목하는 모든 문장

**판단 기준**: *"이 문장이 우리 문항 세트 밖의 낯선 장애에서도 유용한가?"* 아니면 빼야 한다.

**전체 가설**: 5회의 감점·오판 원인이 전부 수집 채널이었으므로, **프롬프트 튜닝보다 도구
수정의 델타가 크다.** 이 예측이 빗나가면(도구를 고쳤는데 점수가 안 오르면) 병목이 모델
추론 쪽이라는 뜻이고, 그때 프롬프트·에이전틱 루프(v2)로 넘어갈 근거가 생긴다.

## 5. 실행 순서

측정의 자를 먼저 고정하고, 그 다음에 개선한다. 순서를 지키지 않으면 점수 변화가 개선
때문인지 자가 바뀐 탓인지 증명할 수 없다.

```
① 앵커 v2 확정                      ← 완료 (2026-07-27)
② 오염 차단 (0절 cwd 격리)          ← 이것부터. 안 하면 이후 측정이 전부 무효
③ v0 + v2앵커로 baseline 재측정      ← 5개 traceId 재조사, 새 자로 잰 기준점
④ 도구 수정 (1절) → 재조사 → 델타
⑤ 프롬프트 개선 (3절) → 재조사 → 델타
```

②와 ③ 사이를 붙여야 한다 — ②가 토큰·컨텍스트를 바꾸므로, ③의 baseline은 ② 이후에 재야
④의 델타가 순수해진다.
